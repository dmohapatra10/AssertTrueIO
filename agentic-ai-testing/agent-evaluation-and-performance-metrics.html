Agent Evaluation and Performance Metrics

Beginner 8 min read

Prerequisites: Testing Agent Recovery

What is this?

This page brings together every check from this chapter's earlier pages — plan quality, tool accuracy, memory usage, state accuracy, recovery — into one genuine scorecard, tracked across many runs the same way Chapter 11 tracked LLM output quality.

A Genuine Agent Scorecard

def compute_agent_scorecard(run_reports):
    from statistics import mean
    scorecard = {
        "plan_quality_pass_rate": mean(
            1 if r["plan_check"]["passed"] else 0 for r in run_reports),
        "tool_selection_accuracy": mean(
            r["tool_selection_correct_pct"] for r in run_reports),
        "tool_parameter_accuracy": mean(
            r["tool_parameter_correct_pct"] for r in run_reports),
        "memory_effective_rate": mean(
            1 if r["memory_check"]["influenced_behavior"] else 0
            for r in run_reports),
        "state_accuracy_rate": mean(
            1 if r["state_check"]["state_accurate"] else 0
            for r in run_reports),
        "recovery_success_rate": mean(
            1 if r["recovery_check"]["recovered"] else 0
            for r in run_reports),
        "avg_steps_per_task": mean(r["steps_taken"] for r in run_reports),
    }
    return scorecard

Why Per-Dimension, Not a Single Blended "Agent Quality" Score

This is DIRECTLY Chapter 11's OWN argument, now applied to
agent architecture instead of LLM response quality:

A blended "87% agent quality" score could HIDE that
recovery_success_rate is a genuinely CONCERNING 40%, while
tool_selection_accuracy sits at a GENUINELY solid 98% —
AVERAGING these together produces a NUMBER that looks
REASONABLE while COMPLETELY OBSCURING the SPECIFIC, SERIOUS
weakness (recovery) that ACTUALLY needs real attention.

A Genuine Scorecard Revealing a Real Priority

{
  "plan_quality_pass_rate": 0.96,
  "tool_selection_accuracy": 0.98,
  "tool_parameter_accuracy": 0.94,
  "memory_effective_rate": 0.91,
  "state_accuracy_rate": 0.89,
  "recovery_success_rate": 0.42,  # GENUINELY concerning
  "avg_steps_per_task": 5.2,
}

FIVE dimensions genuinely strong. ONE — recovery — genuinely
weak, and it's PRECISELY the dimension Testing Agent Recovery
argued matters MOST for real-world reliability, since
happy-path success alone (which the OTHER five dimensions
largely reflect) doesn't predict how an agent handles GENUINE,
real-world surprises.

🧠 Think About It

Why might this page's example scorecard — five strong dimensions, one weak — be a genuinely realistic, common pattern for agents in practice, rather than an artificially constructed example? An agent's core execution logic (planning, tool use, memory, state) tends to be exercised heavily during normal development and happy-path testing, naturally getting refined through that repeated use. Recovery from genuinely unexpected obstacles is exercised far less often during ordinary development — exactly Testing Agent Recovery's own point about needing deliberate, injected testing rather than relying on natural occurrence — making it a genuinely plausible, realistic dimension to lag behind the others in practice, not just a contrived example.

⚠️ Common Mistake

Reporting a single, blended "agent quality" percentage that averages across every dimension this chapter has covered. This page's own example shows exactly how this can hide a genuinely serious, specific weakness — recovery — behind an overall number that looks reassuring.

💡 Quick Tip

Tracking this scorecard over time — the same way Chapter 7 tracked performance trends and Chapter 11 tracked LLM quality trends — lets a team see whether a specific dimension is improving, stable, or degrading after changes to the agent's prompt, tools, or architecture, not just its current snapshot.

Best Practices

  • Report agent quality per dimension — planning, tool selection, tool parameters, memory, state, recovery — never as one blended score.
  • Treat a genuinely weak dimension as the priority for improvement, even when every other dimension looks strong.
  • Track this scorecard over time to catch dimension-specific trends, not just a single, current-moment snapshot.

🎯 Key Takeaway

  • A genuine agent scorecard combines every check from this chapter's earlier pages into per-dimension metrics, never a single blended score.
  • Recovery is a genuinely plausible dimension to lag behind others in practice, since it's exercised far less during ordinary development than core execution logic.
  • This page closes the chapter the same way Chapter 11 closed its own — honest, distribution-and-dimension-aware measurement over a single reassuring number.

Why does this page argue recovery is "a genuinely plausible dimension to lag behind others," rather than assuming all six dimensions should naturally develop at a similar pace?▾

The OTHER five dimensions get GENUINELY exercised repeatedly during ORDINARY development and happy-path testing, naturally IMPROVING through that REPEATED use — recovery, per the PREVIOUS page's OWN argument, requires DELIBERATE, INJECTED testing to be exercised AT ALL, meaning it GENUINELY has FEWER natural opportunities to improve without SPECIFIC, deliberate attention.

Why PLANNING, TOOL USE, MEMORY, and STATE naturally get
EXERCISED and REFINED during ORDINARY development:
EVERY SINGLE happy-path test run EXERCISES planning, tool
  selection, memory, and state TRACKING — REPEATED use
  NATURALLY surfaces and helps FIX problems in THESE
  dimensions, even WITHOUT dimension-SPECIFIC testing
  DELIBERATELY targeting them.

Why RECOVERY specifically DOESN'T get this SAME natural
exercise:
Per Testing Agent Recovery's OWN argument, GENUINE obstacles
  occur RARELY and UNPREDICTABLY during ORDINARY testing — a
  team COULD run HUNDREDS of happy-path tests WITHOUT EVER
  GENUINELY exercising recovery AT ALL, meaning this DIMENSION
  specifically DOESN'T benefit from the SAME kind of NATURAL,
  REPEATED refinement the OTHER five dimensions get FOR FREE.

This is a GENUINELY useful, practical insight connecting THIS page directly back to the PREVIOUS one — recovery's tendency to LAG isn't a COINCIDENCE, it's a DIRECT, LOGICAL consequence of the SAME testing-reliability gap Testing Agent Recovery identified, now showing up CONCRETELY in this page's OWN scorecard metrics.

Explain why tracking this scorecard OVER TIME matters, using a concrete scenario where a single, current snapshot would genuinely mislead a team.▾

A single SNAPSHOT can't distinguish "this dimension has ALWAYS been at THIS level" from "this dimension USED to be BETTER and is NOW GENUINELY DEGRADING" — a GENUINELY important distinction for deciding WHETHER a recent change caused a REAL regression.

A GENUINELY misleading single-SNAPSHOT scenario:
Team checks the scorecard TODAY: tool_parameter_accuracy is
  94% — LOOKS genuinely fine in ISOLATION. But WITHOUT
  historical TRACKING, there's NO way to know this SAME metric
  was 99% LAST MONTH, BEFORE a recent TOOL DEFINITION change —
  a GENUINE, real REGRESSION that a SINGLE snapshot COMPLETELY
  hides.

What TRACKING OVER TIME (this page's OWN "Quick Tip") would
REVEAL instead:
A CLEAR, VISIBLE DOWNWARD trend in tool_parameter_accuracy,
  CORRELATING with the TIMING of a RECENT tool definition
  change — DIRECTLY actionable evidence of a REGRESSION,
  EXACTLY the kind of finding a SINGLE, CURRENT-moment
  snapshot could NEVER reveal on its OWN.

This directly reuses Chapter 7's OWN trend-detection argument — SOME regressions are ONLY visible as a TREND across MULTIPLE measurements over TIME, NEVER from ANY SINGLE snapshot ALONE, REGARDLESS of how CAREFULLY that ONE snapshot is examined.

Why might avg_steps_per_task be a genuinely useful metric to track ALONGSIDE the pass/fail-style rates, rather than just another dimension score?▾

This connects DIRECTLY to Chapter 12's OWN opening page — a RISING step count, even WITHOUT any dimension's PASS rate dropping, is EXACTLY the kind of signal that page argued deserves INVESTIGATION even when the SURFACE-level "success" outcome looks UNCHANGED.

Why avg_steps_per_task GENUINELY adds something the OTHER
metrics MISS:
An agent could MAINTAIN a PERFECT 100% success rate across
  EVERY dimension while GRADUALLY taking MORE steps to
  ACCOMPLISH the SAME tasks OVER TIME — EXACTLY the kind of
  "technically PASSING but GENUINELY concerning" pattern Why
  AI Agents Need Testing warned COULD hide BEHIND a clean-
  looking SUCCESS report.

What a RISING avg_steps_per_task might GENUINELY indicate:
INCREASING reliance on RETRIES, GENUINELY GROWING inefficiency
  in REASONING, or a SUBTLE, GRADUAL DEGRADATION in SOME
  underlying CAPABILITY that HASN'T YET crossed the THRESHOLD
  to cause an OUTRIGHT FAILURE in any SINGLE dimension's PASS
  rate — WORTH catching EARLY, before it EVENTUALLY does.

This is a GENUINELY valuable, COMPLEMENTARY metric — it catches a DIFFERENT KIND of degradation (GROWING inefficiency) than the PASS-rate-style metrics are DESIGNED to catch (OUTRIGHT failures), EXACTLY the kind of "look BEYOND simple pass/fail" principle THIS entire chapter (and COURSE) has consistently argued for.
