Connecting an AI Agent with Playwright

Beginner 9 min read

Prerequisites: AI + Playwright overview

What is this?

Chapter 3's agent had exactly three tools — enough for a simple login check. Exploring ShopEasy's search and product pages genuinely needs more: searching, reading structured results, scrolling, and filtering. This page extends that same toolkit, not replaces it.

A Genuinely Fuller Toolkit

# tools.py — extending Chapter 3's original three

def search(page, query):
    page.get_by_placeholder("Search products...").fill(query)
    page.keyboard.press("Enter")
    return f"Searched for '{query}'"

def get_search_results(page):
    # returns STRUCTURED data, not just raw page text — a
    # genuinely important upgrade covered later on this page
    results = page.locator("[data-testid='product-card']").all()
    return [
        {
            "name": r.locator("[data-testid='product-name']").inner_text(),
            "price": r.locator("[data-testid='product-price']").inner_text(),
            "in_stock": "Out of stock" not in r.inner_text(),
        }
        for r in results
    ]

def apply_filter(page, filter_name, value):
    page.get_by_role("button", name=filter_name).click()
    page.get_by_role("option", name=value).click()
    return f"Applied filter: {filter_name} = {value}"

def scroll_to_bottom(page):
    page.mouse.wheel(0, 10000)
    return "Scrolled to bottom of the page"

Why Structured Results Beat Raw Page Text

❌ get_page_text() (Chapter 3's original, general-purpose tool):
  Returns EVERYTHING as one long string — product names, prices,
  navigation menu text, footer links, all mixed together. The
  reasoner has to PARSE this itself from unstructured text,
  genuinely error-prone for anything beyond a quick glance.

✅ get_search_results() (this page's new, structured tool):
  Returns a genuine LIST of objects, each with clearly labeled
  name, price, and stock status. The reasoner can work with
  this directly — "are any of these out of stock" is now a
  simple, reliable check instead of a text-parsing exercise.

This connects directly to Chapter 2's Reasoning page — reducing irrelevant detail and structuring what the reasoner actually receives genuinely improves decision quality, not just convenience.

Registering the New Tools

TOOL_DEFINITIONS = [
    # ...Chapter 3's original three, unchanged...
    {"name": "search",
     "description": "Searches for products using the search box.",
     "input_schema": {"type": "object",
        "properties": {"query": {"type": "string"}},
        "required": ["query"]}},
    {"name": "get_search_results",
     "description": "Returns structured data (name, price, stock status) for all currently visible search results.",
     "input_schema": {"type": "object", "properties": {}}},
    {"name": "apply_filter",
     "description": "Applies a filter (e.g. price range, category) to search results.",
     "input_schema": {"type": "object",
        "properties": {"filter_name": {"type": "string"}, "value": {"type": "string"}},
        "required": ["filter_name", "value"]}},
]

🧠 Think About It

Why might adding get_search_results() as a genuinely new, structured tool be better than simply asking the reasoner to "parse the results out of the page text yourself" using the existing get_page_text tool? Every additional parsing responsibility placed on the reasoner is one more place a genuine reasoning error could occur — misreading a price, missing a product buried in unrelated text. A dedicated, structured tool moves that parsing into reliable, deterministic code (exactly Chapter 2's tools-should-be-deterministic principle), leaving the reasoner to work with clean, already-correct data instead.

⚠️ Common Mistake

Adding browser tools reactively, one at a time, only once the agent gets visibly stuck without one. This page's tools were chosen deliberately, based on what the search-and-filter flow genuinely needs — a more thoughtful upfront design tends to produce a cleaner, more reliable toolkit than patching gaps discovered through repeated trial and error.

💡 Quick Tip

When a tool returns structured data (like get_search_results's list of dictionaries), it still needs to become TEXT before it can go into the LLM prompt — a simple, readable format (like one line per result) is usually more effective than raw, dense JSON for the reasoner to work with directly.

Best Practices

  • Design a task's toolkit deliberately upfront, based on the genuine needs of the actual flow, rather than reactively patching gaps as they appear.
  • Prefer structured tool outputs over raw text whenever a tool's result has genuine internal structure worth preserving.
  • Keep new tools narrow and specific, exactly matching Chapter 2's safety reasoning — apply_filter does one thing, not "any possible page interaction."

🎯 Key Takeaway

  • A richer task genuinely needs a richer toolkit — this page extends Chapter 3's foundation rather than replacing it.
  • Structured tool outputs reduce the reasoner's parsing burden and reduce a real category of reasoning error.
  • New tools should be designed deliberately for a task's actual needs, staying narrow and specific rather than reactively patched together.

Interview Questions

A teammate suggests just using get_page_text() for everything, arguing "the LLM is smart enough to parse results out of raw text." What would you say, using this page's own reasoning?▾

I'd point out this isn't really about whether the LLM is "smart enough" — it's about where parsing responsibility should genuinely live, and Chapter 2 already established that deterministic code is more reliable than LLM reasoning for exactly this kind of mechanical extraction task.

What relying on raw text parsing genuinely risks:
The LLM might correctly parse 9 out of 10 product prices from
  a long, messy page-text string, but misread the 10th — not
  because it's "not smart enough," but because text parsing
  from unstructured content is inherently more error-prone
  than reading pre-structured data, regardless of capability.

What the structured tool guarantees:
get_search_results() ALWAYS correctly separates name, price,
  and stock status — this is ORDINARY, deterministic Playwright
  code doing exactly what it's told, with no room for the kind
  of subtle misreading raw-text parsing could introduce.

The argument isn't "the LLM can't do this" — it's "why make the LLM do unreliable work that deterministic code can do reliably instead," directly following Chapter 2's Anatomy page distinction between what belongs in reasoning versus what belongs in tools.

Why does apply_filter take both a filter_name and a value parameter, rather than being several separate tools like filter_by_price and filter_by_category?▾

This is a genuine, reasonable design trade-off — a single, parameterized tool versus several narrow ones — and the right choice depends on whether the underlying ACTION is genuinely the same mechanism, just with different inputs, or genuinely different mechanisms.

Why ONE parameterized tool is reasonable here:
Applying a price filter and applying a category filter likely
  use the SAME underlying UI pattern on ShopEasy (click a
  filter button, select an option) — the ACTION is genuinely
  the same shape, just with different button/option TEXT.
  One tool with two parameters cleanly captures this.

When SEPARATE tools would make more sense instead:
If price filtering and category filtering used GENUINELY
  different UI patterns (a slider for price, a checkbox list
  for category), separate tools would better reflect that
  real difference, rather than forcing genuinely different
  mechanisms into one artificially generic interface.

The general principle, consistent with Chapter 2's tool-design guidance: tool boundaries should reflect genuine differences in the underlying mechanism, not just differences in what's being filtered — same mechanism, different inputs, reasonably becomes one parameterized tool.

Explain why this page's get_search_results specifically checks for the text "Out of stock" to determine in_stock status, and what risk this specific implementation choice carries.▾

This is a genuinely pragmatic implementation — checking for specific text is simple and often reliable — but it carries a real, concrete risk worth naming explicitly: it depends entirely on that exact text staying stable in the real application.

The real risk, concretely:
If ShopEasy's actual wording changes from "Out of stock" to
  "Currently unavailable" (a genuinely plausible copy change
  a content team might make), this tool would SILENTLY start
  reporting EVERY product as in_stock: true — a real, serious
  bug that wouldn't throw an error, just quietly produce
  wrong data from that point forward.

A more ROBUST alternative worth considering:
Checking for a dedicated data attribute or ARIA state
  specifically meant for this purpose (like a
  data-testid="out-of-stock-badge" or aria-disabled attribute
  on the Add to Cart button) — genuinely more resilient to
  wording changes than matching specific display text.

This is a real, honest trade-off worth naming rather than glossing over — text-matching is simple to implement but fragile to exactly the kind of copy change that happens routinely in a real, actively-maintained application.

Why might scroll_to_bottom be a genuinely useful tool specifically for a search-results page, beyond just "sometimes you need to scroll"?▾

Many real search-results pages use lazy loading or infinite scroll, where additional results only load once a user scrolls near the bottom — without this tool, an agent's get_search_results() call might only see the first, initially-visible batch, silently missing later results.

A genuinely realistic scenario this tool addresses:
ShopEasy's search returns 40 matching products, but only the
  FIRST 12 are rendered until the user scrolls down, at which
  point more load dynamically. An agent that calls
  get_search_results() WITHOUT first scrolling would only see
  12 of the 40 genuinely matching products — not because
  anything is broken, but because it never triggered the
  lazy-loading behavior real users experience naturally.

With scroll_to_bottom available as an explicit tool:
The agent can deliberately trigger this loading behavior
  before reading results, getting a genuinely complete picture
  rather than an artificially incomplete one.

This is a good example of a tool that exists specifically because of how the REAL application actually behaves, not because of some general, abstract browser-automation principle — good tool design genuinely depends on understanding the real target application's actual behavior.

How would you decide whether a new browser interaction genuinely needs its own new tool, versus being achievable with this page's existing toolkit?▾

The genuinely useful test: can an EXISTING tool, used as designed, actually accomplish the new interaction, or does it require a fundamentally different UI interaction pattern the current tools don't cover at all?

Example that DOESN'T need a new tool:
"Search for a specific product" — the EXISTING search() tool
  already covers this exactly, regardless of what specific
  query string is passed in — no new tool needed, just a call
  to the existing one with different input.

Example that GENUINELY needs a new tool:
"Add a product to the wishlist" — this is a FUNDAMENTALLY
  different interaction (likely a distinct button, a different
  part of the page, different resulting state) that none of
  this page's existing tools (search, filter, scroll, read
  results) can accomplish — a genuinely new capability,
  needing its own new, narrow tool definition.

The test isn't "does this feel like a new feature" — it's specifically "can an existing tool's actual mechanism accomplish this," which keeps the toolkit growing deliberately around genuine new capabilities, rather than either needlessly duplicating existing tools or trying to force a fundamentally different interaction into an ill-fitting existing one.
