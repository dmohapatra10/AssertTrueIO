AI Agent + MCP

Beginner 9 min read

Prerequisites: MCP + API Testing

What is this?

This chapter's synthesis: taking Chapter 3's actual QAAgent and connecting it to an MCP server instead of its original hardcoded execute_tool function. The genuinely interesting part is how little of Chapter 3's architecture actually needs to change.

What Changes — the Tool-Calling Layer

# Chapter 3's ORIGINAL execute_tool:
def execute_tool(tool_name, tool_input, page):
    if tool_name == "click_element":
        return find_and_click(page, tool_input["role"], tool_input["name"])
    elif tool_name == "fill_field":
        return fill_field(page, tool_input["label"], tool_input["value"])
    # ... hardcoded, one branch per tool ...

# The MCP-connected VERSION:
from mcp import ClientSession
from mcp.client.stdio import stdio_client

async def execute_tool_via_mcp(session: ClientSession, tool_name, tool_input):
    result = await session.call_tool(tool_name, tool_input)
    return result.content

Notice what genuinely happened here: the hardcoded if/elif chain became a single, generic call — the MCP client doesn't need to know WHICH tools exist in advance; it discovers and calls them through the protocol.

What Doesn't Change — the Reasoning Loop Itself

# Chapter 3's run() loop structure is GENUINELY unchanged:
async def run(self, session: ClientSession, page):
    history = []
    for step in range(self.max_steps):
        prompt = self._build_prompt(history, page)
        response = self.client.messages.create(
            model=self.model, max_tokens=1024,
            system=self.instructions,
            tools=await self._get_mcp_tool_definitions(session),
            messages=[{"role": "user", "content": prompt}]
        )
        if self._is_task_complete(response):
            return self._build_report(history, success=True)

        tool_call = self._extract_tool_call(response)
        result = await execute_tool_via_mcp(session, tool_call.name, tool_call.input)
        history.append({"step": step, "action": tool_call, "result": result})
    return self._build_report(history, success=False)

This is genuinely still Chapter 3's own loop — reason, act, observe, repeat. The ONLY structural change is HOW tool definitions are obtained (_get_mcp_tool_definitions now asks the MCP server, rather than reading a hardcoded Python list) and HOW a tool call actually executes.

🧠 Think About It

Why is it genuinely significant that Chapter 3's reasoning loop needed almost no changes to work with MCP? This confirms something this chapter has argued since its opening page — MCP standardizes the tool-calling BOUNDARY, not the reasoning architecture around it. An agent's core capability (planning, deciding, observing results, adapting) is genuinely independent of whether tools are called through a hardcoded dispatch function or a standardized protocol. If the reasoning loop HAD needed substantial rework, that would suggest MCP was actually a different architecture, not a standardized version of the same one.

⚠️ Common Mistake

Assuming that adopting MCP requires rearchitecting an agent's reasoning logic from scratch. This page's own comparison shows the reasoning loop stays genuinely the same — only the tool-discovery and tool-execution mechanisms change, exactly because MCP standardizes that specific boundary, not the reasoning above it.

💡 Quick Tip

When migrating an existing hardcoded-tool agent to MCP, a genuinely useful first step is running the SAME test suite from Chapter 12 against both versions — the MCP-connected agent should pass the identical plan-quality, tool-selection, and recovery tests, confirming the migration preserved behavior rather than accidentally changing it.

Best Practices

  • Expect an agent's core reasoning loop to remain largely unchanged when migrating to MCP — only the tool-discovery and execution layer should genuinely need rework.
  • Reuse Chapter 12's own testing techniques to confirm a migration preserves an agent's actual behavior, not just its ability to run.
  • Treat MCP adoption as a boundary change, not a full architectural rewrite.

🎯 Key Takeaway

  • Connecting Chapter 3's agent to MCP changes how tools are discovered and called, but leaves its core reasoning loop genuinely unchanged.
  • This confirms MCP's real role — standardizing the tool-calling boundary, not replacing the reasoning architecture around it.
  • Chapter 12's own agent-testing techniques remain directly applicable to verify an MCP migration preserved correct behavior.

Why might the async/await syntax appearing in this page's MCP-connected code be a GENUINELY necessary change, even though it's NOT mentioned as PART of the "reasoning loop stays the SAME" argument?▾

This is a GENUINELY real, if somewhat MECHANICAL, change — MCP's ACTUAL communication happens OVER a REAL protocol (JSON-RPC, typically over STDIO or HTTP), which INVOLVES genuine I/O and TYPICALLY uses ASYNCHRONOUS patterns in PYTHON, unlike Chapter 3's ORIGINAL, SYNCHRONOUS, IN-PROCESS function CALLS.

Why Chapter 3's ORIGINAL execute_tool didn't NEED async:
DIRECT, IN-PROCESS Python function CALLS (find_and_click,
  fill_field) execute SYNCHRONOUSLY and IMMEDIATELY — no
  GENUINE network or INTER-process COMMUNICATION involved AT
  ALL.

Why the MCP VERSION genuinely NEEDS async:
session.call_tool() INVOLVES REAL communication ACROSS a
  PROTOCOL boundary (POTENTIALLY a SEPARATE PROCESS, or EVEN
  a NETWORK connection) — this KIND of I/O is TYPICALLY
  handled ASYNCHRONOUSLY in Python, EXPLAINING the AWAIT
  keywords THROUGHOUT this PAGE'S MCP-connected code that
  WEREN'T present in Chapter 3's ORIGINAL, SIMPLER version.

This is a GENUINELY real, PRACTICAL implementation DETAIL worth NAMING explicitly — it DOESN'T contradict this PAGE'S "reasoning LOOP stays the SAME" argument (the LOOP'S STRUCTURE and LOGIC ARE unchanged), but it IS a REAL, mechanical ADAPTATION needed BECAUSE tool CALLS now GENUINELY cross a PROTOCOL boundary RATHER than being SIMPLE, DIRECT function CALLS.

How would you extend this page's migrated agent to gracefully handle an MCP server BECOMING unavailable mid-run, connecting to Chapter 12's OWN recovery-testing PRINCIPLES?▾

This is GENUINELY a NEW kind of OBSTACLE Chapter 12's ORIGINAL recovery TESTING didn't SPECIFICALLY anticipate (a MODAL, not a PROTOCOL disconnection) — but the SAME underlying PRINCIPLE (test DELIBERATE, injected FAILURES, don't WAIT for them to occur NATURALLY) applies DIRECTLY.

async def run_with_mcp_resilience(self, session, page):
    try:
        return await self.run(session, page)
    except ConnectionError as e:
        # A GENUINE, honest failure REPORT — exactly Chapter 8's
        # OWN failure-report PRINCIPLE, applied HERE to an MCP-
        # SPECIFIC failure MODE
        return {
            "success": False,
            "summary": (f"MCP server connection LOST mid-run: "
                        f"{e}. UNABLE to complete the OBJECTIVE "
                        f"due to a PROTOCOL-level failure, NOT "
                        f"an application OR reasoning issue."),
            "classification": "mcp_connection_failure",  # EXPLICITLY
                # distinguished from Chapter 8's OWN SIX failure
                # categories — a GENUINELY new, INFRASTRUCTURE-level
                # category THIS chapter's MCP integration INTRODUCES
        }

This EXTENDS Chapter 12's OWN "DELIBERATELY inject REAL obstacles" testing PHILOSOPHY to a GENUINELY new FAILURE mode this CHAPTER'S OWN MCP integration INTRODUCES — a TEST would DELIBERATELY kill the MCP SERVER process MID-run and CONFIRM the agent PRODUCES this KIND of HONEST, INFORMATIVE failure REPORT rather than HANGING indefinitely OR producing a CONFUSING, UNEXPLAINED error, EXACTLY the SAME "FAIL gracefully and HONESTLY" standard Chapter 12's OWN recovery testing ESTABLISHED, now APPLIED to a RISK that's SPECIFICALLY introduced by THIS chapter's OWN MCP ARCHITECTURE.
