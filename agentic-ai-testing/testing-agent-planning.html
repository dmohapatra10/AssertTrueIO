Testing Agent Planning

Beginner 9 min read

Prerequisites: Why AI Agents Need Testing

What is this?

Chapter 2's Agent Planning page taught what a genuinely good plan looks like — rough, goal-oriented, appropriately unspecific. This page is about verifying an agent's ACTUAL plan against that standard, before a single action ever executes.

A Genuine Plan-Level Check

GOAL: "Verify that a user with valid credentials can log into
ShopEasy, ending up on their account dashboard."

The agent's OWN generated plan (captured BEFORE execution
begins — this requires the agent to expose its plan as a
distinct, inspectable step, not bury it inside execution):
  1. Navigate to the login page
  2. Fill in valid credentials
  3. Submit the login form
  4. Confirm the dashboard is reached

def evaluate_plan_quality(goal, plan, client):
    prompt = f"""Given this goal and this agent's generated
plan, assess: does the plan genuinely address the STATED goal?
Is it appropriately ROUGH (goal-oriented steps) rather than
overly specific (exact selectors, exact values)? Does it
include a genuine way to CONFIRM the goal's success condition
was actually met?

Goal: {goal}
Plan: {plan}"""
    result = client.messages.create(
        model="claude-sonnet-4-6", max_tokens=300,
        messages=[{"role": "user", "content": prompt}]
    )
    return result.content[0].text

A Genuine Plan-Level Failure This Would Catch

A DIFFERENT, WORSE plan for the SAME goal:
  1. Navigate to the login page
  2. Fill in valid credentials
  3. Submit the login form

Structurally REASONABLE-looking — but comparing against the
GOAL directly reveals a genuine gap: the goal explicitly says
"ending up on their account dashboard," and this plan has NO
step confirming that outcome at all. The agent might
TECHNICALLY complete steps 1-3 and call the task done, without
EVER actually verifying the dashboard was reached — exactly
the kind of plan-level gap worth catching BEFORE execution,
not discovered only after a genuinely incomplete run.

🧠 Think About It

Why does catching this specific gap BEFORE execution matter more than catching it AFTER, given that Chapter 3's loop would presumably still eventually reach some kind of conclusion? A plan missing an explicit success-confirmation step doesn't necessarily cause an obvious, visible failure — the agent might simply report "TASK COMPLETE" after step 3, having technically done everything its (flawed) plan specified, without ever genuinely confirming the goal's actual success condition. This produces a false-positive "success" report, exactly the kind of unsound-but-passing result the previous page warned about — catching the gap at the PLAN level, before execution, prevents this specific false confidence from ever being generated in the first place.

⚠️ Common Mistake

Only ever evaluating an agent by its final outcome, never by examining the plan it generated before acting on it. This page's own example shows a plan-level gap that could produce a false "success" — catching this requires looking at the plan itself, not just waiting to see what happens when the agent executes it.

💡 Quick Tip

For plan-quality evaluation to be possible at all, an agent's architecture needs to expose its plan as a genuinely separate, inspectable artifact — if planning and execution are fully entangled in code with no distinct checkpoint, there's nothing concrete to evaluate before execution begins.

Best Practices

  • Evaluate an agent's plan against its stated goal before execution, not only the final outcome after the fact.
  • Check specifically that a plan includes a genuine way to confirm the goal's actual success condition, not just its mechanical steps.
  • Design agent architectures to expose planning as a distinct, inspectable step, making this kind of pre-execution evaluation genuinely possible.

🎯 Key Takeaway

  • Plan-level testing checks an agent's generated plan against its actual goal before any execution happens, catching gaps that could otherwise produce false "success" reports.
  • A structurally reasonable-looking plan can still be missing a genuine confirmation step for the goal's actual success condition.
  • This kind of testing requires an agent architecture that exposes planning as a distinct, evaluable step, not buried entirely inside execution.

🛠️ Try It Yourself

Write a plan for the goal "verify a user can successfully apply a valid discount code at checkout" that has a genuine, different gap than this page's missing-confirmation example — then write the corrected version, and explain specifically what evaluate_plan_quality should flag about the original.

Interview Questions

A reviewer says "the agent's plan looks fine to me — three reasonable, sequential steps." Using this page's example, what specifically might they be missing?▾

They're likely evaluating whether each individual step looks reasonable in isolation, without checking the plan AS A WHOLE against the goal's full, stated success condition — exactly the gap this page's own three-step example demonstrates.

What "three reasonable steps" superficially LOOKS like:
Navigate, fill credentials, submit — each INDIVIDUAL step is
  genuinely sensible and well-formed on its own.

What this SURFACE-LEVEL review MISSES:
The GOAL explicitly states "ending up on their account
  dashboard" as PART of what success means — and NONE of the
  three steps actually CONFIRMS this happened. The plan is
  INTERNALLY coherent while being INCOMPLETE relative to the
  ACTUAL goal it was supposed to address.

The fix for the reviewer's own process: don't just ask "does each step make sense" — ask "does the FULL SET of steps, together, genuinely address EVERY part of the stated goal," exactly the comparison this page's evaluate_plan_quality function is specifically designed to make.

Why does this page argue that a missing confirmation step is worse than it might initially seem, connecting to the previous page's discussion?▾

This connects directly to the previous page's core concern — a plan missing its confirmation step doesn't just produce an INCOMPLETE run, it can produce a FALSE "success" report, exactly the unsound-but-passing outcome that page warned creates dangerous, false confidence.

Why this ISN'T just "a minor gap in thoroughness":
Without a CONFIRMATION step, the agent might complete steps 1-3,
  observe NOTHING contradicting success, and REPORT "TASK
  COMPLETE" — even if the LOGIN actually FAILED silently
  (perhaps redirecting back to the login page with a subtle
  error the agent never explicitly CHECKED for, since its plan
  never told it to look).

Why this is EXACTLY the previous page's concern, made concrete:
A "successful"-LOOKING report, built on a plan that never
  actually VERIFIED the goal's real success condition, is
  PRECISELY the "correct-looking outcome, unsound process"
  pattern the previous page argued is genuinely MORE dangerous
  than an honest, visible failure.

This is a deliberate, direct continuation — plan-level testing (this page) is specifically valuable because it can catch, BEFORE execution, exactly the kind of gap that would otherwise produce the false-confidence problem the previous page introduced conceptually.

Explain why this page insists the agent's plan needs to be "exposed as a genuinely separate, inspectable artifact" — isn't the FINAL result enough to evaluate?▾

The final result alone can't reveal a PLAN-LEVEL gap the way this page's own example shows — by the time you HAVE a final result, the flawed plan has ALREADY potentially produced a false-positive "success," which is exactly the outcome you wanted to CATCH before it happened, not diagnose after the fact.

What evaluating ONLY the final result can tell you:
Whether THIS SPECIFIC RUN happened to produce a correct-
  looking outcome — but by DEFINITION, this is AFTER the plan
  has ALREADY been used to guide execution, meaning any
  PLAN-LEVEL flaw has ALREADY had its chance to cause a
  problem (like a false-positive "success").

What evaluating the PLAN ITSELF, BEFORE execution, provides
INSTEAD:
A chance to catch the GAP (missing confirmation step) BEFORE
  it can EVER produce a misleading result — genuinely
  PREVENTIVE, rather than only DIAGNOSTIC after the fact.

This is the core, practical argument for why plan-level testing deserves its OWN dedicated page and technique, rather than simply relying on outcome-based testing — it catches an ENTIRE CATEGORY of problem at a point where prevention is still possible, not just after-the-fact diagnosis.

Why might evaluate_plan_quality's prompt specifically ask whether the plan is "appropriately rough" rather than just asking whether it's "good"?▾

This directly reuses Chapter 2's own specific standard for plan quality — "good" alone is vague and could reward an OVERLY SPECIFIC plan that seems thorough, while "appropriately rough" checks for the EXACT property Chapter 2 established as genuinely important: leaving room for the reasoner to handle specifics using REAL, current observation.

Why a VAGUE "is this a good plan" prompt is INSUFFICIENT:
An overly SPECIFIC plan (hardcoded selectors, exact expected
  text) might SUPERFICIALLY look "thorough" and "good" to an
  evaluator without the SPECIFIC context Chapter 2 established
  — but Chapter 2's Agent Planning page was EXPLICIT that this
  specificity is actually a GENUINE weakness, not a strength.

Why "appropriately ROUGH" is the CORRECT, specific standard:
This directly encodes Chapter 2's OWN established criteria —
  goal-oriented steps, not locked-in technical specifics —
  into the EVALUATION prompt itself, ensuring the evaluator
  checks for the SAME property this course has consistently
  argued actually matters for GOOD agent planning.

This is a genuinely good example of an evaluation prompt encoding a SPECIFIC, previously-established standard, rather than a generic quality judgment — connecting THIS chapter's testing techniques directly back to the SPECIFIC architectural principles Chapter 2 built up, rather than evaluating against some independent, less precise notion of "good."

How would you extend this page's approach to test whether an agent's RE-PLANNING (from Chapter 2's own discussion) is genuinely sound, not just its initial plan?▾

A genuinely useful extension would capture EVERY plan revision during a run (not just the initial one) and evaluate each new plan against BOTH the original goal AND the specific observation that triggered the re-planning, checking the revision genuinely, appropriately responds to what was actually observed.

def evaluate_replan_quality(goal, triggering_observation,
                              original_plan, revised_plan, client):
    prompt = f"""An agent's original plan was: {original_plan}
It then observed: {triggering_observation}
And revised its plan to: {revised_plan}

Does the REVISED plan genuinely, appropriately respond to
what was ACTUALLY observed? Does it still address the
ORIGINAL goal: {goal}? Or does the revision seem like an
OVERREACTION, UNDERREACTION, or GENUINELY unrelated change
given what was actually observed?"""
    result = client.messages.create(
        model="claude-sonnet-4-6", max_tokens=300,
        messages=[{"role": "user", "content": prompt}]
    )
    return result.content[0].text

This directly extends this page's own technique to Chapter 2's re-planning capability specifically — checking not just whether an initial plan is sound, but whether the agent's ADAPTATION to a genuinely unexpected observation is ITSELF reasonable, exactly the kind of deeper, process-level verification this entire chapter argues is necessary beyond simply checking final outcomes.
