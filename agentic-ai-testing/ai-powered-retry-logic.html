AI-Powered Retry Logic

Beginner 10 min read

Prerequisites: Failure Triage in CI/CD

A Direct Confrontation With Chapter 9's Warning

Chapter 9's Recommended Fixes page was explicit: "just add a retry" masks the symptom, keeps the cause. This page has to earn its place against that warning directly — the retry logic here only retries a failure when a genuine classification suggests it's actually warranted, not as a default response to any red test.

The Genuine Decision — Classify First, Then Decide

def should_retry(failure, client):
    # Reuses Chapter 8's OWN classification — this is the
    # ENTIRE point: retry ONLY when the CLASSIFICATION itself
    # suggests genuine transience, not by DEFAULT
    classification = classify_failure(failure)  # Chapter 8's
        # six categories: application defect, test defect,
        # locator problem, environment problem, network
        # problem, flaky behavior

    RETRY_WORTHY = {"environment problem", "network problem"}
    NEVER_RETRY = {"application defect", "test defect", "locator problem"}

    if classification in RETRY_WORTHY:
        return {"retry": True, "reason": (
            f"Classified as '{classification}' — genuinely "
            f"consistent with a transient issue, worth one retry.")}
    if classification in NEVER_RETRY:
        return {"retry": False, "reason": (
            f"Classified as '{classification}' — a retry would "
            f"NOT resolve this; it needs an actual fix, not "
            f"another attempt.")}
    # "flaky behavior" specifically — Chapter 9's own territory
    return {"retry": False, "reason": (
        "Classified as flaky behavior — per Chapter 9, this "
        "needs genuine root-cause investigation, not a retry "
        "that would mask the underlying race condition.")}

Why "Flaky Behavior" Specifically Never Gets Auto-Retried Here

This is the DIRECT, DELIBERATE answer to Chapter 9's warning.
A NAIVE retry system would see "INCONSISTENT failure" and
think "retry until it PASSES." THIS system does the OPPOSITE
for EXACTLY that classification — flaky BEHAVIOR is FLAGGED
for Chapter 9's OWN diagnostic PROCESS, NOT auto-retried,
BECAUSE auto-retrying a GENUINE race condition is PRECISELY
the mask CHAPTER 9 warned AGAINST.

A Genuine Case Where Retry Is Actually Warranted

# A failure classified as "environment problem" — per Chapter
# 8's OWN example, staging was mid-migration when a test ran,
# and the SAME test passes cleanly against production.

should_retry(this_failure, client)
# → {"retry": True, "reason": "Classified as 'environment
#    problem' — genuinely consistent with a transient issue,
#    worth one retry."}

This is GENUINELY different from Chapter 9's warned-against
pattern — the RETRY here is a DIRECT CONSEQUENCE of a REAL
classification (staging was UNHEALTHY, confirmed by EVIDENCE),
not a REFLEXIVE response to ANY red test.

🧠 Think About It

Why does this page's function require running Chapter 8's full classification BEFORE deciding whether to retry, rather than retrying first and only classifying if the retry also fails? Retrying first would mean paying the retry's real time cost even for failures that genuinely never should have been retried at all — like a test defect, which will fail identically every time regardless of how many attempts are made. Classifying first means the retry cost is only paid when there's genuine evidence it might actually help, directly matching Chapter 8's own cost-ordering principle of checking cheaper, more diagnostic evidence before committing to a more expensive action.

⚠️ Common Mistake

Implementing "AI-powered retry logic" as simply an LLM deciding, without a real classification step, whether a failure "seems retry-worthy." This page's entire design is that the retry decision is a direct, mechanical consequence of Chapter 8's classification — not a separate, independent judgment call that could drift from that classification's own conclusions.

💡 Quick Tip

Logging the classification alongside every retry decision (this page's reason field) makes the system's behavior auditable — a team can later verify that retries genuinely tracked classifications correctly, rather than trusting the retry logic blindly.

Best Practices

  • Base every retry decision directly on Chapter 8's genuine classification, never on a failure simply looking retry-worthy in isolation.
  • Never auto-retry a failure classified as flaky behavior — that classification specifically calls for Chapter 9's diagnostic process, not a mask.
  • Log the classification behind every retry decision, making the system's behavior auditable against Chapter 8's own conclusions.

🎯 Key Takeaway

  • Genuine retry logic decides based on Chapter 8's classification, retrying only categories consistent with real transience — environment and network problems, specifically.
  • Flaky behavior is deliberately excluded from auto-retry, directly honoring Chapter 9's warning that retries mask exactly this failure mode.
  • Classifying before retrying, not after, avoids paying a real retry cost for failures that were never going to benefit from one.

Trace through this page's should_retry function for a failure Chapter 8's classification labels "test defect" (a stale test password, per that chapter's own example) — confirm the function correctly declines to retry, and explain in your own words why a retry genuinely wouldn't help this specific case.

Interview Questions

A teammate reads this page's title and says "wait, didn't Chapter 9 say retries are basically always a bad idea?" How would you reconcile this page with that warning?▾

CHAPTER 9's WARNING was SPECIFICALLY about BLIND, UNCONDITIONAL retries MASKING a REAL cause — THIS page's SYSTEM never RETRIES blindly; it ONLY retries AFTER Chapter 8's CLASSIFICATION provides GENUINE evidence the FAILURE is CONSISTENT with real, TRANSIENT causes.

What Chapter 9 ACTUALLY warned against:
"Just ADD a retry" as a DEFAULT response to ANY flaky-LOOKING
  test, WITHOUT investigating WHY it's FAILING — THIS masks
  the GENUINE underlying cause (LIKE a race CONDITION) rather
  than ADDRESSING it.

What THIS page's system ACTUALLY does, DIFFERENTLY:
Retries ONLY happen AFTER Chapter 8's classification CONFIRMS
  a GENUINE, evidence-BASED reason to EXPECT transience
  (environment or NETWORK problems SPECIFICALLY) — and
  EXPLICITLY, DELIBERATELY excludes "FLAKY behavior"
  (Chapter 9's OWN territory) from EVER being auto-RETRIED.

These AREN'T contradictory — THIS page's SYSTEM is the DIRECT, RESPONSIBLE answer to Chapter 9's WARNING, not a REVERSAL of it. "RETRIES are GENERALLY bad WITHOUT genuine JUSTIFICATION" and "a SPECIFIC, evidence-BASED retry CAN be WARRANTED" are BOTH true SIMULTANEOUSLY, and THIS page's DESIGN reflects EXACTLY that DISTINCTION.

Why does this page's function EXPLICITLY exclude "flaky behavior" from the retry-WORTHY set, GIVEN that a race CONDITION genuinely IS transient in SOME sense?▾

A RACE condition being "TRANSIENT" in the SENSE that it doesn't FAIL every TIME is GENUINELY different from it BEING something a RETRY should MASK — Chapter 9's OWN diagnosis PROCESS (isolation EXPERIMENTS, trace ANALYSIS) exists SPECIFICALLY because the UNDERLYING mechanism NEEDS fixing, not JUST tolerating.

Why "TRANSIENT" and "SHOULD be retried" AREN'T the SAME
thing:
A GENUINE race condition (LIKE Chapter 9's OWN cart-TOTAL
  example) DOES fail INCONSISTENTLY — in THAT narrow SENSE,
  it's "TRANSIENT." But RETRYING it REPEATEDLY doesn't FIX
  the UNDERLYING timing ISSUE — it just HIDES it, LETTING it
  CONTINUE to occasionally FAIL in PRODUCTION or FUTURE runs,
  EXACTLY Chapter 9's OWN "retries MASK the SYMPTOM" argument.

Why environment/NETWORK problems are GENUINELY different:
An ENVIRONMENT problem (STAGING mid-MIGRATION) or a NETWORK
  problem (a ONE-off connection RESET) GENUINELY has NOTHING
  to do with the TEST'S or APPLICATION'S own LOGIC — a retry
  HERE isn't MASKING anything, since THERE'S no UNDERLYING
  code-LEVEL issue to MASK in the FIRST place.

This is EXACTLY why this PAGE'S classification-driven APPROACH matters — it DISTINGUISHES "TRANSIENT because of an EXTERNAL, unrelated FACTOR" (genuinely RETRY-worthy) FROM "TRANSIENT because of an UNFIXED, internal RACE condition" (Chapter 9's OWN territory, NEEDING diagnosis, NOT a retry).

Explain why this page insists on classifying BEFORE retrying, rather than RETRYING first and CLASSIFYING only if the RETRY also fails.▾

RETRYING first would MEAN paying the RETRY'S real TIME cost EVEN for FAILURES that GENUINELY never SHOULD have been RETRIED at ALL — CLASSIFYING first ENSURES that COST is ONLY paid WHEN there's GENUINE evidence it MIGHT actually HELP.

What "RETRY first, CLASSIFY later" would GENUINELY waste:
For a TEST DEFECT (like Chapter 8's OWN stale-PASSWORD
  example), a RETRY would FAIL IDENTICALLY, EVERY single TIME
  — the UNDERLYING cause (a STALE credential) doesn't CHANGE
  BETWEEN attempts. RETRYING FIRST means PAYING the FULL retry
  TIME cost BEFORE eventually DISCOVERING (via CLASSIFICATION)
  that the retry WAS never GOING to help AT ALL.

Why CLASSIFYING first (THIS page's ACTUAL approach) AVOIDS
this waste:
CLASSIFICATION HAPPENS BEFORE any RETRY is ATTEMPTED — for a
  TEST defect, should_retry IMMEDIATELY returns retry: False,
  SAVING the ENTIRE retry TIME cost for a CASE where it WAS
  genuinely NEVER going to HELP.

This DIRECTLY mirrors Chapter 8's OWN cost-ORDERING principle — CHECK cheaper, more DIAGNOSTIC evidence (CLASSIFICATION) BEFORE committing to a MORE expensive ACTION (a retry AND its associated TIME cost), EXACTLY the SAME "cheap EVIDENCE first" LOGIC this COURSE has applied CONSISTENTLY since Chapter 8's OWN Failure Classification page.

Why might logging the classification alongside EVERY retry decision (this page's "Quick Tip") matter MORE for retry LOGIC specifically than for SOME other kinds of automated DECISIONS?▾

RETRY logic SPECIFICALLY operates in a SPACE where Chapter 9 ALREADY established GENUINE, real-world HARM from getting it WRONG (masking FLAKINESS) — LOGGING the REASONING makes it POSSIBLE to VERIFY, after the FACT, that the SYSTEM is GENUINELY honoring THAT warning, not QUIETLY drifting AWAY from it.

Why RETRY logic CARRIES higher STAKES for AUDITABILITY than
SOME other automated decisions:
Chapter 9 ESTABLISHED a REAL, documented RISK (retries MASKING
  genuine PROBLEMS) — GIVEN this KNOWN risk, a TEAM has a
  GENUINE reason to want ONGOING confidence that THEIR retry
  system is ACTUALLY behaving as INTENDED, not JUST trusting
  it BLINDLY once and FORGETTING about it.

What LOGGING the classification SPECIFICALLY enables:
A team can PERIODICALLY audit: "ARE we EVER auto-retrying
  something CLASSIFIED as flaky BEHAVIOR?" (WHICH should be
  IMPOSSIBLE per THIS page's DESIGN) — IF this EVER happens,
  the LOGGED reason IMMEDIATELY reveals a GENUINE bug in the
  RETRY logic ITSELF, rather than THIS drift going UNNOTICED
  until it CAUSES a REAL, visible PROBLEM.

This is a GENUINELY practical, IMPORTANT safeguard — GIVEN Chapter 9's OWN documented, REAL concern about RETRIES specifically, MAINTAINING an AUDITABLE record of EVERY retry DECISION'S reasoning is a REASONABLE, EXTRA precaution BEYOND what MIGHT be NECESSARY for a LOWER-stakes automated DECISION.

How would you extend this page's should_retry function to LIMIT retries to a MAXIMUM of ONE attempt, rather than RETRYING indefinitely UNTIL a test PASSES?▾

A GENUINELY important safeguard TRACKS how MANY times a SPECIFIC failure has ALREADY been RETRIED, REFUSING further RETRIES beyond a REASONABLE limit — connecting DIRECTLY to Chapter 2's OWN loop-guardrail PRINCIPLE, now APPLIED to retry ATTEMPTS specifically.

def should_retry_with_limit(failure, retry_history, client, max_retries=1):
    prior_retries_for_this_failure = sum(
        1 for r in retry_history
        if r["test_name"] == failure["test_name"]
        and r["commit_hash"] == failure["commit_hash"]
    )
    if prior_retries_for_this_failure >= max_retries:
        return {"retry": False, "reason": (
            f"Already retried {prior_retries_for_this_failure} "
            f"time(s) for this exact failure — further retries "
            f"would risk masking a genuine, unresolved issue "
            f"rather than confirming a transient one.")}
    return should_retry(failure, client)  # THIS page's ORIGINAL
        # classification-based LOGIC, now GUARDED by a HARD limit

This DIRECTLY extends THIS page's approach with a HARD, MECHANICAL SAFEGUARD — EVEN a GENUINELY well-classified "environment PROBLEM" retry SHOULDN'T repeat INDEFINITELY; if the FIRST retry STILL fails, that's ITSELF evidence WORTH escalating to a HUMAN RATHER than CONTINUING to retry, EXACTLY the SAME "BOUND the loop, DON'T let it run FOREVER" principle Chapter 2 ESTABLISHED for agent EXECUTION loops, now APPLIED to THIS chapter's OWN retry DECISION specifically.
