Debugging with Observability Data

Beginner 8 min read

Prerequisites: Dashboards for QA Automation

What is this, and how it differs from Chapter 8

Chapter 8's Root Cause Analysis gathered evidence AD HOC, for ONE specific failure — capturing a fresh screenshot, pulling logs for that one timestamp. This page is about a genuinely different starting point: the evidence already exists, continuously, because of everything this chapter's earlier pages built. Debugging here means QUERYING standing history, not gathering fresh evidence.

A Genuine Investigation Starting From Existing History

A team notices the "unexplained REPEATS" flag from THIS
chapter's DASHBOARD (2 runs, past 7 DAYS). Chapter 8's
APPROACH would gather FRESH evidence for ONE of THESE runs.
THIS page's approach QUERIES what's ALREADY there, ACROSS
BOTH:

def investigate_repeat_pattern(traces_db):
    flagged_runs = traces_db.query(
        "is_repeat_of_previous_step = true"
    )
    # BOTH runs, ALREADY captured, with FULL reasoning text,
    # per this CHAPTER'S own Structured Logging and TRACING
    # pages — NOTHING new needs to be GATHERED
    for run in flagged_runs:
        print(f"Run {run['run_id']}, step {run['step']}: "
              f"{run['reasoning']}")

# OUTPUT, from data that ALREADY existed:
# Run run-88213, step 4: "The previous click may not have
#   registered; attempting again."
# Run run-91847, step 7: "The previous click may not have
#   registered; attempting again."

The Genuine Finding This Standing Data Reveals

BOTH flagged RUNS show the IDENTICAL reasoning TEXT — a
GENUINE, real PATTERN, immediately VISIBLE because the DATA
was ALREADY there to COMPARE. Chapter 8's AD HOC approach,
investigating ONE failure at a TIME, would have NEEDED to
independently GATHER and then MANUALLY compare TWO separate
investigations to NOTICE this SAME pattern — with STANDING,
QUERYABLE data, the COMPARISON is IMMEDIATE.

🧠 Think About It

Why does this page's investigation start with a database QUERY rather than Chapter 8's own opening step — reading a fresh stack trace? Chapter 8 was designed for a situation where the evidence didn't yet exist and had to be gathered specifically for that one failure. This chapter's entire earlier content — structured logging, tracing, monitoring — exists specifically to ensure the evidence ALREADY exists, continuously, before any specific investigation begins. The genuinely different starting point isn't a stylistic choice; it's a direct consequence of the infrastructure this chapter built.

⚠️ Common Mistake

Treating every debugging session as needing Chapter 8's full ad-hoc evidence-gathering process, even when this chapter's standing observability data already contains everything needed. Querying existing history is genuinely faster and can reveal cross-run patterns Chapter 8's single-failure focus would miss entirely.

💡 Quick Tip

When observability data is available, a genuinely useful first debugging step is checking whether the SAME pattern has occurred before, across the full standing history — not just investigating the current instance in isolation. This is often what reveals whether something is a one-off or a genuine, recurring issue.

Best Practices

  • Query standing observability data as a debugging starting point when it's available, rather than defaulting to Chapter 8's ad-hoc evidence gathering.
  • Look for cross-run patterns in existing history, since standing data makes this kind of comparison immediate rather than requiring separate, manual investigations.
  • Reserve Chapter 8's full evidence-gathering process for situations where standing data genuinely doesn't cover what's needed.

🎯 Key Takeaway

  • Debugging with standing observability data starts from queryable, already-captured history, genuinely different from Chapter 8's ad-hoc, per-failure evidence gathering.
  • This difference is a direct consequence of this chapter's earlier infrastructure — structured logging and tracing exist specifically to make evidence already available.
  • Standing data makes cross-run pattern comparison immediate, revealing findings Chapter 8's single-failure focus would need multiple separate investigations to notice.

How would you EXTEND this page's approach to COMBINE standing DATA with Chapter 8's AD HOC investigation, RATHER than treating THEM as fully SEPARATE alternatives?▾

A GENUINELY powerful COMBINED workflow uses STANDING data FIRST to IDENTIFY which RUNS are WORTH deeper investigation, THEN applies Chapter 8's AD HOC techniques SPECIFICALLY to THOSE identified runs, RATHER than choosing ONE approach EXCLUSIVELY.

def investigate_with_combined_approach(traces_db, run_id):
    # STEP 1: use STANDING data to CONFIRM this is PART of a
    # genuine, RECURRING pattern (THIS page's approach)
    similar_runs = traces_db.query(
        f"reasoning LIKE '%previous click may not have registered%'"
    )
    if len(similar_runs) >= 2:
        print(f"Confirmed recurring pattern across "
              f"{len(similar_runs)} runs — worth deeper "
              f"investigation.")

        # STEP 2: NOW apply Chapter 8's AD HOC, fresh-evidence
        # gathering to ONE representative RUN, to understand
        # the ROOT CAUSE behind the CONFIRMED pattern
        return gather_fresh_evidence_for_run(run_id)  # Chapter
            # 8's OWN screenshot, trace, and LOG gathering
    return "Isolated instance — standing data alone may suffice."

This GENUINELY combines BOTH chapters' STRENGTHS — STANDING data (THIS page) EFFICIENTLY confirms WHETHER something is a GENUINE, recurring PATTERN worth DEEPER attention, WHILE Chapter 8's AD HOC techniques PROVIDE the DEEPER, root-CAUSE evidence STANDING data alone WASN'T designed to CAPTURE — EXACTLY the KIND of complementary, NOT competing, relationship THIS chapter's EARLIER pages have CONSISTENTLY argued for BETWEEN new and EXISTING techniques.
