Why LLM Applications Are Different

Beginner 9 min read

Prerequisites: Testing LLM Applications overview

What is this?

Every test in this entire course, up to this chapter, eventually compared something against a known-correct value — a status code, a total, a specific error message. An LLM-powered feature genuinely has no single correct output to compare against, and that changes what "testing" has to mean.

Watch the Exact-Match Approach Fail

❌ Trying to test the shopping assistant the OLD way:
  question = "What's your return policy for electronics?"
  response = shopping_assistant.ask(question)
  assert response == "Electronics can be returned within 30 " \
                      "days of purchase, unopened, with a receipt."

  Ask the SAME question TWICE, with the IDENTICAL policy
  UNCHANGED, and you'll likely get TWO genuinely different,
  BOTH CORRECT phrasings:
  Run 1: "You can return electronics within 30 days if unopened,
          with your receipt."
  Run 2: "Our electronics return window is 30 days, provided
          the item is unopened and you have proof of purchase."

  The EXACT-MATCH assertion FAILS on run 2 — not because
  anything is WRONG, but because this kind of test is asking
  the wrong QUESTION entirely.

The Question That Actually Matters

Not: "Does this EXACTLY MATCH one specific string?"

But: "Does this response have the PROPERTIES a good answer
should have?" — specifically:
  - Is it RELEVANT to what was actually asked?
  - Is it CORRECT relative to the real, actual policy?
  - Is it GROUNDED in real information, not fabricated?
  - Would it be CONSISTENT if asked again, in substance if
    not exact wording?

These four questions are genuinely this chapter's core —
covered together in depth on the Evaluation Dimensions page.

🧠 Think About It

Why might a team that's spent this entire course building genuinely careful, exact-checking testing habits find LLM application testing specifically uncomfortable at first? Every earlier chapter trained toward precision — an exact status code, an exact schema match, an exact boundary value. LLM output genuinely resists that precision by its very nature; two equally correct answers can be worded completely differently. This isn't a failure of the testing approach from earlier chapters — it's a genuinely different kind of system, where the exact skills that made API and browser testing reliable (demanding one precise, correct value) actively work against you here.

⚠️ Common Mistake

Concluding that LLM features simply "can't be tested rigorously" because exact-match assertions don't work, and giving up on systematic testing entirely. This chapter's remaining six pages exist specifically to show genuinely rigorous testing IS possible here — it just needs different tools than exact comparison, not the abandonment of rigor altogether.

💡 Quick Tip

A genuinely useful reframe when starting to test an LLM feature: instead of asking "what's the correct answer," ask "what would make an answer WRONG, specifically?" — a factually incorrect return window, a fabricated policy detail, an answer about the wrong product entirely. Defining wrongness precisely is often more tractable than defining the one correct phrasing.

Best Practices

  • Replace exact-match assertions with property-based checks — relevance, correctness, groundedness, consistency — for any LLM-generated output.
  • Define what would make a response genuinely wrong, rather than searching for the one correct phrasing to match against.
  • Treat this as a real, distinct testing discipline requiring different tools, not an extension of exact-match testing habits from earlier chapters.

🎯 Key Takeaway

  • LLM-generated responses genuinely have no single correct output — the same correct information can be phrased in many different, equally valid ways.
  • Testing LLM features means checking properties a good response should have, not comparing against one specific expected string.
  • This is a genuinely distinct testing discipline, not a degraded or less-rigorous version of the exact-match testing this course has built up until now.

🛠️ Try It Yourself

For the question "Is the Ergo Wireless Mouse compatible with Mac?", write two genuinely different, both-correct phrasings of a good answer — then write one WRONG answer that's still fluent and confident-sounding, to make the "what would make this wrong" reframe concrete for yourself.

Interview Questions

A QA engineer new to LLM testing writes assert response == expected_text for the shopping assistant and is confused when it fails intermittently despite the answers "looking right." What would you explain to them?▾

I'd explain that "looking right" and "matching exactly" are genuinely different standards, and the intermittent failures aren't revealing a real bug — they're revealing that exact-match is the wrong tool for this specific kind of output.

What's ACTUALLY happening:
The shopping assistant is likely producing GENUINELY correct,
  GENUINELY good answers every time — just with different
  WORDING each run, exactly this page's own return-policy
  example. The test is failing because it's checking something
  (exact string equality) that was NEVER a meaningful
  requirement for this kind of feature.

The fix ISN'T making the LLM more consistent in WORDING — it's
recognizing that WORDING consistency was never the actual
GOAL. The real goal is CONTENT correctness, which needs a
GENUINELY different kind of check (covered in this chapter's
remaining pages), not a tighter or looser exact-match assertion.

This is exactly the reframe this page argues for — the intermittent failures are a signal to change the TESTING APPROACH, not a signal that the FEATURE itself is broken or inconsistent in any way that actually matters.

Why does this page suggest "what would make an answer WRONG" is often more tractable than "what's the correct answer" for LLM features?▾

The space of CORRECT phrasings is genuinely unbounded — infinitely many wordings could all be equally valid — while the space of what makes an answer factually WRONG is usually much narrower and more concretely checkable.

Why "what's correct" is GENUINELY hard to fully specify:
For the return-policy question, there's no way to enumerate
  EVERY possible correct phrasing in advance — the space is
  effectively unbounded, exactly this page's own two-run
  example demonstrates.

Why "what's WRONG" is often MORE tractable:
"The stated return window is NOT 30 days" — this IS a
  concrete, CHECKABLE fact. "The response mentions a DIFFERENT
  product than what was asked about" — ALSO concrete and
  checkable. WRONGNESS often has specific, nameable, FEWER
  failure modes than correctness has possible expressions.

This isn't a claim that defining wrongness is EASY — just that it's often more TRACTABLE than trying to enumerate every acceptable correct answer, which is exactly why this chapter's Hallucination Testing page specifically focuses on one well-defined, checkable failure mode rather than trying to validate correctness in the abstract.

Explain why a team's PRECISION habits from earlier chapters (exact status codes, exact schema matches) could actively work AGAINST them when first testing an LLM feature.▾

Those habits were genuinely well-suited to systems with one correct, deterministic output — applying the SAME instinct to a system that legitimately has MANY correct outputs means treating normal, expected variation as if it were a bug.

Where PRECISION habits genuinely served earlier chapters well:
A status code, a schema field's type, a boundary value — ALL
  genuinely have exactly ONE correct value. Demanding EXACT
  matches was the CORRECT approach precisely because
  correctness itself was narrow and singular.

Why the SAME instinct misfires here:
Applying "demand an exact match" to a system where CORRECTNESS
  is genuinely BROAD (many valid phrasings) means the test
  itself becomes the source of false failures — not because
  the underlying skill (demanding precision) was wrong in
  GENERAL, but because it was applied to a system where the
  UNDERLYING ASSUMPTION (one correct value exists) simply
  doesn't hold.

This is a genuinely important, honest recognition — the skills from earlier chapters aren't WRONG, they're SCOPED to systems with genuinely singular correctness, and recognizing when that scope no longer applies is itself part of testing LLM features well, rather than assuming more rigor always means tighter, more exact assertions.

Why might it be a mistake to conclude that BECAUSE exact-match testing fails here, LLM features are inherently LESS testable than deterministic ones?▾

This conflates "the SPECIFIC technique I know doesn't work" with "NO technique could work" — this page's own final section already points toward property-based checks as a genuinely rigorous alternative, not an admission that rigor is impossible here.

The FLAWED reasoning:
"Exact-match assertions don't work for this feature →
  therefore this feature CAN'T be tested rigorously" — this
  treats ONE SPECIFIC testing technique as if it were the ONLY
  possible form of rigor, an assumption this ENTIRE chapter
  exists specifically to correct.

The MORE accurate conclusion:
"Exact-match assertions don't work for this feature →
  therefore I need DIFFERENT techniques suited to THIS kind of
  output" — relevance, correctness, groundedness, and
  consistency checks (the next several pages) are GENUINELY
  rigorous, just STRUCTURALLY different from string equality.

This distinction matters practically — teams that give up on testing LLM features entirely, rather than adopting the RIGHT tools for them, end up shipping genuinely unvalidated AI behavior, exactly the risk this entire chapter is designed to help avoid through legitimate, alternative rigor.

How would you explain the relationship between this page's "properties a good answer should have" framing and the exact-vs-fuzzy distinction from Chapter 5 onward?▾

This page's entire subject is, in a real sense, an extreme case of "fuzzy" — while Chapter 5 introduced exact-vs-fuzzy as a CHOICE depending on the situation, THIS chapter's subject matter is a domain where the fuzzy side is essentially unavoidable, not just one available option among several.

Chapter 5's original framing — a CHOICE between two options:
"Is there ONE specific correct value (use EXACT), or does
  correctness require genuine JUDGMENT (use FUZZY)?" — BOTH
  options were genuinely available, and CHOOSING correctly
  between them was the actual skill being taught.

THIS chapter's situation — fuzzy is essentially the ONLY
option:
For LLM-generated TEXT specifically, there's rarely a
  meaningful EXACT option available at all — even a "simple"
  factual question (like the return policy) has MULTIPLE
  correct phrasings, meaning property-based (fuzzy) evaluation
  isn't just the BETTER choice here, it's close to the ONLY
  genuinely viable one for the core content of the response.

This is a useful way to place this entire chapter within the course's broader framework — it's not introducing a BRAND NEW concept so much as showing what happens when you're in a domain where the fuzzy side of Chapter 5's original distinction is overwhelmingly, almost exclusively the relevant one, rather than one of two genuinely available choices.
