Installing Dependencies & Caching

Beginner 6 min read

Prerequisites: Setting Up Programming Languages: Java, Node.js & Python

What is this?

Once a language is set up, a real project needs its actual dependencies installed before anything can build or run. This page covers installing them correctly, and — genuinely important for pipeline speed — not redoing that work from scratch on every single run.

Installing Dependencies, By Ecosystem

# Node.js
- run: npm ci   # NOT npm install — see note below

# Python
- run: pip install -r requirements.txt

# Java (Maven)
- run: mvn install

npm ci specifically (not npm install) is the correct choice in CI — it installs exactly what's locked in package-lock.json, failing loudly if that file and package.json are out of sync, rather than silently updating anything. This genuine, deliberate strictness is exactly what a CI pipeline should want.

Why Caching Matters

Without caching: every single run downloads and installs every
                 dependency from scratch — genuinely slow, and
                 repeated identically on every run.

With caching:    dependencies already downloaded in a previous run
                 are reused, skipping most of that repeated work.

For a project with a substantial dependency tree, this can be the difference between a pipeline taking two minutes versus ten — a genuinely significant, real cost multiplied across every single run.

Built-in Caching via the Setup Actions

- uses: actions/setup-node@v4
  with:
    node-version: 20
    cache: 'npm'

The simplest option — setup-node, setup-python, and others accept a cache option directly, handling the caching logic for you with no separate configuration needed.

Manual Caching With actions/cache

- uses: actions/cache@v4
  with:
    path: ~/.m2/repository
    key: maven-${{ hashFiles('**/pom.xml') }}
    restore-keys: maven-

For ecosystems without built-in setup-action caching (like Maven), actions/cache handles it directly — path is what to cache, key determines when a cached version is considered valid (here, based on a hash of pom.xml — if that file changes, the cache key changes too, correctly invalidating the old cache), and restore-keys provides a fallback to a partial match if no exact key match exists.

Detailed Example — A Fully Cached Node.js Job

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'
      - run: npm ci
      - run: npm test

The first run populates the cache normally, taking the full install time. Every subsequent run (as long as package-lock.json hasn't changed) reuses that cache, making npm ci noticeably faster — genuinely valuable across the dozens or hundreds of runs a real, active project accumulates over time.

🧠 Think About It

Why does the cache key in the manual actions/cache example include a hash of pom.xml, rather than being a fixed, unchanging string? If pom.xml changes (a dependency version bumped, a new dependency added), the previously cached dependencies are no longer necessarily correct for the new configuration. Hashing the file that defines dependencies means the cache automatically invalidates itself exactly when it actually needs to, without any manual intervention.

⚠️ Common Mistake

Using npm install instead of npm ci in a CI pipeline. npm install can silently modify the lock file and install slightly different versions than what's actually locked — exactly the kind of subtle, non-reproducible behavior a CI pipeline should actively avoid, since a pipeline's whole point is producing consistent, trustworthy results.

💡 Quick Tip

A cache that never gets invalidated (a fixed key that never changes) is arguably worse than no cache at all — it can silently serve genuinely stale dependencies indefinitely. Always base a cache key on something that changes exactly when the cache should actually be invalidated, like a lock file's hash.

Best Practices

  • Use the ecosystem's strict, lock-file-respecting install command in CI (npm ci, not npm install) — reproducibility matters more here than convenience.
  • Prefer a setup action's built-in cache option when available — it's simpler and handles the details correctly.
  • For ecosystems needing manual actions/cache, always base the cache key on a hash of the actual dependency-defining file, never a fixed string.

🎯 Key Takeaway

  • Use npm ci, not npm install, in CI — strict, lock-file-respecting, reproducible.
  • Caching dependencies can dramatically reduce pipeline time across many runs, especially for projects with substantial dependency trees.
  • A cache key should be based on something that changes exactly when the cache should invalidate — typically a hash of the lock file or dependency definition.

🏆 Challenge

Interview Questions

Why is npm ci preferred over npm install specifically in a CI environment?▾
npm ci installs exactly what's specified in package-lock.json and fails loudly if that file is out of sync with package.json, rather than silently resolving and potentially modifying the lock file the way npm install can. This strictness produces reproducible, trustworthy installs — exactly what a CI pipeline needs — rather than risking subtly different dependency versions between runs.
Why does basing a cache key on a hash of the dependency file (like package-lock.json or pom.xml) matter?▾
When the dependency-defining file changes — a version bump, a new dependency — the previously cached dependencies may no longer be correct for the new configuration. A cache key derived from that file's hash automatically changes whenever the file changes, correctly invalidating the old cache and forcing a fresh install, without needing any manual cache-management step.
What's the practical risk of using a cache key that never changes?▾
A fixed, unchanging cache key means the cache is never invalidated, even after the actual dependency requirements change — the pipeline could keep silently reusing genuinely outdated dependencies indefinitely. This can mask real problems or cause the CI environment to drift out of sync with what a fresh install would actually produce, defeating much of the value of running CI in the first place.
Why might a project using Maven need to configure actions/cache manually, rather than relying on a built-in caching option the way setup-node offers?▾
Not every language's setup action includes a built-in caching option — availability depends on what that specific action's maintainers have implemented. For ecosystems without this built-in convenience, actions/cache provides the same underlying caching capability, just requiring the path, key, and restore-keys to be configured explicitly rather than through a single, simpler option.
What's the purpose of restore-keys in an actions/cache configuration?▾
restore-keys provides a fallback mechanism — if no cache exactly matches the current key, GitHub Actions can still restore the closest previous cache matching a broader prefix, rather than starting completely from scratch. This means even when the exact cache key has changed (because a dependency file changed slightly), much of the previous cache can still be reused as a starting point, rather than losing all caching benefit entirely.
