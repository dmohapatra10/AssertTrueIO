Checking Out Repository Code

Beginner 5 min read

Prerequisites: Working with Code in CI overview

What is this?

actions/checkout has appeared as the first step in nearly every example throughout this course, without ever being explained on its own. This page covers why it's needed and the options that actually matter in a real project.

Why do we need it?

A fresh GitHub-hosted runner starts completely empty — no code, no repository, nothing. actions/checkout downloads your repository's code onto that runner, which is why it's almost always the very first step in any real job.

The Basic Usage

steps:
  - uses: actions/checkout@v4

By default, this checks out the specific commit that triggered the workflow — exactly the code that should actually be tested or built for this run.

fetch-depth — Shallow vs. Full History

- uses: actions/checkout@v4
  with:
    fetch-depth: 1    # default: only the latest commit (shallow)

- uses: actions/checkout@v4
  with:
    fetch-depth: 0    # full history, every commit

By default, checkout fetches only the single most recent commit — genuinely faster, and sufficient for most CI tasks (building, testing). Some tasks genuinely need full history — computing a changelog, comparing against a specific older commit — and those need fetch-depth: 0 explicitly.

Checking Out a Different Ref

- uses: actions/checkout@v4
  with:
    ref: develop

By default, checkout uses whatever triggered the workflow. ref: overrides this — useful for a workflow that deliberately needs to check out a specific branch, tag, or commit regardless of what actually triggered the run.

Submodules

- uses: actions/checkout@v4
  with:
    submodules: true

If a repository uses Git submodules (nested repositories referenced from within the main one), they aren't checked out by default — this needs to be explicitly requested, or any code depending on a submodule's contents will fail to find it.

Detailed Example — Choosing Options for a Real Scenario

ShopEasy's CI pipeline needs to:
1. Build and test the current commit (fast, common case)
2. A separate "changelog" workflow needs full commit history

Pipeline 1 (build/test):
  - uses: actions/checkout@v4
    # default fetch-depth: 1 is genuinely sufficient and faster

Pipeline 2 (changelog):
  - uses: actions/checkout@v4
    with:
      fetch-depth: 0   # needs the FULL history to generate a real changelog

🧠 Think About It

Why is fetch-depth: 1 (shallow) the default, rather than always fetching full history just to be safe? Full history can be genuinely large for an older, active repository — fetching it on every single run when most tasks don't need it would add real, unnecessary time to every pipeline run. The default optimizes for the common case, while fetch-depth: 0 remains available for the genuinely less common cases that need it.

⚠️ Common Mistake

Forgetting actions/checkout entirely and being confused when a later step fails with something like "file not found" or "not a git repository." This is one of the most common early mistakes — every step depending on the repository's actual code needs checkout to have run first, in that same job.

💡 Quick Tip

Checkout needs to happen once per job, not once per workflow — since each job gets a completely fresh runner (covered in the previous chapter), a workflow with multiple jobs needing the repository's code needs actions/checkout repeated in each of those jobs separately.

Best Practices

  • Always include actions/checkout as the first step in any job that needs the repository's actual code.
  • Leave fetch-depth at its default (shallow) unless a specific task genuinely needs full history.
  • Explicitly enable submodules: true if your project actually uses Git submodules — don't assume they're included automatically.

🎯 Key Takeaway

  • A fresh runner has no code at all — actions/checkout is what puts your repository's code onto it.
  • The default shallow checkout (latest commit only) is faster and sufficient for most tasks; full history needs fetch-depth: 0 explicitly.
  • Checkout needs to happen in every job that needs the code — it doesn't carry over between jobs.

🛠️ Try It Yourself

For a hypothetical workflow that needs to compare the current commit against the commit from exactly 30 days ago, decide what fetch-depth setting would actually be necessary, and explain why the default wouldn't be sufficient for this specific task.

Interview Questions

Why does almost every real GitHub Actions job need actions/checkout as its very first step?▾
A GitHub-hosted runner starts as a completely empty virtual machine with no knowledge of your repository at all. actions/checkout explicitly downloads the repository's code onto that runner, which is a prerequisite for almost any subsequent step that needs to read, build, or test that actual code.
Why is fetch-depth: 1 the default rather than fetching the complete commit history every time?▾
Most CI tasks — building, running tests — only need the current state of the code, not its full history, and fetching complete history can be genuinely slow for an older or very active repository. Defaulting to a shallow, single-commit checkout optimizes for the common case, while fetch-depth: 0 remains available explicitly for the less common tasks that do need full history.
If a workflow has two separate jobs that both need the repository's code, does checkout need to run in both?▾
Yes — each job runs on its own separate, fresh runner with no shared filesystem between jobs. actions/checkout needs to be included as a step in every individual job that requires the repository's code, since nothing automatically carries over from one job's checkout to another's.
Why do Git submodules need an explicit submodules: true setting rather than being checked out automatically?▾
Submodules represent additional, separate repositories nested within the main one, and checking them out requires additional work and network requests beyond a standard checkout. Making this opt-in via an explicit setting avoids the extra overhead for the many projects that don't use submodules at all, while still supporting the ones that do.
What would you set the ref: option to if a workflow needed to check out a specific tag rather than whatever triggered the run?▾
You'd set ref: to that specific tag's name, exactly as you would a branch name — ref: accepts branches, tags, or specific commit SHAs, and overrides checkout's default behavior of using whatever commit actually triggered the workflow. This is useful for a workflow that deliberately needs to operate on a specific, named version of the code regardless of what event started it running.
