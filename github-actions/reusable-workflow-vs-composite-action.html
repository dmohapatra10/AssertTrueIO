Reusable Workflow vs. Composite Action: Choosing the Right One

Beginner 6 min read

Prerequisites: Composite Actions Explained

What is this?

Both solve duplication — but at genuinely different scales, with different real capabilities. This page is a direct decision guide, not new mechanics, since both have already been covered individually.

The Genuine Distinction

Reusable workflow — an entire WORKFLOW: multiple jobs, its own triggers,
                     its own runners; called at the JOB level
Composite action  — a sequence of STEPS: no jobs of its own, no runner
                     selection; called at the STEP level, within a job

A Real Decision Guide

Use a Reusable Workflow whenUse a Composite Action when
You need multiple jobs, possibly with a matrix or job dependenciesYou need a repeated sequence of steps, nothing more structurally complex
Different jobs might need different runners (OS, matrix)Everything runs within one job's existing runner
The shared logic represents a genuine, complete pipeline stageThe shared logic is a smaller, repeated setup or utility sequence
You need workflow-level outputs derived from multiple jobsYou need simple step-level outputs, nothing more elaborate

Detailed Example — The Same Real Need, Solved Two Different Ways

Need: "Every repository needs to check out code, set up Node.js,
       and install dependencies before doing anything else."

This is a SEQUENCE OF STEPS, not a whole pipeline stage on its own
→ COMPOSITE ACTION is the right tool (covered on the previous page)


Need: "Every repository needs a complete CI pipeline: build, run unit
       tests, run API tests, run UI tests, and report results —
       potentially across a matrix of Node versions."

This is genuinely MULTIPLE JOBS, with real job-level structure
→ REUSABLE WORKFLOW is the right tool

Real-World Example — Using Both Together

# A reusable workflow that ITSELF uses a composite action internally:

# .github/workflows/shared-ci.yml (REUSABLE WORKFLOW)
on:
  workflow_call:
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: ./.github/actions/setup-project   # COMPOSITE ACTION, used inside
      - run: npm run build
  test:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: ./.github/actions/setup-project   # reused again, same composite action
      - run: npm test

These aren't mutually exclusive alternatives — a reusable workflow can genuinely use a composite action internally, getting the benefit of both: job-level structure from the workflow, step-level reuse from the action.

🧠 Think About It

Why might a team building shared CI/CD infrastructure for an organization end up using both tools together, rather than choosing just one? The two solve genuinely different scales of duplication — a composite action eliminates repeated step sequences within a reusable workflow's own jobs, while the reusable workflow itself eliminates duplicated pipeline structure across repositories. Using both together applies DRY thinking at both levels simultaneously.

⚠️ Common Mistake

Trying to force a composite action to do something genuinely requiring multiple jobs — like running a matrix, or having one job's outcome affect another's execution. A composite action has no concept of jobs at all; if you find yourself wanting job-level structure inside what you thought was a composite action, that's a real signal you actually need a reusable workflow instead.

💡 Quick Tip

When genuinely unsure which to use, a useful question: "does this shared thing need its own runner selection?" A composite action always runs within whatever job called it, using that job's existing runner — if the shared logic genuinely needs to choose or vary its own runner, that's a reusable workflow's job specifically.

Best Practices

  • Choose based on genuine structural need — job-level complexity favors a reusable workflow; step-level repetition favors a composite action.
  • Consider combining both — a reusable workflow using composite actions internally — when a shared pipeline has both kinds of duplication to solve.
  • Treat "does this need its own runner or job structure" as the deciding question when genuinely uncertain.

🎯 Key Takeaway

  • A reusable workflow operates at the job level — multiple jobs, its own runners, matrix support; a composite action operates at the step level within one existing job.
  • The two aren't mutually exclusive — a reusable workflow can use composite actions internally for its own step-level reuse.
  • "Does this need its own runner or job structure" is the practical deciding question.

🏆 Challenge

For each of these three real needs, decide whether a reusable workflow or a composite action is the correct tool, and justify each in one sentence: (1) a shared sequence for authenticating to a cloud provider, used at the start of several different jobs, (2) a complete, multi-stage deployment pipeline shared across a dozen microservice repositories, (3) a shared "build and test across three Node versions" sequence used by two related repositories.

Interview Questions

What's the fundamental structural difference between a reusable workflow and a composite action?▾
A reusable workflow represents an entire workflow — potentially multiple jobs, each with its own runner selection, matrix support, and job dependencies — called at the job level using uses:. A composite action is a sequence of steps with no concept of jobs or runner selection of its own, called at the step level within whatever job is already using it.
Why might a team building shared CI infrastructure genuinely use both a reusable workflow and a composite action together?▾
The two solve duplication at different scales — a composite action can eliminate a repeated step sequence within a reusable workflow's own jobs, while the reusable workflow itself eliminates duplicated pipeline structure across many calling repositories. Using both together applies the same duplication-avoidance principle at both the step level and the job/pipeline level simultaneously.
What's a clear signal that something intended as a composite action actually needs to be a reusable workflow instead?▾
Needing genuine job-level structure — multiple jobs, a matrix strategy, job dependencies, or different runners for different parts of the logic — is a clear signal, since a composite action has no concept of jobs at all and always runs entirely within whatever single job is already using it. Wanting any of these capabilities means a reusable workflow is the actual correct tool.
Why is "does this shared thing need its own runner selection" a useful practical question for choosing between the two?▾
A composite action always executes within the existing runner of whatever job called it — it has no ability to choose or vary its own runner. If the shared logic genuinely needs to select or vary its own runner (a specific OS, a matrix of environments), that capability only exists at the job level, meaning a reusable workflow is the tool that actually supports it.
Can a reusable workflow's own jobs use a composite action internally?▾
Yes — a reusable workflow's jobs can call a composite action just like any other job's steps would, getting the benefit of both tools simultaneously: the reusable workflow provides job-level structure and cross-repository sharing, while the composite action eliminates repeated step sequences within that workflow's own jobs.
