Containers & Services in GitHub Actions

Beginner 6 min read

Prerequisites: Self-Hosted Runners

What is this?

A job can run its steps inside a specific container image rather than directly on the runner's own OS, and can additionally have real service containers — a database, a cache — running alongside it, genuinely reachable during the job.

Running a Job in a Container

jobs:
  build:
    runs-on: ubuntu-latest
    container: node:20-alpine
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test

Every step in this job runs inside the node:20-alpine container, rather than directly on the Ubuntu runner's own environment. Genuinely useful for guaranteeing an exact, specific environment — a particular OS version, particular pre-installed tools — regardless of what the underlying runner happens to provide by default.

Adding a Service Container

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:15
        env:
          POSTGRES_PASSWORD: testpass
        ports:
          - 5432:5432
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test
        env:
          DATABASE_URL: postgresql://postgres:testpass@localhost:5432/postgres

The services: block starts a genuine, real PostgreSQL container alongside the job — not a mock, not an in-memory substitute, an actual running database the test suite connects to over localhost:5432.

Why This Matters for Integration Testing

Unit tests (Chapter 5): mock or fake dependencies, isolated logic
Integration tests: need something REAL to actually integrate with

A service container provides that real thing — a genuine database,
a genuine cache — without needing to install and configure it
manually on the runner itself.

Detailed Example — Application + Database + Redis, Together

jobs:
  integration-tests:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:15
        env: { POSTGRES_PASSWORD: testpass }
        ports: ['5432:5432']
      redis:
        image: redis:7
        ports: ['6379:6379']
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npm run test:integration
        env:
          DATABASE_URL: postgresql://postgres:testpass@localhost:5432/postgres
          REDIS_URL: redis://localhost:6379

This is exactly the "Application + Database + Redis, for integration testing" scenario from the original spec's own real-world examples — the application code (checked out and installed normally) runs its integration test suite against two genuinely real services, both started and torn down automatically as part of the job's own lifecycle.

🧠 Think About It

Why might a team specifically prefer a real database service container over mocking database calls entirely, for a genuine integration test suite? A mock only verifies that your code calls the database library correctly according to your own assumptions about how it behaves — it can't catch a real SQL syntax error, an actual constraint violation, or a genuine behavior difference in how the real database handles a specific query. A real service container catches problems a mock structurally cannot.

⚠️ Common Mistake

Forgetting that a service container's data doesn't persist between separate job runs — each run gets a completely fresh instance, matching the exact same "fresh runner every time" principle from Chapter 4. A test suite that assumes some specific pre-existing data from a previous run will fail unpredictably; the test's own setup needs to create whatever data it actually needs.

💡 Quick Tip

The port mapping (ports: ['5432:5432']) makes the service reachable at localhost from the job's own steps — this exact port number is a convention matching PostgreSQL's own default, not something GitHub Actions requires specifically; a different service would use its own appropriate default port.

Best Practices

  • Use service containers for genuine integration testing against real dependencies, not as a substitute for the mocking already appropriate in unit tests.
  • Never assume any data persists in a service container between separate job runs — each run's test setup needs to create what it actually needs.
  • Use container: specifically when a job genuinely needs a guaranteed, exact environment beyond what the runner's own default OS provides.

🎯 Key Takeaway

  • container: runs a job's own steps inside a specific container image, rather than directly on the runner's OS.
  • services: starts genuine, real service containers (a database, a cache) alongside the job, reachable via localhost.
  • Service containers are ideal for real integration testing — verifying against actual dependencies, not mocked substitutes.

🏆 Challenge

Extend the integration test example with a third service, a MySQL container instead of PostgreSQL, running on its own default port — write the complete services: block including the correct default MySQL port and a reasonable environment variable for its root password.

Interview Questions

Why might a job specify container: node:20-alpine rather than relying on whatever Node.js version the runner happens to have pre-installed?▾
Specifying a container guarantees an exact, specific environment — a particular Node.js version, a particular base OS, specific pre-installed tools — regardless of what a GitHub-hosted runner's own default environment happens to provide or how it might change over time. This provides stronger environment consistency than relying on a setup action against whatever the runner's underlying OS already has.
Why is a real database service container generally better for integration testing than mocking database calls entirely?▾
A mock only verifies that code calls a database library correctly according to assumptions about its behavior — it can't catch a real SQL syntax error, an actual database constraint violation, or a genuine behavioral difference in how the real database handles a specific query. A real service container exposes the application to the database's actual, genuine behavior, catching a category of problem a mock structurally cannot.
Does data written to a service container's database persist between two separate workflow runs?▾
No — each workflow run gets a completely fresh service container instance, with no data carried over from a previous run, following the same "fresh runner every time" principle covered when jobs and runners were first introduced. A test suite needs to create whatever data it actually requires as part of its own setup, rather than assuming any prior state exists.
How does a job's steps actually connect to a service container like PostgreSQL running alongside it?▾
Through the port mapping configured in the services: block, the service becomes reachable at localhost on the specified port from within the job's own steps — for PostgreSQL, conventionally port 5432. The job's test code then connects using a standard connection string pointing at localhost and that port, exactly as it would connect to a database running on a real local machine.
Why does the "Application + Database + Redis" pattern shown here specifically represent integration testing rather than unit testing?▾
Unit tests, as covered in an earlier chapter, verify individual pieces of logic in isolation, typically using mocks or fakes for external dependencies. This pattern instead runs the application's code against genuinely real, running services — an actual database, an actual cache — verifying real, end-to-end interaction with actual dependencies, which is exactly the definition of integration testing rather than isolated unit testing.
