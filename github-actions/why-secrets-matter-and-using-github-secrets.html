Why Secrets Matter & Using GitHub Secrets

Beginner 6 min read

Prerequisites: Secrets, Security & Permissions overview

What is this?

A secret is a sensitive value — a password, an API key, a deployment credential — that a workflow genuinely needs, but that must never appear in plain text anywhere a repository's contents are visible. This page covers why that matters, and GitHub's three actual mechanisms for storing secrets safely.

Why do we need it?

A repository's history is effectively permanent and often widely visible — anyone with read access can see every commit, including old ones. A credential committed directly into a workflow file, even if later removed, typically still exists in that history, retrievable by anyone who looks. Secrets exist specifically to keep sensitive values out of the repository's contents entirely.

❌ Bad — A Hardcoded Credential

env:
  DATABASE_PASSWORD: mypassword123

This is visible to anyone with repository access, permanently, in the commit history, even if this exact line is later deleted in a subsequent commit.

✅ Good — A Referenced Secret

env:
  DATABASE_PASSWORD: ${{ secrets.DATABASE_PASSWORD }}

The actual value lives in GitHub's own secret storage, never in the workflow file itself — the file only references it by name. Even someone with full repository access can't view an existing secret's actual value through the GitHub interface once it's been set.

Repository Secrets

Settings → Secrets and variables → Actions → New repository secret

Available to every workflow in that specific repository. The right default choice for a credential genuinely specific to one project.

Environment Secrets

Settings → Environments → (select an environment) → Add secret

Scoped to a specific GitHub Environment (like "staging" or "production," covered fully in Chapter 12) — only available to a job explicitly configured to use that environment. This is genuinely important for one common, real scenario: different credentials for staging versus production, where a workflow should never accidentally use the wrong one.

Organization Secrets

Organization Settings → Secrets and variables → Actions → New organization secret

Available across multiple repositories within an organization — useful for a credential genuinely shared across many projects (a shared registry login, for instance), avoiding the need to duplicate the same secret into every individual repository separately.

Detailed Example — Choosing the Right Scope for ShopEasy

ShopEasy's actual credentials:
- A staging database password → Environment secret (staging environment)
- A production database password → Environment secret (production environment)
- A project-specific third-party API key → Repository secret
- A shared internal package registry login, used by 12 different
  repositories across the company → Organization secret

Each credential's actual scope of use determines where it belongs — a value relevant to exactly one environment, one repository, or the whole organization should be stored at exactly that matching level, not broader than necessary.

🧠 Think About It

Why might using an environment secret specifically (rather than one repository secret shared across both staging and production) meaningfully reduce risk? If staging and production use genuinely separate environment secrets, a workflow mistakenly configured to run against the wrong environment simply won't have access to the other environment's credential at all — the separation itself is a real safeguard, not just an organizational convenience.

⚠️ Common Mistake

Assuming a secret, once removed from a workflow file, is also removed from the repository's history. It isn't — the old commit still contains the old value. If a real credential was ever committed in plain text, the correct response is rotating that credential (creating a new one and invalidating the old), not just deleting the line that exposed it.

💡 Quick Tip

Secret names are conventionally written in UPPER_SNAKE_CASE (like DATABASE_PASSWORD) — not a strict technical requirement, but a strong, near-universal convention that makes secrets immediately visually distinct from other configuration in a workflow file.

Best Practices

  • Never commit a real credential to a repository, even temporarily "to test something quickly" — treat every commit as permanent.
  • Choose the narrowest secret scope that's actually correct — repository, environment, or organization — matching where the credential is genuinely used.
  • If a credential is ever accidentally exposed, rotate it immediately — removing the exposing line alone is not sufficient.

🎯 Key Takeaway

  • Secrets exist specifically to keep sensitive values out of a repository's visible contents and permanent history.
  • GitHub offers three scopes — repository, environment, and organization — each matching a different real scope of use.
  • A secret's value, once set, is never viewable again through GitHub's interface — only referenceable by name.

🛠️ Try It Yourself

For a hypothetical project with a shared company-wide Docker registry login, a project-specific third-party analytics API key, and separate staging/production deployment credentials, decide which of the three secret scopes each one belongs in, and justify each choice in one sentence.

Interview Questions

Why is removing a hardcoded credential from a workflow file not sufficient to actually secure it?▾
A repository's commit history is effectively permanent — even after a line is deleted in a later commit, the earlier commit containing the original value still exists and remains retrievable by anyone with read access to that history. The correct response to an accidentally exposed credential is rotating it entirely (creating a new one and invalidating the old), not just removing the line that exposed it.
Why might a team use separate environment secrets for staging and production rather than one shared repository secret?▾
Separate environment secrets mean a workflow mistakenly configured to target the wrong environment simply won't have access to the other environment's credential at all — the separation itself acts as a genuine safeguard against accidentally using a production credential in a staging context or vice versa, rather than relying purely on workflow logic to keep them straight.
When would an organization secret be the right choice over a repository secret?▾
When a credential is genuinely shared across multiple repositories within the same organization — a shared package registry login, for instance — an organization secret avoids needing to duplicate that same value into every individual repository's own secret storage separately, keeping one single source of truth for a value that's legitimately used in many places.
Can someone with full repository access view the actual value of an existing secret through GitHub's interface?▾
No — once a secret's value has been set, GitHub's interface only allows updating or deleting it, never viewing the current value again. This is a deliberate design choice, ensuring that even someone with legitimate repository access can't casually retrieve a secret's actual value just by browsing the repository's settings.
Why does the specific scope of a credential's actual use (one project, one environment, or many repositories) matter when deciding where to store it as a secret?▾
Storing a secret at a broader scope than it's actually needed unnecessarily widens its exposure — an organization secret is available to every repository in that organization, which is more access than a credential genuinely specific to one project should have. Matching the secret's scope to its actual, real scope of use keeps access appropriately narrow, following the same least-privilege thinking covered later in this chapter.
