Variables vs. Secrets: Choosing the Right One

Beginner 5 min read

Prerequisites: Why Secrets Matter & Using GitHub Secrets

What is this?

Chapter 6 introduced the vars context alongside secrets without dwelling on the distinction. Both store named, repository-level (or environment/organization-level) configuration — but they exist for genuinely different reasons, and mixing them up is a real, common mistake.

The Genuine Distinction

vars     — configuration that ISN'T sensitive; fine to be visible
secrets  — configuration that IS sensitive; must never be visible

Both are configured through GitHub's settings, outside the workflow file, and both are referenced through expressions. The real difference is entirely about sensitivity, not mechanics.

Using Each

env:
  DEFAULT_REGION: ${{ vars.DEFAULT_REGION }}      # a plain configuration value
  API_KEY: ${{ secrets.API_KEY }}                   # a genuinely sensitive value

A Real Decision Guide

Use vars whenUse secrets when
The value being visible wouldn't cause any harmThe value being visible could genuinely be misused
It's a plain configuration setting (a region, a URL, a flag)It's a credential, key, token, or password
Team members reasonably need to see the current valueThe value should never be viewable again once set
It changes based on environment but isn't risky either wayExposure would allow unauthorized access to something real

Detailed Example — Classifying Real ShopEasy Values

DEFAULT_REGION: "us-east-1"          → vars (just a config setting, harmless if seen)
LOG_LEVEL: "info"                      → vars (harmless configuration)
STRIPE_SECRET_KEY: "sk_live_..."         → secrets (a real payment credential)
DATABASE_CONNECTION_STRING: "..."          → secrets (contains real access credentials)
FEATURE_FLAG_NEW_CHECKOUT: "true"            → vars (just a toggle, no sensitivity)

Notice the test isn't "does this look technical" or "is this a single value versus a complex one" — it's specifically whether exposure would actually cause harm.

🧠 Think About It

Why might a connection string specifically need to be a secret, even if the database hostname alone would be harmless as a var? A full connection string typically includes the username and password needed to actually authenticate — the hostname alone reveals only where the database is, which is far less useful to an attacker than credentials that would let them actually connect and access it.

⚠️ Common Mistake

Defaulting to secrets for everything "just to be safe," even for values that genuinely aren't sensitive. This isn't harmless caution — it makes ordinary, harmless configuration values impossible for team members to actually view when they legitimately need to check or discuss them, without any real corresponding security benefit.

💡 Quick Tip

A useful gut-check question: "If this value appeared in a public screenshot of someone's terminal, would that be a genuine problem?" If yes, it belongs in secrets. If the honest answer is no, it belongs in vars.

Best Practices

  • Classify every configuration value by actual sensitivity, not by how technical or important it seems.
  • Don't default to secrets as a blanket "safer" choice — it has a real cost in visibility and debuggability for values that don't need that protection.
  • When genuinely unsure, err toward secrets for anything touching authentication or access — but don't apply that same caution to plain configuration.

🎯 Key Takeaway

  • vars and secrets are mechanically similar but serve genuinely different purposes — sensitivity is the real distinguishing factor.
  • A credential, key, token, or password belongs in secrets; ordinary configuration belongs in vars.
  • Defaulting everything to secrets "to be safe" has a real, unnecessary cost for values that don't need that protection.

🏆 Challenge

For each of these five values, decide whether it belongs in vars or secrets, and justify each in one sentence: (1) a GitHub personal access token, (2) the name of the current deployment environment ("staging"), (3) a Slack webhook URL used to post build notifications, (4) the number of parallel test workers to use, (5) an SSH private key used for deployment.

Interview Questions

What's the actual, fundamental distinction between vars and secrets, given that both are configured outside the workflow file?▾
The distinction is entirely about sensitivity, not mechanics — both are stored in GitHub's settings and referenced through similar expression syntax. vars is for configuration that's fine to be visible; secrets is for values that must never be exposed, and which GitHub specifically prevents from being viewed again once set.
Why might a full database connection string need to be a secret even if the hostname alone would be fine as a var?▾
A connection string typically bundles in the actual credentials (username and password) needed to authenticate and access the database, not just its location. The hostname alone only reveals where something is, which is far less immediately useful to an attacker than credentials that would grant them real access to connect and interact with it.
Why is defaulting every configuration value to secrets "just to be safe" not actually a good practice?▾
Treating every value as a secret makes genuinely harmless configuration impossible for team members to view or discuss when they legitimately need to, without providing any real security benefit for values that were never sensitive to begin with. It trades away real debuggability and transparency for protection that isn't actually needed.
What's a practical, quick test for deciding whether a specific value belongs in vars or secrets?▾
Asking whether the value appearing in a public screenshot or accidentally shared log would actually be a problem. If exposure would genuinely cause harm — allowing unauthorized access to something real — it belongs in secrets. If the honest answer is that exposure wouldn't matter, it belongs in vars.
Why does a feature flag like FEATURE_FLAG_NEW_CHECKOUT: true belong in vars rather than secrets?▾
A feature flag is simply a configuration toggle — knowing its current value doesn't grant anyone unauthorized access to anything or reveal a credential. Since its exposure carries no genuine risk, it fits the vars category exactly, and forcing it into secrets would just make it harder for the team to view or reason about without any corresponding security benefit.
