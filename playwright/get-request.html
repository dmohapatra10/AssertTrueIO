GET Requests

Beginner 7 min read

Prerequisites: API Testing overview

What is this?

request.get(url: string, options?: { params?, headers?, timeout? })

GET retrieves data without changing anything on the server — no request body, and (by HTTP convention) no side effects. This is the method behind almost every "read" verification in an API test: fetching a list, checking a single resource's current state, confirming a search returns the right results.

Why it's important

GET is usually the first API method engineers reach for, since it's the simplest and safest — but "simple" doesn't mean there's nothing to get wrong. Query parameter encoding, header requirements, and pagination are where most real GET-related bugs in test suites actually live.

Basic Example

const response = await request.get('/api/orders/ORD-10492');
expect(response.ok()).toBeTruthy();

const order = await response.json();
expect(order.status).toBe('shipped');

Query Parameters

// Pass params as an object — Playwright handles URL encoding for you
const response = await request.get('/api/orders', {
  params: { status: 'pending', limit: '10', sort: 'created_at' },
});
// Actual request URL: /api/orders?status=pending&limit=10&sort=created_at

Building the query string manually (string concatenation) is a common early mistake — special characters (spaces, &, non-ASCII text) need proper encoding, and the params option handles that automatically rather than requiring a manual encodeURIComponent() call for every value.

Headers

const response = await request.get('/api/profile', {
  headers: {
    Authorization: 'Bearer test-token',
    'Accept-Language': 'en-GB',
  },
});

Most authenticated GET requests don't need manual headers at all — as covered on the API Testing overview page, the request fixture shares cookies/storage with page, so an already-logged-in session (via storageState) authenticates automatically. Manual headers are for the remaining cases: testing with a specific, deliberately different token, or headers unrelated to auth (locale, content negotiation).

Detailed Example — Pagination

test('paginated results return the requested page size', async ({ request }) => {
  const page1 = await request.get('/api/products', { params: { page: '1', per_page: '20' } });
  const body1 = await page1.json();

  expect(body1.items).toHaveLength(20);
  expect(body1.total).toBeGreaterThan(20);
  expect(body1.page).toBe(1);

  const page2 = await request.get('/api/products', { params: { page: '2', per_page: '20' } });
  const body2 = await page2.json();

  // Confirm page 2 actually contains DIFFERENT items, not a repeat of page 1
  const idsPage1 = body1.items.map((item) => item.id);
  const idsPage2 = body2.items.map((item) => item.id);
  expect(idsPage1.some((id) => idsPage2.includes(id))).toBe(false);
});

That last assertion is the one engineers skip most often — confirming the item count is correct doesn't catch a broken pagination implementation that silently returns the same page of data regardless of the page parameter. Checking that the actual IDs differ between pages catches that class of bug directly.

Real-World Example — Search With Filters

test('search filters by category and price range', async ({ request }) => {
  const response = await request.get('/api/products/search', {
    params: {
      q: 'mouse',
      category: 'electronics',
      min_price: '10',
      max_price: '50',
    },
  });

  expect(response.ok()).toBeTruthy();
  const results = await response.json();

  for (const item of results.items) {
    expect(item.category).toBe('electronics');
    expect(item.price).toBeGreaterThanOrEqual(10);
    expect(item.price).toBeLessThanOrEqual(50);
  }
});

Looping through every returned item to confirm each one individually satisfies the filter is a stronger check than just asserting a non-empty result — it catches a filter that's partially broken (correctly narrowing by category but ignoring price) that a simple "results exist" assertion would miss entirely.

❌ Fragile vs. ✅ Recommended

// ❌ Manual string concatenation — breaks on special characters, easy to get wrong
const response = await request.get(`/api/products/search?q=${searchTerm}&category=electronics`);

// ✅ Let Playwright handle encoding
const response = await request.get('/api/products/search', {
  params: { q: searchTerm, category: 'electronics' },
});

Common Mistakes

  • Manually building query strings instead of using the params option — easy to get encoding wrong for values with spaces or special characters.
  • Only checking item count after a filtered or paginated request, not the actual content — a count can be right while the underlying data is wrong (repeated page, ignored filter).
  • Adding manual auth headers when storageState already covers it — redundant, and can mask a real auth-sharing bug if the manual header happens to paper over it.

Edge Cases

  • Empty result sets — a GET with filters matching nothing should return a valid empty array with a 200, not an error; explicitly testing this (a search with no matches) is easy to forget.
  • Very large limit/page-size values — worth testing that the API caps them sensibly (a client requesting limit=100000 shouldn't be able to force the server to return an unbounded response).

Debugging

If a GET request returns unexpected data, log the fully resolved URL (most HTTP clients, including Playwright's, expose the final request URL on the response) to confirm the query parameters were actually encoded and sent the way you expect, rather than assuming the params object was interpreted correctly.

Best Practices

  • Always use the params option for query parameters rather than manual string building.
  • Validate actual returned content for filtered/paginated requests, not just counts.
  • Test the empty-result case explicitly for any search or filter endpoint.

Practice Exercise

Write a test that fetches three pages of a paginated endpoint and asserts that no item ID appears on more than one page, confirming pagination doesn't silently duplicate results across pages.

Summary

GET requests retrieve data without side effects. The params option handles query-string encoding correctly; validating actual content (not just counts) after filtering or pagination catches bugs a superficial check would miss; and most authenticated GETs need no manual headers at all, since storageState already covers session sharing.

Interview Questions

Why is asserting only the item count insufficient when testing a paginated or filtered GET endpoint?▾
A correct count can coexist with wrong data — a broken pagination implementation might return the same 20 items regardless of the requested page, or a broken filter might return the right number of items while ignoring the filter criteria entirely. Asserting on the actual returned content (specific IDs across pages, or that every item satisfies the filter) is what actually catches those bugs; count alone doesn't.
Why prefer the params option over manually building a query string?▾
Playwright handles URL encoding correctly for special characters; manual string concatenation is easy to get wrong for spaces or symbols.
Why check actual item IDs across pages, not just the count, when testing pagination?▾
A broken implementation could return the same page repeatedly with a correct count — checking IDs differ catches that.
Do most authenticated GET requests need manual auth headers in Playwright?▾
No — the request fixture shares storageState with page by default, so an already-logged-in session authenticates automatically.
Why test a search with filters that match nothing?▾
It should return a valid empty result with 200, not an error — an easy case to leave uncovered if only the happy path is tested.
