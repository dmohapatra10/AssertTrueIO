DELETE Requests

Beginner 7 min read

Prerequisites: PUT & PATCH Requests

What is this?

request.delete(url: string, options?: { headers? })

DELETE removes a resource. It's the method behind most test cleanup — the teardown half of the Hooks and Fixtures chapters' setup/teardown patterns, and the method the Fixtures chapter's dedicated "cleanup fixture" pattern is usually calling under the hood.

Why it's important

DELETE looks trivially simple, but two things trip people up in practice: confirming a resource is genuinely gone (not just that the request returned success), and handling cleanup for resources that may or may not still exist by the time teardown runs.

Basic Example

const response = await request.delete('/api/orders/ORD-10492');
expect(response.status()).toBe(204); // 204 No Content — common for successful deletes

A 204 response has no body by design — calling .json() on it will throw, since there's nothing to parse. If your API returns the deleted resource's final state instead (some do, as a convenience), it'll use 200 with a body instead; check which convention your specific API follows before writing the assertion.

Detailed Example — Verifying the Resource Is Actually Gone

test('deleting an order removes it completely', async ({ request }) => {
  const created = await request.post('/api/orders', {
    data: { item: 'Wireless Mouse', quantity: 1 },
  });
  const { id } = await created.json();

  const deleteResponse = await request.delete(`/api/orders/${id}`);
  expect(deleteResponse.status()).toBe(204);

  // Don't stop at the delete response — confirm it's genuinely gone
  const fetchResponse = await request.get(`/api/orders/${id}`);
  expect(fetchResponse.status()).toBe(404);
});

This is the DELETE equivalent of the pattern from the API + UI Workflows section on the overview page: the delete call succeeding tells you the server accepted the request, but a follow-up GET returning 404 is what actually proves the resource is gone — a server could return a "successful" delete response due to a bug while leaving the resource fully intact.

DELETE Is Idempotent

// Deleting the same (already-deleted) resource again should NOT be treated as
// an unexpected failure by well-behaved cleanup code — DELETE is idempotent by
// HTTP convention: calling it multiple times should have the same end effect as once
await request.delete(`/api/orders/${id}`); // first call: 204, resource removed
const second = await request.delete(`/api/orders/${id}`);
// A well-behaved API returns 404 (already gone) here, not a 500 error —
// either way, the END STATE (resource doesn't exist) is the same as after the first call

This idempotence is exactly why cleanup code (in an afterEach hook or a cleanup fixture) can safely call delete on something that might already be gone, without needing to first check whether it exists — the operation is safe to repeat.

Real-World Example — Resilient Cleanup in afterEach

test.describe('order tests', () => {
  let orderId: string;

  test.beforeEach(async ({ request }) => {
    const res = await request.post('/api/orders', { data: { item: 'Keyboard', quantity: 1 } });
    ({ id: orderId } = await res.json());
  });

  test.afterEach(async ({ request }) => {
    // .catch() here matters: if the test ITSELF already deleted the order
    // as part of what it was testing, this second delete would otherwise throw
    await request.delete(`/api/orders/${orderId}`).catch(() => {});
  });

  test('can view order details', async ({ page }) => { /* doesn't delete the order */ });

  test('can cancel and delete an order', async ({ page }) => {
    // this test's own logic already deletes orderId —
    // the afterEach's delete-again is now a safe no-op, not a failure
  });
});

This pattern — cleanup that tolerates "already gone" — is what makes teardown robust across a whole suite of tests that may or may not have already deleted the resource themselves as part of what they were testing.

Soft Delete vs. Hard Delete

Not every DELETE actually removes data from the database — many APIs implement a soft delete, marking a record inactive/archived rather than removing it. This changes what "verify it's gone" actually means for a test:

// Hard delete — a follow-up GET returns 404
const fetchResponse = await request.get(`/api/orders/${id}`);
expect(fetchResponse.status()).toBe(404);

// Soft delete — the resource may still be fetchable directly, but should be
// excluded from normal listings and flagged as deleted
const fetchResponse = await request.get(`/api/orders/${id}`);
expect((await fetchResponse.json()).deletedAt).not.toBeNull();

const listResponse = await request.get('/api/orders');
const ids = (await listResponse.json()).items.map((o) => o.id);
expect(ids).not.toContain(id); // excluded from the normal list view

Assuming hard-delete semantics (a 404 after deletion) against an API that actually soft-deletes is a common source of confusing test failures — the resource genuinely was "deleted" from the application's point of view, but a direct GET by ID still succeeds, which looks like the delete silently failed if you don't know the API's actual behavior.

❌ Fragile vs. ✅ Recommended

// ❌ Only checking the delete call's own status, never confirming removal
await request.delete(`/api/orders/${id}`);
// test ends here — never actually proved the order is gone

// ✅ Follow up to confirm the resource is genuinely removed (or correctly soft-deleted)
await request.delete(`/api/orders/${id}`);
const fetched = await request.get(`/api/orders/${id}`);
expect(fetched.status()).toBe(404);

Common Mistakes

  • Never verifying the delete actually took effect — trusting the delete response's status code alone, without a follow-up check.
  • Assuming hard-delete when the API actually soft-deletes, leading to a test that expects a 404 but gets a 200 with a "deleted" flag instead.
  • Not making cleanup code tolerant of "already deleted" — an afterEach that throws when a resource the test itself already removed can't be deleted again, failing tests that were otherwise passing.
  • Calling .json() on a 204 response, which has no body and throws when parsed.

Edge Cases

  • Cascading deletes (deleting a user also deletes their orders) — worth explicitly verifying the cascade actually happened, not just that the top-level resource is gone.
  • Deleting a resource that doesn't exist — a well-behaved API returns 404, not a 500 server error; this is worth its own explicit test, since it's an easy path to leave uncovered.

Debugging

If a "delete" test fails with an unexpected status on a follow-up GET, check whether the API implements soft delete before assuming the delete itself failed — a soft-deleted resource often still returns 200 from a direct GET by ID, which is correct behavior for that API, not a bug.

Best Practices

  • Always follow a delete with a verification step — a GET expecting 404 (hard delete) or a flag/exclusion check (soft delete) — never trust the delete response alone.
  • Make cleanup code (afterEach, cleanup fixtures) tolerant of resources that may already be gone, using .catch(() => {}) or an equivalent.
  • Know which delete semantics (hard vs. soft) your specific API implements before writing verification assertions.
  • Test deleting a non-existent resource explicitly, confirming a clean 404 rather than a server error.

Practice Exercise

Write a test that creates an order, deletes it, verifies a follow-up GET returns 404, and then calls delete on the same (already-deleted) ID again, asserting the second call doesn't throw and reflects idempotent behavior.

Summary

DELETE removes a resource and is idempotent by convention — safe to call more than once with the same end effect. Always verify removal with a follow-up request rather than trusting the delete response alone, know whether your API implements hard or soft delete, and make cleanup code tolerant of resources that may already be gone.

Interview Questions

Why is it important to make cleanup code (like an afterEach hook) tolerant of a resource that's already been deleted, rather than assuming it always still exists?▾
Some tests delete a resource as part of what they're actually testing (a "cancel order" test, for instance), while an afterEach hook designed for general cleanup might also try to delete that same resource afterward. Since DELETE is idempotent, calling it again on an already-gone resource should be harmless — but if the cleanup code doesn't handle the resulting 404 gracefully (e.g., with a .catch()), it can throw and fail an otherwise-passing test purely because of teardown logic, not because anything actually went wrong.
Why isn't a successful delete response enough to prove a resource is actually gone?▾
A server bug could return a 'successful' response while leaving the resource intact — a follow-up GET expecting 404 is what actually proves removal.
Why is DELETE described as idempotent?▾
Calling it again on an already-deleted resource should have the same end effect as the first call — safe for cleanup code to repeat without checking existence first.
What's the difference in verification needed for hard delete versus soft delete?▾
Hard delete: a follow-up GET should return 404. Soft delete: the resource may still be fetchable but should be flagged and excluded from normal listings.
Why should cleanup code in afterEach use .catch(() => {}) around a delete call?▾
So it doesn't throw if the test itself already deleted the resource as part of what it was testing, making the second delete a safe no-op.
