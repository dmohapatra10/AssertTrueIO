Chapter 18: Fixtures

Beginner 11 min read

Prerequisites: Hooks, Playwright Test Runner

What is this?

A fixture is a piece of setup that a test declares it needs, by naming it as a parameter — and Playwright provides it automatically, already built. page is a fixture. So is context, browser, and request. You've been using fixtures since Chapter 2 without necessarily calling them that; this chapter covers what they actually are and how to build your own.

Why is it important?

Hooks (Chapter 17) share setup across tests, but the setup itself still lives in the test file, and every test that needs it must remember to declare the right beforeEach. Fixtures flip this: the test just asks for what it needs — async ({ loggedInPage }) => { ... } — and Playwright figures out how to build it, including anything that fixture itself depends on. This is what lets large suites share complex setup (authenticated sessions, seeded data, page objects) without every test file repeating boilerplate.

Built-in fixtures

FixtureScopeWhat it provides
pageTestA fresh page (tab) in a fresh, isolated context.
contextTestThe BrowserContext the page belongs to.
browserWorkerThe shared browser instance for the current worker.
requestTestAn APIRequestContext for making HTTP calls (Chapter 9's API chapter).

Notice browser is worker-scoped, not test-scoped — one browser process is reused for every test that worker runs, while page and context are recreated fresh for each individual test. This is the same Browser → BrowserContext → Page hierarchy from Chapter 3, expressed as fixture scopes.

Writing a custom fixture

// fixtures.ts
import { test as base } from '@playwright/test';

type MyFixtures = {
  loggedInPage: Page;
};

export const test = base.extend<MyFixtures>({
  loggedInPage: async ({ page }, use) => {
    // --- setup ---
    await page.goto('/login');
    await page.getByLabel('Email').fill('user@example.com');
    await page.getByLabel('Password').fill('secret123');
    await page.getByRole('button', { name: 'Sign in' }).click();
    await page.waitForURL('/dashboard');

    await use(page); // --- hand control to the test ---

    // --- teardown (runs after the test, even if it fails) ---
    await page.context().clearCookies();
  },
});

export { expect } from '@playwright/test';
// login.spec.ts
import { test, expect } from './fixtures';

test('dashboard shows the welcome banner', async ({ loggedInPage }) => {
  await expect(loggedInPage.getByText('Welcome back')).toBeVisible();
});

The use(page) call is the pivot point: everything before it is setup, everything after it is teardown, and Playwright guarantees the teardown half runs even if the test itself throws. This single-function setup/teardown shape is what replaces a matched beforeEach/afterEach pair.

Test-scoped vs. worker-scoped fixtures

export const test = base.extend<{}, { apiToken: string }>({
  apiToken: [async ({}, use) => {
    const token = await fetchServiceToken(); // expensive — do it once
    await use(token);
  }, { scope: 'worker' }],
});

A test-scoped fixture (the default) is rebuilt for every test — right for anything that must be isolated per test, like page. A worker-scoped fixture is built once and reused across every test that worker runs — right for genuinely expensive, shareable setup, like acquiring a service-account API token. Mixing these up in the wrong direction causes two different problems: making page worker-scoped would leak state between tests; making an expensive token fetch test-scoped would slow the suite down for no isolation benefit.

Fixture dependencies

Fixtures can depend on other fixtures simply by naming them as parameters — Playwright resolves the dependency graph automatically:

export const test = base.extend<{ dashboardPage: DashboardPage }>({
  dashboardPage: async ({ loggedInPage }, use) => {
    await use(new DashboardPage(loggedInPage));
  },
});

Here dashboardPage depends on loggedInPage, which itself depends on page. Playwright builds them in the correct order automatically — a test that asks for dashboardPage transparently gets a logged-in session wrapped in a page object.

Automatic fixtures

export const test = base.extend({
  forEachTest: [async ({ page }, use) => {
    console.log('Starting test...');
    await use();
    console.log('Finished test.');
  }, { auto: true }],
});

{ auto: true } makes a fixture run for every test automatically, even if no test explicitly asks for it — useful for cross-cutting concerns like logging or setting a consistent viewport, but easy to overuse into "invisible magic" that makes tests harder to reason about in isolation.

Real-world example: Page Object fixture

export const test = base.extend<{ inventoryPage: InventoryPage }>({
  inventoryPage: async ({ page }, use) => {
    const inventoryPage = new InventoryPage(page);
    await inventoryPage.goto();
    await use(inventoryPage);
  },
});

// inventory.spec.ts
test('can add item to cart', async ({ inventoryPage }) => {
  await inventoryPage.addToCart('Wireless Mouse');
  await expect(inventoryPage.cartBadge).toHaveText('1');
});

This is the pattern Chapter 11's Page Object Model chapter builds on directly — the page object's navigation is handled once, in the fixture, instead of repeated in every test that needs it.

Six Custom Fixture Patterns

The login and page object fixtures above are two of the six patterns that cover almost every real custom fixture you'll write. The remaining four:

API fixture

Wraps APIRequestContext in a small client class, so tests call readable methods instead of raw request.post() calls with inline URLs and payloads scattered everywhere.

class OrdersApi {
  constructor(private request: APIRequestContext) {}
  async create(data: { item: string; quantity: number }) {
    const res = await this.request.post('/api/orders', { data });
    return res.json();
  }
}

export const test = base.extend<{ ordersApi: OrdersApi }>({
  ordersApi: async ({ request }, use) => {
    await use(new OrdersApi(request));
  },
});

This is the exact pattern the API Testing and Framework Folder Structure chapters build on — an API fixture is what turns "seed some test data fast" from a repeated block of request.post() calls into a single, readable ordersApi.create(...) line.

Test data fixture

Generates fresh, unique data a test needs — not hardcoded, so parallel tests (Parallelism chapter) never collide over the same fixed values.

type NewUser = { email: string; password: string };

export const test = base.extend<{ newUser: NewUser }>({
  newUser: async ({}, use) => {
    const user = {
      email: `test-${Date.now()}-${Math.random().toString(36).slice(2)}@example.com`,
      password: 'correct-horse-battery-staple',
    };
    await use(user);
  },
});

// signup.spec.ts
test('new user can complete signup', async ({ page, newUser }) => {
  await page.goto('/signup');
  await page.getByLabel('Email').fill(newUser.email);
  await page.getByLabel('Password').fill(newUser.password);
  await page.getByRole('button', { name: 'Create account' }).click();
});

Unlike the login or API fixtures, this one has no use() teardown at all — there's nothing to clean up for data that only ever existed as a plain in-memory object, which is a normal, valid shape for a fixture to take.

Database fixture

Provides a real database connection (or a scoped transaction) directly to a test — useful for tests that need to verify backend state a UI or API response wouldn't fully expose, such as confirming a row was actually deleted, not just that the UI stopped showing it.

import { Pool } from 'pg';

export const test = base.extend<{}, { dbPool: Pool }>({
  dbPool: [async ({}, use) => {
    const pool = new Pool({ connectionString: process.env.TEST_DATABASE_URL });
    await use(pool); // worker-scoped — one pool shared across that worker's tests
    await pool.end();
  }, { scope: 'worker' }],
});

// order-cleanup.spec.ts
test('cancelled orders are actually removed from the database', async ({ page, dbPool }) => {
  // ...cancel the order via the UI...
  const { rows } = await dbPool.query('SELECT * FROM orders WHERE id = $1', [orderId]);
  expect(rows).toHaveLength(0);
});

A database connection is exactly the kind of genuinely expensive, safely shareable resource the Test-Scoped vs. Worker-Scoped section above is describing — worker scope here isn't just an option, it's the correct choice, since opening a fresh connection pool per test would be needlessly slow.

Cleanup fixture

Sometimes a fixture's entire purpose is teardown, not setup — tracking resources a test creates during its body (not known in advance) and guaranteeing they're all removed afterward, regardless of how many were created or whether the test passed.

export const test = base.extend<{ trackOrder: (id: string) => void }>({
  trackOrder: async ({ request }, use) => {
    const createdIds: string[] = [];

    await use((id: string) => { createdIds.push(id); }); // setup: just an empty tracking array

    // teardown: clean up EVERYTHING the test tracked, however many there were
    for (const id of createdIds) {
      await request.delete(`/api/orders/${id}`).catch(() => {});
    }
  },
});

// bulk-orders.spec.ts
test('creating three orders in a row all succeed', async ({ request, trackOrder }) => {
  for (let i = 0; i < 3; i++) {
    const res = await request.post('/api/orders', { data: { item: `Item ${i}` } });
    trackOrder((await res.json()).id); // register each one for cleanup
  }
});

This is a genuinely different shape from the other five patterns: use() here doesn't hand the test a resource to act on, it hands the test a function the test calls during its body to register cleanup work — flexible enough to handle "however many things this specific test happens to create," which a fixed teardown block can't do.

Extending Fixtures

Fixture files aren't limited to one flat base.extend() call — they can build on each other, and one project's fixtures can extend another's, which is how larger codebases avoid one enormous fixtures file.

// auth-fixtures.ts
export const authTest = base.extend<{ loggedInPage: Page }>({
  loggedInPage: async ({ page }, use) => { /* ...login... */ await use(page); },
});

// checkout-fixtures.ts — extends authTest, adding on top of it rather than starting over
import { authTest } from './auth-fixtures';

export const checkoutTest = authTest.extend<{ checkoutPage: CheckoutPage }>({
  checkoutPage: async ({ loggedInPage }, use) => {
    await use(new CheckoutPage(loggedInPage));
  },
});

checkoutTest now has both loggedInPage and checkoutPage available, without redefining the login logic — a test file that only needs auth imports from auth-fixtures, one that needs checkout too imports from checkout-fixtures. Playwright also provides mergeTests() for combining multiple independent fixture files (rather than one extending another) when two unrelated fixture sets both need to be available together:

import { mergeTests } from '@playwright/test';
import { authTest } from './auth-fixtures';
import { apiTest } from './api-fixtures';

export const test = mergeTests(authTest, apiTest); // has fixtures from BOTH files

Overriding an inherited fixture (rather than adding a new one) is also supported — a later .extend() call can redefine a fixture the base already provides, useful when one specific test file needs slightly different behavior (a different login role, a mocked version of an otherwise-real fixture) without affecting every other file that imports the original.

Common mistakes

  • Making an expensive, shareable resource test-scoped by default, slowing the whole suite down — check whether it actually needs per-test isolation before defaulting to test scope.
  • Overusing automatic fixtures for things only some tests need, making test behavior harder to trace back to its source.
  • Forgetting the teardown half after use() — a fixture that opens a resource but never cleans it up will leak across a long test run.
  • Reaching for a fixture when a plain hook would do — a one-off setup used by a single test file doesn't need the extra indirection of a custom fixture.

beforeEach vs. Fixture vs. beforeAll

Use for
beforeEachSimple, file-local setup used by every test in that file.
FixtureSetup shared across many files, with dependencies, or that needs teardown logic tied to it.
beforeAllGenuinely one-time, expensive setup with no per-test variation.

Best practices

  • Default new fixtures to test scope; promote to worker scope only when the setup is provably expensive and safely shareable.
  • Keep the teardown half of every fixture symmetrical with its setup — whatever you open, close.
  • Reserve { auto: true } for setup that genuinely applies to every single test in the project.
  • Put shared fixtures in a dedicated fixtures.ts file and import test/expect from there, not from @playwright/test directly, once a project has more than one or two custom fixtures.

Summary

Fixtures are named, declarative setup that Playwright builds on demand and tears down automatically, with dependencies resolved for you. Built-in fixtures like page and browser already use this system, at test and worker scope respectively. Custom fixtures — for logins, page objects, API tokens, or seeded data — are the main tool for scaling shared setup across a large suite without repeating it, and are the foundation Chapter 11's framework architecture builds on.

Interview Questions

Why would you make a fixture worker-scoped instead of test-scoped, and what's the risk of getting it wrong?▾
Worker scope reuses the fixture's value across every test in that worker, so it's right for expensive setup that's safe to share, like an API token. Making something worker-scoped that actually needs per-test isolation — like a logged-in page — would leak state between tests. Making something test-scoped that's expensive to build but safe to share just wastes time rebuilding it unnecessarily for every test.
What's the real difference between expect(locator) and worker-scoped vs test-scoped fixtures?▾
Test-scoped fixtures rebuild fresh for every test (right for isolation, like page); worker-scoped fixtures build once per worker and are reused (right for expensive, safely shareable resources).
What does the use() call inside a fixture actually do?▾
It's the pivot point — everything before it is setup, everything after is teardown, and Playwright guarantees the teardown half runs even if the test throws.
How do you combine fixtures from two independent fixture files?▾
Use mergeTests() to combine them, or have one file's test extend() the other's if one should build on top of it.
Why is a 'cleanup fixture' shaped differently from the other fixture patterns?▾
Its use() call hands the test a function to register cleanup work during the test body, rather than handing back a ready-to-use resource.
