Parallel Execution & Workers

Beginner 6 min read

Prerequisites: Architecture, Configuration Options

What is this?

Recall from the Architecture chapter: each worker is a separate Node.js process with its own browser instance. This chapter is about designing tests that actually run correctly under that model — since parallel execution introduces failure modes that don't exist when everything runs sequentially.

Why it's important

Parallelism is where the biggest speed gains in a large suite come from, but it's also where subtle bugs appear — two tests sharing a database record, a global counter, or a fixed test account can pass individually and fail unpredictably when run alongside each other.

How Playwright Distributes Work

export default defineConfig({
  workers: 4,
  fullyParallel: true, // individual tests within a file also run in parallel, not just files
});

By default, Playwright parallelizes at the file level — each worker takes whole files. fullyParallel: true goes further, parallelizing individual tests within a file too, which usually means faster runs but places a stricter requirement on true test isolation within a file, not just between files.

Basic Example — Worker-Safe vs. Worker-Unsafe Test Data

// ❌ Worker-unsafe — two parallel tests hitting the same fixed account
// will race against and interfere with each other's state
test('user can update their profile name', async ({ page }) => {
  await loginAs('shared-test-user@example.com', page);
  // ...
});

// ✅ Worker-safe — each test gets its own unique data
test('user can update their profile name', async ({ page }) => {
  const email = `test-${Date.now()}-${Math.random()}@example.com`;
  await registerNewUser(email, page);
  // ...
});

Detailed Example — Using workerInfo for Deterministic Uniqueness

test('creates a uniquely-named list per worker', async ({ page }, testInfo) => {
  const listName = `Test List (worker ${testInfo.workerIndex})`;
  await page.getByLabel('List name').fill(listName);
  await page.getByRole('button', { name: 'Create list' }).click();

  await expect(page.getByText(listName)).toBeVisible();
});

testInfo.workerIndex is a clean way to guarantee uniqueness without random values, when a test needs data that's stable within a single worker's tests but distinct from what other workers are doing simultaneously.

Real-World Example — A Worker-Scoped Shared Resource

// A worker-scoped fixture (from the Fixtures chapter) is the correct place
// for something genuinely safe to share across all tests IN ONE WORKER —
// like a single API token that's expensive to fetch but read-only
export const test = base.extend<{}, { apiToken: string }>({
  apiToken: [async ({}, use) => {
    const token = await fetchServiceToken();
    await use(token);
  }, { scope: 'worker' }],
});

This is the same worker-scoped fixture pattern from the Fixtures chapter, revisited here specifically for what it means under parallel execution: it's fetched once per worker, not once for the whole run and not once per test — exactly the right granularity for something expensive but safely read-only.

Tuning Worker Count

SettingEffect
workers: undefined (default)Auto-detects based on CPU cores (roughly half, locally)
workers: 1Fully sequential — useful for debugging a suspected worker-isolation bug
workers: NFixed count — common in CI where auto-detection may not match actual available capacity

More workers isn't always faster: past your CPU's real capacity, additional workers compete for resources and can make the whole run slower, not faster — this is worth actually measuring for your specific CI runner rather than assuming higher is always better.

❌ Fragile vs. ✅ Recommended

// ❌ A global variable shared across tests in the same file, assuming sequential order
let cartItemCount = 0;
test('adding an item increases the count', async ({ page }) => {
  cartItemCount++; // breaks under fullyParallel — order isn't guaranteed
});

// ✅ Each test manages its own independent state
test('adding an item increases the count', async ({ page }) => {
  const initialCount = await getCartCount(page);
  await addItemToCart(page);
  await expect(page.getByTestId('cart-count')).toHaveText(String(initialCount + 1));
});

Common Mistakes

  • Using a single shared test account or fixed test data across many tests, causing collisions once those tests run in parallel across different workers.
  • Relying on test execution order (assuming test B runs after test A within a file) — fullyParallel makes no such guarantee, and even without it, order shouldn't be load-bearing for correctness.
  • Setting an arbitrarily high worker count without measuring whether it actually improves total run time on the real CI hardware.
  • Debugging a suspected race condition with workers still parallelized — set workers: 1 temporarily to isolate whether an issue is genuinely about parallel execution or something else entirely.

Edge Cases

  • Tests that must run in a specific sequence (rare, but sometimes genuinely necessary) — test.describe.serial() forces tests within that block to run in order, in the same worker, as an explicit, deliberate escape hatch rather than an accidental dependency.
  • Rate-limited external APIs — many parallel workers hitting the same rate-limited third-party service simultaneously can cause failures unrelated to the application under test; consider a lower worker count or request throttling for suites that hit real external services.

Debugging

If a test fails intermittently and only under full parallel execution, re-run with workers: 1 to check whether it passes reliably in isolation — if it does, the bug is almost certainly a shared-state or ordering assumption, not the feature itself.

Best Practices

  • Generate unique test data per test (timestamps, random values, or testInfo.workerIndex) rather than reusing fixed accounts or records.
  • Never assume test execution order; use test.describe.serial() explicitly on the rare occasions order genuinely matters.
  • Reserve worker-scoped fixtures for genuinely expensive, safely shareable, read-only resources.
  • Measure actual run time at different worker counts on your real CI hardware rather than guessing at an optimal number.

Practice Exercise

Take a test that currently logs in as a single hardcoded test user shared across the file, and rewrite it to register a uniquely generated user per test, so it's safe to run under fullyParallel: true.

Summary

Playwright parallelizes across worker processes, each with its own browser and (by default) its own file assignment — fullyParallel extends this to individual tests within a file. Worker-safe test design means unique data per test, no assumptions about execution order, and reserving shared/worker-scoped state for things that are genuinely safe to share.

Interview Questions

A test passes reliably when run alone but fails intermittently as part of the full parallel suite. What would you investigate first?▾
Shared state — check whether the test uses a fixed test account, a hardcoded record ID, or any data that another test running concurrently in a different worker might also be reading or modifying. Re-running with workers: 1 is a fast way to confirm: if the test becomes reliable, the root cause is almost certainly a worker-isolation violation rather than a bug in the feature under test.
A test passes alone but fails intermittently in the full parallel suite — what's the first thing to check?▾
Shared state — a fixed test account, hardcoded record ID, or any data another concurrently running test might also touch.
What does fullyParallel: true actually change?▾
It parallelizes individual tests within a file, not just whole files across workers, which is the default without it.
Why is testInfo.workerIndex useful for generating test data?▾
It provides a stable, deterministic way to guarantee uniqueness across workers without needing random values.
Is more workers always faster?▾
No — past your machine's or CI runner's actual CPU capacity, additional workers compete for resources and can slow the whole run down.
