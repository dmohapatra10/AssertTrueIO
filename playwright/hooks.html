Chapter 17: Hooks

Beginner 9 min read

Prerequisites: Playwright Test Runner

What is this?

Hooks let you run setup and teardown code around your tests — before each test, after each test, once before all tests in a file, or once after. They're how repeated setup (navigating to a starting page, seeding data) gets factored out of every individual test.

Why it's important

Without hooks, every test repeats its own setup inline, which is both repetitive and easy to get subtly inconsistent between tests. But hooks are also a common source of hidden coupling between tests if used carelessly — this chapter covers both the mechanics and the discipline needed to use them well.

Test Lifecycle

For a single test, the lifecycle runs in exactly this order:

Test Suite
   │
   ▼
beforeAll
   │
   ▼
beforeEach
   │
   ▼
Test
   │
   ▼
afterEach
   │
   ▼
afterAll

That linear picture is exactly right for a suite with one test — but it slightly understates what happens with more than one, which is the far more common real case:

Mental Model — Execution Order With Multiple Tests

beforeAll                (once, start of file)
   │
   ├── beforeEach → Test 1 → afterEach
   ├── beforeEach → Test 2 → afterEach
   ├── beforeEach → Test 3 → afterEach
   │
afterAll                 (once, end of file)

beforeAll and afterAll genuinely run exactly once each — at the very start and very end of the file — no matter how many tests it contains. beforeEach and afterEach, by contrast, wrap every individual test: with three tests in a file, you get three full beforeEach → Test → afterEach cycles, not one. The simple linear diagram above is the correct mental model for what happens around any single test; this one is the correct picture for a whole file.

With nested describe blocks, outer hooks always run before/after inner ones for each test — an outer beforeEach fires before an inner beforeEach, and the corresponding afterEach hooks unwind in the reverse order, the same nesting behavior you'd expect from any layered setup/teardown pattern.

The Four Hooks

import { test } from '@playwright/test';

test.beforeEach(async ({ page }) => {
  await page.goto('/dashboard'); // runs before every test in this file/describe block
});

test.afterEach(async ({ page }, testInfo) => {
  console.log(`${testInfo.title} finished with status: ${testInfo.status}`);
});

test.beforeAll(async () => {
  // runs once, before any test in this file — no page/context fixture available here
});

test.afterAll(async () => {
  // runs once, after all tests in this file complete
});

beforeEach/afterEach receive the same fixtures (like page) as a regular test, since a fresh one exists for each test. beforeAll/afterAll run once for the whole file and don't get a per-test page fixture, since no single test's isolated context exists yet at that point.

Basic Example — Scoping Hooks to a describe Block

test.describe('admin panel', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/admin');
    await page.getByLabel('Email').fill('admin@example.com');
    await page.getByLabel('Password').fill('admin-password');
    await page.getByRole('button', { name: 'Sign in' }).click();
  });

  test('can view all users', async ({ page }) => {
    await expect(page.getByRole('heading', { name: 'Users' })).toBeVisible();
  });

  test('can suspend a user', async ({ page }) => {
    await page.getByRole('button', { name: 'Suspend' }).first().click();
  });
});

A hook inside a describe block only applies to tests within that block — this is the main tool for giving different groups of tests different setup without repeating it in every single test.

Detailed Example — Extra Diagnostics on Failure via afterEach

test.afterEach(async ({ page }, testInfo) => {
  if (testInfo.status !== testInfo.expectedStatus) {
    // Capture an extra full-page screenshot specifically for failed tests,
    // beyond whatever the config's default screenshot setting already captures
    const screenshotPath = testInfo.outputPath('failure.png');
    await page.screenshot({ path: screenshotPath, fullPage: true });
    testInfo.attachments.push({ name: 'failure-screenshot', path: screenshotPath, contentType: 'image/png' });
  }
});

testInfo carries useful metadata about the test that just ran — its title, status, and duration — making afterEach a natural place for custom failure diagnostics beyond what automatic screenshot/video/trace config already provides.

Real-World Example — Seeding and Cleaning Up Test Data

import { test, expect } from '@playwright/test';

test.describe('order cancellation', () => {
  let orderId: string;

  test.beforeEach(async ({ request }) => {
    // Seed a fresh order via the API before each test, rather than the UI —
    // faster and decoupled from unrelated UI flows.
    const response = await request.post('/api/orders', {
      data: { item: 'Wireless Mouse', quantity: 1 },
    });
    ({ id: orderId } = await response.json());
  });

  test.afterEach(async ({ request }) => {
    await request.delete(`/api/orders/${orderId}`);
  });

  test('customer can cancel a pending order', async ({ page }) => {
    await page.goto(`/orders/${orderId}`);
    await page.getByRole('button', { name: 'Cancel order' }).click();
    await expect(page.getByText('Order cancelled')).toBeVisible();
  });
});

This uses afterEach for cleanup regardless of whether the test passed or failed — important, since leftover test data from a failed test can otherwise pollute the next run.

Hooks vs. Fixtures — Quick Recap

The Fixtures chapter covers this comparison in full, but the short version: a hook is simpler and file/describe-scoped, right for setup only a handful of tests in one file need. A fixture is reusable across many files, supports dependencies between fixtures, and separates "what a test needs" from "how it's built" — worth the extra structure once shared setup spans more than one test file.

❌ Fragile vs. ✅ Recommended

// ❌ Shared mutable state across tests via beforeAll — makes test order matter
let sharedOrderId;
test.beforeAll(async ({ request }) => {
  const res = await request.post('/api/orders', { data: { /* ... */ } });
  sharedOrderId = (await res.json()).id;
});
// Multiple tests now all depend on the SAME order, and on running after this hook

// ✅ Fresh data per test via beforeEach — no cross-test coupling
let orderId;
test.beforeEach(async ({ request }) => {
  const res = await request.post('/api/orders', { data: { /* ... */ } });
  orderId = (await res.json()).id;
});

Common Mistakes

  • Sharing mutable state between tests via a variable set in beforeAll and mutated by individual tests — this makes test order matter, breaking the isolation the test runner otherwise guarantees, especially under parallel execution.
  • Putting expensive UI-based login in beforeEach for every single test in a large suite instead of using storageState (from the Browser/Context chapter) to skip repeating login entirely.
  • Forgetting cleanup in afterEach/afterAll, letting test data accumulate across runs.
  • Using a hook when a fixture would scale better — a hook duplicated across many files is a sign that setup belongs in a shared fixture instead.

Edge Cases

  • A hook that itself throws — if beforeEach fails, the test itself is marked failed without running at all, and any already-registered afterEach for that test still runs, giving cleanup a chance even when setup didn't fully succeed.
  • Multiple beforeEach hooks at the same level — Playwright runs them in the order they're declared, which matters if one depends on state set up by another.

Debugging

If a test's actual body never seems to run, check whether a beforeEach at any enclosing level is silently failing or hanging — Trace Viewer (Chapter 15) includes hook execution in its timeline, making this visible rather than needing to guess.

Best Practices

  • Prefer API calls over UI actions for setup/teardown in hooks (as in the example above) — faster, and decoupled from whatever the UI flow being tested is.
  • Keep beforeAll/afterAll for genuinely one-time, expensive setup; default to beforeEach/afterEach otherwise to preserve test isolation.
  • Always pair setup with corresponding teardown, especially anything that writes real data.
  • Once a hook's logic is duplicated across more than one or two files, consider promoting it to a fixture instead.

Practice Exercise

Write a describe block for a "user profile" suite that uses beforeEach to create a test user via the API, and afterEach to delete that user regardless of whether the test passed or failed.

Summary

Hooks factor out repeated setup and teardown — beforeEach/afterEach run per-test with full fixture access, while beforeAll/afterAll run once per file without one. Scoping hooks to a describe block is the main tool for giving different groups of tests different setup, and API-based setup in hooks is usually faster and more reliable than UI-based setup — with fixtures as the natural next step once setup needs to be shared across files.

Interview Questions

Why don't beforeAll and afterAll receive the page fixture the way beforeEach and afterEach do?▾
The test runner creates a fresh, isolated BrowserContext and page for each individual test. beforeAll/afterAll run once for an entire file, before any single test's isolated context exists (or after all of them have finished), so there's no single test-scoped page to hand them — using page-level fixtures there would break the per-test isolation model.
How many times do beforeAll and afterAll run in a file with 10 tests?▾
Exactly once each — at the very start and very end of the file — regardless of how many tests it contains.
Why don't beforeAll/afterAll receive the page fixture the way beforeEach/afterEach do?▾
They run before any single test's isolated context exists (or after all finish), so there's no per-test page to hand them.
What's a common mistake with hooks and parallel execution?▾
Sharing mutable state across tests via a variable set in beforeAll, which makes test order matter and breaks isolation under parallel runs.
When should you promote a hook to a fixture instead?▾
Once its logic is duplicated across more than one or two files — that's a sign the setup belongs in shared, reusable fixture code.
