Page Object Model

Beginner 7 min read

Prerequisites: Fixtures, Projects & Environments

What is this?

The Page Object Model (POM) wraps a page's locators and interactions in a class, so tests call readable, intention-revealing methods (loginPage.signIn(email, password)) instead of repeating raw locator chains everywhere. This is where this course shifts from "how do I write a test" to "how do I build a maintainable suite of many tests."

Why it's important

Without POM, the same locator (say, the "Add to cart" button) gets duplicated across dozens of tests. When that button's accessible name or structure changes, every duplicated copy needs updating. With POM, it's defined once, and every test that uses it automatically benefits from the fix.

Basic Example — A Simple Page Object

// pages/login-page.ts
import { Page, Locator } from '@playwright/test';

export class LoginPage {
  readonly page: Page;
  readonly emailInput: Locator;
  readonly passwordInput: Locator;
  readonly signInButton: Locator;

  constructor(page: Page) {
    this.page = page;
    this.emailInput = page.getByLabel('Email');
    this.passwordInput = page.getByLabel('Password');
    this.signInButton = page.getByRole('button', { name: 'Sign in' });
  }

  async goto() {
    await this.page.goto('/login');
  }

  async signIn(email: string, password: string) {
    await this.emailInput.fill(email);
    await this.passwordInput.fill(password);
    await this.signInButton.click();
  }
}
// login.spec.ts
import { test, expect } from '@playwright/test';
import { LoginPage } from './pages/login-page';

test('valid credentials redirect to the dashboard', async ({ page }) => {
  const loginPage = new LoginPage(page);
  await loginPage.goto();
  await loginPage.signIn('user@example.com', 'correct-horse-battery-staple');

  await expect(page).toHaveURL('/dashboard');
});

Notice the assertion stays in the test, not the page object — a deliberate boundary covered in detail below.

Combining POM With Fixtures

The cleanest real-world pattern (foreshadowed in the Fixtures chapter) injects page objects as fixtures instead of instantiating them manually in every test:

// fixtures.ts
import { test as base } from '@playwright/test';
import { LoginPage } from './pages/login-page';
import { DashboardPage } from './pages/dashboard-page';

type Pages = { loginPage: LoginPage; dashboardPage: DashboardPage };

export const test = base.extend<Pages>({
  loginPage: async ({ page }, use) => { await use(new LoginPage(page)); },
  dashboardPage: async ({ page }, use) => { await use(new DashboardPage(page)); },
});
export { expect } from '@playwright/test';
// login.spec.ts
import { test, expect } from './fixtures';

test('valid credentials redirect to the dashboard', async ({ loginPage, dashboardPage }) => {
  await loginPage.goto();
  await loginPage.signIn('user@example.com', 'correct-horse-battery-staple');
  await expect(dashboardPage.welcomeHeading).toBeVisible();
});

No manual new LoginPage(page) anywhere in the test file — the fixture handles construction, and every test that needs the page object just declares it as a parameter.

A Base Page for Shared Behavior

// pages/base-page.ts
export class BasePage {
  constructor(protected page: Page) {}

  async waitForToast(text: string) {
    await expect(this.page.getByRole('status')).toHaveText(text);
  }
}

// pages/login-page.ts
export class LoginPage extends BasePage {
  // inherits waitForToast() automatically
}

A base page is worth introducing once several page objects share genuinely common behavior (a toast helper, a nav bar present on every page) — but see the anti-patterns below for how this can be overdone.

Component Objects — Reusable UI Pieces

// components/nav-bar.ts
export class NavBar {
  constructor(private page: Page) {}

  async goToOrders() {
    await this.page.getByRole('link', { name: 'Orders' }).click();
  }
}

// A page object can compose a shared component rather than duplicating it
export class DashboardPage extends BasePage {
  readonly navBar: NavBar;
  constructor(page: Page) {
    super(page);
    this.navBar = new NavBar(page);
  }
}

Component objects address the same "structure that appears on many pages" problem POM solves at the page level, applied to a shared header, sidebar, or modal that appears across many different pages.

❌ Anti-Pattern vs. ✅ Recommended

// ❌ Assertions living inside the page object
class LoginPage {
  async signIn(email, password) {
    // ...
    await expect(this.page).toHaveURL('/dashboard'); // hides what the test actually verifies
  }
}

// ✅ Page objects perform actions; tests own their own assertions
class LoginPage {
  async signIn(email, password) { /* actions only, no expect() calls */ }
}
test('...', async ({ page }) => {
  await loginPage.signIn(...);
  await expect(page).toHaveURL('/dashboard'); // visible, explicit, in the test
});

Common Mistakes (What NOT to Do)

  • Giant page objects covering an entire large application in one class — split by logical page or feature area instead, mirroring how a user would actually navigate.
  • Assertions inside page objects — this hides what a test is actually verifying behind a method name, and makes tests harder to read and debug. Page objects should expose locators and perform actions; tests should own their own expect() calls.
  • Business logic mixed with UI interaction — a page object method that calculates a discounted price and asserts on it is doing two unrelated jobs; keep page objects focused purely on interacting with the DOM.
  • Excessive inheritance chains (a page object extending a class that extends another class three levels deep) — prefer composition (component objects) over deep inheritance for shared behavior.
  • Over-abstraction — wrapping a single, simple page.goto('/settings') in an elaborate page object with no other meaningful behavior adds indirection without benefit.

Edge Cases

  • A page object needing conditional behavior across environments (a feature flag hidden in one environment) — keep this logic explicit and visible, ideally as a clearly named method or parameter, not silently branching inside a shared method.
  • Very simple pages with almost no interaction — not every page needs a page object; a one-line page.goto('/about') plus a direct assertion in the test is often clearer than a page object with a single trivial method.

Debugging

If a test fails inside a page object method and the failure is hard to trace, check whether the method is doing too much — a page object method that does five things in sequence makes it unclear which one actually failed; breaking it into smaller, named methods (or using test.step() around the call site) usually helps.

Best Practices

  • Page objects encapsulate locators and actions; tests own assertions.
  • Inject page objects via fixtures rather than manual instantiation in every test.
  • Use composition (component objects) for shared UI pieces rather than deep inheritance.
  • Don't create a page object for every page reflexively — reserve it for pages with genuine, reused interaction complexity.

Practice Exercise

Build a CheckoutPage page object with methods for filling shipping details and submitting payment (no assertions inside it), inject it via a fixture, and write two tests using it — one for successful checkout, one for a declined card — with each test owning its own assertions.

Summary

Page Object Model encapsulates locators and actions behind readable methods, reducing duplication and centralizing updates when the UI changes. Combine it with fixtures for clean injection, use composition over deep inheritance for shared UI pieces, and keep assertions in tests, not page objects — the single most important discipline for keeping a POM-based suite maintainable.

Interview Questions

Why is it generally considered an anti-pattern to put expect() assertions inside page object methods?▾
It hides what a test is actually verifying behind a method call, making tests harder to read and their failures harder to diagnose — a reader has to open the page object to discover what's being checked. Keeping assertions in the test itself makes the test's intent explicit at the call site, and keeps the page object focused on a single responsibility: interacting with the page, not verifying outcomes.
Why is putting expect() assertions inside page object methods considered an anti-pattern?▾
It hides what a test is actually verifying behind a method call, making the test's intent and failures harder to read and diagnose.
What's the cleanest way to make page objects available to tests?▾
Inject them via fixtures rather than manually instantiating them with `new` in every test file.
When would you use composition (component objects) over inheritance for shared page behavior?▾
For UI pieces that appear across many unrelated pages, like a shared nav bar — composition avoids deep, fragile inheritance chains.
Is it worth creating a page object for every single page in an app?▾
No — reserve it for pages with genuine, reused interaction complexity; a one-line goto() plus a direct assertion is often clearer for trivial pages.
