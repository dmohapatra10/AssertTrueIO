Chapter 9: Browser and BrowserContext

Beginner 10 min read

Prerequisites: Playwright Architecture, Pages and Navigation

What is this?

Chapter 3 introduced Browser and BrowserContext conceptually. This chapter is the practical follow-up: the actual options you configure on each — launch options for the browser, and context options that control viewport, permissions, geolocation, cookies, and stored session state.

Why it's important

Most real test suites need at least a few of these options — a mobile viewport for responsive testing, geolocation for a location-aware feature, denied permissions to test a fallback UI, or reused login state so hundreds of tests don't each perform a fresh login. Knowing what's configurable here removes a lot of workarounds people otherwise reach for.

Launching a Browser

import { chromium } from '@playwright/test';

const browser = await chromium.launch({
  headless: false,   // show the browser window
  slowMo: 100,       // slow down each operation by 100ms, useful for debugging
});

In most projects, though, you never call launch() yourself — the Test Runner manages the browser lifecycle for you based on playwright.config.ts, and these options are set there under each project's use block instead.

Common BrowserContext Options

OptionPurpose
viewportSimulated browser window size
userAgentOverride the reported user agent string
geolocation / permissionsSimulated GPS coordinates and granted browser permissions
locale / timezoneIdSimulated language and timezone
storageStatePreloaded cookies/localStorage — the basis for session reuse
colorSchemeSimulate light or dark mode preference

Basic Example — Mobile, Geolocation-Aware Context

const context = await browser.newContext({
  viewport: { width: 390, height: 844 },
  geolocation: { latitude: 51.5074, longitude: -0.1278 },
  permissions: ['geolocation'],
  locale: 'en-GB',
});

const page = await context.newPage();
await page.goto('/nearby-stores');
await expect(page.getByText('London')).toBeVisible();

Timezone

timezoneId is easy to overlook until a test needs to verify something that's genuinely timezone-sensitive — a "delivery by 6pm local time" message, a scheduling widget, or a timestamp displayed in the user's own timezone rather than UTC. Without setting it, contexts inherit whatever timezone the machine running the test happens to be in, which is exactly the kind of hidden, environment-dependent behavior that makes a test pass locally and fail (or vice versa) in CI.

const context = await browser.newContext({
  timezoneId: 'America/New_York',
});
const page = await context.newPage();
await page.goto('/schedule-delivery');

// The app renders delivery slots in the context's local time —
// this assertion is only meaningful because the timezone is pinned explicitly
await expect(page.getByText('Delivery slot: 2:00 PM EST')).toBeVisible();

Use the standard IANA timezone database names ('America/New_York', 'Europe/London', 'Asia/Kolkata') — the same identifiers JavaScript's own Intl API and most backend systems use, so there's no separate mapping to maintain. Pair timezoneId with locale when a feature depends on both (a date format and a local time), since they're independent settings that don't imply each other — setting locale: 'en-GB' does not also set the timezone to London.

Detailed Example — Reading and Setting Cookies Directly

// Read all cookies in the current context
const cookies = await context.cookies();
console.log(cookies.find((c) => c.name === 'session_id'));

// Set a cookie directly, bypassing the UI entirely — useful for seeding
// state a test doesn't actually need to exercise
await context.addCookies([{
  name: 'feature_flag_new_checkout',
  value: 'true',
  domain: 'staging.example.com',
  path: '/',
}]);

Manipulating cookies and storage directly is a common technique for setting up preconditions a test doesn't care about testing itself — feature flags, consent banners already dismissed, A/B test bucketing — without spending time clicking through UI that isn't the point of the test.

Local Storage and Session Storage

Not every app stores state in cookies — many keep it in the browser's localStorage or sessionStorage instead (a JWT auth token, a "don't show this tip again" flag, a theme preference). These live per-origin, separately from cookies, and Playwright reads and writes them through the page's own JavaScript context rather than a dedicated context-level API like cookies().

// Read a value out of localStorage
const theme = await page.evaluate(() => window.localStorage.getItem('theme'));

// Set a value directly, bypassing the UI — e.g. pre-seed a dismissed announcement banner
await page.addInitScript(() => {
  window.localStorage.setItem('announcement_dismissed', 'true');
});

// sessionStorage works the same way, but the value only persists for that one tab's session
await page.evaluate(() => window.sessionStorage.setItem('wizard_step', '2'));

page.addInitScript() is the important detail here — it runs before the page's own scripts on every navigation in that page, which is what lets you seed a localStorage value the app will actually read on its very first load. Setting it via a plain page.evaluate() call after the page has already loaded works for values the app reads later, but is too late for anything the app checks during its initial render.

This is also why storageState (below) captures more than just cookies: it snapshots each origin's localStorage alongside its cookies, which is exactly what's needed to correctly reproduce a session where auth lives in a token rather than a cookie.

Testing a Denied-Permission Fallback

const context = await browser.newContext({ permissions: [] }); // deny geolocation
const page = await context.newPage();
await page.goto('/nearby-stores');

await expect(page.getByText('Enable location to see nearby stores')).toBeVisible();

This is easy to overlook but important: apps that request a browser permission almost always need a fallback UI for when it's denied, and that fallback is just as testable as the happy path — simply omit the permission instead of granting it.

Real-World Example — Persisting Login with storageState

// Log in once, save the resulting session
const context = await browser.newContext();
const page = await context.newPage();
await page.goto('/login');
await page.getByLabel('Email').fill('user@example.com');
await page.getByLabel('Password').fill('correct-horse-battery-staple');
await page.getByRole('button', { name: 'Sign in' }).click();
await context.storageState({ path: 'auth.json' });

// Later tests: start already logged in
const authedContext = await browser.newContext({ storageState: 'auth.json' });

This is normally wired into the Test Runner's project configuration rather than written by hand in every test file — covered in depth in the Authentication chapter.

Multiple Contexts for Multi-User Scenarios

test('two users can chat with each other', async ({ browser }) => {
  const alice = await (await browser.newContext()).newPage();
  const bob = await (await browser.newContext()).newPage();

  await alice.goto('/chat');
  await bob.goto('/chat');

  await alice.getByLabel('Message').fill('Hi Bob!');
  await alice.getByRole('button', { name: 'Send' }).click();

  await expect(bob.getByText('Hi Bob!')).toBeVisible();
});

Because each context is a fully isolated "profile," this genuinely simulates two separate browser sessions in one test — the deliberate, correct use of multiple contexts referenced back in Chapter 3.

Multiple Pages Within One Context

Distinct from multiple contexts (different isolated users) is multiple pages within the same context — several open tabs that deliberately do share the same cookies and login session, exactly like a real person opening a second tab in the same browser window instead of a separate incognito session.

const context = await browser.newContext();

const productPage = await context.newPage();
await productPage.goto('/products/wireless-mouse');

// Open a second tab in the SAME context — shares the same login session
const cartPage = await context.newPage();
await cartPage.goto('/cart');

// Both pages see the same logged-in user, because they belong to one context
await productPage.getByRole('button', { name: 'Add to cart' }).click();
await cartPage.reload();
await expect(cartPage.getByText('Wireless Mouse')).toBeVisible();

This is the mechanism underneath every "opens in a new tab" interaction a real user triggers — clicking a target="_blank" link, a "sign in with Google" popup — which is why context.pages() returns every currently open page in that context, and why capturing a newly opened tab (covered fully in the Multiple Tabs & Windows chapter) means listening for the context's page event rather than expecting a return value from the click itself.

console.log(context.pages().length); // 2 — productPage and cartPage, both still open

await cartPage.close(); // closing one page doesn't affect the context or its other pages
console.log(context.pages().length); // 1

The distinction to keep straight: reach for a new context when you need genuinely separate identities (two different logged-in users, as in the chat example above); reach for a new page in the same context when you're modeling one user who simply has more than one tab open.

❌ Fragile vs. ✅ Recommended

// ❌ Setting viewport inline in every mobile-related test
test('mobile menu opens', async ({ browser }) => {
  const context = await browser.newContext({ viewport: { width: 390, height: 844 } });
  // ...
});

// ✅ Define a dedicated mobile project once in playwright.config.ts
// projects: [{ name: 'Mobile Safari', use: { ...devices['iPhone 13'] } }]

Common Mistakes

  • Calling browser.launch() manually inside tests that already run under the Test Runner, duplicating what the runner already manages via playwright.config.ts.
  • Setting viewport per-test with inline code instead of defining a dedicated mobile project in the config, making mobile coverage inconsistent across the suite.
  • Forgetting to grant a permission that a simulated capability (geolocation, notifications) depends on, then debugging the wrong layer when it silently fails.
  • Not testing the denied-permission path — teams often only test the granted case, leaving the fallback UI uncovered.

Edge Cases

  • Permissions that require a user gesture in real browsers (like clipboard access) — Playwright's permissions option pre-grants these for testing, bypassing the interactive prompt a real user would see.
  • Contexts with expired storageState — a saved session with an expired token will silently behave as logged-out; regenerate auth.json periodically or as part of CI setup rather than committing a long-lived static file.

Debugging

If a location- or permission-dependent feature isn't behaving as expected, check context.cookies()/context.storageState() directly in a debug session or via --debug mode to confirm the simulated values actually took effect, rather than assuming the option was applied correctly.

Best Practices

  • Configure context options (viewport, locale, permissions) at the project level in playwright.config.ts wherever they apply to a whole class of tests, not per-test.
  • Use storageState for any suite where more than a handful of tests require being logged in.
  • Only reach for manual browser.newContext() calls for scenarios that genuinely need multiple simultaneous contexts within one test — most tests should rely on the runner's built-in page fixture instead.
  • Test both the granted and denied paths for any feature that depends on a browser permission.

Practice Exercise

Write a test that creates two separate browser contexts representing two different users with different storageState files, and verifies one user can't see the other's private data on a shared dashboard URL.

Summary

Browser launch options control the browser process itself; BrowserContext options control the isolated session within it — viewport, locale, permissions, cookies, and stored login state among them. Most of these belong in playwright.config.ts rather than scattered through individual tests, and storageState is the standard way to avoid repeating login across a whole suite.

Interview Questions

Where should context options like viewport and locale typically be configured in a real project, and why?▾
In playwright.config.ts, as part of a project's use block, rather than inline in individual tests. Centralizing them keeps every test in that project consistent automatically, and makes adding a new device/locale target (e.g., a mobile Safari project) a config change rather than an edit to every test file.
What's the difference between opening a new context versus a new page in the same context?▾
A new context is a genuinely separate identity with its own cookies/storage; a new page in the same context shares the session, like a second tab for the same logged-in user.
Why does page.addInitScript() matter for seeding localStorage?▾
It runs before the page's own scripts on every navigation, letting you seed a value the app reads during its very first render — a plain evaluate() after load would be too late.
Why is a database connection typically a worker-scoped fixture rather than test-scoped?▾
It's expensive to open and safe to share across tests in the same worker, unlike page-level state which genuinely needs per-test isolation.
What's a common mistake with browser permissions in tests?▾
Only testing the granted-permission path and never testing the denied-permission fallback UI, which most apps also need to handle correctly.
