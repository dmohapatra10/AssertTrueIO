Configuration Options

Beginner 8 min read

Prerequisites: Getting Started, Network Mocking

What is this?

playwright.config.ts has been referenced throughout this course — baseURL, storageState, trace, testIdAttribute. This chapter is the consolidated, dedicated look at the config file itself: the options that matter for almost every real project, in one place.

Why it's important

Scattering environment-specific values (base URLs, timeouts, credentials) through individual test files means changing environments requires editing many files. Centralizing them in config means switching environments, tuning reliability, or adjusting reporting is a one-line change.

The Options That Matter Most

import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  timeout: 30_000,               // per-test timeout
  expect: { timeout: 5_000 },    // per-assertion timeout
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 4 : undefined, // undefined = auto-detect based on CPU cores
  fullyParallel: true,
  reporter: [['html'], ['junit', { outputFile: 'results.xml' }]],
  outputDir: 'test-results',

  use: {
    baseURL: process.env.BASE_URL || 'http://localhost:3000',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
  },

  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox', use: { ...devices['Desktop Firefox'] } },
  ],
});

timeout vs. expect.timeout

These are easy to confuse because they sound similar but apply at different scopes:

OptionApplies toDefault
timeoutThe whole test — everything it does, combined30 seconds
expect.timeoutEach individual web-first assertion's retry window5 seconds

A test can have a 30-second overall timeout while each assertion within it only gets 5 seconds to resolve before that specific assertion fails — raising the global timeout doesn't extend how long any single assertion waits.

The Remaining Options: testMatch, fullyParallel, outputDir, browserName, webServer, reporter

Six more options round out the set that matters for almost every project — each shown above in passing, each worth its own explanation:

export default defineConfig({
  testMatch: '**/*.spec.ts',      // which files count as tests (this is the default pattern)
  fullyParallel: true,             // parallelize individual tests within a file, not just whole files
  outputDir: 'test-results',       // where screenshots/videos/traces get written
  reporter: 'html',                // which reporter(s) to use — see the Reporting chapter for the full set

  use: {
    browserName: 'chromium',       // explicit engine choice, when not using the projects array
  },

  webServer: {
    command: 'npm run start',      // start the app under test automatically before running tests
    url: 'http://localhost:3000',
    reuseExistingServer: !process.env.CI,
  },
});
  • testMatch — the glob or regex pattern deciding which files the runner treats as tests. The default (**/*.spec.ts) is usually fine; it becomes useful to override when splitting test categories into different projects, as the Projects chapter shows for a smoke-vs-regression split.
  • fullyParallel — by default, Playwright parallelizes at the file level, running whole files concurrently across workers but tests within one file sequentially. Setting this to true parallelizes individual tests too, which is usually faster but places a stricter demand on true test isolation within a file (covered in the Parallelism chapter).
  • outputDir — where Playwright writes artifacts a test run produces: failure screenshots, videos, and traces. Rarely needs changing from its default, but worth knowing about before a screenshot path in an error message looks unfamiliar.
  • browserName — sets the browser engine directly inside use, as an alternative to defining a full projects array. Fine for a single-browser setup; once more than one browser or device target is needed, the projects array (Projects chapter) is the better tool, since browserName alone can't express "run this suite against three different browsers."
  • webServer — tells Playwright to start (and wait for) the application under test itself before running any tests, instead of assuming it's already running. reuseExistingServer: !process.env.CI is the standard pattern: locally, reuse a dev server you likely already have running; in CI, always start a fresh one.
  • reporter — which output format(s) to generate; accepts a single reporter name or an array of several at once. The full comparison of html, junit, json, github, and list — and when to use which — is covered in depth in the Reporting chapter.

webServer is worth calling out specifically: without it, every engineer and every CI job needs to remember to start the app manually before running tests, which is exactly the kind of easy-to-forget manual step that playwright.config.ts centralizing config is meant to eliminate — npx playwright test alone becomes enough to run the whole suite from a clean checkout.

Basic Example — Environment-Aware Retries and Workers

export default defineConfig({
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 4 : undefined,
});

Retries are usually enabled only in CI, not locally — locally, a failing test should surface immediately for debugging, not silently retry and mask a real, reproducible problem. Workers default to undefined locally (auto-detected from CPU cores) but are often pinned to a specific number in CI, where the runner's actual available cores may differ from what auto-detection assumes.

Detailed Example — Per-Test Overrides

// A specific test needs more time than the global default —
// override locally rather than raising the timeout for the whole suite
test('generates a large PDF export', async ({ page }) => {
  test.setTimeout(90_000);
  // ...
});

// Or override use-block options just for one file
test.use({ viewport: { width: 390, height: 844 } });

Prefer scoped overrides like these over raising a global default — a single genuinely slow test shouldn't force every test in the suite to wait longer before Playwright considers it hung.

Real-World Example — A Config Tuned for CI Reliability

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  forbidOnly: !!process.env.CI, // fail the build if test.only() was accidentally committed
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 4 : undefined,
  reporter: process.env.CI ? [['github'], ['html', { open: 'never' }]] : 'list',

  use: {
    baseURL: process.env.BASE_URL,
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
  },
});

forbidOnly is a small but valuable safeguard from the Test Runner chapter's common mistakes — it turns an accidentally committed test.only() into a hard CI failure instead of a silently disabled suite.

❌ Fragile vs. ✅ Recommended

// ❌ Hardcoded, environment-specific values scattered across test files
await page.goto('https://staging.example.com/login');

// ✅ Centralized in config, referenced via environment variable
// use: { baseURL: process.env.BASE_URL }
await page.goto('/login');

Common Mistakes

  • Confusing timeout and expect.timeout, raising the wrong one when a specific assertion needs more time.
  • Enabling retries locally, which can mask a genuinely flaky test that should be investigated, not silently passed on a second attempt.
  • Hardcoding a fixed worker count that doesn't match the actual CI runner's available cores, either under- or over-subscribing it.
  • Not setting forbidOnly for CI, allowing an accidentally committed test.only() to silently skip the rest of the suite in production CI runs.

Edge Cases

  • Different timeout needs per project (e.g., mobile Safari genuinely slower than desktop Chrome) — timeouts can be set per-project, not just globally, when one browser/device target consistently needs more headroom.
  • CI environments with variable, shared CPU availability — a fixed workers count is often safer than auto-detection on shared CI infrastructure, where the reported core count may not reflect actually available capacity.

Debugging

If a test times out and it's unclear whether it's the overall timeout or a specific expect.timeout, the error message names which one was exceeded — read it before adjusting either value, since raising the wrong one won't fix the actual issue.

Best Practices

  • Centralize every environment-specific value in config, referenced via environment variables — never hardcode a base URL or credential in a test file.
  • Keep retries off locally, on in CI.
  • Set forbidOnly: !!process.env.CI as a standing safeguard.
  • Override timeouts locally, per-test or per-project, rather than raising global defaults for the whole suite.

Practice Exercise

Write a playwright.config.ts that uses a different baseURL depending on an environment variable, enables retries and a fixed worker count only in CI, and sets forbidOnly appropriately.

Summary

playwright.config.ts centralizes everything environment- and reliability-related — base URL, timeouts (both global and per-assertion), retries, workers, and reporters — so switching environments or tuning CI behavior is a config change, not a multi-file edit. Environment variables plus conditional config values (like process.env.CI) are the standard way to make one config file serve both local and CI runs correctly.

Interview Questions

Why would a team typically enable retries in CI but not locally?▾
Locally, a developer wants immediate, clear feedback when a test fails so they can debug it right away — a silent retry that happens to pass the second time could mask a real, reproducible bug. In CI, some flakiness genuinely comes from environment variance (slower shared runners, network jitter) that isn't worth blocking a build over, so a bounded retry count there absorbs that noise while still surfacing consistently failing tests as real failures.
Why doesn't raising the global timeout fix an assertion that keeps timing out?▾
timeout and expect.timeout are separate scopes — the global one covers the whole test, while each assertion has its own independent retry window.
Why is enabling retries locally usually discouraged?▾
A silent retry that happens to pass on a second attempt can mask a real, reproducible bug a developer would otherwise catch immediately.
What does forbidOnly actually protect against?▾
An accidentally committed test.only() silently disabling the rest of the suite in CI — forbidOnly turns it into a hard build failure instead.
Why is webServer valuable beyond just convenience?▾
It removes an easy-to-forget manual step (starting the app) so a clean checkout can run the whole suite with just npx playwright test.
