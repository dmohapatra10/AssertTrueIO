Test Reporting

Beginner 6 min read

Prerequisites: Configuration Options, Trace Viewer

What is this?

A reporter turns raw test results into a specific output format. Playwright ships several built in, and the right choice depends on who's consuming the report — a human browsing results interactively, a CI system parsing pass/fail counts, or a custom dashboard ingesting structured data.

Why it's important

The HTML report (rich, interactive, includes traces/screenshots) is what a human wants to browse after a failure. JUnit XML is what most CI systems expect to render a pass/fail summary in their own UI. Using the wrong one for the wrong audience means either a human squinting at raw XML, or a CI dashboard that can't parse your results at all.

The Built-In Reporters

ReporterBest for
htmlHuman browsing — interactive, includes traces, screenshots, videos
listTerminal output while developing locally (the default)
junitCI systems that render JUnit XML natively (Jenkins, GitLab, Azure DevOps)
jsonCustom tooling, dashboards, or programmatic post-processing
githubGitHub Actions — annotates failures directly on the PR diff
dotMinimal terminal output — one character per test, useful for very large suites

Basic Example — Configuring Multiple Reporters at Once

export default defineConfig({
  reporter: [
    ['html', { open: 'never' }],
    ['junit', { outputFile: 'results/junit.xml' }],
    ['json', { outputFile: 'results/results.json' }],
  ],
});

Reporters aren't mutually exclusive — running several at once (one for humans, one for CI, one for custom tooling) is normal and costs almost nothing extra.

Viewing the HTML Report

npx playwright test
npx playwright show-report

The HTML report links directly to each failed test's trace, screenshot, and video (from the Screenshots & Videos and Trace Viewer chapters) — it's the natural jumping-off point for investigating any failure, not just a pass/fail summary.

Detailed Example — Environment-Aware Reporter Config

export default defineConfig({
  reporter: process.env.CI
    ? [['github'], ['html', { open: 'never' }], ['junit', { outputFile: 'results/junit.xml' }]]
    : 'list',
});

Locally, a developer just wants fast terminal feedback (list). In CI, you typically want the github reporter for inline PR annotations, an HTML report as a downloadable artifact for deeper investigation, and JUnit XML for the CI platform's own pass/fail UI — three different consumers, three different formats, one config line switching between them.

Real-World Example — Uploading the HTML Report as a CI Artifact

# GitHub Actions step, after running tests
- name: Upload HTML report
  if: always() # upload even if tests failed — that's when it matters most
  uses: actions/upload-artifact@v4
  with:
    name: playwright-report
    path: playwright-report/
    retention-days: 14

if: always() is the detail that's easy to miss — a report is most valuable exactly when tests failed, so the upload step must run regardless of the test step's outcome, not only on success.

Custom Reporting With the JSON Output

// A small script reading results.json to post a Slack summary
const results = JSON.parse(fs.readFileSync('results/results.json', 'utf-8'));
const failed = results.suites.flatMap(s => s.specs).filter(s => !s.ok);
console.log(`${failed.length} test(s) failed`);

The JSON reporter's structured output is the foundation for any custom integration — a Slack notification, a custom dashboard, a flaky-test tracker — that the built-in reporters don't directly support.

❌ Fragile vs. ✅ Recommended

// ❌ Only the terminal list reporter in CI — no artifact to investigate a failure afterward
export default defineConfig({ reporter: 'list' });

// ✅ HTML report as an uploaded artifact, plus a CI-native format
export default defineConfig({
  reporter: process.env.CI ? [['github'], ['html', { open: 'never' }]] : 'list',
});

Common Mistakes

  • Using only the terminal reporter in CI, with no HTML report artifact — once the CI logs scroll away, there's nothing left to actually investigate a failure with.
  • Forgetting if: always() when uploading report artifacts, so exactly the failed runs that need investigating produce no artifact at all.
  • Using open: 'always' in CI — this tries to open a browser window on a headless CI runner, which fails or hangs; use 'never' in CI and let the default apply locally.
  • Not using a CI-native reporter (like github or junit) when one's available, missing out on inline annotations or native pass/fail UI the CI platform already provides.

Edge Cases

  • Very large suites with thousands of tests — the dot reporter's minimal output can be more practical for terminal visibility than list, which prints a full line per test.
  • Multiple CI systems consuming the same run (e.g., both GitHub Actions and an external dashboard) — configuring several reporters simultaneously, as shown above, handles this without needing separate test runs.

Debugging

If a CI pass/fail summary looks wrong or incomplete, check that the correct reporter for that CI platform is actually configured and that its output file path matches what the CI job is configured to read — a mismatched path is a common, easy-to-miss cause of a CI step silently not finding results to parse.

Best Practices

  • Use list locally for fast feedback; use CI-native plus HTML in CI.
  • Always upload the HTML report as an artifact with if: always().
  • Configure multiple reporters simultaneously rather than picking just one — the cost is minimal and each serves a different audience.
  • Reach for the JSON reporter's output as the foundation for any custom reporting need the built-in reporters don't cover.

Practice Exercise

Configure a project to use list locally and github + html + junit in CI, then write the corresponding GitHub Actions step that uploads the HTML report as an artifact only when tests actually ran (regardless of pass/fail).

Summary

Playwright's reporters serve different audiences: html for human investigation (with direct links to traces and videos), junit/github for CI-native integration, and json for custom tooling. Configuring several at once and always uploading the HTML report as a CI artifact (with if: always()) is the standard, low-cost setup most real projects should use.

Interview Questions

Why would a CI pipeline typically configure both a JUnit reporter and an HTML report artifact, rather than just one?▾
They serve different purposes: JUnit XML lets the CI platform's own UI render a native pass/fail summary and integrate with its dashboards, while the HTML report is what a human actually opens to investigate a specific failure — traces, screenshots, and videos included. JUnit alone gives no way to dig into why a test failed; the HTML report alone doesn't integrate with the CI platform's own results UI. Together they cover both needs.
Why configure multiple reporters at once instead of just one?▾
Each serves a different audience — HTML for a human investigating a failure, JUnit/GitHub for CI-native integration — running several costs little extra.
Why is if: always() critical on the report-upload CI step?▾
A report is most valuable exactly when tests failed — without always(), that's precisely the case where the artifact wouldn't get uploaded.
Why avoid open: 'always' for the HTML reporter in CI?▾
It tries to open a browser window on a headless CI runner, which fails or hangs — use 'never' in CI and let the default apply locally.
What's the dot reporter useful for?▾
Very large suites, where its minimal one-character-per-test output is more practical in a terminal than a full line per test.
