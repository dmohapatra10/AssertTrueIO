Tables

Beginner 7 min read

Prerequisites: Forms, Filtering & Chaining

What is this?

Tables — order lists, user management grids, inventory dashboards — are one of the densest, most repeated-element-heavy structures in real applications, which makes them a natural stress test for the filtering and chaining patterns from the Locators chapter. This page applies those patterns specifically to rows, cells, sorting, and pagination.

Why it's important

The single biggest mistake in table testing is finding a row by its position (nth(2)) instead of its content. Position-based tests break the moment sort order changes, a new row is added, or the table re-renders in a different order — all of which happen constantly in real, data-driven tables.

Finding a Row by Content

const row = page.getByRole('row').filter({ hasText: 'Wireless Mouse' });
await expect(row).toBeVisible();

This is the pattern from the Filtering & Chaining page, applied specifically to tables — always the starting point for a table test, rather than nth().

Reading a Specific Cell

const row = page.getByRole('row').filter({ hasText: 'Wireless Mouse' });
const priceCell = row.getByRole('cell').nth(2); // 3rd column — position within the ROW is fine here

await expect(priceCell).toHaveText('$29.99');

Note the distinction: nth() to find the row among many rows is fragile (order-dependent). nth() to find a column within an already-uniquely-identified row is fine, since column order within a table is structural, not data-dependent, and rarely changes without the whole feature changing.

Basic Example — Acting Within a Row

const row = page.getByRole('row').filter({ hasText: 'Wireless Mouse' });
await row.getByRole('button', { name: 'Edit' }).click();

Detailed Example — Asserting Row Count and Contents Together

test('search filters the table to matching rows only', async ({ page }) => {
  await page.goto('/inventory');
  await page.getByRole('searchbox').fill('mouse');

  const rows = page.getByRole('row').filter({ hasNotText: 'Product Name' }); // exclude header row
  await expect(rows).toHaveCount(2);
  await expect(rows.filter({ hasText: 'Wireless Mouse' })).toBeVisible();
  await expect(rows.filter({ hasText: 'Bluetooth Mouse' })).toBeVisible();
});

hasNotText excluding the header row is a common, useful pattern — many tables render the header as a <tr> too, and it would otherwise count toward toHaveCount() unexpectedly.

Real-World Example — Sorting

test('clicking the Price header sorts ascending', async ({ page }) => {
  await page.goto('/inventory');
  await page.getByRole('columnheader', { name: 'Price' }).click();

  const priceCells = page.getByRole('row').filter({ hasNotText: 'Product Name' })
    .getByRole('cell').nth(2); // simplified — see note below

  const prices = await priceCells.allTextContents();
  const numericPrices = prices.map((p) => parseFloat(p.replace('$', '')));
  expect(numericPrices).toEqual([...numericPrices].sort((a, b) => a - b));
});

allTextContents() resolves every matching element's text at once into a plain array — the right tool when a test needs to reason about a whole column's data together (like verifying sort order), rather than checking one row at a time.

Pagination

test('pagination shows the next page of results', async ({ page }) => {
  await page.goto('/inventory');

  await expect(page.getByRole('row')).toHaveCount(11); // 10 rows + header
  const firstPageFirstItem = await page.getByRole('row').nth(1).textContent();

  await page.getByRole('button', { name: 'Next page' }).click();

  await expect(page).toHaveURL(/page=2/);
  const secondPageFirstItem = await page.getByRole('row').nth(1).textContent();
  expect(secondPageFirstItem).not.toBe(firstPageFirstItem);
});

Confirming the content actually changed (not just the URL or page number label) catches the real bug this kind of test is meant to catch — a "Next" button that updates the URL but silently fails to fetch new data.

❌ Fragile vs. ✅ Recommended

// ❌ Positional — breaks if sort order or row insertion changes
await page.getByRole('row').nth(3).getByRole('button', { name: 'Delete' }).click();

// ✅ Content-based — correct regardless of order
await page.getByRole('row').filter({ hasText: 'Wireless Mouse' })
  .getByRole('button', { name: 'Delete' }).click();

Common Mistakes

  • Using nth() to find a row instead of filtering by content — the most common table-testing anti-pattern.
  • Forgetting the header row counts as a <tr> in many implementations, throwing off toHaveCount() expectations by one.
  • Asserting sort/filter results only by count, not content — a table showing the right number of rows with the wrong data would pass a count-only check.
  • Not handling pagination when a test expects to find a row that's actually on a different page than the one currently displayed.

Edge Cases

  • Virtualized/windowed tables (only rendering visible rows for performance, common in very large datasets) — rows outside the current scroll position may not exist in the DOM at all yet; scrolling the container into view before asserting is necessary here.
  • Tables built from <div>s instead of semantic <table>/<tr>/<td> — getByRole('row') won't match unless proper ARIA roles (role="row", role="cell") are applied; check the actual accessibility tree if role-based locators don't match a visually table-like layout.

Debugging

If getByRole('row') matches zero rows on something that's visually a table, inspect the accessibility tree directly — a <div>-based table needs explicit ARIA roles to be discoverable this way; without them, a CSS-based fallback locator (from the locator() and CSS/XPath page) may be the pragmatic option.

Best Practices

  • Always find rows by content (filter({ hasText })), never by position, unless order is genuinely and stably part of what's being tested.
  • Exclude header rows explicitly when asserting counts on tables that render headers as regular rows.
  • Use allTextContents() when a test needs to reason about a whole column together, like verifying sort order.
  • Verify pagination by content change, not just URL or page-number label change.

Practice Exercise

Write a test that finds a specific row by product name, reads its quantity cell, increments the quantity via an in-row input, and asserts the row's total price cell updates correctly — all without using nth() to locate the row itself.

Summary

Reliable table testing means finding rows by content rather than position, using nth() only for structurally stable things like column index within an already-identified row, and verifying sorting/pagination by actual data change rather than superficial signals like a page number label.

Interview Questions

Why is page.getByRole('row').nth(2) considered a fragile way to find a specific row, and what's the alternative?▾
nth(2) depends entirely on the row's current position, which can change due to sorting, filtering, or new rows being added — none of which necessarily reflect a bug in the feature under test. Filtering by content, like getByRole('row').filter({ hasText: 'Wireless Mouse' }), identifies the row by what makes it meaningfully unique, so the test remains correct regardless of where that row happens to currently sit in the table.
Why is finding a table row by nth() considered fragile?▾
It depends on the row's current position, which can shift due to sorting or new rows — unrelated to the actual feature being tested.
When is nth() actually acceptable in a table test?▾
For selecting a column within an already-uniquely-identified row — structural, not data-dependent, and rarely changes.
Why exclude the header row when asserting a table's row count?▾
Many implementations render the header as its own <tr>, which would otherwise inflate the count by one.
How do you verify pagination actually fetched new data, not just changed the page label?▾
Compare the actual content (e.g. the first item's text) between pages, not just the URL or displayed page number.
