Chapter 15: Trace Viewer

Beginner 7 min read

Prerequisites: Screenshots and Videos

What is this?

A trace is a complete recording of a test run — DOM snapshots for every action, network requests, console logs, and source code — that can be opened afterward in an interactive, time-travel debugger. It's the single most useful tool for debugging a test that fails in CI but passes locally.

Why it's important

A screenshot shows one moment; a video shows what happened but not why. A trace lets you step through the test action-by-action, inspect the DOM exactly as it was at each step, see the network request that was in flight, and read console output — turning "it failed somewhere in this 40-line test" into "it failed on this exact line, and here's the page state at that instant."

Mental Model

Think of a trace as the test-execution equivalent of a flight recorder: it doesn't change how the test runs, it just records everything that happened alongside it — every action, every DOM state, every network call — into a single portable .zip file. That file can be opened, shared, and replayed on any machine, entirely independent of whether the environment that generated it is still available.

Enabling Tracing

// playwright.config.ts
export default defineConfig({
  use: {
    trace: 'on-first-retry',
  },
});

'on-first-retry' is the recommended default: it only records a trace when a test fails and is retried, which avoids the overhead of tracing every passing test while still capturing the exact failure that matters. Other values include 'retain-on-failure' (keep a trace for any failed test, no retry needed) and 'on' (trace everything, useful temporarily while actively debugging).

Opening a Trace

npx playwright show-trace trace.zip

# Or open the trace from the last test run automatically:
npx playwright show-report

This opens a browser-based UI with a timeline of every action, a DOM snapshot you can inspect like real dev tools at any point in that timeline, a network tab, and console output — all reconstructed from the trace file, without needing to rerun the test.

What the Trace Viewer Shows

  • Action timeline — every locator call, action, and assertion, in order, with duration
  • DOM snapshot per action — a real, inspectable snapshot of the page at that exact moment, before and after each action
  • Network tab — every request and response during the test
  • Console tab — any console.log/warnings/errors the page itself produced
  • Source tab — the exact line of test code that ran at each step

Basic Example — Walking Through a Failure

A concrete debugging sequence: a test fails asserting toBeVisible() on a "Success" message. Opening its trace, you'd typically:

  1. Scrub to the last action before the failure in the timeline.
  2. Check the DOM snapshot at that moment — is the expected element present but hidden? Not present at all? Covered by something?
  3. Switch to the Network tab at that same timestamp — did the API call the success message depends on actually complete, or is it still pending or did it fail?
  4. Check the Console tab for a JavaScript error that might explain why the UI never updated.

This sequence — DOM, then network, then console — resolves the large majority of "why did this fail" questions without needing to add a single console.log or re-run anything.

Trace Viewer vs. UI Mode

These are related but distinct: UI Mode (Chapter 2) is for running and watching tests live during development, with its own built-in trace-like timeline for the current run. Trace Viewer is specifically for opening a saved trace file — often one generated by a CI run you weren't watching live at all. In practice, UI Mode is the everyday local tool; standalone Trace Viewer is what you reach for once a trace artifact has been downloaded from a CI failure.

Real-World Example — Debugging a CI-Only Failure

// playwright.config.ts — capture just enough to debug without bloating CI storage
export default defineConfig({
  use: {
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
  },
  retries: process.env.CI ? 1 : 0,
});

With this config, a test that fails in CI automatically retries once, and if it fails again, a trace is captured for that retry. Downloading that trace artifact and opening it with npx playwright show-trace usually turns a "works on my machine" mystery into an obvious root cause within a couple of minutes — a timing issue, an unexpected redirect, a different viewport size triggering a responsive layout change.

❌ Fragile vs. ✅ Recommended

// ❌ Debugging a flaky CI failure by adding console.log and re-running repeatedly
// (slow, and may not even reproduce the same way twice)

// ✅ Download the trace artifact that was already captured and open it directly
// npx playwright show-trace downloaded-trace.zip

Common Mistakes

  • Setting trace: 'on' permanently in CI, generating a large trace file for every single test regardless of outcome.
  • Not configuring retries in CI, meaning 'on-first-retry' never actually captures anything since there's no retry to capture during.
  • Debugging a flaky failure by adding console.log statements and re-running many times, instead of just opening the trace that was likely already captured.
  • Not uploading trace artifacts from CI, throwing away exactly the evidence needed the next time a failure needs investigating.

Edge Cases

  • Traces for tests using multiple browser contexts/pages (Chapter 9) — the trace viewer shows a separate timeline tab for each page, making multi-tab and multi-user tests fully inspectable too.
  • Very long-running tests — trace files scale with test duration and action count; for exceptionally long tests, consider whether the test should be split rather than producing an unwieldy trace.

Debugging

When a trace itself seems incomplete or missing an expected action, confirm the trace config value actually applies to the project/run in question — a common surprise is a per-project override in playwright.config.ts silently taking precedence over the top-level default.

Best Practices

  • Use trace: 'on-first-retry' paired with at least one CI retry — this is the standard, low-overhead setup most projects should default to.
  • Upload trace artifacts from CI runs (most CI providers support this easily) so failures can be debugged without reproducing them locally first.
  • Reach for trace: 'on' only temporarily, scoped to a single local debugging session for a specific stubborn test.
  • Follow the DOM → network → console sequence when reading an unfamiliar trace, rather than scrubbing randomly.

Practice Exercise

Configure a project with trace: 'on-first-retry' and one retry, intentionally break a test, run it, and practice opening and navigating the resulting trace file with npx playwright show-trace.

Summary

A trace is a full recording of a test run — DOM, network, console, and source — replayable in an interactive viewer, and distinct from UI Mode's live-run timeline. trace: 'on-first-retry' combined with CI retries is the standard low-overhead setup, and it's usually the fastest path to diagnosing a failure you can't reproduce locally.

Interview Questions

Why is 'on-first-retry' generally preferred over 'on' for the trace setting in CI?▾
'on' records a trace for every test regardless of outcome, which adds overhead and storage cost for tests that already passed and revealed nothing new. 'on-first-retry' only captures a trace when a test actually fails and is retried — exactly the case where a trace is useful — giving the same debugging value at a fraction of the cost.
Why is trace: 'on-first-retry' the recommended default over 'on'?▾
It only captures a trace for a test that actually failed and is retried — the exact case where a trace is useful — at a fraction of the storage cost of tracing everything.
What's the difference between UI Mode and standalone Trace Viewer?▾
UI Mode is for running and watching tests live during local development; Trace Viewer opens a saved trace file, often from a CI run you weren't watching live.
What's the recommended order for reading an unfamiliar trace?▾
DOM snapshot first, then the Network tab, then Console — this sequence resolves the majority of 'why did this fail' questions.
Why does trace: 'on-first-retry' require retries to be configured to actually capture anything?▾
Without at least one retry configured, there's never a 'first retry' for the trace setting to attach to, so nothing gets captured.
