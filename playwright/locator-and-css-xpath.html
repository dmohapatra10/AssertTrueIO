locator(), CSS, and XPath

Beginner 5 min read

Prerequisites: Locators overview, getByTestId()

What is locator()?

page.locator(selector: string)

locator() is the generic, low-level way to find elements — by CSS selector by default, or by XPath if the string is prefixed with xpath=. Every getBy*() method is, under the hood, a more readable wrapper that eventually resolves to something like this — locator() is the escape hatch when none of them fit.

Why it's ranked last

CSS and XPath selectors describe an element's position or implementation in the DOM — a class name, a tag hierarchy, an nth-child index — rather than what the element means to a user. That makes them the most fragile locator category: a designer renaming a CSS class for purely visual reasons, or a developer wrapping an element in one extra <div> for layout, can silently break a CSS/XPath locator without changing anything a user would notice.

Basic Example — CSS

await page.locator('.product-card__title').click();
await page.locator('#checkout-form input[name="email"]').fill('user@example.com');

Basic Example — XPath

await page.locator('xpath=//button[contains(text(), "Submit")]').click();

XPath can express relationships CSS can't — like "the button, but only if it's inside a form that also contains an error message" — but this expressive power comes at the cost of readability; most teams should reach for XPath rarely, and only after confirming CSS genuinely can't do it.

Detailed Example — When CSS Is Actually the Right Tool

// A generic, low-level container with no meaningful role, label, or text —
// e.g. a drag handle icon with a stable, purpose-specific class
await page.locator('.drag-handle').first().hover();

// Combining a stable data attribute with CSS for structural precision
await page.locator('[data-row-id="1042"] .quantity-input').fill('3');

Real-World Example — Legacy Application Without Accessibility Attributes

test('user can update shipping quantity', async ({ page }) => {
  await page.goto('/cart');

  // This legacy table has no roles, labels, or test IDs available yet —
  // CSS structural selection is the pragmatic choice here, not the ideal one
  await page.locator('table.cart-items tr:nth-child(1) input.qty').fill('2');
  await page.locator('table.cart-items tr:nth-child(1) button.update').click();

  await expect(page.locator('.cart-total')).toHaveText('$129.98');
});

This is a realistic scenario, not a recommendation — a team inheriting an older codebase without data-testid or semantic markup often has no better option in the short term, while separately pushing to add proper attributes over time.

❌ Fragile vs. ✅ Recommended

// ❌ Positional and implementation-coupled — breaks if column order changes
await page.locator('table tr td:nth-child(3)').click();

// ✅ If a data-testid or role exists, prefer it over structural CSS
await page.getByTestId('cart-item-quantity').click();

Common Mistakes

  • Reaching for CSS/XPath as the first instinct out of familiarity with older tools like Selenium, before checking whether a getBy*() locator would work.
  • Using deep, brittle nth-child chains (div > div:nth-child(2) > span) that encode the exact current DOM shape — these break on almost any unrelated markup change.
  • Preferring XPath over CSS purely out of Selenium habit when CSS can express the same selector more simply and readably.

CSS vs. XPath — When Each Is Appropriate

Use when
CSSTargeting by class, attribute, or simple structural relationship — the large majority of cases where a selector is genuinely needed.
XPathYou need to select based on text content combined with ancestor/descendant relationships CSS can't express, or navigate upward (parent/ancestor) from a known element.

Edge Cases

  • Selecting an ancestor — CSS has no way to select "the parent of X"; this is one of the few cases XPath (xpath=ancestor::div[@class="row"]) or Playwright's own locator('..') chaining genuinely earns its use over CSS.
  • Shadow DOM — Playwright's CSS engine pierces open shadow roots automatically for most selectors, unlike traditional CSS querySelector; this is covered in depth in Chapter 6's Shadow DOM section.

Debugging

Use the browser's own DevTools console to test a CSS selector with document.querySelectorAll(...) before pasting it into a test — if it matches zero or unexpectedly many elements there, it will behave the same way in Playwright, and this is a faster feedback loop than re-running the whole test.

Best Practices

  • Treat CSS/XPath as a last resort, after confirming no getBy*() method fits — including getByTestId().
  • Prefer attribute selectors ([data-row-id="1042"]) over positional ones (nth-child(3)) when a selector is genuinely needed — attributes tend to be more intentional and stable than DOM position.
  • When a CSS/XPath locator turns out to be necessary and load-bearing, consider it a signal to add a proper data-testid or accessibility attribute to the app instead, over time.

Practice Exercise

Given a legacy table with no test IDs, write one CSS-based locator to target the "Edit" button in the row containing the text "Wireless Mouse" — then rewrite it as if a data-testid="row-{sku}" attribute were added, and compare the two for readability and stability.

Summary

locator() with CSS or XPath is the generic, most powerful, and most fragile locator category — reserved for cases the semantic getBy*() methods genuinely can't cover. CSS should be the default within this category; XPath is for the narrower set of cases needing ancestor navigation or complex text-plus-structure conditions.

Interview Questions

Why does Playwright's official guidance rank CSS/XPath below even getByTestId(), despite CSS selectors being extremely powerful?▾
Power isn't the deciding factor — coupling is. A CSS selector tied to class names or DOM structure changes for reasons that have nothing to do with the feature being tested (a redesign, a refactor), while data-testid is a deliberate, stable contract that only changes when a team explicitly decides to change it. Semantic locators additionally double as accessibility checks, which neither CSS/XPath nor test IDs provide.
Why is locator() with CSS/XPath ranked below even getByTestId()?▾
It couples the test to DOM structure or class names that can change for reasons unrelated to the feature, while a test ID is a deliberate, stable contract.
When does XPath genuinely earn its use over CSS?▾
When you need to select an ancestor or combine text content with structural relationships — things CSS alone can't express.
How can you quickly test whether a CSS selector is correct before using it in Playwright?▾
Run document.querySelectorAll(selector) in the browser DevTools console and check the match count.
Does Playwright's CSS engine handle Shadow DOM the same way a browser's native querySelector does?▾
No — Playwright's CSS engine pierces open shadow roots automatically, unlike the native querySelector API.
