Chapter 5: Actions

Beginner 5 min read

Prerequisites: Locators

What is this?

Actions are the methods that actually interact with the page: clicking, typing, checking a box, selecting from a dropdown, uploading a file. Every action in this chapter is called on a locator, and every one of them waits for the target element to be truly ready before doing anything. Each action gets its own dedicated page:

  1. click() and dblclick()
  2. fill() and pressSequentially()
  3. press() — single keys and key combinations
  4. check() and uncheck()
  5. selectOption()
  6. hover()
  7. setInputFiles()
  8. dragTo()
  9. Actionability checks and force

Why is it important?

Actions are where most flaky-test problems in other frameworks come from — clicking a button before it's rendered, typing into a field before it's enabled. Playwright's actionability checks exist specifically to eliminate that entire category of bug, but only if you understand what they check and don't work around them.

Actionability checks

See Actionability Checks and force for the full deep dive. In short, before most actions, Playwright automatically waits (up to the timeout) for the element to be:

  • Attached — present in the DOM
  • Visible — has non-zero size and no visibility: hidden/display: none
  • Stable — not still animating or transitioning
  • Enabled — not disabled
  • Receives events — not obscured by another element (e.g., a loading overlay)

If any check keeps failing past the timeout, Playwright throws a clear, specific error naming which check failed — a major debugging advantage over a generic "element not found."

The core action methods

MethodUse for
click() / dblclick()Buttons, links, any clickable element
fill()Setting a text input's value directly (fast, clears existing value)
pressSequentially()Typing character-by-character (for autocomplete/keypress-driven UI)
press()A single key or key combination (e.g. Enter, Control+A)
check() / uncheck()Checkboxes and radio buttons
selectOption()Native <select> dropdowns
setInputFiles()File upload inputs
hover()Triggering hover states/menus
dragTo()Drag-and-drop interactions
focus() / blur()Manually moving focus without clicking
clear()Clearing a field's value without typing over it

fill() vs pressSequentially()

These are easy to mix up. fill() sets a value directly through the DOM — fast, and the right default for almost all form-filling.

await page.getByLabel('Email').fill('user@example.com');

pressSequentially() dispatches real keydown/keyup events per character — slower, but necessary when the page has JavaScript that reacts to individual keystrokes (autocomplete suggestions, live character counters, masked inputs).

// Needed here because the search box shows live suggestions per keystroke
await page.getByRole('searchbox').pressSequentially('play', { delay: 100 });
await expect(page.getByText('Playwright')).toBeVisible();

Real-world example: a checkout form

import { test, expect } from '@playwright/test';

test('completes checkout with a valid card', async ({ page }) => {
  await page.goto('/checkout');

  await page.getByLabel('Full name').fill('Jordan Lee');
  await page.getByLabel('Shipping method').selectOption('express');
  await page.getByLabel('I agree to the terms').check();
  await page.getByLabel('Card number').fill('4242 4242 4242 4242');

  await page.getByRole('button', { name: 'Place order' }).click();

  await expect(page.getByText('Order confirmed')).toBeVisible();
});

Each action targets a role- or label-based locator (per the priority from the Locators chapter), and every call auto-waits — there's no manual delay between filling the form and clicking submit, even though the "Place order" button may only become enabled once the terms checkbox is checked.

Common mistakes

  • Using pressSequentially() everywhere out of habit — it's slower and unnecessary for plain form fields where fill() works fine.
  • Adding a manual wait before an action "just in case" — actionability checks already handle this; a manual wait usually just masks a different underlying problem.
  • Calling click() on a `<div>` styled to look like a button instead of fixing the markup to use a real <button> — this breaks both accessibility and role-based locators.

Best practices

  • Default to fill() for text input; reach for pressSequentially() only when the UI genuinely depends on keystroke events.
  • Let actionability checks do the waiting — if an action keeps timing out, that's usually a real bug (an overlay blocking the element, a disabled button) worth investigating, not something to paper over with a longer timeout.
  • Pair actions with assertions afterward (see the next chapter) to confirm the action actually had the intended effect, not just that it didn't throw.

Summary

Actions are how Playwright interacts with the page, and every one of them waits for the target element to be genuinely ready first via actionability checks. Choose fill() for most text input, reserve pressSequentially() for keystroke-sensitive UI, and trust auto-waiting instead of adding manual delays.

Interview Questions

What's the practical difference between fill() and pressSequentially(), and when would you choose one over the other?▾
fill() sets an input's value directly through the DOM in one step — fast, and correct for the vast majority of form fields. pressSequentially() simulates real keystrokes one at a time, which is necessary when the page's JavaScript listens for individual keydown/keyup events — for example, an autocomplete dropdown that only appears in response to actual typing.
What single mechanism underlies most of Playwright's action reliability?▾
Actionability checks that run automatically before every action, waiting for the element to be attached, visible, stable, enabled, and receiving events.
Why is fill() generally faster than pressSequentially()?▾
fill() sets the value directly in one step; pressSequentially() dispatches a real keydown/keyup pair for every character.
What's the risk of defaulting to { force: true } whenever an action times out?▾
It skips the actionability checks that usually indicate a real problem, potentially clicking something a real user couldn't actually interact with.
Why does check() behave differently from click() on a checkbox?▾
check() is idempotent — it guarantees the checked state regardless of starting point — while click() simply toggles whatever state is currently there.
