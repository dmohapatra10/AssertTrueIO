Chapter 8: Pages and Navigation

Beginner 8 min read

Prerequisites: Playwright Architecture, Waiting and Synchronization

What is this?

This chapter covers everything the page object gives you for controlling and observing navigation: moving between URLs, reloading, browser history, and confirming where a test actually ended up — both for full page loads and for the client-side routing used by single-page apps.

Why it's important

Nearly every test starts with a navigation, and many end by asserting the user landed somewhere specific — a confirmation page, a redirect after login, a client-side route change with no full reload at all. Getting navigation right avoids two common failure modes: tests that race ahead of a page that hasn't finished loading, and tests that hardcode brittle full URLs that break the moment the same suite runs against a different environment.

Mental Model

There are really two distinct kinds of "navigation" a test needs to handle differently:

  • Full page navigation — page.goto(), clicking a normal link, form submission. The browser tears down the old page and loads a new one; Playwright's own navigation-wait logic (Chapter 7's Waiting content) applies automatically.
  • Client-side (SPA) navigation — a JavaScript router changes the URL and swaps content without a real page reload. page.goto() is never involved; the URL just changes as a side effect of something else happening on the page.

Confusing these two is the source of most navigation-related test bugs — assuming a client-side route change is covered by the same automatic waiting a full goto() gets, when it isn't.

Core navigation methods

MethodUse for
page.goto(url)Navigate to a URL; waits for load by default
page.reload()Refresh the current page
page.goBack() / page.goForward()Browser history navigation
page.waitForURL(pattern)Wait for the URL to match after a client-side navigation

Basic Example

await page.goto('/login');
await page.reload();
await page.goBack();
await page.goForward();

Using a Base URL

Hardcoding the full domain in every test is a common early mistake. Setting baseURL once in playwright.config.ts lets every test use short, relative paths instead:

// playwright.config.ts
export default defineConfig({
  use: {
    baseURL: 'https://staging.example.com',
  },
});

// In a test — no hardcoded domain:
await page.goto('/login');

This also means switching environments (staging vs. production) is a one-line config change instead of a find-and-replace across the whole suite — covered fully in Chapter 10 (Configuration).

Client-Side Navigation and waitForURL()

Single-page apps often change the URL via client-side routing (no full page reload), which goto() isn't involved in at all — that navigation happens as a side effect of clicking something on the page. waitForURL() is the correct tool for confirming it happened:

await page.getByRole('link', { name: 'Settings' }).click();
await page.waitForURL('**/settings');
await expect(page.getByRole('heading', { name: 'Settings' })).toBeVisible();

Detailed Example — Page Events

Beyond direct navigation, the page object emits events for things that happen as a byproduct of navigation — useful when a test needs to react to something the app triggers rather than something it directly calls:

// Capture a new tab/window opened by a link with target="_blank"
const [newPage] = await Promise.all([
  context.waitForEvent('page'),
  page.getByRole('link', { name: 'View invoice (opens in new tab)' }).click(),
]);
await newPage.waitForLoadState();
await expect(newPage).toHaveURL(/\/invoices\//);

// React to an unexpected page-level JavaScript error during a test
page.on('pageerror', (err) => console.log('Uncaught exception:', err));

Multiple tabs/windows get their own full treatment in the next chapter — this is just the entry point: navigation and multi-page handling share the same underlying event model.

Real-World Example — Login Redirect

import { test, expect } from '@playwright/test';

test('redirects to the dashboard after login', async ({ page }) => {
  await page.goto('/login');

  await page.getByLabel('Email').fill('user@example.com');
  await page.getByLabel('Password').fill('correct-horse-battery-staple');
  await page.getByRole('button', { name: 'Sign in' }).click();

  await page.waitForURL('**/dashboard');
  await expect(page).toHaveURL(/\/dashboard$/);
  await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
});

Note the combination: waitForURL() actively waits for the redirect to happen, while expect(page).toHaveURL() is the web-first assertion that documents the expectation and would retry if needed. They serve related but distinct purposes — waiting vs. asserting — covered in depth in the Waiting & Synchronization chapter.

❌ Fragile vs. ✅ Recommended

// ❌ Hardcoded full domain, breaks in every other environment
await page.goto('https://myapp.com/login');

// ✅ Relative path against a configured baseURL
await page.goto('/login');

Common Mistakes

  • Hardcoding full URLs (https://myapp.com/login) in every test instead of setting baseURL once.
  • Asserting on the URL immediately after a click without waitForURL() first, when the navigation is client-side and not instantaneous.
  • Using an exact string match for a URL that includes a dynamic segment (like an order ID) instead of a regex or wildcard pattern.
  • Assuming goto()'s wait covers a subsequent client-side route change triggered by something the user does after the page loads — it doesn't; that's a separate wait.

Edge Cases

  • Redirect chains (login → intermediate page → final destination) — match the final expected URL with a pattern rather than asserting on every intermediate hop, which can change without affecting the feature under test.
  • Navigation that fails (404, DNS error, network failure) — page.goto() throws in genuine navigation failures; wrap in a try/catch only when a test specifically needs to verify failure handling.
  • Anchor-only URL changes (#section) — these don't trigger a full navigation event; waitForURL() still works since it just watches the URL string, but no load event fires.

Debugging

If a URL-related assertion fails unexpectedly, check whether the actual issue is a client-side route that simply takes longer than expected — Trace Viewer's timeline (Chapter 15) shows exactly when the URL changed relative to the triggering action, which is usually faster than guessing from the code alone.

Best Practices

  • Always configure baseURL; never hardcode the domain inside individual tests.
  • Use toHaveURL() with a regex when only part of the URL is predictable (e.g., matching a path but not a dynamic ID).
  • Reach for waitForURL() specifically after actions that trigger client-side routing, not after a plain page.goto(), which already waits for navigation itself.

Practice Exercise

Write a test that clicks a link opening a new tab, waits for that new tab/page to load, and asserts its URL matches a dynamic invoice ID pattern without hardcoding a specific ID.

Summary

Playwright's navigation methods — goto(), reload(), history navigation, and waitForURL() — cover both full page loads and client-side routing. Configure baseURL once, use waitForURL() for SPA navigation, and assert on the final URL with toHaveURL() rather than assuming it's already correct.

Interview Questions

Why might you need waitForURL() even though goto() already waits for navigation?▾
goto() only waits for navigations it itself initiates. When a URL changes as a side effect of a client-side action — like clicking a link in a single-page app — that navigation isn't tied to a goto() call at all, so waitForURL() is needed to wait for the resulting URL change explicitly.
Why might you need waitForURL() even though goto() already waits for navigation?▾
goto() only waits for navigations it itself initiates; a URL change from client-side routing needs its own explicit wait.
What's the benefit of configuring baseURL instead of hardcoding full domains?▾
Switching environments becomes a one-line config change instead of a find-and-replace across every test file.
How would you capture a new tab opened by a target="_blank" link?▾
Wrap the click and context.waitForEvent('page') together in Promise.all to avoid a race condition.
Does an anchor-only URL change (like #section) trigger a full load event?▾
No — waitForURL() still works since it watches the URL string, but no navigation load event fires for a same-page anchor change.
