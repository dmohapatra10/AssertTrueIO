waitForSelector() & waitForTimeout()

Beginner 5 min read

Prerequisites: waitForRequest() & waitForResponse()

What is this?

page.waitForSelector(selector: string, options?: { state?: 'attached'|'visible'|'hidden'|'detached' })
page.waitForTimeout(timeout: number)

Both predate the modern locator-based API. waitForSelector() waits for an element matching a CSS/text selector to reach a given state. waitForTimeout() just pauses for a fixed number of milliseconds — no condition, no signal, just a delay.

Why waitForSelector() is mostly legacy now

Every locator already waits automatically when you act on it or assert against it — await expect(locator).toBeVisible() does everything waitForSelector(sel, { state: 'visible' }) does, with a clearer, more consistent API and better error messages. waitForSelector() still exists and works, but a modern Playwright test written from scratch rarely needs to reach for it directly.

Basic Example — Old vs. Modern

// Legacy style
await page.waitForSelector('.results-list', { state: 'visible' });

// Modern equivalent — same effect, better locator semantics
await expect(page.locator('.results-list')).toBeVisible();

When waitForSelector() Still Has a Legitimate Use

// Waiting for an element to be REMOVED, in a context where you don't
// already have a locator instance you want to keep re-querying
await page.waitForSelector('.loading-overlay', { state: 'detached' });

It occasionally shows up in scripts using the lower-level Playwright Library API without the Test framework's locator conveniences, or in codebases migrating from older Playwright versions. If you're writing new Playwright Test code today, prefer the locator-plus-assertion pattern.

waitForTimeout() — Why It's an Anti-Pattern

// ❌ Anti-pattern — do not do this in real test code
await page.getByRole('button', { name: 'Submit' }).click();
await page.waitForTimeout(3000); // guessing how long is "enough"
await expect(page.getByText('Success')).toBeVisible();

A fixed sleep is both unreliable and slow: too short, and it fails intermittently the moment CI is under load or the network is slower than usual; too long, and it wastes real wall-clock time on every single test run, even when the actual condition was ready in a fraction of that time. Multiply that wasted time across a suite with hundreds of tests and it becomes a genuinely significant, avoidable slowdown.

The One Legitimate Use of waitForTimeout()

// Acceptable: temporarily, while interactively debugging in headed mode,
// to visually observe what's happening at a specific point
await page.waitForTimeout(2000); // TEMP — remove before committing

waitForTimeout() is genuinely useful as a debugging tool — pausing briefly while watching a headed browser run to see what's on screen at a given moment. It should never survive into committed test code as an actual synchronization strategy.

Real-World Example — Replacing a Timeout-Based Wait

// Before: guessing
await page.getByRole('button', { name: 'Generate report' }).click();
await page.waitForTimeout(5000);
await expect(page.getByText('Report ready')).toBeVisible();

// After: waiting for the real signal
const [response] = await Promise.all([
  page.waitForResponse((res) => res.url().includes('/api/reports') && res.status() === 200),
  page.getByRole('button', { name: 'Generate report' }).click(),
]);
await expect(page.getByText('Report ready')).toBeVisible();

This mirrors the pattern from the previous page — almost every waitForTimeout() in a real codebase can be replaced with either a content assertion (if one exists) or a specific network wait, once you identify what the fixed delay was actually approximating.

❌ Fragile vs. ✅ Recommended

// ❌ Fixed delay, no real signal
await page.waitForTimeout(2000);

// ✅ Wait for the thing that actually indicates readiness
await expect(page.getByText('Report ready')).toBeVisible();

Common Mistakes

  • Leaving debug waitForTimeout() calls in committed code — easy to forget after using it temporarily during local debugging.
  • Using waitForSelector() out of old habit in new code instead of the more idiomatic locator-plus-assertion pattern.
  • Treating a waitForTimeout() that "fixed" a flaky test as a real fix — it usually just widens the timing window enough to hide the underlying race most of the time, not eliminate it.

Edge Cases

  • Genuinely fixed, known delays (a UI that deliberately shows a spinner for a minimum of exactly 1 second regardless of actual load time) — even here, asserting on the spinner's disappearance is more robust than hardcoding the same 1000ms elsewhere, since it stays correct if that minimum duration changes.

Debugging

If you find a waitForTimeout() in an existing test, don't just delete it — figure out what real condition it was approximating (a network response? a content change? an animation finishing?) and replace it with a wait on that specific thing.

Best Practices

  • Treat any waitForTimeout() found in test code as a bug to fix, not a working solution to leave alone.
  • Use waitForSelector() only in Playwright Library (non-Test) contexts, or when maintaining older code — write new Test-framework code with locators and assertions instead.
  • When removing a waitForTimeout(), identify the real signal it was standing in for before replacing it.

Practice Exercise

Given a test containing await page.waitForTimeout(2000); right after a click that triggers a toast notification, rewrite it using a proper assertion, and explain what signal you're now actually waiting on instead of a guess.

Summary

waitForSelector() is largely superseded by locators plus web-first assertions in modern Playwright Test code. waitForTimeout() is an anti-pattern for real synchronization — useful only as a temporary, interactive debugging aid — and should always be replaced with a wait on a real signal (a network response, a content change) before code is committed.

Interview Questions

A test uses waitForTimeout(3000) and passes reliably in CI. Why would you still flag it in code review?▾
Passing reliably today doesn't mean the wait is correct — it means the fixed delay happens to be long enough under current conditions. It's still both slower than necessary (paying the full 3 seconds even when the real condition resolves faster) and fragile against any future slowdown (a slower CI runner, a heavier page) that could push the real timing past the hardcoded value. Replacing it with a wait on the actual signal removes both risks.
Why is waitForSelector() considered mostly legacy in modern Playwright Test code?▾
A locator combined with a web-first assertion achieves the same effect with clearer semantics and better error messages.
