Projects & Environments

Beginner 7 min read

Prerequisites: Configuration Options

What is this?

A project is a named configuration variant within a single playwright.config.ts — a different browser, device, or even a different subset of tests, each with its own settings. An environment is the actual deployed target a project points at — local, QA, staging, production. These are related but distinct axes of configuration.

Why it's important

Real suites need to run the same tests against multiple browsers, and sometimes need entirely different test subsets (a fast smoke suite vs. a full regression suite, or an API-only project vs. a UI project) — projects are how Playwright expresses all of this without duplicating config or test files.

Basic Example — Multi-Browser Projects

export default defineConfig({
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox', use: { ...devices['Desktop Firefox'] } },
    { name: 'webkit', use: { ...devices['Desktop Safari'] } },
    { name: 'Mobile Chrome', use: { ...devices['Pixel 7'] } },
    { name: 'Mobile Safari', use: { ...devices['iPhone 14'] } },
  ],
});
# Run every project
npx playwright test

# Run just one
npx playwright test --project=webkit

The same test files run unchanged across every project — Playwright substitutes each project's use options (browser engine, viewport, device emulation) without any per-browser test code.

Detailed Example — Splitting Smoke vs. Full Regression

export default defineConfig({
  projects: [
    {
      name: 'smoke',
      testMatch: /.*\\.smoke\\.spec\\.ts/,
    },
    {
      name: 'regression',
      testMatch: /.*\\.spec\\.ts/,
      testIgnore: /.*\\.smoke\\.spec\\.ts/,
    },
  ],
});
# Fast subset for every commit
npx playwright test --project=smoke

# Full suite, less frequently (nightly, pre-release)
npx playwright test --project=regression

This is a common, practical use of projects beyond just browsers — different test categories that need to run on different cadences, expressed entirely through config rather than separate scripts or CI pipelines.

An API-Only Project

Projects aren't limited to browser variants — a project can skip browser configuration entirely and just point at a subset of tests, which is exactly what a pure-API test suite needs: no devices spread, no viewport, nothing browser-specific at all.

projects: [
  {
    name: 'api',
    testDir: './tests/api', // only the API test files, no browser needed
  },
  { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
],
# Run only the fast, browser-free API suite — useful as an early CI stage
# that fails fast before paying the cost of spinning up real browsers
npx playwright test --project=api

Since the API Testing chapter's request fixture doesn't need a browser at all, an API project genuinely runs without launching Chromium/Firefox/WebKit — meaningfully faster, and a natural first stage in a CI pipeline that only proceeds to the slower browser projects once the API layer's own tests pass.

Dependencies Between Projects

Referenced in the Authentication chapter — a project can depend on another, which is how the setup-project authentication pattern works:

projects: [
  { name: 'setup', testMatch: /global\\.setup\\.ts/ },
  {
    name: 'chromium',
    use: { ...devices['Desktop Chrome'], storageState: 'playwright/.auth/user.json' },
    dependencies: ['setup'],
  },
],

Environments — Development, QA, Staging, Production

Environments aren't a Playwright-specific config concept the way projects are — they're typically expressed through environment variables read into the use.baseURL option:

export default defineConfig({
  use: {
    baseURL: process.env.BASE_URL || 'http://localhost:3000',
  },
});
# .env.development — usually just localhost, often the defineConfig default itself
BASE_URL=http://localhost:3000

# .env.qa
BASE_URL=https://qa.example.com

# .env.staging
BASE_URL=https://staging.example.com

# .env.production — run sparingly and carefully; see the note below
BASE_URL=https://www.example.com
# Run against a specific environment
BASE_URL=https://staging.example.com npx playwright test
# or, with a package like dotenv-cli:
dotenv -e .env.qa -- npx playwright test

The same test suite runs unchanged against any environment — the only thing that varies is which value baseURL resolves to, which is exactly the payoff of never hardcoding URLs, referenced throughout this course. Development is usually the implicit default (localhost, often not even needing its own .env file); QA and staging are where the bulk of full-suite runs happen; production deserves special caution — most teams either skip full automated suites there entirely, or run only a small, deliberately non-destructive smoke subset (using the project-based smoke/regression split from earlier on this page) rather than the full suite with its state-mutating tests.

Real-World Example — Environment-Specific Credentials

// global.setup.ts — credentials also come from environment variables,
// never hardcoded, so the same setup script works across environments
setup('authenticate', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill(process.env.TEST_USER_EMAIL!);
  await page.getByLabel('Password').fill(process.env.TEST_USER_PASSWORD!);
  await page.getByRole('button', { name: 'Sign in' }).click();
  await page.context().storageState({ path: 'playwright/.auth/user.json' });
});

Secrets belong in environment variables (injected by CI, or a local .env file excluded from version control) — never committed directly into config or test files, regardless of which environment they're for.

❌ Fragile vs. ✅ Recommended

// ❌ Separate, duplicated playwright.config.ts files per environment
// playwright.staging.config.ts, playwright.prod.config.ts — drift over time

// ✅ One config, environment-driven via variables
// use: { baseURL: process.env.BASE_URL }

Common Mistakes

  • Maintaining separate full config files per environment instead of one config driven by environment variables — these inevitably drift apart over time.
  • Committing real credentials or environment-specific secrets into config or .env files that get checked into version control.
  • Running the full regression suite on every commit instead of splitting a fast smoke subset for frequent runs and reserving the full suite for less frequent, scheduled runs.
  • Forgetting testIgnore when splitting projects by test category, causing smoke tests to also run (redundantly) as part of the "regression" project.

Edge Cases

  • A test that should only run against one specific project (e.g., a mobile-only gesture test) — use test.skip(condition, reason) based on testInfo.project.name rather than maintaining a separate file just for that one test.
  • Environments with different feature flags enabled — some tests may need to be conditionally skipped per environment if a feature isn't yet available there; keep this logic explicit and visible in the test, not hidden in shared config.

Debugging

If a test behaves differently than expected in CI versus locally, check which project and which BASE_URL actually ran — testInfo.project.name and the resolved baseURL are both visible in the HTML report and worth confirming before assuming the application itself behaved differently.

Best Practices

  • Use one playwright.config.ts driven by environment variables, not multiple near-duplicate config files.
  • Split smoke vs. full regression via projects and testMatch/testIgnore, not separate scripts.
  • Keep all secrets and environment-specific values in environment variables, injected by CI or a git-ignored local file.
  • Use project dependencies for setup steps (like authentication) that other projects rely on.

Practice Exercise

Configure a project setup with a fast @smoke-tagged subset and a full regression project, both reading baseURL from an environment variable, and verify both can be run independently via --project.

Summary

Projects express configuration variants (browsers, devices, test categories, dependencies) within one config file; environments express which real deployed target a run points at, typically via environment variables feeding baseURL and credentials. Together, they let one test suite and one config file serve every browser, device, test category, and deployment target without duplication.

Interview Questions

What's the difference between a Playwright "project" and an "environment," and how do they typically work together?▾
A project is a named configuration variant defined in playwright.config.ts — different browsers, devices, or test subsets, each potentially with different use options. An environment is the actual deployed target (local, staging, production) a test run points at, usually controlled via an environment variable feeding baseURL. They're independent axes: the same project (say, "chromium") can run against any environment depending on what BASE_URL is set to when the suite runs.
What's the practical difference between a Playwright 'project' and an 'environment'?▾
A project is a config variant (browser, device, test subset) inside playwright.config.ts; an environment is the actual deployed target a run points at, usually via a BASE_URL variable.
Why maintain one config file driven by environment variables instead of separate config files per environment?▾
Separate files inevitably drift apart over time; one config with conditional values stays consistent by construction.
What's the benefit of an API-only project with no browser configuration?▾
It runs genuinely faster since no browser launches at all — a good early, fail-fast stage in a CI pipeline before slower browser projects run.
Why is running a full destructive test suite against production risky?▾
Most teams either skip full automated runs there entirely or limit it to a small, deliberately non-destructive smoke subset instead.
