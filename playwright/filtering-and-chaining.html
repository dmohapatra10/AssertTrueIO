Filtering and Chaining Locators

Beginner 6 min read

Prerequisites: Locators overview, getByRole()

What is this?

Every locator strategy so far finds elements by a single property — a role, a label, some text. Real UIs are full of repeated structures (table rows, list items, cards) where many elements share that same role or text, and you need to narrow down to exactly one. Filtering and chaining are how you do that precisely, without falling back to a positional CSS selector.

Why it's important

This is where locator strategy stops being about which getBy*() method to use and starts being about composition — combining locators to describe "the button, but specifically inside this row" the way a person would describe it, instead of "the third button on the page," which breaks the moment the list order changes.

filter() with hasText

page.locator(selector).filter(options: {
  hasText?: string | RegExp,
  hasNotText?: string | RegExp,
  has?: Locator,
  hasNot?: Locator,
})
// Find the list item that CONTAINS certain text, then act inside it
await page.getByRole('listitem')
  .filter({ hasText: 'Wireless Mouse' })
  .getByRole('button', { name: 'Remove' })
  .click();

filter() doesn't change what a locator matches directly — it takes a locator that matches several elements and narrows it down to the subset satisfying the filter condition, still returning a locator (lazy, re-searched on each use), not a snapshot.

filter() with has

// Find the table row that CONTAINS a specific button — narrowing by
// the presence of a child element, not just text
const outOfStockRow = page.getByRole('row').filter({
  has: page.getByText('Out of stock'),
});
await outOfStockRow.getByRole('button', { name: 'Notify me' }).click();

has filters by the presence of a matching descendant locator — useful when the distinguishing feature isn't the row's own text, but something nested inside it, like a status badge or icon.

Basic Example — first(), last(), nth()

await page.getByRole('listitem').first().click();   // first match
await page.getByRole('listitem').last().click();    // last match
await page.getByRole('listitem').nth(2).click();    // third match (0-indexed)

These select by position within the current match set — powerful, but the least meaningful option here, since position is exactly the kind of implementation detail that changes for reasons unrelated to the feature under test. Reach for these only when position is genuinely part of what's being tested (e.g., "the most recently added item").

Detailed Example — Chaining into a Specific Row

// Chaining: scope a search to inside one specific, uniquely-identified row
const row = page.getByRole('row', { name: 'Order #1042' });
await row.getByRole('button', { name: 'Cancel' }).click();
await expect(row.getByText('Cancelled')).toBeVisible();

Chaining calls .getByRole() (or any locator method) directly on an existing locator, scoping the search to descendants of that element only. This is the cleanest way to disambiguate repeated elements — find the unique container first, then search within it.

Real-World Example — Shopping Cart Table

test('user can remove a specific item from the cart', async ({ page }) => {
  await page.goto('/cart');

  const mouseRow = page.getByRole('row').filter({ hasText: 'Wireless Mouse' });
  const keyboardRow = page.getByRole('row').filter({ hasText: 'Mechanical Keyboard' });

  await mouseRow.getByRole('button', { name: 'Remove' }).click();

  await expect(mouseRow).toBeHidden();
  await expect(keyboardRow).toBeVisible(); // untouched
  await expect(page.getByTestId('cart-count')).toHaveText('1 item');
});

Filtering both rows by text up front, then asserting one disappeared while the other remained, is a stronger test than checking cart count alone — it confirms the right item was removed, not just that an item was.

❌ Fragile vs. ✅ Recommended

// ❌ Positional — breaks the moment sort order or a new item changes the index
await page.getByRole('row').nth(2).getByRole('button', { name: 'Remove' }).click();

// ✅ Content-based — stays correct regardless of order
await page.getByRole('row')
  .filter({ hasText: 'Wireless Mouse' })
  .getByRole('button', { name: 'Remove' })
  .click();

Common Mistakes

  • Defaulting to .first() to silence a strict-mode error instead of writing a more specific locator — this doesn't resolve ambiguity, it just picks an arbitrary match that can be wrong, or become wrong later.
  • Using nth() for content that isn't inherently ordered (e.g., cards in a grid that could re-flow) — makes the test coupled to layout, not content.
  • Chaining too deep without an intermediate variable, producing an unreadable one-line locator that's hard to debug when it fails — assigning the intermediate row/section to a named variable (as in the cart example) keeps it traceable.

Edge Cases

  • Filtering by a locator that itself matches multiple elements (has) — this doesn't cause a strict-mode error on its own, since has just checks presence within each candidate, not uniqueness of the inner match.
  • Combining hasText and has together in one filter() call — both conditions must be satisfied; useful for very specific disambiguation, like "the row containing this text AND this icon."

Debugging

When a filtered/chained locator matches zero elements, verify each step in isolation — first confirm the outer locator (e.g., getByRole('row')) matches the expected number of rows on its own, then add the filter, then add the chained action. Debugging the whole composed locator at once makes it hard to tell which link in the chain is wrong.

Best Practices

  • Prefer filter({ hasText }) or filter({ has }) over nth() whenever the distinguishing feature is content, not position.
  • Name intermediate locators with descriptive variables (mouseRow, not a re-typed chain) for both readability and reuse across multiple actions/assertions in the same test.
  • Treat a strict-mode violation as a prompt to add a filter or chain, not to reach for .first().

Practice Exercise

A notifications list has five items, three marked "unread." Write a locator that filters to only unread items, then clicks the "Mark as read" button inside the first one, using filter() rather than nth() where the choice matters.

Summary

filter() (with hasText or has) and chaining are how you disambiguate repeated elements by content and structure rather than position. first()/last()/nth() exist for genuinely order-dependent cases, but should be the exception, not the default way of resolving strict-mode errors.

Interview Questions

Why is filter({ hasText }) generally preferred over nth() when both could isolate the same element in a test run today?▾
nth() encodes the element's current position, which is incidental and can change (sorting, a new item added, a filter applied) without the underlying feature actually changing. filter({ hasText }) encodes what makes that element meaningfully distinct, so the locator keeps working even if its position shifts — it's the same principle behind preferring role/label over CSS, applied to disambiguation instead of initial selection.
Why is filter({ hasText }) usually better than nth() for finding a specific row?▾
nth() depends on position, which can change due to sorting or new rows; filtering by content stays correct regardless of order.
What's the difference between filter({ hasText }) and filter({ has })?▾
hasText matches by the element's own text content; has matches by the presence of a descendant matching a given locator.
When is using .first() to resolve a strict-mode violation a mistake?▾
When it just silences the error without actually disambiguating intent — it can pick the wrong element if order isn't guaranteed.
How would you scope an action to inside one specific table row?▾
Locate the row uniquely first (e.g. getByRole('row').filter({ hasText: '...' })), assign it to a variable, then chain further locator calls on that variable.
