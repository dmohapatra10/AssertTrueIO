Visibility & State Assertions

Beginner 5 min read

Prerequisites: Assertions overview

What is this?

These are the assertions that check whether an element is present, showing, or interactable: toBeVisible(), toBeHidden(), toBeEnabled(), toBeDisabled(), and toBeChecked(). They're the most-used assertions in any Playwright suite, because "is this thing actually there and usable" is the first thing almost every test needs to confirm.

Why it's important

Each of these mirrors a real actionability check from the Actions chapter — toBeVisible() is the assertion-side equivalent of the visibility check that runs before a click. Using the assertion explicitly (rather than relying on a later action to implicitly fail) makes a test's intent clear and gives a much more specific failure message than "click() timed out."

Basic Example

await expect(page.getByRole('dialog')).toBeVisible();
await expect(page.getByText('Loading...')).toBeHidden();
await expect(page.getByRole('button', { name: 'Submit' })).toBeEnabled();
await expect(page.getByRole('button', { name: 'Submit' })).toBeDisabled();
await expect(page.getByLabel('Remember me')).toBeChecked();

Detailed Example — Waiting Out a Disabled State

// The Submit button starts disabled until all required fields are filled.
// toBeEnabled() polls until that becomes true, instead of checking once.
await page.getByLabel('Email').fill('user@example.com');
await page.getByLabel('Password').fill('secret123');
await expect(page.getByRole('button', { name: 'Sign in' })).toBeEnabled();
await page.getByRole('button', { name: 'Sign in' }).click();

This pattern — asserting a precondition is true before acting — produces a much clearer failure than skipping straight to the click and letting actionability timeout do the work; the assertion names exactly what was expected.

Real-World Example — Toast Lifecycle

test('adding an item shows and then dismisses a confirmation toast', async ({ page }) => {
  await page.goto('/inventory');
  await page.getByRole('button', { name: 'Add to cart' }).first().click();

  await expect(page.getByText('Added to cart')).toBeVisible();
  await expect(page.getByText('Added to cart')).toBeHidden({ timeout: 5000 });
});

Both assertions retry — the first waits for the toast to appear, the second waits (up to 5 seconds) for it to disappear. Neither needs a manual waitForTimeout().

toBeVisible() vs. Element Existing in the DOM

An element can be attached to the DOM but not visible (display: none, zero size, visibility: hidden). toBeVisible() checks true visual visibility, not just DOM presence — use toBeAttached() (a separate, less common assertion) when presence in the DOM is genuinely what matters, such as content that's deliberately visually hidden but still meant to exist for screen readers.

❌ Fragile vs. ✅ Recommended

// ❌ One-time check, no retry — flaky if the element renders a beat later
if (await page.getByRole('dialog').isVisible()) { /* ... */ }

// ✅ Auto-retrying assertion — waits for the real condition
await expect(page.getByRole('dialog')).toBeVisible();

Common Mistakes

  • Using isVisible() as an if-condition instead of an assertion — this checks once, immediately, with no retry, and is a frequent source of flaky tests when developers reach for it from habit.
  • Asserting toBeEnabled() when the real question is whether an element exists at all — a missing element and a disabled one fail differently; read the actual error message rather than assuming.
  • Forgetting toBeChecked() has a { checked: false } option for explicitly asserting the unchecked state, instead of always reaching for .not.toBeChecked().

Edge Cases

  • Elements with zero opacity but full size — depending on how a fade transition is implemented, toBeVisible() may or may not consider a fully-transparent-but-present element visible; verify behavior against your specific animation library if this matters to a test.
  • Indeterminate checkboxes (neither checked nor unchecked) — toBeChecked() and its negation don't have a third state; use toHaveJSProperty('indeterminate', true) for that specific case.

Debugging

A failed toBeVisible() assertion's error message includes the element's last known state — check whether it says "not found" (locator matched nothing) versus "hidden" (matched but not visible); these point to different root causes.

Best Practices

  • Reach for these assertions instead of manual isVisible()/isEnabled() boolean checks anywhere a condition needs to become true.
  • Assert preconditions explicitly before actions that depend on them, rather than relying on the action's own actionability timeout to surface the problem.

Practice Exercise

Write a test for a multi-step form where the "Next" button is disabled until a required checkbox is checked. Assert the disabled state first, check the box, then assert the button becomes enabled.

Summary

toBeVisible(), toBeHidden(), toBeEnabled(), toBeDisabled(), and toBeChecked() are auto-retrying checks for an element's presence and interactive state — the assertion-level counterpart to actionability checks, and almost always preferable to a one-time boolean check.

Interview Questions

What's the practical difference between if (await locator.isVisible()) and await expect(locator).toBeVisible()?▾
isVisible() returns the current state at the instant it's called, with no retry — if the element isn't visible yet but will be in 200ms, the check fails immediately. expect().toBeVisible() polls repeatedly until the condition is true or the timeout is reached, which is what makes it reliable against normal page timing variance.
What's the practical difference between isVisible() and toBeVisible()?▾
isVisible() checks once immediately with no retry; toBeVisible() polls repeatedly until true or timeout, matching real page timing.
Does toBeVisible() check DOM presence or true visual visibility?▾
Visual visibility — an element can be attached to the DOM but fail toBeVisible() if it's display:none or has zero size.
How would you assert a checkbox is specifically unchecked, not just 'not checked due to absence'?▾
Use .not.toBeChecked(), or toBeChecked({ checked: false }) to be explicit about the expected state.
Why assert a precondition like toBeEnabled() before an action that depends on it?▾
It produces a much clearer failure message naming exactly what was expected, rather than relying on the action's own actionability timeout to surface the problem indirectly.
