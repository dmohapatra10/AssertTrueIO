Chapter 13: File Upload and Download

Beginner 7 min read

Prerequisites: Actions, Waiting and Synchronization

What is this?

File uploads and downloads both involve the browser talking to the local filesystem — something normal DOM interaction doesn't cover. Playwright provides dedicated APIs for both: setInputFiles() for uploads (covered in full depth on its own page in the Actions chapter), and a download event for downloads, which is this page's main focus.

Why it's important

Real operating-system file pickers and native "Save As" dialogs can't be automated through the DOM at all — Playwright sidesteps both entirely rather than trying to automate a dialog that's fundamentally outside a browser's control.

Uploading Files — Quick Recap

await page.getByLabel('Upload resume').setInputFiles('fixtures/resume.pdf');

// Drag-and-drop widgets usually style over a hidden <input type="file"> —
// target it directly rather than trying to simulate the drag gesture
await page.locator('input[type="file"]').setInputFiles('fixtures/report.csv');

See the dedicated setInputFiles() page in the Actions chapter for the full treatment — multiple files, in-memory buffers, and hidden-input edge cases.

Mental Model — Handling Downloads

Downloads are captured via a download event, following the same event-pairing pattern used for new tabs in the previous chapter: the download starts as a side effect of an action, and you need to be listening for the event before that action fires — not after.

const [download] = await Promise.all([
  page.waitForEvent('download'),
  page.getByRole('button', { name: 'Export CSV' }).click(),
]);

expect(download.suggestedFilename()).toBe('orders-export.csv');
await download.saveAs('downloads/orders-export.csv');

Basic Example — Inspecting a Download Without Saving It

const [download] = await Promise.all([
  page.waitForEvent('download'),
  page.getByRole('button', { name: 'Export CSV' }).click(),
]);

// Playwright keeps a temporary copy — read it directly without a permanent save
const downloadPath = await download.path();
const fs = require('fs');
const contents = fs.readFileSync(downloadPath, 'utf-8');
expect(contents).toContain('order_id,total,status');

download.path() is often more useful than saveAs() for tests — you usually want to verify the file's contents, not keep a permanent copy on disk after the test run.

Detailed Example — Verifying a Generated PDF's Size

const [download] = await Promise.all([
  page.waitForEvent('download'),
  page.getByRole('button', { name: 'Download invoice' }).click(),
]);

const downloadPath = await download.path();
const stats = fs.statSync(downloadPath);
expect(stats.size).toBeGreaterThan(1000); // sanity check it's not an empty/broken file

Full content verification of a binary file like a PDF is often impractical, but confirming a plausible file size is a cheap, useful sanity check that catches the common failure mode of a broken or empty export.

Real-World Example — Upload Then Verify Processing

import { test, expect } from '@playwright/test';
import path from 'path';

test('uploads a CSV and shows a processed preview', async ({ page }) => {
  await page.goto('/import');

  await page.getByLabel('Choose file').setInputFiles(
    path.join(__dirname, '../fixtures/customers.csv')
  );

  await page.getByRole('button', { name: 'Upload' }).click();

  await expect(page.getByText('142 rows detected')).toBeVisible();
  await expect(page.getByRole('table')).toBeVisible();
});

Using path.join(__dirname, ...) keeps the fixture path correct regardless of which directory the test is run from — a small habit that avoids "file not found" errors that only show up in CI.

❌ Fragile vs. ✅ Recommended

// ❌ Click first, then listen — the download event may already have fired
await page.getByRole('button', { name: 'Export CSV' }).click();
const download = await page.waitForEvent('download'); // race condition

// ✅ Listen and trigger together
const [download] = await Promise.all([
  page.waitForEvent('download'),
  page.getByRole('button', { name: 'Export CSV' }).click(),
]);

Common Mistakes

  • Trying to click a native "Choose file" OS dialog instead of calling setInputFiles() directly on the input element.
  • Using a relative fixture path that only happens to work when the test is run from the project root, breaking in CI or from a different working directory.
  • Not pairing the download-triggering click with waitForEvent('download') in a Promise.all, risking a race exactly like the one covered for new tabs.
  • Calling saveAs() when the test only needs to verify content — reading via download.path() avoids leaving files scattered across CI runners.

Edge Cases

  • Downloads that fail server-side (a broken export) — the download event still fires even for a failed/empty download in some cases; checking file size or content, not just that the event fired, catches this.
  • Downloads triggered without a full page navigation (a client-side blob URL) — Playwright's download event handles these the same way as a traditional server-driven download.
  • Very large files — for genuinely large downloads, prefer checking file size/hash over reading full contents into memory in the test process.

Debugging

If a download-triggering test hangs, confirm the button actually initiates a real browser download (versus, say, opening a PDF in a new tab for in-browser viewing, which is a different interaction entirely and wouldn't fire a download event).

Best Practices

  • Store test fixture files (sample PDFs, CSVs, images) in a dedicated fixtures/ directory and reference them with path.join(__dirname, ...).
  • Assert on download.suggestedFilename() to catch cases where the wrong file or an unexpectedly-named file gets exported.
  • Prefer inspecting download.path() directly over saveAs() unless the test genuinely needs a permanent copy.

Practice Exercise

Write a test that uploads a CSV, triggers a "Download processed results" export, and verifies the downloaded file's content reflects the uploaded data (e.g., the same row count appears in both).

Summary

setInputFiles() sets a file input's value directly, sidestepping the native OS file picker Playwright can't automate. Downloads are captured with a download event using the same event-pairing pattern as new tabs, giving access to the suggested filename and the file's contents (via path()) for verification without necessarily saving a permanent copy.

Interview Questions

Why can't Playwright just click the native "Choose file" button and interact with the OS file picker directly?▾
The native OS file picker is outside the browser's DOM and outside what any browser automation protocol can control — it's rendered by the operating system, not the page. Playwright avoids the problem entirely by exposing setInputFiles(), which sets the file input's value programmatically, achieving the same end state as a real user picking a file without needing to automate a dialog that's fundamentally out of reach.
Why can't Playwright automate a native 'Save As' download dialog?▾
It's a native OS-level dialog outside the browser's control, the same reason the file upload picker can't be automated directly.
How do you inspect a downloaded file's contents without permanently saving it?▾
Use download.path() to get a temporary file path Playwright already keeps, and read it directly rather than calling saveAs().
Why pair a download-triggering click with Promise.all and waitForEvent('download')?▾
To avoid the same race condition covered for new tabs — the download event could fire before a wait registered afterward starts listening.
What's a cheap sanity check for a downloaded binary file like a PDF?▾
Checking the file size is above a reasonable minimum, catching the common failure mode of an empty or broken export.
