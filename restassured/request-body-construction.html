Request Body Construction

Beginner 5 min read

Prerequisites: Path Parameters

What is this?

RestAssured accepts a request body in several different shapes. This isn't a stylistic choice you make once and forget — picking the right representation for a given test is a real design decision, covered here in depth.

1. Raw String Body

String requestBody = """
{
  "name": "John",
  "email": "john@example.com"
}
""";

given()
    .contentType(ContentType.JSON)
    .body(requestBody)
.when()
    .post("/users");

Java's text blocks ("""...""", since Java 15) make raw JSON far more readable than old-style escaped-quote string concatenation. Use a raw string specifically when you need to test malformed or intentionally invalid JSON — a POJO literally can't represent something that isn't valid Java in the first place, so this is the only approach available for that specific negative-testing need.

2. Map

Map<String, Object> user = new HashMap<>();
user.put("name", "John");
user.put("email", "john@example.com");

given()
    .contentType(ContentType.JSON)
    .body(user)
.when()
    .post("/users");

Fast to write with no class definition required — RestAssured serializes it to JSON automatically. The tradeoff: zero compile-time safety. A typo'd key ("emial" instead of "email") compiles fine and silently sends a slightly wrong payload with no warning at all.

3. POJO

public class User {
    private String name;
    private String email;
    // no-arg constructor, parameterized constructor, getters/setters
}

User user = new User("John", "john@example.com");

given()
    .contentType(ContentType.JSON)
    .body(user)
.when()
    .post("/users");

The approach real production suites converge on once a payload shape is reused: the compiler catches typo'd field names immediately, your IDE offers autocomplete, and renaming a field updates every usage at once. Chapter 5 (JSON, Serialization & Deserialization) goes considerably deeper on POJO design, serialization control, and nested structures — this is just the entry point.

Decision Table

ApproachUse when
Raw StringTesting malformed/invalid JSON specifically, or a genuine one-off with no reuse
MapQuick prototyping, or a payload shape that's legitimately dynamic/unpredictable
POJOAnything reused across more than one or two tests — the default for real projects

Real-World Example — Testing a Validation Error with a Raw String

@Test
void malformedJsonReturns400() {
    String brokenJson = "{ \\"name\\": \\"John\\", }"; // trailing comma — invalid JSON

    given()
        .contentType(ContentType.JSON)
        .body(brokenJson)
    .when()
        .post("/users")
    .then()
        .statusCode(400);
}

This is exactly the scenario a POJO can never express — a trailing comma is a JSON syntax error, and Java's own type system won't let you construct an object that serializes to invalid JSON in the first place. A raw string is the only tool available for this specific, deliberately-malformed-input test.

❌ Fragile vs. ✅ Recommended

// ❌ A raw Map body for a payload shape reused across a dozen tests,
// with no compiler protection against a typo'd key anywhere
Map<String, Object> order = new HashMap<>();
order.put("itme", "Wireless Mouse"); // typo — compiles fine, silently wrong

// ✅ A POJO catches this at compile time
OrderRequest order = new OrderRequest("Wireless Mouse", 2); // typo'd field name won't compile

Common Mistakes

  • Defaulting to Map<String, Object> for a growing test suite instead of graduating to a POJO once the same payload shape gets reused — silently accumulates typo risk with zero compiler protection.
  • Attempting to represent deliberately malformed JSON as a POJO — this isn't possible; a raw string is the only correct tool for testing invalid input.
  • Forgetting .contentType(ContentType.JSON) regardless of which body representation is used — some servers infer it correctly, but relying on that is fragile across different API implementations.

Edge Cases

  • Multipart/form-data bodies (file uploads via API) — none of the three approaches above apply; use .multiPart() instead of .body() for this specific case.
  • Bodies that legitimately need dynamic, unpredictable shape (a generic proxy test, for instance) — a Map is the more honest representation here, since a POJO would need to over-specify a shape that isn't actually fixed.

Debugging

If you're unsure exactly what JSON a POJO or Map will produce once serialized, add .log().body() right after given() to print the actual outgoing body before RestAssured sends the request.

Best Practices

  • Graduate from raw Maps to POJOs once a payload shape is genuinely reused across multiple tests.
  • Reserve raw string bodies specifically for malformed/invalid-JSON negative tests, not as a general-purpose default.
  • Always set Content-Type explicitly, regardless of which body representation you're using.

Practice Exercise

Write three versions of the same "create user" test — one using a raw String body, one using a Map, and one using a POJO — and note which felt most maintainable, and which would most quickly surface a typo'd field name.

Summary

Raw strings, Maps, and POJOs each serve a genuinely different purpose as a request body: raw strings for testing malformed input a POJO structurally can't represent, Maps for quick one-offs with no lasting reuse, and POJOs as the default once a payload shape is reused enough that compile-time safety starts paying for itself.

Interview Questions

Why can't you use a POJO to test how an API handles malformed JSON, like a trailing comma or an unquoted key?▾
A POJO is a Java object, and Java's serialization libraries (Jackson/Gson) only ever produce syntactically valid JSON from it — there's no way to configure a POJO to serialize into JSON containing a syntax error, because valid Java objects simply don't have a representation for "broken JSON." Testing malformed input specifically requires bypassing object serialization entirely and providing the raw, deliberately invalid JSON text directly via a String body.
When is a raw String body the only viable option for a request?▾
When testing deliberately malformed or invalid JSON — a POJO structurally can't represent invalid syntax, since Java's type system only ever produces valid JSON when serialized.
What's the main risk of using Map<String, Object> for a payload reused across many tests?▾
Zero compile-time safety — a typo'd key compiles fine and silently sends a slightly wrong payload with no warning, unlike a POJO where the compiler catches a misspelled field name immediately.
At what point should a project graduate from Map-based bodies to POJOs?▾
Once the same payload shape gets reused across more than a couple of tests — for a genuine one-off, a Map is faster to write with no real downside.
Why can't you meaningfully test 'invalid quantity type' using a POJO with an int field?▾
Java's own compiler prevents assigning a string to an int field, so there's no way to construct a POJO instance representing that invalid state — this scenario requires a raw string body instead.
