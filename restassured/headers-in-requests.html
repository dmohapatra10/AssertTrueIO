Headers

Beginner 6 min read

Prerequisites: Building HTTP Requests overview

What is this?

given()
    .header("Content-Type", "application/json")
.when()
    .get("/users");

A header attaches metadata to a request, separate from the actual body content — what format the body is in, what format you want back, credentials, tracing identifiers. This page covers setting them correctly and knowing which ones actually matter for a given request.

Single Header

given()
    .header("X-Request-ID", UUID.randomUUID().toString())
.when()
    .get("/users");

Multiple Headers

Map<String, String> headers = new HashMap<>();
headers.put("Content-Type", "application/json");
headers.put("Accept", "application/json");
headers.put("X-Request-ID", UUID.randomUUID().toString());

given()
    .headers(headers)
.when()
    .get("/users");

Chaining .header() repeatedly works for two or three headers; beyond that, a Map passed to .headers() reads more cleanly and avoids a long chain of near-identical calls.

Content-Type vs. Accept

These two are frequently confused because they often carry the same value in practice, but they answer different questions: Content-Type describes the format of the body you're sending — relevant on POST/PUT/PATCH, meaningless on a bodyless GET. Accept describes the format you want back — relevant on every request, including GET.

// POST with a body — Content-Type matters here
given()
    .contentType(ContentType.JSON)  // shorthand for .header("Content-Type", "application/json")
    .body(user)
.when()
    .post("/users");

// GET with no body — only Accept is meaningful
given()
    .accept(ContentType.JSON)
.when()
    .get("/users");

.contentType() and .accept() are typed convenience methods RestAssured provides specifically for these two headers — functionally equivalent to setting them via .header(), but clearer about intent and less error-prone than typing the header name as a raw string.

Custom Headers

given()
    .header("X-Request-ID", UUID.randomUUID().toString())
    .header("X-Client-Version", "2.4.1")
.when()
    .get("/users");

Custom headers (anything prefixed X- by convention, though this isn't a hard rule) follow the exact same .header() pattern as standard ones — there's no special API for "important" headers. A request-tracing ID is a common real-world example: attaching one to every outgoing test request makes it far easier to correlate a specific test run with server-side logs when debugging a failure.

Real-World Example — A Realistic Authenticated Request

given()
    .contentType(ContentType.JSON)
    .accept(ContentType.JSON)
    .header("Authorization", "Bearer " + token)
    .header("X-Request-ID", UUID.randomUUID().toString())
    .body(order)
.when()
    .post("/orders")
.then()
    .statusCode(201);

This combines typed convenience methods (contentType, accept) with raw .header() calls for anything without a dedicated method — the natural shape of a real authenticated request.

Overriding a Header Set Elsewhere

RequestSpecification baseSpec = new RequestSpecBuilder()
    .addHeader("Authorization", "Bearer default-token")
    .build();

given()
    .spec(baseSpec)
    .header("Authorization", "Bearer " + testSpecificToken) // overrides the base spec's value
.when()
    .get("/profile");

When a header is set both in a shared RequestSpecification (covered fully in Chapter 8) and again directly in a specific test, the value set later — closer to when the request actually fires — wins. This is genuinely useful for a test that needs to run as a specific, different user than whatever the shared base configuration defaults to.

Sending a Header Multiple Times

given()
    .header("X-Tag", "beta")
    .header("X-Tag", "internal") // does NOT overwrite — RestAssured sends BOTH
.when()
    .get("/features");
// Sends two separate X-Tag headers: beta AND internal

Unlike overriding a value from a shared spec (above), calling .header() twice with the same name within a single request adds a second instance of that header rather than replacing the first — some APIs genuinely expect repeated headers with the same name (uncommon, but real). If you actually meant to replace a value rather than add a second one, double-check you're not accidentally sending both.

❌ Fragile vs. ✅ Recommended

// ❌ Setting Content-Type manually as a raw string, prone to typos
given().header("Content-Type", "aplication/json").body(user); // typo — silently wrong

// ✅ Typed convenience method — no string typo possible
given().contentType(ContentType.JSON).body(user);

Common Mistakes

  • Setting Content-Type on a GET request where it's meaningless — a GET has no body, so there's nothing for Content-Type to describe.
  • Typing header values as raw strings when a typed method exists (.contentType(ContentType.JSON) instead of a hand-typed string) — trades away typo protection for no real benefit.
  • Confusing Content-Type and Accept when only one is actually relevant to the request being made.

Edge Cases

  • Multiple values for the same header name — some APIs genuinely expect this (rare, but happens with certain caching or CDN headers); RestAssured supports it via repeated .header() calls with the same name.
  • Case sensitivity — HTTP header names are case-insensitive by spec; don't assume a test failure is header-name-casing related without checking the actual response first.

Debugging

If a request seems to be missing an expected header, add .log().headers() right after given() to print exactly what's being sent before the request goes out.

Best Practices

  • Use typed convenience methods (.contentType(), .accept()) over raw string headers whenever one exists.
  • Only set headers that are actually meaningful for the specific method being used.
  • Consider a request-tracing header (like X-Request-ID) as a standing habit in a real test suite — it pays off during debugging far more often than it costs to add.

Practice Exercise

Write a POST request with a JSON body, setting Content-Type via the typed convenience method, plus a custom X-Request-ID header with a randomly generated UUID — then confirm via .log().headers() that all three headers appear correctly in the outgoing request.

Summary

Headers carry metadata alongside a request — Content-Type describes what you're sending, Accept describes what you want back, and custom headers (tracing IDs, client versions) follow the same pattern as standard ones. Typed convenience methods like .contentType() are safer than raw string headers wherever RestAssured provides one.

Interview Questions

Why is setting Content-Type meaningless on a GET request?▾
Content-Type describes the format of the request body — but a GET request, by REST convention, doesn't carry a body at all; anything the request needs to express goes in the URL via query or path parameters instead. Setting Content-Type on a bodyless GET has nothing to actually describe, so it's a harmless but meaningless header in that context — Accept, which describes the format of the response you want back, is the one that's actually relevant on a GET.
What's the actual difference between Content-Type and Accept?▾
Content-Type describes the format of the body you're SENDING (relevant on POST/PUT/PATCH); Accept describes the format you want back (relevant on any request, including a bodyless GET).
Why prefer .contentType(ContentType.JSON) over manually setting the header as a string?▾
The typed convenience method avoids the possibility of a typo in the raw header value string, which would silently produce a wrong Content-Type with no compile-time protection.
What happens if you call .header() twice with the same name in one request?▾
It adds a second instance of that header rather than replacing the first — some APIs genuinely expect repeated headers with the same name; if you meant to replace a value, check you're not accidentally sending both.
Why is a request-tracing header like X-Request-ID worth adding as a standing habit?▾
It makes correlating a specific test run with server-side logs far easier during debugging — a small addition that pays off disproportionately when investigating a failure.
