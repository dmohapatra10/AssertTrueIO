Dynamic & Polymorphic JSON

Beginner 7 min read

Prerequisites: Advanced JsonPath Navigation

What is this?

So far, every example has assumed a uniform, predictable shape — every order has the same fields, every user looks the same. Real APIs frequently don't work that way: fields that are sometimes present and sometimes not, values that are sometimes a string and sometimes null, or — the most complex case — a collection where different elements genuinely have different shapes depending on their type.

Optional Fields — Testing Presence Explicitly

{ "id": 1, "name": "John", "middleName": null, "nickname": "Johnny" }
{ "id": 2, "name": "Jane" }
// Don't assume every response has every field — test presence explicitly where it matters
.then().body("$", hasKey("nickname")); // does this response include this key at all?

// Distinguish "key present but null" from "key absent entirely"
JsonPath json = response.jsonPath();
boolean hasMiddleNameKey = json.getMap("$").containsKey("middleName");
Object middleNameValue = json.get("middleName"); // null either way — this alone can't distinguish the two cases

This is a genuinely important distinction some APIs care about: a field explicitly set to null versus a field omitted from the response entirely can mean different things (an intentional "no value" versus "this field doesn't apply here at all"). hasKey() / containsKey() checks presence directly; a plain value read can't tell the two apart, since both produce null in Java.

Null Values — Asserting Correctly

.then().body("middleName", nullValue());       // explicitly checking it's null
.then().body("nickname", notNullValue());        // explicitly checking it's present and non-null

Both are legitimate, deliberate assertions — the mistake isn't using either one, it's not being deliberate about which fields in a response are allowed to be null and testing that contract explicitly, rather than only ever testing the "happy" fully-populated case.

Polymorphic Responses — Different Shapes in One Collection

{
  "events": [
    { "type": "order_created", "orderId": 500, "total": 120.00 },
    { "type": "user_registered", "userId": 42, "email": "john@example.com" },
    { "type": "payment_failed", "orderId": 500, "reason": "insufficient_funds" }
  ]
}
// Each event type has genuinely different fields — validate by type
.then().body("events.findAll { it.type == 'order_created' }.orderId", hasItem(500));
.then().body("events.findAll { it.type == 'payment_failed' }.reason", hasItem("insufficient_funds"));

// Confirm every element at least has the common field every type shares
.then().body("events.type", everyItem(notNullValue()));

This is a real pattern in event-driven or activity-feed APIs — one array containing meaningfully different object shapes, distinguished by a type discriminator field. The strategy is always the same: filter by the discriminator first (using the advanced JsonPath filtering from the previous page), then assert on the fields specific to that filtered subset.

Detailed Example — Deserializing Polymorphic JSON into Java (Jackson Polymorphism)

@JsonTypeInfo(use = JsonTypeInfo.Id.NAME, property = "type")
@JsonSubTypes({
    @JsonSubTypes.Type(value = OrderCreatedEvent.class, name = "order_created"),
    @JsonSubTypes.Type(value = UserRegisteredEvent.class, name = "user_registered")
})
public abstract class Event {
    public String type;
}

public class OrderCreatedEvent extends Event {
    public int orderId;
    public double total;
}

public class UserRegisteredEvent extends Event {
    public int userId;
    public String email;
}
Event[] events = given().when().get("/events").as(Event[].class);
for (Event event : events) {
    if (event instanceof OrderCreatedEvent oce) {
        assertThat(oce.total, greaterThan(0.0));
    }
}

For polymorphic responses you need to work with extensively in Java (not just validate a field or two), Jackson's @JsonTypeInfo/@JsonSubTypes annotations let deserialization automatically produce the correct concrete subclass based on a discriminator field — building on the POJO deserialization fundamentals from the JSON & Serialization chapter, extended to handle genuinely varying shapes.

Real-World Example — A Response Where a Field's Type Itself Varies

// Some APIs (inconsistently) return a single object OR an array
// depending on how many results matched
{ "results": { "id": 1, "name": "Single Match" } }
// vs.
{ "results": [{ "id": 1 }, { "id": 2 }] }
Object results = response.jsonPath().get("results");
if (results instanceof List) {
    // handle as a collection
} else {
    // handle as a single object
}

This specific inconsistency (a field that's sometimes a single object, sometimes an array of the same shape) is a genuine, if unfortunate, API design pattern you'll occasionally encounter — worth recognizing rather than assuming your test is broken when a JsonPath expression that worked for the array case suddenly fails against the single-object case, or vice versa.

❌ Fragile vs. ✅ Recommended

// ❌ Assuming every element in a collection has the same shape,
// then being surprised when a NullPointerException or ClassCastException occurs
.then().body("events[1].orderId", equalTo(500)); // events[1] is actually a user_registered event — no orderId field

// ✅ Filter by the discriminator first, THEN assert on type-specific fields
.then().body("events.findAll { it.type == 'order_created' }.orderId", hasItem(500));

Common Mistakes

  • Assuming every element in a collection shares the same shape without checking for a type discriminator field first.
  • Not distinguishing "null value" from "absent field" when the API's contract actually treats them differently.
  • Only testing the fully-populated, no-nulls-anywhere version of a response, never a response with legitimately optional fields actually omitted.

Edge Cases

  • A field whose type varies inconsistently (single object vs. array) — handle this explicitly with a type check in Java rather than assuming one shape; this is an API design smell worth flagging if you control the API.
  • Deeply polymorphic structures (events containing other polymorphic sub-events) — apply the same filter-by-discriminator strategy recursively at each level.

Debugging

If a test fails with a null-related or type-related error on what looked like straightforward field access, suspect a polymorphic or optional-field structure before assuming a bug — print the raw response and check whether every element in a collection genuinely shares the field you assumed was universal.

Best Practices

  • Filter by a type discriminator before asserting on type-specific fields in a polymorphic collection.
  • Test optional/nullable fields in both their present and absent states explicitly, not just the fully-populated case.
  • Use Jackson's polymorphic deserialization annotations when working extensively with varying-shape data in Java, rather than manual type-checking scattered throughout test code.

Practice Exercise

Design a hypothetical "activity feed" response with at least three different event types sharing a common type field but different additional fields each. Write assertions that correctly validate each event type's specific fields using filter-by-discriminator, and one assertion confirming every event (regardless of type) has a non-null timestamp.

Summary

Real API responses often aren't uniformly shaped — fields can be optional or null, and collections can contain genuinely different object shapes distinguished by a type discriminator. The consistent strategy across all these cases: check presence and type explicitly rather than assuming uniformity, and filter by a discriminator field before asserting on shape-specific fields in a polymorphic collection.

Interview Questions

A response has an array of "events" where some elements have an orderId field and others don't. Asserting events[2].orderId sometimes throws a null-related error. What's actually happening, and how should the test be restructured?▾
The array is polymorphic — different event types carry different fields, and event at index 2 happens to be a type that doesn't include orderId at all. Asserting by fixed position assumes every element shares the same shape, which isn't true here. The fix is to filter the collection by its type discriminator field first (events.findAll { it.type == 'order_created' }), then assert on the type-specific field within that filtered, shape-consistent subset — rather than assuming any arbitrary position in the array has a predictable shape.
