Basic & Bearer Authentication

Beginner 6 min read

Prerequisites: Authentication & Authorization overview

What is this?

These are the two simplest authentication mechanisms you'll encounter — Basic Auth sends a username/password pair on every request; Bearer tokens send a single opaque credential obtained once, typically via a login step, and reused across subsequent requests.

Basic Authentication

given()
    .auth()
    .basic("username", "password")
.when()
    .get("/profile")
.then()
    .statusCode(200);

Under the hood, this base64-encodes "username:password" and sends it in an Authorization: Basic ... header — RestAssured's .auth().basic() helper handles that encoding for you, so you never need to do it manually. Basic Auth is less common in modern public APIs (it sends credentials on literally every request, which is less flexible than token-based approaches), but you'll still encounter it in internal tools, legacy systems, and some infrastructure APIs.

Bearer Token Authentication

given()
    .header("Authorization", "Bearer " + token)
.when()
    .get("/profile")
.then()
    .statusCode(200);

This is by far the most common authentication style for modern REST APIs. Unlike Basic Auth, there's no dedicated .auth().bearer() shorthand in older RestAssured versions (newer versions do provide one) — most real codebases set it as a plain header, which also makes the pattern trivially reusable across any future token type (JWT, OAuth access token) since they're all just "a Bearer token" from the request's perspective.

Basic Example — Obtaining a Bearer Token First

@Test
void bearerTokenObtainedViaLoginThenReused() {
    String token =
        given()
            .contentType(ContentType.JSON)
            .body(Map.of("email", "user@example.com", "password", "secret"))
        .when()
            .post("/login")
        .then()
            .statusCode(200)
        .extract()
            .path("token");

    given()
        .header("Authorization", "Bearer " + token)
    .when()
        .get("/profile")
    .then()
        .statusCode(200);
}

This is the fundamental shape of Bearer token testing: a login request extracts the token (the validate-then-extract pattern from Chapter 4), and every subsequent request attaches it as a header. Doing this in every single test is wasteful, though — the Authentication Reuse page later in this chapter shows how to avoid repeating the login step per test.

Detailed Example — Testing an Invalid Basic Auth Credential

@Test
void wrongPasswordReturns401() {
    given()
        .auth()
        .basic("username", "definitely-wrong-password")
    .when()
        .get("/profile")
    .then()
        .statusCode(401);
}

Testing the failure path is just as important here as for any other authentication mechanism — confirming the API correctly rejects bad credentials, rather than only ever testing the successful login case.

Real-World Example — Testing a Missing Authorization Header Entirely

@Test
void noAuthorizationHeaderReturns401() {
    given()
    .when()
        .get("/profile") // no Authorization header at all
    .then()
        .statusCode(401);
}

This is a distinct scenario from an invalid token — a completely missing header — and both are worth testing separately, since some APIs handle them with subtly different code paths (and occasionally, subtly different bugs).

❌ Fragile vs. ✅ Recommended

// ❌ Hardcoding real (or even test) credentials directly in test code
given().auth().basic("admin", "SuperSecret123!").when().get("/profile");

// ✅ Reading credentials from environment variables
given().auth().basic(System.getenv("TEST_USERNAME"), System.getenv("TEST_PASSWORD"))
    .when().get("/profile");

Common Mistakes

  • Hardcoding credentials directly in test source code, even for a test-only account — read them from environment variables or a secrets manager instead, consistent with the environment strategy from Chapter 10.
  • Only testing successful authentication, never a wrong password, a missing header, or an expired/invalid token.
  • Manually base64-encoding credentials instead of using RestAssured's .auth().basic() helper — unnecessary and more error-prone.

Edge Cases

  • Basic Auth with special characters in the password — RestAssured's helper handles encoding correctly; a manually-constructed header risks getting this wrong.
  • A Bearer token that's technically well-formed but for the wrong environment (a QA token used against staging) — worth testing that the API correctly rejects tokens issued elsewhere, if that's a real security boundary your API is supposed to enforce.

Debugging

If an authenticated request unexpectedly returns 401, log the request headers with .log().headers() to confirm the Authorization header is actually present and correctly formatted (the right scheme — Basic vs. Bearer — with no accidental leading/trailing whitespace in the token).

Best Practices

  • Never hardcode credentials — always read them from environment variables or a secrets manager.
  • Test both the missing-header and invalid-credential failure paths, not just successful authentication.
  • Use RestAssured's built-in .auth() helpers where they exist rather than manually constructing headers.

Practice Exercise

Write three tests against a Bearer-token-protected endpoint: one with a valid token (200), one with no Authorization header at all (401), and one with a syntactically plausible but invalid token (401) — confirming the API handles all three distinctly and correctly.

Summary

Basic Auth sends a username/password pair on every request via RestAssured's .auth().basic() helper; Bearer tokens are obtained once (typically via login) and attached as a plain Authorization header on every subsequent request. Both need their failure paths tested explicitly, not just the successful case, and credentials should never be hardcoded in test source.

Interview Questions

Why is Bearer token authentication generally preferred over Basic Auth for modern APIs?▾
Basic Auth sends the actual username and password on every single request, which means the raw credential is repeatedly exposed and there's no way to limit its scope or revoke it independently without changing the password itself. A Bearer token is obtained once through a separate authentication step and can be scoped, time-limited, and revoked independently of the user's actual password — meaning a compromised token doesn't compromise the underlying credential, and access can be granted or revoked without the user needing to change anything.
