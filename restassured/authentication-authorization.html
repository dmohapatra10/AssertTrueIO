Authentication & Authorization

Beginner 4 min read

Prerequisites: JSON, Serialization & Deserialization

Proving Who You Are, and What You're Allowed to Do

Almost no real-world API is fully open — nearly everything you test in a real job sits behind some form of authentication. Here's every mechanism you're likely to encounter, across six pages:

  1. Basic & Bearer Authentication — the two simplest, most common mechanisms
  2. API Key Authentication — header-based and query-parameter-based approaches
  3. OAuth 2.0 Authentication — access tokens, refresh tokens, client credentials
  4. JWT Authentication — structure, validation, and what's actually inside a token
  5. Authentication Reuse & Token Management — avoiding a fresh login on every single test
  6. Role-Based API Testing — testing what different user roles can and can't do

Authentication vs. Authorization — A Reminder

An earlier page introduced this distinction conceptually: authentication answers "who are you?"; authorization answers "what are you allowed to do?" The first four pages here are almost entirely about authentication — proving identity, in various mechanisms. The sixth page, Role-Based API Testing, is where authorization becomes the real focus — testing that an authenticated-but-insufficiently-privileged user correctly gets blocked.

Why Authentication Testing Is Its Own Skill

It's tempting to treat authentication as a one-time setup detail — log in once, get a token, move on to "the real testing." In practice, authentication logic is itself a frequent source of real bugs: tokens that don't expire when they should, permission checks that are inconsistent across endpoints, refresh flows that silently fail. Treating authentication as worth testing in its own right, not just a precondition to get past, is what the pages ahead are really about.

A Quick Preview — The Same Protected Endpoint, Four Ways

// Basic Auth
given().auth().basic("username", "password").when().get("/profile");

// Bearer Token
given().header("Authorization", "Bearer " + token).when().get("/profile");

// API Key
given().header("X-API-Key", apiKey).when().get("/profile");

// OAuth 2.0 (conceptually — the token itself is still sent as a Bearer token)
given().auth().oauth2(accessToken).when().get("/profile");

Notice how similar these look in code — most of the real complexity in authentication testing isn't in the RestAssured syntax itself (which is often a single line), it's in correctly obtaining the credential in the first place, and reusing it efficiently across a whole test suite. That's where this chapter spends most of its depth.

Common Mistakes to Watch For

  • Logging in fresh for every single test instead of reusing a token — covered fully on the Token Management page, and one of the most impactful performance fixes available to a slow test suite.
  • Only testing the authenticated-success path, never a missing/invalid/expired token, or a valid-but-insufficiently-privileged user.
  • Hardcoding real credentials directly in test code instead of reading them from environment variables or a secrets manager — never acceptable, even for a test environment.

What You'll Be Able to Do

By the end of the six pages that follow, you should be able to implement and test any of the four major authentication mechanisms, build a reusable token manager so your suite isn't re-authenticating on every test, and design tests that verify not just "can this user log in" but "does this user have exactly the permissions they should, and not more." Start with Basic & Bearer Authentication below.

Interview Questions

What's the practical difference between authentication and authorization in test terms?▾
Authentication tests answer 'who are you' — missing/invalid/expired credentials; authorization tests answer 'what are you allowed to do' — a genuinely valid identity attempting something outside its permissions, which is a 403, not a 401.
Why treat authentication as worth testing in its own right, not just a precondition to get past?▾
Authentication logic itself is a frequent source of real bugs — tokens that don't expire correctly, inconsistent permission checks, silently broken refresh flows — all invisible if auth is only ever treated as setup boilerplate.
What do Basic, Bearer, API Key, and OAuth all reduce to once a credential is actually obtained?▾
In code, most look nearly identical — typically a single header. The real complexity in authentication testing is in correctly OBTAINING and reusing the credential efficiently, not in the syntax of attaching it to a request.
Why never hardcode credentials, even for a dedicated test-only account?▾
Hardcoded credentials in source code are a real exposure risk regardless of whether the account is 'just for testing' — reading from environment variables or a secrets manager is the only acceptable pattern.
Why is authentication described as a discipline worth testing in its own right, not just a precondition?▾
Authentication logic is itself a frequent source of real bugs — tokens that don't expire correctly, inconsistent permission checks — treating it as mere setup boilerplate means those bugs go untested.
