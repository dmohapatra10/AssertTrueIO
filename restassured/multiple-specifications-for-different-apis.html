Multiple Specifications for Different APIs

Beginner 5 min read

Prerequisites: ResponseSpecification Deep Dive

What is this?

Real projects often need more than one specification — a different base API to test against, different authenticated roles, or an unauthenticated spec for the login request itself. This page is about managing several specs cleanly, without duplicating the logic that builds each one.

Why One Spec Usually Isn't Enough

A single hardcoded RequestSpecification works fine for a project testing one API with one role. Real projects are rarely that simple — a microservices architecture might mean testing several genuinely different base APIs; role-based testing (Chapter 6) needs a differently-authenticated spec per role; and the very first request in most test suites (logging in) can't use an authenticated spec at all, since there's no token yet.

Basic Example — Separate Specs for Different Services

RequestSpecification usersServiceSpec =
    new RequestSpecBuilder()
        .setBaseUri(System.getenv("USERS_SERVICE_URL"))
        .setContentType(ContentType.JSON)
        .build();

RequestSpecification ordersServiceSpec =
    new RequestSpecBuilder()
        .setBaseUri(System.getenv("ORDERS_SERVICE_URL"))
        .setContentType(ContentType.JSON)
        .build();

given().spec(usersServiceSpec).when().get("/users/42").then().statusCode(200);
given().spec(ordersServiceSpec).when().get("/orders/500").then().statusCode(200);

In a microservices architecture, different services often live at genuinely different base URLs — a shared spec per service, rather than one spec trying to serve every service, keeps each one correctly scoped to its own base URI.

Detailed Example — Unauthenticated vs. Authenticated Specs

RequestSpecification unauthenticatedSpec =
    new RequestSpecBuilder()
        .setBaseUri(System.getenv("API_BASE_URL"))
        .setContentType(ContentType.JSON)
        .build();

// The login request itself CANNOT use an authenticated spec — there's no token yet
String token = given().spec(unauthenticatedSpec).body(credentials).when().post("/login")
    .then().statusCode(200).extract().path("token");

RequestSpecification authenticatedSpec =
    new RequestSpecBuilder()
        .setBaseUri(System.getenv("API_BASE_URL"))
        .setContentType(ContentType.JSON)
        .addHeader("Authorization", "Bearer " + token)
        .build();

given().spec(authenticatedSpec).when().get("/profile").then().statusCode(200);

This is a genuine, common chicken-and-egg problem: you need a spec to make the login request, but the login request is exactly what produces the token the authenticated spec needs. The resolution is always the same shape — a minimal unauthenticated spec for the login step itself, and a separate, richer authenticated spec built afterward using the result.

Real-World Example — Role-Scoped Specs Built via a Factory Method

public class SpecFactory {
    public static RequestSpecification forRole(String role) {
        return new RequestSpecBuilder()
            .setBaseUri(System.getenv("API_BASE_URL"))
            .setContentType(ContentType.JSON)
            .addHeader("Authorization", "Bearer " + TokenManager.getTokenForRole(role))
            .build();
    }
}

// Usage:
given().spec(SpecFactory.forRole("admin")).when().get("/admin/users").then().statusCode(200);
given().spec(SpecFactory.forRole("user")).when().get("/admin/users").then().statusCode(403);

Rather than manually building and storing a separate static spec for every possible role, a small factory method builds one on demand for whichever role a specific test needs — combining directly with the per-role token caching from Chapter 6, and scaling cleanly to however many roles the project actually has without needing a hardcoded static field for each one.

❌ Fragile vs. ✅ Recommended

// ❌ One spec, manually mutated per test to switch roles —
// error-prone, and easy to accidentally leave in the wrong state for a later test
RequestSpecification sharedSpec = buildBaseSpec();
sharedSpec = sharedSpec.header("Authorization", "Bearer " + adminToken); // mutating shared state

// ✅ A factory producing a fresh, correctly-scoped spec per call, no shared mutable state
given().spec(SpecFactory.forRole("admin")).when().get("/admin/users");

Common Mistakes

  • Trying to force one spec to serve multiple genuinely different APIs or roles by mutating it between tests — risks state leaking between tests that shouldn't share it.
  • Forgetting the login request itself needs an unauthenticated spec — a common chicken-and-egg oversight when first introducing specs to an existing suite.
  • Hardcoding a static spec per role instead of a factory method, when the actual number of roles is large or grows over time.

Edge Cases

  • A project testing genuinely unrelated third-party APIs alongside its own — each deserves its own completely separate spec, with no attempt to share configuration that doesn't actually overlap.
  • Specs that need per-test customization beyond just role (a specific locale header, a feature flag) — a factory method can accept additional parameters beyond just role to accommodate this.

Debugging

If a test seems to be using the wrong base URI or authentication, confirm which specific spec object it's actually referencing — in a project with several specs, it's easy to accidentally apply the wrong one, especially after a refactor.

Best Practices

  • Give each genuinely distinct API or service its own spec, rather than forcing one spec to serve multiple bases.
  • Use a minimal unauthenticated spec specifically for the login step, separate from the authenticated spec built afterward.
  • Use a factory method for role-scoped (or otherwise parameterized) specs rather than a hardcoded static field per variant.
  • Avoid mutating a shared spec object between tests — build fresh, correctly-scoped instances instead.

Practice Exercise

Build a SpecFactory with a method that returns a role-scoped, authenticated RequestSpecification, and a separate method that returns a minimal unauthenticated spec for login. Use both across a small test scenario: log in via the unauthenticated spec, then use the resulting token with a role-scoped spec for a follow-up request.

Summary

Real projects often need more than one specification — separate specs per service in a microservices architecture, an unauthenticated spec for the login step itself, and role-scoped specs (often built via a factory method) for role-based testing. The unifying principle: give each genuinely distinct concern its own spec rather than forcing one spec to awkwardly serve everything, and avoid mutating shared spec state between tests.

Interview Questions

Why can't a single authenticated RequestSpecification be used for the login request itself?▾
An authenticated spec includes an Authorization header built from a token — but the login request is exactly what produces that token in the first place. There's no token yet at the point the login request needs to be made, so it has to use a separate, minimal spec (typically just base URI and content type, no auth header) — only after the login succeeds and a token is extracted can an authenticated spec be built and used for every subsequent request.
Why might a project testing a microservices architecture need multiple RequestSpecifications?▾
Different services often live at genuinely different base URLs; a shared spec per service, rather than one spec forced to serve all of them, keeps each one correctly scoped to its own base URI.
What's the chicken-and-egg problem multiple specs need to resolve for authentication?▾
You need a spec to make the login request, but the authenticated spec needs the login's own result (the token) — resolved with a minimal unauthenticated spec for login itself, and a richer authenticated spec built afterward.
Why use a factory method for role-scoped specs rather than a hardcoded static field per role?▾
A factory method scales cleanly to however many roles a project actually has, building a correctly-scoped spec on demand, rather than requiring a manually maintained static field for every possible role.
Why avoid mutating a shared spec object between tests to switch roles?▾
It risks state leaking between tests that shouldn't share it — a factory producing a fresh, correctly-scoped instance per call avoids this shared-mutable-state risk entirely.
