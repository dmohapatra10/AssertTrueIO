Custom Logging & Filters

Beginner 8 min read

Prerequisites: Conditional Logging

What is this?

RestAssured.filters(new RequestLoggingFilter(), new ResponseLoggingFilter());

// Now EVERY request/response in the project logs automatically —
// no need to add .log() calls to individual tests at all
given().when().get("/users/2").then().statusCode(200);

Everything covered so far has been per-test — adding .log() to individual chains. A Filter is RestAssured's mechanism for applying logic to every request/response in the project automatically, configured once globally rather than repeated per test.

Why it's important

Repeating .log().ifValidationFails() in every single test, while better than nothing, is still a small piece of boilerplate multiplied across a large suite. A globally configured filter applies the same behavior everywhere at once — and, more importantly, opens the door to real logging frameworks instead of raw console output, which matters once test output needs to integrate with CI log aggregation, structured logging, or a team's existing logging conventions.

Built-In Filters

RestAssured.filters(
    new RequestLoggingFilter(),
    new ResponseLoggingFilter()
);

These two built-in filters log every request and every response for every test in the project, unconditionally — genuinely useful during initial framework setup or focused debugging sessions, but exactly as noisy in CI as .log().all() would be per-test, just applied globally instead. For most real projects, a custom filter with conditional logic (shown next) is the more practical long-term choice.

Writing a Custom Filter

public class ConditionalLoggingFilter implements Filter {
    @Override
    public Response filter(FilterableRequestSpecification requestSpec,
                            FilterableResponseSpecification responseSpec,
                            FilterContext ctx) {
        Response response = ctx.next(requestSpec, responseSpec);

        if (response.getStatusCode() >= 400) {
            System.out.println("FAILED REQUEST: " + requestSpec.getMethod() + " " + requestSpec.getURI());
            System.out.println("RESPONSE: " + response.getBody().asPrettyString());
        }

        return response;
    }
}

// Register it once, globally:
RestAssured.filters(new ConditionalLoggingFilter());

A custom Filter intercepts every request/response pair, letting you apply exactly the logic you want — here, logging only when the status code indicates a real problem, applied automatically across the whole project with zero per-test .log() calls needed at all.

Integrating with SLF4J/Logback Instead of System.out

public class Slf4jLoggingFilter implements Filter {
    private static final Logger logger = LoggerFactory.getLogger(Slf4jLoggingFilter.class);

    @Override
    public Response filter(FilterableRequestSpecification requestSpec,
                            FilterableResponseSpecification responseSpec,
                            FilterContext ctx) {
        Response response = ctx.next(requestSpec, responseSpec);

        if (response.getStatusCode() >= 400) {
            logger.warn("API call failed: {} {} -> {}",
                requestSpec.getMethod(), requestSpec.getURI(), response.getStatusCode());
        } else {
            logger.debug("API call succeeded: {} {} -> {}",
                requestSpec.getMethod(), requestSpec.getURI(), response.getStatusCode());
        }

        return response;
    }
}

Raw System.out.println() output — everything shown on the earlier three pages — works fine for local debugging but doesn't integrate with a real project's logging infrastructure: log levels, structured output, log aggregation in CI, correlation with the rest of the application's logs. Routing RestAssured's logging through SLF4J (the standard Java logging facade) instead means API test logs behave exactly like every other log statement in the project — respecting configured log levels, formats, and destinations.

Real-World Example — A Production-Style Logging Filter

public class ApiTestLoggingFilter implements Filter {
    private static final Logger logger = LoggerFactory.getLogger("api-tests");

    @Override
    public Response filter(FilterableRequestSpecification req,
                            FilterableResponseSpecification res,
                            FilterContext ctx) {
        long start = System.currentTimeMillis();
        Response response = ctx.next(req, res);
        long durationMs = System.currentTimeMillis() - start;

        String outcome = response.getStatusCode() < 400 ? "OK" : "FAILED";
        logger.info("[{}] {} {} -> {} ({}ms)",
            outcome, req.getMethod(), req.getURI(), response.getStatusCode(), durationMs);

        if (response.getStatusCode() >= 400) {
            logger.debug("Failure body: {}", response.getBody().asPrettyString());
        }

        return response;
    }
}

// Registered once, in a shared base test class's @BeforeAll:
RestAssured.filters(new ApiTestLoggingFilter());

This single filter now gives every test in the project a consistent one-line summary log (method, URL, outcome, timing) for every API call, with full response detail only for actual failures — a genuinely useful, CI-friendly logging strategy applied automatically, without any individual test needing to think about logging at all.

❌ Fragile vs. ✅ Recommended

// ❌ Repeating .log().ifValidationFails() in every single test file,
// with no consistent, project-wide logging strategy beyond that
.then().log().ifValidationFails().statusCode(200);
// ...repeated identically across hundreds of test methods

// ✅ One filter, registered once, applied automatically everywhere
RestAssured.filters(new ApiTestLoggingFilter());
// every test in the project now gets consistent logging with zero repetition

Common Mistakes

  • Using the unconditional built-in RequestLoggingFilter/ResponseLoggingFilter in CI without realizing they log absolutely everything, unconditionally — just as noisy as .log().all() per test, applied project-wide.
  • Sticking with raw System.out.println() output once a project has real logging infrastructure already in place — misses the chance to integrate cleanly with existing log levels and aggregation.
  • Writing a custom filter with expensive logic (heavy string formatting, external calls) that runs on every single request regardless of outcome — filters run for every test, so their overhead compounds across a large suite.

Edge Cases

  • Multiple filters registered at once — they run in registration order, each able to inspect (and even short-circuit) the request/response chain; be deliberate about ordering if you have more than one.
  • Filters and per-test .log() calls combined — both can coexist, but consider whether a per-test .log() call is still necessary once a project-wide filter already covers the same need.

Debugging

If a custom filter doesn't seem to be firing, confirm it's actually registered via RestAssured.filters(...) before any test runs — typically in a shared @BeforeAll, not scattered inconsistently across individual test classes.

Best Practices

  • Prefer a custom, conditional filter over the unconditional built-in ones for anything beyond initial setup or focused debugging.
  • Route logging through a real framework (SLF4J/Logback) once a project has existing logging infrastructure to integrate with.
  • Register filters once, globally, in a shared base test class — not per individual test file.
  • Keep filter logic lightweight, since it runs on every single request across the whole suite.

Practice Exercise

Write a custom Filter that logs a one-line summary (method, URL, status code) for every request via SLF4J at INFO level, and additionally logs the full response body at DEBUG level specifically when the status code is 500 or higher. Register it globally and confirm it fires correctly across several different tests without any per-test logging code.

Summary

RestAssured's Filter interface applies logging (or any other cross-cutting logic) to every request in a project automatically, registered once rather than repeated per test. Custom filters with conditional logic, routed through a real logging framework like SLF4J rather than raw console output, are what a mature production test framework actually uses — the natural endpoint of everything this chapter has built toward.

Interview Questions

Why would a real production test framework prefer a custom Filter with SLF4J logging over scattering .log().ifValidationFails() calls across every individual test?▾
A per-test .log() call is boilerplate repeated across every test file, easy to forget in a new test and inconsistent if different authors make different choices. A global filter applies identical, consistent logging behavior across the entire project automatically, with zero repetition. Routing that logging through SLF4J instead of raw console output additionally means test logs integrate properly with the project's actual logging infrastructure — respecting configured log levels, formats, and destinations — rather than producing raw console text that doesn't fit into a team's broader logging and monitoring setup.
What does RestAssured's Filter interface let you do that per-test .log() calls can't?▾
Apply logic to EVERY request/response in a project automatically, configured once globally rather than repeated per test — the project-wide equivalent of what conditional logging does per-test.
Why might a mature project route logging through SLF4J instead of raw System.out?▾

What's the risk of the built-in RequestLoggingFilter/ResponseLoggingFilter in CI?▾

Why should custom filter logic stay lightweight?▾
