Getting Started with Java & RestAssured

Beginner 13 min read

Prerequisites: API & REST Fundamentals

What is this chapter for?

This chapter covers exactly the Java and tooling knowledge you need to run your first RestAssured test — not a general Java course. If you already write Java for a living, skim the project-setup sections and slow down at "The given/when/then structure," since that mental model is the one thing every later chapter assumes you have solid.

Java Prerequisites

You need working knowledge of: classes and objects, methods, basic collections (List, Map), and how to read a stack trace. You do not need to be an expert in Java's more advanced features yet — streams, generics, and records get introduced later in this course, in the specific contexts where API automation actually uses them (mostly around test data builders and POJOs).

Maven vs. Gradle

Both are build tools that manage your project's dependencies (like RestAssured itself) and run your tests. Maven uses XML (pom.xml) and is still the more common choice in enterprise API automation projects, largely due to familiarity and a huge ecosystem of existing examples. Gradle uses a more concise Groovy or Kotlin DSL and tends to build faster on large projects. This course uses Maven for its examples, since it's what you'll most often inherit in a real job — but everything RestAssured-specific transfers directly to a Gradle project with only the dependency-declaration syntax changing.

Project Structure

restassured-project/
├── src/
│   ├── main/java/        # framework code you'll build in later chapters
│   └── test/java/        # your actual test classes live here
├── pom.xml                # Maven's dependency and build configuration
└── target/                 # compiled output and test reports (generated, not committed)

For now, everything lives directly under src/test/java — the split into main vs. test, and the deeper folder structure (clients, models, specs, utils), only starts to matter once you reach the Framework Architecture chapter. Don't over-organize a two-test project; let structure grow as genuine need arises.

Adding the RestAssured Dependency

<dependency>
    <groupId>io.rest-assured</groupId>
    <artifactId>rest-assured</artifactId>
    <version>5.5.0</version>
    <scope>test</scope>
</dependency>

Always check Maven Central for the current version rather than trusting a hardcoded number in any tutorial, including this one — RestAssured releases regularly, and a tutorial's pinned version can quietly go stale. The <scope>test</scope> matters: it tells Maven this dependency is only needed for running tests, not for your application's actual production code (which, for a pure test project, doesn't really apply — but it's the correct convention regardless).

JUnit 5 vs. TestNG

RestAssured itself doesn't care which test framework runs it — given().when().get(...) works identically either way. The choice is about how you want to organize, group, and run your tests:

JUnit 5TestNG
PopularityMore common overall, especially newer projectsCommon in larger enterprise QA teams
Parameterized testsBuilt-in, flexible (@ParameterizedTest)Built-in (@DataProvider), long-established
Parallel executionSupported, configuration-basedNative, very mature — a big reason some teams still prefer it
Grouping testsTagsGroups (often considered more flexible)

Recommended for this course: JUnit 5. It's the more actively developed of the two, has excellent parameterized-test support (genuinely useful for the data-driven testing you'll do in the Test Data Management chapter), and is what most new Java projects default to today. If your actual workplace uses TestNG, everything here transfers with only the annotation names changing (@Test, @BeforeEach/@BeforeMethod, etc.) — the RestAssured code itself is identical either way.

Your First RestAssured Test

import io.restassured.RestAssured;
import org.junit.jupiter.api.Test;
import static io.restassured.RestAssured.given;
import static org.hamcrest.Matchers.equalTo;

public class FirstApiTest {

    @Test
    void getSingleUserReturns200() {
        given()
            .baseUri("https://reqres.in/api")
        .when()
            .get("/users/2")
        .then()
            .statusCode(200)
            .body("data.id", equalTo(2));
    }
}

Run it exactly like any other JUnit test — from your IDE, or via mvn test from the terminal. If it passes, you've just made a real HTTP GET request, received a real response, and validated both its status code and a value inside its JSON body — the entire request/response cycle from Chapter 1, expressed in code.

The given() / when() / then() Structure, Deeply Explained

given()
   ↓
when()
   ↓
then()

This isn't arbitrary syntax — it's a deliberate readability pattern (RestAssured calls it BDD-style) that mirrors how you'd naturally describe an API test out loud: "given this setup, when I do this action, then I expect this result."

  • given() — everything about the request's preconditions: base URI, headers, query/path parameters, request body, authentication. Nothing here has been sent yet; you're just building the request.
  • when() — the actual action: which HTTP method, against which endpoint. This is the moment the request is genuinely sent over the network.
  • then() — validation of what came back: status code, headers, body content. This section runs against the real response your request just received.

Keeping these three concerns visually separated is what makes RestAssured tests readable months later without re-deriving what each line does — a real advantage over hand-rolling raw HTTP calls with a generic Java HTTP client, where setup, action, and validation all blur together in ordinary imperative code.

Static Imports

import static io.restassured.RestAssured.given;
import static org.hamcrest.Matchers.equalTo;

given() is a static method on the RestAssured class — without the static import, you'd have to write RestAssured.given() on every single test, which adds noise without adding clarity. The convention across essentially every RestAssured codebase you'll encounter is to statically import given (and the Hamcrest matchers like equalTo, hasItem, greaterThan you'll use in assertions) so the test body reads as cleanly as possible.

RequestSpecification, Response, and ValidatableResponse

Three types quietly flow through every test you write, even when you never name them explicitly:

  • RequestSpecification — what given() returns. It represents the request you're building, before it's sent. Every method you chain after given() — .header(), .queryParam(), .body() — returns this same type, which is why you can keep chaining them.
  • Response — what you get back after when().get(...) actually fires the request. It holds the raw status code, headers, and body, and you can extract data from it directly without ever calling .then() at all.
  • ValidatableResponse — what .then() returns, wrapping the same response specifically for fluent assertion-chaining (.statusCode(200).body(...)).
// You don't have to use .then() at all — this is equally valid,
// and useful when you want to inspect a Response object directly
Response response = given().when().get("/users/2");
System.out.println(response.getStatusCode());
System.out.println(response.getBody().asString());

Understanding that .then() isn't mandatory — it's just RestAssured's fluent path for assertions — makes the difference between validating a response and extracting data from one much clearer, a distinction the next chapter goes much deeper on.

RestAssured Base Configuration

@BeforeAll
static void setup() {
    RestAssured.baseURI = "https://reqres.in";
    RestAssured.basePath = "/api";
}

Repeating .baseUri("https://reqres.in/api") in every single test is exactly the kind of duplication that makes a suite painful to maintain — if the base URL ever changes, you'd need to update it everywhere. Setting RestAssured.baseURI once (commonly in a @BeforeAll, or in a shared base test class) means every test's given() automatically starts from that base, and only needs to specify the path that's actually unique to it: .get("/users/2") instead of the full URL. This is the seed of the RequestSpecification reuse pattern the Specifications chapter builds on properly.

Real-World Example — A Minimal Base Test Class

public abstract class BaseApiTest {

    @BeforeAll
    static void configureBaseUri() {
        RestAssured.baseURI = System.getProperty("api.baseUrl", "https://reqres.in");
    }
}

public class UserApiTest extends BaseApiTest {

    @Test
    void getUserReturnsExpectedName() {
        given()
            .pathParam("id", 2)
        .when()
            .get("/api/users/{id}")
        .then()
            .statusCode(200)
            .body("data.first_name", equalTo("Janet"));
    }
}

Reading the base URL from a system property (with a sensible default) rather than hardcoding it is a small habit worth building immediately — it's the first thread connecting this chapter to the multi-environment strategy (local, QA, staging) covered fully once you reach Framework Architecture.

❌ Fragile vs. ✅ Recommended

// ❌ Full URL repeated and hardcoded in every single test
given().when().get("https://reqres.in/api/users/2").then().statusCode(200);

// ✅ Base URI configured once; each test only specifies what's unique to it
given().when().get("/users/2").then().statusCode(200);

Common Mistakes

  • Hardcoding the full URL in every test instead of configuring RestAssured.baseURI once — painful the moment the base URL needs to change for a new environment.
  • Skipping the static import for given(), leading to verbose RestAssured.given() scattered throughout, which most real codebases avoid by convention.
  • Not knowing .then() is optional — some engineers assume every request must end in a .then() chain, and don't realize a plain Response object is often the more natural tool when you're extracting data rather than asserting.
  • Choosing a test framework based on unfamiliarity avoidance rather than what the team already standardizes on — consistency across a codebase matters more than which framework is "better" in the abstract.

Edge Cases

  • Multiple base URLs in one project (calling two different microservices) — don't force a single global RestAssured.baseURI; use separate RequestSpecification objects instead, covered in Chapter 8.
  • Running the same test suite against different environments — reading the base URL from a system property or environment variable (as shown above) rather than a hardcoded default is what makes this possible without editing test code per environment.

Debugging

If a test fails with a connection error before you even get to an assertion, check RestAssured.baseURI first — a typo'd or unset base URI is one of the most common "why is this failing" moments for a brand-new project, and the resulting stack trace (a connection failure) doesn't always make the actual cause obvious at a glance.

Best Practices

  • Configure RestAssured.baseURI once, in a shared base class or a @BeforeAll, never per-test.
  • Statically import given and your Hamcrest matchers — it's the near-universal convention for a reason.
  • Pick JUnit 5 unless your team already has a strong, established TestNG codebase — don't introduce a second test framework into an existing project without a good reason.
  • Read environment-specific values (base URL, credentials) from system properties or environment variables from day one, even in a two-test project — retrofitting this later means touching every test.

Practice Exercise

Set up a fresh Maven project with the RestAssured and JUnit 5 dependencies, configure a shared base URI against https://reqres.in in a @BeforeAll, and write two tests: one asserting a successful GET on an existing user, and one asserting a 404 on a user ID that doesn't exist.

Summary

A RestAssured project needs just three real ingredients: a build tool (Maven or Gradle) to manage the dependency, a test framework (JUnit 5 recommended) to run and organize tests, and the RestAssured dependency itself. The given()/when()/then() structure isn't decoration — it's a readability convention separating request setup, the actual call, and response validation into three clear, scannable sections, and understanding that Response and ValidatableResponse are two different tools for two different jobs (extracting vs. asserting) sets up the next chapter cleanly.

Interview Questions

Why is JUnit 5 recommended over TestNG for this course specifically?▾
It's more actively developed, has strong parameterized-test support genuinely useful for data-driven testing, and is what most new Java projects default to today — though the RestAssured code itself is identical regardless of which framework runs it.
What's the actual difference between what given() and .then() return?▾
given() returns a RequestSpecification representing the request being built; .then() returns a ValidatableResponse specifically for fluent assertion chaining — two different types serving two different phases of the same request.
Why configure RestAssured.baseURI once instead of repeating it in every test?▾
Repeating it means updating dozens or hundreds of near-identical lines if the base URL ever changes; configuring it once (typically in a shared base class) means every test's given() automatically starts from that base.
What problem does the static import of given() actually solve?▾
Without it, every test would need the verbose RestAssured.given() — the static import is purely a readability convention nearly every real RestAssured codebase follows.
What's the actual purpose of the given/when/then structure beyond just syntax?▾
It's a deliberate readability convention separating a request's preconditions, the action that sends it, and validation of what came back — keeping these three concerns visually distinct is what makes a test readable months later without re-deriving what each line does.
