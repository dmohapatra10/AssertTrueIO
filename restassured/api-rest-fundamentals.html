API & REST Fundamentals

Beginner 13 min read

Prerequisites: None — this is where the RestAssured track begins.

Why start here, before any RestAssured syntax?

It's tempting to jump straight to given().when().get(...) — it looks simple, and you can copy-paste your way to a passing test within minutes. But every RestAssured method you'll ever call is just a Java-shaped wrapper around an actual HTTP request. If you don't understand what's really happening on the wire — what a status code means, why a header exists, what separates a path parameter from a query parameter — you'll be able to write tests that pass, but you won't be able to explain why one fails, or design a new test for a scenario nobody showed you first. This chapter builds that foundation before RestAssured enters the picture at all.

What is an API?

An API (Application Programming Interface) is a defined contract that lets one piece of software ask another piece of software to do something, without needing to know how that something is implemented internally. When a mobile banking app shows your balance, it isn't reading your bank's database directly — it's calling an API that the bank exposes specifically for that purpose, and the bank's actual database, business logic, and infrastructure stay hidden behind that contract.

This hiding is the whole point: the bank can completely rewrite its internal systems, and as long as the API contract stays the same, every app built against it keeps working unchanged. As an API automation engineer, you're specifically testing that contract — not the internal implementation behind it.

What is a REST API?

REST (Representational State Transfer) is an architectural style for designing APIs — a set of conventions, not a rigid protocol or a specific technology. A REST API represents things (users, orders, accounts) as resources, each identified by a URL, and lets clients act on those resources using standard HTTP methods. /users/42 represents a specific user; what you do to that user — read them, update them, delete them — is expressed by which HTTP method you use, not by a different URL for each action.

REST principles, briefly

  • Client-server separation — the client (your test, a mobile app, a browser) and the server are independent; either can change without breaking the other, as long as the contract holds.
  • Statelessness — each request contains everything the server needs to process it; the server doesn't remember your previous request. This is precisely why authentication tokens get sent on every request rather than being "remembered" server-side between calls — a detail that becomes very relevant once you start writing tests.
  • Resource-based URLs — URLs identify things (/orders/1024), not actions (/getOrderById?id=1024 is a common but less RESTful pattern you'll still encounter in real projects).
  • Uniform interface — the same small set of HTTP methods (GET, POST, PUT, PATCH, DELETE) is reused consistently across every resource, instead of each API inventing its own verbs.

Client-Server Architecture and the Full Request/Response Cycle

Every single API interaction you'll ever test follows this same shape:

Client
   ↓
HTTP Request
   ↓
API Server
   ↓
Business Logic
   ↓
Database / External Services
   ↓
HTTP Response
   ↓
Client

Your RestAssured test is the client in this diagram. It sends an HTTP Request, the server runs its business logic (validating input, checking permissions, maybe calling a database or another service), and sends back an HTTP Response. Everything you'll test in this entire course — every assertion you'll ever write — is really just examining one of two things: did the right Request get constructed, and does the resulting Response reflect what the business logic should have done. Keep this shape in your head; it's the mental model this whole course keeps returning to.

HTTP and HTTPS

HTTP (HyperText Transfer Protocol) is the protocol nearly all web APIs communicate over — a plain-text request/response format that both browsers and API clients like RestAssured speak natively. HTTPS is the same protocol wrapped in TLS encryption, so the request and response can't be read or tampered with in transit. Every production API you'll test uses HTTPS; you'll mostly encounter plain HTTP only against local development servers.

HTTP Methods

These five methods cover the overwhelming majority of what you'll automate:

MethodPurposeHas a body?Idempotent?
GETRetrieve a resourceNoYes
POSTCreate a new resourceYesNo
PUTReplace a resource entirelyYesYes
PATCHPartially update a resourceYesUsually not
DELETERemove a resourceRarelyYes
HEADSame as GET, but headers only, no bodyNoYes
OPTIONSDiscover what methods a resource supportsNoYes

Idempotent means calling it multiple times with the same input produces the same end state as calling it once. This isn't academic trivia — it directly shapes how you design tests: a POST retried after a timeout might create a duplicate resource, while a PUT retried the same way is safe by design. You'll rely on this distinction constantly once you get to API chaining and cleanup logic later in this course.

GET vs. POST

GET retrieves data and should never change server state — a GET request is safe to call repeatedly, cache, retry, or even accidentally trigger twice with no consequence. POST creates something or triggers an action with a side effect, and calling it twice by accident (a network retry, a double-click) can create two records instead of one. This is exactly why GET requests don't carry a body — there's nothing to "submit," only criteria to describe what you want back — while POST requests carry a body describing what to create.

PUT vs. PATCH

PUT conventionally replaces the entire resource with what you send — any field you omit can be reset to empty or default by a strict implementation. PATCH updates only the fields you actually include, leaving everything else untouched. Confusing these two is one of the most common real bugs in API test suites: sending a partial payload to a PUT endpoint that expects the full resource, and watching fields you never meant to touch silently disappear.

HTTP Status Codes

The status code is the single most important piece of a response to understand correctly, because it tells you which of five broad outcomes happened before you even look at the body:

RangeMeaningExample
2xxSuccess200 OK, 201 Created, 204 No Content
3xxRedirection301 Moved Permanently, 304 Not Modified
4xxClient error — you sent something wrong400, 401, 403, 404, 409
5xxServer error — the server failed to handle a valid request500, 502, 503

400 vs. 404

400 Bad Request means the request itself was malformed or invalid — a missing required field, an invalid data type, unparseable JSON. 404 Not Found means the request was perfectly well-formed, but the specific resource it asked for doesn't exist — GET /users/99999 when no user 99999 exists. The distinction matters for test design: a 400 is a request-construction problem, a 404 is a data/existence problem, and asserting the wrong one for the wrong scenario is a common negative-testing mistake covered in depth in the Negative Testing chapter.

401 vs. 403

401 Unauthorized means the server doesn't know who you are — no credentials, or invalid/expired credentials. 403 Forbidden means the server knows exactly who you are, but you don't have permission to do what you're asking. A regular user hitting an admin-only endpoint gets a 403, not a 401 — they're authenticated, just not authorized. This distinction is exactly what "authentication vs. authorization" means in practice, covered next.

Authentication vs. Authorization

Authentication answers "who are you?" — logging in, presenting a token, proving your identity. Authorization answers "what are you allowed to do?" — given that you're authenticated, does your role or permission level let you perform this specific action? A valid, authenticated token can still get a 403 if the authenticated user simply isn't allowed to do what they're asking. You'll test both independently: authentication failures (bad/missing/expired tokens) and authorization failures (a real, valid user attempting something outside their role) are two genuinely different categories of negative test, covered fully in the Authentication chapter.

Request Headers, Response Headers, and Content-Type

Headers are metadata that travel alongside a request or response, separate from the actual body content. A few you'll use constantly:

  • Content-Type — tells the server (on a request) or the client (on a response) what format the body is in, most commonly application/json. Get this wrong on a request and a perfectly valid JSON body can be rejected, because the server never even tried to parse it as JSON.
  • Accept — tells the server what format you want the response in. Most JSON APIs default to JSON regardless, but some APIs genuinely support multiple formats and use this header to decide.
  • Authorization — carries credentials, most often as Bearer <token> — the mechanism behind nearly every authenticated request you'll write.

Request Body and Response Body

The body is the actual payload — the data being sent (on POST/PUT/PATCH requests) or the data being returned (in most responses). GET requests conventionally have no body at all; anything they need to specify goes in the URL instead, via query or path parameters.

Query Parameters vs. Path Parameters

Both appear in the URL, and both are easy to blur together as a beginner — but they express genuinely different intent:

Path parameter — identifies WHICH resource:
GET /users/42

Query parameter — filters, sorts, or paginates WITHIN a resource collection:
GET /users?status=active&page=2&limit=10

A path parameter is part of the resource's identity — /users/42 and /users/43 are two entirely different resources. A query parameter narrows or shapes a request against a resource (or collection) that already exists independent of that parameter — /users?status=active is still fundamentally the users collection, just filtered. If you find yourself unsure which to use when designing a test against a new endpoint, ask: "does this value change which resource I'm even talking about, or does it just adjust how I'm querying it?"

Cookies

Cookies are small pieces of data the server asks the client to store and send back on subsequent requests — commonly used for session-based authentication in older or hybrid web/API systems. Modern REST APIs more often use token-based authentication (covered in depth in Chapter 6) instead of cookies, since tokens fit REST's stateless principle more cleanly, but you'll still encounter cookie-based auth in real projects, especially ones with a shared web and API backend.

JSON and XML

JSON (JavaScript Object Notation) is the dominant format for modern REST API bodies — lightweight, human-readable, and a natural fit for nested data:

{
  "id": 101,
  "name": "John",
  "address": {
    "city": "Delhi"
  },
  "roles": ["ADMIN", "USER"]
}

XML predates JSON and is still common in older enterprise systems, SOAP-based services, and some financial/banking APIs. RestAssured supports validating both natively — this course focuses primarily on JSON since it's what you'll encounter most often, with XML handling covered where it genuinely differs.

Common Mistakes at This Stage

  • Treating a 403 as if it were a 401 in a test assertion — they signal genuinely different problems (identity vs. permission), and conflating them produces misleading test failures.
  • Assuming a query parameter and a path parameter are interchangeable because both "just go in the URL" — using the wrong one against a real API will produce a 404 or unexpected results, not a helpful error.
  • Not distinguishing 400 from 404 when writing negative tests, leading to a test that asserts the wrong status code for the wrong reason.
  • Assuming GET requests are always side-effect-free in every real API — while this is the REST convention, poorly designed APIs occasionally violate it (a GET that increments a view counter, for instance); worth confirming for APIs you don't control.

Recommended Approach

Before writing your first RestAssured line, spend five minutes with any API you're about to test and answer these questions: What resources does it expose? Which HTTP methods does each endpoint actually support? What does a successful response look like — status code and body shape? What does a realistic failure look like? This five-minute habit prevents the majority of confused, hard-to-debug early test failures.

Debugging

When an API behaves unexpectedly and you're not yet writing RestAssured code, use a tool like curl or Postman first to see the raw request and response — confirming the actual status code, headers, and body shape before you start troubleshooting test code. Most "my test is broken" problems at this stage turn out to be "I misunderstood what the API actually returns."

Best Practices

  • Always check the actual status code and response shape of an endpoint (via curl/Postman/API docs) before writing an automated test against it — don't assume based on similar endpoints.
  • Learn to read status codes as a first diagnostic signal, before opening the response body.
  • Keep the Request/Response mental model (method, headers, body, params → status, headers, body) in mind for every test you write, in every chapter that follows.

Practice Exercise

Using a public test API (like https://reqres.in or https://jsonplaceholder.typicode.com), use curl to make three requests: a GET for a single resource, a GET for a resource that doesn't exist, and a POST creating a new resource. Note the status code and response shape for each, and identify which HTTP method and parameter type (path vs. query) each request used.

Summary

An API is a contract between systems; REST is a style for designing that contract around resources and standard HTTP methods. Every API interaction follows the same request/response cycle, and understanding status codes, headers, body structure, and the path-vs-query and PUT-vs-PATCH distinctions gives you the vocabulary every later chapter — and every RestAssured method — builds directly on top of.

What does REST's statelessness principle actually require of each request?▾
