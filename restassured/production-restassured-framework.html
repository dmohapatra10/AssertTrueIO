Building the Framework

Beginner 8 min read

Prerequisites: Every previous chapter — this is the capstone that assembles them all.

What is this?

This chapter doesn't introduce new APIs. It's a complete, progressive walkthrough of a small but genuinely production-style framework, built for a realistic e-commerce application — browsing products, placing an order, processing payment, checking order history — showing exactly how every earlier chapter's piece fits into one working whole.

Why It's Important

Knowing each individual technique — specs, builders, token management, parallel-safe design — is different from knowing how they compose into a single coherent project. This capstone is the missing piece: seeing the whole shape at once, built up one deliberate step at a time.

The Domain

An e-commerce API: user registration and login, product browsing, order creation, payment processing, and order history. Enough surface area to exercise authentication, CRUD chaining, negative testing, and framework architecture meaningfully, without being an unwieldy example.

Step 5 — Authentication & Token Management

// auth/TokenManager.java
public class TokenManager {
    private static volatile String cachedToken;
    private static long expiresAtMillis;

    public static synchronized String getToken() {
        if (cachedToken == null || System.currentTimeMillis() > expiresAtMillis) {
            Response response = given()
                .baseUri(EnvConfig.baseUrl())
                .body(Map.of("email", System.getenv("TEST_USER_EMAIL"),
                              "password", System.getenv("TEST_USER_PASSWORD")))
                .when().post("/auth/login");
            cachedToken = response.jsonPath().getString("token");
            expiresAtMillis = System.currentTimeMillis() + 3_600_000 - 5000;
        }
        return cachedToken;
    }
}

The expiration-aware, thread-safe token manager from Chapter 6 and Chapter 14, given its permanent home.

Step 6 — Specifications

// specs/SpecFactory.java
public class SpecFactory {
    public static RequestSpecification authenticated() {
        return new RequestSpecBuilder()
            .setBaseUri(EnvConfig.baseUrl())
            .setContentType(ContentType.JSON)
            .addHeader("Authorization", "Bearer " + TokenManager.getToken())
            .build();
    }
    public static RequestSpecification unauthenticated() {
        return new RequestSpecBuilder()
            .setBaseUri(EnvConfig.baseUrl())
            .setContentType(ContentType.JSON)
            .build();
    }
}

Step 7 — API Clients

// clients/OrderClient.java
public class OrderClient {
    private final RequestSpecification spec;
    public OrderClient(RequestSpecification spec) { this.spec = spec; }

    public Response create(Order order) {
        return given().spec(spec).body(order).when().post("/orders");
    }
    public Response getById(String id) {
        return given().spec(spec).pathParam("id", id).when().get("/orders/{id}");
    }
    public Response cancel(String id) {
        return given().spec(spec).pathParam("id", id).when().put("/orders/{id}/cancel");
    }
}

// clients/PaymentClient.java
public class PaymentClient {
    private final RequestSpecification spec;
    public PaymentClient(RequestSpecification spec) { this.spec = spec; }

    public Response process(String orderId, Payment payment) {
        return given().spec(spec).pathParam("orderId", orderId).body(payment)
            .when().post("/orders/{orderId}/payment");
    }
}

Step 8 — Test Data Builders

// data/OrderBuilder.java
public class OrderBuilder {
    private List<LineItem> items = List.of(new LineItem("Default Product", 1));

    public static OrderBuilder anOrder() { return new OrderBuilder(); }
    public OrderBuilder withItems(List<LineItem> items) { this.items = items; return this; }
    public Order build() { return new Order(items); }
}

Step 9 — A Positive Test: The Full Order-to-Payment Chain

// tests/orders/OrderCheckoutTest.java
@Test
void completeCheckoutFlowSucceeds() {
    OrderClient orderClient = new OrderClient(SpecFactory.authenticated());
    PaymentClient paymentClient = new PaymentClient(SpecFactory.authenticated());

    // Create — extract — verify (Chapter 7's full CRUD chain pattern)
    String orderId = orderClient.create(OrderBuilder.anOrder().build())
        .then().statusCode(201).extract().path("id");

    orderClient.getById(orderId).then().statusCode(200).body("status", equalTo("pending"));

    // Process payment for this order
    Payment payment = new Payment("4242424242424242", "12/28", "123");
    paymentClient.process(orderId, payment)
        .then().statusCode(200).body("status", equalTo("succeeded"));

    // Verify the order status updated as a result
    orderClient.getById(orderId).then().statusCode(200).body("status", equalTo("confirmed"));
}

Every piece traces back to a specific earlier chapter: the client layer (Chapter 13) built on a shared spec (Chapter 9) using cached authentication (Chapter 6), a data builder (Chapter 10), and a chained create→verify→pay→verify sequence (Chapter 7) with thorough response validation throughout (Chapter 4).

Step 10 — Negative Tests: The Failure Modes That Matter

// tests/orders/OrderNegativeTest.java
@Test
void creatingAnOrderWithNoItemsIsRejected() {
    OrderClient client = new OrderClient(SpecFactory.authenticated());
    Order emptyOrder = OrderBuilder.anOrder().withItems(List.of()).build();

    client.create(emptyOrder).then().statusCode(400)
        .body("code", equalTo("VALIDATION_ERROR"));
}

@Test
void payingForAnotherUsersOrderIsForbidden() {
    OrderClient ownerClient = new OrderClient(SpecFactory.authenticated());
    String orderId = ownerClient.create(OrderBuilder.anOrder().build())
        .then().statusCode(201).extract().path("id");

    PaymentClient otherUserPaymentClient = new PaymentClient(
        SpecFactory.forRole("otherUser")); // Chapter 6's role-scoped spec
    otherUserPaymentClient.process(orderId, new Payment("4242424242424242", "12/28", "123"))
        .then().statusCode(403);
}

@Test
void invalidCardNumberIsRejected() {
    OrderClient orderClient = new OrderClient(SpecFactory.authenticated());
    PaymentClient paymentClient = new PaymentClient(SpecFactory.authenticated());
    String orderId = orderClient.create(OrderBuilder.anOrder().build())
        .then().extract().path("id");

    paymentClient.process(orderId, new Payment("0000000000000000", "12/28", "123"))
        .then().statusCode(422).body("code", equalTo("PAYMENT_DECLINED"));
}

Straight from Chapter 12's principle: for a real checkout flow, negative scenarios (empty order, unauthorized payment attempt, declined card) meaningfully outnumber the single happy path — and the unauthorized-payment test specifically exercises the exact kind of security gap that's invisible to happy-path testing alone.

Step 11 — Schema Validation Across the API

@ParameterizedTest
@MethodSource("endpointsWithSchemas")
void everyResponseMatchesItsSchema(String endpoint, String schema) {
    given().spec(SpecFactory.authenticated()).when().get(endpoint)
        .then().statusCode(200).body(matchesJsonSchemaInClasspath(schema));
}

static Stream<Arguments> endpointsWithSchemas() {
    return Stream.of(
        Arguments.of("/products", "product-list-schema.json"),
        Arguments.of("/orders", "order-list-schema.json")
    );
}

The Chapter 11 contract-testing pattern, sweeping schema validation across every major endpoint as its own fast, broad check.

Step 12 — CI/CD

# .github/workflows/api-tests.yml
name: E-Commerce API Tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '21', distribution: 'temurin', cache: 'maven' }
      - run: mvn -B test
        env:
          API_BASE_URL: ${{ secrets.QA_BASE_URL }}
          TEST_USER_EMAIL: ${{ secrets.TEST_USER_EMAIL }}
          TEST_USER_PASSWORD: ${{ secrets.TEST_USER_PASSWORD }}
      - if: always()
        uses: actions/upload-artifact@v4
        with: { name: surefire-reports, path: target/surefire-reports/ }

What Makes This "Production-Style," Not Just a Working Script

  • No hardcoded URLs or credentials anywhere — everything environment-driven, per Chapters 2 and 10.
  • Authentication centralized in one thread-safe manager — a scheme change touches one file, not every test (Chapter 13's separation-of-concerns payoff, made concrete).
  • Negative tests genuinely outnumber positive ones for the checkout flow — including a security-relevant authorization test, not just format validation.
  • Schema validation runs broadly across the API as a fast contract-regression check, separate from deep functional assertions.
  • The suite is parallel-safe — no static mutable state, dynamically unique test data throughout.
  • CI failure produces a diagnosable artifact, not just a red X.

Common Mistakes at This Scale

  • Skipping the client/spec layers "since the project is still small" — this is exactly the debt that makes a growing suite painful; introduce it from the start, it costs little.
  • Testing payment success without testing payment failure — a declined card, an invalid card number, and an unauthorized payment attempt are all genuinely distinct, each worth its own test.
  • Letting test-created orders accumulate in a shared QA environment without any cleanup strategy (Chapter 10's layered cleanup approach).

Where to Go From Here

This framework is intentionally small enough to hold in your head — a real production suite grows the same structure outward: more clients, more models, more negative scenarios per endpoint, a dedicated contract-testing CI stage running schema validation separately from the full functional suite, and probably Allure reporting once the team's reporting needs outgrow raw JUnit XML. None of that requires new concepts beyond this course — it's the same pieces, more of them, composed the same way.

Summary

A production-style RestAssured framework is not a single advanced technique — it's the disciplined composition of everything covered in this course: REST fundamentals and request construction for reliable interaction, response validation and JsonPath for thorough verification, authentication and token management for secure and efficient access, API chaining for realistic workflows, test data management for safe and repeatable data, negative testing for genuine coverage of what actually goes wrong, layered architecture for maintainability at scale, and parallel-safe CI/CD for fast, automated, trustworthy feedback on every push. Every piece traces back to a specific earlier chapter; the skill this capstone teaches is fitting them together.

Interview Questions

What separates a "framework" from a folder of individual RestAssured test classes?▾
A framework has consistent, reusable structure — shared specs instead of per-test setup duplication, a client layer instead of repeated inline request construction, centralized and thread-safe authentication instead of ad-hoc token handling scattered across tests, and environment-driven configuration instead of hardcoded values. A folder of individual test classes might each work in isolation, but every new test re-solves problems (authentication, request setup, data generation) that a framework solves once and makes available everywhere — which is what actually lets a test suite scale to hundreds of tests, run safely in parallel, and survive real infrastructure changes without becoming unmaintainable.
