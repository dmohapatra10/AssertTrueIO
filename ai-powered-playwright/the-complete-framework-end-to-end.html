Introduction

Six earlier pages each built one real stage. This page connects them — the complete framework, running the discount-code bug from a single, open-ended objective all the way to a confirmed, honestly-reported resolution.

Step-by-Step Implementation — The Complete, Assembled Framework

// src/autonomous-framework.ts
import { generateCapstonePlan } from './capstone-pipeline';
import { executeCapstonePlan } from './capstone-pipeline';
import { evaluateCapstoneResults } from './capstone-pipeline';
import { findRootCauseAndProposeFix } from './capstone-pipeline';
import { revalidateAfterFix } from './capstone-pipeline';
import { generateCapstoneReport } from './capstone-pipeline';
import { Page, TestInfo } from '@playwright/test';

export async function runAutonomousFramework(
  objective: string, page: Page, testInfo: TestInfo, history: TestRunRecord[]
) {
  // STAGE 1 — Chapters 3, 4
  const plan = await generateCapstonePlan(objective);

  // STAGE 2 — Chapters 5, 9, 10, 13
  const execution = await executeCapstonePlan(plan.playwrightTests, page, testInfo);

  // STAGE 3 — Chapters 9, 12, 16
  const payload = selectEvidenceForAnalysis(execution.evidence);
  const evaluation = await evaluateCapstoneResults(execution.evidence, history);

  if (!evaluation.genuineFailure) {
    return generateCapstoneReport({
      plan, execution, evaluation, rootCause: null, revalidation: null,
    });
  }

  // STAGE 4 — Chapters 9, 11
  const rootCause = await findRootCauseAndProposeFix(payload, evaluation.classification);

  // STAGE 5 — Chapter 11 (after a REAL, human-applied fix)
  const revalidation = await revalidateAfterFix(
    'apply discount code SAVE10 twice in succession', page
  );

  // STAGE 6 — Chapters 9, 14
  return generateCapstoneReport({ plan, execution, evaluation, rootCause, revalidation });
}

Code Explanation

Every import traces to a real, earlier page — either from this chapter or from the fourteen chapters that built the underlying functions this chapter's pipeline calls. The conditional early return after stage 3 matters too: if evaluation finds no genuine failure, this framework honestly reports clean success rather than manufacturing a root cause for something that isn't actually broken.

Interview Questions

Beginner: Why does the autonomous framework return early after stage 3 if evaluateCapstoneResults finds no genuine failure?▾

Root cause analysis and fix generation only make sense for a confirmed, genuine defect — running them against something that turned out to be expected behavior or a known flaky pattern would waste real cost and produce a diagnosis for a problem that doesn't actually exist. The early return reflects the same honesty this track has practiced throughout: report what's actually true, including clean success, rather than manufacturing findings to justify continuing through every stage regardless of what the evidence shows.

Beginner: Why does this capstone use one real, single scenario (the discount-stacking bug) rather than several unrelated examples across its pages?▾

A single, continuous scenario lets each stage's output become the next stage's real input, the same way it would in an actual production run — the generated plan feeds real execution, real execution produces real evidence, real evidence feeds real evaluation, and so on. Using several unrelated examples would obscure exactly the thing this capstone exists to demonstrate: that these stages genuinely connect into one working pipeline, not just that each stage works in isolation.

Intermediate: Explain why stage 4 (root cause and fix) stops short of proposing an application code patch, even though Chapter 11 built a real self-healing pipeline.▾

Chapter 11's self-healing pipeline was built specifically for test-file fixes — locators and assertions within the test suite itself, not the application under test. The discount-stacking bug lives in ShopSmart's own discount-calculator.ts, genuinely outside that pipeline's real, intended scope. Extending it to autonomously patch application source code would be a meaningfully different, riskier capability than anything this track actually built and validated — this stage stays honest about that boundary, delivering a complete diagnosis for the development team rather than pretending to a capability the framework doesn't genuinely have.

Intermediate: Why does stage 5 re-run the exact original exploration action rather than writing a new test specifically for the fix?▾

The original action is exactly what revealed the bug — re-running it is the most direct, honest way to confirm this specific, reported problem is genuinely resolved. A newly written test, however well-intentioned, risks subtly not exercising the exact same condition that triggered the original failure, potentially passing while the real bug persists in some edge case the new test didn't happen to cover. Re-running the original trigger closes this specific gap with certainty a new test can't fully guarantee.

Advanced: Trace how Chapter 11's human-approval rule shapes this capstone's design, even though the final assembled framework never explicitly shows a pull request being opened.▾

The rule's influence is visible in what this framework deliberately doesn't do, not just in explicit approval-gate code. Stage 4 stops at diagnosis rather than generating and auto-applying an application code fix — a direct, structural consequence of Chapter 11's rule, since autonomously patching application source without review would violate it. The framework hands a complete, evidence-grounded diagnosis to a human development team, who apply the actual fix themselves; stage 5 then re-validates that real, human-applied change. The absence of an autonomous application-code-patching step in this capstone's architecture is Chapter 11's rule operating exactly as designed — shaping what the framework was built to do in the first place, not merely gating a step after the fact.

Scenario-based: A teammate wants to extend this framework so that stage 4 automatically applies a fix to discount-calculator.ts when confidence is "high," reasoning that Chapter 14's honest confidence scoring makes this safe. How would you respond, drawing on this entire track's reasoning?▾

I'd draw on several threads from across this track at once. First, Chapter 14's confidence scoring in this capstone is assessed on the pipeline's own diagnosis and revalidation — it was never validated against the much harder, different question of whether a specific proposed application-code change is itself correct, which is exactly the gap Chapter 11's assertion-healing page warned about: a confident-sounding conclusion can still be wrong in ways only business and application context reveal. Second, Chapter 11's rule was never confidence-conditional — it applies regardless of how certain any automated system claims to be, precisely because certainty and correctness are different things, a distinction this track has returned to since Chapter 1. Third, this specific bug lives in application source code, a scope Chapter 11's real, validated self-healing pipeline was deliberately never built to touch autonomously. High confidence in a diagnosis is not the same as high confidence in a specific code change being the correct fix — I'd suggest the genuinely safer, still valuable extension is having the framework draft a suggested patch for human review, following Chapter 11's own draft-PR pattern exactly, never an automatic application.

A Note on Finishing This Track

Twenty-one chapters, one hundred and fifty-eight pages, and one real, continuous framework later — every technique in this final page traces back to something genuinely built, explained, and validated somewhere earlier in this journey. From Chapter 1's honest distinction between AI-assisted and autonomous testing, through locator healing, evidence-based failure analysis, self-healing automation, exploratory agents, MCP, and now this capstone's complete, working pipeline — the throughline has been the same from the very first page: know exactly when AI genuinely earns its place, and never let it operate without the safeguards that make it trustworthy. That discipline, more than any single technique, is what this track was really teaching all along.
