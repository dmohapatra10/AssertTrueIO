Why Thresholds Are the Real Payoff of Everything So Far

Every chapter up to this point has built toward being able to run a meaningful test and read its results correctly. Thresholds are what make that judgment automatic and repeatable — instead of a human reading a summary and deciding "this looks okay," a properly configured threshold gives a definitive, scriptable pass or fail, which is exactly what a CI/CD pipeline (Chapter 13) needs to act on without a person watching every run.

A Quick Preview

export const options = {
  thresholds: {
    http_req_duration: ['p(95)<500'],
    http_req_failed: ['rate<0.01'],
  },
};

This is the direct, executable form of a requirement like "95% of requests should complete within 500ms and error rate should remain below 1%" — the exact translation this chapter teaches properly.

Common Mistakes to Watch For

  • Confusing thresholds with checks — they serve genuinely different purposes, covered directly on the second page.
  • Setting a threshold value that's just a guess rather than derived from something real — an SLA, an SLO, or actual historical performance.
  • Defining a threshold on response time but forgetting error rate, or vice versa — leaving a real gap a "passing" test could hide behind, exactly as covered in the previous chapter.
