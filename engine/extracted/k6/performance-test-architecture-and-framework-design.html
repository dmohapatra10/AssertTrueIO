From One Good Script to a Real Project

Chapter 3 introduced the instinct — extract a repeated request into a function, then into a shared module. That instinct is the seed of everything here: what happens once a project has many workflows, many test types (Chapter 10), many environments (Chapter 9's __ENV), and enough scripts that "where does this code even go" becomes a real, recurring question. From Scripts to a Framework — What Actually Changes

A handful of independent scripts, each doing its own setup inline, is perfectly fine for a small project — nothing here is about declaring that approach wrong at small scale. A framework becomes worth the investment specifically once a project has enough scripts that duplicated logic, inconsistent patterns, and hardcoded values scattered across files start costing real time whenever something needs to change.

A Quick Preview of the Structure

k6-performance/
├── tests/         (smoke, load, stress, spike, soak — Chapter 10's configurations)
├── workflows/      (Chapter 9's realistic journeys — login, browse, checkout)
├── api/             (Chapter 3's reusable request functions, one module per resource)
├── data/             (Chapter 8's SharedArray-loaded test data)
├── config/            (Chapter 9's environment configuration, __ENV-driven)
├── utils/              (unique-data generation, JWT decoding, shared helpers)
├── metrics/              (Chapter 6's custom Counter/Gauge/Rate/Trend definitions)
├── thresholds/            (Chapter 7's threshold configurations, per test type)
└── reports/                (output destination for results)

Every folder here maps directly onto a concept already covered in this course — this chapter is about organizing those concepts into one coherent project, not introducing new k6 mechanics.

Common Mistakes to Watch For

  • Duplicating request logic across many test files instead of extracting it once into the api/ layer, exactly the Chapter 3 instinct applied at project scale.
  • Hardcoding URLs and credentials directly in test files instead of the config/ layer, undoing Chapter 9 and Chapter 10's environment-variable practices.
  • Letting test scripts grow into giant, unstructured files mixing workflow logic, data generation, and configuration all in one place.
