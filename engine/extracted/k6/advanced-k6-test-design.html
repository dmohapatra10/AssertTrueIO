What's Actually New Here

Scenarios, groups, custom metrics, and multiple workloads have all already been covered in depth. What hasn't: tagging requests for filtering and analysis, environment variables for configuring a test without editing its code, and — the genuine centerpiece of this chapter — turning the six test types from Chapter 1 into real, distinct configurations of the exact same underlying script. Two focused pages:

  1. Tags & Environment Variables — filtering results by tag, and configuring a test from outside its own code
  2. Designing Every Test Type From One Script — smoke, load, stress, spike, soak, and regression, as configuration, not separate scripts

The Real Point of This Chapter

Chapter 1 defined load, stress, spike, and soak testing conceptually. Chapter 4 taught the executor mechanics that make any of them possible. What's never been shown directly: that a well-built script — the realistic journey from Chapter 9, for instance — doesn't need to be rewritten six times to serve as six different test types. It needs the same logic, and six different options blocks around it.

A Quick Preview

Same script. Different options:

Smoke:      1 VU, 1 minute      — does it work at all?
Load:       200 VUs, 15 minutes — does it hold up at expected traffic?
Stress:     ramping to 2000 VUs — where does it actually break?
Spike:      instant jump to 1000 VUs — does it survive a shock?
Soak:       100 VUs, 4 hours    — does it degrade over time?
Regression: 200 VUs, compared against last week's baseline

This is the actual practical payoff of everything built across this entire course so far — one well-designed script, reused deliberately across an entire testing strategy.

Common Mistakes to Watch For

  • Writing a separate script for every test type instead of reconfiguring one well-built script — needless duplication that drifts out of sync over time.
  • Skipping the smoke test before running an expensive, long stress or soak test — burning real time and resources discovering a basic script bug the hard way.
  • Never tagging requests in a multi-step or multi-scenario test, making it hard to break results down meaningfully afterward.
