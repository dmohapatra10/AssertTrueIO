4-5 — API Clients & Authentication

// api/auth.js
import http from 'k6/http';
import { config } from '../config/index.js';

let vuToken = null;
export function ensureLoggedIn(credentials) {
  if (!vuToken) {
    const response = http.post(`${config.baseUrl}/login`, JSON.stringify(credentials),
      { headers: { 'Content-Type': 'application/json' } });
    vuToken = response.json('token');
  }
  return vuToken;
}

// api/portfolio.js
export function getPortfolio(token) {
  return http.get(`${config.baseUrl}/portfolio`, {
    headers: { Authorization: `Bearer ${token}` }, tags: { endpoint: 'portfolio' },
  });
}

// api/orders.js
export function placeOrder(token, order) {
  return http.post(`${config.baseUrl}/orders`, JSON.stringify(order),
    { headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${token}` },
      tags: { endpoint: 'orders' } });
}

Chapter 9's correct per-VU authentication pattern — each simulated trader logs in as a genuinely distinct user, never sharing one identity across VUs, which matters enormously here since a user-isolation bug in a trading platform (one trader seeing another's portfolio) would be a serious, real problem.

7-8 — The Realistic User Journey & Scenarios

// workflows/trading-journey.js
import { check, sleep, group } from 'k6';
import { ensureLoggedIn } from '../api/auth.js';
import { getPortfolio } from '../api/portfolio.js';
import { searchStock } from '../api/search.js';
import { placeOrder } from '../api/orders.js';
import { traders } from '../data/traders.js';
import { uniqueOrderRef } from '../utils/unique-data.js';
import { ordersPlaced, orderSuccessRate } from '../metrics/index.js';

export default function () {
  const trader = traders[__VU % traders.length];
  const token = ensureLoggedIn(trader);

  group('Trading Journey', function () {
    const portfolio = getPortfolio(token);
    check(portfolio, { 'portfolio loaded': (r) => r.status === 200 });
    sleep(2 + Math.random() * 2);

    const stock = searchStock(token, 'AAPL');
    check(stock, { 'stock found': (r) => r.status === 200 });
    sleep(1);

    const order = placeOrder(token, {
      symbol: 'AAPL', quantity: 10, reference: uniqueOrderRef(),
    });
    const orderOk = check(order, {
      'order placed': (r) => r.status === 201,
      'order confirmation matches quantity': (r) => r.json('quantity') === 10,
    });
    orderSuccessRate.add(orderOk);
    if (orderOk) ordersPlaced.add(1);
  });
}

Chapter 9's complete journey pattern, applied to trading instead of e-commerce — login, browse (portfolio), search, and a purchase-equivalent (placing an order) — with functional checks verifying correctness, not just speed, per Chapter 5's core principle.

name: TradeFlow Performance Tests
on: { push: { branches: [main] }, schedule: [{ cron: '0 5 * * 1-5' }] } # weekday mornings

jobs:
  performance:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Smoke test

        env: { TARGET_ENV: staging, API_KEY: ${{ secrets.STAGING_API_KEY }} }
      - name: Load test

      - name: Archive results
        uses: actions/upload-artifact@v4
        with: { name: k6-results-${{ github.run_id }}, path: results.json }
      - name: Check regression against last week's baseline
        run: node scripts/check-regression.js results.json baseline.json

Common Mistakes Across a Real Project Like This

  • Building the load test before confirming the smoke test passes — wastes real time discovering a basic bug the expensive way, exactly as Chapter 10 warned.
  • Treating the trading journey's functional checks as optional — for a financial platform specifically, verifying an order's confirmed quantity matches what was requested isn't optional polish, it's the actual point.
  • Skipping regression detection and relying only on fixed thresholds — missing a real, gradual degradation that never quite crosses the absolute threshold line.

Interview Questions

Why does this capstone use per-VU authentication rather than a single shared setup()-based login, and why does that matter more for a trading platform specifically?▾
Per-VU authentication ensures each simulated trader is a genuinely distinct, isolated session — critical for a financial platform, where a user-isolation bug (one trader's session accidentally accessing another's portfolio or placing an order under the wrong identity) would be a serious, real-world problem. A shared setup()-based session would make this entire class of bug structurally invisible to the test, exactly as covered when this distinction was first introduced.
Why does the order-placement check verify the confirmed quantity, not just the response status code?▾
A 201 status code alone confirms the server accepted the request, not that it processed it correctly — under concurrent load, a race condition or data-handling bug could return success while recording the wrong quantity. Verifying the actual confirmed quantity matches what was requested is exactly the functional-correctness-under-load principle established when this course first covered why performance tests should validate functionality, not just speed.
Why does the spike test scenario in this capstone specifically model a "breaking news" surge rather than a generic traffic spike?▾
Designing a workload from a real, domain-specific scenario (rather than an abstract, generic one) is exactly the workload-modeling discipline this course emphasizes — a trading platform's most realistic and consequential spike scenario is genuinely triggered by market-moving news, not an arbitrary traffic burst, and modeling that specific real-world trigger produces a more meaningful test than a generic spike shape would.
Why does the CI/CD pipeline schedule performance tests for weekday mornings specifically, rather than an arbitrary time?▾
Scheduling deliberately, based on when a regression would actually matter most (before real markets open on trading days), rather than an arbitrary time, is a direct application of designing tests around genuine business context rather than convenience — catching a regression before it could affect real trading activity is far more valuable than catching the same regression at a moment when it wouldn't yet have any real consequence.
How does this capstone's threshold configuration directly trace back to the original business requirement, rather than being a set of arbitrary numbers?▾
Every threshold value — the p95 response time, the error rate, the order-success rate — was derived directly from the stated business requirement ("3,000 concurrent traders, 95% of orders under 1 second, error rate under 0.5%"), not picked because it sounded reasonable. This is the threshold-derivation discipline established earlier in this course, applied concretely: a threshold disconnected from a real requirement either fails constantly or passes meaninglessly, and grounding every value in the actual stated requirement is what keeps the whole test genuinely meaningful.
