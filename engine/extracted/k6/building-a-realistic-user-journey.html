Building a Realistic User Journey

Prerequisites: Session Management: Token Reuse, Expiration & Refresh

What is this?

This page assembles everything from this chapter — proper per-VU authentication, realistic pacing — into one complete journey: Login → Browse → Search → Add to Cart → Checkout, with each virtual user genuinely representing a distinct, independent shopper.

Step 1 — Login, Per-VU

const users = new SharedArray('users', function () {
  return JSON.parse(open('./users.json'));
});

let vuToken = null;

function ensureLoggedIn() {
  if (!vuToken) {
    const user = users[__VU % users.length];
    const response = http.post(loginUrl,
      JSON.stringify({ username: user.username, password: user.password }),
      { headers: { 'Content-Type': 'application/json' } });
    check(response, { 'login succeeded': (r) => r.status === 200 });
    vuToken = response.json('token');
  }
}

This is the correct per-VU pattern from the previous page — each virtual user genuinely logs in as itself, once, using a genuinely distinct real credential.

Step 2 — Browse Products

function browseProducts() {
  const response = http.get('https://api.example.com/products', {
    headers: { Authorization: `Bearer ${vuToken}` },
  });
  check(response, { 'products loaded': (r) => r.status === 200 });
  sleep(2 + Math.random() * 2); // 2-4 seconds, realistic browsing pause
}

Step 3 — Search

function searchProducts(query) {
  const response = http.get(`https://api.example.com/products/search?q=${encodeURIComponent(query)}`, {
    headers: { Authorization: `Bearer ${vuToken}` },
  });
  check(response, { 'search returned results': (r) => r.status === 200 });
  sleep(1 + Math.random() * 2);
  return response.json()[0]?.id; // pick the first search result
}

Note the encoded query parameter, from Chapter 5's request-building material — a real search term could contain spaces or special characters that need proper URL encoding.

Step 4 — Add to Cart

function addToCart(productId) {
  const response = http.post('https://api.example.com/cart',
    JSON.stringify({ productId, quantity: 1 }),
    { headers: {
        'Content-Type': 'application/json',
        Authorization: `Bearer ${vuToken}`,
      } });
  check(response, { 'added to cart': (r) => r.status === 201 });
  sleep(1);
}

Step 5 — Checkout

function checkout() {
  const response = http.post('https://api.example.com/checkout', null, {
    headers: { Authorization: `Bearer ${vuToken}` },
  });
  check(response, {
    'checkout succeeded': (r) => r.status === 200,
    'order confirmation includes an id': (r) => r.json('orderId') !== undefined,
  });
}

Detailed Example — The Complete Journey, Assembled

export default function () {
  ensureLoggedIn();

  group('Shopping Journey', function () {
    browseProducts();

    const productId = searchProducts('wireless headphones');
    if (productId) {
      addToCart(productId);
      checkout();
    }
  });
}

export const options = {
  scenarios: {
    shoppers: {
      executor: 'ramping-vus',
      startVUs: 0,
      stages: [
        { duration: '3m', target: 200 },
        { duration: '10m', target: 200 },
        { duration: '3m', target: 0 },
      ],
    },
  },
  thresholds: {
    checks: ['rate>0.97'],
    http_req_duration: ['p(95)<800'],
  },
};

❌ Fragile vs. ✅ Recommended

// ❌ One endpoint, hammered repeatedly, one shared session — unrealistic
export default function () {
  http.get('https://api.example.com/products'); // repeated forever, same session
}

// ✅ A genuine multi-step journey, per-VU sessions, realistic pacing
export default function () {
  ensureLoggedIn();
  browseProducts();
  const id = searchProducts('headphones');
  if (id) { addToCart(id); checkout(); }
}

Common Mistakes

  • Testing only the "happy path" every single time — a search that returns zero results (the if (productId) check above) is a real scenario worth handling gracefully in the script, not assuming away.
  • No pacing between steps — an unrealistic burst through the entire journey doesn't represent how real shoppers actually move through a site.
  • Forgetting per-VU session isolation after everything covered in this chapter — reverting to a shared session out of habit undoes the whole point.

Edge Cases

  • A search returning no results for some VUs' randomly-selected query terms — the script needs to handle this gracefully (as shown, skipping the cart/checkout steps) rather than crashing or generating a misleading failed check.
  • Cart state persisting (or not) between a VU's separate iterations — worth being deliberate about whether each iteration should represent a fresh shopping session or a continuation of a previous one, since real systems handle this differently.

Debugging

If this kind of realistic journey test shows problems a simpler single-endpoint test never revealed, that's actually the intended outcome, not a sign something's wrong with the test — a realistic, multi-step, properly-isolated journey is specifically designed to surface exactly the kind of integration and isolation issues a simpler test structurally cannot reach.

Best Practices

  • Build journeys that reflect how real users actually move through a system, not just a sequence of technically-connected API calls.
  • Handle realistic edge cases within the journey itself (an empty search result) rather than assuming only the happy path will occur.
  • Keep per-VU session isolation intact throughout — this chapter's central lesson applies to the whole journey, not just the login step.

Interview Questions

Why is a realistic multi-step journey more valuable than repeatedly testing a single endpoint in isolation?▾
A single endpoint tested in isolation, repeatedly, doesn't represent how real users actually interact with a system — it misses integration issues between steps, doesn't exercise session state realistically, and can't reveal problems specific to a particular workflow stage (like checkout specifically struggling while browsing performs fine). A realistic journey exercises the system far closer to how production traffic genuinely behaves.
Why does the search step in this journey need to handle the case of zero results gracefully?▾
A real search doesn't always return results, and a script that assumes it always will (without checking) risks either crashing on undefined data or generating a misleading failed check that has nothing to do with an actual system problem — it's simply an expected, realistic outcome of a search that happened not to match anything, which the script needs to account for explicitly.
Why does this journey's pacing use a randomized sleep range rather than a single fixed duration?▾
Real users don't all pause for the identical amount of time between actions — some browse quickly, others linger. A randomized range better approximates the natural variation in real user behavior than a single fixed value, which would produce an artificially synchronized pattern across every simulated shopper.
What would be lost if this journey reverted to a single shared session (via setup()) instead of per-VU authentication?▾
The entire test would secretly represent one real shopper, no matter how many virtual users it configured — cart state, checkout behavior, and any user-isolation logic in the target system would never genuinely be exercised across multiple distinct identities, making an entire category of real, concurrency-specific bug structurally unreachable by the test, exactly as covered earlier in this chapter.
How does this journey's threshold configuration (checks and http_req_duration together) reflect the lessons from earlier chapters?▾
A threshold on checks enforces that the functional correctness verified throughout the journey (login succeeding, products loading, checkout actually completing) meets a real bar — not just that requests were fast. Combined with a response-time threshold, this directly reflects the "fast and correct, not just fast" principle established earlier in this course, now applied to a genuinely realistic, multi-step scenario rather than a single isolated request.
