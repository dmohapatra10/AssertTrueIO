Why the Tool Comes Right After the Vocabulary

Every concept covered so far — virtual users, throughput, percentiles — needs a real tool to actually produce and measure them. What follows is deliberately still light on deep scripting (that comes next); the goal here is getting comfortable with k6 as a tool — installed, running, and understood at the architecture level — before layering scripting depth on top of it.

A Quick Preview

import http from 'k6/http';
import { sleep } from 'k6';

export default function () {
  http.get('https://test-api.example.com/products');
  sleep(1);
}
$ k6 run script.js

This is a genuinely complete, runnable k6 test — five lines of actual logic. Part of what makes k6 approachable is exactly this: the barrier between "installed" and "running a real test" is small, which is why this chapter can move from zero to a working test quickly, before Chapter 3 goes deep on everything a real script needs.

Common Mistakes to Watch For

  • Treating k6 like a browser-automation tool — it's a load-generation tool that speaks HTTP directly, not a browser; there's no DOM, no rendering, no clicking.
  • Not understanding which lifecycle stage a piece of code runs in — code in the wrong stage (like expensive setup logic inside the main VU function) gets repeated unnecessarily by every single virtual user, every iteration.
  • Choosing a load-testing tool based on popularity alone rather than what actually fits the team's language, infrastructure, and testing needs.
