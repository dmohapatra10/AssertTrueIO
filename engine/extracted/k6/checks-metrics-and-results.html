Understanding What k6 Actually Reports

check() and percentiles were already covered earlier in this course. What hasn't been covered yet: k6's specific, individually-named metrics — what each one precisely measures — and the custom metric types available when the built-in ones aren't enough. Three focused pages:

  1. Built-in HTTP Metrics Explained — http_req_duration and its parts, http_req_failed, vus, iterations, and more
  2. Custom Metrics: Counter, Gauge, Rate, Trend — measuring something k6 doesn't track by default
  3. Good vs. Misleading Performance Analysis — applying everything from this chapter (and Chapter 1) to a real result correctly

Why This Comes Right After Building a Real Workflow

The workflow test built in the previous chapter produces real output — a wall of metrics after every run. Up to this point, that output has mostly been glanced at for pass/fail; this is where it actually gets read properly, understanding precisely what each number means and, just as importantly, what it doesn't.

Every line here has a precise meaning — not just "duration" and "requests," but specific, distinguishable measurements, each telling a genuinely different part of the story. The first page ahead breaks down exactly what each of these lines is actually measuring.

Common Mistakes to Watch For

  • Reading http_req_duration as a single, simple number when it's actually composed of several distinguishable sub-phases, each worth understanding separately.
  • Never defining a custom metric when the built-in ones genuinely don't capture what actually matters for a specific test's real goal.
  • Treating a "passing" summary as automatically meaning the test found nothing wrong — a passing threshold and a genuinely healthy system aren't always the same thing, covered directly on the last page.
