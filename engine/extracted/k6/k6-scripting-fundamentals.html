How a k6 Script Differs From a Normal JavaScript Program

A k6 script looks like JavaScript, and mostly is — but it runs inside k6's own execution engine, gets re-executed repeatedly by design (once per iteration, per virtual user, not once like a typical script), and its top-level exports (setup, default, teardown) have specific, reserved meanings k6 looks for automatically. Writing k6 scripts well means keeping this repeated-execution model in mind constantly — code that would be perfectly reasonable in a normal one-shot script can be a real problem once it's about to run thousands of times per test.

Common Mistakes to Watch For

  • Treating a k6 script as a one-shot program — forgetting that the default function runs repeatedly changes what "reasonable" code looks like.
  • Writing a "test" with no check() calls — a script that only sends requests without verifying anything can run against a broken endpoint indefinitely without ever reporting a problem.
  • Copy-pasting the same request logic across many test files instead of extracting it into a reusable function once a pattern repeats.
