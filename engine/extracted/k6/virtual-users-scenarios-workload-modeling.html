Controlling Load Deliberately

Everything so far has run a script with default, minimal settings — one virtual user, one iteration. This is about controlling load deliberately: how many virtual users, for how long, ramping up gradually or arriving at a fixed rate, and how to actually decide those numbers from a real requirement rather than guessing. Five focused pages:

  1. Virtual Users & Iterations — the basic units of load: vus, duration, iterations
  2. Ramping & Stages — gradually increasing or decreasing load instead of a flat, constant level
  3. k6 Executors Explained — the four executor types, and when each one is actually the right choice
  4. Scenarios: Multiple Workloads in One Test — running genuinely different load patterns simultaneously
  5. Translating a Business Requirement into a Workload — the real skill everything here builds toward

Why This Is the Deepest Material in This Course

The actual k6 configuration syntax for load (a few keys in an options object) is genuinely small. What takes real skill — and what most of what follows is actually about — is workload modeling: correctly deciding what those numbers should be, based on real traffic patterns and real business requirements, rather than picking values that happen to look reasonable. Two engineers can write syntactically identical k6 configuration and produce tests that mean completely different things, because the numbers behind that syntax were reasoned about completely differently.

A Quick Preview — The Same Test, Configured Three Different Ways

// A flat, constant number of VUs for a fixed duration
export const options = { vus: 50, duration: '5m' };

// Gradually ramping up, holding, then ramping down
export const options = {
  stages: [
    { duration: '2m', target: 100 },
    { duration: '5m', target: 100 },
    { duration: '2m', target: 0 },
  ],
};

// A fixed rate of new iterations per second, independent of how many VUs that requires
export const options = {
  executor: 'constant-arrival-rate',
  rate: 50,
  timeUnit: '1s',
  duration: '5m',
  preAllocatedVUs: 100,
};

These three configurations produce genuinely different load patterns — and choosing correctly between them, for a specific real scenario, is exactly what this chapter teaches, not just the syntax to write any one of them.

Common Mistakes to Watch For

  • Picking a VU count that "sounds like a lot" without connecting it to any real traffic data or business requirement.
  • Confusing virtual users with requests per second — these are related but genuinely different things, covered precisely in this chapter.
  • Defaulting to a flat, constant load when the real traffic pattern being modeled is actually a gradual ramp, a sudden spike, or something else entirely.
