A Subtle Bug Hiding in an Earlier Example

Chapter 2 showed authenticating once inside setup(), sharing the resulting token across every virtual user — correct for a single, shared service-level credential. But if the actual goal is simulating many distinct real users, that same pattern is quietly wrong: setup() runs exactly once for the entire test, so every VU would be using the identical session, not their own. This chapter is about getting that right. Three focused pages:

  1. Authentication Mechanisms: Basic, Bearer, API Key, JWT, OAuth — every mechanism, as k6 syntax
  2. Session Management: Token Reuse, Expiration & Refresh — including the setup() nuance above, done correctly
  3. Building a Realistic User Journey — Login → Browse → Search → Add to Cart → Checkout, with each VU as a genuinely distinct user

Why This Matters More Than It Sounds Like It Should

A test where every virtual user shares one identical session isn't just a technical inaccuracy — it can hide real bugs (a user-isolation problem in the target system would be invisible if every "user" is secretly the same one) and can even produce misleadingly good performance numbers, since the system may cache or reuse resources for a single repeated session far more efficiently than it ever could for hundreds of genuinely distinct ones.

A Quick Preview of the Distinction

❌ One shared login for the whole test (setup(), used naively):
   All 200 VUs → 1 real session → not realistic user isolation

✅ Each VU authenticates for itself (this chapter's actual approach):
   200 VUs → 200 real, independent sessions → genuinely realistic

Common Mistakes to Watch For

  • Reusing Chapter 2's setup()-login pattern for a test meant to simulate many distinct real users, without realizing it produces one shared identity instead.
  • Never handling token expiration in a longer-running or soak-style test, leading to a wave of authentication failures partway through that look like a system problem but aren't.
  • Treating cookies and bearer tokens as interchangeable — a real system may combine both, each needing to be handled correctly.
