Unique Test Data & Avoiding Collisions

Prerequisites: Test Data, Correlation & Dynamic Workflows overview

What is this?

Any data meant to be unique — an email, a username, an order reference — needs to actually be unique across every virtual user and every iteration in a real performance test, not just look plausible in a single example run. This page covers how to make that genuinely true.

The Problem, Concretely

const payload = JSON.stringify({ email: 'testuser@example.com' });
// Every VU, every iteration, sends the exact same email.
// A real system correctly rejects duplicates — so most of these fail,
// and the test stops measuring what it was meant to measure.

k6's Execution Context — __VU and __ITER

export default function () {
  const uniqueEmail = `user-${__VU}-${__ITER}@example.com`;
  // VU 3, iteration 12 → user-3-12@example.com
  // Genuinely unique as long as no two VUs share the same __VU number
  // (which k6 guarantees) and no VU repeats an __ITER value (which it also guarantees)
}

k6 exposes __VU (the current virtual user's ID) and __ITER (the current iteration number for that VU) as built-in variables — combining them produces a value that's guaranteed unique across the entire test, since no two VUs share a __VU number and no VU repeats an __ITER value.

Adding a Timestamp for Cross-Run Uniqueness

const runId = Date.now(); // captured once, outside the default function (init code)

export default function () {
  const uniqueEmail = `user-${runId}-${__VU}-${__ITER}@example.com`;
  // Unique within THIS run, and unlikely to collide with a PREVIOUS run's
  // leftover data, if cleanup didn't fully succeed last time
}

Adding a timestamp captured once at script load time (init code, from Chapter 2's lifecycle model) protects against collisions with data left over from a previous test run — genuinely useful if a system doesn't guarantee full cleanup between runs.

Detailed Example — Randomization for Non-Sequential Uniqueness

function randomString(length) {
  const chars = 'abcdefghijklmnopqrstuvwxyz0123456789';
  let result = '';
  for (let i = 0; i < length; i++) {
    result += chars.charAt(Math.floor(Math.random() * chars.length));
  }
  return result;
}

export default function () {
  const uniqueEmail = `user-${randomString(8)}@example.com`;
}

__VU/__ITER-based uniqueness is predictable and sequential — fine for most cases, but sometimes a test specifically needs data that doesn't reveal an obvious pattern (testing a system that might behave differently for sequential vs. genuinely random-looking input). Randomization achieves that, at the cost of needing a large enough random space that collisions remain vanishingly unlikely rather than guaranteed impossible.

Real-World Example — Why "Random" Isn't Automatically Collision-Free

❌ const id = Date.now(); // milliseconds since epoch
// Two VUs executing in the SAME millisecond generate the IDENTICAL "unique" ID
// — genuinely possible at high VU counts with fast-executing iterations

✅ const id = `${Date.now()}-${__VU}-${__ITER}`;
// Combining timestamp with guaranteed-unique VU/iteration context
// eliminates the collision risk entirely

This is a genuinely common mistake — a timestamp alone feels unique, but at real concurrency, two virtual users can execute the same line of code within the same millisecond, especially for fast, lightweight requests. Combining a timestamp with k6's guaranteed-unique __VU/__ITER context removes this risk entirely, rather than merely making it unlikely.

❌ Fragile vs. ✅ Recommended

// ❌ A single hardcoded value shared across every VU and iteration
const email = 'testuser@example.com';

// ✅ Genuinely unique per VU and iteration, using k6's execution context
const email = `user-${__VU}-${__ITER}-${Date.now()}@example.com`;

Common Mistakes

  • Reusing a single hardcoded value for anything the system treats as unique, across every VU and iteration.
  • Relying on a timestamp alone for uniqueness — genuinely possible to collide when multiple VUs execute within the same millisecond.
  • Using a random string that's too short for the actual scale of the test — a real, if small, collision probability at very high iteration counts with an insufficiently large random space.

Edge Cases

  • A test that needs to reuse the same identity across iterations for one VU but not across different VUs — capture the unique value once, outside the default function (relying on Chapter 2's per-VU init code behavior), rather than regenerating it every iteration.
  • A system with its own strict uniqueness rules beyond a simple string match (like a checksum-validated ID format) — uniqueness generation needs to also produce data that satisfies whatever format rules the target system actually enforces, not just be different from other generated values.

Debugging

If a test shows a high failure rate specifically on "create" operations (accounts, orders) under load but not at low concurrency, check whether the data being sent is actually unique per iteration — a collision-based failure often only appears once concurrency is high enough for the collision probability to become likely.

Best Practices

  • Combine __VU and __ITER as the foundation for guaranteed uniqueness within a single test run.
  • Add a run-level timestamp when protection against leftover data from previous runs matters.
  • Use genuine randomization only when sequential, predictable data specifically isn't appropriate for what's being tested — it adds real collision-probability math that __VU/__ITER combinations don't require.

Summary

Data meant to be unique in a performance test needs genuine, guaranteed uniqueness — not just data that looks different in a single example run. Combining k6's built-in __VU and __ITER values, optionally with a run-level timestamp, produces data that's mathematically guaranteed unique across an entire test, which a timestamp alone or an insufficiently large random value cannot promise.

Interview Questions

Why does a single hardcoded test value that works fine in a functional test break under performance testing?▾
A functional test typically runs a script once, sequentially — a hardcoded value never has to compete with itself. A performance test runs the same script hundreds or thousands of times, often simultaneously, so every virtual user attempting to use the identical value for something the system treats as unique (an email, a username) causes most of those attempts to fail with a duplicate error, changing what the test actually measures.
Why isn't Date.now() alone sufficient to guarantee unique data across virtual users?▾
Date.now() has millisecond resolution, and at real concurrency, multiple virtual users can execute the same line of code within the same millisecond — especially for fast, lightweight requests. This means two VUs can genuinely generate the identical "unique" timestamp-based value, causing exactly the collision the uniqueness was meant to prevent.
How do __VU and __ITER combine to guarantee uniqueness within a single test run?▾
__VU is k6's built-in identifier for the current virtual user, and no two VUs ever share the same value. __ITER is the current iteration number for that specific VU, and a single VU never repeats an __ITER value. Combining the two produces a value that's mathematically guaranteed unique across the entire test, since the combination of (VU number, iteration number) can never repeat.
Why might a test add a run-level timestamp on top of __VU and __ITER, even though those two already guarantee uniqueness within one run?▾
__VU and __ITER only guarantee uniqueness within a single test execution — if a previous run's test data wasn't fully cleaned up, a new run using the exact same __VU/__ITER combinations could collide with leftover data from before. A run-level timestamp, captured once at script load, protects against exactly this cross-run collision risk.
When might __VU/__ITER-based uniqueness actually be insufficient, requiring genuine randomization instead?▾
__VU/__ITER-based values are predictable and sequential in pattern — if a test specifically needs to verify system behavior against genuinely unpredictable, non-sequential input (testing whether a system behaves differently for obviously patterned versus organic-looking data, for instance), true randomization is more appropriate, accepting the tradeoff that it requires a sufficiently large random space to keep collision probability acceptably low rather than mathematically impossible.
