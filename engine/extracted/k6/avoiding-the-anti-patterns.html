Avoiding the Anti-Patterns

Prerequisites: The Recommended Folder Structure

What is this?

This page names the specific mistakes that turn a growing k6 project painful to maintain, each tied directly to a fix already covered somewhere in this course — this is a checklist, not new material.

Anti-Pattern 1 — Duplicated Code

❌ Three test files each independently constructing the same login request

✅ Fix (Chapter 3, formalized in this chapter's api/ layer):
   One shared function, imported everywhere it's needed

Symptom: a bug fix or API change requires editing several files instead of one. Every layer covered in this chapter exists specifically to prevent this.

Anti-Pattern 2 — Hardcoded URLs

❌ const baseUrl = 'https://staging-api.example.com'; // scattered across many files

✅ Fix (Chapter 9, centralized in config/):
   const config = environments[__ENV.TARGET_ENV] || environments.staging;

Symptom: switching environments means find-and-replace across the whole project, with a real risk of missing one file and accidentally testing the wrong target.

Anti-Pattern 3 — Hardcoded Credentials

❌ const apiKey = 'abc123secretkey'; // committed to version control, visible to anyone

✅ Fix (Chapter 9, via __ENV, injected at run time):
   const apiKey = __ENV.API_KEY;

Symptom: a genuine secret sitting in plain text in version control, visible to anyone with repository access, regardless of whether they should have credential access.

Anti-Pattern 4 — Shared Mutable State

❌ let sharedCounter = 0; // at module scope, mutated by every VU simultaneously
export default function () {
  sharedCounter++; // a genuine race condition — this isn't safe
}

✅ Fix (k6's own metric types, Chapter 6):
   const counter = new Counter('my_counter');
export default function () {
  counter.add(1); // k6's Counter handles concurrent updates safely
}

Symptom: a plain JavaScript variable shared across VUs and mutated directly is a genuine concurrency bug in the test script itself — exactly the kind of race condition Chapter 5 warned about in the system under test, except here it's a bug in the test's own code. k6's built-in metric types are specifically designed to handle concurrent updates safely; a plain shared variable is not.

Anti-Pattern 5 — Unrealistic Workloads

❌ vus: 5000 // "sounds like enough," no connection to any real number

✅ Fix (Chapter 4's workload modeling, Chapter 7's threshold derivation):
   A VU count and threshold derived from an actual business requirement,
   baseline, or SLA — never a guess.

Symptom: a test that either never fails (too lenient to ever catch a real regression) or always fails (too strict to ever pass, so the team learns to ignore it) — exactly the failure mode Chapter 7 covered in depth.

Anti-Pattern 6 — Giant Test Scripts

❌ One 800-line file mixing login logic, product browsing, cart management,
   checkout, data generation, and configuration all together

✅ Fix (this chapter's entire layered structure):
   The same logic, split across workflows/, api/, data/, config/, and utils/,
   each file small and focused

Symptom: understanding or safely changing any single piece of behavior requires reading through hundreds of unrelated lines first, and the risk of an unintended side effect from an edit grows with the file's size and lack of clear boundaries.

Common Mistakes

  • Fixing only one anti-pattern while leaving others in place — a project can have well-organized layers but still hardcode a credential, or use safe custom metrics but still duplicate request logic; the six patterns are independent, and each needs its own attention.
  • Assuming "we haven't hit a problem yet" means an anti-pattern is fine — a shared mutable state race condition might not manifest visibly until VU count crosses some specific threshold, by which point the test's own results may already be quietly unreliable.
  • Treating this as a one-time cleanup rather than an ongoing discipline — new code added later can just as easily reintroduce any of these patterns without deliberate review.

Edge Cases

  • A genuinely small, short-lived script where full anti-pattern avoidance feels like overkill — the same proportionality judgment from earlier chapters applies; a five-line, one-off diagnostic script doesn't need the full framework treatment a production suite does.
  • Legacy scripts inherited from before these practices were adopted — worth prioritizing which anti-patterns to fix first based on actual risk (hardcoded credentials and shared mutable state are usually the most urgent, since they carry real security or correctness risk, not just maintainability cost).

Debugging

If a k6 project has become genuinely hard to maintain, walk through this page's six anti-patterns as a literal checklist against the actual codebase — in most real, troubled projects, several of them are present simultaneously, and addressing them together (not just one) is usually necessary to see real improvement.

Best Practices

  • Review a project against all six anti-patterns periodically, not just once during initial setup.
  • Prioritize fixing hardcoded credentials and shared mutable state first — these carry genuine security and correctness risk, not just maintainability cost.
  • Apply proportional judgment — a small, short-lived script doesn't need the same rigor as a long-term production suite.

Summary

Duplicated code, hardcoded URLs, hardcoded credentials, shared mutable state, unrealistic workloads, and giant test scripts are the six specific patterns that turn a growing k6 project painful — and every one of them has a concrete fix already covered across this course: the layered structure from this chapter, __ENV-based configuration, k6's built-in metric types for safe concurrent measurement, and workload/threshold values grounded in real requirements rather than guesses. Reviewing a project against this checklist, deliberately and periodically, is what keeps a k6 suite maintainable as it grows.

Interview Questions

Why is a plain shared JavaScript variable, mutated directly across virtual users, genuinely unsafe in a k6 script?▾
Multiple virtual users executing concurrently can race to read and update the same plain variable, producing a genuine race condition within the test script itself — the same class of concurrency bug covered as a risk in the system under test, except here it's a bug in the test's own code. k6's built-in metric types (Counter, Rate, and the others) are specifically designed to handle concurrent updates safely, which a plain shared variable is not.
Why is hardcoding an API key directly in a script a more urgent problem than, say, duplicated request logic?▾
A hardcoded credential is a genuine security exposure — anyone with access to the script's source code, including anyone with repository access who shouldn't necessarily have credential access, gains the actual secret. Duplicated code is a real maintainability problem, but it doesn't carry the same immediate security risk, which is why hardcoded credentials generally warrant more urgent prioritization when reviewing a troubled project.
Why might an unrealistic, ungrounded VU count produce a test that "never fails," and why is that itself a problem?▾
A VU count picked arbitrarily, with no connection to real traffic patterns, could be set far below what the system would actually need to handle in production — a test that never approaches genuine stress will pass consistently regardless of real underlying problems, giving false confidence. This is the same core issue covered when discussing thresholds disconnected from reality: a test that can't meaningfully fail isn't actually providing useful information.
Why does this chapter describe these six anti-patterns as needing independent attention, rather than assuming fixing one automatically fixes the others?▾
A project can genuinely exhibit a well-organized folder structure (fixing duplicated code) while still hardcoding a credential, or use k6's safe custom metrics while still running an ungrounded, arbitrary workload — the six patterns address independent concerns (code organization, configuration, security, concurrency safety, workload realism, file structure), and progress on one doesn't guarantee progress on any of the others.
Why is it important to treat anti-pattern avoidance as an ongoing discipline rather than a one-time cleanup?▾
New code written after an initial cleanup can just as easily reintroduce any of these six patterns if there's no deliberate, ongoing review — a new test file added later might duplicate existing request logic instead of importing it, or a new script might hardcode a URL out of convenience. Without treating this as a continuing practice, the benefits of an initial cleanup erode gradually as a project keeps growing.
