Prerequisites: Performance Test Architecture & Framework Design

A Principle Already Mentioned Twice, Explained Properly

"The load generator must not become the bottleneck" came up in passing when covering SharedArray's memory efficiency, and again around resource contention between simultaneous scenarios. This chapter is where that principle gets its actual depth — how to recognize it happening, and when the fix is genuinely "use more than one machine." Two focused pages:

  1. Recognizing When the Load Generator Is the Bottleneck — the actual diagnostic skill, distinguishing your own infrastructure's limits from the system under test's
  2. Local vs. Distributed Execution & Geographic Distribution — when one machine is enough, and when it genuinely isn't

Why This Comes Near the End, Not the Beginning

Every technique in this course so far — workload modeling, thresholds, unique data, proper session handling, framework architecture — matters regardless of how many machines are generating the load. This chapter is specifically about what changes once a single machine's own resources genuinely can't produce the load a real test requires, which is a scale problem, not a technique problem.

A Quick Preview of the Core Confusion This Chapter Resolves

Observation: "Response times got worse as we increased VUs."

Question this chapter answers: Is that the SYSTEM UNDER TEST struggling
under genuine load — or is it the MACHINE RUNNING K6 running out of its
own CPU, memory, or network capacity, unable to generate the load it
was configured to generate?

These produce genuinely similar-looking symptoms from a distance, and confusing one for the other leads to investigating (or fixing) entirely the wrong system.

Common Mistakes to Watch For

  • Assuming degrading results always mean the target system is struggling, without checking whether the load generator itself is resource-constrained.
  • Reaching for distributed execution by default, when a single properly-sized machine would have been entirely sufficient for the actual required load.
  • Testing exclusively from one geographic location when real users are meaningfully distributed, missing latency characteristics that only show up from elsewhere.

What You'll Be Able to Do

By the end of the two pages that follow, you should be able to recognize the specific symptoms of a resource-constrained load generator, distinguish that from a genuine system-under-test bottleneck, and make a deliberate, informed decision about when local execution is sufficient versus when distributed or geographically-spread execution is actually necessary.
