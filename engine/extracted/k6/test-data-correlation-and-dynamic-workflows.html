A Problem Functional Testing Never Has to Solve

The workflow built in Chapter 5 used a single hardcoded test user. That's fine for one request — but run that same script with 200 concurrent virtual users, and every one of them tries to create an account with the identical email address. A functional test never hits this problem, because it typically runs once, sequentially. A performance test runs the same script hundreds or thousands of times, often simultaneously — and that changes what "test data" actually has to mean. Three focused pages:

  1. Unique Test Data & Avoiding Collisions — why identical data breaks under concurrency, and how to avoid it
  2. Parameterization: CSV, JSON & SharedArray — feeding real external data sets to many VUs efficiently
  3. Building the Full CRUD Chain With Real Data — Create → Get → Update → Delete, done correctly at scale

Why Performance-Test Data Needs Different Design

Functional-test data optimizes for clarity and repeatability — the same known input, every time, so a failure is easy to reproduce. Performance-test data optimizes for something different: enough genuine variety and uniqueness that hundreds of simultaneous virtual users don't collide with each other or with themselves, while still remaining realistic enough that the load actually represents how real, distinct users behave. These are genuinely different goals, and data designed well for one can actively break the other.

A Quick Preview of the Core Problem

// ❌ Fine for a single functional test. Breaks under concurrent load.
const payload = JSON.stringify({ email: 'testuser@example.com', name: 'Test User' });

// 200 VUs running this simultaneously → 200 attempts to create the
// exact same account → most fail with a duplicate-email error, and the
// test is now measuring error-handling, not the create-account flow

This is the exact problem the first page ahead solves properly — not by working around it, but by generating data that's genuinely unique per iteration.

Common Mistakes to Watch For

  • Reusing a single hardcoded value across many virtual users for anything meant to be unique — emails, usernames, order references.
  • Loading a large external data file inefficiently, duplicating it in memory once per VU instead of sharing it — a real problem at high VU counts.
  • Generating "random" data that isn't actually random enough to avoid collisions at real scale, like a timestamp-only ID that two VUs can generate in the same millisecond.
