Tags & Environment Variables

Prerequisites: Advanced k6 Test Design overview

What is this?

Two genuinely new, practical tools: tags let you label requests and metrics for meaningful filtering afterward, and environment variables let you configure a test — which environment it targets, what credentials it uses — without editing the script itself every time.

Tags — Labeling Requests for Later Filtering

http.get('https://api.example.com/products', {
  tags: { endpoint: 'products', workflow: 'browse' },
});

http.post('https://api.example.com/checkout', payload, {
  tags: { endpoint: 'checkout', workflow: 'purchase' },
});

Every request can carry custom tags — arbitrary key-value labels attached to that request's metrics. In result output and external dashboards (Grafana, covered in Chapter 13), these tags let you break down http_req_duration or http_req_failed by whichever dimension actually matters — by endpoint, by workflow stage, by user type — rather than only ever seeing one undifferentiated aggregate.

Tags on Groups and Checks Too

group('Checkout', function () {
  // requests inside automatically inherit the group name as a tag
});

check(response, { 'status ok': (r) => r.status === 200 }, { workflow: 'checkout' });

group() already provides automatic tagging by group name (which is part of why group() from Chapter 3 is useful for more than just code organization — it feeds directly into this filtering capability). Explicit tags can be added to checks too, for the same kind of after-the-fact segmentation.

Environment Variables — Configuring From Outside the Script

$ k6 run -e ENVIRONMENT=staging -e VUS=50 script.js
// Inside the script:
const baseUrl = __ENV.ENVIRONMENT === 'production'
  ? 'https://api.example.com'
  : 'https://staging-api.example.com';

const vuCount = Number(__ENV.VUS) || 10; // fallback default

export const options = {
  vus: vuCount,
  duration: '5m',
};

__ENV gives a script access to values passed in via the -e flag at run time — this is what lets the exact same script target staging or production, or run at different VU counts, without ever editing the script's own source code. This becomes essential once a script runs in CI/CD (Chapter 13), where the same script typically needs to run against different environments depending on the pipeline stage.

Detailed Example — A Fully Configurable Script

const environments = {
  staging: 'https://staging-api.example.com',
  production: 'https://api.example.com',
};

const baseUrl = environments[__ENV.TARGET_ENV] || environments.staging;
const apiKey = __ENV.API_KEY; // a real secret, never hardcoded

export default function () {
  http.get(`${baseUrl}/products`, {
    headers: { 'X-API-Key': apiKey },
    tags: { endpoint: 'products' },
  });
}
$ k6 run -e TARGET_ENV=production -e API_KEY=$SECRET_KEY script.js

This is the correct way to handle a secret like an API key — read from __ENV, sourced from an actual environment variable or CI/CD secret at run time, never hardcoded directly in the committed script, exactly the practice Chapter 9 flagged as necessary for OAuth client credentials.

Real-World Example — Using Tags to Diagnose a Multi-Endpoint Problem

Aggregate result: http_req_duration p95 = 890ms — something's off, but where?

Filtered by tag:
  { endpoint: 'products' }: p95 = 210ms   ✓ fine
  { endpoint: 'checkout' }: p95 = 3,200ms  ← the actual problem

Without tags, this diagnosis would require re-running the test with only one endpoint at a time, or manually correlating timestamps — with tags, the same single test run's data can be filtered after the fact to immediately isolate exactly which part of the system is actually responsible for a poor aggregate result.

❌ Fragile vs. ✅ Recommended

// ❌ A hardcoded target URL and secret, requiring a script edit for every environment
const baseUrl = 'https://staging-api.example.com';
const apiKey = 'abc123secretkey';

// ✅ Configured from outside, no script edit needed to change environment or secret
const baseUrl = __ENV.TARGET_ENV === 'production' ? prodUrl : stagingUrl;
const apiKey = __ENV.API_KEY;

Common Mistakes

  • Hardcoding environment URLs and secrets directly in a script — requires an edit (and a risk of accidentally committing a secret) every time the target needs to change.
  • Never tagging requests in a multi-endpoint or multi-workflow test — makes after-the-fact result analysis far harder than it needs to be.
  • Forgetting a fallback default for an environment variable that might not always be provided — __ENV.VUS is undefined if -e VUS=... wasn't passed, which can silently break a calculation downstream without a sensible default.

Edge Cases

  • An environment variable that's always a string — __ENV values are always strings, even if the value looks numeric; explicit conversion (like Number(__ENV.VUS)) is needed before using it in numeric configuration.
  • Too many distinct tag combinations — tagging every request with a highly unique value (like a full request ID) can produce an unmanageable number of distinct series in an external dashboard; tags work best as a small number of meaningful, reusable categories, not unique-per-request identifiers.

Debugging

If a test behaves unexpectedly differently than intended (wrong environment, wrong VU count), check whether an expected environment variable was actually passed via -e and whether the script has a sensible fallback for when it's missing — a silently undefined __ENV value is a common, easy-to-miss cause of unexpected test behavior.

Best Practices

  • Configure environment targets and secrets via __ENV, never hardcoded directly in the script.
  • Tag requests by meaningful category (endpoint, workflow stage) to enable after-the-fact filtering, without over-tagging into unmanageably specific categories.
  • Always provide a sensible fallback default for any environment variable a script depends on.

Practice Exercise

Modify a script to accept the target environment, a VU count, and an API key all via environment variables, with sensible fallback defaults for each, and add tags distinguishing requests made during a "browse" phase versus a "checkout" phase.

Summary

Tags attach meaningful, filterable labels to requests, groups, and checks, letting a single test run's results be broken down by whatever dimension actually matters afterward — endpoint, workflow stage, user type. Environment variables, accessed via __ENV, let a script's target environment, load level, and secrets be configured from outside its own source code, which is essential for a script that needs to run consistently across different environments, especially once it's running inside CI/CD.

Interview Questions

Why are tags useful even in a test that already uses group() for organization?▾
group() provides automatic tagging by group name, which is useful, but explicit tags allow finer-grained or cross-cutting categorization that a group hierarchy alone might not capture — like tagging by endpoint, user type, or workflow stage independently of how the script happens to be structured into groups. Tags give more deliberate control over exactly which dimension of a result you want to filter by afterward.
Why should a script read its target environment and API credentials from __ENV rather than hardcoding them?▾
Hardcoding requires editing the script's own source code every time the target environment or credential needs to change, and risks accidentally committing a real secret into version control. Reading from __ENV lets the exact same script run against staging, production, or any other target, and receive secrets injected safely at run time — critical once the script runs inside a CI/CD pipeline that needs to target different environments at different stages.
Why does a value like __ENV.VUS need explicit conversion before being used in numeric configuration?▾
Every value accessed via __ENV is always a string, regardless of what it looks like — passing -e VUS=50 makes __ENV.VUS equal to the string "50", not the number 50. Using it directly in numeric configuration (like a VU count) without explicit conversion (Number(__ENV.VUS)) can produce unexpected behavior, since JavaScript's type coercion in that context doesn't always behave the way a raw number would.
Why might tagging every single request with a unique identifier actually be counterproductive?▾
Tags are most useful as a small number of meaningful, reusable categories that group many requests together for analysis — like "endpoint: checkout" applying to every checkout request. Tagging with a highly unique value per request (a full request ID, for instance) produces an enormous number of distinct series in results or dashboards, defeating the purpose of tags as an aggregation and filtering tool rather than a per-request identifier.
How do tags help diagnose a problem in a test covering multiple endpoints or workflow stages within a single run?▾
Without tags, a poor aggregate result (like an elevated p95) only tells you something is wrong somewhere in the test, requiring separate runs or manual correlation to isolate which part. With requests tagged by endpoint or workflow stage, the same single test run's data can be filtered after the fact to immediately see which specific tagged category is actually responsible for the poor result, without needing to re-run anything.
