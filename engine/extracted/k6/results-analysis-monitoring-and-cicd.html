Reading k6's own output correctly was Chapter 6's job. Why This Is the Second-to-Last Chapter

Everything covered here — dashboards, correlation, automation — depends directly on having a genuinely well-built script and framework (Chapter 11) to actually run. This is where that investment starts paying off concretely, immediately before the capstone project pulls every single piece of this course together into one real, production-style project.

A Quick Preview of the Correlation This Chapter Teaches

k6 metrics (Chapter 6)  →  Application metrics  →  Infrastructure metrics  →  Bottleneck
"checkout is slow"          "checkout service        "database CPU at 95%
                              CPU at 90%"               during checkout calls"

k6 alone can tell you that something is slow. Correlating its metrics against what the application and infrastructure were actually doing at the same moment is what tells you why — and that "why" is the actual, actionable finding a performance test exists to produce.

Common Mistakes to Watch For

  • Only ever looking at k6's own terminal output, never correlating it against what the target system's own monitoring showed at the same time.
  • Running performance tests only manually, as an occasional, easy-to-forget task, instead of automatically on a schedule or on every relevant change.
  • Having a CI pipeline run k6 but never actually gating the build on its results — collecting data nobody automatically acts on, the same gap covered when comparing checks and thresholds.
