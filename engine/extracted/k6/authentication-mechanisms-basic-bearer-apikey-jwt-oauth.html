Authentication Mechanisms: Basic, Bearer, API Key, JWT, OAuth

Prerequisites: Authentication, Sessions & Realistic User Journeys overview

What is this?

Bearer tokens have already appeared in code examples throughout this course, without being named as one option among several. This page covers every common authentication mechanism as its own distinct pattern, with real k6 syntax for each.

Basic Authentication

const credentials = `${btoa('username:password')}`;

http.get('https://api.example.com/profile', {
  headers: { Authorization: `Basic ${credentials}` },
});

Basic Auth sends a base64-encoded username and password directly in the Authorization header, on every single request. It's simple but genuinely insecure without HTTPS (base64 is trivially decodable, not encryption) — still found in internal tools and simpler APIs, but rare in anything customer-facing today.

Bearer Tokens

http.get('https://api.example.com/profile', {
  headers: { Authorization: `Bearer ${token}` },
});

The pattern used throughout this course so far — a token, typically obtained from a login endpoint, sent in the Authorization header on every subsequent request. This is the most common modern pattern for API authentication.

API Keys

// Header-based
http.get('https://api.example.com/data', {
  headers: { 'X-API-Key': apiKey },
});

// Query-parameter-based
http.get(`https://api.example.com/data?api_key=${apiKey}`);

API keys identify the calling application or account, often with no separate login step at all — the key itself is the credential, issued once (typically outside the test, from a developer portal or admin panel) and used directly. Common for third-party integrations and public APIs.

JWT — What's Actually Inside a Bearer Token

// A JWT has three base64-encoded parts, separated by dots:
// header.payload.signature

function decodeJwtPayload(token) {
  const payload = token.split('.')[1];
  return JSON.parse(atob(payload));
}

const decoded = decodeJwtPayload(token);
console.log(decoded.exp); // expiration timestamp, if present

A JWT (JSON Web Token) is a specific, structured format many bearer tokens actually use — decoding the payload (no cryptographic verification needed for this, just reading the structure) can reveal useful information like an expiration timestamp, directly relevant to the token-expiration handling covered on the next page.

OAuth 2.0 Concepts, Applied to k6

// Client Credentials flow — common for service-to-service auth, no user involved
function getOAuthToken() {
  const response = http.post('https://auth.example.com/oauth/token',
    'grant_type=client_credentials&client_id=' + clientId + '&client_secret=' + clientSecret,
    { headers: { 'Content-Type': 'application/x-www-form-urlencoded' } });
  return response.json('access_token');
}

Full OAuth flows involving a real user's browser redirect aren't something k6 can (or should try to) simulate directly — but the Client Credentials flow, used for service-to-service authentication with no human interaction, maps directly onto a k6 script exactly like any other login-then-use-token pattern.

Detailed Example — Choosing the Right Mechanism for a Test

Target system uses:        Use in k6:
Basic Auth                 Authorization: Basic header, base64-encoded
Bearer token from login     POST to login, extract token, Bearer header
Static API key              Header or query param, no login step needed
OAuth Client Credentials    POST to token endpoint, extract access_token

The right approach isn't a choice you make — it's determined entirely by what the target system actually requires. Identifying which mechanism a real system uses (from its documentation, or by inspecting real traffic) is the first real step before writing any authentication code at all.

Real-World Example — A System Using Both API Keys and Bearer Tokens

function callApi(userToken) {
  http.get('https://api.example.com/orders', {
    headers: {
      'X-API-Key': staticServiceKey,       // identifies the calling application
      Authorization: `Bearer ${userToken}`, // identifies the specific user
    },
  });
}

This is a genuinely common real-world pattern — an API key identifying which application is calling (for rate limiting or billing purposes), combined with a user-specific bearer token identifying which actual user is making the request. Both are needed together, serving different purposes.

❌ Fragile vs. ✅ Recommended

// ❌ Guessing at an auth mechanism without checking what the system actually requires
http.get(url, { headers: { Authorization: `Bearer ${somethingGuessed}` } });

// ✅ Implementing the mechanism the target system's documentation actually specifies
http.get(url, { headers: { 'X-API-Key': realApiKey } }); // if that's what's documented

Common Mistakes

  • Assuming every API uses bearer tokens without checking what the specific target system actually requires.
  • Decoding a JWT and trusting its contents without considering that verification (signature checking) is a separate concern — reading the payload for useful info like expiration is fine; treating unverified claims as authoritative is not, though for test purposes reading is usually all that's needed.
  • Hardcoding OAuth client credentials directly in a script committed to version control — these are genuine secrets and should be handled the way any sensitive credential is (environment variables, a secrets manager), covered further in Chapter 13's CI/CD material.

Edge Cases

  • A system requiring multiple authentication factors together (an API key AND a bearer token, as shown above) — don't assume a single mechanism when the real system genuinely requires more than one simultaneously.
  • A JWT with no expiration claim at all — not every JWT includes an exp field; token-expiration handling (next page) needs to account for tokens that simply don't expire, or that expire via a mechanism other than an embedded timestamp.

Debugging

If every request in a test fails with a 401 despite what looks like correct authentication code, verify the target system's actual expected mechanism directly (documentation, or inspecting a real successful request from a browser's network tab) rather than assuming the most common pattern (bearer tokens) is automatically correct for this specific system.

Best Practices

  • Confirm the target system's actual authentication mechanism before writing any auth code, rather than assuming the most common pattern.
  • Handle secrets (API keys, OAuth client credentials) the same way any sensitive credential should be handled — never hardcoded directly in a script.
  • Remember a real system may require more than one authentication mechanism simultaneously.

Practice Exercise

For a hypothetical system requiring an OAuth Client Credentials token that must then be sent as a Bearer token on every subsequent request, write the k6 code to obtain that token once and use it correctly across multiple requests.

Summary

Basic Auth, Bearer tokens, API keys, JWTs, and OAuth Client Credentials each represent a genuinely different authentication pattern, and which one (or combination) to implement in k6 is determined entirely by what the target system actually requires — never assumed. A JWT's structure can be decoded (without cryptographic verification) to read useful information like an expiration claim, directly setting up the token-expiration handling covered next.

Interview Questions

Why is Basic Authentication generally considered less secure than a bearer token pattern?▾
Basic Auth sends a base64-encoded username and password on every single request — base64 encoding is trivially reversible, not encryption, so this relies entirely on the transport layer (HTTPS) for any real protection, and the actual credentials are transmitted repeatedly. A bearer token, by contrast, is typically a separate, often short-lived credential obtained once via a login step, limiting exposure of the actual underlying password.
What's actually inside a JWT, and why might decoding it matter for a k6 test?▾
A JWT consists of three base64-encoded, dot-separated parts — a header, a payload, and a signature. The payload often contains useful claims like an expiration timestamp (exp). Decoding just the payload (without cryptographic signature verification, which isn't necessary for reading this information in a test context) lets a k6 script proactively check when a token will expire, directly relevant to handling token expiration in a longer-running test.
Why might a real system require both an API key and a bearer token on the same request?▾
These serve different purposes — an API key typically identifies which application or client is making the call (useful for rate limiting or billing at the application level), while a bearer token identifies which specific authenticated user is making the request. A system might need both pieces of information simultaneously, requiring a k6 script to send both headers together rather than assuming only one mechanism applies.
Why is the OAuth Client Credentials flow more directly applicable to k6 testing than a full OAuth authorization code flow?▾
Client Credentials is designed for service-to-service authentication with no human user or browser involved — it's a straightforward POST request that returns a token, fitting naturally into k6's request-based scripting model. A full authorization code flow involves a real user's browser being redirected through a login and consent screen, which isn't something a k6 script is designed to simulate directly, since k6 operates at the HTTP request level, not as a browser.
Why shouldn't OAuth client credentials or API keys be hardcoded directly into a k6 script committed to version control?▾
These are genuine secrets — anyone with access to the script's source code (including anyone with repository access, even if not intended to have credential access) would gain the actual credential. The correct approach is handling them the way any sensitive credential should be handled: environment variables, a secrets manager, or a CI/CD platform's secret-injection mechanism, none of which exposes the actual value in the committed source code itself.
