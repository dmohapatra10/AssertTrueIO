Built-in HTTP Metrics Explained

Prerequisites: Checks, Metrics & Results overview

What is this?

k6 automatically tracks a specific set of metrics for every HTTP request, with no configuration required. This page covers what each one precisely measures — not a vague "duration" and "requests," but a set of genuinely distinguishable measurements.

http_req_duration — And Its Component Phases

http_req_duration = http_req_connecting + http_req_waiting + http_req_receiving
  • http_req_connecting — time spent establishing the TCP connection itself.
  • http_req_waiting — time spent waiting for the server to start responding, once the request was sent — often called "time to first byte." This is usually the phase most directly reflecting actual server-side processing time.
  • http_req_receiving — time spent actually downloading the response body once it started arriving.

http_req_duration is the sum of these — the full request/response cycle. Breaking it into these component phases matters for diagnosis: a slow http_req_connecting points toward a network or connection-establishment problem, while a slow http_req_waiting points toward the server itself being slow to process the request — genuinely different problems needing genuinely different fixes.

http_req_failed — The Error Rate Metric

http_req_failed: 0.42%  ✓ 2103   ✗ 9

http_req_failed reports the percentage (and count) of requests k6 considers to have failed — by default, this means non-2xx/3xx status codes or requests that failed at the network level entirely (a timeout, a connection refused). This is the direct, built-in implementation of the "error rate" concept from Chapter 1, now as a real, reportable k6 metric.

http_reqs — Raw Throughput

http_reqs: 2112   35.2/s

http_reqs reports the total count of HTTP requests made, and the rate per second — this is k6's direct implementation of the "requests per second" concept from Chapter 1. Note this counts every individual HTTP request, which (as covered in Chapter 4) is not the same as the iteration count if a single iteration makes more than one request.

vus and vus_max

vus: 50   min=50   max=50

vus reports the number of active virtual users at the point the summary was generated (or, in the min/max form, the range over the whole test); vus_max reports the maximum number of VUs the test was ever configured to reach — useful for confirming a ramping or arrival-rate test actually reached its intended peak, not just what it happened to be running at the final instant.

iterations

iterations: 2112   35.2/s

iterations reports the total count of complete passes through the default function, and the rate per second — distinct from http_reqs whenever an iteration contains more than one HTTP request, exactly the distinction covered in Chapter 4.

Detailed Example — Reading a Full Summary Correctly

http_req_duration..............: avg=245ms min=89ms med=210ms max=3.2s p(90)=380ms p(95)=520ms
  { expected_response:true }...: avg=240ms min=89ms med=208ms max=1.1s p(90)=375ms p(95)=510ms
http_req_connecting.............: avg=12ms  min=1ms  med=8ms   max=180ms
http_req_waiting.................: avg=225ms min=75ms med=195ms max=3.0s
http_req_receiving...............: avg=8ms   min=2ms  med=6ms   max=95ms
http_req_failed...................: 0.42%  ✓ 2103   ✗ 9
http_reqs..........................: 2112   35.2/s
iterations..........................: 2112   35.2/s
vus...................................: 50     min=50   max=50

Reading this together: total request duration (245ms average) is dominated by http_req_waiting (225ms average) — meaning the time is overwhelmingly spent on the server actually processing the request, not on connection setup or downloading the response. Combined with a 0.42% failure rate and a max of 3.2 seconds against a median of 210ms, this points toward a small number of individually slow or failing requests, worth investigating specifically, rather than a uniformly slow system.

Real-World Example — Diagnosing With the Component Phases

http_req_connecting: avg=380ms  ← unusually high
http_req_waiting:    avg=45ms   ← fine
http_req_receiving:  avg=5ms    ← fine

Here, nearly all the time is in http_req_connecting, not http_req_waiting — this points specifically toward a connection-establishment problem (DNS resolution, TCP handshake overhead, TLS negotiation, or possibly hitting a connection pool limit), not slow server-side processing. Optimizing application code here would be effort spent in the wrong place entirely; the component-phase breakdown is what makes that clear immediately rather than requiring separate investigation.

❌ Fragile vs. ✅ Recommended

// ❌ Only looking at the top-line http_req_duration number
"avg=245ms" — fine, but doesn't say WHERE the time is actually going

// ✅ Reading the component phases together for real diagnosis
http_req_connecting=12ms, http_req_waiting=225ms, http_req_receiving=8ms
→ time is dominated by server processing, not network setup

Common Mistakes

  • Treating http_req_duration as an atomic, undifferentiated number — missing the diagnostic value of its three component phases.
  • Confusing iterations with http_reqs — these are only equal when every iteration makes exactly one request.
  • Forgetting to check vus_max against the intended peak — a ramping test that never actually reached its configured target VU count would show this clearly, but only if you look.

Edge Cases

  • A high http_req_receiving specifically — usually points toward a large response body or a slow network on the download side, distinct from either connection setup or server processing time.
  • Requests that fail before any response phase begins (a connection refused, a DNS failure) — these show up in http_req_failed but may not have meaningful values for the duration sub-metrics at all, since the request never got far enough to measure them.

Debugging

If overall response time looks poor but it's unclear why, break it down into http_req_connecting, http_req_waiting, and http_req_receiving before investigating further — this single step usually narrows the problem to a specific layer (network setup, server processing, or response download) immediately.

Best Practices

  • Read http_req_duration's component phases together, not just the top-line total, when actually diagnosing a problem.
  • Cross-check vus_max against your test's intended peak to confirm a ramping or arrival-rate test actually reached its target.
  • Remember iterations and http_reqs are only equal for single-request-per-iteration scripts — check your actual script before assuming otherwise.

Practice Exercise

Given a summary showing http_req_connecting averaging 5ms, http_req_waiting averaging 1,800ms, and http_req_receiving averaging 12ms, write a one-sentence diagnosis of where the actual problem most likely lies, and what kind of investigation should follow.

Summary

http_req_duration is the sum of three distinguishable phases — connecting, waiting, and receiving — each pointing toward a genuinely different layer of the system when something is slow. http_req_failed is k6's direct error-rate metric, http_reqs is raw throughput, and vus/vus_max/iterations round out the picture of exactly how much load was generated and sustained. Reading these together, not just the top-line duration average, is what turns a k6 summary into an actual diagnostic tool.

Interview Questions

What are the three phases that make up http_req_duration, and why does breaking them apart matter?▾
http_req_duration is the sum of http_req_connecting (TCP connection setup), http_req_waiting (time waiting for the server to start responding, roughly server processing time), and http_req_receiving (time downloading the response body). Breaking these apart matters because each points toward a genuinely different layer of the system — a slow connecting phase suggests a network or connection-pool issue, while a slow waiting phase suggests the server itself is slow, requiring completely different investigation and fixes.
How does http_req_failed determine whether a request counts as failed?▾
By default, http_req_failed considers a request failed if it returns a non-2xx/3xx status code, or if it fails at the network level entirely (a timeout, a connection refused, and similar). This is k6's direct, built-in implementation of the error rate concept — a request that returns quickly but with an error status still counts against this metric, since a fast failure is still a failure.
Why isn't iterations always equal to http_reqs?▾
An iteration is one complete pass through the default function, which can contain any number of actual HTTP requests depending on what that function does. The two metrics are only equal when every iteration makes exactly one HTTP request — a script making three requests per iteration will show an http_reqs count three times higher than its iterations count.
Why would you check vus_max after running a ramping-vus test?▾
vus_max reports the maximum number of virtual users the test was ever configured to reach — checking it confirms the test actually achieved its intended peak concurrency, rather than assuming it did just because the test completed without an explicit error. A ramping test that was interrupted, misconfigured, or hit some resource constraint might never have actually reached its intended target, and vus_max is the direct way to verify that.
If http_req_connecting shows an unusually high average while http_req_waiting and http_req_receiving both look normal, what does that suggest?▾
It suggests the problem lies specifically in establishing connections — possibly DNS resolution delays, TLS handshake overhead, or the system hitting a connection pool or concurrent-connection limit — rather than in how the server processes requests once connected or how large the responses are. This would redirect investigation toward network and connection-layer configuration rather than application code, which the waiting and receiving metrics would otherwise (correctly) implicate if they were the ones showing elevated values instead.
