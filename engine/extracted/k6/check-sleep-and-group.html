check(), sleep(), and group()

Prerequisites: Making HTTP Requests: GET, POST, PUT, PATCH, DELETE

What is this?

Sending requests alone doesn't make a meaningful test — these three functions are what turn a sequence of HTTP calls into something that actually verifies correctness, behaves like a realistic user, and stays organized as a script grows.

check() — Verifying a Response

import { check } from 'k6';

const response = http.get('https://test-api.example.com/products');

check(response, {
  'status is 200': (r) => r.status === 200,
  'response has products': (r) => r.json().length > 0,
});

check() takes a response and an object of named conditions, each a function returning true or false. Every check is reported independently in k6's output — a named check that fails is immediately identifiable, rather than the test just generically "not working." This is the single most important function for making a performance test actually validate something, not just generate load blindly.

check() Failures Don't Stop the Test

This is a genuinely important distinction from how assertions typically work in functional testing: a failed check() in k6 does not stop script execution or fail the iteration outright — it's recorded as a failed check, and the script continues. This is deliberate: a performance test needs to keep generating load even if some checks are failing, since stopping entirely the moment one request looks wrong would defeat the purpose of sustained load generation. Thresholds (Chapter 7) are the mechanism that turns a check failure rate into an actual pass/fail signal for the whole test.

sleep() — Realistic Pacing

import { sleep } from 'k6';

export default function () {
  http.get('https://test-api.example.com/products');
  sleep(2); // pause for 2 seconds, simulating a user reading the page
  http.get('https://test-api.example.com/products/500');
}

sleep() pauses execution for a given number of seconds. Without any sleep, a virtual user hammers the target system with requests back-to-back as fast as possible — which is almost never how a real user actually behaves. Real users read, think, scroll, and hesitate between actions; sleep() is what makes simulated traffic resemble that instead of an unrealistic, unbroken burst.

Why Sleep Duration Actually Matters for Test Validity

// No sleep at all — unrealistic; produces far more load than real users ever would
export default function () {
  http.get(url); // repeated as fast as physically possible, no pause
}

// Realistic pacing
export default function () {
  http.get(url);
  sleep(Math.random() * 3 + 1); // 1-4 seconds, mimicking natural variation
}

A script with no sleep at all doesn't just look unrealistic — it produces a fundamentally different, exaggerated load pattern that doesn't represent how real traffic would actually hit the system, which can make your test's results genuinely misleading rather than just imprecise.

group() — Organizing Related Requests

import { group } from 'k6';

export default function () {
  group('Browse Products', function () {
    http.get('https://test-api.example.com/products');
    http.get('https://test-api.example.com/products/500');
  });

  group('Checkout', function () {
    http.post('https://test-api.example.com/cart/checkout', payload);
  });
}

group() wraps related requests together under a named label, which then appears in k6's output as its own reportable section — letting you see performance metrics broken down by logical workflow step ("Browse Products" vs. "Checkout") rather than one undifferentiated pile of every request the whole script made.

Detailed Example — All Three Together in a Realistic User Journey

import http from 'k6/http';
import { check, sleep, group } from 'k6';

export default function () {
  group('Browse', function () {
    const response = http.get('https://test-api.example.com/products');
    check(response, { 'browse succeeded': (r) => r.status === 200 });
    sleep(2);
  });

  group('View Product Detail', function () {
    const response = http.get('https://test-api.example.com/products/500');
    check(response, { 'product detail loaded': (r) => r.status === 200 });
    sleep(3);
  });

  group('Add to Cart', function () {
    const response = http.post('https://test-api.example.com/cart',
      JSON.stringify({ productId: 500, quantity: 1 }),
      { headers: { 'Content-Type': 'application/json' } });
    check(response, { 'added to cart': (r) => r.status === 201 });
  });
}

This reads almost like a narrative of a real user's session — browse, view a product, add it to cart — with each step verified and paced realistically, and grouped so the eventual results clearly show which stage of the journey performs well and which doesn't.

Real-World Example — Diagnosing Which Step Is Actually Slow

Without groups: overall p95 = 1.2s (which step is slow? unclear)

With groups:
  Browse............: p95=180ms
  View Product Detail: p95=210ms
  Add to Cart........: p95=3.1s  ← the actual problem, isolated clearly

This is the real, practical payoff of group() — without it, a slow overall result tells you something is wrong somewhere in the whole script; with it, you immediately know which specific step of the user journey is actually the bottleneck, without needing to manually correlate timestamps or guess.

❌ Fragile vs. ✅ Recommended

// ❌ No checks, no sleep, no groups — load with zero verification, unrealistic pacing
export default function () {
  http.get(url);
  http.post(url2, body);
}

// ✅ Verified, realistically paced, and organized
export default function () {
  group('Step 1', function () {
    const r = http.get(url);
    check(r, { 'ok': (r) => r.status === 200 });
    sleep(1);
  });
}

Common Mistakes

  • Writing a script with zero check() calls — generates load without verifying anything, which can run against a broken endpoint indefinitely without ever reporting a problem.
  • Omitting sleep() entirely — produces an unrealistic, unbroken burst of requests that doesn't represent real user behavior, skewing what the test actually measures.
  • Not using group() in a multi-step script — makes it much harder to identify which specific step is actually slow when results come back generically poor.
  • Assuming a failed check() stops the test — it doesn't; thresholds (Chapter 7) are the actual mechanism for turning check failures into a pass/fail test result.

Edge Cases

  • A check() condition that throws an exception rather than returning false — this is treated as a failed check, but debugging why it threw requires looking at the actual error, not just the check's pass/fail count.
  • Nested groups — k6 supports groups within groups for deeply structured workflows, though excessive nesting can make results harder to read rather than easier.

Debugging

If overall test results look poor but it's unclear why, add group() around each logical step of the script before investigating further — this alone often immediately reveals which specific part of a multi-step workflow is actually the problem, without any other diagnostic work.

Best Practices

  • Include at least one meaningful check() for every request that matters to the test's purpose.
  • Use realistic, varied sleep durations (not a single fixed value) to better mimic genuine user behavior.
  • Wrap logically distinct steps of a multi-request script in group(), especially once a script has more than two or three requests.

Practice Exercise

Take the "no checks, no sleep, no groups" example from this page and rewrite it into a realistic three-step user journey (browse, view detail, purchase), adding appropriate checks, realistic sleep pacing, and named groups for each step.

Summary

check() verifies a response without stopping the test on failure (thresholds handle the pass/fail decision), sleep() paces a script to resemble realistic user behavior instead of an unbroken burst, and group() organizes related requests so results can be broken down by logical workflow step rather than one undifferentiated pile. Together, these three functions are what turn "a script that sends requests" into a genuinely meaningful performance test.

Interview Questions

Why doesn't a failed check() stop a k6 test's execution?▾
A performance test needs to keep generating load even when some individual checks are failing, since the whole point is measuring sustained behavior under load — stopping entirely at the first failure would defeat that purpose. Instead, k6 records the failure and continues; thresholds (covered in a later chapter) are the actual mechanism that turns an accumulated check failure rate into a genuine pass/fail decision for the test as a whole.
Why does omitting sleep() from a script produce misleading test results, not just an unrealistic-looking one?▾
Without sleep(), a virtual user sends requests back-to-back as fast as physically possible, which almost never matches how real users actually behave — they read, think, and pause between actions. This produces a fundamentally different, exaggerated load pattern than real traffic would generate, meaning the test's results describe a scenario that doesn't actually represent genuine usage, not just a cosmetically unrealistic one.
What practical problem does group() solve that check() and sleep() don't address?▾
check() verifies correctness and sleep() paces requests realistically, but neither helps you understand WHICH part of a multi-step script is actually performing poorly when overall results look bad. group() breaks results down by logical workflow step, so a slow overall test immediately points to a specific stage (like "Checkout" specifically, not the whole script generically) rather than requiring manual investigation to isolate the problem.
If a check() condition function throws an exception instead of returning false, what happens?▾
It's treated as a failed check, similar to a condition that explicitly returns false — but the underlying cause is different, and diagnosing it requires looking at the actual thrown error rather than just noting that the check failed. This is worth knowing specifically because a check written carelessly (assuming a field always exists on a response, for instance) can fail via an exception rather than a clean false, which looks the same in the pass/fail count but needs different debugging.
Why might you use a randomized sleep duration instead of a single fixed value?▾
Real users don't all pause for exactly the same amount of time between actions — some read quickly, others slowly. A fixed sleep duration across every virtual user produces an artificially synchronized pattern of requests that doesn't reflect the natural variation in real traffic, while a randomized range (like 1 to 4 seconds) better approximates how genuine user behavior is actually distributed.
