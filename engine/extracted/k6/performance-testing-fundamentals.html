Building the Vocabulary Before Touching k6

Performance testing answers a question functional testing never asks: not "does this feature work," but "does it still work correctly and fast enough when many people use it at once, or when it's pushed harder than usual." Before touching k6 itself, here's the vocabulary and mental models everything later assumes you already have — across five focused pages:

  1. Load, Stress, Spike, Soak & Volume Testing — the five core test types, and when each answers a genuinely different question
  2. Baseline, Capacity & Scalability Testing — knowing what "normal" is, and what happens when you add resources
  3. Response Time, Throughput, Latency & Concurrency — the four measurements everything else builds on
  4. Percentiles & Reading Performance Data — why an average can lie, and how p95/p99 tell the truth
  5. SLAs, SLOs, SLIs & Virtual Users — turning a business requirement into an actual, testable target

Why Vocabulary Comes Before Syntax

k6's actual API surface — http.get(), check(), options — is genuinely small and learnable in an afternoon. What takes real skill is knowing what to test, how much load represents something meaningful, and which number in a wall of output actually matters. Skipping straight to k6 syntax without this foundation produces someone who can run a load test but can't design one, or interpret what it actually found.

Functional Testing vs. Performance Testing

Functional test:  "Does POST /orders correctly create an order?"
Performance test: "Does POST /orders still respond correctly and quickly
                    when 500 people are creating orders at the same time?"

These are complementary, not competing — and this distinction matters throughout this entire course: a performance test that only measures speed while ignoring whether responses are still functionally correct under load can miss a real class of bug, like a race condition that only appears under concurrency. Chapter 5 covers this directly — good performance tests validate functionality, not just timing.

Performance vs. Reliability

These get conflated but measure different things: performance asks "how fast, and under how much load"; reliability asks "does it keep working correctly over time, without crashing or corrupting data." A system can be fast but unreliable (quick responses that occasionally return corrupted data under load) or reliable but slow (never crashes, but takes 8 seconds per request). Good performance testing keeps an eye on both, since a system that gets faster by becoming less correct hasn't actually improved.

Performance Degradation vs. Functional Failure

Functional failure:      The request returns a 500 error — something is definitively broken.
Performance degradation: The request returns 200 successfully, but takes 8 seconds
                          instead of the usual 200ms — nothing is "broken," but users
                          are having a measurably worse experience.

This distinction matters for how you triage a problem: a functional failure is unambiguous and usually gets fixed fast; performance degradation is often gradual, easy to dismiss as "not really a bug," and can quietly worsen for a long time before anyone treats it with urgency — exactly the kind of problem the baseline comparisons and soak testing covered in this chapter exist to catch early.

Common Mistakes to Watch For

  • Relying on average response time alone — a healthy-looking average can hide a genuinely bad experience for a meaningful percentage of real users, covered in depth on the Percentiles page.
  • Confusing load testing with stress testing — designing a test that doesn't actually answer the question you meant to ask.
  • Treating performance degradation as "not a real bug" since nothing technically errors — exactly the mindset that lets a slow, gradually-worsening system go unaddressed.
