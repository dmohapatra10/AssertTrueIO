Chaining Requests Into a Real User Journey

Every request built so far has been isolated — one GET, one POST, tested on its own. Almost no real system is exercised that way; a real user logs in, browses, adds something to a cart, and checks out — a chain of dependent calls, each one needing data the last one produced. Three focused pages:

  1. Building a Realistic End-to-End Workflow — Login → Get Token → Get Products → Create Order → Get Order, worked in full
  2. Cookies in Performance Tests — session cookies, cookie jars, and when they actually matter for load
  3. Why Performance Tests Should Validate Functionality Too — the idea this whole chapter is really in service of

What's Genuinely New Here vs. Already Covered

The individual HTTP methods, headers, query parameters, and request bodies were already covered in depth earlier — nothing about the syntax of a single request changes here. What's new is putting several of those requests together into a workflow that actually resembles how a real system gets used, with data flowing from one response into the next request, session state (cookies) persisting across the chain, and — critically — checking that each step did the right thing, not just that it responded fast.

A Quick Preview of the Shape This Takes

Login (POST) → extract token
      ↓
Get Products (GET, authenticated) → extract a product ID
      ↓
Create Order (POST, authenticated) → extract order ID
      ↓
Get Order (GET, authenticated) → verify it matches what was ordered

This is a genuinely realistic shape — nearly any e-commerce, banking, or SaaS workflow follows some version of it. The next page builds this exact chain, explained step by step.

Common Mistakes to Watch For

  • Testing each endpoint in total isolation, never as a connected workflow — misses exactly the kind of integration problem that only shows up when data flows between real, dependent steps.
  • Ignoring cookies entirely in APIs that actually rely on session state, then wondering why a chained workflow behaves differently than production.
  • Treating "fast" and "correct" as the same thing — a workflow that completes quickly but silently returns wrong data at one step is still a real problem, just an invisible one to a test that only checks response time.
