Rate Limiting & Server Errors

Prerequisites: Resource Errors: 404 & 409

What is this?

These are the negative scenarios that are hardest to test reliably, precisely because they're about the API's own infrastructure behavior — rate limiting and server-side failure — rather than something you can simply construct in a request body.

429 — Too Many Requests

@Test
void exceedingRateLimitReturns429() {
    Response lastResponse = null;
    for (int i = 0; i < 100; i++) {
        lastResponse = given().header("X-API-Key", apiKey).when().get("/weather");
        if (lastResponse.getStatusCode() == 429) break;
    }
    assertThat(lastResponse.getStatusCode(), equalTo(429));
    assertThat(lastResponse.getHeader("Retry-After"), is(notNullValue()));
}

Testing rate limiting genuinely means triggering it — sending requests until the limit kicks in. This is slower and more resource-intensive than most negative tests, and worth being deliberate about: running this against a shared test environment's real rate limit can affect other tests or users sharing that same limit, so consider whether a dedicated, isolated rate-limit-testing key or environment is available before running this routinely.

The Retry-After Header

.then()
    .statusCode(429)
    .header("Retry-After", notNullValue());

A well-behaved rate-limited API tells the client how long to wait before retrying, via the Retry-After header — worth asserting on directly, since a 429 with no retry guidance forces clients to guess, which is a real usability gap in the API's own design.

500 — Internal Server Error

@Test
void malformedButUnusualInputDoesNotCauseA500() {
    // Deliberately probing for an unhandled edge case that might crash
    // the server instead of being gracefully rejected with a 400
    String extremeInput = "a".repeat(100_000); // an unusually long string

    given().body(Map.of("name", extremeInput)).when().post("/users")
        .then().statusCode(not(500)); // should be a graceful 400, NOT a crash
}

You generally can't (and shouldn't try to) deliberately trigger a genuine server bug on purpose in most testing scenarios — but you can test that unusual, edge-case inputs are handled gracefully (a proper 400) rather than crashing the server (a 500). A 500 in response to bad client input is itself a bug worth catching — the server should validate and reject gracefully, not fail unexpectedly.

Unsupported HTTP Method — 405

@Test
void unsupportedMethodReturns405() {
    given()
    .when()
        .patch("/health-check") // a read-only endpoint that shouldn't accept PATCH at all
    .then()
        .statusCode(405)
        .header("Allow", containsString("GET")); // tells the client which methods ARE supported
}

A well-designed API returns 405 Method Not Allowed (not a generic 404 or 400) when a valid resource exists but doesn't support the specific method attempted — and often includes an Allow header listing which methods actually are supported, similar in spirit to the Retry-After header for 429.

Real-World Example — A Resilience-Focused Test Suite Section

@Nested
class ApiResilience {
    @Test void unsupportedMethodIsRejectedGracefully() {
        given().when().patch("/health-check").then().statusCode(405);
    }

    @Test void extremelyLargePayloadIsRejectedNotCrashed() {
        String hugeBody = "x".repeat(10_000_000);
        given().body(hugeBody).when().post("/users").then().statusCode(not(500));
    }

    @Test void deeplyNestedJsonIsHandledGracefully() {
        String deeplyNested = buildDeeplyNestedJson(1000); // 1000 levels deep
        given().contentType(ContentType.JSON).body(deeplyNested).when().post("/data")
            .then().statusCode(not(500));
    }
}

This grouping reflects a genuinely different testing mindset from the rest of this chapter — not "does the API correctly reject THIS specific invalid input," but "does the API remain stable and gracefully rejecting under unusual, edge-case load," a lightweight form of resilience testing that fits naturally inside a functional negative-testing suite.

❌ Fragile vs. ✅ Recommended

// ❌ Running rate-limit tests routinely against a SHARED environment's
// real, limited quota — can disrupt other tests or users sharing the same limit
@Test void everyBuildTriggersRateLimit() { /* runs 100+ requests EVERY CI run */ }

// ✅ Reserve rate-limit testing for a dedicated environment/key,
// or run it deliberately and infrequently, not as part of every routine build
@Tag("rate-limit-heavy") // excluded from the default fast CI run
@Test void rateLimitEventuallyTriggers() { /* ... */ }

Common Mistakes

  • Running rate-limit tests as part of every routine CI build against a shared quota — slows the suite and can genuinely disrupt other consumers of the same limit.
  • Trying to deliberately trigger a real server bug to test 500 handling — instead, test that unusual-but-not-malicious inputs are handled gracefully, which is both safer and more representative of a real resilience concern.
  • Not checking the Allow header on a 405 response — a useful piece of the contract worth validating alongside the status code itself.

Edge Cases

  • Rate limits that reset on a rolling window vs. a fixed window — worth understanding which your API uses if you're testing the reset behavior specifically, not just that the limit triggers at all.
  • APIs with different rate limits per endpoint or per authentication tier — a single generic rate-limit test may not represent every tier; be explicit about which specific limit you're testing.

Debugging

If a resilience-style test unexpectedly returns 500, treat it as a genuine finding worth reporting, not a test bug to work around — a server crash on unusual-but-plausible input is exactly the class of issue this kind of test exists to surface.

Best Practices

  • Tag or separate rate-limit and heavy-load tests from the routine fast CI suite, running them deliberately rather than on every build.
  • Test graceful handling of unusual inputs (very large payloads, deeply nested structures) rather than trying to deliberately trigger a genuine server bug.
  • Validate the Retry-After header on 429 responses and the Allow header on 405 responses, not just the status codes alone.

Practice Exercise

Design (without necessarily running against a real shared environment) a rate-limit test that sends requests until a 429 is returned, asserting both the status code and the presence of a Retry-After header — and a separate resilience test confirming an unusually large request body is rejected gracefully rather than causing a 500.

Summary

429 and 500 are the hardest negative scenarios to test reliably — rate limiting requires genuinely triggering it (carefully, given shared-environment impact), and server errors shouldn't be deliberately triggered at all, but rather probed for via graceful-handling tests against unusual, edge-case inputs. Unsupported HTTP methods (405) round out this chapter's coverage, including the often-overlooked Allow header that should accompany them.

Interview Questions

Why shouldn't you try to deliberately trigger a real 500 server error to test how your test suite handles it?▾
A genuine 500 represents an actual bug in the server — you generally can't reliably construct a request that triggers one on purpose (if you could predict it, the server would likely already have a fix or a validation check preventing it), and deliberately hunting for crashes isn't the same discipline as functional negative testing. The more valuable and reliable approach is testing that unusual, edge-case-but-plausible inputs — very large payloads, deeply nested structures, boundary values — are handled gracefully with an appropriate 4xx response rather than crashing the server; if one of these tests does surface a real 500, that's a genuine finding worth reporting, not something the test was specifically designed to force.
