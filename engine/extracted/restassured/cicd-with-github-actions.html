CI/CD with GitHub Actions

Prerequisites: Test Reporting: JUnit, TestNG, Allure

What is this?

Developer Push
      ↓
GitHub Actions
      ↓
Build
      ↓
Run API Tests
      ↓
Generate Report
      ↓
Upload Artifacts

This is the pipeline every page in this chapter has been building toward — automating the entire test lifecycle so it runs consistently on every push, without anyone needing to trigger it manually or have Maven installed locally.

A Complete Working Workflow

# .github/workflows/api-tests.yml
name: RestAssured API Tests
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up JDK 21
        uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'
          cache: 'maven'

      - name: Build
        run: mvn -B compile

      - name: Run API Tests
        run: mvn -B test
        env:
          API_BASE_URL: ${{ secrets.QA_BASE_URL }}
          TEST_USER_EMAIL: ${{ secrets.TEST_USER_EMAIL }}
          TEST_USER_PASSWORD: ${{ secrets.TEST_USER_PASSWORD }}

      - name: Upload Test Report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: surefire-reports
          path: target/surefire-reports/
          retention-days: 14

Every step maps directly onto the pipeline diagram above — checkout, build, test, report. cache: 'maven' caches downloaded dependencies between runs, meaningfully speeding up repeat builds. if: always() on the upload step ensures the report gets archived even when tests fail — exactly the case where you need it most, echoing the same principle from the Playwright track's CI chapter.

Environment Variables and Secrets

env:
  API_BASE_URL: ${{ secrets.QA_BASE_URL }}
  TEST_USER_EMAIL: ${{ secrets.TEST_USER_EMAIL }}
  TEST_USER_PASSWORD: ${{ secrets.TEST_USER_PASSWORD }}

Every credential referenced here comes from GitHub's repository secrets (configured in the repo's Settings → Secrets), never hardcoded in the workflow file — the CI-level equivalent of the environment-variable configuration pattern from Chapter 2 and Chapter 10, now feeding into EnvConfig at runtime through the CI environment rather than a local .env file.

Detailed Example — Running Against Multiple Environments

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        environment: [qa, staging]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '21', distribution: 'temurin' }
      - run: mvn -B test
        env:
          API_BASE_URL: ${{ matrix.environment == 'qa' && secrets.QA_BASE_URL || secrets.STAGING_BASE_URL }}

A matrix strategy runs the same test suite against multiple environments in parallel CI jobs — the CI-infrastructure-level parallelism, distinct from (but complementary to) the JUnit-level thread parallelism covered earlier in this chapter. This is genuinely useful for confirming a change behaves correctly across every environment it needs to work in, not just one.

Real-World Example — Combining Parallel Test Execution With CI Sharding

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1, 2, 3, 4]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '21', distribution: 'temurin' }
      - name: Run shard ${{ matrix.shard }} of 4
        run: mvn -B test -Dgroups="shard-${{ matrix.shard }}"
        env:
          API_BASE_URL: ${{ secrets.QA_BASE_URL }}

For a genuinely large suite, splitting tests across multiple CI machines (via JUnit 5 tags acting as shard identifiers, or a dedicated test-splitting plugin) works alongside the in-JVM thread parallelism from earlier in this chapter — two complementary layers of parallelism, one across machines, one across threads within each machine.

Publishing Test Results Natively in GitHub's UI

- name: Publish Test Results
  if: always()
  uses: dorny/test-reporter@v1
  with:
    name: RestAssured Test Results
    path: target/surefire-reports/*.xml
    reporter: java-junit

Beyond just archiving the raw report as a downloadable artifact, a dedicated reporting action can parse JUnit's XML output and display pass/fail results directly in GitHub's pull request UI — meaningfully more convenient than requiring anyone to download and open an artifact manually to see what happened.

❌ Fragile vs. ✅ Recommended

// ❌ Hardcoding a base URL or credential directly in the workflow YAML file
env:
  API_BASE_URL: "https://qa.example.com"
  TEST_USER_PASSWORD: "hardcoded-password-123"

// ✅ Every credential and environment-specific value from repository secrets
env:
  API_BASE_URL: ${{ secrets.QA_BASE_URL }}
  TEST_USER_PASSWORD: ${{ secrets.TEST_USER_PASSWORD }}

Common Mistakes

  • Hardcoding credentials or environment URLs directly in the workflow file — the CI equivalent of hardcoding them in test code, and just as unsafe, since workflow files are typically committed to version control.
  • Forgetting if: always() on the report-upload step — loses exactly the report you need most, from a failed run.
  • Not caching Maven dependencies, causing every CI run to re-download the same dependencies from scratch, needlessly slowing every build.

Edge Cases

  • Tests that need a running application to test against (rather than an already-deployed QA environment) — a workflow can include a step that starts the application locally within the CI job first, similar in spirit to the webServer concept from browser-based testing, though the specific mechanism varies by application.
  • Flaky tests specifically in CI but not locally — often traces back to genuine parallel-execution race conditions (earlier in this chapter) that are more likely to actually manifest under CI's typically higher parallelism than a local machine's.

Debugging

If a CI run fails in a way that's hard to diagnose from the uploaded report alone, that's the signal to improve the reporting setup (the previous page's guidance) rather than accepting "download the artifact and dig through it manually" as the normal workflow.

Best Practices

  • Store every credential and environment-specific value in repository secrets, never in the workflow file itself.
  • Always use if: always() on report/artifact upload steps.
  • Cache Maven dependencies to keep CI runs fast.
  • Consider matrix strategies for multi-environment runs and sharding for genuinely large suites.

Summary

A complete RestAssured CI/CD pipeline in GitHub Actions checks out code, builds with Maven, runs tests with credentials sourced from repository secrets, and archives reports — always, including on failure. Matrix strategies extend this to multiple environments or shards running in parallel, and a dedicated reporting action can surface results directly in GitHub's UI rather than requiring a manual artifact download.

Interview Questions

Why is if: always() specifically important on the artifact upload step in a GitHub Actions workflow?▾
Without it, a step only runs if every previous step in the job succeeded — but the test report is often most valuable precisely when tests fail, since that's when someone needs to investigate what went wrong. If the test-running step fails and the upload step doesn't have if: always(), GitHub Actions skips the upload entirely, meaning the exact run that most needs a diagnosable report has none available at all — forcing someone to reproduce the failure locally instead of simply downloading the artifact that should have already captured it.
Why is if: always() specifically important on the artifact-upload step?▾
Without it, a step only runs if every previous step succeeded — but the test report is most valuable exactly when tests fail; skipping the upload on failure means the run that most needs a diagnosable report has none available.
Why should credentials and environment URLs live in repository secrets rather than the workflow YAML file directly?▾
Workflow files are typically committed to version control — hardcoding a credential there exposes it the same way hardcoding it in test source code would.
What's the difference between a matrix strategy for environments and sharding for a large suite?▾
A matrix runs the SAME suite against different environments in parallel jobs (confirming behavior across each); sharding splits ONE suite across multiple machines, each running a portion — two complementary, distinct axes of CI-level parallelism.
Why cache Maven dependencies in a GitHub Actions workflow?▾
Without caching, every CI run re-downloads the same dependencies from scratch, needlessly slowing every single build for no benefit.
