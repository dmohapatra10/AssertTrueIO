Validation Errors: 400 & 422

Prerequisites: Error Handling & Negative Testing overview

What is this?

The most common category of negative test — sending a request that's wrong in some way and confirming the API correctly rejects it, rather than silently accepting bad data or crashing.

400 vs. 422 — The Real Distinction

400 Bad Request conventionally means the request is malformed at the protocol/syntax level — invalid JSON, a completely wrong data type where a specific type is required. 422 Unprocessable Entity means the request is syntactically well-formed (valid JSON, correct types) but semantically invalid — a business rule violation, like an email that's syntactically a string but doesn't match a valid email pattern. Not every API observes this distinction consistently — some use 400 for everything — but where an API does distinguish them, your negative tests should assert the specific code that API actually uses, not assume one universally.

Missing Required Field

@Test
void missingRequiredNameFieldReturns400() {
    Map<String, Object> incompleteUser = Map.of("email", "john@example.com");
    // "name" deliberately omitted

    given().body(incompleteUser).when().post("/users")
        .then().statusCode(400)
        .body("error", containsString("name"));
}

Invalid Data Type

@Test
void wrongTypeForQuantityFieldReturns400() {
    String malformedBody = """
    { "item": "Mouse", "quantity": "not-a-number" }
    """;

    given().contentType(ContentType.JSON).body(malformedBody).when().post("/orders")
        .then().statusCode(400);
}

Notice this uses a raw string body (from the Request Body Construction page) rather than a POJO — a POJO with a strongly-typed int quantity field literally can't represent this scenario, since Java's own type system prevents assigning a string to an int field. Testing wrong-type input specifically requires bypassing your own POJO's type safety.

Invalid Email Format

@ParameterizedTest
@ValueSource(strings = {"not-an-email", "missing-at-sign.com", "@no-local-part.com", "spaces in@email.com"})
void invalidEmailFormatsAreRejected(String invalidEmail) {
    User user = UserBuilder.aUser().withEmail(invalidEmail).build();
    given().body(user).when().post("/users").then().statusCode(anyOf(is(400), is(422)));
}

This combines the parameterized testing pattern from Chapter 10 with the builder pattern from the same chapter — four format variants, one test method, each overriding only the field actually under test.

Malformed JSON

@Test
void malformedJsonSyntaxReturns400() {
    String brokenJson = "{ \\"name\\": \\"John\\", }"; // trailing comma — invalid JSON syntax

    given().contentType(ContentType.JSON).body(brokenJson).when().post("/users")
        .then().statusCode(400);
}

This is a genuinely different category of failure from an invalid field value — the request body isn't valid JSON at all, which should fail before the API even attempts to interpret the fields inside it. A well-behaved API returns 400 here specifically because parsing failed, not because of any particular field's content.

Real-World Example — A Full Field-by-Field Validation Sweep

@ParameterizedTest
@CsvSource({
    "'', valid@example.com, 30, Name is required",
    "John, '', 30, Email is required",
    "John, not-an-email, 30, Invalid email format",
    "John, valid@example.com, -5, Age must be positive",
    "John, valid@example.com, abc, Age must be a number"
})
void fieldValidationRulesAreEnforced(String name, String email, String age, String expectedErrorFragment) {
    Map<String, Object> user = new HashMap<>();
    user.put("name", name.isEmpty() ? null : name);
    user.put("email", email.isEmpty() ? null : email);
    user.put("age", age);

    given().body(user).when().post("/users")
        .then().statusCode(anyOf(is(400), is(422)))
        .body("error", containsString(expectedErrorFragment));
}

Five distinct validation rules, tested in one parameterized method, each asserting both the status code AND that the error message actually names the right problem — not just "something failed," but "the API correctly identified which thing failed."

❌ Fragile vs. ✅ Recommended

// ❌ Only testing that an invalid request returns SOME 4xx code
given().body(badData).when().post("/users").then().statusCode(greaterThanOrEqualTo(400));

// ✅ Asserting the SPECIFIC status code the API's documented contract promises
given().body(badData).when().post("/users").then().statusCode(400);

Common Mistakes

  • Asserting a loose "any 4xx" status instead of the specific code the API's contract actually promises — misses a real regression where the API starts returning the wrong (but still 4xx) code.
  • Testing only one invalid variant per field when several distinct invalid formats exist — a parameterized sweep catches more than a single hardcoded bad example.
  • Assuming a POJO can represent every invalid-input scenario — wrong-type and malformed-JSON tests specifically need raw string bodies, since Java's type system prevents constructing the invalid case through a POJO.

Edge Cases

  • Boundary values (an age of exactly 0, or a string at exactly the maximum allowed length) — worth testing explicitly, since off-by-one validation bugs are common right at a boundary.
  • Extra, unexpected fields in the request — some APIs silently ignore them, others reject the request; know which your API does and test accordingly.

Debugging

If a validation test fails with an unexpected status, check whether the API actually distinguishes 400 from 422 consistently, or uses one code for everything — don't assume the distinction from this page applies universally without confirming against the specific API's actual behavior.

Best Practices

  • Assert the specific status code an API's contract promises, not a loose "any 4xx" range.
  • Use parameterized tests to sweep multiple invalid variants per field rather than one hardcoded example.
  • Assert on the error message content, not just the status code, confirming the API correctly identifies which field failed.
  • Use raw string bodies specifically for wrong-type and malformed-JSON scenarios that a POJO can't represent.

Practice Exercise

Write a parameterized test covering five distinct validation failures for a hypothetical "create product" endpoint (missing name, negative price, invalid category, price as a string instead of a number, and malformed JSON), asserting both the correct status code and that each error message identifies the specific problem.

Summary

Validation error testing covers missing fields, wrong types, invalid formats, and malformed JSON — each testable with the right tool (builders and parameterized tests for format variants, raw string bodies for type/syntax violations that a POJO can't represent). Assert the specific status code an API's contract promises, and verify the error message actually identifies the right problem, not just that something failed.

Interview Questions

Why would you use a raw JSON string instead of a POJO to test that an API correctly rejects a wrong data type, like a string where a number is expected?▾
A POJO is defined with specific Java types for each field — if quantity is declared as an int, Java's own compiler prevents you from ever assigning a string to it, so there's no way to construct a POJO instance representing that invalid state in the first place. Testing this specific scenario requires bypassing the POJO entirely and sending a raw, deliberately malformed JSON string as the request body, which is the only way to actually produce a request containing the wrong type for the API to reject.
Why can't a strongly-typed POJO represent a 'wrong data type' test scenario?▾
If a field is declared as an int, Java's compiler prevents assigning a string to it — there's no way to construct that invalid POJO state; this specific test needs a raw string body instead.
Why is malformed JSON syntax a genuinely different failure category from an invalid field value?▾
The request body isn't valid JSON at all, so a well-behaved API should fail before even attempting to interpret any fields inside it — a different code path than field-level validation.
Why assert on error message content, not just the status code, for a validation test?▾
A 400 could mean a missing name, an invalid email, or malformed JSON — three different problems, all producing the same code; the message confirms the API caught the SPECIFIC problem the test introduced.
Why combine a parameterized test with a builder for multi-format validation testing?▾
The builder supplies sensible defaults for every field not under test, while the parameterized data varies just the one field being tested — each test overrides only what's actually relevant to it.
