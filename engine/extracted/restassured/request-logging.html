Request Logging

Prerequisites: Logging in RestAssured overview

What is this?

given()
    .log().all()
    .contentType(ContentType.JSON)
    .body(user)
.when()
    .post("/users");

.log().all(), placed inside given(), prints the fully resolved outgoing request — method, URL, headers, and body — to the console right before RestAssured sends it. This is the single fastest way to confirm exactly what a request contains, rather than assuming your .header(), .queryParam(), or .body() calls did what you expected.

Why it's important

A surprising number of "why is my test failing" moments have nothing to do with the API at all — they're a request that isn't actually shaped the way you think it is. A typo'd path parameter, a Content-Type that didn't get set, a body that serialized differently than expected. Request logging resolves these in seconds instead of minutes of guessing.

Basic Example — Logging Everything

given()
    .log().all()
    .pathParam("id", 42)
    .queryParam("include", "profile")
.when()
    .get("/users/{id}");

// Prints something like:
// Request method: GET
// Request URI:    /users/42?include=profile
// Headers:        Accept=*/*
// Cookies:        <none>
// Body:           <none>

Targeted Logging — Just One Piece

given().log().body().body(user).when().post("/users");        // only the body
given().log().headers().header("Authorization", "Bearer " + t).when().get("/profile"); // only headers
given().log().params().queryParam("page", 2).when().get("/users"); // only params
given().log().cookies().when().get("/dashboard");               // only cookies

Full .log().all() output can be a lot to scan through when you only care about one specific piece — did the body serialize correctly, did a specific header actually get set. The targeted variants print just that one section, which is faster to read when you already know which part you're troubleshooting.

Detailed Example — Confirming a POJO Serialized Correctly

@Test
void debuggingWhatAPojoActuallySerializesTo() {
    OrderRequest order = new OrderRequest("Wireless Mouse", 2);

    given()
        .log().body() // print ONLY the serialized JSON body
        .contentType(ContentType.JSON)
        .body(order)
    .when()
        .post("/orders");

    // Console shows the actual JSON RestAssured generated from the POJO —
    // confirms field names, nesting, and types all came out as expected
}

This is exactly the debugging technique referenced in the Serialization chapter for confirming what JSON a POJO actually produces — seeing the real serialized output is more reliable than assuming it matches your mental model of the class.

Real-World Example — Debugging an Unexpected 400

@Test
void investigatingAnUnexpectedValidationError() {
    given()
        .log().all() // temporarily added while investigating
        .contentType(ContentType.JSON)
        .pathParam("id", customerId)
        .body(newOrder)
    .when()
        .post("/customers/{id}/orders")
    .then()
        .statusCode(201); // currently failing with 400 — logging helps find out why
}

When a request fails unexpectedly, adding .log().all() temporarily is usually the fastest first step — before checking API documentation, before adding more assertions, before assuming the API itself is broken. Confirm what was actually sent first.

❌ Fragile vs. ✅ Recommended

// ❌ Leaving .log().all() permanently in committed test code — floods
// CI logs with full request dumps for every test, including passing ones
given().log().all().body(user).when().post("/users").then().statusCode(201);

// ✅ Use it while debugging, remove it (or use conditional logging,
// covered on the next page) before committing
given().body(user).when().post("/users").then().statusCode(201);

Common Mistakes

  • Leaving .log().all() in committed code — floods CI output for every passing test, making genuine failures harder to spot in the noise.
  • Using full .log().all() when a targeted log would answer the question faster — if you specifically need to confirm the body, .log().body() gets there with less scrolling.
  • Not logging when a request behaves unexpectedly — guessing at what might be wrong instead of just looking at what was actually sent.

Edge Cases

  • Logging a request with sensitive data (a real password, a production API key) — be deliberate about what ends up in logs, especially any that might be captured in CI artifacts; consider whether test credentials specifically (not production ones) are what's being logged.
  • Very large request bodies — full logging can produce a lot of console output for a large payload; targeted logging or truncation may be more practical.

Debugging

If you're not sure why a request is producing an unexpected response, request logging should be your very first troubleshooting step, before touching assertions or API documentation — confirm what was actually sent before investigating why the server responded the way it did.

Best Practices

  • Use .log().all() liberally while actively writing or debugging a test.
  • Reach for targeted logging (.log().body(), .log().headers()) when you already know which piece you're troubleshooting.
  • Remove or replace request logging with conditional logging (next page) before committing test code.

Practice Exercise

Write a test that sends a POST request with a POJO body, a path parameter, and a custom header. Use .log().all() to print the full outgoing request, then switch to using only .log().body() and confirm you can still verify the serialized payload is correct with less console output to scan.

Summary

Request logging — full via .log().all(), or targeted via .log().body()/.log().headers()/.log().params()/.log().cookies() — prints exactly what RestAssured is about to send, resolving the large class of test failures that are really about the request being malformed, not the API misbehaving. Use it freely while debugging; remove it before committing.

Interview Questions

Why might you reach for log().body() instead of log().all() when debugging a serialization issue?▾
.log().all() prints the entire request — method, URL, headers, cookies, and body — which can be a lot of output to scan through when you specifically only care about whether a POJO serialized correctly. .log().body() prints just the body, getting you directly to the information you actually need with less noise to filter through, especially useful when the request has many headers or a large query string that aren't relevant to the question at hand.

Why should .log().all() rarely survive into committed test code?▾

What's a legitimate reason to be careful about what request logging captures?▾
