The Recommended Folder Structure

Prerequisites: Layer-by-Layer Responsibilities

What is this?

src/
├── main/
│   └── java/
│       ├── config/
│       ├── clients/
│       ├── models/
│       ├── specs/
│       ├── utils/
│       ├── auth/
│       └── constants/
│
└── test/
    └── java/
        ├── tests/
        ├── data/
        └── assertions/

The previous page covered what each folder is responsible for. This page is about the structure itself — specifically, why it's split across src/main and src/test, and what a fully fleshed-out version looks like in a real project.

Why src/main vs. src/test at All?

This is a genuine, deliberate Maven/Gradle convention, not an arbitrary choice: src/main/java is meant for code that could theoretically be reused or even shipped as a library, while src/test/java is exclusively test-scoped code, compiled and included only when running tests. The framework layers (clients, models, specs, utils, auth, constants) are genuinely reusable — a client class doesn't inherently know it's "for testing," it just knows how to call an API. The test-side layers (tests, data, assertions) are inherently test-specific and belong in src/test accordingly.

A Fully Fleshed-Out Example

src/
├── main/java/com/example/api/
│   ├── config/
│   │   └── EnvConfig.java
│   ├── clients/
│   │   ├── UserClient.java
│   │   ├── OrderClient.java
│   │   └── ProductClient.java
│   ├── models/
│   │   ├── User.java
│   │   ├── Order.java
│   │   └── LineItem.java
│   ├── specs/
│   │   └── SpecFactory.java
│   ├── utils/
│   │   └── JsonUtils.java
│   ├── auth/
│   │   └── TokenManager.java
│   └── constants/
│       └── ApiConstants.java
│
└── test/java/com/example/api/
    ├── tests/
    │   ├── users/
    │   │   ├── UserCreationTest.java
    │   │   └── UserValidationTest.java
    │   ├── orders/
    │   │   ├── OrderLifecycleTest.java
    │   │   └── OrderNegativeTest.java
    │   └── auth/
    │       └── AuthenticationTest.java
    ├── data/
    │   ├── UserBuilder.java
    │   └── OrderBuilder.java
    └── assertions/
        └── ErrorAssertions.java

Note the test folder is further organized by feature area (users/, orders/, auth/) — this is the RestAssured-specific analog of the same organizational principle covered for a different tech stack elsewhere in this course: organize by what the tests are actually about, not by test type. Splitting positive from negative tests into separate files (UserCreationTest vs. UserValidationTest) is a common, optional further refinement once a feature area has enough tests to benefit from it.

Detailed Example — How a Package Declaration Reflects This Structure

package com.example.api.clients;

public class UserClient {
    // ...
}
package com.example.api.tests.users;

import com.example.api.clients.UserClient;
import com.example.api.data.UserBuilder;

public class UserCreationTest {
    // ...
}

The folder structure and Java's package structure are the same thing — a class in src/main/java/com/example/api/clients/UserClient.java declares package com.example.api.clients;, and every test importing it references that exact package path. This is standard Java convention, worth calling out explicitly since the folder structure diagrams throughout this chapter map directly onto it.

Real-World Example — Where a New File Actually Goes

// Scenario: you need to add support for a new "Invoice" resource

// 1. The data shape:
src/main/java/com/example/api/models/Invoice.java

// 2. The API client for it:
src/main/java/com/example/api/clients/InvoiceClient.java

// 3. Test data generation for it:
src/test/java/com/example/api/data/InvoiceBuilder.java

// 4. The actual tests:
src/test/java/com/example/api/tests/invoices/InvoiceCreationTest.java
src/test/java/com/example/api/tests/invoices/InvoiceValidationTest.java

This is the practical payoff of a clear structure — adding support for an entirely new resource has an obvious, repeatable pattern to follow, rather than an ad-hoc decision every time about where things should live.

❌ Fragile vs. ✅ Recommended

// ❌ Everything in one flat folder, with no layer separation at all
src/test/java/
├── UserTest.java          (contains request-building, assertions, AND data setup, all inline)
├── OrderTest.java          (same, duplicated slightly differently)
└── Utils.java               (a catch-all grab-bag of unrelated helpers)

// ✅ The layered structure from this page
src/main/java/.../clients/, models/, specs/, ...
src/test/java/.../tests/, data/, assertions/

Common Mistakes

  • Putting framework code (clients, models) in src/test instead of src/main — works functionally, but blurs the Maven/Gradle convention distinguishing reusable code from test-only code.
  • A flat test folder with no feature-based organization once a project grows past a handful of test files — makes it hard to find where a given feature's tests actually live.
  • Inconsistent package naming that doesn't match the folder structure — Java requires these to align, and a mismatch produces compilation errors, not just a style inconsistency.

Edge Cases

  • A monorepo testing multiple genuinely separate APIs — consider a top-level package per API (com.example.usersapi, com.example.ordersapi) rather than trying to force one flat structure to serve unrelated services.

Debugging

If a class isn't found during compilation despite seemingly being in the right place, double-check its package declaration exactly matches its folder path — this is the most common cause of "class not found" errors when working within this kind of structured project.

Best Practices

  • Keep the src/main vs. src/test split aligned with genuinely reusable framework code vs. test-specific code.
  • Organize the tests/ folder by feature area, not by test type.
  • Follow the pattern consistently when adding support for a new resource — model, client, builder, tests, each in their established location.

Summary

The src/main vs. src/test split reflects a genuine Maven/Gradle convention distinguishing reusable framework code from test-specific code, with the tests/ folder further organized by feature area rather than test type. Once this structure is established, adding support for a new resource follows an obvious, repeatable pattern — a model, a client, a data builder, and tests — rather than an ad-hoc decision each time.

Interview Questions

Why does the recommended structure organize the tests/ folder by feature area (users/, orders/) rather than by test type (positive/, negative/)?▾
Organizing by feature area mirrors how the team actually thinks about the product and where they'd naturally look for a given feature's tests — "where are the order tests" has an obvious answer. Organizing by test type instead scatters tests for the same feature across different top-level folders, and doesn't naturally scale as new dimensions get added (what about performance tests, or tests scoped to a specific role?). Test type is better handled orthogonally — via tags, JUnit's @Tag, or naming conventions within a feature folder (as shown with UserCreationTest vs. UserValidationTest) — rather than as the primary folder-level organizing principle.
