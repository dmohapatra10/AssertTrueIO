PUT Requests

Prerequisites: POST Requests

What is this?

given()
    .contentType(ContentType.JSON)
    .pathParam("id", orderId)
    .body(fullOrderPayload)
.when()
    .put("/orders/{id}")
.then()
    .statusCode(200);

PUT conventionally replaces the entire resource with what you send — not a partial update. This distinguishes it sharply from PATCH (the next page), and getting this wrong is one of the most common real API bugs.

Why it's important

Sending a partial payload to a strict PUT endpoint is a genuinely common source of confusing data loss — fields you didn't include can silently get reset to empty or default values, a bug that looks like "half my update didn't work" rather than "I used the wrong HTTP method with the wrong payload."

Basic Example

OrderRequest fullOrder = new OrderRequest("Wireless Mouse", 3, "confirmed");

given()
    .contentType(ContentType.JSON)
    .pathParam("id", orderId)
    .body(fullOrder) // includes EVERY field, even ones that aren't changing
.when()
    .put("/orders/{id}")
.then()
    .statusCode(200);

Detailed Example — The Bug a Partial PUT Payload Causes

@Test
void demonstratesDataLossFromPartialPutPayload() {
    Response created = given()
        .body(new OrderRequest("Keyboard", 1, "pending", "Happy Birthday!"))
        .when().post("/orders");
    String id = created.jsonPath().getString("id");

    // ❌ Sending PUT with only the field being changed — on a strict PUT
    // implementation, this can wipe out the gift note and other omitted fields
    Map<String, Object> partialPayload = new HashMap<>();
    partialPayload.put("quantity", 2);
    given().pathParam("id", id).body(partialPayload).when().put("/orders/{id}");

    Response fetched = given().pathParam("id", id).when().get("/orders/{id}");
    // On a strict PUT implementation, this assertion FAILS —
    // giftNote got reset to null, even though we never intended to change it
    fetched.then().body("giftNote", equalTo("Happy Birthday!"));
}

This isn't hypothetical — it's the single most common real bug this method produces. Testing the omitted-field behavior explicitly, not just the field you intentionally changed, is what actually catches it.

Idempotence — What It Actually Means for Testing

@Test
void puttingTheSamePayloadTwiceProducesTheSameResult() {
    OrderRequest payload = new OrderRequest("Keyboard", 2, "confirmed");

    Response first = given().pathParam("id", orderId).body(payload).when().put("/orders/{id}");
    Response second = given().pathParam("id", orderId).body(payload).when().put("/orders/{id}");

    assertThat(first.jsonPath().getString("quantity"), equalTo(second.jsonPath().getString("quantity")));
    // Both calls produce the identical end state — this is what idempotent actually means
}

PUT is idempotent by HTTP convention — sending the exact same PUT request twice should produce the same end state as sending it once. This is genuinely testable, not just a theoretical property: calling PUT with the same payload twice in a row and confirming the resulting state is identical both times is a legitimate, useful test.

Real-World Example — Full Update With Verification

@Test
void putReplacesEntireResourceCorrectly() {
    OrderRequest updated = new OrderRequest("Wireless Mouse", 5, "confirmed");

    given()
        .contentType(ContentType.JSON)
        .pathParam("id", orderId)
        .body(updated)
    .when()
        .put("/orders/{id}")
    .then()
        .statusCode(200)
        .body("quantity", equalTo(5))
        .body("status", equalTo("confirmed"));

    // Follow-up GET confirms the change actually persisted, not just that
    // the PUT response echoed it back correctly
    given().pathParam("id", orderId).when().get("/orders/{id}")
        .then().body("quantity", equalTo(5));
}

❌ Fragile vs. ✅ Recommended

// ❌ Using PUT with a partial payload, risking silent data loss on omitted fields
given().pathParam("id", id).body(Map.of("quantity", 3)).when().put("/orders/{id}");

// ✅ Include the FULL current resource state, or use PATCH instead (next page)
given().pathParam("id", id).body(fullOrderWithAllFields).when().put("/orders/{id}");

Common Mistakes

  • Using PUT with a partial payload against an API that implements strict full-replacement semantics — the most common bug this method produces.
  • Only asserting the changed field, never the unchanged ones — this misses exactly the "did this silently reset other fields" bug PUT testing needs to catch.
  • Not checking whether an API's PUT actually follows strict convention before assuming — some APIs implement PUT more leniently than the spec technically describes; verify against real behavior, not just assumption.

Edge Cases

  • APIs that treat PUT as upsert (create if the resource doesn't exist, replace if it does) — a real, documented pattern for some APIs; verify whether yours does this before assuming PUT only ever operates on existing resources.
  • PUT against a resource that doesn't exist — depending on the API's upsert behavior, this either creates it (200/201) or fails with 404; know which your API does.

Debugging

If a field you didn't intend to change shows up as null/empty after a PUT, check whether you sent a partial payload against a strict-replacement endpoint — this is the single most common root cause, and either including the full resource or switching to PATCH resolves it.

Best Practices

  • Confirm an endpoint's actual PUT semantics (full replacement vs. lenient partial) from documentation rather than assuming.
  • Always include the full current resource state in a PUT payload unless you've confirmed the API tolerates partial ones.
  • Test both the changed and deliberately-unchanged fields after a PUT, to catch silent data loss.
  • Consider a genuine idempotence test — the same PUT payload sent twice — for endpoints where that property matters.

Practice Exercise

Create a resource with three distinct fields, then PUT an update changing only one field but including all three in the payload — assert all three fields have the expected values afterward, confirming nothing was accidentally lost.

Summary

PUT conventionally replaces a resource wholesale and is idempotent by design. The most common real bug is sending a partial payload against a strict-replacement API, silently resetting omitted fields — testing both the changed and deliberately-unchanged fields on every PUT test is what catches this.

Interview Questions

A test sends a PUT request with only the fields being changed, and afterward a field that wasn't included comes back empty. What happened?▾
The API's PUT endpoint implements full-replacement semantics — it treats the request body as the complete new state of the resource, so any field not included gets reset to empty or default. The fix is either to include the full current resource in the PUT payload, or to switch that specific request to PATCH, which is designed to update only the fields actually provided.
What's the single most common real bug PUT causes?▾
Sending a partial payload to a strict full-replacement PUT endpoint, silently resetting any omitted fields to empty or default values.
Why does a genuine idempotence test for PUT send the SAME payload twice?▾
Idempotent means repeating the exact same request produces the same end state as doing it once — sending identical payloads twice and confirming identical results is what actually verifies that property, not just a functional assumption.
Why should a PUT test assert on unchanged fields, not just the changed one?▾
Confirming the changed field updated correctly proves nothing about whether OTHER fields were silently reset — asserting deliberately-unchanged fields is what actually catches the data-loss bug PUT is prone to.
What's the 'upsert' pattern some APIs implement for PUT?▾
Some APIs treat PUT as create-if-missing, replace-if-exists — worth verifying whether your specific API does this before assuming PUT only ever operates on resources that already exist.
