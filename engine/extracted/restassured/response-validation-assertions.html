Prerequisites: Building HTTP Requests

Validating What Came Back

Building a correct request is only half of an API test — the other half, arguably the more important half, is validating that the response actually reflects what the business logic should have done. A test that sends a perfect request but never meaningfully checks the response isn't really testing anything. Doing that checking properly is covered across six focused pages:

  1. Status Code Validation — why it's almost always your first assertion
  2. Response Header Validation — Content-Type, rate limits, and other contract-carrying headers
  3. JSON Body Validation — flat fields, nested objects, and arrays
  4. JsonPath & extract() — reading values out of a response
  5. Validate vs. Extract — the conceptual distinction that ties everything on this page together
  6. XML Response Validation — the same ideas, for XML/SOAP-based APIs

Why Validation Is the Part That Actually Tests Something

It's genuinely possible to write a RestAssured test that compiles, runs, sends a real request, gets a real response back — and verifies nothing at all. Constructing the request correctly (Chapter 3) proves your test can talk to the API; it proves nothing about whether the API behaved correctly. Every meaningful assertion your test suite makes lives in this chapter's six pages. This is worth internalizing early, because it's tempting for a beginner's first tests to over-invest in getting the request right and under-invest in checking the result — the response is where the actual test lives.

A Layered Approach to Validation

A thorough test doesn't validate just one thing about a response — it layers several checks, each catching a different class of problem:

given()
    .pathParam("id", 2)
.when()
    .get("/api/users/{id}")
.then()
    .statusCode(200)                                          // Layer 1: did it even succeed?
    .header("Content-Type", containsString("application/json")) // Layer 2: right format?
    .body("data.id", equalTo(2))                              // Layer 3: right data?
    .body("data.email", containsString("@reqres.in"));        // Layer 3: right data, continued

A response could pass any one of these layers while failing another — a 200 status with the wrong body, or a correct body wrapped in the wrong Content-Type. Testing only one layer leaves the others completely unverified, which is exactly why the six pages in this chapter build toward a validation habit that covers status, headers, and body together rather than picking just one.

Different Ways to Validate the Response Body

Chapter 1 covered that a response body can be JSON or XML. RestAssured gives you a matching validation language for each — the format of the body determines which one applies, and both plug into the exact same .then().body(...) assertion style.

JSON Responses — Validated with JsonPath

{ "user": { "name": "John", "roles": ["ADMIN", "USER"] } }
.then()
    .body("user.name", equalTo("John"))           // dot notation into a nested object
    .body("user.roles", hasItem("ADMIN"));         // array membership

JsonPath is the addressing language behind every JSON body assertion — dot notation for nested objects, bracket notation for array elements, and a small set of function-like helpers (.size(), .find { }) for more complex queries. This is what the JSON Body Validation and JsonPath & extract() pages, later in this chapter, cover in full depth.

XML Responses — Validated with XPath

<user>
  <name>John</name>
  <roles>
    <role>ADMIN</role>
  </roles>
</user>
.then()
    .body("user.name", equalTo("John"))            // same dot-notation SHAPE as JSON...
    .body("user.roles.role", hasItem("ADMIN"));      // ...backed by XPath underneath instead

// For more complex queries, drop into raw XPath directly:
.then().body(hasXPath("/user/roles/role[text()='ADMIN']"));

XPath is the equivalent addressing language for XML bodies — RestAssured's dot-notation shorthand looks almost identical to the JSON version, deliberately, so switching between validating JSON and XML responses doesn't require learning a completely separate mental model. The one real syntax difference: XML attributes need an @ prefix (user.@id), since XML has a structural concept — attributes vs. child elements — that JSON simply doesn't have. The XML Response Validation page, later in this chapter, covers this fully.

How RestAssured Knows Which One to Use

You never explicitly tell RestAssured "use JsonPath" or "use XPath" — it inspects the response's Content-Type header (application/json vs. application/xml or text/xml) and picks the matching validation engine automatically. This is exactly why the .body(...) assertion syntax looks the same regardless of format — the dispatching happens invisibly underneath.

Quick Example — A Fully Validated Response

given()
    .pathParam("id", 2)
.when()
    .get("/api/users/{id}")
.then()
    .statusCode(200)
    .header("Content-Type", containsString("application/json"))
    .body("data.id", equalTo(2))
    .body("data.email", containsString("@reqres.in"));

This one chain touches three of the six pages in this chapter: status code, header, and JSON body validation, all working together.

Common Mistakes to Watch For

  • Validating only the body and skipping status/headers — a body-shape coincidence on an error response can produce a false-positive pass that a status check would have caught immediately.
  • Extracting a value and treating the extraction itself as a check — reading a field's value proves nothing about whether it's correct; this exact confusion is what the dedicated Validate vs. Extract page exists to untangle.
  • Defaulting to exact-match assertions for every field, including ones with legitimately dynamic values — makes tests brittle against harmless variation for no real benefit.

What You'll Be Able to Do

By the end of the six pages that follow, you should be able to write a validation chain that layers status, header, and body checks appropriately for a given endpoint, choose the right matcher for each field based on whether it's stable or dynamic, and clearly distinguish — in your own code — the moments where you're asserting something is true versus the moments where you're simply reading a value out for later use. Interview Questions

Why should status code validation almost always come before body validation?▾
A test that only checks the body can produce a false positive against an error response whose body shape happens to satisfy the assertions; checking status first eliminates that risk.
What determines whether Playwright — sorry, RestAssured — uses JsonPath or XPath to validate a response body?▾
RestAssured inspects the response's Content-Type header (application/json vs application/xml) and picks the matching engine automatically — you never explicitly choose.
What's the value of layering status, header, and body checks in one validation chain?▾
Each layer catches a different class of regression — a response could pass any one check while failing another (a 200 with the wrong body, or a correct body with the wrong Content-Type).
Why is checking a header like Content-Type sometimes just as important as checking the body?▾
Headers carry real contract information — caching directives, pagination totals, rate-limit counters — that a body-only test suite would leave completely unverified.
Why does this chapter's diagram distinguish the REQUEST side from the RESPONSE side so explicitly?▾
Chapter 3 covered request construction entirely; this chapter is entirely about the response — keeping that mental split clear is what the diagram is meant to reinforce throughout the rest of the course.
