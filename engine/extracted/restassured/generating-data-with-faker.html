Generating Data with Faker

Prerequisites: Data-Driven Testing with JSON & CSV

What is this?

Faker faker = new Faker();

String name = faker.name().fullName();
String email = faker.internet().emailAddress();
String address = faker.address().fullAddress();
String company = faker.company().name();

Faker is a library for generating realistic-looking fake data — names, addresses, phone numbers, company names, and dozens of other categories — without hand-writing or hardcoding any of it. Unlike the UUID-based uniqueness from earlier in this chapter (which produces safe but obviously fake-looking values like test-a1b2c3@example.com), Faker produces data that actually looks like real user input.

Why It's Important

Some tests genuinely benefit from realistic-looking data, not just unique data — testing a UI that displays a user's name, confirming an address field handles genuinely varied real-world formatting, or generating volume test data that doesn't look obviously synthetic. Faker fills exactly this gap between "technically unique" and "actually realistic."

Basic Example — A Faker-Powered Builder

public class UserBuilder {
    private static final Faker faker = new Faker();

    private String name = faker.name().fullName();
    private String email = faker.internet().emailAddress();
    private String phone = faker.phoneNumber().cellPhone();

    public static UserBuilder aUser() { return new UserBuilder(); }
    // ...withX() methods as before...
}

Combining Faker with the builder pattern from earlier in this chapter means every default value is both realistic and — since Faker generates fresh values on each call — different every time, without needing a separate UUID-suffixing step.

Detailed Example — Generating a Realistic Order

Faker faker = new Faker();

Order order = new Order(
    faker.commerce().productName(),
    faker.number().numberBetween(1, 10),
    faker.commerce().price(),
    faker.address().fullAddress()
);

given().body(order).when().post("/orders").then().statusCode(201);

Faker's category methods (commerce(), address(), name(), phoneNumber(), and many more) cover most common data types you'd need for realistic test payloads — worth browsing Faker's documentation for the specific category matching whatever domain your API models.

Real-World Example — Generating Bulk Volume Test Data

@Test
void bulkCreateOneHundredRealisticUsers() {
    Faker faker = new Faker();

    for (int i = 0; i < 100; i++) {
        Map<String, Object> user = Map.of(
            "name", faker.name().fullName(),
            "email", faker.internet().emailAddress(),
            "address", faker.address().fullAddress()
        );
        given().body(user).when().post("/users").then().statusCode(201);
    }
}

Generating a batch of realistic — but not identical or obviously synthetic-looking — records is genuinely useful for load-adjacent scenarios or for populating a demo/staging environment with data that behaves like real usage, something a hundred copies of the same UUID-suffixed template value wouldn't achieve nearly as convincingly.

Locale-Aware Data Generation

Faker indianFaker = new Faker(new Locale("en-IND"));
String indianName = indianFaker.name().fullName();
String indianAddress = indianFaker.address().fullAddress();

Faker supports locale-specific data generation — useful if your API needs to be tested against realistic data for a specific region (names, address formats, and phone number conventions that actually match that locale), rather than defaulting to generic Western-style fake data regardless of the actual user base you're modeling.

❌ Fragile vs. ✅ Recommended

// ❌ Hand-maintaining a hardcoded list of "realistic-looking" names to
// rotate through — extra maintenance, and eventually repeats/runs out
String[] names = {"John Smith", "Jane Doe", "Bob Johnson"};
String name = names[testIndex % names.length];

// ✅ Faker generates fresh, varied, realistic names on demand, indefinitely
String name = faker.name().fullName();

Common Mistakes

  • Using Faker where plain UUID-based uniqueness would be simpler and sufficient — if a test genuinely doesn't care whether the data looks realistic, Faker adds a dependency and complexity for no real benefit over the simpler approach from earlier in this chapter.
  • Assuming Faker-generated data is always valid for every possible constraint your API enforces — an API with unusual validation rules (a maximum name length, a restricted character set) might occasionally receive Faker output that doesn't satisfy them; worth being aware this can happen rather than assuming Faker output is universally safe.
  • Not seeding Faker for tests that need reproducible output — if a specific test genuinely needs the exact same "random" data across runs (rare, but possible for certain debugging or snapshot-style scenarios), Faker supports a seeded random source; the unseeded default produces different output every run.

Edge Cases

  • Faker output colliding with real, pre-existing data in a shared environment — statistically rare given Faker's large data pools, but not impossible; combine with a UUID suffix for genuinely collision-critical fields like email.
  • APIs with strict format validation that occasionally rejects otherwise-realistic Faker output — worth a quick sanity check against your specific API's validation rules before relying on Faker heavily for a given field.

Debugging

If a Faker-driven test occasionally fails with a validation error unrelated to what's actually being tested, print the specific generated value that caused it — Faker's output space is large, and an edge-case value (an unusually long name, a special character) occasionally exposes a real, previously-uncovered validation gap in the API itself, which is a legitimate and useful discovery, not just test flakiness.

Best Practices

  • Use Faker specifically when realistic-looking (not just unique) data adds real value to what's being tested.
  • Combine Faker with a UUID suffix for fields where collision-safety is critical (like email), rather than relying on Faker's realism alone.
  • Consider locale-aware generation when testing region-specific data formats.

Summary

Faker generates realistic-looking test data — names, addresses, emails — across dozens of categories, filling the gap between "technically unique" (UUID-based) and "actually realistic" data. It's the right tool when realism specifically matters to what's being tested, not a universal replacement for simpler uniqueness strategies where realism doesn't add real value.

Interview Questions

What's the difference between generating test data with a UUID and generating it with Faker, and when would you choose one over the other?▾
A UUID-based approach (like "test-" + UUID.randomUUID() + "@example.com") guarantees uniqueness but produces obviously synthetic-looking data. Faker generates data that looks like genuine user input — a real-sounding name, a properly formatted address — but doesn't guarantee uniqueness on its own. Choose UUID-based generation when the test only cares about avoiding collisions (most negative/validation tests); choose Faker when the test benefits from data that's actually realistic, such as verifying a UI correctly displays varied real-world name/address formats, or generating convincing bulk data for a demo environment. The two can also be combined — Faker for realism, with a UUID suffix layered on for guaranteed uniqueness where it matters.
