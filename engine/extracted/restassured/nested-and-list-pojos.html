Nested Objects & List POJOs

Prerequisites: ObjectMapper Configuration

What is this?

Real API payloads are rarely flat. This page covers modeling the structures every non-trivial API actually has: objects nested inside objects, arrays of objects, and fields that are legitimately optional or nullable.

Nested Objects — One POJO Referencing Another

{
  "id": 101,
  "name": "John",
  "address": {
    "city": "Delhi",
    "zip": "110001"
  }
}
public class Address {
    private String city;
    private String zip;
    // no-arg constructor + getters/setters
}

public class User {
    private int id;
    private String name;
    private Address address; // ← a nested POJO, not a flat field
    // no-arg constructor + getters/setters
}

Model nesting exactly as it appears in the JSON — a nested object becomes a field whose type is another POJO, not an attempt to flatten everything into one giant class. Jackson deserializes the nested structure recursively without any extra configuration: address.city in the JSON naturally becomes user.getAddress().getCity() in Java.

Arrays of Objects — Lists of a POJO Type

{
  "id": 500,
  "items": [
    { "productName": "Widget", "quantity": 2 },
    { "productName": "Gadget", "quantity": 1 }
  ]
}
public class LineItem {
    private String productName;
    private int quantity;
}

public class Order {
    private int id;
    private List<LineItem> items; // an array of objects becomes a List of a POJO type
}

Order order = response.as(Order.class);
int totalItems = order.getItems().stream().mapToInt(LineItem::getQuantity).sum();

Once deserialized, order.getItems() is a genuine Java List<LineItem> — every stream/collection operation you'd use on any other Java list works here, which is exactly the payoff mentioned in the Deserialization page for choosing POJOs over raw JsonPath when working with array data.

Optional and Nullable Fields

public class Order {
    private String id;
    private String status;
    private String cancelledAt; // null unless actually cancelled — document this
    private List<String> tags;  // per this API, always a list, never null (possibly empty)
}

Java has no built-in distinction between "this field is always present" and "this field might be null" beyond primitive types (which can't be null at all) versus object types (which can). The practical approach: use boxed/object types (String, Integer, not int) for anything that might be null or absent, and document the actual contract — as shown here — since the type system alone won't communicate it.

Real-World Example — A Realistically Nested E-Commerce Order

public class Customer {
    private String name;
    private String email;
}

public class LineItem {
    private String productName;
    private int quantity;
    private double unitPrice;
}

public class Order {
    private String id;
    private String status;
    private Customer customer;       // nested object
    private List<LineItem> items;    // array of objects
    private Double discountPercent;  // nullable — boxed Double, not primitive double
}

Order order = given().pathParam("id", orderId).when().get("/orders/{id}")
    .then().statusCode(200).extract().as(Order.class);

assertThat(order.getCustomer().getEmail(), containsString("@"));
assertThat(order.getItems(), hasSize(greaterThan(0)));
double total = order.getItems().stream()
    .mapToDouble(item -> item.getQuantity() * item.getUnitPrice())
    .sum();

This is the realistic shape a production e-commerce order test would take — nested customer info, a list of line items, and a nullable discount field — modeled as three small, focused POJOs rather than one sprawling flat class trying to represent everything at once.

❌ Fragile vs. ✅ Recommended

// ❌ Flattening nested data with manual JsonPath into loosely-typed local variables
String customerName = response.jsonPath().getString("customer.name");
List<String> productNames = response.jsonPath().getList("items.productName");
// repeated per field, no real object to pass around afterward

// ✅ One deserialization call, a fully-typed nested object graph
Order order = response.as(Order.class);
String customerName = order.getCustomer().getName();

Common Mistakes

  • Flattening nested JSON into one giant POJO instead of modeling it as genuinely nested classes — loses the structural clarity the JSON itself already has.
  • Using primitive types (int, double) for fields that can legitimately be null — a primitive can't hold null, so a missing field either throws during deserialization or silently defaults to 0, which can mask a real data problem.
  • Not distinguishing "empty list" from "null list" in test assertions when the API's actual contract matters — check what the specific API guarantees rather than assuming.

Edge Cases

  • Deeply nested structures (three or more levels) — model each level as its own small POJO rather than one large nested inline structure; it stays far more readable and testable.
  • A field that can be either a single object or an array depending on context (some inconsistent APIs do this) — this needs a custom deserializer; it's a genuine API design smell worth flagging rather than an ordinary case to model cleanly.

Debugging

If a nested field deserializes as null unexpectedly, confirm the nested POJO itself has a no-arg constructor — the same requirement from the POJO Design page applies independently to every nested class, not just the top-level one.

Best Practices

  • Model nested JSON structure with genuinely nested POJOs — one class per meaningful sub-object, matching the JSON's own shape.
  • Use boxed types, not primitives, for any field that can legitimately be null or absent.
  • Keep each POJO focused on one part of the structure rather than one sprawling class trying to represent an entire complex response.

Practice Exercise

Model a "Blog Post" API response with a nested "Author" object and a list of nested "Comment" objects (each with an author name and text). Deserialize a sample response and write an assertion using Java streams that confirms every comment has non-empty text.

Summary

Nested JSON objects become nested POJOs (a field whose type is another class); arrays of objects become List<POJO> fields. Model structure the way the JSON actually has it rather than flattening everything, use boxed types for nullable fields, and document each field's real nullability contract — the type system alone won't communicate it for you.

Interview Questions

Why should a nullable numeric field be typed as Double rather than double in a response POJO?▾
Java's primitive double cannot represent null at all — it always has some numeric value, defaulting to 0.0 if never set. If the API's response can legitimately omit or null that field, deserializing into a primitive either throws an error or silently produces a misleading 0.0 that looks like real data. The boxed Double type can genuinely be null, correctly representing "this field wasn't present" as distinct from "this field was present and equal to zero."
How does a nested JSON object translate into a POJO?▾
As a field whose TYPE is another POJO class, not a flattened field — Jackson deserializes the nested structure recursively without needing extra configuration.
Why type a nullable numeric field as Double instead of double?▾
A primitive double can never be null — it defaults to 0.0, which can misleadingly look like real data; a boxed Double can genuinely represent null, correctly distinguishing 'absent' from 'present and zero'.
What does a List<LineItem> field give you once deserialized that raw JsonPath extraction doesn't as naturally?▾
Every ordinary Java stream/collection operation becomes available directly — filtering, summing, mapping — on a genuinely typed list, not just a generic extracted collection.
Why is one large flat POJO usually worse than several small nested ones for a complex response?▾
It loses the structural clarity the JSON itself already has — modeling nesting explicitly, one focused class per meaningful sub-object, keeps the POJO structure matching the data's actual shape.
