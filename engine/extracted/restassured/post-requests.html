POST Requests

Prerequisites: GET Requests

What is this?

given()
    .contentType(ContentType.JSON)
    .body(newUser)
.when()
    .post("/users")
.then()
    .statusCode(201);

POST creates a new resource (or triggers a non-idempotent action) by sending a request body. This is the most common method for test data setup — creating a user, an order, a comment — the pattern behind almost every "arrange" step in a larger test scenario.

Why it's important

Almost every multi-step API test uses POST somewhere for setup. Getting the payload shape and validation right here is what makes that whole pattern reliable rather than a source of confusing, hard-to-debug setup failures downstream.

Basic Example

User newUser = new User("John", "john@example.com");

Response response =
    given()
        .contentType(ContentType.JSON)
        .body(newUser)
    .when()
        .post("/users");

response.then()
    .statusCode(201) // 201 Created, not 200 — worth being deliberate about
    .body("id", notNullValue());

Checking specifically for 201 rather than a looser "any success" check is worth being deliberate about — a well-behaved creation endpoint should specifically return 201 Created, and asserting the exact code catches an API that's technically succeeding but not following its own contract.

Detailed Example — Validating the Full Response Shape

@Test
void creatingAnOrderReturnsFullExpectedShape() {
    OrderRequest order = new OrderRequest("Wireless Mouse", 2);

    given()
        .contentType(ContentType.JSON)
        .body(order)
    .when()
        .post("/orders")
    .then()
        .statusCode(201)
        .body("item", equalTo("Wireless Mouse"))
        .body("quantity", equalTo(2))
        .body("status", equalTo("pending"))
        .body("id", matchesPattern("^ORD-\\\\d+$"))
        .body("createdAt", notNullValue());
}

A thorough creation test validates both the fields you sent (echoed back correctly) and the fields the server generated (an ID matching an expected pattern, a timestamp) — the second category is often skipped, but it's exactly where a server-side bug in ID generation or timestamping would actually show up.

Real-World Example — Testing a Validation Error

@Test
void missingRequiredFieldReturns400() {
    Map<String, Object> incompleteOrder = new HashMap<>();
    incompleteOrder.put("item", "Wireless Mouse");
    // "quantity" deliberately omitted — a required field

    given()
        .contentType(ContentType.JSON)
        .body(incompleteOrder)
    .when()
        .post("/orders")
    .then()
        .statusCode(400)
        .body("error", containsString("quantity"));
}

Testing that POST correctly rejects invalid input is just as important as testing successful creation — a suite that only ever exercises the happy path has never verified the API's validation logic actually works, covered more fully in the Negative Testing chapter later in this course.

Why POST Isn't Idempotent

// Calling this twice creates TWO separate orders — POST has no built-in
// protection against duplicate submission
given().contentType(ContentType.JSON).body(order).when().post("/orders");
given().contentType(ContentType.JSON).body(order).when().post("/orders"); // a second, distinct order

This matters directly for test design: if a test retries a POST after a timeout without knowing whether the first attempt actually succeeded, it risks creating duplicate data. Some APIs support an idempotency key header for exactly this scenario — worth checking your API's documentation if retry-safety around POST is a genuine concern.

❌ Fragile vs. ✅ Recommended

// ❌ Only checking response.getStatusCode() < 300, missing that the API
// returned the wrong specific status
Response response = given().body(order).when().post("/orders");
assertThat(response.getStatusCode(), lessThan(300)); // true for 200 OR 201 — imprecise

// ✅ Assert the specific expected status for a creation endpoint
.then().statusCode(201);

Common Mistakes

  • Using a loose "any success" check instead of an exact status assertion when the specific code (201 vs. 200) actually matters to the contract being tested.
  • Not validating server-generated fields (ID, timestamp) after creation, only the fields you sent.
  • Only testing successful creation, never a validation-error path with intentionally invalid or incomplete data.
  • Assuming POST requests are safe to blindly retry without considering duplicate-creation risk.

Edge Cases

  • Creating a resource that already exists (a duplicate email during user registration) — should return a 409 Conflict, worth testing explicitly.
  • Large payloads — some APIs cap request body size; intentionally exceeding it can verify the API rejects it gracefully rather than crashing.

Debugging

If a POST unexpectedly fails, log both the status code and the full response body — a 400 response almost always includes a useful validation error message that immediately explains what was wrong with the payload.

Best Practices

  • Assert the specific expected status code for creation endpoints, not just "any success."
  • Validate both echoed-back fields and server-generated fields (ID, timestamp) after creation.
  • Test validation-error paths (missing/invalid fields) alongside the happy path.

Practice Exercise

Write a test that POSTs an order with a missing required field and asserts the API returns a 400 with a validation error message naming the missing field, then write a second test confirming a valid POST returns 201 with a correctly-formatted generated ID.

Summary

POST creates resources via a request body. Assert the specific expected status code (usually 201) rather than a loose success check, validate both echoed and server-generated fields, and remember POST has no built-in protection against duplicate creation on retry.

Interview Questions

Why might it be risky to automatically retry a failed POST request in a test, and what's a safer approach?▾
POST isn't idempotent — if the first request actually succeeded on the server but the response was lost (a timeout, a network blip), retrying creates a second, duplicate resource. A safer approach is to first check whether the resource already exists (a GET by some natural key) before retrying, or to rely on an idempotency key if the API supports one, rather than blindly resubmitting the same POST.
Why assert response.getStatusCode() == 201 specifically instead of just checking ok()?▾
ok() is true for any 2xx status; asserting the exact code catches an API that's technically succeeding but not following its own documented contract (returning 200 when 201 Created is the correct convention).
What should a thorough POST creation test validate beyond the fields that were sent?▾
Server-generated fields too — an ID matching an expected pattern, a creation timestamp — since that's exactly where a bug in ID generation or timestamping would actually show up.
Why is retrying a failed POST request risky?▾
POST isn't idempotent — if the first request actually succeeded but the response was lost, retrying creates a second, duplicate resource; a safer approach checks for existing data first or relies on an idempotency key.
What does the multipart option handle that .body() can't?▾
File uploads via API — .body() serializes structured data like JSON, while .multiPart() sends the raw multipart/form-data encoding files actually require.
