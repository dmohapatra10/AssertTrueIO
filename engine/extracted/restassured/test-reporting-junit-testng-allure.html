Test Reporting: JUnit, TestNG, Allure

Prerequisites: Parallel Execution & Thread Safety

What is this?

A test that fails silently, with no clear record of what happened, is nearly as unhelpful as no test at all — someone still has to manually re-run it locally to understand the failure. Reporting is about making test results genuinely useful without that extra step, especially in CI where nobody's watching the run live.

JUnit's Built-In Reports

# Generated automatically by Maven's Surefire plugin
target/surefire-reports/
├── com.example.api.tests.UserCreationTest.txt
└── com.example.api.tests.UserCreationTest.xml

Every Maven project running JUnit tests gets this for free, with zero configuration — an XML report (the format most CI systems, including GitHub Actions, know how to parse and display natively) and a plain-text summary. This is the baseline every project has automatically, before adding anything else.

TestNG Reports (If Your Project Uses TestNG)

test-output/
├── index.html      ← a browsable HTML report
├── emailable-report.html
└── testng-results.xml

TestNG's built-in HTML report is more immediately readable than JUnit's raw XML — a real advantage if a human is going to browse results directly rather than relying entirely on CI's own XML parsing. Recall from Chapter 2 that this course recommends JUnit 5 as the default, but if your project already uses TestNG, its native reporting is a reasonable, ready-made option.

Allure — Rich, Detailed Reporting

<dependency>
    <groupId>io.qameta.allure</groupId>
    <artifactId>allure-junit5</artifactId>
    <version>2.29.0</version>
</dependency>
@Test
@Description("Verifies a user can be created with valid data")
@Severity(SeverityLevel.CRITICAL)
void validUserCreationSucceeds() {
    Allure.step("Create user with valid data", () -> {
        given().body(validUser).when().post("/users").then().statusCode(201);
    });
}

Allure produces a genuinely rich, interactive HTML report — step-by-step breakdowns (via Allure.step(), similar in spirit to RestAssured's own request logging), severity levels, historical trend graphs across multiple runs, and screenshots/attachments where relevant. It requires more setup than JUnit's free default, but is worth it for a project where reporting quality genuinely matters to stakeholders beyond just the engineering team — a QA lead or a product manager who wants to browse results without reading raw XML.

Attaching Request/Response Details to Allure Reports

@Test
void createOrderWithFullRequestResponseLogging() {
    Response response = given().body(newOrder).when().post("/orders");

    Allure.addAttachment("Request Body", "application/json",
        new ObjectMapper().writeValueAsString(newOrder));
    Allure.addAttachment("Response Body", "application/json",
        response.getBody().asPrettyString());

    response.then().statusCode(201);
}

This combines Chapter 8's logging concepts with Allure's attachment mechanism — instead of (or alongside) console-based logging, the actual request and response get embedded directly into the report itself, viewable later without needing to re-run the test or dig through CI console logs.

Real-World Example — Layering Conditional Logging Into Reporting

public class ReportingUtils {
    public static void attachOnFailure(Response response, String testName) {
        if (response.getStatusCode() >= 400) {
            Allure.addAttachment(testName + " - Failure Response",
                "application/json", response.getBody().asPrettyString());
        }
    }
}

This is Chapter 8's .log().ifValidationFails() pattern, reimplemented for report attachments instead of console output — attaching full response detail to the report specifically on failure keeps successful test reports clean while still capturing everything needed to diagnose a failure, without anyone needing to re-run anything.

Failure Diagnostics — What a Good Report Actually Needs

  • What was being tested — a clear test name/description, ideally readable without opening the source code.
  • What was sent — the actual request (Chapter 8's request logging, or an Allure attachment).
  • What came back — the actual response, especially for a failure.
  • What was expected vs. actual — the specific assertion that failed and why.

A report missing any of these four forces someone to reproduce the failure locally just to understand what happened — exactly the extra step good reporting exists to eliminate.

❌ Fragile vs. ✅ Recommended

// ❌ A failure report with only "AssertionError: expected 200 but was 400" —
// no idea WHICH request, WHAT was sent, or WHY it failed
.then().statusCode(200);

// ✅ Enough context that the failure is diagnosable from the report alone
Allure.addAttachment("Request", "application/json", requestBodyJson);
.then().log().ifValidationFails().statusCode(200);

Common Mistakes

  • Relying on a bare assertion failure message alone with no request/response context attached — forces a local re-run to actually diagnose the failure.
  • Choosing a reporting tool based on features alone without considering setup cost relative to the project's actual needs — Allure is powerful but genuinely more setup than a small project may need.
  • Not making reports accessible to non-engineers who might need to review results — raw XML output is fine for CI parsing, but a human-readable HTML report matters if anyone outside engineering needs to look at results.

Edge Cases

  • Very large reports from a suite with hundreds of tests — consider whether attaching full request/response detail to every single test (not just failures) is sustainable at that scale, or whether the conditional/failure-only pattern is the more practical default.

Debugging

If a CI failure's report doesn't provide enough detail to diagnose without a local re-run, that's a signal the reporting setup itself needs improvement — add request/response attachments (or conditional logging output) rather than accepting "just re-run it locally" as a normal workflow.

Best Practices

  • Ensure every report includes enough context (request, response, expected vs. actual) to diagnose a failure without re-running locally.
  • Use conditional attachment/logging (failure-only) to keep reports clean for passing tests while thorough for failing ones.
  • Choose a reporting tool proportional to the project's actual needs — JUnit's free default for a small project, Allure once richer reporting genuinely adds value.

Practice Exercise

Add Allure to a sample project, annotate a few tests with @Description and @Severity, and implement a conditional attachment helper that only attaches the full response body to the report when a test actually fails.

Summary

JUnit's built-in reports are free and CI-friendly out of the box; TestNG's native HTML reports are a solid option if that's your existing framework; Allure offers genuinely rich, interactive reporting worth the extra setup once a project's reporting needs go beyond CI parsing alone. Whatever the tool, a good report needs enough context — what was tested, what was sent, what came back — to diagnose a failure without a local re-run.

Interview Questions

Why is attaching request/response details specifically on failure (not on every test) usually the better default?▾
Attaching full request/response detail to every single test, including hundreds of passing ones, produces a large, noisy report where the signal (the handful of actual failures) gets buried in detail nobody needs for a passing test. Conditional attachment — only capturing the detail when a test actually fails — mirrors the same principle behind Chapter 8's .log().ifValidationFails(): stay clean and quiet when everything's fine, but automatically capture everything needed the moment something actually goes wrong, which is precisely when that detail becomes valuable.
