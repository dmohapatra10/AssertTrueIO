GET Requests

Prerequisites: Building HTTP Requests overview

What is this?

given()
.when()
    .get("/users/2")
.then()
    .statusCode(200);

GET retrieves data without changing anything on the server — no request body, and by REST convention, no side effects. This is the method behind almost every "read" scenario you'll automate: fetching a single resource, listing a filtered collection, paging through results.

Why it's important

GET is usually the first method engineers reach for, since it's the simplest and safest — but "simple" doesn't mean there's nothing to get wrong. Query parameter construction, pagination correctness, and knowing exactly what a "not found" response should look like are where most real GET-related bugs in test suites actually live.

Basic Example — Fetching a Single Resource

given()
    .pathParam("id", 2)
.when()
    .get("/users/{id}")
.then()
    .statusCode(200)
    .body("data.id", equalTo(2));

Detailed Example — Fetching a Filtered Collection

given()
    .queryParam("status", "active")
    .queryParam("role", "admin")
.when()
    .get("/users")
.then()
    .statusCode(200)
    .body("data.status", everyItem(equalTo("active")))
    .body("data.role", everyItem(equalTo("admin")));

Notice the assertion checks that every returned item actually satisfies both filters — not just that the response came back non-empty. This catches a partially-broken filter (one that correctly narrows by status but ignores role) that a simple "results exist" assertion would miss entirely.

Real-World Example — Pagination Correctness

@Test
void paginationReturnsDistinctPages() {
    Response page1 = given().queryParam("page", 1).queryParam("limit", 10).when().get("/products");
    Response page2 = given().queryParam("page", 2).queryParam("limit", 10).when().get("/products");

    List<Integer> page1Ids = page1.jsonPath().getList("data.id", Integer.class);
    List<Integer> page2Ids = page2.jsonPath().getList("data.id", Integer.class);

    assertThat(page1Ids, hasSize(10));
    assertThat(Collections.disjoint(page1Ids, page2Ids), is(true)); // no overlap between pages
}

This is the single most valuable pagination test you can write, and the one most often skipped: confirming the item count is correct doesn't catch a broken pagination implementation that silently returns the same page of data regardless of the page parameter. Checking that the actual IDs differ between pages catches that class of bug directly.

Testing the Empty-Result Case

@Test
void searchWithNoMatchesReturnsEmptyArrayNot404() {
    given()
        .queryParam("q", "zzz-no-such-product-exists-zzz")
    .when()
        .get("/products/search")
    .then()
        .statusCode(200) // still 200 — a search with no matches is not an error
        .body("data", hasSize(0));
}

A search or filter returning zero matches is a legitimate, successful outcome — it should return 200 with an empty array, not an error status. This is an easy case to leave completely uncovered, since most manual testing naturally gravitates toward queries that actually return something.

❌ Fragile vs. ✅ Recommended

// ❌ Only checking that SOME results came back — a broken filter that ignores
// the "role" parameter entirely would still pass this
.then().body("data", hasSize(greaterThan(0)));

// ✅ Confirming every result actually satisfies the filter
.then().body("data.role", everyItem(equalTo("admin")));

Common Mistakes

  • Only checking result count after a filtered or paginated request, not the actual content — a count can be correct while the underlying data is wrong (a repeated page, an ignored filter).
  • Never testing the empty-result case for a search or filter endpoint — an easy path to leave uncovered.
  • Assuming a GET has literally zero side effects on every real API — while this is the REST convention, a poorly designed API occasionally violates it (a GET that increments a view counter); worth confirming for APIs you don't control.

Edge Cases

  • Very large limit/page-size values — worth testing that the API caps them sensibly rather than allowing a client to force an unbounded response.
  • A GET for a resource that was recently deleted — should return 404, not a stale cached copy; worth testing explicitly if the API has any caching layer.

Debugging

If a GET returns unexpected data, log the fully resolved URL with .log().all() to confirm the query parameters were actually encoded and sent the way you expect, rather than assuming the .queryParam() calls were interpreted correctly.

Best Practices

  • Validate actual returned content for filtered/paginated requests, not just counts.
  • Test the empty-result case explicitly for any search or filter endpoint.
  • For pagination, confirm consecutive pages return genuinely different data, not just the right count.

Practice Exercise

Write a test that fetches three pages of a paginated endpoint and asserts that no item ID appears on more than one page, confirming pagination doesn't silently duplicate results.

Summary

GET requests retrieve data without side effects. Beyond the basic single-resource fetch, real GET testing means validating that filters actually filter (checking every returned item, not just the count), that pagination returns genuinely distinct pages, and that an empty result set is treated as a valid 200, not an error.

Interview Questions

Why is asserting only the item count insufficient when testing a paginated or filtered GET endpoint?▾
A correct count can coexist with wrong data — a broken pagination implementation might return the same items regardless of the requested page, or a broken filter might return the right number of items while ignoring the filter criteria entirely. Asserting on the actual returned content (specific IDs across pages, or that every item satisfies the filter) is what actually catches those bugs; count alone doesn't.
Why should a pagination test check actual item IDs across pages, not just that each page returns the right count?▾
A broken implementation could silently return the same page of data regardless of the page parameter — the count would still be correct while the underlying data is wrong; checking IDs differ catches that specific bug.
Is it acceptable for a search with no matches to return a 404?▾
No — a search or filter returning zero results is a legitimate, successful outcome and should return 200 with an empty array, not an error status.
Why test that every item in a filtered result satisfies the filter, not just that results came back non-empty?▾
A partially broken filter (correctly narrowing by one criterion but ignoring another) would still pass a simple non-empty check; asserting every item actually matches catches that partial failure.
What's a legitimate reason a GET request might have a side effect, despite REST convention?▾
A poorly designed API might increment a view counter or similar on a GET — worth confirming for third-party APIs you don't control, rather than assuming REST convention is always followed strictly.
