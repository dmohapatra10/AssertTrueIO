Conditional Logging

Prerequisites: Response Logging

What is this?

.then()
    .log().ifValidationFails()   // stays SILENT if the test passes
    .statusCode(200)
    .body("name", equalTo("John"));

.log().ifValidationFails() is the resolution to the tension the chapter overview raised: it prints nothing at all for a passing test, but automatically dumps the full response the instant any assertion in the same chain actually fails — exactly when you need the detail, and not a moment before.

Why it's important

This is the single most valuable logging pattern for real, committed test code — it gives you the debugging value of full logging without the CI-noise cost of always-on logging. Most production RestAssured codebases default to this pattern rather than either extreme (always logging, or never logging).

Basic Example

given()
    .pathParam("id", 2)
.when()
    .get("/users/{id}")
.then()
    .log().ifValidationFails()
    .statusCode(200)
    .body("data.first_name", equalTo("Janet"));

// If this passes: ZERO log output
// If this fails: the full response prints automatically, right in the failure output

ifError() — A Related but Distinct Variant

.then()
    .log().ifError()  // logs only if the STATUS CODE indicates an error (4xx/5xx)
    .statusCode(200);

.log().ifError() triggers based specifically on the response's status code falling in the error range, independent of whether your own assertions pass or fail. This is a subtly different trigger condition from ifValidationFails() — a response could have a successful 200 status while still failing one of your body assertions (in which case ifError() would stay silent but ifValidationFails() would trigger), or conversely return a 500 that you're deliberately testing for and asserting against successfully (in which case ifError() triggers even though your test is passing).

Detailed Example — Choosing the Right Trigger for the Situation

@Test
void mostTestsWantIfValidationFails() {
    // The common case: log only when something you asserted didn't match
    given().when().get("/users/2").then()
        .log().ifValidationFails()
        .statusCode(200)
        .body("data.id", equalTo(2));
}

@Test
void deliberatelyTestingAnErrorResponse() {
    // Here, a 404 is the EXPECTED, correct outcome — ifError() would
    // log every time this test runs (even though it's passing), which
    // is noise; ifValidationFails() is still the better choice here too
    given().pathParam("id", 999999).when().get("/users/{id}").then()
        .log().ifValidationFails()
        .statusCode(404);
}

In practice, ifValidationFails() is the right default for nearly every test — it directly tracks whether the assertions you actually wrote passed, which is what you actually care about. ifError() is a narrower tool, more useful for exploratory or monitoring-style scripts that want visibility into any error response regardless of what's being explicitly asserted.

Real-World Example — A Team-Wide Default

// A shared base test class establishing the team convention
public abstract class BaseApiTest {
    protected ValidatableResponse validate(Response response) {
        return response.then().log().ifValidationFails();
    }
}

// Individual tests use it consistently, without each one repeating the log() call
public class UserApiTest extends BaseApiTest {
    @Test
    void getUser() {
        Response response = given().pathParam("id", 2).when().get("/users/{id}");
        validate(response).statusCode(200).body("data.id", equalTo(2));
    }
}

Baking conditional logging into a shared base class or helper method means every test in the project gets clean-by-default, detailed-on-failure output automatically, without every individual test author needing to remember to add it themselves.

❌ Fragile vs. ✅ Recommended

// ❌ No logging at all — a CI failure gives you a bare assertion
// message with no context about what the actual response looked like
.then().statusCode(200).body("data.id", equalTo(2));

// ✅ Silent when passing, fully detailed the moment something fails
.then().log().ifValidationFails().statusCode(200).body("data.id", equalTo(2));

Common Mistakes

  • Using .log().all() in committed code "to be safe," when ifValidationFails() gives strictly more useful information (only appears on genuine failures) at a fraction of the log volume.
  • Choosing ifError() when ifValidationFails() is actually the better fit — for most tests, what you care about is whether your assertions passed, not the raw status code range in isolation.
  • Not standardizing conditional logging as a team convention — inconsistent logging across a codebase means some failures are easy to debug and others aren't, depending on which pattern the original author happened to use.

Edge Cases

  • A test with multiple separate .then() chains (rare, but possible) — conditional logging only covers the chain it's actually attached to; a failure in a separate, unlogged chain won't trigger it.
  • Assertions that throw before reaching .then() at all (a NullPointerException from bad test setup, for instance) — conditional response logging can't help here, since there's no response validation step to trigger from; this is a different failure category entirely.

Debugging

If a CI failure lacks the detail you need despite conditional logging being in place, confirm .log().ifValidationFails() is actually positioned within the same .then() chain as the assertion that failed — it only captures failures in its own chain, not globally.

Best Practices

  • Default to .log().ifValidationFails() in essentially all committed test code — it's the right balance for the overwhelming majority of cases.
  • Consider baking it into a shared base class or helper method so the whole team gets it consistently, without repeating it in every test.
  • Reserve .log().all() for active, temporary local debugging only.

Practice Exercise

Take a test with a deliberately wrong assertion (one that will fail), add .log().ifValidationFails(), and run it — confirm the full response prints automatically. Then fix the assertion so the test passes, and confirm the log output disappears entirely on the next run.

Summary

.log().ifValidationFails() is the standard, recommended logging pattern for real test code — silent when a test passes, automatically detailed the moment any assertion in its chain fails. This resolves the core tension between debugging usefulness and CI noise better than either always-on or always-off logging, and is worth establishing as a team-wide default via a shared base class.

Interview Questions

What's the difference between log().ifValidationFails() and log().ifError(), and when might they behave differently for the same test?▾
ifValidationFails() triggers based on whether the assertions you actually wrote pass or fail. ifError() triggers based on the response's status code falling in the 4xx/5xx range, regardless of your assertions. They diverge in two cases: a 200 response that still fails one of your body assertions (ifValidationFails triggers, ifError stays silent), and a deliberately-tested error response — like asserting a 404 is correctly returned — where the test passes but ifError still triggers because the status code itself is in the error range. For most tests, ifValidationFails is the more useful default since it directly tracks what you actually care about: did my assertions pass.
Why is .log().ifValidationFails() considered the standard pattern for committed test code?▾
It's silent for a passing test but automatically dumps the full response the moment an assertion in its chain fails — full debugging value with none of the CI-noise cost of always-on logging.
What's the actual difference between ifValidationFails() and ifError()?▾
ifValidationFails() triggers based on whether YOUR assertions passed; ifError() triggers based on the response's status code alone, regardless of what you actually asserted — they diverge whenever a test deliberately expects an error status and passes.
Why might baking conditional logging into a shared base class be better than repeating it per test?▾
Every test in the project gets clean-by-default, detailed-on-failure output automatically, without individual authors needing to remember to add the logging call themselves.

A test deliberately asserting a 404 is correctly returned — the status code IS in the error range even though the test's own assertion (expecting exactly that) succeeds; ifValidationFails() would correctly stay silent here, but ifError() would still fire.
