Prerequisites: Advanced Response Validation

Testing What Should Fail, Not Just What Should Work

Earlier pages have occasionally tested a failure case in passing — an invalid email here, a missing token there. Negative testing deserves treatment as its own systematic discipline, not an afterthought bolted onto happy-path tests. Six pages:

  1. Validation Errors: 400 & 422 — missing fields, wrong types, malformed JSON
  2. Authentication & Authorization Errors — 401 and 403, tested systematically
  3. Resource Errors: 404 & 409 — invalid IDs and duplicate data
  4. Rate Limiting & Server Errors — 429 and 500, and unsupported methods
  5. Verifying Error Response Structure — not just the status code, the whole error shape
  6. Why Negative Testing Matters — the case for why this often matters more than the happy path

Positive Testing vs. Negative Testing

Positive testing confirms a valid request produces the expected successful response — nearly everything tested so far in this course. Negative testing confirms an invalid request is handled correctly — rejected with the right status code, the right error message, and no unintended side effects. Both matter, but the pages ahead are specifically about the second half, which real suites systematically under-invest in.

The Eleven Negative Scenarios, at a Glance

Missing required field       → 400
Invalid data type            → 400
Invalid email format         → 400 or 422
Malformed JSON               → 400
Invalid token                → 401
Expired token                → 401
Missing authorization        → 401
Insufficient permissions     → 403
Invalid ID                   → 404
Duplicate data               → 409
Unsupported HTTP method      → 405

These eleven scenarios recur across almost every API you'll ever test — the specific status codes an API returns for each may vary slightly (some use 422 where others use 400, for instance), but the categories of thing that can go wrong are remarkably consistent, which is exactly why this chapter organizes around them systematically rather than treating each as a one-off.

Why This Chapter Comes After (Not Before) Everything Else

Writing genuinely good negative tests draws on nearly every earlier chapter: request construction (Chapter 3) to deliberately send something wrong, response validation (Chapter 4) to verify the error came back correctly, authentication (Chapter 6) to test invalid/expired credentials specifically, and test data management (Chapter 10) to generate realistic invalid inputs rather than just one hardcoded bad example. This chapter is where all of that comes together with a specific, deliberate focus.

Interview Questions

What's the fundamental difference between positive and negative testing?▾
Positive testing confirms a valid request produces the expected successful response; negative testing confirms an INVALID request is handled correctly — rejected with the right status, message, and no unintended side effects.
Why do the eleven negative scenarios in this chapter recur across almost every API?▾
The specific status codes an API uses for each might vary slightly, but the CATEGORIES of things that can go wrong (missing fields, bad auth, non-existent resources, conflicts) are remarkably consistent across different APIs.
Why does this chapter draw on nearly every earlier chapter in the course?▾
Writing good negative tests needs request construction (to deliberately send something wrong), response validation (to verify the error came back correctly), authentication (for invalid/expired credential testing), and test data management (for realistic invalid inputs).
What's the difference between 422 and 400 where an API distinguishes them?▾
400 conventionally means malformed at the protocol/syntax level; 422 means well-formed but semantically invalid — a business rule violation rather than a structural one; not every API observes this distinction consistently.
