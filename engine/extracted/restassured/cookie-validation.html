Cookie Validation

Prerequisites: Response Size & Time Validation

What is this?

Chapter 1 mentioned cookies briefly as a mechanism sometimes used for session-based authentication. This page gives them the full treatment — reading, setting, and validating cookies in RestAssured, which matters for any API sitting behind a cookie-based session (common in APIs that share infrastructure with a traditional server-rendered web app).

Reading Cookies From a Response

Response response = given().body(credentials).when().post("/login");

String sessionId = response.getCookie("SESSION_ID");
Map<String, String> allCookies = response.getCookies();

.getCookie() reads a single cookie's value by name; .getCookies() returns all of them as a map — the same extraction-not-validation distinction from Chapter 4 applies here, both are reads with no pass/fail judgment attached.

Validating a Cookie Was Set

.then()
    .cookie("SESSION_ID", notNullValue())
    .cookie("SESSION_ID", matchesPattern("^[a-zA-Z0-9]{32}$")); // format validation

Just like headers and body fields, cookies support the full range of Hamcrest matchers — presence checks, exact values, or pattern matching against an expected format.

Sending Cookies on a Request

given()
    .cookie("SESSION_ID", sessionId)
.when()
    .get("/profile")
.then()
    .statusCode(200);

This is the request-side counterpart — attaching a cookie (typically one extracted from an earlier login response) to a subsequent request, the cookie-based equivalent of the Bearer token reuse pattern from Chapter 6.

Detailed Example — Cookie Attributes (Not Just the Value)

Response response = given().body(credentials).when().post("/login");

Cookie sessionCookie = response.getDetailedCookie("SESSION_ID");

assertThat(sessionCookie.isHttpOnly(), is(true));   // not accessible via client-side JavaScript
assertThat(sessionCookie.isSecure(), is(true));      // only sent over HTTPS
assertThat(sessionCookie.getSameSite(), equalTo("Strict"));
assertThat(sessionCookie.getMaxAge(), greaterThan(0));

A cookie's value is often less security-relevant than its attributes. HttpOnly, Secure, and SameSite are real security controls — testing that a session cookie actually has them set correctly is a legitimate, valuable security-adjacent test, not just a functional nicety. getDetailedCookie() (as opposed to the plain getCookie() shown earlier) is what exposes these attributes, not just the raw value.

Real-World Example — A Full Cookie-Based Session Lifecycle Test

@Test
void cookieBasedSessionWorksEndToEnd() {
    // 1. Login — capture the session cookie
    Response loginResponse = given().body(credentials).when().post("/login");
    loginResponse.then().statusCode(200);
    String sessionId = loginResponse.getCookie("SESSION_ID");
    assertThat(sessionId, is(notNullValue()));

    // 2. Use the cookie on a subsequent authenticated request
    given().cookie("SESSION_ID", sessionId).when().get("/profile")
        .then().statusCode(200);

    // 3. Logout — confirm the session is actually invalidated server-side
    given().cookie("SESSION_ID", sessionId).when().post("/logout")
        .then().statusCode(200);

    // 4. The SAME cookie should no longer work after logout
    given().cookie("SESSION_ID", sessionId).when().get("/profile")
        .then().statusCode(401);
}

Step 4 is the test most suites skip — confirming that logout genuinely invalidates the session server-side, not just that the client discards the cookie locally. A session that's still technically valid after "logout" (if an attacker somehow retained the cookie value) is a real, meaningful security gap this specific test is designed to catch.

❌ Fragile vs. ✅ Recommended

// ❌ Only testing that login sets SOME cookie, never its security attributes
.then().cookie("SESSION_ID", notNullValue());

// ✅ Testing the attributes that actually matter for session security
Cookie sessionCookie = response.getDetailedCookie("SESSION_ID");
assertThat(sessionCookie.isHttpOnly(), is(true));
assertThat(sessionCookie.isSecure(), is(true));

Common Mistakes

  • Only checking a session cookie's presence and value, never its security attributes (HttpOnly, Secure, SameSite) — misses a real, testable security concern.
  • Not testing that logout actually invalidates the session server-side, only that the login/cookie mechanism works in the forward direction.
  • Confusing getCookie() and getDetailedCookie() — the former only gives you the raw value; the latter is what you need for attribute-level assertions.

Edge Cases

  • Cookies with an expiration set in the past or a very short max-age — worth testing that an expired session cookie is correctly rejected, similar to token expiration testing from Chapter 6.
  • Multiple cookies with related but distinct purposes (a session cookie and a separate CSRF token cookie) — test each independently rather than assuming one cookie's presence implies the other is also correctly configured.

Debugging

If a cookie-dependent request unexpectedly fails, log the request (Chapter 8) to confirm the cookie is actually being sent, and check whether it matches the exact name and value the server set — a cookie name typo produces the same practical failure as a missing cookie, but looks different if you're specifically checking for it.

Best Practices

  • Test both a session cookie's value/presence and its security attributes (HttpOnly, Secure, SameSite).
  • Explicitly test that logout invalidates a session server-side, not just that the login flow works.
  • Use getDetailedCookie() whenever attribute-level validation matters, not just the raw value.

Summary

Cookie validation in RestAssured covers reading (.getCookie()/.getDetailedCookie()), sending (.cookie() on a request), and asserting (.then().cookie(...)) — with the security-relevant attributes (HttpOnly, Secure, SameSite) deserving explicit testing, not just the raw cookie value. A full session lifecycle test — login, use, logout, and confirm the old session no longer works — catches a real security gap that a login-only test would miss entirely.

Interview Questions

Why is testing that a logout request actually invalidates the session server-side more important than just confirming the login flow sets a valid cookie?▾
A client can always simply discard a cookie locally, but that alone doesn't prove the server has actually invalidated the underlying session — if an old cookie value is somehow retained or intercepted (a security concern in its own right), it might still work against the API even after the user believes they've logged out. Testing that the exact same cookie value is rejected with a 401 after a logout request confirms the server genuinely invalidated the session, not just that the client-side flow completed — a meaningfully stronger and more security-relevant guarantee.
Why is testing a session cookie's attributes as important as testing its value?▾
HttpOnly, Secure, and SameSite are real security controls, not just metadata — a cookie's value being present says nothing about whether it's actually protected against the specific threats those attributes exist to mitigate.
What's the difference between getCookie() and getDetailedCookie()?▾
getCookie() returns only the raw value; getDetailedCookie() exposes the full Cookie object including its security attributes (HttpOnly, Secure, SameSite, max-age) — needed for attribute-level assertions.
Why is confirming logout actually invalidates a session server-side a meaningful test, not just a nice-to-have?▾
A client can always discard a cookie locally regardless of server state — proving the exact same cookie value is rejected with 401 AFTER logout confirms the server genuinely invalidated the session, a real security guarantee a login-only test wouldn't verify.
Why might sending a cookie on a request be considered the request-side counterpart to Bearer token reuse?▾
Both patterns extract a credential from an earlier response (login) and attach it to subsequent requests — the same underlying reuse pattern, just carried via a cookie instead of an Authorization header.
