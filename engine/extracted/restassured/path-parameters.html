Path Parameters

Prerequisites: Query Parameters

What is this?

given()
    .pathParam("id", 123)
.when()
    .get("/users/{id}");
// Resulting URL: /users/123

.pathParam() fills a named placeholder ({id}) inside the URL string itself — used specifically for values that identify which resource a request is about, not for filtering or sorting a collection (that's what query parameters, covered on the previous page, are for).

Named Matching, Not Positional

given()
    .pathParam("orderId", 500)
    .pathParam("customerId", 42)
.when()
    .get("/customers/{customerId}/orders/{orderId}");
// Correctly resolves regardless of the ORDER the .pathParam() calls appear in —
// RestAssured matches by NAME against the {placeholder} in the URL string

This matters in practice: you can declare .pathParam() calls in whatever order is most readable, and RestAssured still resolves each one against its matching {name} placeholder correctly, regardless of the URL's actual placeholder order.

Multiple Path Parameters — A Nested Resource

given()
    .pathParam("customerId", 42)
    .pathParam("orderId", 500)
.when()
    .get("/customers/{customerId}/orders/{orderId}")
.then()
    .statusCode(200);

Nested resource URLs like this are common in real APIs — an order genuinely belongs to a specific customer, and the URL structure reflects that relationship directly. Both path parameters identify part of "which specific resource" the request is about.

Real-World Example — Path Params Combined with a Request Body

given()
    .pathParam("customerId", 42)
    .contentType(ContentType.JSON)
    .body(newOrder)
.when()
    .post("/customers/{customerId}/orders")
.then()
    .statusCode(201);

This is a common real shape: a path parameter identifying the parent resource (which customer), combined with a body describing what to create (the new order) — the path says where, the body says what.

URL Encoding of Path Parameter Values

given()
    .pathParam("username", "john doe") // contains a space
.when()
    .get("/users/{username}");
// RestAssured automatically encodes this to /users/john%20doe

Just like query parameters, path parameter values are URL-encoded automatically — a value containing a space, a slash, or other reserved character is transformed into its safe encoded form without any extra effort on your part. This is another concrete reason to prefer .pathParam() over manual string concatenation: forgetting to encode a value by hand produces a URL that looks fine in your test code but is actually malformed on the wire, often manifesting as a confusing 404.

Detailed Example — A Realistic Three-Level Resource Hierarchy

@Test
void getSpecificReviewForAProduct() {
    given()
        .pathParam("storeId", "store-42")
        .pathParam("productId", "prod-1001")
        .pathParam("reviewId", "rev-77")
    .when()
        .get("/stores/{storeId}/products/{productId}/reviews/{reviewId}")
    .then()
        .statusCode(200)
        .body("rating", greaterThanOrEqualTo(1));
}

Three levels of nesting is about as deep as path-based resource identification comfortably goes in most well-designed APIs — each level narrows down to a more specific resource, and every one of the three values here is genuinely part of "which resource," not a filter or sort criterion, which is exactly what makes path parameters the correct tool for all three.

❌ Fragile vs. ✅ Recommended

// ❌ Manually building the URL with string concatenation
given().when().get("/users/" + userId);

// ✅ Named path parameter — clearer intent, and RestAssured
// handles any necessary encoding of the value automatically
given().pathParam("id", userId).when().get("/users/{id}");

Common Mistakes

  • Using a query parameter where a path parameter belongs — sending ?id=123 instead of /users/123 when the API's actual routing expects the latter produces a completely different (likely non-matching) URL.
  • Forgetting to declare a .pathParam() for every {placeholder} in the URL string — RestAssured throws a clear error here, but it's an easy thing to miss when copy-pasting a URL template.
  • String-concatenating a URL manually instead of using named path parameters — works for simple cases, but loses the encoding safety and readability of the named approach.

Edge Cases

  • Path parameter values containing special characters (a resource ID that happens to include a slash or other reserved character) — RestAssured URL-encodes the value automatically, which is exactly the safety lost by manual string concatenation.
  • Very deeply nested resource paths (three or more path parameters) — worth pausing to consider whether the API design itself, not your test code, has gotten unnecessarily complex; this is sometimes a genuine API design smell worth flagging.

Debugging

If a request against a path-parameterized URL returns an unexpected 404, confirm the resolved URL is actually what you expect via .log().all() — a typo'd parameter name (one that doesn't match any {placeholder} in the URL string) fails clearly, but a wrong value for a correctly-named parameter just produces a URL pointing at the wrong (or non-existent) resource.

Best Practices

  • Always use named .pathParam() calls rather than manual URL string concatenation.
  • Reserve path parameters specifically for values that identify which resource is being addressed — not for filtering or sorting, which belongs in query parameters.
  • Name your path parameters to exactly match their {placeholder} in the URL string, even though matching is by name rather than order — consistent naming avoids confusion when reading the code later.

Practice Exercise

Write a test against a nested resource URL with two path parameters (a parent and child ID), declaring the .pathParam() calls in the opposite order from how they appear in the URL string, and confirm via .log().all() that the resolved URL is still correct.

Summary

.pathParam() fills named {placeholder} values in a URL string, matched by name rather than declaration order — the correct tool for identifying which specific resource (or nested resource) a request addresses, as distinct from query parameters, which filter or shape a request against a collection that already exists independent of them.

Interview Questions

Does the order in which you call .pathParam() need to match the order placeholders appear in the URL string?▾
No — RestAssured matches each .pathParam() call to its corresponding {placeholder} in the URL by name, not by the order the calls appear in your code. You can declare .pathParam("orderId", ...) before .pathParam("customerId", ...) even if the URL string is /customers/{customerId}/orders/{orderId}, and it resolves correctly either way — what matters is that every name used matches a placeholder actually present in the URL.
Does the order you declare .pathParam() calls need to match their order in the URL?▾
No — RestAssured matches each .pathParam() call to its {placeholder} by NAME, not by declaration order, so you can declare them in whatever order is most readable.
Are path parameter values automatically URL-encoded?▾
Yes — a value containing a space or reserved character is encoded automatically, which is exactly the safety lost by manually concatenating a URL string instead.
Why might a very deeply nested path (four or more parameters) be worth questioning?▾
It can be a sign the API's own resource design has gotten unnecessarily complex — worth flagging as a design consideration, not just something to work around in test code.
What happens if a URL template has a {placeholder} with no matching .pathParam() call?▾
RestAssured throws a clear error — an easy thing to miss when copy-pasting a URL template, but it fails loudly rather than silently sending a malformed URL.
