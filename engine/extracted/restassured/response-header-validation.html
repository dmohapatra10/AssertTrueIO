Response Header Validation

Prerequisites: Status Code Validation

What is this?

.then()
    .header("Content-Type", equalTo("application/json; charset=utf-8"));

Response headers carry metadata alongside the body — content type, caching rules, rate-limit counters, pagination hints. Validating them means asserting that metadata is correct, the same way you'd validate any other part of the response.

Why header validation is easy to skip — and why that's a mistake

Headers feel secondary compared to the body, so they're often the first thing left out of a test. But if an API's real contract includes specific headers — a required Content-Type, a rate-limit header clients depend on, a pagination total in a header rather than the body — skipping header checks means that part of the contract is completely unverified by your suite, even if everything else looks thorough.

Basic Example — Single Header

.then()
    .header("Content-Type", containsString("application/json"));

Multiple Headers at Once

.then()
    .headers(
        "Content-Type", containsString("application/json"),
        "X-RateLimit-Remaining", notNullValue(),
        "Cache-Control", containsString("no-cache")
    );

.headers(...) takes alternating name/matcher pairs, letting you validate several headers in one fluent call instead of chaining multiple separate .header() calls — purely a readability convenience, functionally identical to chaining.

Detailed Example — Rate Limit Headers

@Test
void rateLimitHeadersArePresent() {
    given()
    .when()
        .get("/users")
    .then()
        .statusCode(200)
        .header("X-RateLimit-Limit", notNullValue())
        .header("X-RateLimit-Remaining", notNullValue());
}

Many production APIs expose rate-limit information via headers rather than the body — testing that these headers exist (and, where relevant, that the remaining count decreases across requests) is genuinely useful coverage for any client relying on them to throttle its own request rate.

Real-World Example — Full Header + Status + Body Check

given()
    .pathParam("id", 2)
.when()
    .get("/users/{id}")
.then()
    .statusCode(200)
    .header("Content-Type", containsString("application/json"))
    .body("data.id", equalTo(2));

This is the natural shape of a well-rounded validation chain — status, then the headers that matter for this specific endpoint, then body content — each check catching a different class of regression the others wouldn't.

❌ Fragile vs. ✅ Recommended

// ❌ Hardcoding an exact Content-Type string including charset, which
// can vary slightly between server configurations without being wrong
.then().header("Content-Type", equalTo("application/json; charset=utf-8"));

// ✅ containsString() is more resilient to harmless formatting differences
.then().header("Content-Type", containsString("application/json"));

Extracting a Header's Value (Not Just Asserting It)

Response response = given().when().get("/users");
String contentType = response.getHeader("Content-Type");
String rateLimitRemaining = response.getHeader("X-RateLimit-Remaining");

// Or extract all headers at once
Headers allHeaders = response.getHeaders();
for (Header h : allHeaders) {
    System.out.println(h.getName() + ": " + h.getValue());
}

Sometimes you need a header's value for something other than an immediate assertion — passing a pagination cursor into the next request, or logging a rate-limit value for later analysis. .getHeader() reads a single header by name with no pass/fail judgment attached, the same extraction-not-validation distinction covered fully later in this chapter.

Real-World Example — Using an Extracted Header for Pagination

Response firstPage = given().queryParam("limit", 20).when().get("/users");
String nextCursor = firstPage.getHeader("X-Next-Cursor");

if (nextCursor != null) {
    given()
        .queryParam("cursor", nextCursor)
        .queryParam("limit", 20)
    .when()
        .get("/users")
    .then()
        .statusCode(200);
}

Some APIs expose cursor-based pagination entirely through headers rather than the response body — this pattern (extract a header, feed it into the next request) is the RestAssured equivalent of the API chaining pattern covered fully in Chapter 7, just threaded through a header instead of a body field.

Common Mistakes

  • Skipping header validation entirely because it "feels secondary" — a real contract regression in headers goes completely uncaught.
  • Using exact string equality for Content-Type when a substring check would be more resilient to legitimate formatting variance (charset ordering, casing).
  • Not testing headers that the API's actual clients depend on (rate limits, pagination) just because they're not in the response body.

Edge Cases

  • Case sensitivity — HTTP header names are case-insensitive by spec, and RestAssured's .header() lookup respects this; header values, however, are matched exactly as written by whatever matcher you use.
  • Headers that only appear conditionally (an ETag only on cacheable responses) — don't assert their presence universally if the API's contract doesn't guarantee them on every response.

Debugging

If a header assertion fails unexpectedly, print all response headers with response.getHeaders() or .log().headers() to see the actual full set — a header you expected might be present under slightly different casing or a completely different name than assumed.

Best Practices

  • Validate headers that are actually part of the API's contract, not exhaustively every header present.
  • Prefer substring/contains matchers for values with legitimate minor formatting variance.
  • Combine header checks with status and body validation in the same logical test, rather than treating headers as a separate, optional concern.

Practice Exercise

Against a public API that returns pagination info in headers (or simulate one), write a test validating both the Content-Type header and a custom pagination header, alongside a standard status code and body check.

Summary

Header validation is often skipped but frequently carries real contract information — content type, caching, rate limits, pagination. .header() and .headers() validate them with the same Hamcrest matcher flexibility as body assertions, and substring matching is usually more resilient than exact equality for values with legitimate minor formatting differences.
