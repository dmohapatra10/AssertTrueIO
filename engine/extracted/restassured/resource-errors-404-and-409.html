Resource Errors: 404 & 409

Prerequisites: Authentication & Authorization Errors

What is this?

These two codes cover a genuinely different category of failure from validation or auth errors — the request itself is perfectly well-formed and properly authenticated, but the specific resource it's asking about either doesn't exist (404) or conflicts with something that already does (409).

404 — Invalid or Non-Existent ID

@Test
void requestingNonExistentResourceReturns404() {
    given()
        .pathParam("id", "99999999") // an ID that (almost certainly) doesn't exist
    .when()
        .get("/users/{id}")
    .then()
        .statusCode(404);
}

404 — Malformed ID (A Distinct Sub-Case)

@Test
void malformedIdFormatReturns404OrBadRequest() {
    given()
        .pathParam("id", "not-a-valid-id-format")
    .when()
        .get("/users/{id}")
    .then()
        .statusCode(anyOf(is(404), is(400))); // APIs vary in how they handle this
}

Worth being precise about which is which: a numeric ID that's syntactically valid but doesn't correspond to any real record is unambiguously a 404. An ID that's structurally wrong (a string where a UUID is expected, for instance) is more ambiguous — some APIs treat it as "not found" (404), others as "bad request" (400), and it's worth confirming which your specific API actually does rather than assuming.

409 — Duplicate Data

@Test
void creatingDuplicateEmailReturns409() {
    String sharedEmail = "duplicate-" + UUID.randomUUID() + "@example.com";

    given().body(Map.of("email", sharedEmail, "name", "First")).when().post("/users")
        .then().statusCode(201);

    given().body(Map.of("email", sharedEmail, "name", "Second")).when().post("/users")
        .then().statusCode(409);
}

This is the exact pattern from Chapter 10's Static vs. Dynamic Test Data page, revisited here specifically as a negative test — the shared email needs to be dynamically generated (to avoid colliding with a previous test run) while still being deliberately reused within this one test (to trigger the actual conflict being tested).

Detailed Example — Testing an Update That Creates a Conflict

@Test
void updatingToAnAlreadyTakenEmailReturns409() {
    String existingEmail = createAUserAndReturnTheirEmail();
    String userIdToUpdate = createAnotherUserAndReturnTheirId();

    given()
        .pathParam("id", userIdToUpdate)
        .body(Map.of("email", existingEmail)) // trying to take an email that's already someone else's
    .when()
        .patch("/users/{id}")
    .then()
        .statusCode(409);
}

Duplicate conflicts aren't limited to creation — an update that would result in a conflict (two users ending up with the same unique field) needs the same rejection, and it's a genuinely distinct code path from the creation-time check, worth testing separately rather than assuming the same validation automatically applies to updates too.

Real-World Example — Combining Resource Errors With Cleanup

@Test
void deletedResourceReturns404OnSubsequentAccess() {
    String orderId = createATestOrderAndReturnItsId();

    given().pathParam("id", orderId).when().delete("/orders/{id}").then().statusCode(204);

    // The Chapter 7 pattern, revisited as an explicit negative test in its own right
    given().pathParam("id", orderId).when().get("/orders/{id}")
        .then().statusCode(404);
}

This is the same "verify deletion" step from Chapter 7's full CRUD chain — worth recognizing that it's also a legitimate negative test in its own right (confirming 404 is correctly returned for a resource that genuinely doesn't exist anymore), not just a chain-completeness check.

❌ Fragile vs. ✅ Recommended

// ❌ Using a fixed, hardcoded "non-existent" ID that might accidentally
// exist in some environments (or stop existing, breaking the test's assumption)
given().pathParam("id", "1").when().get("/users/{id}").then().statusCode(404);

// ✅ Using an ID virtually guaranteed not to exist, or one you KNOW was just deleted
given().pathParam("id", "999999999").when().get("/users/{id}").then().statusCode(404);
// or, more robustly: create then delete a resource, then check 404 against ITS specific ID

Common Mistakes

  • Using a low, "probably safe" ID like 1 or 2 to test 404, when that ID might legitimately exist in some environments — a genuinely-deleted resource's own ID is a more reliable way to guarantee non-existence.
  • Only testing duplicate detection on creation, never on update — these can be genuinely separate code paths with independently possible bugs.
  • Assuming malformed IDs always produce 404 — some APIs correctly return 400 for a structurally invalid ID instead; verify rather than assume.

Edge Cases

  • Soft-deleted resources (from Chapter 3's DELETE page) — a soft-deleted resource might still return 200 from a direct GET, which is correct for that API's design, not a 404 bug; know which delete semantics your API uses before writing this assertion.
  • Case-sensitivity in duplicate detection — does the API treat John@Example.com and john@example.com as duplicates? Worth testing explicitly if case-insensitive uniqueness is part of the API's actual contract.

Debugging

If a 404 test unexpectedly returns 200, confirm the "non-existent" ID you're using genuinely doesn't exist in whatever environment the test is running against — a hardcoded low ID is the most common cause of this specific false failure.

Best Practices

  • Use a resource you know was just deleted (rather than a guessed "probably safe" ID) for the most reliable 404 test.
  • Test duplicate detection on both creation and update, as potentially separate code paths.
  • Verify whether your specific API returns 404 or 400 for malformed (not just non-existent) IDs, rather than assuming.

Practice Exercise

Write a test that creates a resource, deletes it, and confirms a 404 on subsequent access using that specific resource's own ID (not a guessed "safe" ID) — then write a second test confirming that updating one resource to take another resource's unique field value correctly triggers a 409.

Summary

404 and 409 cover requests that are well-formed and properly authenticated but fail because of the specific resource's state — it doesn't exist, or it conflicts with something that does. The most reliable way to test 404 is against a resource you know was just deleted, not a guessed "probably safe" ID, and duplicate-conflict testing deserves coverage on both creation and update, since they're often genuinely separate code paths.

Interview Questions

Why is using a hardcoded ID like "1" to test a 404 response considered unreliable?▾
A low, hardcoded ID like 1 might legitimately correspond to a real record in some environments — a seed admin account, an early test fixture — which would make the test fail with an unexpected 200 instead of the intended 404, not because of a real bug but because the test's underlying assumption (that ID 1 doesn't exist) was wrong for that particular environment. A more reliable approach is to use an ID you can actually guarantee doesn't exist — either a very large, essentially-impossible-to-collide-with number, or better, the ID of a resource the test itself just created and deleted, which is verifiably non-existent at that point.
