JSON Body Validation

Prerequisites: Response Header Validation

What is this?

.then()
    .body("name", equalTo("John"));

The string "name" is a JsonPath expression — a way of addressing into a JSON structure by field name. This page covers the three shapes you'll validate constantly: flat fields, nested objects, and arrays.

Flat Fields

{ "name": "John", "active": true, "age": 30 }
.then()
    .body("name", equalTo("John"))
    .body("active", equalTo(true))
    .body("age", equalTo(30));

Nested Objects

{
  "name": "John",
  "address": {
    "city": "Delhi",
    "zip": "110001"
  }
}
.then()
    .body("address.city", equalTo("Delhi"))
    .body("address.zip", equalTo("110001"));

Dot notation walks into nested objects exactly as you'd describe the structure verbally — address.city reads almost identically to "the city field inside the address object." Arbitrarily deep nesting works the same way: a.b.c.d for four levels deep.

Arrays — Two Different Questions

{
  "users": [
    { "name": "John", "active": true },
    { "name": "Jane", "active": false }
  ]
}
// "Is John ANYWHERE in this array?" — membership, order doesn't matter
.then().body("users.name", hasItem("John"));

// "Is the array non-empty?"
.then().body("users.size()", greaterThan(0));

// "Is John SPECIFICALLY the first element?" — position matters
.then().body("users[0].name", equalTo("John"));

// Collecting a field from every array element into a list
.then().body("users.name", hasItems("John", "Jane"));

users.name (no index) collects the name field from every object in the array into a list — which is exactly why hasItem()/hasItems() (membership matchers) pair naturally with it. users[0].name is a different question entirely: it addresses one specific element by position, appropriate when order genuinely matters (the most recent item, the top search result) rather than just "is this value present somewhere."

Filtering Within an Array

// Find the name of whichever user has active == true
.then().body("users.find { it.active == true }.name", equalTo("John"));

JsonPath supports Groovy-style closures for filtering — genuinely useful once responses contain arrays where you need a specific element matching a condition, not just "any element" or "the element at position N." This becomes especially relevant once you reach the Advanced Response Validation chapter, where responses get considerably more complex.

Real-World Example — Validating a Realistic List Response

given()
.when()
    .get("/users")
.then()
    .statusCode(200)
    .body("data", hasSize(greaterThan(0)))
    .body("data.email", everyItem(containsString("@")))
    .body("data[0].id", notNullValue());

everyItem() is a strong pattern worth knowing: instead of checking one specific array element, it asserts that every element in the collected list satisfies a condition — every email contains an @, for instance — catching a data-quality regression that only affects some elements, which a single-index check would completely miss.

A Common Gotcha — Numeric Types

{ "id": 42, "price": 19.99 }
// ❌ This can fail with a type mismatch — JsonPath may parse "id" as
// Integer, and comparing it to a long or the wrong wrapper type can trip up equalTo()
.then().body("id", equalTo(42L)); // might fail — 42 (int) != 42L (long)

// ✅ Match the exact type JsonPath actually produces, or use a looser numeric matcher
.then().body("id", equalTo(42));           // int, matches JsonPath's default parsing
.then().body("price", equalTo(19.99f));    // JsonPath often parses decimals as Float

This is a genuinely common source of confusing failures for people new to RestAssured: equalTo() uses strict type equality, and JsonPath's default numeric parsing (int for whole numbers, float for decimals) doesn't always match the type you'd naturally reach for in Java. When a numeric assertion fails with values that look identical when printed, suspect a type mismatch before assuming your data is wrong.

Comparing an Entire Object or List at Once

Map<String, Object> expected = new HashMap<>();
expected.put("name", "John");
expected.put("active", true);

.then().body("", equalTo(expected)); // compares the WHOLE response body against the map

Most of the time, asserting field-by-field (as shown throughout this page) is clearer and gives better failure messages — when one field is wrong, the error names exactly that field. Whole-object comparison is a narrower tool, useful mainly when you have a known-correct reference object already available and want a single terse check that literally everything matches, accepting that a mismatch failure message will be less specific about which field was wrong.

❌ Fragile vs. ✅ Recommended

// ❌ Asserting only the first element, missing regressions elsewhere in the array
.then().body("data[0].email", containsString("@"));

// ✅ Asserting the property holds across the whole collection
.then().body("data.email", everyItem(containsString("@")));

Common Mistakes

  • Using indexed access ([0]) when membership is what you actually mean — brittle against re-ordering that doesn't represent a real bug.
  • Only validating one array element when the property being checked should hold for every element — use everyItem() instead.
  • Forgetting arrays can legitimately be empty — hasItem() against an empty array correctly fails; make sure an empty result is actually the failure case you intend to test, not an accidental empty response.

Edge Cases

  • Deeply nested arrays of objects (an order containing a list of line items, each with nested product details) — chain dot notation and array syntax together: orders[0].items.productName.
  • Fields that are sometimes null — equalTo(null) works, but nullValue()/notNullValue() read more clearly for presence checks.

Debugging

When a body assertion fails and the reason isn't obvious, print the response with .log().ifValidationFails() (or response.getBody().asPrettyString()) before assuming your JsonPath expression itself is wrong — many failures turn out to be "the response doesn't have the shape I assumed," not a syntax mistake.

Best Practices

  • Use hasItem()/hasItems() for membership questions, indexed access only when position genuinely matters.
  • Prefer everyItem() over single-element checks when a property should hold across an entire collection.
  • Keep JsonPath expressions as close to how you'd describe the structure verbally as possible — it keeps tests readable months later.

Practice Exercise

Against a public API returning a list of resources, write assertions that: confirm the list is non-empty, confirm every item has a non-null ID, and confirm at least one item matches a specific known value — using the most appropriate matcher for each.

Summary

JSON body validation covers three shapes: flat fields (direct name access), nested objects (dot notation), and arrays (membership via hasItem(), position via indexing, or every-element checks via everyItem()). Choosing the matcher that actually matches your intent — membership vs. position vs. universal — is what keeps these assertions both correct and resilient to harmless changes.

Interview Questions

What's the difference between body("users.name", hasItem("John")) and body("users[0].name", equalTo("John"))?▾
The first checks whether "John" appears anywhere in the array, regardless of position — a membership question. The second checks specifically whether the first element's name is "John" — a positional question. Using the positional version when you actually mean membership makes a test brittle against harmless reordering; using the membership version when order genuinely matters can let a real bug (wrong item first) slip through undetected.
What's the difference between users.name with hasItem() and users[0].name with equalTo()?▾
The first checks membership — is this value anywhere in the collected list, order irrelevant; the second checks a specific position — appropriate only when order genuinely matters, like the most recent item.

When a property should hold across an ENTIRE collection — everyItem() catches a regression affecting only some elements, which checking just index 0 would completely miss.
