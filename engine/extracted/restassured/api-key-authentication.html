API Key Authentication

Prerequisites: Basic & Bearer Authentication

What is this?

An API key is a single, typically long-lived credential — no login step required, unlike Bearer tokens. It's issued once (often through a developer portal or account settings) and sent with every request, in one of two conventions: a header, or a query parameter.

Header-Based API Keys

given()
    .header("X-API-Key", apiKey)
.when()
    .get("/weather")
.then()
    .statusCode(200);

This is the more common, and generally more secure, convention — the key doesn't appear in the URL, which means it's less likely to leak through server access logs, browser history, or a URL accidentally shared/screenshotted. The header name itself varies by API — X-API-Key is common but not universal; always check the specific API's documentation.

Query-Parameter-Based API Keys

given()
    .queryParam("apikey", apiKey)
.when()
    .get("/weather")
.then()
    .statusCode(200);

Some APIs (especially older or simpler ones) expect the key as a query parameter instead. This is generally considered less secure than the header approach — the key ends up directly in the URL, which is far more likely to be logged, cached, or accidentally exposed than a header value. Testing an API you don't control means matching whichever convention it actually uses, regardless of which one is "better."

Detailed Example — Testing Both Valid and Invalid Keys

@Test
void validApiKeyReturns200() {
    given().header("X-API-Key", validKey).when().get("/weather").then().statusCode(200);
}

@Test
void invalidApiKeyReturns401() {
    given().header("X-API-Key", "clearly-not-a-real-key").when().get("/weather")
        .then().statusCode(401);
}

@Test
void missingApiKeyReturns401() {
    given().when().get("/weather").then().statusCode(401);
}

The same three-case pattern from Basic/Bearer auth applies here — valid, invalid, and missing — each a genuinely distinct scenario worth its own test.

Real-World Example — An API Key That's Rate-Limited Per Key

@Test
void rateLimitHeadersReflectPerKeyUsage() {
    Response response = given().header("X-API-Key", apiKey).when().get("/weather");

    response.then().statusCode(200);
    String remaining = response.getHeader("X-RateLimit-Remaining");
    assertThat(Integer.parseInt(remaining), greaterThanOrEqualTo(0));
}

Many API-key-based services tie rate limiting directly to the key rather than to the authenticated user (since there may be no separate "user" concept at all) — worth testing that rate-limit headers actually reflect usage against your specific key, tying back to the Response Header Validation page from Chapter 4.

❌ Fragile vs. ✅ Recommended

// ❌ Committing a real API key directly into test source code, version control, or CI config in plain text
given().header("X-API-Key", "sk_live_abc123realkey").when().get("/weather");

// ✅ Reading it from an environment variable, never committed anywhere
given().header("X-API-Key", System.getenv("WEATHER_API_KEY")).when().get("/weather");

Common Mistakes

  • Committing a real API key to version control, even in a test file — treat it with the same care as any other secret.
  • Assuming every API uses the same header name or query parameter name for its key — this varies significantly; always check the specific API's documentation rather than assuming a convention.
  • Never testing the invalid/missing key paths, only the happy path with a known-good key.

Edge Cases

  • API keys with usage quotas (a limited number of calls per day/month) — running a full test suite repeatedly against a real, quota-limited key can exhaust it; consider whether a dedicated, higher-quota test key is available, or whether some tests should be mocked instead (Chapter 11 covers this tradeoff for Playwright-style network mocking, though RestAssured's equivalent tooling is more limited).
  • Keys scoped to specific IP addresses or domains — a CI runner's IP may need to be allowlisted separately from a developer's local machine.

Debugging

If an API-key-authenticated request unexpectedly fails, confirm you're using the exact header or query parameter name the API's documentation specifies — a near-miss (Api-Key vs. X-API-Key, for instance) produces the same 401 as a genuinely wrong key, and it's easy to assume the key itself is invalid when the real issue is the parameter name.

Best Practices

  • Read API keys from environment variables or a secrets manager, never hardcoded.
  • Confirm the exact header/query parameter name and convention from the specific API's documentation.
  • Test valid, invalid, and missing key scenarios as three distinct cases.
  • Be mindful of usage quotas on shared or rate-limited test keys.

Practice Exercise

Find a public API that uses header-based API key authentication (many weather or geocoding APIs offer free tiers), write a test confirming a valid key succeeds, and a second test confirming a deliberately malformed key returns the API's actual documented error response.

Summary

API keys are simple, typically long-lived credentials sent via a header (more secure, more common) or a query parameter (less secure, still common with older APIs) — no login step required. Test valid, invalid, and missing key scenarios distinctly, and always source keys from environment variables rather than hardcoding them.

Interview Questions

Why is a header-based API key generally considered more secure than a query-parameter-based one?▾
A query parameter becomes part of the URL itself, which is far more likely to be captured incidentally — in server access logs, browser history, proxy logs, or even accidentally shared when someone copies a URL to send to a colleague. A header is not part of the URL and is generally excluded from those same logging and caching paths by default, making accidental exposure meaningfully less likely, even though neither approach is as secure as a properly scoped, short-lived OAuth token.
