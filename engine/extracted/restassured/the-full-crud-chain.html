The Full CRUD Chain

Prerequisites: API Chaining & End-to-End Workflows overview

What is this?

The full lifecycle of a resource, tested end to end in a single scenario:

Create User
    ↓
Extract User ID
    ↓
Get User
    ↓
Update User
    ↓
Verify User
    ↓
Delete User
    ↓
Verify deletion

Each arrow represents a dependency — the step below needs data produced by the step above. This page works through the whole chain in real code, one step at a time.

Step 1 — Create

Response createResponse =
    given()
        .contentType(ContentType.JSON)
        .body(new User("John", "john@example.com"))
    .when()
        .post("/users");

createResponse.then().statusCode(201);

Step 2 — Extract the Generated ID

String userId = createResponse.jsonPath().getString("id");
assertThat(userId, is(notNullValue())); // fail fast if extraction itself produced nothing

Validating the creation succeeded (step 1) before extracting is exactly the validate-then-extract pattern from Chapter 4 — and adding an explicit assertion on the extracted value itself is worth doing in a multi-step chain specifically, since a silently-null ID here would otherwise corrupt every subsequent step in a confusing way.

Step 3 — Get (Verify Creation)

given()
    .pathParam("id", userId)
.when()
    .get("/users/{id}")
.then()
    .statusCode(200)
    .body("name", equalTo("John"))
    .body("email", equalTo("john@example.com"));

This step verifies something the creation response alone doesn't prove: that the resource was actually persisted, not just echoed back in the creation response. A buggy API could return a correct-looking 201 response while failing to actually save the record — this GET is what would catch that.

Step 4 — Update

given()
    .pathParam("id", userId)
    .body(Map.of("name", "John Updated"))
.when()
    .patch("/users/{id}")
.then()
    .statusCode(200);

Step 5 — Verify the Update

given()
    .pathParam("id", userId)
.when()
    .get("/users/{id}")
.then()
    .statusCode(200)
    .body("name", equalTo("John Updated"))
    .body("email", equalTo("john@example.com")); // confirming this was genuinely a PARTIAL update

This is the same principle from the PATCH Requests page in Chapter 3 — confirming both the changed field and a deliberately unchanged one, proving the update was genuinely partial rather than accidentally overwriting something else.

Step 6 — Delete

given()
    .pathParam("id", userId)
.when()
    .delete("/users/{id}")
.then()
    .statusCode(204);

Step 7 — Verify Deletion

given()
    .pathParam("id", userId)
.when()
    .get("/users/{id}")
.then()
    .statusCode(404); // proves the resource is genuinely gone, not just that DELETE returned success

Real-World Example — The Whole Chain as One Test

@Test
void fullUserLifecycle() {
    // 1. Create
    Response created = given().body(new User("John", "john@example.com")).when().post("/users");
    created.then().statusCode(201);

    // 2. Extract
    String userId = created.jsonPath().getString("id");
    assertThat(userId, is(notNullValue()));

    // 3. Get (verify creation)
    given().pathParam("id", userId).when().get("/users/{id}")
        .then().statusCode(200).body("name", equalTo("John"));

    // 4. Update
    given().pathParam("id", userId).body(Map.of("name", "John Updated"))
        .when().patch("/users/{id}").then().statusCode(200);

    // 5. Verify update
    given().pathParam("id", userId).when().get("/users/{id}")
        .then().statusCode(200).body("name", equalTo("John Updated"));

    // 6. Delete
    given().pathParam("id", userId).when().delete("/users/{id}").then().statusCode(204);

    // 7. Verify deletion
    given().pathParam("id", userId).when().get("/users/{id}").then().statusCode(404);
}

Seven distinct assertions across seven steps, all in one test, all genuinely dependent on the same resource created in step one. This is meaningfully different from seven independent tests each creating their own resource — here, the test is specifically verifying the lifecycle as a coherent whole, not seven unrelated facts.

❌ Fragile vs. ✅ Recommended

// ❌ Skipping the GET-based verification steps, trusting the mutating
// endpoints' own responses without confirming persistence
given().body(user).when().post("/users").then().statusCode(201);
given().pathParam("id", userId).body(update).when().patch("/users/{id}").then().statusCode(200);
// never confirms via GET that either change actually persisted

// ✅ Verify persistence explicitly after each mutation, not just the mutation's own response
given().pathParam("id", userId).when().get("/users/{id}").then().body("name", equalTo("John Updated"));

Common Mistakes

  • Trusting a mutating endpoint's own response without a follow-up GET — a POST/PATCH/DELETE response can look correct while the underlying data wasn't actually persisted or removed.
  • Not asserting on the extracted ID itself before using it in later steps — a silently-null ID corrupts every subsequent step with confusing, hard-to-trace failures.
  • Combining too many unrelated assertions into one giant chain — if this test fails, you want the failure to clearly indicate which of the seven steps broke, not just "something in this long test failed."

Edge Cases

  • A chain step that legitimately can fail independent of the others (a rate limit hit mid-chain) — consider whether retry logic belongs at the chain level or whether the test should simply fail and be re-run.
  • Resources with required fields that can't be set via PATCH — some fields may only be settable at creation time; know your API's actual constraints before assuming every field is always updatable.

Debugging

When a full-chain test fails, the step number (or a descriptive step name, via test.step()-equivalent patterns if your test framework supports named steps) is the first thing to identify — knowing exactly which of the seven steps broke narrows the investigation immediately, rather than needing to re-read the whole chain from scratch.

Best Practices

  • Verify persistence with a follow-up GET after every mutating step, not just trust the mutation's own response.
  • Assert on extracted values immediately, before using them in later steps.
  • Consider breaking a very long chain into named sub-steps (or separate but related tests) for clearer failure attribution.

Practice Exercise

Implement the full seven-step chain shown on this page against a real or sandbox API of your choice, then deliberately introduce a bug (skip the extraction's null check) and observe how the failure manifests several steps later — noting how much harder it is to diagnose without the explicit check.

Summary

A full CRUD chain — create, extract, get, update, verify, delete, verify deletion — tests a resource's entire lifecycle as one coherent scenario, catching integration bugs that isolated single-endpoint tests can't. The key discipline throughout: verify persistence with a follow-up read after every mutation, and validate every extracted value before trusting it in the next step.

Interview Questions

Why include a GET request immediately after a POST, rather than just trusting the POST response's own status code and body?▾
A POST response reflects what the server claims it did, but doesn't independently prove the resource was actually persisted — a bug could produce a correct-looking 201 response with the right body while failing to actually save the record to the database. A follow-up GET, as a genuinely separate request, verifies the data is retrievable after the fact — proving persistence, not just that the creation endpoint returned a plausible-looking response.
Why include a GET immediately after a POST instead of trusting the POST response alone?▾
A POST response reflects what the server claims it did, not independent proof of persistence — a bug could return a correct-looking 201 while failing to actually save the record; a follow-up GET verifies it was genuinely persisted.
Why assert on both a changed field AND a deliberately unchanged one after the update step?▾
Confirming the changed field updated correctly is necessary but not sufficient — asserting an unchanged field proves the update was genuinely partial and didn't silently clobber something else, tying to the PUT/PATCH lessons from Chapter 3.
Why does the final chain step verify deletion with a GET expecting 404, not just trust the DELETE response?▾
The same principle as step 3's create verification — the delete response alone doesn't independently prove removal; a follow-up GET returning 404 is what actually confirms the resource is genuinely gone.
Why assert on the extracted ID's presence before using it in step 3?▾
A silently null ID here would corrupt every subsequent step with a confusing, hard-to-trace failure — an explicit check at the extraction point fails fast and clearly instead.
