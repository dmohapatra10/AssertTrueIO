XML Response Validation

Prerequisites: Validate vs. Extract

What is this?

Not every API you'll test speaks JSON. Older enterprise systems, SOAP-based services, and some financial/banking APIs still respond in XML. RestAssured detects an XML response (via its Content-Type header) and lets you validate it with syntax that looks similar to JSON validation, backed by XPath instead of JsonPath underneath.

Basic Example

<user>
  <name>John</name>
  <email>john@example.com</email>
</user>
.then()
    .body("user.name", equalTo("John"))
    .body("user.email", equalTo("john@example.com"));

The dot-notation shape looks nearly identical to JSON body validation — this is deliberate on RestAssured's part, so switching between validating JSON and XML responses doesn't require learning an entirely separate mental model, just a different underlying path language.

Nested Elements and Attributes

<order id="1024">
  <customer>
    <name>John</name>
  </customer>
  <items>
    <item>Widget</item>
    <item>Gadget</item>
  </items>
</order>
.then()
    .body("order.@id", equalTo("1024"))            // XML attribute — note the @ prefix
    .body("order.customer.name", equalTo("John"))
    .body("order.items.item", hasItems("Widget", "Gadget"));

The @ prefix addresses an XML attribute rather than a child element — a distinction that doesn't exist in JSON at all, since JSON has no separate concept of "attribute" versus "field." This is the one syntax difference worth internalizing when moving between the two formats.

Using Raw XPath Directly

.then()
    .body(hasXPath("/order/customer/name[text()='John']"));

For more complex queries than the dot-notation shorthand comfortably expresses — conditions, sibling relationships, more elaborate filtering — dropping into raw XPath via hasXPath() gives you the full expressive power of the XPath language itself.

Real-World Example — A SOAP-Style Response

<soap:Envelope>
  <soap:Body>
    <GetUserResponse>
      <User>
        <Id>42</Id>
        <Name>John</Name>
      </User>
    </GetUserResponse>
  </soap:Body>
</soap:Envelope>
.then()
    .body("Envelope.Body.GetUserResponse.User.Id", equalTo("42"))
    .body("Envelope.Body.GetUserResponse.User.Name", equalTo("John"));

Namespace prefixes (like soap:) are typically omitted in the dot-path expression — RestAssured's default XML path handling generally ignores them for simple lookups, though deeply namespace-sensitive validation may need raw XPath with explicit namespace declarations instead.

❌ Fragile vs. ✅ Recommended

// ❌ Manually parsing the raw XML string with regex or string manipulation
String body = response.getBody().asString();
boolean hasJohn = body.contains("<name>John</name>"); // extremely fragile

// ✅ Structured XML validation
.then().body("user.name", equalTo("John"));

Common Mistakes

  • Forgetting the @ prefix for XML attributes — attempting to address order.id when id is actually an attribute (order.@id) rather than a child element.
  • Manually parsing raw XML strings instead of using RestAssured's structured validation — loses all the readability and matcher flexibility structured validation gives you.
  • Assuming JSON-style array syntax works identically — repeated XML elements (like the <item> elements above) collect into a list similarly to JSON arrays, but the underlying XML structure (no explicit array marker the way JSON has []) means some edge cases behave differently than a JSON developer might expect.

Edge Cases

  • Mixed content (an element containing both text and child elements) — XPath handles this natively; dot-notation shorthand can get awkward here, and raw XPath via hasXPath() is usually the more reliable tool.
  • Namespace-heavy documents — if simple dot-path lookups aren't resolving correctly, the namespace prefixes are the most likely cause; raw XPath with explicit namespace context is the fallback.

Debugging

When an XML path expression isn't matching as expected, print the raw response body first (.log().all() or response.getBody().asPrettyString()) to confirm the actual element/attribute structure — XML namespaces and attribute-vs-element confusion account for the large majority of "my path expression doesn't work" moments here.

Best Practices

  • Use the dot-notation shorthand for straightforward lookups; drop into raw hasXPath() only when you genuinely need XPath's fuller expressiveness.
  • Remember the @ prefix specifically marks attributes, not child elements — check the actual XML structure before assuming which one a value is.
  • Never fall back to manual string/regex parsing of raw XML — it's exactly the kind of fragile approach structured validation exists to replace.

Practice Exercise

Given a small XML response with a root element, one attribute, one nested child element, and a repeated sibling element, write RestAssured assertions validating all three: the attribute value, the nested element's text, and that the repeated elements collectively contain a specific expected value.

Summary

XML validation in RestAssured mirrors JSON validation's dot-notation style, backed by XPath instead of JsonPath — with one meaningful syntax difference, the @ prefix for attributes. You'll use this far less than JSON validation in most modern projects, but the pattern stays familiar when a SOAP service or legacy XML API shows up in a real project.

JSON has no equivalent concept — every field is simply a key-value pair with no separate "attribute" category — so JSON body validation never needs this prefix at all.
