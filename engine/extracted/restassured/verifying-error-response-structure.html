Verifying Error Response Structure

Prerequisites: Rate Limiting & Server Errors

What is this?

Every negative test on the previous four pages asserted a status code — often alongside a partial check on the error message. This page is about being thorough on the error body itself: the message, an error code, the overall structure, and any error-specific fields, not just the numeric status.

Why Status Code Alone Isn't Enough

// This confirms the API rejected the request — but tells you NOTHING
// about whether it rejected it for the RIGHT reason
.then().statusCode(400);

A 400 could mean the email was invalid, or that the name was missing, or that the request body wasn't valid JSON — three completely different problems, all producing the same status code. If a test only checks the status, it can't distinguish "the API correctly caught the specific problem I introduced" from "the API is broken in some unrelated way that happens to also return 400."

Verifying the Error Message

.then()
    .statusCode(400)
    .body("message", containsString("email"));

Confirming the message references the actual field that was wrong — not just any error message, but specifically one naming the problem this test introduced.

Verifying an Error Code

{
  "status": 400,
  "code": "INVALID_EMAIL_FORMAT",
  "message": "The provided email address is not valid"
}
.then()
    .statusCode(400)
    .body("code", equalTo("INVALID_EMAIL_FORMAT"));

A structured, machine-readable error code (as opposed to a human-readable message) is more reliable to assert against than message text — a message can be reworded for clarity or localized without changing its meaning, but a well-designed API's error code is meant to stay stable, making it the more robust thing to assert on when an API provides one.

Verifying Overall Error Structure

{
  "status": 400,
  "code": "VALIDATION_ERROR",
  "message": "Request validation failed",
  "fields": [
    { "field": "email", "issue": "Invalid format" },
    { "field": "name", "issue": "Required field missing" }
  ]
}
@Test
void multiFieldValidationErrorHasCorrectStructure() {
    given().body(Map.of("email", "bad-format")).when().post("/users")
    .then()
        .statusCode(400)
        .body("code", equalTo("VALIDATION_ERROR"))
        .body("fields.field", hasItems("email", "name"))
        .body("fields.find { it.field == 'email' }.issue", containsString("format"));
}

Many real APIs return multiple validation problems in a single error response (rather than stopping at the first one found) — this test confirms both fields are correctly reported, and uses the advanced JsonPath filtering from Chapter 11 to check the specific issue text for one particular field within the array.

Detailed Example — A Reusable Error Structure Assertion Helper

public class ErrorAssertions {
    public static void assertValidationError(ValidatableResponse response, String field, String expectedIssueFragment) {
        response
            .statusCode(400)
            .body("code", equalTo("VALIDATION_ERROR"))
            .body("fields.field", hasItem(field))
            .body("fields.find { it.field == '" + field + "' }.issue", containsString(expectedIssueFragment));
    }
}

// Usage — every validation test in the suite now checks the FULL structure consistently
@Test
void invalidEmailIsRejectedWithCorrectStructure() {
    ValidatableResponse response =
        given().body(Map.of("email", "bad")).when().post("/users").then();
    ErrorAssertions.assertValidationError(response, "email", "format");
}

This is exactly the utility-method pattern from Chapter 9 applied to error verification specifically — a shared helper that encapsulates the full error-structure check, so every validation test in the suite verifies the complete shape consistently, rather than each test hand-rolling a slightly different, possibly incomplete check.

Real-World Example — Combining This With Chapter 11's Schema Validation

ResponseSpecification errorSpec =
    new ResponseSpecBuilder()
        .expectBody("status", notNullValue())
        .expectBody("code", notNullValue())
        .expectBody("message", notNullValue())
        .build();

@Test
void everyErrorResponseHasTheRequiredStructure() {
    given().body(invalidUser).when().post("/users")
        .then().spec(errorSpec).statusCode(400);
}

This is the shared response spec pattern from Chapter 9 applied specifically to the "does every error response have the required shape" question — combined with, or as an alternative to, a full JSON Schema for the error format (Chapter 11's advanced schema validation), depending on how rigorously the project wants this structural contract enforced.

❌ Fragile vs. ✅ Recommended

// ❌ Status code only — can't distinguish the right rejection from a wrong one
.then().statusCode(400);

// ✅ Status code AND error content, confirming the RIGHT thing was rejected
.then().statusCode(400).body("code", equalTo("INVALID_EMAIL_FORMAT"));

Common Mistakes

  • Only asserting the status code on a negative test — can't distinguish "correctly caught the specific problem" from "failed for some unrelated reason that happens to share the same status code."
  • Asserting on exact error message text when a message might legitimately be reworded — an error code, where the API provides one, is generally the more stable thing to assert against.
  • Not verifying multi-field error responses report every problem, only checking the first or checking count without content.

Edge Cases

  • APIs with inconsistent error structures across different endpoints — worth flagging as an API design inconsistency, and worth a shared response spec or schema (as shown above) specifically to catch and enforce consistency going forward.
  • Localized error messages — if the API supports multiple languages, message-text assertions become fragile across locales; prefer code-based assertions in this scenario specifically.

Debugging

If an error-structure assertion fails unexpectedly, print the full error response body (Chapter 8's logging) — it's easy to assume a field name (message vs. error vs. errorMessage) without checking the API's actual, real response shape first.

Best Practices

  • Always verify error content, not just the status code, on every negative test.
  • Prefer error codes over message text when an API provides both, for more stable assertions.
  • Build a reusable helper or shared response spec for error structure, applied consistently across the whole negative-testing suite.
  • Verify multi-field validation responses report every problem, not just the first.

Practice Exercise

Build a reusable ErrorAssertions helper (like the one shown on this page) for your own hypothetical API's error format, and use it across at least three different negative tests, confirming it correctly verifies status, error code, and field-specific issue text consistently.

Summary

Thorough negative testing verifies the full error response — status code, error code, message, and any field-specific error details — not just the status alone, which can't distinguish a correctly-caught problem from an unrelated failure sharing the same code. A reusable assertion helper or shared response spec applied consistently across a suite's negative tests is what keeps this thoroughness practical at scale, rather than every test hand-rolling its own partial check.

Interview Questions

Why is checking only the status code insufficient to confirm a negative test is actually testing what it claims to test?▾
Multiple different validation failures on the same endpoint often produce the same status code — a missing name, an invalid email, and malformed JSON might all return 400. A test that only asserts statusCode(400) would pass identically regardless of which specific problem the API actually detected, which means it can't distinguish "the API correctly caught the invalid email I sent" from "the API is rejecting this request for a completely different, possibly wrong reason." Verifying the error message or error code confirms the API identified the specific problem the test was actually designed to introduce, not just that it rejected the request for some reason.
