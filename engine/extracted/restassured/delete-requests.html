DELETE Requests

Prerequisites: PATCH Requests

What is this?

given()
    .pathParam("id", orderId)
.when()
    .delete("/orders/{id}")
.then()
    .statusCode(204);

DELETE removes a resource. It's the method behind most test cleanup — the teardown half of any setup/teardown pattern, and the operation the API Chaining chapter's "create, use, clean up" scenarios end with.

Why it's important

DELETE looks trivially simple, but two things trip people up in practice: confirming a resource is genuinely gone (not just that the request returned success), and handling cleanup for resources that may or may not still exist by the time teardown actually runs.

Basic Example

Response response = given().pathParam("id", orderId).when().delete("/orders/{id}");
response.then().statusCode(204); // 204 No Content — common for successful deletes

A 204 response has no body by design — calling .jsonPath() on it will find nothing to parse. If your API returns the deleted resource's final state instead (some do, as a convenience), it'll use 200 with a body instead; check which convention your specific API follows.

Detailed Example — Verifying the Resource Is Actually Gone

@Test
void deletingAnOrderRemovesItCompletely() {
    Response created = given().body(newOrder).when().post("/orders");
    String id = created.jsonPath().getString("id");

    given().pathParam("id", id).when().delete("/orders/{id}")
        .then().statusCode(204);

    // Don't stop at the delete response — confirm it's genuinely gone
    given().pathParam("id", id).when().get("/orders/{id}")
        .then().statusCode(404);
}

The delete call succeeding tells you the server accepted the request, but a follow-up GET returning 404 is what actually proves the resource is gone — a server could return a "successful" delete response due to a bug while leaving the resource fully intact.

DELETE Is Idempotent

@Test
void deletingAnAlreadyDeletedResourceDoesNotThrow() {
    given().pathParam("id", id).when().delete("/orders/{id}"); // first call: removed
    Response second = given().pathParam("id", id).when().delete("/orders/{id}");

    // A well-behaved API returns 404 here (already gone), not a 500 error —
    // either way, the END STATE is the same as after the first call
    assertThat(second.getStatusCode(), isOneOf(204, 404));
}

This idempotence is exactly why cleanup code can safely call delete on something that might already be gone, without needing to first check whether it exists — the operation is safe to repeat.

Real-World Example — Resilient Cleanup in @AfterEach

public class OrderTests {
    private String orderId;

    @BeforeEach
    void setup() {
        Response created = given().body(newOrder).when().post("/orders");
        orderId = created.jsonPath().getString("id");
    }

    @AfterEach
    void cleanup() {
        // Tolerates "already deleted" — if the test ITSELF already deleted
        // the order as part of what it was testing, this is a safe no-op
        given().pathParam("id", orderId).when().delete("/orders/{id}");
    }

    @Test
    void canViewOrderDetails() { /* doesn't delete the order itself */ }

    @Test
    void canCancelAndDeleteAnOrder() {
        // this test's own logic already deletes orderId —
        // the @AfterEach's delete-again is now a safe no-op, not a failure
    }
}

This pattern — cleanup that tolerates "already gone" — is what makes teardown robust across a whole suite of tests that may or may not have already deleted the resource themselves as part of what they were testing.

Soft Delete vs. Hard Delete

// Hard delete — a follow-up GET returns 404
given().pathParam("id", id).when().get("/orders/{id}").then().statusCode(404);

// Soft delete — the resource may still be fetchable directly, but should be
// excluded from normal listings and flagged as deleted
Response fetched = given().pathParam("id", id).when().get("/orders/{id}");
fetched.then().body("deletedAt", notNullValue());

Response list = given().when().get("/orders");
List<String> ids = list.jsonPath().getList("data.id");
assertThat(ids, not(hasItem(id))); // excluded from the normal list view

Not every DELETE actually removes data from the database — many APIs implement a soft delete, marking a record inactive/archived rather than removing it. Assuming hard-delete semantics against an API that actually soft-deletes is a common source of confusing test failures.

❌ Fragile vs. ✅ Recommended

// ❌ Only checking the delete call's own status, never confirming removal
given().pathParam("id", id).when().delete("/orders/{id}").then().statusCode(204);
// test ends here — never actually proved the order is gone

// ✅ Follow up to confirm genuine removal (or correctly soft-deleted state)
given().pathParam("id", id).when().delete("/orders/{id}");
given().pathParam("id", id).when().get("/orders/{id}").then().statusCode(404);

Common Mistakes

  • Never verifying the delete actually took effect — trusting the delete response's status code alone.
  • Assuming hard-delete when the API actually soft-deletes, leading to a test that expects 404 but gets 200 with a "deleted" flag instead.
  • Not making cleanup code tolerant of "already deleted" — an @AfterEach that throws when a resource the test itself already removed can't be deleted again, failing tests that were otherwise passing.

Edge Cases

  • Cascading deletes (deleting a customer also deletes their orders) — worth explicitly verifying the cascade actually happened, not just that the top-level resource is gone.
  • Deleting a resource that never existed — a well-behaved API returns 404, not a 500 server error; worth its own explicit test.

Debugging

If a "delete" test fails with an unexpected status on a follow-up GET, check whether the API implements soft delete before assuming the delete itself failed — a soft-deleted resource often still returns 200 from a direct GET by ID, which is correct behavior for that API, not a bug.

Best Practices

  • Always follow a delete with a verification step — never trust the delete response alone.
  • Make cleanup code tolerant of resources that may already be gone.
  • Know which delete semantics (hard vs. soft) your specific API implements before writing verification assertions.
  • Test deleting a non-existent resource explicitly, confirming a clean 404 rather than a server error.

Practice Exercise

Write a test that creates an order, deletes it, verifies a follow-up GET returns 404, and then calls delete on the same (already-deleted) ID again, asserting the second call doesn't throw and reflects idempotent behavior.

Summary

DELETE removes a resource and is idempotent by convention. Always verify removal with a follow-up request rather than trusting the delete response alone, know whether your API implements hard or soft delete, and make cleanup code tolerant of resources that may already be gone.

Interview Questions

Why is it important to make cleanup code (like an @AfterEach hook) tolerant of a resource that's already been deleted?▾
Some tests delete a resource as part of what they're actually testing (a "cancel order" test, for instance), while an @AfterEach hook designed for general cleanup might also try to delete that same resource afterward. Since DELETE is idempotent, calling it again on an already-gone resource should be harmless — but if the cleanup code doesn't handle the resulting 404 gracefully, it can throw and fail an otherwise-passing test purely because of teardown logic, not because anything actually went wrong.
Why isn't a 204 response from DELETE enough to prove a resource is actually gone?▾
The delete response only tells you the server accepted the request — a bug could return a successful-looking delete response while leaving the resource intact; a follow-up GET expecting 404 actually proves removal.
Why is DELETE described as idempotent, and why does that matter for cleanup code?▾
Calling it again on an already-deleted resource should produce the same end state as the first call — this is exactly why cleanup hooks can safely call delete on something that might already be gone, without checking existence first.
What's the difference in verification needed for hard delete vs. soft delete?▾
Hard delete: a follow-up GET should return 404. Soft delete: the resource may still be fetchable but should be flagged (a deletedAt field) and excluded from normal list views.
Why should cleanup code use .catch(() -> {}) or equivalent around a delete call?▾
So it doesn't throw if the test's own logic already deleted the resource as part of what it was testing — making a second delete call a safe no-op instead of an unexpected failure.
