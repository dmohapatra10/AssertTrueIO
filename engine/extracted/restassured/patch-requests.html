PATCH Requests

Prerequisites: PUT Requests

What is this?

given()
    .contentType(ContentType.JSON)
    .pathParam("id", orderId)
    .body(Map.of("quantity", 5)) // ONLY the field changing
.when()
    .patch("/orders/{id}")
.then()
    .statusCode(200);

PATCH applies a partial update — only the fields included in the payload change; everything else on the resource stays exactly as it was. This is the natural counterpart to the previous page's PUT, and choosing between them correctly matters directly for data integrity.

Why it's important

PATCH is generally the safer default for "update one or two fields" scenarios, since it doesn't carry PUT's risk of silently clobbering fields you forgot to include. But PATCH has its own subtlety worth understanding: unlike PUT, it isn't always idempotent.

Basic Example

given()
    .contentType(ContentType.JSON)
    .pathParam("id", orderId)
    .body(Map.of("quantity", 5))
.when()
    .patch("/orders/{id}")
.then()
    .statusCode(200)
    .body("quantity", equalTo(5));

Detailed Example — Confirming Omitted Fields Stay Untouched

@Test
void patchOnlyChangesSpecifiedFields() {
    Response created = given()
        .body(Map.of("item", "Wireless Mouse", "quantity", 1, "giftNote", "For Alex"))
        .when().post("/orders");
    String id = created.jsonPath().getString("id");

    given()
        .pathParam("id", id)
        .body(Map.of("quantity", 5)) // ONLY quantity
    .when()
        .patch("/orders/{id}");

    Response fetched = given().pathParam("id", id).when().get("/orders/{id}");
    fetched.then()
        .body("quantity", equalTo(5))              // changed, as intended
        .body("giftNote", equalTo("For Alex"))      // UNCHANGED — proves this was a real partial update
        .body("item", equalTo("Wireless Mouse"));   // UNCHANGED
}

That second and third assertion are doing the real work here — confirming the field you intentionally changed changed is necessary but not sufficient; confirming fields you didn't touch are still correct is what actually proves the update was genuinely partial and didn't accidentally affect anything else.

Why PATCH Isn't Always Idempotent

// A simple field-replacement PATCH IS idempotent — sending it twice
// produces the same end state as sending it once
given().body(Map.of("status", "confirmed")).when().patch("/orders/{id}"); // idempotent

// A RELATIVE-change PATCH is NOT idempotent — applying it twice
// produces a DIFFERENT result than applying it once
given().body(Map.of("increment", 1)).when().patch("/orders/{id}/quantity"); // NOT idempotent

This distinction is worth testing explicitly if your API supports relative-change PATCH operations (increment/decrement style, common in inventory or counter APIs) — don't assume PATCH is safe to retry blindly the way PUT is, without first confirming which flavor a specific endpoint implements.

Real-World Example — Testing Idempotence (or the Lack of It) Directly

@Test
void relativePatchIsNotIdempotent() {
    Response before = given().pathParam("id", id).when().get("/orders/{id}");
    int startingQuantity = before.jsonPath().getInt("quantity");

    given().pathParam("id", id).body(Map.of("increment", 1)).when().patch("/orders/{id}/quantity");
    given().pathParam("id", id).body(Map.of("increment", 1)).when().patch("/orders/{id}/quantity");

    Response after = given().pathParam("id", id).when().get("/orders/{id}");
    // Called twice — quantity should have increased by 2, NOT stayed the same
    // (which is what a genuinely idempotent operation would do)
    assertThat(after.jsonPath().getInt("quantity"), equalTo(startingQuantity + 2));
}

Writing this test explicitly documents and verifies the API's actual (non-idempotent) behavior — useful both as regression coverage and as living documentation for anyone reading the test later, wondering whether this specific endpoint is safe to retry.

❌ Fragile vs. ✅ Recommended

// ❌ Sending the full resource to a PATCH endpoint, unnecessary and
// risking accidentally overwriting a field that changed between read and write
given().body(fullOrderObject).when().patch("/orders/{id}");

// ✅ Send only what's actually changing
given().body(Map.of("quantity", 5)).when().patch("/orders/{id}");

Common Mistakes

  • Sending a full resource payload to PATCH unnecessarily — defeats the point of partial updates, and can reintroduce PUT-style overwrite risk if the payload is stale.
  • Assuming all PATCH operations are idempotent — true for simple field-replacement patches, not guaranteed for relative/incremental ones.
  • Only asserting the changed field, never confirming untouched fields stayed that way — misses exactly the bug class PATCH testing needs to catch.
  • Not checking which PATCH format an API expects — some APIs expect a plain partial JSON object (shown throughout this page), others expect a formal JSON Patch document (an array of operations); check the API's documentation.

Edge Cases

  • JSON Patch format (RFC 6902) — some APIs expect PATCH bodies as an array of explicit operations ([{"op": "replace", "path": "/quantity", "value": 5}]) rather than a plain partial object; this is a distinct, more formal convention worth recognizing if you encounter it.
  • Patching a field to null explicitly vs. omitting it — some APIs distinguish "set this field to null" from "don't touch this field," which matters for how you construct the payload.

Debugging

If a PATCH test fails because an unexpected field changed, check whether the payload accidentally included more than intended — a full-object payload sent to what should have been a targeted PATCH is the most common cause.

Best Practices

  • Send only the fields actually changing — don't pad a PATCH payload with unchanged fields.
  • Always assert both the changed field and at least one deliberately-unchanged field, to prove the update was genuinely partial.
  • Confirm whether a specific PATCH endpoint is idempotent before assuming it's safe to retry — don't extend PUT's idempotence guarantee to PATCH by default.

Practice Exercise

Create a resource with three fields, PATCH only one of them, and write assertions confirming the changed field has its new value while the other two remain exactly as they were originally set.

Summary

PATCH updates only the fields included in its payload, leaving everything else untouched — the safer default for single-field updates compared to PUT's full-replacement risk. Simple field-replacement PATCHes are typically idempotent, but relative/incremental ones (increment-by-N style) are not — a distinction worth testing explicitly rather than assuming.

Interview Questions

Give an example of a PATCH operation that is NOT idempotent, and explain why.▾
A PATCH that applies a relative change — like {"increment": 1} against a quantity field — is not idempotent, because applying it twice produces a different result than applying it once (the value increases by 2, not 1). This contrasts with a simple field-replacement PATCH like {"status": "confirmed"}, which IS idempotent — setting the same absolute value twice produces the identical end state both times. The distinction matters for retry safety: a relative PATCH should never be blindly retried after an ambiguous failure, since a duplicate application produces a genuinely different, incorrect result.
Is PATCH always idempotent?▾
No — a simple field-replacement PATCH usually is, but a relative-change PATCH (like {"increment": 1}) is not, since applying it twice produces a different result than applying it once.
Why send only the changing field to PATCH instead of the full resource?▾
Sending the full resource defeats PATCH's purpose and risks accidentally overwriting a field that changed between when you read the resource and when you wrote the update.
What does asserting an unchanged field after a PATCH actually prove?▾
That the update was genuinely partial — the changed field updated correctly AND everything else was left alone, which a check of only the changed field can't confirm on its own.
What's JSON Patch (RFC 6902) and how does it differ from a plain partial object?▾
Some APIs expect PATCH bodies as a formal array of explicit operations (like [{"op":"replace","path":"/quantity","value":5}]) rather than a simple partial JSON object — a distinct, more formal convention worth recognizing if encountered.
