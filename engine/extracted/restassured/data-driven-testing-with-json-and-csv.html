Data-Driven Testing with JSON & CSV

Prerequisites: Test Data Builders

What is this?

Data-driven testing runs the same test logic repeatedly against different input data — instead of writing four nearly-identical test methods for four email formats, you write the logic once and supply four rows of data. JUnit 5's @ParameterizedTest is the mechanism this page builds on.

Basic Example — Inline Parameterized Data

@ParameterizedTest
@ValueSource(strings = {"not-an-email", "missing-at-sign.com", "@no-local-part.com", ""})
void invalidEmailFormatsAreRejected(String invalidEmail) {
    given()
        .body(Map.of("email", invalidEmail, "name", "Test"))
    .when()
        .post("/users")
    .then()
        .statusCode(400);
}

Four invalid email formats, one test method — JUnit runs it once per value, reporting each as its own distinct result, so a failure clearly identifies exactly which input caused it, not just "the parameterized test failed" generically.

CSV-Based Test Data

# test-data/invalid-users.csv
name,email,expectedStatus
John,not-an-email,400
,valid@example.com,400
Jane,,400
@ParameterizedTest
@CsvFileSource(resources = "/test-data/invalid-users.csv", numLinesToSkip = 1)
void invalidUserDataIsRejected(String name, String email, int expectedStatus) {
    Map<String, Object> user = new HashMap<>();
    user.put("name", name);
    user.put("email", email);

    given().body(user).when().post("/users").then().statusCode(expectedStatus);
}

A CSV file is a natural fit when the data itself is genuinely tabular — several fields varying together across many rows. This also means non-developers (a QA lead, a business analyst) can meaningfully review or even contribute test data without touching Java code at all — a real, practical benefit CSV-based data-driven testing offers over inline code.

JSON-Based Test Data

// test-data/users.json
[
  { "name": "John", "email": "john@example.com", "role": "admin" },
  { "name": "Jane", "email": "jane@example.com", "role": "user" }
]
@ParameterizedTest
@MethodSource("loadUsersFromJson")
void eachUserCanBeCreatedSuccessfully(User user) {
    given().body(user).when().post("/users").then().statusCode(201);
}

static Stream<User> loadUsersFromJson() throws IOException {
    ObjectMapper mapper = new ObjectMapper();
    User[] users = mapper.readValue(
        new File("src/test/resources/test-data/users.json"), User[].class);
    return Arrays.stream(users);
}

JSON is the more natural fit when the test data itself has a nested, non-tabular shape — a user with an embedded address object, for instance, doesn't flatten cleanly into CSV columns the way it deserializes naturally from JSON into a POJO via the same Jackson mechanism from Chapter 5.

Excel — Where It's Actually Appropriate

// Using Apache POI to read an Excel-based data set
Workbook workbook = new XSSFWorkbook(new FileInputStream("test-data/users.xlsx"));
Sheet sheet = workbook.getSheetAt(0);

List<User> users = new ArrayList<>();
for (Row row : sheet) {
    if (row.getRowNum() == 0) continue; // skip header
    users.add(new User(
        row.getCell(0).getStringCellValue(),
        row.getCell(1).getStringCellValue()
    ));
}

Excel-based test data is heavier tooling (requiring a library like Apache POI) than CSV or JSON, and is genuinely appropriate in a narrower set of cases — typically when non-technical stakeholders are already maintaining test data in Excel as part of an existing process, and converting that workflow to CSV/JSON would be more disruptive than just reading the Excel file directly. Don't reach for Excel by default; CSV or JSON cover the overwhelming majority of data-driven testing needs with far less tooling overhead.

Real-World Example — Combining a Builder With Parameterized Data

@ParameterizedTest
@CsvSource({
    "'', valid@example.com, 400",       // missing name
    "John, '', 400",                     // missing email
    "John, not-an-email, 400"           // invalid email format
})
void invalidUserFieldsAreRejected(String name, String email, int expectedStatus) {
    User user = UserBuilder.aUser()
        .withName(name.isEmpty() ? null : name)
        .withEmail(email.isEmpty() ? null : email)
        .build();

    given().body(user).when().post("/users").then().statusCode(expectedStatus);
}

This combines the previous page's builder (for sensible defaults on every field not explicitly being varied) with inline parameterized data (for the specific fields under test) — the two tools compose naturally rather than competing.

❌ Fragile vs. ✅ Recommended

// ❌ Four nearly-identical test methods, each hardcoding one variant
@Test void invalidEmail1() { /* ...same body, different email... */ }
@Test void invalidEmail2() { /* ...same body, different email... */ }
@Test void invalidEmail3() { /* ...same body, different email... */ }

// ✅ One parameterized test, four data points, one clear failure attribution per input
@ParameterizedTest
@ValueSource(strings = {"bad1", "bad2", "bad3"})
void invalidEmailIsRejected(String email) { /* ... */ }

Common Mistakes

  • Writing near-duplicate test methods instead of a single parameterized test — more code to maintain, and no structural guarantee the duplicated logic stays consistent across variants.
  • Reaching for Excel by default when CSV or JSON would work with far less tooling overhead — reserve it specifically for cases where existing non-technical workflows already use Excel.
  • Putting genuinely nested data into a flat CSV, forcing an awkward flattening — JSON is the better fit once the data itself isn't naturally tabular.

Edge Cases

  • Very large data-driven test sets (hundreds of rows) — consider whether every row genuinely adds distinct coverage, or whether a smaller, deliberately chosen set of representative cases would be just as effective and much faster to run.
  • Data files that need environment-specific values — covered in depth on the Environment-Specific Test Data page later in this chapter.

Debugging

When a parameterized test fails, JUnit's test report identifies exactly which specific input caused the failure — read that carefully rather than assuming the whole parameterized method is broken; usually only one or a few specific data points are actually the problem.

Best Practices

  • Prefer JUnit's @ParameterizedTest over hand-written near-duplicate test methods whenever the same logic needs to run against multiple inputs.
  • Choose CSV for tabular data, JSON for nested data, and reserve Excel for cases with a genuine existing non-technical workflow reason.
  • Keep data-driven test sets focused on genuinely distinct scenarios, not exhaustive combinations that don't add real coverage.

Practice Exercise

Convert four hand-written near-duplicate test methods (testing four different invalid email formats) into a single @ParameterizedTest using @ValueSource, then extend it to also read the same data from an external CSV file using @CsvFileSource.

Summary

Data-driven testing via JUnit 5's @ParameterizedTest family — @ValueSource for simple inline values, @CsvFileSource/@CsvSource for tabular data, @MethodSource for JSON or other custom-loaded data — replaces near-duplicate hand-written test methods with one method and many data points, each reported and attributed individually on failure.

Interview Questions

When would you choose a CSV file over a JSON file for data-driven test data, and vice versa?▾
CSV fits naturally when the data is genuinely tabular — several simple fields varying together across many rows — and has the added benefit that non-developers can review or edit it without touching code. JSON fits better when the data has a nested or non-flat shape — an object with an embedded sub-object, for instance — which doesn't flatten cleanly into CSV columns but deserializes naturally into a POJO via the same mechanism covered in the JSON & Serialization chapter. The deciding factor is the actual shape of the data, not a fixed preference for one format over the other.
Why is @ParameterizedTest preferable to four near-identical hand-written test methods?▾
One method with multiple data points is less code to maintain and structurally guarantees the tested logic stays consistent across variants — each input is still reported and attributed individually on failure.
When would you choose CSV over JSON for external test data?▾
When the data is genuinely tabular — several simple fields varying together across rows — and when non-developers benefit from being able to review or edit it without touching code.
When does JSON fit external test data better than CSV?▾
When the data has a nested, non-flat shape that doesn't flatten cleanly into CSV columns but deserializes naturally into a POJO.
Why is Excel described as appropriate only in a narrower set of cases?▾
It requires heavier tooling (like Apache POI) than CSV or JSON; it's genuinely justified mainly when non-technical stakeholders already maintain data in Excel as part of an existing workflow, not as a default choice.
