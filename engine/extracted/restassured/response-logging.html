Response Logging

Prerequisites: Request Logging

What is this?

given()
    .when()
        .get("/users/2")
    .then()
        .log().all() // logs the RESPONSE — placed after .then(), not given()
        .statusCode(200);

Response logging is the mirror image of request logging: instead of confirming what you sent, it shows you exactly what came back — status code, headers, and body. Placed after .then(), it prints the response either before or as part of the assertion chain, depending on where in the chain it appears.

Why it's important

When an assertion fails, the failure message tells you what was expected and (often) a summary of what didn't match — but seeing the entire response gives you the full context: is a field missing entirely, or present with the wrong value? Is the whole response shaped differently than you assumed? Response logging answers these faster than inferring from a partial failure message alone.

Basic Example — Logging the Full Response

given()
.when()
    .get("/users/2")
.then()
    .log().all()
    .statusCode(200);

// Prints something like:
// Status: 200 OK
// Headers: Content-Type=application/json; charset=utf-8, ...
// Body: { "data": { "id": 2, "first_name": "Janet", ... } }

Logging Just the Body

given()
.when()
    .get("/users/2")
.then()
    .log().body()  // response body only, skip status/headers
    .statusCode(200);

When you're specifically trying to understand a response's structure — confirming field names before writing a JsonPath expression, for instance — logging just the body avoids scrolling past headers you don't currently care about.

Pretty-Printing for Readability

Response response = given().when().get("/users/2");
System.out.println(response.getBody().asPrettyString());

// vs. the compact, single-line default:
System.out.println(response.getBody().asString());

.asPrettyString() formats JSON (or XML) with indentation, which is dramatically easier to read for anything beyond a very small, flat response — worth reaching for whenever you're manually inspecting a response body rather than relying on .log()'s default formatting.

Detailed Example — Understanding an Unfamiliar Response Shape

@Test
void exploringAResponseShapeBeforeWritingAssertions() {
    Response response = given().when().get("/orders/500");
    System.out.println(response.getBody().asPrettyString());

    // Output reveals the actual structure — nested customer object,
    // array of line items, etc. — informing exactly which JsonPath
    // expressions the REAL assertions (written next) should use
}

This is a genuinely common, legitimate workflow: before writing assertions against an API you haven't worked with before, print and read one real response first. Guessing at a response's structure and writing assertions against your assumption is slower (and more error-prone) than looking at the real thing once.

Real-World Example — Comparing Expected vs. Actual on a Failure

@Test
void debuggingAFailingBodyAssertion() {
    given()
    .when()
        .get("/users/2")
    .then()
        .log().ifValidationFails() // covered fully on the next page
        .body("data.first_name", equalTo("Janet"));
    // If this assertion fails, the full response prints automatically —
    // revealing whether "first_name" is missing, misspelled, or just has a different value
}

❌ Fragile vs. ✅ Recommended

// ❌ Guessing at a response's structure without ever having looked at a real one
.then().body("user.details.contact.email", equalTo("john@example.com")); // wrong nesting, fails mysteriously

// ✅ Log a real response first, THEN write assertions against its actual structure
Response sample = given().when().get("/users/2");
System.out.println(sample.getBody().asPrettyString());
// ...now write assertions matching what you actually saw

Common Mistakes

  • Writing assertions against an assumed response structure without ever having looked at a real response first.
  • Using the compact .asString() when manually inspecting a response, instead of .asPrettyString() — makes anything beyond a trivial response hard to read.
  • Leaving full response logging in committed code for the same reason covered on the Request Logging page — floods CI output unnecessarily.

Edge Cases

  • Very large response bodies (a big paginated list) — full logging can produce a huge amount of console output; consider logging just a specific extracted piece instead of the entire response.
  • Binary response bodies (a downloaded file, an image) — .log().body() isn't meaningful here; check Content-Type and length instead of attempting to print binary content.

Debugging

When a test fails and the assertion message alone doesn't make the cause obvious, log the full response next — comparing what you expected against everything the API actually returned resolves most confusing failures faster than staring at the assertion error alone.

Best Practices

  • Log and read one real response before writing assertions against an unfamiliar API's shape.
  • Use .asPrettyString() for manual inspection of anything beyond a trivially small response.
  • Prefer conditional response logging (next page) over permanent full logging in committed test code.

Practice Exercise

Against an API endpoint you haven't tested before, log and pretty-print a real response first, then write three assertions based on what you actually observed — confirming this workflow is faster and more accurate than guessing at the structure upfront.

Summary

Response logging — full via .log().all() after .then(), targeted via .log().body(), or manual via .asPrettyString() — shows you exactly what an API returned, which is invaluable both for understanding an unfamiliar response shape before writing assertions and for diagnosing why an existing assertion is failing.

Interview Questions

Why is it a good habit to log and inspect a real response before writing assertions against an API you haven't tested before?▾
Assumptions about a response's structure — field names, nesting, whether something is an object or an array — are frequently wrong in small but assertion-breaking ways, especially for APIs you didn't design yourself. Writing assertions against an assumed structure produces confusing failures that look like bugs in the API but are actually just incorrect JsonPath expressions. Looking at one real, logged response first means every subsequent assertion is written against the actual shape, not a guess.
Why print a real response and read it before writing assertions against an unfamiliar API?▾
Assumptions about response structure — field names, nesting — are frequently wrong in small, assertion-breaking ways; looking at one real response first means every subsequent assertion matches the actual shape, not a guess.
What does .asPrettyString() give you that .asString() doesn't?▾
Indented, formatted output that's dramatically easier to read for anything beyond a trivially small response — the compact default is hard to parse visually once a response has any real structure.
Why does a failing assertion often benefit from full response logging, not just the assertion's own error message?▾
The assertion error alone might say 'expected X, got Y' without full context; the complete response reveals whether a field is missing entirely, misspelled, or just has an unexpected value.
Is logging the full response appropriate for every test in committed code?▾
No — the same CI-noise concern from request logging applies; conditional logging (covered on the next page) is the pattern real projects converge on for committed code.
