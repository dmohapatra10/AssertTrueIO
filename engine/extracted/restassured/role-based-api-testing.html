Role-Based API Testing

Prerequisites: Authentication Reuse & Token Management

What is this?

Every page so far in this chapter has been about authentication — proving who you are. This page is about authorization — testing that once authenticated, a user can only do what their role actually permits. This is where the authentication-vs-authorization distinction from Chapter 1 becomes the real focus.

Why it's important

A permission check that's missing or wrong on even one endpoint is a genuine security bug, not just a functional one — a regular user able to hit an admin-only endpoint because a permission check was forgotten on that specific route is exactly the kind of gap thorough role-based testing exists to catch, and exactly the kind of gap that's easy to miss if you only ever test with one admin account.

Common Roles Worth Testing

  • Admin — typically has access to everything, including other users' data and system-level operations.
  • Regular User — access limited to their own data and standard operations.
  • Read-Only User — can view but not modify; a common role for auditors, support staff, or reporting access.
  • Manager — often an intermediate role: broader access than a regular user, narrower than a full admin (e.g., managing their own team's data, but not the entire system).

Basic Example — The Same Endpoint, Different Roles, Different Outcomes

@Test
void adminCanAccessUserManagement() {
    given().header("Authorization", "Bearer " + TokenManager.getTokenForRole("admin"))
        .when().get("/admin/users")
        .then().statusCode(200);
}

@Test
void regularUserCannotAccessUserManagement() {
    given().header("Authorization", "Bearer " + TokenManager.getTokenForRole("user"))
        .when().get("/admin/users")
        .then().statusCode(403); // authenticated, but not authorized
}

Notice the second test expects 403, not 401 — the user is genuinely authenticated (a valid token), just not authorized for this specific action. Getting this distinction right in your assertions (from Chapter 1) matters for precisely diagnosing what a failure actually means.

Detailed Example — Testing a Read-Only Role's Boundary Precisely

@Test
void readOnlyUserCanViewButNotModify() {
    String readOnlyToken = TokenManager.getTokenForRole("readonly");

    // CAN view
    given().header("Authorization", "Bearer " + readOnlyToken)
        .when().get("/orders")
        .then().statusCode(200);

    // CANNOT create
    given().header("Authorization", "Bearer " + readOnlyToken)
        .body(newOrder)
        .when().post("/orders")
        .then().statusCode(403);

    // CANNOT modify
    given().header("Authorization", "Bearer " + readOnlyToken)
        .pathParam("id", existingOrderId)
        .body(updatedOrder)
        .when().put("/orders/{id}")
        .then().statusCode(403);

    // CANNOT delete
    given().header("Authorization", "Bearer " + readOnlyToken)
        .pathParam("id", existingOrderId)
        .when().delete("/orders/{id}")
        .then().statusCode(403);
}

A single test verifying all four operations against one role is a thorough, precise way to confirm a "read-only" role actually means read-only across every mutating operation — not just one of them. It's a common, real bug for a permission system to correctly block CREATE but accidentally allow UPDATE or DELETE for the same role.

Real-World Example — Testing a Manager's Scoped Access

@Test
void managerCanOnlyAccessOwnTeamsData() {
    String managerToken = TokenManager.getTokenForRole("manager");

    // CAN access their own team's data
    given().header("Authorization", "Bearer " + managerToken)
        .pathParam("teamId", managerOwnTeamId)
        .when().get("/teams/{teamId}/reports")
        .then().statusCode(200);

    // CANNOT access a DIFFERENT team's data — this is the real test
    given().header("Authorization", "Bearer " + managerToken)
        .pathParam("teamId", someOtherTeamId)
        .when().get("/teams/{teamId}/reports")
        .then().statusCode(403);
}

This is a subtler, often-missed category of authorization bug: not "does this role have permission for this type of action at all," but "is this specific instance of data scoped correctly to this specific user." A manager correctly having access to a team's reports doesn't guarantee they're correctly restricted to their own team's reports — this needs its own explicit test, since it's a genuinely different failure mode than a missing role check entirely.

❌ Fragile vs. ✅ Recommended

// ❌ Only ever testing with one admin account — the suite has no idea
// whether permission boundaries are actually enforced for anyone else
given().header("Authorization", "Bearer " + adminToken).when().get("/orders").then().statusCode(200);

// ✅ Testing the same endpoint across multiple roles, confirming
// each gets the outcome their role should actually produce
given().header("Authorization", "Bearer " + adminToken).when().get("/admin/users").then().statusCode(200);
given().header("Authorization", "Bearer " + userToken).when().get("/admin/users").then().statusCode(403);

Common Mistakes

  • Only ever testing with an admin account — a suite that never authenticates as anything less privileged has zero coverage of whether permission boundaries actually work.
  • Testing that a role CAN'T do something for only one type of operation, not all the mutating ones — a read-only role blocked from CREATE but accidentally allowed UPDATE is a real, missable bug.
  • Testing role-level permissions but never data-scoping — confirming a manager role can access "team reports" in general without confirming they're restricted to their own specific team.
  • Using 401 instead of 403 in assertions for an authenticated-but-unauthorized scenario — conflates two genuinely different failure categories.

Edge Cases

  • A user whose role changes mid-session (promoted from user to manager while their token is still valid) — worth testing whether the API re-checks permissions per-request (using current role) or trusts whatever was baked into the token at issuance time; this is a real design decision with security implications.
  • Roles with overlapping but not identical permissions — don't assume role hierarchies are strictly nested (manager ⊃ user, admin ⊃ manager); verify the actual permission matrix rather than assuming a clean hierarchy.

Debugging

If a role-based test fails unexpectedly, first confirm which token was actually used — logging the Authorization header (or at minimum, decoding the JWT's role claim, from the JWT Authentication page) rules out "wrong role's token was accidentally used" as the cause before investigating the API's permission logic itself.

Best Practices

  • Test every meaningfully distinct role your API supports, not just admin.
  • For any role with restricted permissions, test every mutating operation (create/update/delete) it should be blocked from, not just one.
  • Test data-scoping (own resources vs. others') as a distinct concern from role-level permission checks.
  • Use 403 (not 401) for authenticated-but-unauthorized assertions.

Practice Exercise

Design a test suite section for an API with Admin, Manager, and Regular User roles, covering: what each role can access, what each role is explicitly blocked from, and at least one data-scoping test confirming a Manager can't access another manager's team data.

Summary

Role-based API testing is where authorization — not authentication — becomes the real focus: confirming each role can do exactly what it should and nothing more, across every mutating operation, and that data access is correctly scoped to what a given user or role actually owns, not just gated by role-level checks alone. A suite that only ever tests with an admin account has effectively no authorization coverage at all.

Interview Questions

A permission test confirms a read-only role gets a 403 when attempting to POST a new resource. Is this test sufficient to confirm the role is genuinely read-only?▾
Not on its own — confirming CREATE is blocked doesn't guarantee UPDATE and DELETE are also correctly blocked; a real, common bug is a permission system that correctly restricts one mutating operation while accidentally allowing another for the same role. Thoroughly confirming a role is genuinely read-only requires testing all three mutating operations (create, update, delete) return the correct forbidden status, plus confirming the role can still successfully read — a role that's accidentally blocked from reading too would also be a bug, just a different one.
Why does testing only with an admin account provide zero authorization coverage?▾
A suite that never authenticates as anything less privileged has no way of verifying whether permission boundaries actually work for anyone but the most privileged account.
Why is confirming a read-only role is blocked from POST insufficient to confirm it's genuinely read-only?▾
A permission system could correctly block CREATE while accidentally allowing UPDATE or DELETE for the same role — a real, missable bug; all mutating operations need testing, not just one.
What's the difference between role-level authorization and data-scoping authorization?▾
Role-level asks 'can this role perform this TYPE of action at all'; data-scoping asks 'is this specific instance of data correctly restricted to the right owner' — a manager correctly having team-report access doesn't guarantee they're restricted to their OWN team specifically.
Why use 403, not 401, when a valid but insufficiently-privileged user hits a restricted endpoint?▾
The user is genuinely, successfully authenticated — the failure is purely about permission, which is exactly what 403 signals, as opposed to 401's 'we don't know who you are.'
