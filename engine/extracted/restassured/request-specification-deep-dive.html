RequestSpecification Deep Dive

Prerequisites: Request & Response Specifications overview

What is this?

RequestSpecification requestSpec =
    new RequestSpecBuilder()
        .setBaseUri("https://api.example.com")
        .setContentType(ContentType.JSON)
        .build();

given()
    .spec(requestSpec)
.when()
    .get("/users");

A RequestSpecification is a reusable bundle of request setup — base URI, headers, content type, and more — built once and applied via .spec() to any number of individual requests. Recall from Chapter 2 that given() itself already returns a RequestSpecification; building one explicitly with RequestSpecBuilder just lets you construct and name that object ahead of time, separately from any individual test.

Why It Exists

Without it, every test repeats the same base URI, headers, and content type — the exact duplication problem the chapter overview showed. A shared RequestSpecification means that setup is defined in exactly one place; changing it once (a new base URI for a new environment, an additional required header) automatically applies everywhere the spec is used.

What Typically Goes in a Shared Spec

  • Base URI — the API's root URL, read from an environment variable for the multi-environment strategy covered in the next chapter.
  • Content-Type — almost always the same across an entire API (typically JSON).
  • Common headers — anything sent on nearly every request, like a client identifier or API version header.

Authentication is a more nuanced case, worth its own discussion below.

Basic Example — A Shared Spec With Common Headers

RequestSpecification requestSpec =
    new RequestSpecBuilder()
        .setBaseUri(System.getenv("API_BASE_URL"))
        .setContentType(ContentType.JSON)
        .addHeader("X-Client-Version", "2.4.1")
        .addHeader("Accept", "application/json")
        .build();

given().spec(requestSpec).when().get("/users").then().statusCode(200);
given().spec(requestSpec).when().get("/orders").then().statusCode(200);

Reading the base URI from an environment variable, rather than hardcoding it, is what lets this exact spec run correctly against local, QA, or staging without any code changes — tying directly back to the environment strategy from earlier in this course.

Detailed Example — Including Authentication in a Shared Spec

RequestSpecification authenticatedSpec =
    new RequestSpecBuilder()
        .setBaseUri(System.getenv("API_BASE_URL"))
        .setContentType(ContentType.JSON)
        .addHeader("Authorization", "Bearer " + TokenManager.getToken())
        .build();

given().spec(authenticatedSpec).when().get("/profile").then().statusCode(200);

Building the spec after obtaining a token (via the Token Management pattern from Chapter 6) means the auth header is baked into the spec itself, and every test using it is automatically authenticated with no per-test header repetition. Be mindful of when this spec is built, though — if it's constructed once at class load time with a token that later expires, every subsequent test using it will start failing; specs built per-class in a @BeforeAll, refreshed appropriately, avoid this.

Overriding Part of a Shared Spec Per Test

// The shared spec includes a default Authorization header —
// this ONE test needs to run as a different role
given()
    .spec(authenticatedSpec)
    .header("Authorization", "Bearer " + TokenManager.getTokenForRole("admin")) // overrides the spec's value
.when()
    .get("/admin/dashboard");

This is the same override behavior covered in Chapter 8's Headers page — a value set after .spec(...) in the same chain takes precedence over what the spec itself defined. This is genuinely useful for the occasional test that needs to deviate from the shared default without needing a second, nearly-identical spec just for that one case.

Real-World Example — A Base Test Class Building the Spec Once

public abstract class BaseApiTest {
    protected static RequestSpecification requestSpec;

    @BeforeAll
    static void setupSpec() {
        requestSpec = new RequestSpecBuilder()
            .setBaseUri(System.getenv("API_BASE_URL"))
            .setContentType(ContentType.JSON)
            .addHeader("Authorization", "Bearer " + TokenManager.getToken())
            .build();
    }
}

public class OrderApiTest extends BaseApiTest {
    @Test
    void getOrders() {
        given().spec(requestSpec).when().get("/orders").then().statusCode(200);
    }
}

This is the natural home for a shared spec in a real project — built once, in a base class every test class extends, exactly mirroring the base URI configuration pattern from Chapter 2, just consolidated into one richer object instead of several separate RestAssured.baseURI-style static fields.

❌ Fragile vs. ✅ Recommended

// ❌ Repeating base URI, content type, and auth header setup in every test file
given().baseUri(url).contentType(JSON).header("Authorization", "Bearer " + t).when().get("/orders");
// ...identical setup repeated across dozens of files

// ✅ One shared spec, referenced everywhere
given().spec(requestSpec).when().get("/orders");

Common Mistakes

  • Building a spec with a token that later expires, without any refresh mechanism — every test using the stale spec starts failing with 401s, all traceable to one root cause.
  • Not overriding a spec's value when a specific test genuinely needs to — instead duplicating an entire near-identical spec just to change one header.
  • Putting environment-specific values directly in the spec definition instead of reading them from environment variables — defeats the purpose of a spec that's meant to work across environments.

Edge Cases

  • A spec needed before authentication has happened yet (the login request itself) — this request can't use an authenticated spec, since there's no token yet; it either uses no spec, or a separate unauthenticated one (covered further on the Multiple Specifications page).
  • Specs built per-test instead of per-class — usually unnecessary overhead; building once and reusing across every test in a class is almost always the right scope.

Debugging

If a test using a shared spec fails with an unexpected header or URL, use .log().all() (Chapter 8) — the fully resolved request shows exactly what the spec actually contributed, which is useful for confirming a spec was built or applied correctly.

Best Practices

  • Build a shared spec once, typically in a base test class's @BeforeAll, not per individual test.
  • Read environment-specific values (base URI, credentials) from environment variables within the spec, not hardcoded.
  • Override specific values per test when needed, rather than duplicating an entire spec for a one-off difference.

Practice Exercise

Build a shared RequestSpecification with a base URI (from an environment variable), a Content-Type, and an Authorization header from a token manager. Use it across three different test methods, then write a fourth test that overrides the Authorization header to use a different role's token.

Summary

RequestSpecification, built via RequestSpecBuilder, bundles reusable request setup — base URI, headers, content type, authentication — into one object applied via .spec(). Building it once (typically in a shared base class) and referencing it everywhere eliminates the setup duplication that plagues a suite where every test repeats the same handful of configuration lines.

Interview Questions

If a shared RequestSpecification includes an Authorization header, and one specific test needs to run as a different user role, do you need a separate spec for that test?▾
No — a value set directly in a test's own given() chain, after .spec(...), overrides the same value defined in the shared spec, since it's applied later in the chain. This means one test can use the shared spec for everything else (base URI, content type, common headers) while overriding just the Authorization header for its specific role, without needing to duplicate an entire near-identical spec just for that one difference.
Why does a value set after .spec(requestSpec) in the same chain override the spec's own value?▾
It's applied later in the chain than the spec — RestAssured resolves the request in order, so anything set afterward takes precedence, letting one test deviate from a shared default without needing an entirely separate spec.
What's the risk of building an authenticated spec once at class load time with a token that later expires?▾
Every subsequent test using that spec starts failing with 401s once the token expires — specs refreshed appropriately (via a proper token manager) avoid this.
Why can't the login request itself use the authenticated RequestSpecification?▾
The authenticated spec includes an Authorization header built from a token — but login is exactly what produces that token; there's no token yet, so login needs a separate, minimal unauthenticated spec.
Where is the natural home for building a shared RequestSpecification in a real project?▾
A shared base test class's @BeforeAll — built once, alongside base URI configuration, so every subclassing test inherits consistent setup automatically.
