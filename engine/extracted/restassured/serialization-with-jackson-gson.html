Serialization with Jackson & Gson

Prerequisites: POJO Design for API Testing

What is this?

User user = new User("John", "john@example.com");

given()
    .contentType(ContentType.JSON)
    .body(user)     // ← serialization happens here, automatically
.when()
    .post("/users");

Serialization is the process of converting a Java object into its JSON text representation. When you pass a POJO to .body(), RestAssured hands it to whichever JSON library is on your classpath — Jackson or Gson — which walks the object's fields (via getters, by default) and produces the equivalent JSON string, entirely automatically. You never call a serialization method directly in typical usage.

Why it's important

Understanding that this conversion is automatic — and what it actually does under the hood — is what lets you predict and control the exact JSON your request will contain, rather than treating it as an opaque black box you only discover through trial and error.

Jackson vs. Gson

Both are JSON libraries capable of the same fundamental job; RestAssured detects whichever is present on your classpath and uses it. Jackson is the more common default in most Java projects (and Spring-based projects almost always already have it as a transitive dependency), with more configuration options and annotations. Gson, from Google, is simpler and has a smaller footprint, sometimes preferred for that reason. If both are on the classpath, RestAssured picks one (Jackson takes priority in recent versions) — worth confirming explicitly if your project has both and you're seeing unexpected serialization behavior.

Basic Example

public class User {
    private String name;
    private String email;
    // getters/setters
}

User user = new User("John", "john@example.com");
given().contentType(ContentType.JSON).body(user).when().post("/users");

// Produces this JSON body:
// { "name": "John", "email": "john@example.com" }

By default, the JSON field names match the Java field names exactly (or more precisely, the getter names with "get" stripped and the first letter lowercased) — getName() becomes "name" in the output JSON.

Controlling the Output with Annotations

public class User {
    @JsonProperty("full_name")
    private String name;

    @JsonInclude(JsonInclude.Include.NON_NULL)
    private String middleName; // omitted from JSON entirely if null

    @JsonIgnore
    private String internalNotes; // never serialized, regardless of value
}

@JsonProperty maps a Java field to a differently-named JSON key — essential when the API uses snake_case (full_name) but your Java code follows camelCase convention (name), or when a JSON field name is a reserved Java keyword. @JsonInclude(NON_NULL) omits a field from the output entirely when it's null, rather than serializing it as "middleName": null — useful for APIs that treat an omitted field differently from an explicitly-null one. @JsonIgnore excludes a field from serialization entirely, useful for fields that exist on the Java side for test-only bookkeeping but shouldn't appear in the actual request.

Detailed Example — Testing an API That Expects snake_case

public class OrderRequest {
    @JsonProperty("item_name")
    private String itemName;

    @JsonProperty("quantity_ordered")
    private int quantityOrdered;
}

OrderRequest order = new OrderRequest("Wireless Mouse", 2);
given().contentType(ContentType.JSON).body(order).when().post("/orders");

// Produces: { "item_name": "Wireless Mouse", "quantity_ordered": 2 }
// NOT: { "itemName": "Wireless Mouse", "quantityOrdered": 2 }

Without the @JsonProperty annotations, this request would serialize using the Java field names directly — itemName, not item_name — and a snake_case API would likely reject it or silently ignore fields it doesn't recognize. This exact mismatch is covered more systematically in the ObjectMapper Configuration page, which shows a project-wide alternative to annotating every single field.

❌ Fragile vs. ✅ Recommended

// ❌ Manually building JSON strings to work around naming mismatches
String body = "{\\"item_name\\": \\"" + itemName + "\\", \\"quantity_ordered\\": " + qty + "}";

// ✅ Let annotated POJO serialization handle the mapping correctly and safely
OrderRequest order = new OrderRequest(itemName, qty);
given().body(order).when().post("/orders");

Common Mistakes

  • Assuming Java field names always match JSON field names without checking — snake_case APIs are common and will silently produce a mismatched request without @JsonProperty.
  • Serializing null fields the API doesn't expect to see at all, instead of using @JsonInclude(NON_NULL) when the distinction between "omitted" and "explicitly null" matters to that specific API.
  • Not knowing which JSON library is actually active when both Jackson and Gson are on the classpath, leading to confusing "why doesn't this annotation work" moments (Gson doesn't recognize Jackson's annotations, and vice versa).

Edge Cases

  • Enums — serialize to their name by default (ACTIVE, not a custom string) unless you add a custom serializer or @JsonValue annotation to control the output.
  • Date/time fields — Jackson's default date handling has historically been a common source of confusion (numeric timestamps vs. ISO strings); the jackson-datatype-jsr310 module and explicit @JsonFormat annotations give you control over this.

Debugging

If you're unsure exactly what JSON a POJO will produce, serialize it manually and print the result before sending it: new ObjectMapper().writeValueAsString(user). This isolates whether a problem is in your POJO's serialization or somewhere else in the request.

Best Practices

  • Use @JsonProperty explicitly whenever Java naming convention and the API's actual JSON naming convention diverge.
  • Be deliberate about @JsonInclude(NON_NULL) — only apply it where the API genuinely distinguishes "omitted" from "null."
  • Know which JSON library is active in your project, and don't mix annotations from both.

Practice Exercise

Design a POJO for an API that expects snake_case field names, using @JsonProperty to map from camelCase Java fields. Serialize an instance manually with an ObjectMapper and print the result to confirm the field names match what the API expects.

Summary

Serialization converts a Java POJO into JSON automatically the moment you pass it to .body() — driven by Jackson or Gson, whichever is on your classpath. By default, field names map directly, but @JsonProperty, @JsonInclude, and @JsonIgnore give you precise control over the output whenever an API's naming convention or null-handling contract differs from your POJO's natural Java shape.

Interview Questions

Your POJO has a field named itemName, but the API expects item_name in the JSON body. What happens if you don't address this, and how do you fix it?▾
Without any adjustment, Jackson serializes the field using its Java name directly, producing "itemName" in the JSON — not the "item_name" the API expects. Depending on how strict the API is, this either gets silently ignored (the field the API actually looks for is missing) or rejected outright. The fix is annotating the field with @JsonProperty("item_name"), which tells Jackson to use that specific JSON key regardless of the Java field's own name.
What does @JsonProperty actually solve?▾
Mapping a Java field to a differently-named JSON key — essential when an API uses snake_case but your Java code follows camelCase convention, or when a JSON field name is a reserved Java keyword.
What's the difference between @JsonInclude(NON_NULL) and just leaving a field null?▾
Without it, a null field serializes as "field": null in the output; with it, the field is omitted from the JSON entirely — useful for APIs that treat 'omitted' differently from 'explicitly null'.
Why might RestAssured behave unexpectedly if both Jackson and Gson are on the classpath?▾
RestAssured picks one automatically (Jackson takes priority in recent versions) — worth confirming explicitly if a project has both and is seeing unexpected serialization behavior, since annotations from one library aren't recognized by the other.
How would you confirm exactly what JSON a POJO produces before sending it?▾
Serialize it manually first with new ObjectMapper().writeValueAsString(obj) and print the result — isolates whether a problem is in the POJO's serialization or somewhere else in the request.
