Prerequisites: Getting Started with Java & RestAssured

Building a Request, Piece by Piece

Every RestAssured test starts with the same job: describe exactly what request you want to send — which method, which resource, what headers, what data. That's the given() half of the given/when/then structure from Chapter 2, and it's genuinely rich enough to deserve real depth of its own, covered across nine focused pages:

  1. GET Requests — fetching, filtering, and pagination correctness
  2. POST Requests — creating resources and validating what got generated
  3. PUT Requests — full resource replacement, and the data-loss bug it causes if misused
  4. PATCH Requests — partial updates, and when they are (and aren't) idempotent
  5. DELETE Requests — verifying removal, and resilient cleanup patterns
  6. Headers — Content-Type, Accept, and custom headers
  7. Query Parameters — filtering and shaping a request against a collection
  8. Path Parameters — identifying which specific resource a request addresses
  9. Request Body Construction — raw String, Map, and POJO approaches, and when to use each

The first five pages cover each HTTP method in depth — the scenarios, edge cases, and real bugs specific to that method. The last four cover the mechanics of constructing any request, regardless of which method you're using.

Why Getting This Right Matters

A poorly constructed request produces a confusing failure that has nothing to do with what you're actually trying to test — a 400 because a required header is missing, a 404 because a path parameter was used where a query parameter belonged, a rejected body because the wrong Content-Type was set. None of these failures tell you anything about your application's business logic; they're purely artifacts of the request being built incorrectly. Getting comfortable with every piece covered here means your test failures actually mean something when they happen.

Request Methods

given().when().get("/users");
given().when().post("/users");
given().when().put("/users/{id}");
given().when().patch("/users/{id}");
given().when().delete("/users/{id}");

Which method you call determines what RestAssured actually sends on the wire — the choice isn't cosmetic. Calling .post() instead of .get() against the same URL sends a fundamentally different HTTP request, and a real API will very likely respond differently (or reject it outright) depending on which method it receives. Chapter 1 covered what each method means conceptually — the five method pages that open this chapter (GET, POST, PUT, PATCH, DELETE) each go deep on that specific method's real testing scenarios: pagination correctness for GET, validating generated fields for POST, the data-loss bug PUT causes when misused, idempotence for PATCH, and resilient cleanup for DELETE.

The Anatomy of a given() Block

given()
    .header("Authorization", "Bearer " + token)   // ← Headers page
    .queryParam("include", "profile")               // ← Query Parameters page
    .pathParam("id", 42)                             // ← Path Parameters page
    .body(newUser)                                   // ← Request Body Construction page
.when()
    .post("/users/{id}/update");

Every one of these four building blocks can appear in the same request, in any order — RestAssured collects them all before actually sending anything when .when() fires. Reading a real given() block, you should be able to identify at a glance which category each line belongs to: is this metadata about the request (header), a filter on a collection (query param), an identifier for a specific resource (path param), or the actual payload (body)?

Query Parameter vs. Path Parameter — A Quick Reminder

Path parameter — identifies WHICH resource:
GET /users/42

Query parameter — filters, sorts, or paginates WITHIN a resource collection:
GET /users?status=active&page=2

This distinction from Chapter 1 gets revisited in real code on the dedicated Query Parameters and Path Parameters pages — getting it wrong is one of the more common early RestAssured mistakes, since both "just go in the URL" at a glance. A useful test: if the value changes which resource you're even talking about, it's a path parameter; if it just narrows or shapes a request against a resource collection that exists independent of it, it's a query parameter.

Real-World Example — Combining Everything

OrderRequest order = new OrderRequest("Wireless Mouse", 2);

given()
    .contentType(ContentType.JSON)
    .header("X-Request-ID", UUID.randomUUID().toString())
    .pathParam("customerId", 42)
    .body(order)
.when()
    .post("/customers/{customerId}/orders")
.then()
    .statusCode(201);

Every piece from this chapter shows up in one realistic request: a header for request tracing, a path parameter identifying which customer the order belongs to, and a POJO body describing what to create — exactly the shape a real e-commerce API test would take.

Common Mistakes to Watch For

  • Hand-building URLs and JSON strings instead of using RestAssured's dedicated methods for each piece — loses encoding safety, type safety, and readability all at once.
  • Confusing which of the four building blocks a value belongs to — a resource identifier in a query parameter, or a filter value in a path parameter, both produce requests that don't match what the API's routing actually expects.
  • Skipping Content-Type on a request with a body — some servers infer it correctly regardless, but relying on that inconsistently across different APIs is fragile.

What You'll Be Able to Do

By the end of the nine pages that follow, you should be able to look at any REST API's documentation and correctly identify: which HTTP method to use for a given scenario, the real testing pitfalls specific to that method, and how to construct the request correctly — headers, query params, path params, and body. Interview Questions

Why does calling .post() instead of .get() against the same URL matter beyond just different Java syntax?▾
It sends a fundamentally different HTTP request — the server's routing and business logic branch based on the method, so the same URL can behave completely differently depending on which method actually hits it.
What determines whether a value belongs in a path parameter or a query parameter?▾
Whether the value changes WHICH resource you're talking about (path parameter) or just filters/shapes a request against a resource collection that exists independent of it (query parameter).
Why might a POJO be the wrong tool for testing malformed JSON specifically?▾
A POJO is a real Java object, and JSON libraries only ever serialize valid Java objects into syntactically valid JSON — there's no way to make a POJO produce a trailing comma or unquoted key, since Java's own type system doesn't have a representation for broken JSON.
What's the risk of forgetting Content-Type on a request with a body?▾
Some servers infer it correctly regardless, but relying on that inconsistently across different APIs means a perfectly valid JSON body can be rejected because the server never attempted to parse it as JSON in the first place.
Why does this chapter open with five dedicated method pages before covering headers, params, and body construction?▾
Which method you use determines what's actually sent on the wire — understanding that distinction first makes the mechanics of constructing a request around a given method easier to reason about.
