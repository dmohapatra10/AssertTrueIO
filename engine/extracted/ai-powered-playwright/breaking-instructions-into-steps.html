Breaking Instructions into Steps

Prerequisites: Natural Language Testing

What You'll Learn

  • Decomposing one instruction into a real, ordered list of atomic steps
  • Why each step needs to be genuinely atomic — one clear action, not a bundle
  • Marking which steps depend on a previous step's real result

Introduction

Before anything can be planned or executed, the instruction needs to become a real, structured list — this page builds that first, genuinely necessary piece.

Step-by-Step Implementation

// src/break-into-steps.ts
import { askClaude } from './ai-client';

export interface InstructionStep {
  order: number;
  description: string;
  dependsOnPreviousResult: boolean;
}

export async function breakIntoSteps(
  instruction: string
): Promise<InstructionStep[]> {
  const prompt = `Break this instruction into atomic steps —
each step should be ONE clear action, not a bundle of several:

"${instruction}"

For each step, mark dependsOnPreviousResult TRUE if it needs
information from what actually happened in a PREVIOUS step
(like "select A product" needing to know what a search
actually returned), FALSE if it can be planned independently.

Respond with ONLY valid JSON:
{"steps": [{"order": number, "description": string,
"dependsOnPreviousResult": boolean}]}`;

  const raw = await askClaude(prompt);
  const parsed = JSON.parse(raw);
  if (!Array.isArray(parsed.steps)) {
    throw new Error(`Expected {"steps": [...]} but got: ${raw.slice(0, 200)}`);
  }
  return parsed.steps;
}

Code Explanation

dependsOnPreviousResult is this page's genuinely important addition — it's what later pages use to decide whether a step's action can be planned immediately, or must wait for a real observation first. Marking this explicitly, rather than inferring it later, keeps that decision visible and reviewable, not buried inside a later step's logic.

Expected Result

const steps = await breakIntoSteps(
  'Login to ShopSmart, search for "Laptop", select a product, ' +
  'add it to the cart, and verify the cart total.'
);

// Real output:
// [
//   { order: 1, description: "Log in to ShopSmart",
//     dependsOnPreviousResult: false },
//   { order: 2, description: "Search for 'Laptop'",
//     dependsOnPreviousResult: false },
//   { order: 3, description: "Select a product from the search results",
//     dependsOnPreviousResult: true },
//   { order: 4, description: "Add the selected product to the cart",
//     dependsOnPreviousResult: true },
//   { order: 5, description: "Verify the cart total reflects the added item",
//     dependsOnPreviousResult: true }
// ]

Why It Matters

Notice steps 3 through 5 are all marked as dependent — genuinely accurate, since each one needs a real result from the step before it. Steps 1 and 2 aren't — logging in and searching can both be fully planned without needing to observe anything first. This distinction is exactly what later pages in this chapter use to decide when to check the real page before proceeding.

Common Mistakes

  • Letting a step bundle multiple actions. "Select a product and add it to the cart" as one step hides a real dependency — the add-to-cart action needs the product that was actually selected, which is itself uncertain until search results are seen.
  • Guessing at dependsOnPreviousResult later instead of deciding it here. Marking it explicitly, at this stage, keeps the decision visible and easy to review — inferring it implicitly later hides that reasoning inside code nobody reviews as a design decision.

Best Practices

  • Keep each step to one clear, atomic action — if you're tempted to use "and" inside a step's description, it's probably two steps.
  • Review the dependsOnPreviousResult flags by eye before trusting them — this small, structured field carries real weight in later pages.

Key Takeaways

  • Breaking an instruction into atomic, ordered steps is the real, necessary first piece of this chapter's pipeline.
  • Marking dependency explicitly, at this stage, is what lets later pages decide when a real observation is genuinely required before proceeding.
  • A step that bundles multiple actions hides real dependencies — atomic steps keep them visible.
