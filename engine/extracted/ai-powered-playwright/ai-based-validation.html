Introduction

The previous page identified genuine judgment-call content; this page builds the real function that judges it. Unlike Chapters 3 through 6's structured JSON responses, the output here is deliberately not just a boolean — a bare true or false hides exactly the reasoning a human would need to trust or challenge the result.

Step-by-Step Implementation

// src/ai-content-validation.ts
import { askClaude } from './ai-client';

export interface ContentJudgment {
  meetsRequirement: boolean;
  reasoning: string;
  confidence: 'high' | 'medium' | 'low';
}

export async function validateContentSemantically(
  content: string, requirement: string
): Promise<ContentJudgment> {
  const prompt = `Content to evaluate: "${content}"
Requirement: "${requirement}"

Judge whether this content genuinely meets the requirement.
This is a real judgment call, not a search for an exact string
match — evaluate based on whether a real user would find this
content clear and appropriate for the stated requirement.

Respond with ONLY valid JSON:
{"meetsRequirement": boolean, "reasoning": string,
"confidence": "high" | "medium" | "low"}`;

  const raw = await askClaude(prompt);
  const parsed = JSON.parse(raw);
  if (typeof parsed.meetsRequirement !== 'boolean') {
    throw new Error(`Expected a boolean judgment but got: ${raw.slice(0, 200)}`);
  }
  return parsed;
}

Code Explanation

reasoning is the genuinely important field here, not meetsRequirement alone. A bare boolean tells you the model's conclusion; the reasoning tells you whether that conclusion is actually sound — the same distinction this tutorial has cared about since Chapter 1's honest treatment of confident-but-wrong output. confidence adds a further, useful signal: a low-confidence judgment deserves more human scrutiny than a high-confidence one, even when both say the same thing.

Example — Judging ShopSmart's Promo Code Error

const judgment = await validateContentSemantically(
  "This promo code has expired or doesn't exist — double-check the code and try again",
  "The error message should clearly explain why the promo code was rejected and suggest a next step"
);

// A REAL, useful judgment:
// {
//   meetsRequirement: true,
//   reasoning: "The message explains two possible causes (expired
//     or nonexistent) and suggests a clear next step (double-check
//     and retry), meeting the stated requirement.",
//   confidence: "high"

Why It Matters — Using This Result in a Real Test

test('promo code error message is genuinely helpful', async ({ page }) => {
  await submitInvalidPromoCode(page);
  const errorText = await page.getByRole('alert').textContent();

  const judgment = await validateContentSemantically(
    errorText ?? '',
    'Clearly explains rejection reason and suggests a next step'
  );

  expect(judgment.meetsRequirement, judgment.reasoning).toBe(true);
  // The REASONING becomes part of the TEST'S OWN failure
  // message — a failing run tells a human WHY, immediately,
  // not just THAT it failed

Common Mistakes

  • Discarding reasoning and using only the boolean. This throws away exactly the information a human needs to trust or challenge a judgment call, turning a nuanced evaluation back into an opaque pass or fail.
  • Treating every judgment result identically regardless of confidence. A low-confidence result is genuinely worth flagging for closer human review, not treating the same as a high-confidence one.

Best Practices

  • Always surface reasoning in test output — Playwright's own expect(..., message) pattern above is a simple, real way to do this.
  • Treat this function's result as a genuine judgment to review, especially at lower confidence — not an infallible, final verdict.

Hands-On Exercise

Run this page's function against two versions of a ShopSmart validation message — one genuinely helpful, one technically accurate but vague ("Error: invalid input"). Key Takeaways

  • Role 2 validation returns a structured judgment with reasoning and confidence, not a bare boolean — this is what makes a genuine judgment call reviewable rather than opaque.
  • Surfacing reasoning directly in test failure output turns "the test failed" into "the test failed, and here's why," genuinely useful for whoever investigates.
  • This is real, working Role 2 — and it's exactly why the next two pages exist, to be explicit about when this approach is and isn't the right call.
