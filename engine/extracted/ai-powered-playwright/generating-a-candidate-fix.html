Generating a Candidate Fix

Introduction

This chapter's earlier pages each produced one kind of fix — a locator change, an assertion change, a grouped set of related changes. This page assembles them into one real, coherent artifact: a genuine diff a human can actually read and evaluate.

Step-by-Step Implementation

// src/build-candidate-diff.ts
import { CodeFix } from './generate-locator-fix';
import { AssertionFixCandidate } from './generate-assertion-fix';
import { FailureGroup } from './detect-related-failures';

export interface CandidatePatch {
  filePath: string;
  changes: { lineNumber: number; before: string; after: string; reasoning: string }[];
  groupContext?: string;
}

export function buildCandidatePatch(
  locatorFixes: CodeFix[], assertionFixes: { fix: AssertionFixCandidate; lineNumber: number }[],
  filePath: string, groupContext?: string
): CandidatePatch {
  const changes = [
    ...locatorFixes.map((f) => ({
      lineNumber: f.lineNumber, before: f.originalLine,
      after: f.proposedLine, reasoning: 'Locator healed via Chapter 6/11 pipeline',
    })),
    ...assertionFixes.map(({ fix, lineNumber }) => ({
      lineNumber, before: fix.originalAssertion,
      after: fix.proposedAssertion, reasoning: fix.reasoning,
    })),
  ].sort((a, b) => a.lineNumber - b.lineNumber);

  return { filePath, changes, groupContext };
}

export function formatAsDiff(patch: CandidatePatch): string {
  const header = patch.groupContext
    ? `# ${patch.filePath}\n# Context: ${patch.groupContext}\n\n`
    : `# ${patch.filePath}\n\n`;
  const body = patch.changes.map((c) =>
    `Line ${c.lineNumber}:\n- ${c.before}\n+ ${c.after}\n  Reason: ${c.reasoning}\n`
  ).join('\n');
  return header + body;
}

Code Explanation

Every change carries its own reasoning field through to the final diff — nothing gets flattened into an anonymous list of line changes. This directly continues Chapter 9's own lesson about surfacing reasoning, not just a bare result: a reviewer reading this diff sees not just what changed, but why, for every single line.

Why It Matters

This is exactly the artifact this chapter's remaining pages need — something concrete enough to validate (does it produce a passing test?), check for regressions (does it break anything else?), and present to a human for genuine, informed review. Every earlier page's work culminates in this one, readable object.

Common Mistakes

  • Presenting locator and assertion fixes as separate, disconnected outputs. A human reviewing a real UI change wants one coherent picture, not several fragments to mentally reassemble.
  • Dropping the reasoning field when formatting the final diff. This is exactly the information that makes the diff reviewable rather than just a list of mysterious changes.

Best Practices

  • Assemble every fix type into one unified patch structure before presenting anything to a human — never in disconnected pieces.
  • Carry reasoning through to the final, formatted output — it should never be lost between generation and review.
