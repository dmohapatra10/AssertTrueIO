Step-by-Step Implementation

// src/run-natural-language-plan.ts
import { chromium } from '@playwright/test';
import { breakIntoSteps } from './break-into-steps';
import { planAction } from './plan-action';
import { executeAction } from './map-to-playwright';
import { observePage } from './observe-page';
import { resolveAmbiguousStep } from './resolve-ambiguity';
import { validateAction } from './validate-action';

export async function runNaturalLanguagePlan(instruction: string) {
  const steps = await breakIntoSteps(instruction);
  const browser = await chromium.launch();
  const page = await browser.newPage();
  await page.goto('https://shopsmart.example.com/login');

  let lastObservation = await observePage(page);

  for (const step of steps) {
    let action;

    if (!step.dependsOnPreviousResult) {
      action = await planAction(step, JSON.stringify(lastObservation));
    } else {
      const resolved = await resolveAmbiguousStep(
        step.description, lastObservation
      );
      action = {
        stepOrder: step.order, actionType: 'click' as const,
        target: resolved.chosenValue,
      };
      console.log(`Step ${step.order} resolved: ${resolved.reasoning}`);
    }

    const validation = await validateAction(action, page);
    if (!validation.valid) {
      console.error(`Step ${step.order} FAILED validation: ${validation.reason}`);
      break;
    }

    await executeAction(action, page);
    lastObservation = await observePage(page);
    console.log(`Step ${step.order} complete: ${step.description}`);
  }

  await browser.close();
}

Code Explanation

Notice the structure directly mirrors this chapter's own architecture diagram: plan (or resolve, for dependent steps) → validate → execute → observe → repeat. lastObservation is what threads real, current information from one iteration into the next — exactly the loop back from Observation to Next Action that made this chapter's problem genuinely different from Chapters 3 and 4's one-shot generation.

Common Mistakes

  • Skipping validation "just for this run" to see the loop work faster. This chapter's own validation page exists specifically because a bad action mid-sequence cascades — skipping it defeats the entire point of building it.
  • Forgetting to update lastObservation after every action, not just dependent ones. Even an independent step can change what the page shows — the next step's planning should always have the most current, real observation available.

Best Practices

  • Log every ambiguous resolution's reasoning, as this page does — it's genuinely cheap now and genuinely valuable during a later investigation.
  • Stop the loop immediately on a validation failure, rather than attempting to continue past a step that couldn't be trusted.

Interview Questions

Beginner: Why can't "select a product" be planned the same way "log in" can, using Chapter 3's one-shot generation approach?▾

"Log in" needs no information beyond what's already known — a fixed email field, password field, and submit button. "Select a product" genuinely depends on what a real search actually returns, which isn't knowable until the search step has actually executed. Planning it in advance, the way Chapter 3 planned a whole test file up front, would force a guess at a specific product name rather than a choice grounded in real, observed results.

Beginner: What is the practical difference between a "step" (from Breaking Instructions into Steps) and an "action" (from AI Action Planning)?▾

A step is still a plain-language description — "log in to ShopSmart." An action is a structured, constrained, concrete intent — { actionType: "fill", target: "Email field", value: "..." } — specific enough to validate completely and map deterministically to a real Playwright call. A step often requires several actions; "log in" alone becomes three separate fill and click actions.

Intermediate: Why does mapping a PlannedAction to an actual Playwright call use plain, deterministic code instead of another AI call?▾

Once actionType is constrained to one of four known values and target is a known, mapped locator, there's exactly one correct Playwright call for that combination — a genuine, exact answer, not a judgment call. This is Chapter 2's core rule applied directly: AI reasoning belongs where genuine judgment is needed, and an exact, deterministic mapping doesn't need it. Using AI here would add real cost and latency, and genuine risk of an incorrect mapping, for zero benefit over a lookup table.

Intermediate: Why does resolveAmbiguousStep record and return its reasoning, rather than just returning the chosen value?▾

An ambiguous instruction resolved silently becomes invisible the moment something later depends on that choice. If a test fails weeks later because ShopSmart's search result ordering changed, the recorded reasoning ("selected the first result because no criteria were specified") immediately tells an investigator this was always an arbitrary-but-reasonable default, not a new, mysterious application bug. Without that record, the same failure looks like ShopSmart itself broke, when the real cause is a resolution strategy nobody could see.

Advanced: Why does validateAction check whether a target exists on the CURRENT page, when Mapping Actions to Playwright already confirmed the target has a known locator?▾

These are genuinely different questions. Having a known locator function in SHOPSMART_LOCATORS confirms the code knows HOW to find that element, in the abstract — it says nothing about whether that element actually exists on the page RIGHT NOW, in this specific moment of a live, unfolding sequence. A "Log In button" locator is valid in the abstract, but querying for it after a previous action already navigated past the login page would find nothing. Checking real, current existence — not just locator validity — is what catches a genuinely different, real class of mistake specific to multi-step, stateful execution.

Scenario-based: A teammate wants to skip the observation step for actions where dependsOnPreviousResult is false, reasoning "independent steps don't need it." How would you respond, using this page's own code?▾

I'd point to this page's own "Common Mistakes" section directly: even an independent step's action can genuinely change what the page shows — clicking "Log In" changes the entire page, regardless of whether that click itself needed a prior observation to be planned. The dependsOnPreviousResult flag governs whether PLANNING that specific step needs a prior observation — it says nothing about whether the RESULT of executing it should be observed for the sake of every step that follows. Skipping observation after an independent step risks the very next step planning against stale, outdated information, even if that next step happens to also be independent. The loop observes after every single action for exactly this reason, not just before dependent ones.
