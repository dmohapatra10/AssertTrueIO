Why It Matters — These Levers Compound

None of these five techniques alone would make a 2,000-test suite affordable at real scale — intelligent selection alone still analyzes every genuine failure fully; caching alone still runs every test. Together, each addressing a different real inefficiency, they compound into something genuinely sustainable, the same way Chapter 11's validation, regression, and approval stages each addressed a different real risk rather than one covering everything.

Interview Questions

Beginner: Why does this chapter avoid stating specific dollar amounts for AI API costs?▾

Pricing changes over time, and a specific dollar figure written into a tutorial becomes stale and potentially misleading the moment pricing actually changes. This chapter instead focuses on the durable, real mechanics — how tokens are counted, relative cost differences between call types, and the arithmetic for estimating real usage — pointing to the live pricing page for current, accurate numbers rather than embedding a number that will go out of date.

Beginner: What is the real, concrete difference between the caching this chapter builds and Chapter 8's test-data caching?▾

Chapter 8 cached generated test data specifically for reproducibility — the same data, deliberately reused across runs so a failure could be reliably reproduced later. This chapter's caching reuses an AI judgment result, like a failure classification, specifically when the exact same input would genuinely produce the same answer — its purpose is avoiding a redundant, real cost, not ensuring reproducibility of test data.

Intermediate: Using this chapter's own audit, explain why classifyFailure from Chapter 9 is described as "borderline" rather than clearly deterministic or clearly requiring AI.▾

It has a fixed, known set of seven possible categories, which might suggest a deterministic lookup — but selecting the genuinely correct category from real, messy evidence requires actual interpretation, not just matching against an exact pattern the way findFailedAction's search for a populated error field does. The categories are fixed, but which one applies to a specific case is a real judgment call, which is why this chapter treats it as AI-appropriate despite the bounded category list — the boundedness alone doesn't make it deterministic.

Intermediate: Why does this chapter argue that the five scale techniques (audit, selection, model matching, caching, quality gates) need to be applied together rather than individually?▾

Each technique addresses a genuinely different source of real inefficiency — the audit removes AI calls that never needed to exist at all, selection reduces which tests run per change, model matching reduces cost per call, caching removes redundant identical calls, and quality gates prevent unnecessary full analysis on known flakiness. Applying only one leaves the inefficiencies the others would have caught completely unaddressed — intelligent selection alone, for instance, still runs Chapter 9's full, expensive analysis pipeline on every genuine failure among the tests it does select, which caching and model matching would otherwise reduce.

Advanced: A team wants to apply this chapter's caching technique to Chapter 13's exploratory hypothesis generation, reasoning it would reduce cost the same way it does for Chapter 9's classification. Why is this a genuine mistake?▾

Caching is appropriate specifically when identical input should genuinely produce identical, reusable output — true for a failure classification, where the same evidence really does point to the same category every time. Chapter 13's exploration deliberately wants genuine variety across runs, generating different hypotheses to explore different, previously-untried paths, even when starting from similar-looking page states. Caching it would mean the exploration keeps returning the same cached hypothesis rather than genuinely exploring something new, directly defeating the entire purpose of open-ended exploration that Chapter 13 built — the technique's mechanical applicability doesn't mean it's the right fit for every call type.

Scenario-based: A teammate suggests switching every AI call in the project to the smallest, fastest available model to cut costs immediately, citing this chapter's model-matching advice. How would you respond?▾

I'd point back to this chapter's actual argument: model matching means fitting capability to task difficulty, not defaulting to the cheapest option everywhere. A blanket switch would genuinely hurt calls this track's own audit identified as needing real reasoning — Chapter 9's root-cause analysis, Chapter 13's hypothesis generation, Chapter 14's objective evaluation — where a less capable model risks producing weaker, less trustworthy output for exactly the tasks where quality matters most. The right approach is auditing call sites individually, the way this chapter's third page did for Chapter 9's own pipeline, and matching each one honestly to its real difficulty — not applying one blanket rule that treats a bounded classification call and an open-ended reasoning call as if they had identical requirements.
