Common Mistakes

  • Treating "the exact value isn't known to me right now" as the same thing as "no single correct value exists." The cart count example shows these are genuinely different — the correct value IS knowable, it just requires calculating it from known inputs, not judging it.
  • Reaching for Role 2 out of habit, once a team has built the infrastructure for it. Having validateContentSemantically available doesn't mean every new assertion should use it — Chapter 7's opening page's methods remain the right default.

Best Practices

  • Run every new assertion through Chapter 7's three criteria before reaching for Role 2, even when it feels intuitively like a judgment call.
  • Default to deterministic assertions; treat every use of Role 2 as something that needed to actively earn its place, not the other way around.

Interview Questions

Beginner: What are the two genuinely different roles AI can play in assertions, according to this chapter?▾

Role 1 is AI helping write deterministic assertion code — once written and reviewed, it behaves exactly like hand-written Playwright code, with no ongoing AI involvement at test-run time. Role 2 is AI making a genuine judgment call at test-run time, for content that has no single correct string to match against — like evaluating whether an error message is genuinely helpful.

Beginner: Why does this chapter insist that Role 1 carries meaningfully less risk than Role 2?▾

In Role 1, the AI's involvement is entirely at authoring time — a human reviews the generated code once, and from then on it runs exactly like any other deterministic Playwright assertion, with no AI call happening during test execution. In Role 2, the AI makes a genuine judgment every single time the test runs, which means every run carries some risk of an incorrect judgment — a risk that simply doesn't exist once Role 1's code has been reviewed and checked in.

Intermediate: Using this chapter's three criteria, explain why "Order Confirmed" being visible is not a genuine Role 2 case.▾

It fails the first criterion immediately: there's no legitimate, alternative correct version of this text — it's a specific, required UI string, not open-ended content where multiple different phrasings could all be correct. Since the first criterion already fails, the check belongs to Role 1 (a deterministic toBeVisible or toHaveText assertion), and there's no need to even evaluate the remaining two criteria.

Intermediate: Why does validateContentSemantically return a structured judgment with reasoning and confidence, rather than a simple true or false?▾

A bare boolean hides exactly the information a human needs to trust or challenge the result. The reasoning field lets a person evaluate whether the model's conclusion is actually sound, rather than accepting it blindly — directly following Chapter 1's warning that confident-sounding AI output isn't automatically correct output. The confidence field adds a further, practical signal: a low-confidence judgment is worth flagging for closer human review, even when it reaches the same conclusion as a high-confidence one.

Advanced: Why is ShopSmart's cart count badge a deterministic check, even though the exact number isn't known in advance when writing the test?▾

Not knowing a value in advance is different from that value genuinely having multiple correct possibilities. Given a known starting cart state and a known action (adding one specific item), the resulting count is fully determined by simple arithmetic — there is exactly one correct answer, it just needs to be calculated from known inputs rather than hardcoded as a literal in the test. This is a deterministic calculation, not a case where legitimate implementations could reasonably differ — the same distinction the transaction ID example draws in the previous page, now applied to a numeric case rather than a text one.

Scenario-based: A team has built out Role 2 validation infrastructure and a teammate suggests using validateContentSemantically for a new assertion "since we already have the tooling built." How would you respond?▾

I'd push back gently, using this chapter's own reasoning: having the infrastructure available doesn't change what a specific assertion actually needs. The right question is still whether this particular piece of content genuinely meets the three criteria from earlier in this chapter — multiple legitimate correct versions, a quality-focused requirement, and tolerable judgment-error cost — not whether the tooling happens to exist already. Using Role 2 "because it's available" repeats the exact mistake this chapter warns against: treating AI as a default rather than something that has to earn its place for each specific check. I'd ask the teammate to walk through the three criteria for this specific assertion before deciding, the same as any other case.
