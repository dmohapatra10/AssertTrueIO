Introduction — The Rule, Traced Across This Track

Chapter 11 stated it: never silently modify the source code and declare the test successful. Chapter 16 confirmed it applies unchanged in CI, arguably more strictly. This page is the dedicated, consolidated treatment — not a new rule, but the real framework for applying the existing one consistently.

How It Works — A Real Decision Framework

Does this ACTION genuinely change something PERSISTENT —
source CODE, production data, a REAL customer-facing system?
  → YES: Chapter 11'S rule applies. Human APPROVAL required,
    REGARDLESS of how confident the AI's OWN judgment is.
  → NO — this is READ-ONLY observation, or a TEMPORARY,
    runtime-only substitution (Chapter 6'S locator healing):
    → Autonomous action is GENUINELY appropriate here.

Example — A Real, Traced Decision for ShopSmart

Chapter 13's exploring agent discovers the discount-code-stacking bug from its own earlier example. Reporting this finding requires no approval — it's a read-only observation. If that finding then flows into Chapter 11's self-healing pipeline to propose an actual code fix, the framework's first branch applies immediately: a draft PR, never an auto-merge, exactly as Chapter 11 and 16 both established.

Common Mistakes

  • Requiring human approval for every single AI action, including read-only observation. This creates unnecessary friction for genuinely safe operations — Chapter 9's classification and Chapter 13's exploration were always meant to run autonomously.
  • Treating high AI confidence as a substitute for human review on a persistent change. Chapter 11's own assertion-healing example is the clearest reason why — a confident-sounding judgment can still be wrong in ways only business context reveals.

Best Practices

  • Apply this page's single, real question — does this change something persistent — to every new autonomous capability before deciding whether it needs a checkpoint.
  • Keep read-only operations genuinely autonomous — reserving human review specifically for the moment something persistent is about to change.

Key Takeaways

  • Chapter 11's rule was never "always require approval" — it was specifically about persistent changes to source code or production systems.
  • This single question — does this change something persistent — cleanly separates every example across this track into "needs approval" and "genuinely autonomous," with no exceptions found.
  • This framework, not a new rule, is this page's real contribution — making an existing, consistent principle explicit and applicable to any new capability.
