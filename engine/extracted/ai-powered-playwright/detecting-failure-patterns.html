Introduction — Another Exact, Deterministic Question

"Does this test show inconsistent outcomes across the same commit" is, once real history exists, an exact, countable question — not a judgment call. This page applies Chapter 5's core rule once more: deterministic code answers this reliably, before any AI reasoning gets involved.

Step-by-Step Implementation

// src/detect-flaky-candidates.ts
import { TestRunRecord } from './collect-test-history';

export interface FlakyCandidate {
  testName: string;
  totalRuns: number;
  failureRate: number;
  sameCommitInconsistency: boolean;
}

const MINIMUM_SAMPLE_SIZE = 10;

export function detectFlakyCandidates(
  history: TestRunRecord[]
): FlakyCandidate[] {
  const byTest = new Map<string, TestRunRecord[]>();
  for (const record of history) {
    const existing = byTest.get(record.testName) ?? [];
    existing.push(record);
    byTest.set(record.testName, existing);
  }

  const candidates: FlakyCandidate[] = [];
  for (const [testName, records] of byTest) {
    if (records.length < MINIMUM_SAMPLE_SIZE) continue;

    const failures = records.filter((r) => r.status === 'failed').length;
    const failureRate = failures / records.length;

    const byCommit = new Map<string, Set<string>>();
    for (const r of records) {
      const outcomes = byCommit.get(r.commitHash) ?? new Set();
      outcomes.add(r.status);
      byCommit.set(r.commitHash, outcomes);
    }
    const sameCommitInconsistency = [...byCommit.values()].some((s) => s.size > 1);

    if (failureRate > 0 && failureRate < 1 && sameCommitInconsistency) {
      candidates.push({ testName, totalRuns: records.length, failureRate, sameCommitInconsistency });
    }
  }
  return candidates;
}

Code Explanation

MINIMUM_SAMPLE_SIZE matters as much as the detection logic itself — a test with only two or three runs recorded doesn't have enough real evidence to distinguish genuine flakiness from ordinary variance. sameCommitInconsistency is the real, decisive check: it specifically looks for the same commit hash producing more than one distinct outcome, exactly the concrete evidence this chapter's previous page identified as unambiguous.

Why It Matters — This Is Where AI Genuinely Isn't Needed Yet

Notice this entire page contains no AI call. Finding which tests show inconsistent outcomes across identical commits is exactly the kind of countable, exact question deterministic code answers completely reliably — the same discipline this tutorial applied to locator mapping in Chapter 5 and failed-action detection in Chapter 10. AI earns its place on this chapter's next page, for a genuinely different, harder question: why.

Common Mistakes

  • Skipping the minimum sample size check. A test with two runs, one pass and one fail, technically shows "inconsistency" — but this is nowhere near enough evidence to trust, and MINIMUM_SAMPLE_SIZE exists specifically to prevent premature conclusions.
  • Reaching for AI to detect the pattern itself. This is an exact, countable question with one correct answer — deterministic code handles it completely and reliably, at zero AI cost.

Best Practices

  • Set a real, deliberate minimum sample size before trusting any flakiness signal — ten runs is a reasonable starting point, adjustable to your own suite's real run frequency.
  • Keep pattern detection itself fully deterministic — reserve AI specifically for the harder, genuinely judgment-requiring questions that follow.
