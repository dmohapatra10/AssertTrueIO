Deterministic Automation vs Probabilistic AI

Prerequisites: AI Models and Model Selection

What You'll Learn

Introduction

Every earlier page in this chapter has been building toward this one distinction. Playwright's own assertions are deterministic — expect(locator).toBeVisible() gives the same answer every time, for the same page state. An LLM's response is probabilistic — genuinely useful, but not guaranteed identical every time, even for the same input. Knowing which kind of check a given step actually needs is the single most important judgment call this tutorial keeps asking you to make.

How It Works — The Concrete Rule

Ask: "Is there ONE, exact, verifiable correct answer here?"

YES — use DETERMINISTIC Playwright code:
  await expect(page.getByRole('heading', {
    name: 'Order Confirmed'
  })).toBeVisible();
  // There's exactly ONE correct answer: is this TEXT visible,
  // yes or no. AI adds NOTHING here except cost and risk.

NO, genuine JUDGMENT is required — AI may genuinely help:
  "Does this error message clearly and helpfully explain
  what the user did wrong?"
  // There's no SINGLE, exact correct string to check for —
  // this genuinely requires judgment about CLARITY and
  // HELPFULNESS, which a fixed assertion can't capture

Example — Applying the Rule to ShopSmart

DETERMINISTIC (Playwright alone is the RIGHT tool):
  - Does the cart total EQUAL $49.98 after adding this item?
  - Does the confirmation PAGE URL contain "/order-confirmed"?
  - Is the "Add to Cart" button DISABLED while out of stock?

GENUINELY NEEDS JUDGMENT (AI may genuinely help):
  - Does this validation error message make SENSE to a real
    user, given what they actually did wrong?
  - Is THIS test failure a real application BUG, or a stale
    locator, or an environment issue? (Chapter 9)
  - Does ShopSmart's checkout flow have any UNEXPECTED,
    undocumented behavior? (Chapter 13)

Why It Matters

Reaching for AI on a genuinely deterministic check doesn't just waste cost and add latency — it introduces real, unnecessary risk of a wrong answer where a plain Playwright assertion would have been completely reliable. Every later chapter that introduces an AI technique — locators in Chapter 6, assertions in Chapter 7, test data in Chapter 8 — is explicit about exactly where this line falls for that specific technique.

Common Mistakes

  • Reaching for AI by default, everywhere, because it's available. This page's rule exists specifically to prevent that — most of a good AI-powered suite is still deterministic Playwright code.
  • Forcing a genuinely judgment-based question into a rigid, exact assertion. "Is this error message helpful" doesn't have one correct string to match against — trying to force it into one produces a brittle, meaningless check.

Best Practices

  • Apply this page's rule explicitly, every time, before writing a new check — not just once, at project setup.
  • Default to deterministic Playwright code; require a genuine reason before reaching for AI reasoning instead.

Key Takeaways

  • Deterministic checks have one exact, verifiable correct answer; probabilistic AI reasoning is for genuine judgment calls without one.
  • This distinction is the single most recurring design decision across this entire tutorial's later chapters.
  • Defaulting to deterministic Playwright code, and requiring a genuine reason before reaching for AI, keeps a test suite reliable and affordable.

Interview Questions

Beginner: What is the practical difference between a system prompt and a user prompt?▾

A system prompt sets standing behavior for an entire session — instructions like "never invent selectors" that should apply to every response. A user prompt is the specific request for the current interaction — "generate a test for adding a product to the cart." Putting standing constraints in the system prompt means you don't have to repeat them in every single user prompt.

Beginner: Why does this chapter insist structured output is important for testing automation specifically?▾

Automation code needs to reliably parse what an AI returns. Free-form prose is not reliably parseable — a slightly different phrasing can break a text parser. Structured output (like JSON with defined fields) gives code something consistent and predictable to loop over and act on, which is exactly what later chapters' generation and agent code depend on.

Intermediate: Explain, with an example, why a vague instruction produces a genuinely worse response than a specific one — not just a differently-styled one.▾

Because of how generation actually works: each token in the response is produced based on everything that came before it, including the original instruction. "Test the login page" gives the model almost no concrete signal to generate from, so it falls back to generic patterns. "Generate negative test scenarios for ShopSmart's login form, covering empty fields, invalid formats, and injection-style input, in a numbered list" gives it concrete constraints to reason within, producing a response that's not just better-formatted but genuinely more useful and specific.

Intermediate: Why might using the most capable available model for every single task in a test suite be a genuine mistake, not just a minor inefficiency?▾

Different tasks have genuinely different requirements. A narrow classification task ("is this a locator issue or an application bug?") doesn't need deep, nuanced reasoning — a smaller, faster model handles it well. Using the most capable model for every task, including narrow ones running potentially hundreds of times across a CI run, means paying real, unnecessary cost and latency repeatedly for capability the task never actually needed.

Advanced: A teammate wants to use an LLM to check "does the cart total equal $49.98." Using this chapter's core distinction, explain why this is a genuine mistake, not just an unnecessary one.▾

This question has exactly one correct, verifiable answer — Playwright's own deterministic assertion (expect(cartTotal).toHaveText('$49.98')) already answers it with complete reliability. Introducing an LLM here doesn't just waste cost and add latency — it introduces genuine risk of an incorrect answer (a hallucinated "yes" or "no") on a question a fixed assertion answers perfectly, every time. The core rule from this chapter's final page — "is there one exact, verifiable correct answer" — says clearly this belongs to deterministic Playwright code, not AI reasoning.

Scenario-based: A stakeholder asks "why not just use AI for everything, since it's available?" How would you respond, using this chapter's own concepts?▾

I'd point to the deterministic-vs-probabilistic distinction directly: most of a real test suite consists of checks with one exact, correct answer — a cart total, a URL, a button's disabled state — where Playwright's own assertions are completely reliable, essentially free, and instantaneous. Using AI there instead would mean paying real cost and latency (covered in Chapter 18) for genuine risk of an incorrect answer, with zero benefit. AI earns its place specifically where genuine judgment is needed — failure classification, exploratory testing, locator healing — which this entire tutorial's later chapters cover deliberately, one technique at a time, rather than applying AI indiscriminately everywhere it's available.
