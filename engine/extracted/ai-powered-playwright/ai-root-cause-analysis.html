Introduction — Category Versus Cause

The previous page's classification tells you what kind of problem occurred. It doesn't tell you why — "Locator Failure" is true whether the accessible name changed, the element moved behind a new modal, or the page simply hasn't finished loading yet. This page is about that deeper, genuinely more useful question.

Step-by-Step Implementation

// src/root-cause-analysis.ts
import { askClaude } from './ai-client';
import { AnalysisPayload } from './select-evidence-for-analysis';
import { Classification } from './classify-failure';

export interface RootCauseAnalysis {
  likelyCause: string;
  supportingEvidence: string;
  alternativeExplanations: string[];
}

export async function analyzeRootCause(
  payload: AnalysisPayload, classification: Classification
): Promise<RootCauseAnalysis> {
  const prompt = `A Playwright test failed and was classified as:
"${classification.category}" — ${classification.reasoning}

Full evidence:
Error: ${payload.errorMessage}
Stack: ${payload.relevantStackFrames}
Console errors: ${JSON.stringify(payload.recentConsoleErrors)}
Network failures: ${JSON.stringify(payload.recentNetworkFailures)}

Explain the LIKELY root cause specifically — not just the
category, the actual WHY. Cite which piece of evidence
supports your explanation. List genuine alternative
explanations you considered and ruled out.

Respond with ONLY valid JSON:
{"likelyCause": string, "supportingEvidence": string,
"alternativeExplanations": [string, ...]}`;

  const raw = await askClaude(prompt);
  return JSON.parse(raw);
}

Code Explanation

alternativeExplanations is deliberately included, not just the winning explanation. This mirrors good human debugging practice — a root cause worth trusting is one where other plausible explanations were genuinely considered and ruled out with a reason, not simply the first plausible story that came to mind.

Why It Matters

This is genuinely more useful than the classification alone — it points directly at what to check first (the heading's current accessible name) rather than just confirming this is "a locator problem," which a human would likely have already suspected from the error message alone. The ruled-out alternatives are equally valuable: they tell a reviewer what's already been considered, so a human's own investigation doesn't waste time re-checking possibilities the analysis already addressed.

Common Mistakes

  • Treating category and root cause as the same output. This page's whole point is that they answer genuinely different questions — what happened versus why.
  • Accepting a root cause with no cited supporting evidence. A plausible-sounding explanation with nothing pointing to why it's plausible is exactly the kind of confident-but-ungrounded output Chapter 1 warned about.

Best Practices

  • Always request supporting evidence alongside a root cause — an unsupported explanation, however plausible, deserves less trust.
  • Review the alternative explanations, not just the winning one — they reveal whether the analysis genuinely considered other possibilities.

Hands-On Exercise

Key Takeaways

  • Category answers "what kind of failure"; root cause answers "why did it actually happen" — genuinely different, both necessary questions.
  • A trustworthy root cause cites specific supporting evidence and names alternatives that were considered and ruled out.
  • This deeper analysis is what actually accelerates a human's investigation, rather than just confirming what the error message already suggested.
