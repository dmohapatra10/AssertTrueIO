Introduction

Chapter 3's generateScenarios function was deliberately narrow — one feature, one scenario shape. This page generalizes it: any requirement, any ShopSmart feature, while keeping every validation discipline Chapter 3 established.

Step-by-Step Implementation

// src/generate-test-cases.ts
import { askClaude } from './ai-client';

export interface TestCase {
  id: string;
  category: string;
  name: string;
  steps: string[];
  expected: string;
}

export async function generateTestCases(
  requirement: string,
  featureContext: string
): Promise<TestCase[]> {
  const prompt = `Requirement: "${requirement}"

Feature context: ${featureContext}

Generate test cases covering this requirement. Respond with
ONLY valid JSON, no other text, in exactly this shape:

{"testCases": [{"id": string, "category": string,
"name": string, "steps": string[], "expected": string}]}

Each test case needs a short, descriptive id (like "search-001"),
a category (like "happy-path" or "negative"), a clear name,
concrete numbered steps, and a specific expected result.`;

  const raw = await askClaude(prompt);
  const parsed = JSON.parse(raw);

  if (!Array.isArray(parsed.testCases)) {
    throw new Error(
      `Expected {"testCases": [...]} but got: ${raw.slice(0, 200)}`
    );
  }
  return parsed.testCases;
}

Code Explanation

Two genuine generalizations from Chapter 3's version matter here. First, featureContext is now a parameter, not hardcoded — the function works for product search exactly as well as login, because the feature-specific knowledge lives outside the function, not baked into it. Second, TestCase is a genuinely richer shape than Chapter 3's login-only TestScenario — it carries a category (used heavily starting on this chapter's next page) and concrete steps, not just input values.

Example — Applying It to Product Search

const searchContext = `ShopSmart's product search: a search box
in the header, searching by product name or category. Results
show in a grid below. An empty search shows all products. A
search with no matches shows "No products found."`;

const cases = await generateTestCases(
  'Test ShopSmart\\'s product search functionality',
  searchContext
);

// Real output includes cases LIKE:
// { id: "search-001", category: "happy-path",
//   name: "Search returns matching products",
//   steps: ["Enter 'laptop' in search box", "Press Enter"],
//   expected: "Grid shows products with 'laptop' in the name" }

Why It Matters — The Requirement's Shape

A vague requirement ("test search") produces vague test cases, exactly Chapter 2's specificity lesson applied concretely here. featureContext is what turns a one-line requirement into genuinely useful test cases — without it, the model has no real, specific knowledge of how ShopSmart's search actually behaves, and falls back to generic search-testing patterns that may not match ShopSmart at all.

Common Mistakes

  • Reusing Chapter 3's hardcoded login prompt for a different feature. This page's whole point is generalizing past that — a copy-pasted, feature-specific prompt doesn't scale to a real application with dozens of features.
  • Skipping featureContext to save a few lines. The resulting test cases will be generic and often genuinely wrong for ShopSmart's actual behavior.

Best Practices

  • Write featureContext with the same care you'd put into explaining a feature to a new team member — concrete, specific, and honest about real edge behavior.
  • Keep the TestCase shape consistent across every feature you generate for — it's what makes later chapters' cross-feature tooling possible.

Key Takeaways

  • Generalizing Chapter 3's function means moving feature-specific knowledge into a parameter, not hardcoding it — the same function now serves every ShopSmart feature.
  • A requirement's real specificity — carried by featureContext — determines whether generated test cases are genuinely useful or genuinely generic.
  • This page's richer TestCase shape, with its category field, is what the rest of this chapter builds directly on.
