Introduction

The previous stage's exploration surfaced something real, but discovery alone doesn't confirm it's a genuine defect worth this capstone's remaining stages. This page runs it through the same real checks this track built for exactly this judgment.

Step-by-Step Implementation

// src/capstone-pipeline.ts (stage 3)
import { selectEvidenceForAnalysis } from './select-evidence-for-analysis';
import { classifyFailure } from './classify-failure';
import { detectFlakyCandidates } from './detect-flaky-candidates';

export async function evaluateCapstoneResults(
  evidence: EvidenceBundle, history: TestRunRecord[]
) {
  const payload = selectEvidenceForAnalysis(evidence);

  // Chapter 12'S OWN check, FIRST — is this ALREADY a KNOWN,
  // flaky pattern, not a genuinely NEW finding at all?
  const flakyCandidates = detectFlakyCandidates(history);
  const isKnownFlaky = flakyCandidates.some(
    (c) => c.testName === 'discount code application'
  );
  if (isKnownFlaky) {
    return { genuineFailure: false, reason: 'Matches known flaky pattern' };
  }

  const classification = await classifyFailure(payload);
  const genuineFailure = ['Application Defect', 'Test Defect'].includes(
    classification.category
  );

  return { genuineFailure, classification };
}

Code Explanation

The flaky check runs first, deliberately, the same discipline Chapter 16's own quality gate established — no reason to spend a fresh classification call investigating something already known and understood. Only once the flaky check comes back clean does this stage reach for Chapter 9's own classification.

Why It Matters — This Confirmation Is What Justifies Continuing

Without this stage, this capstone would be pursuing every exploration finding equally, regardless of whether it's a genuine defect, a known flaky pattern, or a real but low-severity cosmetic issue. This confirmation — a real "Application Defect" classification, backed by concrete evidence — is exactly what justifies committing to this capstone's remaining, more expensive stages: root cause analysis and a real fix proposal.

Common Mistakes

  • Skipping the flaky check and classifying every exploration finding fresh. This wastes real cost on findings that already have a known, understood explanation.
  • Proceeding to root cause analysis without confirming genuine failure first. Not every unexpected observation is actually a defect — this stage's classification step exists specifically to make that distinction before committing further resources.

Best Practices

  • Check known flaky patterns before running a fresh classification, the same order Chapter 16's quality gate established.
  • Only commit to a pipeline's more expensive, later stages once a finding is confirmed as a genuine failure — not on discovery alone.
