Regression Validation

Prerequisites: Validating the Candidate Fix

What You'll Learn

  • Why a fix that passes its own test can still break other, related tests
  • Identifying which other tests are genuinely at risk from a given change
  • Running exactly those tests against the patched file

Introduction

The previous page proved the originally-failing test now passes. This page asks the real, separate question that still matters: could this same change break something else in the suite that was working fine before?

Why It Matters — A Concrete Risk

ShopSmart's "Add to Cart" LOCATOR gets healed from a ROLE-based
selector to a testId-based ONE. The originally-FAILING test now
PASSES. But THREE other tests in the suite ALSO reference this
SAME button, using the SAME original locator STRING — changing
IT in one place, without checking the OTHERS, could leave THEM
now pointing at something SUBTLY different, or break them if
they RELIED on some detail SPECIFIC to the old selector.

Step-by-Step Implementation — Finding Affected Tests

// src/find-affected-tests.ts
import { readFileSync, readdirSync } from 'fs';
import { CandidatePatch } from './build-candidate-diff';

export function findAffectedTests(
  patch: CandidatePatch, testsDir: string
): string[] {
  const affected: string[] = [];
  const testFiles = readdirSync(testsDir).filter((f) => f.endsWith('.spec.ts'));

  for (const file of testFiles) {
    const content = readFileSync(`${testsDir}/${file}`, 'utf-8');
    const referencesChangedCode = patch.changes.some(
      (change) => content.includes(change.before.trim())
    );
    if (referencesChangedCode) affected.push(`${testsDir}/${file}`);
  }

  return affected;
}

Step-by-Step Implementation — Running Just Those Tests

// src/run-regression-check.ts
import { execSync } from 'child_process';

export interface RegressionResult {
  testFile: string;
  passed: boolean;
}

export function runRegressionCheck(affectedTests: string[]): RegressionResult[] {
  return affectedTests.map((testFile) => {
    try {
      execSync(`npx playwright test ${testFile}`, { encoding: 'utf-8' });
      return { testFile, passed: true };
    } catch {
      return { testFile, passed: false };
    }
  });
}

Code Explanation

findAffectedTests deliberately searches for the exact, original locator string across every test file — not just the one that originally failed. This is a real, if imperfect, way to identify genuine risk: any test referencing the same broken code is a test worth re-checking before trusting this fix, even if it wasn't the one that surfaced the original failure.

Example — A Real Regression Check

const affected = findAffectedTests(patch, 'tests/');
// ["tests/cart.spec.ts", "tests/checkout.spec.ts", "tests/wishlist.spec.ts"]

const results = runRegressionCheck(affected);
// [
//   { testFile: "tests/cart.spec.ts", passed: true },
//   { testFile: "tests/checkout.spec.ts", passed: true },
//   { testFile: "tests/wishlist.spec.ts", passed: false }
// ]

// A REAL, genuine finding: this "safe-looking" locator fix
// would BREAK wishlist.spec.ts — caught HERE, before it EVER
// reaches a human REVIEWER, let alone a merged FILE

Why It Matters

Without this page, a fix that looks completely safe — the originally-failing test passes, the diff looks reasonable — could still silently break another test the moment it's merged. This is exactly the kind of real, structural risk a human reviewer glancing at a diff alone might miss, since they'd need to independently know every other place the changed code is referenced.

Common Mistakes

  • Only running the originally-failing test and calling the fix validated. The previous page's validation and this page's regression check answer genuinely different questions — both are necessary.
  • Searching for affected tests only in the immediate test file, not the whole suite. The same broken locator string can appear anywhere across the codebase — this page's search deliberately covers the entire tests directory.

Best Practices

  • Always run a full regression check across every affected test before considering a fix ready for human review.
  • Treat a regression failure as a genuine signal the fix needs rework — never as something to route around or exclude from the check.

Hands-On Exercise

Run findAffectedTests against a candidate patch from this chapter's earlier exercises, across your own project's full test directory. If any affected tests are found, run runRegressionCheck and review the results honestly before considering the fix ready to move forward.

Key Takeaways

  • A fix that passes its own originally-failing test can still break other, unrelated-seeming tests that share the same underlying code.
  • Searching the whole suite for references to the changed code, not just the immediate file, is what surfaces genuine regression risk.
  • This regression check and the previous page's validation are two separate, both-necessary questions — neither one substitutes for the other.
