Step-by-Step Implementation

// src/testcase-to-playwright.ts
import { askClaude } from './ai-client';
import { TestCase } from './generate-test-cases';
import { checkSyntax, checkLocatorsExist } from './validate-test';
import { writeFileSync } from 'fs';

export async function testCaseToPlaywrightCode(
  testCase: TestCase, pageStructure: string
): Promise<string> {
  const prompt = `Generate a single Playwright test in
TypeScript for this test case:
${JSON.stringify(testCase)}

Use ONLY these real, known locators — never invent a selector:
${pageStructure}

Respond with ONLY the TypeScript code, no explanation, no
markdown fences. Import { test, expect } from '@playwright/test'.
Use the test case's "steps" to determine the actions, and its
"expected" to determine the assertion.`;

  return askClaude(prompt);
}

export async function convertAndValidate(
  testCase: TestCase, pageStructure: string,
  filePath: string, pageUrl: string
): Promise<{ success: boolean; reason?: string }> {
  const code = await testCaseToPlaywrightCode(testCase, pageStructure);
  writeFileSync(filePath, code, 'utf-8');

  const syntax = checkSyntax(filePath);
  if (!syntax.valid) {
    return { success: false, reason: `Syntax: ${syntax.error}` };
  }
  const locators = await checkLocatorsExist(filePath, pageUrl);
  if (locators.missing.length > 0) {
    return { success: false, reason: `Missing locators: ${locators.missing.join(', ')}` };
  }
  return { success: true };
}

Code Explanation

Notice this page adds no new validation logic at all — checkSyntax and checkLocatorsExist are the exact same functions Chapter 3 built. This is deliberate: validation shouldn't depend on which category of test case produced the code. A boundary case and a happy-path case get identically rigorous validation, because the risk of a hallucinated locator doesn't depend on which category generated it.

Example — This Chapter's Full Pipeline, End to End

async function runFullPipeline() {
  const cases = await generateTestCases(
    'Test ShopSmart\\'s cart quantity field', cartContext
  );
  const boundaryCases = await generateBoundaryCases(
    'quantity', '1 to 99', cartContext
  );
  const allCases = [...cases, ...boundaryCases];

  const ranked = await prioritizeByRisk(allCases, cartBusinessContext);
  const topFive = ranked.slice(0, 5);

  for (const tc of topFive) {
    const result = await convertAndValidate(
      tc, cartPageStructure,
      `tests/generated/${tc.id}.spec.ts`,
      'https://shopsmart.example.com/cart'
    );
    console.log(`${tc.id}: ${result.success ? 'validated' : result.reason}`);
  }
}

Common Mistakes

  • Writing separate validation logic per category. This page's whole point is that Chapter 3's validation applies identically, regardless of category — duplicating it adds risk of inconsistency for no real benefit.
  • Converting every generated case to code before prioritizing. Running prioritizeByRisk first, then converting only the top-ranked subset, avoids real, wasted cost generating code for cases that won't be executed.

Best Practices

  • Convert and validate only after prioritizing — code generation has a real cost, covered fully in Chapter 18, and shouldn't be spent on cases you won't run.
  • Keep this chapter's pipeline in this order: generate broadly, prioritize, convert the top subset, validate every single one before execution.

Interview Questions

Beginner: What is the genuine difference between a negative test case and a boundary test case?▾

A negative test case uses clearly invalid input and expects the feature to fail safely — a wrong password, an empty required field. A boundary test case uses genuinely valid input, positioned at the exact edge of an allowed range — the minimum or maximum permitted value — and typically expects the feature to succeed, not fail. Confusing the two leads to writing the wrong expected result for a boundary case.

Beginner: Why does this chapter insist on requesting happy-path and negative cases together, explicitly, in one prompt?▾

A general, unstructured request like "generate test cases" tends to produce mostly happy-path scenarios — the model gravitates toward the expected flow first, the same way a human tester relying on intuition alone often does. Explicitly requesting both categories, with minimum counts for each, produces meaningfully more balanced coverage than trusting an unstructured request to balance itself.

Intermediate: Explain why security-oriented test generation in this chapter is framed around "confirming safe handling" rather than "trying to break" a field.▾

The framing genuinely shapes what gets generated. A prompt asking the model to "find a way to break" a field steers generation toward crafting something designed to succeed at causing harm. A prompt asking it to "confirm the application handles this input safely" steers generation toward scenarios that verify correct escaping, storage, and display — exactly what a QA engineer needs, and squarely within ordinary, everyday testing practice rather than specialized attack tooling.

Intermediate: Why does prioritizeByRisk use a `?? 1` fallback for a test case's risk score, rather than assuming every case will always receive one?▾

An AI-generated response can genuinely omit an entry for some input, even with a clear prompt — this is a real, ordinary failure mode, not a hypothetical edge case. Without a fallback, a missing score would either crash the function or silently make that test case vanish from the prioritized list. Defaulting to the lowest risk score means the case is still included, just deprioritized, which is a safer failure mode than losing it entirely — the same defensive validation discipline Chapter 3 established for any AI response the code depends on.

Advanced: Why does this chapter's full pipeline prioritize by risk BEFORE converting to Playwright code, rather than converting every generated test case first and prioritizing which ones to run afterward?▾

Converting a test case to Playwright code is itself a real, costly step — it's a separate AI call with its own latency and token cost, covered fully in Chapter 18. If conversion happened before prioritization, that cost would be paid for every single generated case, including the many low-priority ones that were never going to be executed anyway. Prioritizing first, then converting only the top-ranked subset, means that real cost is spent exclusively on test cases that will actually run — the same cost-awareness principle Chapter 2 introduced when discussing token cost, applied here to a concrete, multi-step pipeline decision rather than a single prompt.

Scenario-based: A teammate wants to add category-specific validation logic — a stricter check for security-oriented generated tests than for happy-path ones. How would you respond, using this chapter's own reasoning?▾

I'd point to this page's own reasoning directly: the risk of a hallucinated or incorrect locator doesn't depend on which category generated the code — a happy-path test and a security-oriented test are both real Playwright code that either references a genuine element on the page or doesn't. Chapter 3's syntax and locator-existence checks already apply identically and rigorously to every generated file, regardless of source. Adding category-specific validation logic would introduce inconsistency and additional maintenance burden without addressing a genuine difference in risk — if anything, it would be worth asking whether the EXISTING validation is already sufficient for every category, which this chapter's own design suggests it is.
