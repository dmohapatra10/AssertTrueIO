Introduction

A trace file is a real, structured record of an entire test run — not a single moment, captured once, the way a failure screenshot is. This page is about understanding that difference honestly before building anything on top of it.

How It Works — What's Actually Inside a trace.zip

trace.zip (a REAL zip archive)
├── trace.trace     — a JSONL file: ONE JSON action per line,
│                      EVERY step Playwright took, in ORDER,
│                      with timestamps and DURATION
├── trace.network    — a JSONL file: EVERY network REQUEST
│                       and response DURING the test run
└── resources/         — DOM SNAPSHOTS and screenshots at
                          MULTIPLE points, not just ONE

Why It Matters — A Timeline, Not a Moment

A SCREENSHOT (Chapter 9): ONE image, at the MOMENT of failure
  → shows WHAT the page looked like WHEN it broke

A TRACE: the ENTIRE sequence LEADING UP to that moment
  → shows navigate → click → fill → click → [FAILURE], with
    a REAL timestamp and DURATION for EVERY single step

This is the DIFFERENCE between a PHOTOGRAPH and a VIDEO with
a TRANSCRIPT — the photograph shows the OUTCOME; the trace
shows the ENTIRE, real STORY leading there.

Example — Opening a Trace Manually First

# Playwright's OWN trace viewer — worth using BY hand at least
# once before this chapter automates ANY of it
npx playwright show-trace test-results/checkout-failure-trace.zip

# This OPENS a real, interactive timeline — click ANY action
# to see the EXACT DOM snapshot and network state AT that
# precise MOMENT, not just at the FINAL failure

Why This Manual Step Is Worth Doing

Before writing any code to extract and analyze trace data programmatically, spend real time in Playwright's own viewer. Seeing, by hand, how a full action timeline reveals things a screenshot alone never could — an earlier step that silently took much longer than expected, a network request that quietly failed three actions before the visible error — is what makes the rest of this chapter's automation feel genuinely motivated, not just technically interesting.

Common Mistakes

  • Jumping straight to programmatic extraction without ever opening a trace manually. The manual step builds real intuition for what's actually valuable in a trace, which shapes every later page's extraction choices.
  • Treating a trace as just "a screenshot with extra steps." The genuine difference is the full timeline — every action's timing and sequence, not just visual state at one instant.

Best Practices

  • Open a real trace in Playwright's own viewer before building any automation on top of it — this page's exercise isn't optional busywork.
  • Keep the timeline-versus-moment distinction in mind throughout this chapter — it's what every later page's techniques are actually exploiting.

Hands-On Exercise

Run a real test of yours with tracing enabled, let it fail deliberately, and open the resulting trace with npx playwright show-trace. Click through several actions in the timeline and note one thing the trace reveals that the failure screenshot alone wouldn't have shown you.

Key Takeaways

  • A trace file contains a full, ordered timeline of every action, every network request, and DOM snapshots at multiple points — genuinely more than a single screenshot.
  • This timeline-versus-moment distinction is what makes trace analysis worth the extra investment this chapter builds toward.
  • Manually exploring a real trace first is what makes the rest of this chapter's automation feel genuinely motivated, not just a technical exercise.
