Introduction

Chapter 5's planning assumed a known sequence; Chapter 13's assumed genuine open-endedness. This chapter's agent needs to handle both, since a real objective can start with known structure and drift into open-ended territory the moment something unexpected appears — exactly as this chapter's opening page's checkout-with-discount-field example showed.

Step-by-Step Implementation — The Unified Planner

// src/agent-planner.ts
import { getNextToolCall } from './call-with-tools';
import { AgentState } from './agent-state';

const AGENT_SYSTEM_PROMPT = `You are a QA agent testing
ShopSmart. You have tools to navigate, click, and fill fields.
Plan your next action based on the objective and everything
you've already tried. If you notice something worth
investigating beyond the literal objective, you may explore
it — but stay focused on genuinely relevant findings. Call
report_objective_complete only when you're genuinely confident
the objective has been achieved.`;

export async function planNextStep(state: AgentState) {
  return getNextToolCall(AGENT_SYSTEM_PROMPT, state.conversationHistory);
}

Code Explanation

Notice this function is genuinely simple — it doesn't separately implement Chapter 5's logic and Chapter 13's logic as two different code paths. Instead, the system prompt itself tells the model it may plan a known step OR explore something unexpected, and the model's own reasoning, given the full conversation history, decides which applies at each moment. This is a real, deliberate simplification: rather than the code deciding "are we in planning mode or exploration mode," the model reasons about it directly, informed by everything in state.conversationHistory.

Step-by-Step Implementation — Execution, Reusing Chapter 5 Directly

// src/agent-execute.ts
import { Page } from '@playwright/test';
import { SHOPSMART_LOCATORS } from './map-to-playwright';

export async function executeAgentTool(
  toolName: string, toolInput: any, page: Page
): Promise<string> {
  switch (toolName) {
    case 'navigate':
      await page.goto(toolInput.url);
      return `Navigated to ${toolInput.url}`;
    case 'click_element':
      await page.getByRole(toolInput.role, { name: toolInput.name }).click();
      return `Clicked ${toolInput.role} "${toolInput.name}"`;
    case 'fill_field':
      await page.getByLabel(toolInput.label).fill(toolInput.value);
      return `Filled "${toolInput.label}"`;
    default:
      throw new Error(`Unrecognized tool: ${toolName}`);
  }
}

Why It Matters — This Is Almost Entirely Chapter 5 and 6's Own Logic

Compare executeAgentTool against Chapter 5's executeAction — they're doing the same real work, mapping a structured intent to a real Playwright call. The genuine difference is the input's origin: a real tool call from Anthropic's API, rather than a manually-parsed JSON object. This confirms Chapter 14's opening claim directly — execution didn't need to change; only how the model's choice reaches this function did.

Common Mistakes

  • Writing separate planning code paths for "known sequence" versus "exploration." This page's whole point is that one system prompt, combined with the full conversation history, lets the model itself decide which mode applies — no separate code branches needed.
  • Rewriting execution logic instead of reusing Chapter 5's mapping. The mapping from structured intent to Playwright call hasn't genuinely changed — only the source of that structured intent has.

Best Practices

  • Let the system prompt, not separate code paths, carry the responsibility for choosing between known-sequence planning and open-ended exploration.
  • Reuse execution logic from earlier chapters unchanged wherever the underlying mapping (intent to Playwright call) hasn't genuinely changed.

Key Takeaways

  • Unifying known-sequence planning and open-ended exploration doesn't require separate code paths — a well-written system prompt, combined with full conversation history, lets the model reason about which applies.
  • Execution logic barely changes from Chapter 5 — the same mapping from structured intent to Playwright call, now fed by a real tool call instead of parsed JSON.
  • This confirms the pattern this entire chapter has followed: assembly and a small amount of genuinely new glue code, not wholesale rewriting.
