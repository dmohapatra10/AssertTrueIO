Prerequisites: What is Playwright Trace, and Why It Matters

Introduction

Chapter 9 configured trace: 'retain-on-failure' as part of comprehensive evidence capture. This page goes deeper into the real options and tradeoffs specific to trace capture, which are genuinely more nuanced than a single setting.

How It Works — The Real Configuration Options

// playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  use: {
    trace: {
      mode: 'on-first-retry',
      // 'on-first-retry' — ONLY capture when a test is being
      //   RETRIED after an initial FAILURE — genuinely cheaper,
      //   since MOST tests never fail at all
      // 'retain-on-failure' — capture EVERY run, keep ONLY the
      //   failed ones — MORE storage during the run ITSELF,
      //   but works even WITHOUT retries configured
      // 'on' — capture EVERYTHING, always — GENUINELY expensive,
      //   rarely the right DEFAULT for a full suite

      screenshots: true,
      snapshots: true,
      sources: true,
      // 'sources: true' — includes the TEST'S OWN source code
      // in the trace, letting the VIEWER show WHICH line of
      // YOUR test was executing at each STEP
    },
  },
});

Why It Matters — The Real Tradeoff

on-first-retry genuinely costs less overall, since most test runs across a real suite pass cleanly and never need a trace at all — capture only kicks in once a test has already failed once and is being retried. retain-on-failure captures during every single run, discarding the data afterward for passing tests, which costs more in-run overhead but doesn't depend on retries being configured at all. Neither is universally correct; it's a genuine choice based on your suite's real retry configuration and performance sensitivity.

Example — ShopSmart's Real Configuration Choice

// ShopSmart's suite runs 400+ tests per CI run and RETRIES
// failed tests once automatically — on-first-retry is the
// GENUINELY better fit: cheap during the COMMON case (tests
// passing), and traces are STILL captured for anything that
// GENUINELY fails and gets retried
export default defineConfig({
  retries: 1,
  use: { trace: { mode: 'on-first-retry', screenshots: true, snapshots: true, sources: true } },
});

Common Mistakes

  • Using trace: 'on' for a full suite "to be safe." This genuinely slows down every single run and consumes real storage for hundreds of traces that will never be looked at, since most tests pass.
  • Setting sources: false without realizing it. Without it, the trace viewer can't show which line of your own test code was running at each step — a real, useful piece of context lost for a small storage saving.

Best Practices

  • Match your trace mode to your suite's real retry configuration — on-first-retry when retries are enabled, retain-on-failure when they're not.
  • Keep sources: true unless storage is a genuinely tight constraint — the ability to see your own test's source alongside the timeline is worth the small cost.

Hands-On Exercise

Check your own project's current trace configuration. If it's set to 'on' or unconfigured entirely, calculate roughly how much storage a full CI run is genuinely consuming, and consider whether on-first-retry or retain-on-failure would be a better real fit given your suite's retry settings.

Key Takeaways

  • Trace capture mode is a genuine, real tradeoff between storage cost and reliability of capture — not a single obviously-correct setting.
  • on-first-retry is often the better default specifically because most tests in a real suite pass and never need a trace at all.
  • sources: true is a small cost for a genuinely useful capability — seeing your own test code alongside the trace timeline.
