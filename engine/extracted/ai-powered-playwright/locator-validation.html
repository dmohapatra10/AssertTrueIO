Locator Validation

Prerequisites: Locator Candidate Ranking

What You'll Learn

  • Why even the top-ranked candidate needs real, empirical validation before use
  • Checking existence and uniqueness — two genuinely different failure modes
  • Falling back to the next-ranked candidate when validation fails

Introduction

The previous page's ranking is a real, principled choice — and it's still a prediction based on strategy type, not a guarantee the top candidate actually works on the real page. This page adds the genuine, empirical check: does it actually exist, and does it match exactly one element, not several.

Step-by-Step Implementation

// src/validate-locator-candidate.ts
import { Page } from '@playwright/test';
import { RankedCandidate } from './rank-locator-candidates';

export interface CandidateValidation {
  candidate: RankedCandidate;
  exists: boolean;
  isUnique: boolean;
  valid: boolean;
}

async function resolveLocatorCode(code: string, page: Page) {
  // A SMALL, deliberately scoped interpreter — NOT a general
  // eval of arbitrary code, which would be a genuine security
  // risk. Only the patterns THIS chapter's generation produces.
  const roleMatch = code.match(/getByRole\('(\w+)', \{ name: '([^']+)' \}\)/);
  if (roleMatch) return page.getByRole(roleMatch[1] as any, { name: roleMatch[2] });

  const testIdMatch = code.match(/getByTestId\('([^']+)'\)/);
  if (testIdMatch) return page.getByTestId(testIdMatch[1]);

  const textMatch = code.match(/getByText\('([^']+)'\)/);
  if (textMatch) return page.getByText(textMatch[1]);

  throw new Error(`Unrecognized locator pattern: ${code}`);
}

export async function validateCandidate(
  candidate: RankedCandidate, page: Page
): Promise<CandidateValidation> {
  const locator = await resolveLocatorCode(candidate.locatorCode, page);
  const count = await locator.count();

  return {
    candidate,
    exists: count > 0,
    isUnique: count === 1,
    valid: count === 1,
  };
}

export async function findFirstValidCandidate(
  ranked: RankedCandidate[], page: Page
): Promise<CandidateValidation | null> {
  for (const candidate of ranked) {
    const result = await validateCandidate(candidate, page);
    if (result.valid) return result;
  }
  return null;
}

Code Explanation

Two genuinely different checks matter here, not one combined pass/fail. exists catches a candidate that matches nothing at all — a hallucinated element or a stale one. isUnique catches something equally real but different: a locator matching several elements, which would click or fill the wrong one unpredictably. Both failure modes are real, and conflating them into one boolean would hide which specific problem occurred.

Example — Validating the Top-Ranked Candidate, With Fallback

const result = await findFirstValidCandidate(ranked, page);

if (result) {
  console.log(`Valid candidate found: ${result.candidate.locatorCode}`);
  // If the testId-based candidate DOESN'T actually exist —
  // maybe the developer never added that attribute yet — this
  // function automatically FALLS BACK to the role-based one,
  // rather than failing on the first, merely HIGHEST-ranked
  // candidate
} else {
  console.error('No valid candidate found among any ranked options.');
}

Why It Matters

Ranking predicts what's LIKELY to be most stable; validation confirms what's ACTUALLY, currently true on the real page. These are genuinely different questions, and this page's fallback logic is what makes the pipeline resilient to the top-ranked prediction occasionally being wrong — exactly the kind of gap between confident-sounding and correct that Chapter 1 warned about, closed here with a real, empirical check rather than trust.

Common Mistakes

  • Accepting the top-ranked candidate without checking it exists on the real page. Ranking is a prediction, not a guarantee — this page's whole point is closing that gap with a genuine check.
  • Treating a locator matching multiple elements as acceptable. isUnique exists because this failure mode is just as real and just as likely to cause a wrong click as a missing element.

Best Practices

  • Always fall back through ranked candidates in order, rather than stopping at the first one and failing outright if it doesn't validate.
  • Keep the small, pattern-based resolveLocatorCode scoped deliberately — never use a general code-evaluation approach for AI-generated strings, a genuine security risk this page's comment calls out directly.

Key Takeaways

  • Ranking predicts likely stability; validation confirms real, current correctness — both are genuinely necessary, and neither substitutes for the other.
  • Existence and uniqueness are two distinct, real failure modes that deserve separate checks, not one combined pass/fail.
  • Falling back through ranked candidates in order is what makes this pipeline resilient when the top prediction doesn't hold up empirically.
