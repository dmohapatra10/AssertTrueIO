Locator Candidate Ranking

What You'll Learn

Introduction

The previous page produced three genuine candidates. This page decides which one is genuinely best — and does it with a deterministic scoring function, directly applying Chapter 5's own lesson that a decision with one correct answer per clear criteria doesn't need another AI call.

Step-by-Step Implementation

// src/rank-locator-candidates.ts
import { LocatorCandidate } from './generate-locator-candidates';

export interface RankedCandidate extends LocatorCandidate {
  stabilityScore: number;
  totalScore: number;
}

const STRATEGY_STABILITY: Record<string, number> = {
  'testId-based': 4,
  'role-based': 3,
  'label-based': 3,
  'text-based': 1,
};

export function rankLocatorCandidates(
  candidates: LocatorCandidate[]
): RankedCandidate[] {
  return candidates
    .map((c) => {
      const stabilityScore = STRATEGY_STABILITY[c.strategy] ?? 1;
      // Uniqueness and maintainability both correlate directly
      // with strategy STABILITY here — a testId is inherently
      // both more unique AND easier to maintain than free text
      const totalScore = stabilityScore;
      return { ...c, stabilityScore, totalScore };
    })
    .sort((a, b) => b.totalScore - a.totalScore);
}

Code Explanation

STRATEGY_STABILITY directly encodes Chapter 6's opening page's stability ranking — testId highest, text-based lowest — as real, deterministic data, not a judgment made fresh each time. This is exactly the kind of decision Chapter 2's core rule says belongs to code: given a known strategy name, there's one genuinely correct relative ranking, decided once and reused, not reasoned about per call.

Example — Ranking the Previous Page's Three Candidates

const ranked = rankLocatorCandidates([

Why It Matters

This ranking is completely reproducible — the same three candidates always produce the same order, every single time, regardless of which day it runs or which model version generated them. That reliability matters: a healing pipeline whose candidate selection varies unpredictably between runs would be genuinely hard to trust or debug.

Common Mistakes

  • Asking AI to rank the candidates it just generated. Given the same, clear stability criteria every time, ranking is an exact operation — reaching for AI here adds cost and unpredictability for no genuine benefit, the same lesson from Chapter 5's mapping page.
  • Using an arbitrary or undocumented scoring scale. STRATEGY_STABILITY is deliberately simple and readable — a scoring system nobody can explain is hard to trust or adjust later.

Best Practices

  • Keep ranking criteria deterministic and code-based whenever the underlying decision has one genuinely correct answer given clear inputs.
  • Document the reasoning behind a scoring table directly in the code, the way this page's comment explains why uniqueness and maintainability track stability here.
