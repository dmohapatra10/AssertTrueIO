Handling Ambiguous Instructions

Prerequisites: Browser Interaction

What You'll Learn

  • Why "select a product" is genuinely ambiguous, not just informally worded
  • Making an honest, disclosed choice rather than a silent, hidden one
  • Recording the reasoning behind an ambiguous choice for later review

Introduction

The previous page's observation returned three real products for "Laptop." The instruction says "select a product" — singular, with no criteria given. This page is about handling that honestly: making a reasonable choice, and making it visible, rather than either failing or silently picking one with no record of why.

Step-by-Step Implementation

// src/resolve-ambiguity.ts
import { askClaude } from './ai-client';
import { PageObservation } from './observe-page';

export interface ResolvedChoice {
  chosenValue: string;
  reasoning: string;
  wasAmbiguous: boolean;
}

export async function resolveAmbiguousStep(
  stepDescription: string, observation: PageObservation
): Promise<ResolvedChoice> {
  const prompt = `Step: "${stepDescription}"
Real options currently visible: ${JSON.stringify(observation.visibleProductNames)}

This step doesn't specify WHICH option to choose. Make a
reasonable choice (the FIRST result is a reasonable default
for an ambiguous "select a product" instruction) and explain
your reasoning honestly in one sentence.

Respond with ONLY valid JSON:
{"chosenValue": string, "reasoning": string}`;

  const raw = await askClaude(prompt);
  const parsed = JSON.parse(raw);
  if (!observation.visibleProductNames.includes(parsed.chosenValue)) {
    throw new Error(
      `Chosen value "${parsed.chosenValue}" wasn't among the ` +
      `real, observed options — refusing to proceed.`
    );
  }
  return {
    chosenValue: parsed.chosenValue,
    reasoning: parsed.reasoning,
    wasAmbiguous: true,
  };
}

Code Explanation

Two things matter beyond the happy path. First, the choice is checked against observation.visibleProductNames — the real, previously-observed list — before being trusted, the same "never invent, always verify against reality" discipline this tutorial has used since Chapter 3. Second, reasoning is captured and returned, not discarded — this is what turns a hidden guess into an honest, auditable decision.

Example — Resolving ShopSmart's Product Selection

Why It Matters

Imagine this test fails a week later because ShopSmart's search now returns results in a different order. With reasoning recorded and logged, whoever investigates immediately sees that "select a product" was always resolved as "pick the first result" — a genuine, useful clue, not a mystery. Without it, this same failure would look like ShopSmart itself broke, when the real cause is that an ambiguous instruction resolved differently.

Common Mistakes

  • Picking an option silently, with no recorded reasoning. This turns a reasonable, defensible choice into an invisible one — exactly the kind of thing that makes a later failure genuinely confusing to investigate.
  • Treating every ambiguous instruction the same way, always picking "the first result." This page's default is reasonable for product selection specifically — a different ambiguous step might warrant a genuinely different, explicit default.

Best Practices

  • Always verify a resolved, ambiguous choice against the real, observed options before proceeding — never trust it blindly.
  • Log reasoning somewhere genuinely visible — Chapter 15's observability chapter covers exactly why this kind of record matters at scale.

Hands-On Exercise

Identify a genuinely ambiguous instruction from your own testing work — something with no explicit selection criteria. Write a resolution function following this page's pattern, and decide, deliberately, what a reasonable default choice should be and why.

Key Takeaways

  • An ambiguous instruction needs a real, honest choice — not a failure, and not a silent, unrecorded guess.
  • Verifying a resolved choice against real, observed options before proceeding is the same discipline this tutorial has applied to every AI output since Chapter 3.
  • Recording the reasoning behind an ambiguous choice turns a later failure into something investigable, rather than a genuine mystery.
