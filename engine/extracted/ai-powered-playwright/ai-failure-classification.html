Introduction

The previous page's selected evidence is genuinely useful for a human — this page turns it into something a whole team, or a CI pipeline, can act on automatically: a specific, structured classification.

How It Works — Seven Genuinely Distinct Categories

Application Defect  — ShopSmart itself is genuinely broken
Test Defect         — the TEST'S logic is wrong, not the app
Locator Failure      — a SELECTOR no longer matches (Chapter 6)
Timeout               — something took LONGER than expected
Network Failure         — a REAL request genuinely failed
Environment Failure      — the TEST environment itself has an
                            issue, unrelated to the APPLICATION
Flaky Test                 — inconsistent, NON-deterministic
                              behavior (Chapter 12 covers this
                              category in real depth)

Step-by-Step Implementation

// src/classify-failure.ts
import { askClaude } from './ai-client';
import { AnalysisPayload } from './select-evidence-for-analysis';

export type FailureCategory =
  | 'Application Defect' | 'Test Defect' | 'Locator Failure'
  | 'Timeout' | 'Network Failure' | 'Environment Failure' | 'Flaky Test';

export interface Classification {
  category: FailureCategory;
  reasoning: string;
}

const VALID_CATEGORIES: FailureCategory[] = [
  'Application Defect', 'Test Defect', 'Locator Failure',
  'Timeout', 'Network Failure', 'Environment Failure', 'Flaky Test',
];

export async function classifyFailure(
  payload: AnalysisPayload
): Promise<Classification> {
  const prompt = `A Playwright test failed:
Error: ${payload.errorMessage}
Stack: ${payload.relevantStackFrames}
Console errors: ${JSON.stringify(payload.recentConsoleErrors)}
Network failures: ${JSON.stringify(payload.recentNetworkFailures)}

Classify into EXACTLY one category: Application Defect, Test
Defect, Locator Failure, Timeout, Network Failure, Environment
Failure, or Flaky Test. Explain your reasoning in one sentence.

Respond with ONLY valid JSON:
{"category": string, "reasoning": string}`;

  const raw = await askClaude(prompt);
  const parsed = JSON.parse(raw);
  if (!VALID_CATEGORIES.includes(parsed.category)) {
    throw new Error(`Invalid category returned: ${parsed.category}`);
  }
  return parsed;
}

Code Explanation

VALID_CATEGORIES is checked explicitly before trusting the result — the same discipline this tutorial has applied to every constrained AI output since Chapter 5's actionType validation. A model occasionally drifting toward a plausible-sounding but non-standard category ("UI Bug" instead of "Application Defect") would otherwise silently break anything downstream expecting one of the seven real values.

Why It Matters — Each Category Implies a Different Next Step

Application Defect  → file a REAL bug report, notify DEV team
Test Defect          → fix the TEST'S own logic
Locator Failure        → run Chapter 6's HEALING pipeline
Timeout                 → investigate PERFORMANCE, not correctness
Network Failure           → check REAL, external service health
Environment Failure         → check CI infrastructure, not code
Flaky Test                    → route to Chapter 12's FLAKY-test
                                 detection, NOT a one-off retry

Common Mistakes

  • Treating classification as the end goal rather than a routing decision. The real value is in what happens next, based on the category — this page's table above is the actual point.
  • Skipping the VALID_CATEGORIES check because "the prompt already lists them." A prompt shapes behavior; it doesn't guarantee it — the same lesson this tutorial has repeated since Chapter 3.

Best Practices

  • Always validate the returned category against a known, fixed list before routing on it downstream.
  • Treat each category as pointing to a specific, different next action — not just a label for a dashboard.
