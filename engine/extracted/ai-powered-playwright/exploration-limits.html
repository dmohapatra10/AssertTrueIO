Introduction — Why This Wasn't Needed in Chapter 5

Chapter 5's loop had a natural end — five known steps, and the loop finished when they were done. This chapter's exploration has no such natural end; "explore checkout and find unexpected behavior" could, in principle, continue indefinitely. Real limits are what prevent that from becoming a genuine, practical problem.

Step-by-Step Implementation

// src/exploration-limits.ts

export interface ExplorationLimits {
  maxSteps: number;
  maxDepthFromStart: number;
  maxDurationMs: number;
}

export interface ExplorationState {
  stepCount: number;
  currentDepth: number;
  startTime: number;
}

export function shouldStopExploring(
  state: ExplorationState, limits: ExplorationLimits
): { stop: boolean; reason?: string } {
  if (state.stepCount >= limits.maxSteps) {
    return { stop: true, reason: `Reached max steps (${limits.maxSteps})` };
  }
  if (state.currentDepth > limits.maxDepthFromStart) {
    return { stop: true, reason: `Exceeded max depth (${limits.maxDepthFromStart})` };
  }
  if (Date.now() - state.startTime > limits.maxDurationMs) {
    return { stop: true, reason: `Exceeded time budget (${limits.maxDurationMs}ms)` };
  }
  return { stop: false };
}

Code Explanation

Three genuinely different, real risks, each with its own check. maxSteps bounds total AI calls and real cost. maxDepthFromStart prevents exploration from wandering arbitrarily far from the actual objective — three or four navigations away from checkout is probably no longer "exploring checkout" in any meaningful sense. maxDurationMs bounds real wall-clock time, important for keeping exploration practical within a CI run or a bounded investigation session.

Why It Matters

Without these limits, a genuinely curious agent could keep generating plausible-sounding hypotheses indefinitely, accumulating real cost with diminishing real value — the tenth hypothesis about the discount field is unlikely to be as valuable as the first three. Explicit limits make exploration bounded and predictable, a real requirement for using it reliably in a real CI pipeline or investigation workflow.

Common Mistakes

  • Running exploration with no limits at all "since it's just testing." Real API cost and real wall-clock time accumulate regardless of intent — this chapter's opening cost discipline from Chapter 2 applies here just as much as anywhere else.
  • Treating hitting a limit as a failure to investigate. It's an expected, healthy stopping condition — this page's example code explicitly treats it as a normal loop exit, not an error.

Best Practices

  • Set all three limit types explicitly before running any exploration — never rely on just one dimension to bound real risk.
  • Log the specific reason exploration stopped — this is genuinely useful context for anyone reviewing what the agent did and why it stopped there.

Hands-On Exercise

Set reasonable limits for a real exploration objective in your own application, considering your own real constraints — how much time you're willing to spend, how many AI calls are affordable. Run a simulated exploration loop and confirm it stops cleanly for the correct, logged reason.

Key Takeaways

  • Open-ended exploration has no natural end, unlike Chapter 5's fixed sequence — explicit limits are what prevent that from becoming unbounded, costly, or impractical.
  • Step count, depth, and time budget are three genuinely different, real risks, each deserving its own explicit check.
  • Hitting a limit is an expected, healthy stopping condition — not a failure of the exploration itself.
