Introduction

The previous page's advice reduces how often locators break — it doesn't eliminate it. This page is about the honest reality: even a genuinely well-written locator, following every best practice, eventually breaks when the application it targets genuinely changes.

Example — A Real ShopSmart Breakage

// The ORIGINAL, well-written locator, following EVERY best
// practice from the previous page:
await page.getByRole('button', { name: 'Add to Cart' }).click();

// ShopSmart's team REDESIGNS the product page. The button now
// shows an icon AND text, and its ACCESSIBLE name genuinely
// changed:
// BEFORE: <button aria-label="Add to Cart">Add to Cart</button>
// AFTER:  <button aria-label="Add ProBook 15 to cart">
//           <svg/> Add to Cart
//         </button>

// The LOCATOR now finds NOTHING — not because it was written
// BADLY, but because the REAL, accessible name of the button
// genuinely CHANGED as part of a legitimate product update

Why It Matters — This Wasn't a Locator-Writing Mistake

Chapter 6's opening page ranked getByRole as a genuinely stable strategy, and it is — this locator followed every recommended practice. It broke anyway, because ShopSmart's accessible name now includes the specific product name for better screen-reader clarity, a genuinely reasonable, real product decision that happened to change what the locator was matching against.

How It Works — The Real Categories of Breakage

STRUCTURAL   — the DOM hierarchy changes, breaking a locator
               that relied on POSITION or NESTING

TEXTUAL      — visible text OR accessible names change, as in
               THIS page's example

ATTRIBUTE    — a test ID or other attribute gets renamed or
               removed during a REFACTOR

TIMING       — an element now appears LATER (or earlier) in a
               NEW, changed loading sequence

Common Mistakes

  • Treating every locator break as evidence of bad locator-writing. This page's example shows a genuinely well-written locator failing for a genuinely legitimate reason — the application changed.
  • Assuming better locator practices alone will eventually eliminate breakage entirely. They reduce frequency significantly; they can't prevent breakage caused by real, deliberate application changes.

Best Practices

  • When a locator breaks, check first whether the application genuinely changed before assuming the locator was poorly written.
  • Keep this page's four breakage categories in mind — they're what this chapter's AI analysis, starting on the next page, actually reasons about.

Hands-On Exercise

Think of a real locator failure you've encountered before. Classify it against this page's four categories — structural, textual, attribute, or timing — and consider honestly whether better locator-writing practice alone would have prevented it, or whether it was a genuine, legitimate application change.

Key Takeaways

  • Even genuinely well-written locators break when the application they target legitimately changes — this isn't always a locator-writing mistake.
  • Breakage falls into real, distinguishable categories — structural, textual, attribute, and timing — that this chapter's AI analysis reasons about directly.
  • This honest reality is exactly why a healing pipeline is worth building, not a sign that better locator discipline alone would make it unnecessary.
