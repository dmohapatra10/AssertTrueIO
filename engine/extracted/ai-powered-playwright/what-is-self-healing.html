Introduction

"Self-healing" gets used loosely to describe anything from a runtime workaround to an automatic code commit. This page draws the real, precise line this entire chapter depends on.

How It Works — The Precise Distinction

CHAPTER 6's LOCATOR HEALING:
  Test RUNS. Locator BREAKS. AI suggests a REPLACEMENT.
  Validation CONFIRMS it exists on the REAL page. The CURRENT
  test run uses IT — and the source FILE is NEVER touched.
  Next run, WITHOUT intervention, the SAME broken locator is
  STILL in the source, and healing must happen AGAIN.

THIS CHAPTER's SELF-HEALING:
  Test FAILS. AI analyzes WHY. A CANDIDATE fix to the ACTUAL
  SOURCE FILE is generated. It's VALIDATED, checked for
  REGRESSIONS across the SUITE, and a HUMAN reviews it BEFORE
  it EVER reaches the real, committed test FILE.

Why It Matters — The Real Line Is Persistence

Chapter 6's healing is temporary and scoped to one run — nothing changes for next time. This chapter's healing is about a permanent, real change to the file itself, which is exactly why it carries meaningfully more risk and needs meaningfully more scrutiny. A wrong runtime substitution affects one run; a wrong permanent code change affects every future run until someone notices.

Example — Why Chapter 6's Approach Alone Isn't Enough Forever

If ShopSmart's "Add to Cart" button's accessible name changed permanently as part of a legitimate redesign, Chapter 6's healing would correctly find a working locator every single run — but the source file would still contain the stale, broken original, forever. Eventually, someone needs to actually update the test file. This chapter is about doing that update safely, with real evidence and real human oversight, rather than leaving it as permanent, silent, runtime-only patching.

Common Mistakes

  • Treating Chapter 6's runtime healing as a full substitute for actually fixing test files. It solves the immediate problem, not the underlying, permanent one — this chapter exists for the second half.
  • Assuming "self-healing" means fully autonomous, unsupervised code changes. This chapter's remaining pages are explicit that human approval remains a required, non-negotiable step.

Best Practices

  • Use Chapter 6's healing for immediate, runtime continuity; use this chapter's approach when a locator or assertion genuinely needs a permanent, reviewed fix.
  • Keep this precise distinction in mind throughout this chapter — every later page assumes it.

Hands-On Exercise

Think of a real, recurring locator failure from your own suite — one Chapter 6's healing would fix at runtime, every single run, without ever updating the source. Write down what the actual, permanent fix to the test file should look like — that's exactly what this chapter's remaining pages build toward generating automatically.

Key Takeaways

  • Self-healing means proposing a real, persistent change to source code — genuinely different from Chapter 6's temporary, runtime-only substitution.
  • The real line between the two is persistence: one changes nothing lasting, the other changes a file every future run will use.
  • Greater persistence means greater real risk, which is exactly why this chapter's architecture includes validation, regression testing, and human approval.
