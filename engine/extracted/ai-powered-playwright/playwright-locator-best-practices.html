Introduction

No AI in this page at all — deliberately. Before any healing or suggestion technique makes sense, it's worth being genuinely clear about what a good locator looks like, since that's exactly what this chapter's later pages are trying to preserve when things go wrong.

How It Works — Playwright's Semantic Locators

getByRole('button', { name: 'Log In' })
  // Targets by ACCESSIBILITY role and accessible name — tied
  // to what a SCREEN READER would announce, genuinely stable
  // across most visual and structural changes

getByLabel('Email')
  // Targets a FORM field by its associated label text —
  // survives CSS changes, DOM restructuring, most refactors

getByText('Order Confirmed')
  // Targets by VISIBLE text content — reasonably stable for
  // STATIC text, fragile for text that changes often

getByTestId('cart-total')
  // Targets by an EXPLICIT, dedicated test attribute — the
  // MOST stable option, since it exists ONLY for testing and
  // changes ONLY when a developer deliberately updates it

Why It Matters — A Concrete Stability Ranking

These four aren't equally stable, and knowing the real order matters. getByTestId is the most robust, since it's explicitly maintained for testing and immune to visual redesigns. getByRole and getByLabel come next, tied to accessibility semantics that change less often than visual styling. getByText is the least stable of the four — genuinely useful for confirmation messages and static content, but the first to break when copy changes.

Example — Choosing the Right One for ShopSmart's Cart

// The CART TOTAL display — changes VALUE constantly, but the
// ELEMENT itself should be reliably targetable:
page.getByTestId('cart-total')
  // BETTER than getByText('$49.98') — that locator breaks
  // the INSTANT the price changes, which is CONSTANTLY

// The "Add to Cart" BUTTON — a stable, semantic control:
page.getByRole('button', { name: 'Add to Cart' })
  // BETTER than a CSS class selector — survives a visual
  // REDESIGN that changes classes but keeps the BUTTON'S role
  // and accessible NAME intact

Common Mistakes

  • Defaulting to CSS class or XPath selectors. These are tied to implementation and visual details that change often, for reasons that have nothing to do with the feature actually breaking.
  • Using getByText for dynamic, frequently-changing content. A price, a count, a timestamp — anything that changes on every page load is a poor fit for text-based targeting.

Best Practices

  • Reach for getByTestId or getByRole first; treat getByText as a last resort for genuinely static content only.
  • Advocate for dedicated test IDs on elements your suite depends on heavily — this is a real, worthwhile conversation with the development team, not just a testing-side concern.

Hands-On Exercise

Look at five real locators from your own existing test suite. Rank each against this page's stability ordering — testId, role, label, text, everything else — and identify any that are genuinely fragile and worth rewriting before this chapter's AI techniques ever need to heal them.

Key Takeaways

  • Playwright's semantic locator methods have a real, meaningful stability ordering — testId and role-based locators are genuinely more robust than text or CSS-based ones.
  • Good locator practice is the real foundation this entire chapter's remaining pages exist to protect, not a step that AI techniques make unnecessary.
  • A test suite built on fragile locators will need healing constantly — the better fix is often writing more stable locators in the first place.
