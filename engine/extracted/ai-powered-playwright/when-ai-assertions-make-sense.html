Introduction

Chapter 7's earlier pages established the core distinction. This page sharpens it into something more concrete and actionable — three real criteria worth checking together, not just the single, broader "no exact match exists" test.

How It Works — Three Concrete Criteria

1. MULTIPLE legitimate, correct versions genuinely EXIST
   → Chapter 7's own promo-code error EXAMPLE, revisited

2. The REAL requirement is about QUALITY, not PRESENCE
   → NOT "does an error message APPEAR" (deterministic,
     toBeVisible() answers THIS) but "is it GENUINELY clear
     and HELPFUL" (a real judgment call)

3. The COST of a WRONG judgment is GENUINELY tolerable
   → A missed, subtly UNCLEAR error message is a REAL but
     LOW-stakes problem — NOT a security or DATA-loss risk

Example — ShopSmart's Shopping Assistant Response

// ALL THREE criteria genuinely apply here:
// 1. Multiple phrasings could correctly answer "what's your
//    return policy" — no single string is THE correct one
// 2. The real requirement is about ACCURACY and CLARITY of
//    the answer, not just "did SOMETHING get returned"
// 3. A slightly imperfect judgment here is LOW-stakes — a
//    human reviewing FLAGGED, low-confidence results catches
//    genuine problems before they REACH real customers

const judgment = await validateContentSemantically(
  assistantResponse,
  "Accurately describes ShopSmart's 30-day return policy " +
  "without inventing details not in the real policy document"
);

Why It Matters — A Case That Meets Only One Criterion

ShopSmart's payment confirmation page showing a specific transaction ID meets criterion 1 loosely — transaction IDs are technically all "different, correct values" in some abstract sense. But it fails criterion 2 completely: the real requirement is that the transaction ID is PRESENT and matches the actual, real transaction — not that it reads as clear or helpful. This is genuinely a deterministic check (toHaveText against the known, real transaction ID), not a judgment call, despite superficially resembling criterion 1.

Common Mistakes

  • Applying Role 2 whenever criterion 1 alone loosely seems to fit. This page's transaction ID example shows why checking all three criteria together matters — a shallow read of criterion 1 alone can mislead.
  • Ignoring criterion 3 for a high-stakes check. A judgment call about whether a security warning is "clear enough" carries real, higher stakes than an error message's phrasing — worth extra scrutiny, not the same casual treatment.

Best Practices

  • Check all three criteria together before reaching for Role 2 — not just whichever one is most obviously true.
  • For genuinely high-stakes content, even content that meets all three criteria, add a human review step rather than trusting AI judgment alone.

Key Takeaways

  • Three concrete criteria — multiple legitimate versions, a quality-focused requirement, and tolerable judgment-error cost — together identify genuine Role 2 cases more reliably than any single test alone.
  • Content that superficially resembles a judgment call can still be a deterministic check in disguise — worth checking carefully, not assuming.
  • Higher-stakes content warrants added human review even when it genuinely meets all three criteria.
