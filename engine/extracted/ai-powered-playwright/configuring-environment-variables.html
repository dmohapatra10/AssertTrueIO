Configuring Environment Variables

Prerequisites: Project Setup and Dependencies

What You'll Learn

  • Setting up real, working credential configuration with .env and dotenv
  • Why this specific setup is non-negotiable, not a nicety
  • Making sure a real credential can never end up in version control

Introduction

An API key hardcoded directly in source code is a genuine, real security risk the moment that code is committed anywhere — a private repo included, since access controls change and history persists. This page sets up the correct pattern once, used unchanged for the rest of this tutorial.

Step-by-Step Implementation

# .env — a REAL file, in your project root, NEVER committed
ANTHROPIC_API_KEY=sk-ant-your-real-key-here
SHOPSMART_BASE_URL=https://shopsmart.example.com
SHOPSMART_TEST_EMAIL=test-user@shopsmart-test.example.com
SHOPSMART_TEST_PASSWORD=your-test-password-here
# .gitignore — add THIS before your first commit, not after
.env
node_modules/
test-results/
playwright-report/
// src/config.ts — loads and validates environment variables
// ONCE, so every other file can trust they're genuinely present
import dotenv from 'dotenv';
dotenv.config();

function requireEnv(name: string): string {
  const value = process.env[name];
  if (!value) {
    throw new Error(
      `Missing required environment variable: ${name}. ` +
      `Copy .env.example to .env and fill in real values.`
    );
  }
  return value;
}

export const config = {
  anthropicApiKey: requireEnv('ANTHROPIC_API_KEY'),
  shopSmartBaseUrl: requireEnv('SHOPSMART_BASE_URL'),
  shopSmartTestEmail: requireEnv('SHOPSMART_TEST_EMAIL'),
  shopSmartTestPassword: requireEnv('SHOPSMART_TEST_PASSWORD'),
};

Code Explanation

requireEnv fails loudly and immediately if a required variable is genuinely missing, rather than letting a later, confusing error surface deep inside an AI client or a Playwright test. Every other file in this tutorial imports config from this one module, rather than reading process.env directly — a single, genuine source of truth for configuration.

Expected Result

Running a small script that imports config and logs config.shopSmartBaseUrl should print your real value — and running the same script with ANTHROPIC_API_KEY deliberately removed from .env should fail immediately, with the clear error message above, not a cryptic downstream failure.

Common Mistakes

  • Adding .gitignore after your first commit. If .env was ever committed, it's in your repository's history — removing it later doesn't erase that; the key should be considered compromised and rotated.
  • Reading process.env directly, scattered across many files. This makes it easy to forget a required variable somewhere, and much harder to see, in one place, exactly what configuration your whole system depends on.

Best Practices

  • Create .gitignore with .env listed before your very first commit, not after.
  • Fail loudly and immediately on missing configuration, rather than letting it surface later as a confusing runtime error.
  • Commit a .env.example file with variable names but no real values, so teammates know exactly what to configure.

Hands-On Exercise

Create your own .env, .gitignore, and src/config.ts following this page's pattern. Then deliberately remove one required variable and confirm you get this page's clear error message, not a cryptic one — that confirms the validation is genuinely working, not just present.

Key Takeaways

  • Credentials belong in .env, never hardcoded in source — and .gitignore needs to exclude it before the first commit, not after.
  • Validating required configuration once, in one place, with a clear error message, is genuinely better than letting missing config surface as a confusing failure elsewhere.
  • Every later chapter's code imports this same config module, rather than reading environment variables directly.
