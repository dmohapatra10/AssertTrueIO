Introduction

Chapter 6 already found a working, validated replacement locator. This page's job is narrower and more concrete: turning that already-validated locator into an actual, reviewable code change to the file where the old one lives.

Step-by-Step Implementation

// src/generate-locator-fix.ts
import { readFileSync } from 'fs';

export interface CodeFix {
  filePath: string;
  originalLine: string;
  proposedLine: string;
  lineNumber: number;
}

export function generateLocatorFix(
  filePath: string, brokenLocatorCode: string, healedLocatorCode: string
): CodeFix | null {
  const content = readFileSync(filePath, 'utf-8');
  const lines = content.split('\n');

  const lineIndex = lines.findIndex((line) => line.includes(brokenLocatorCode));
  if (lineIndex === -1) return null;

  const proposedLine = lines[lineIndex].replace(brokenLocatorCode, healedLocatorCode);

  return {
    filePath,
    originalLine: lines[lineIndex],
    proposedLine,
    lineNumber: lineIndex + 1,
  };
}

Code Explanation

Notice this function only reads the file — it never writes to it. This is deliberate, and it's the same discipline Chapter 6's own healing function followed: producing a candidate is a genuinely different action than applying one, and this chapter keeps that boundary explicit at every single stage, not just at the very end.

Example — Fixing ShopSmart's Add-to-Cart Test

const fix = generateLocatorFix(
  'tests/cart.spec.ts',
  "getByRole('button', { name: 'Add to Cart' })",
  "getByTestId('add-to-cart-btn')"
);

Why It Matters — This Is Still Just a Proposal

The CodeFix object above is genuinely useful information — a specific file, a specific line, a specific before-and-after. It's also nothing more than that yet. This chapter's remaining pages exist specifically because a syntactically correct, well-targeted change like this one can still be wrong in ways this function has no way to detect on its own — it doesn't know whether the new locator is genuinely equivalent in meaning, only that it exists on the page, which Chapter 6 already confirmed.

Common Mistakes

  • Writing the proposed line directly back to the file in this same function. This chapter's later pages exist specifically to validate and gate this change first — combining generation and application defeats that structure entirely.
  • Assuming a locator that passed Chapter 6's runtime validation is automatically safe to commit permanently. Existing uniquely on the page confirms it works today — it says nothing about whether it's the semantically right, intentional choice going forward.

Best Practices

  • Keep fix generation strictly read-only, producing a candidate object rather than writing to disk — the same boundary this page's code demonstrates.
  • Carry forward Chapter 6's own validation results as part of this candidate's supporting evidence, rather than discarding that context.

Key Takeaways

  • Turning a healed locator into a candidate code change is a real, concrete step — a specific file, line, and proposed replacement.
  • This function deliberately stays read-only, keeping generation and application as separate, distinct actions throughout this chapter.
  • A candidate that's syntactically correct and runtime-validated by Chapter 6 still isn't automatically safe to commit — this chapter's remaining pages address exactly that gap.
