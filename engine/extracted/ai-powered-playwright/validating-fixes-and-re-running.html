Validating Fixes and Re-Running

Prerequisites: Root Cause and Safe Fixes

What You'll Learn

  • Why re-running the same real trigger, not a new test, is the honest way to confirm resolution

Introduction

The previous stage produced a diagnosis for the development team, not an automatic fix. This page picks up once that team has actually applied a real fix to discount-calculator.ts — closing the loop this capstone's pipeline exists to close.

Step-by-Step Implementation

// src/capstone-pipeline.ts (stage 5)
import { executeAction } from './map-to-playwright';
import { Page } from '@playwright/test';

export async function revalidateAfterFix(
  originalExplorationAction: string, page: Page
) {
  // Re-run the EXACT same action that ORIGINALLY revealed the
  // bug — applying the SAME discount code TWICE — not a NEW,
  // different test. This IS the honest way to confirm THIS
  // SPECIFIC bug is genuinely RESOLVED.
  await executeAction(originalExplorationAction, page);

  const cartTotal = await page.getByTestId('cart-total').textContent();
  return { cartTotal, retriggeredAction: originalExplorationAction };
}

Code Explanation

Re-running the exact original trigger, rather than writing a new, different test for the fix, is deliberate — it's the most direct, honest way to confirm this specific bug is genuinely gone. A new test could pass while subtly failing to exercise the exact condition that revealed the original problem; re-running the original trigger leaves no such gap.

Example — The Real, Confirmed Fix

const result = await revalidateAfterFix(
  'apply discount code SAVE10 twice in succession', page
);

// BEFORE the fix: cartTotal reflected a 20% REDUCTION
// AFTER the fix:  cartTotal reflects a 10% reduction, and a
//                  CLEAR message: "This code has already been
//                  applied" — the SAME action, GENUINELY
//                  different, CORRECT result

Why It Matters — This Is a Real Regression Check Too

This re-run also functions as Chapter 11's own regression check, applied to this specific case — confirming the fix genuinely resolves the reported behavior without needing a separate, redundant test. If the same action still produced a doubled discount, this stage would correctly report the fix as incomplete, closing the loop honestly either way.

Common Mistakes

  • Writing a new, different test to verify the fix instead of re-running the original trigger. This page's whole point is that the original trigger is the most direct, honest confirmation — a new test risks subtly not exercising the exact same condition.
  • Assuming a fix that compiles and deploys is automatically correct. This stage's actual re-run against the live application is what provides real, genuine confirmation — not just that code changed, but that the reported behavior genuinely changed too.

Best Practices

  • Always re-run the exact original trigger when confirming a fix for a specific, reported bug — it's the most direct, honest verification available.
  • Report the re-run's actual outcome honestly, whether the fix genuinely resolved the issue or not.
