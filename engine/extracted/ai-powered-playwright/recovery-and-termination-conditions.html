Step-by-Step Implementation — Recovery, Reusing Chapter 6 Directly

// src/agent-recovery.ts
import { Page } from '@playwright/test';
import { healLocator } from './heal-locator';

export async function attemptRecovery(
  failedAction: string, page: Page
): Promise<{ recovered: boolean; newApproach?: string }> {
  const healResult = await healLocator(failedAction, page);

  if (healResult.healed) {
    return {
      recovered: true,
      newApproach: `Use ${healResult.workingLocatorCode} instead`,
    };
  }
  return { recovered: false };
}

Code Explanation

This function calls Chapter 6's healLocator directly — no new healing logic exists in this chapter at all. When recovery succeeds, the agent's next planning step gets told about the working alternative directly in its conversation history, letting the model's own reasoning decide how to proceed with this new information, rather than the code silently substituting it without the model ever knowing something went wrong.

How It Works — Three Genuinely Different Termination Conditions

SUCCESS: the EVALUATOR (previous page) reports
  objectiveLikelyMet: true, with GENUINE, honest confidence

LIMIT REACHED: Chapter 13'S OWN shouldStopExploring returns
  true — steps, DEPTH, or time BUDGET exhausted, with the
  objective STILL not confidently achieved

UNRECOVERABLE FAILURE: an action FAILS, Chapter 6'S healing
  ALSO fails to find a WORKING alternative, and NO further
  progress is genuinely POSSIBLE

Example — Handling All Three in the Main Loop

const evaluation = await evaluateProgress(state);
if (evaluation.objectiveLikelyMet && evaluation.confidence !== 'low') {
  return { outcome: 'success', evaluation };
}

const limitCheck = shouldStopExploring(
  { stepCount: state.stepCount, currentDepth: 0, startTime: state.startTime },
  { maxSteps: 30, maxDepthFromStart: 4, maxDurationMs: 5 * 60 * 1000 }
);
if (limitCheck.stop) {
  return { outcome: 'limit-reached', reason: limitCheck.reason };
}

if (lastActionFailed) {
  const recovery = await attemptRecovery(lastFailedAction, page);
  if (!recovery.recovered) {
    return { outcome: 'unrecoverable-failure', action: lastFailedAction };
  }
}

Why It Matters — These Three Outcomes Deserve Different Responses

A run that ends in genuine success needs no further human attention. A run that hits a limit without confident success is worth a human glancing at — the objective might genuinely be unreachable, or the limits might simply be too tight. A run ending in unrecoverable failure deserves the most attention, since it likely represents a real, reportable problem. Collapsing all three into a single "run finished" status would lose this genuinely useful distinction.

Common Mistakes

  • Writing new healing logic specific to the agent, rather than reusing Chapter 6's function. Nothing about locator healing changes just because it's now called from within an agent loop.
  • Treating "limit reached" and "unrecoverable failure" as the same outcome. The first means the agent simply ran out of budget; the second means something genuinely broke — worth investigating differently.

Best Practices

  • Reuse Chapter 6's healing exactly as written — recovery within an agent context is the same problem, not a new one.
  • Always report which of the three termination conditions actually occurred, never just "the run ended."

Key Takeaways

  • Recovery reuses Chapter 6's healing function directly, informing the model's own next reasoning step rather than silently substituting a fix.
  • A run can end in three genuinely different ways — success, limit reached, or unrecoverable failure — each deserving a different real response.
  • Distinguishing these outcomes explicitly, rather than collapsing them into "finished," is what makes the agent's results genuinely actionable.
