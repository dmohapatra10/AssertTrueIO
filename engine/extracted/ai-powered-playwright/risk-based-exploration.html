Introduction

The previous page's limits mean exploration has a real, finite budget — thirty steps, five minutes, whatever you set. This page is about spending that budget on what genuinely matters most, rather than wherever exploration happens to wander first.

How It Works — Reusing Chapter 4's Principle, Applied Differently

CHAPTER 4: risk-based PRIORITIZATION decided WHICH generated
  test CASES were worth RUNNING, given a limited execution
  budget

THIS CHAPTER: the SAME underlying principle decides WHERE
  exploration should SPEND its limited STEP budget — payment
  and CHECKOUT genuinely matter more than a rarely-used
  profile SETTINGS page

Step-by-Step Implementation

// src/risk-based-exploration.ts
import { askClaude } from './ai-client';

export interface AreaRiskScore {
  area: string;
  riskScore: number;
  reasoning: string;
}

export async function scoreExplorationAreas(
  candidateAreas: string[], businessContext: string
): Promise<AreaRiskScore[]> {
  const prompt = `Business context: ${businessContext}
Candidate areas to potentially explore: ${JSON.stringify(candidateAreas)}

Score each area's exploration priority 1-5, based on revenue
impact, usage frequency, and consequence of an undiscovered bug.

Respond with ONLY valid JSON:
{"scores": [{"area": string, "riskScore": number, "reasoning": string}]}`;

  const raw = await askClaude(prompt);
  return JSON.parse(raw).scores.sort(
    (a: AreaRiskScore, b: AreaRiskScore) => b.riskScore - a.riskScore
  );
}

const scores = await scoreExplorationAreas(

  revenue. Profile and newsletter features are non-critical.'

Why It Matters — A Concrete Comparison

Unprioritized exploration, with a 30-step budget, might spend 15 steps thoroughly exploring the profile picture upload simply because the strategy layer happened to wander there first, leaving little budget for payment. Risk-based exploration spends the majority of that same budget on payment and checkout — the areas where an undiscovered bug would genuinely cost the business the most — before ever considering lower-priority areas.

Common Mistakes

  • Letting exploration strategy (from this chapter's earlier page) run without any risk prioritization layered on top. Strategy alone decides what's genuinely new to try; it doesn't know what's genuinely important — this page adds that missing dimension.
  • Scoring areas once and never revisiting priority as exploration proceeds. If payment turns out to be thoroughly covered quickly, remaining budget should shift toward the next-highest area, not stay fixed on an area that's already well-explored.

Best Practices

  • Score candidate areas before exploration begins, using real business context — the same discipline Chapter 4 applied to test case prioritization.
  • Bias the exploration strategy layer's choices toward higher-scored areas, especially early in a limited step budget.

Hands-On Exercise

List five real areas of your own application that could be candidates for exploration. Score them using this page's function with genuine business context, and compare the resulting priority order against your own intuition about where bugs would matter most.

Key Takeaways

  • A limited exploration budget should be spent deliberately on what matters most, not wherever exploration happens to wander first.
  • This reuses Chapter 4's risk-prioritization principle, applied to where an agent explores rather than which generated test cases get run.
  • Without this prioritization, exploration risks spending most of its budget on low-value areas simply because they were encountered first.
