Introduction

This chapter's architecture has an Observation step for a real reason: "select a product" can only be planned once something genuine is known about what the search actually returned. This page builds that observation — the bridge between an executed action and the next, dependent step's planning.

Step-by-Step Implementation

// src/observe-page.ts
import { Page } from '@playwright/test';

export interface PageObservation {
  url: string;
  visibleHeadings: string[];
  visibleProductNames: string[];
}

export async function observePage(page: Page): Promise<PageObservation> {
  const url = page.url();

  const visibleHeadings = await page
    .getByRole('heading')
    .allTextContents();

  const visibleProductNames = await page
    .getByTestId('product-card')
    .getByRole('heading')
    .allTextContents();

  return { url, visibleHeadings, visibleProductNames };
}

Code Explanation

Notice what this function deliberately does NOT capture — full page HTML, every element's full attribute list, network traffic. Capturing everything would genuinely cost more (Chapter 18's token-cost lesson applies directly here) while making the next planning step's prompt noisier, not clearer. visibleProductNames specifically exists because that's exactly what "select a product" needs to reason about — deliberately scoped to the real question at hand.

Why It Matters

This observation is now real, genuine information — not a guess about what ShopSmart's search might return, but what it actually, currently returns. This is exactly what this chapter's next-but-one page needs to plan "select a product" honestly, rather than inventing a product name that may not exist.

Common Mistakes

  • Capturing the entire page's HTML "just in case it's useful later." This adds real token cost to every downstream prompt that uses the observation, for information the specific next step usually doesn't need.
  • Observing too late — after deciding the next action, rather than before. The whole point of this page is that observation happens between actions, feeding directly into the next planning step, not as an afterthought.

Best Practices

  • Scope what you observe to what the next, genuinely dependent step actually needs — not everything the page happens to contain.
  • Keep observation as a separate, explicit function, called between actions — not folded invisibly into execution or planning code.

Key Takeaways

  • Observation captures real, current information from the browser — the genuine alternative to guessing at what a page might contain.
  • Scoping what's captured to what the next step actually needs keeps observations useful and affordable, rather than comprehensive but noisy.
  • This page is what makes planning a dependent step — like "select a product" — honest, rather than a guess dressed up as a plan.
