Prerequisites: Breaking Instructions into Steps

Introduction

The previous page's steps are still just descriptions — "log in to ShopSmart" isn't yet something Playwright can execute. This page turns a step into an action: a specific, structured intent, concrete enough to validate and eventually map to a real Playwright call.

Step-by-Step Implementation

// src/plan-action.ts
import { askClaude } from './ai-client';
import { InstructionStep } from './break-into-steps';

export interface PlannedAction {
  stepOrder: number;
  actionType: 'navigate' | 'fill' | 'click' | 'assert';
  target: string;
  value?: string;
}

export async function planAction(
  step: InstructionStep, pageContext: string
): Promise<PlannedAction> {
  const prompt = `Step: "${step.description}"
Real, known page structure: ${pageContext}

Plan ONE concrete action for this step. actionType must be
exactly one of: navigate, fill, click, assert. target should
describe WHAT element, using the real page structure given —
never invent an element that isn't listed.

Respond with ONLY valid JSON:
{"actionType": string, "target": string, "value": string_or_null}`;

  const raw = await askClaude(prompt);
  const parsed = JSON.parse(raw);
  const validTypes = ['navigate', 'fill', 'click', 'assert'];
  if (!validTypes.includes(parsed.actionType)) {
    throw new Error(`Invalid actionType: ${parsed.actionType}`);
  }

  return {
    stepOrder: step.order,
    actionType: parsed.actionType,
    target: parsed.target,
    value: parsed.value ?? undefined,
  };
}

Code Explanation

PlannedAction is deliberately narrower than free-form text — actionType is constrained to exactly four values, checked explicitly against validTypes before the function trusts it. This is the same discipline Chapter 2 introduced as structured output, applied here to something small and specific enough to validate completely, rather than just checking a general JSON shape.

Example — Planning ShopSmart's Login Step

const loginPageContext = `Login page: Email field
(getByLabel('Email')), Password field (getByLabel('Password')),
Submit button (getByRole('button', { name: 'Log In' })).`;

const action = await planAction(
  { order: 1, description: 'Log in to ShopSmart', dependsOnPreviousResult: false },
  loginPageContext
);

// A REAL, single planned action — genuinely just ONE piece of
// the login step, since "log in" actually needs THREE actions
// (fill email, fill password, click submit)
// { stepOrder: 1, actionType: "fill", target: "Email field",
//   value: "test@shopsmart.example.com" }

Why It Matters — Only Plan What Doesn't Need Observation Yet

Notice this page only plans actions for steps where dependsOnPreviousResult is false. Trying to plan "select a product" here — before search results genuinely exist — would force the model to guess at a real product name, exactly the fragile guessing Chapter 5's opening page warned about. This chapter's next pages handle dependent steps differently, planning them only once a real observation is available.

Common Mistakes

  • Planning every step from this chapter's earlier page in one batch, regardless of dependency. A dependent step planned without a real observation is exactly the guessing problem this entire chapter exists to avoid.
  • Skipping the validTypes check because "the prompt already constrains it." A prompt shapes behavior; it doesn't guarantee it — the same lesson Chapter 3 established for locators applies here to action types.

Best Practices

  • Plan only independent steps ahead of time; handle dependent steps as the plan actually unfolds, covered in this chapter's remaining pages.
  • Keep actionType constrained to a small, known set — a free-form action type would be much harder to validate or map to Playwright reliably.

Hands-On Exercise

Using the previous page's steps for your own instruction, plan actions for every step marked dependsOnPreviousResult: false. For the ones marked true, write down, honestly, what real information would be missing if you tried to plan them right now.

Key Takeaways

  • A planned action is genuinely more concrete than a step — a specific, constrained, structured intent, not just a description.
  • Only independent steps should be planned ahead of time — dependent steps need a real observation first, covered starting on this chapter's next page.
  • Explicit validation of a constrained field like actionType is cheap and catches real, possible mistakes a prompt alone doesn't guarantee against.
