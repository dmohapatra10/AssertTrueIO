Locator Candidate Generation

Prerequisites: AI Locator Suggestions

What You'll Learn

Introduction

The previous page's single suggestion carries real risk on its own. This page's fix isn't asking more carefully — it's asking for several, genuinely different candidates, so a later ranking and validation step has real options to choose between, rather than one guess to simply accept or reject.

Step-by-Step Implementation

// src/generate-locator-candidates.ts
import { Page } from '@playwright/test';
import { askClaude } from './ai-client';
import { capturePageStructure } from './suggest-locator';

export interface LocatorCandidate {
  strategy: string;
  locatorCode: string;
}

export async function generateLocatorCandidates(
  brokenLocatorDescription: string, page: Page
): Promise<LocatorCandidate[]> {
  const structure = await capturePageStructure(page);

  const prompt = `A Playwright locator broke:
"${brokenLocatorDescription}"

Real, current page structure: ${structure}

Generate THREE genuinely different candidate replacement
locators, each using a DIFFERENT strategy (role-based,
testId-based, text-based) where the real page structure
supports it. Use ONLY elements that actually appear above.

Respond with ONLY valid JSON:
{"candidates": [{"strategy": string, "locatorCode": string}]}`;

  const raw = await askClaude(prompt);
  const parsed = JSON.parse(raw);
  if (!Array.isArray(parsed.candidates)) {
    throw new Error(`Expected {"candidates": [...]} but got: ${raw.slice(0, 200)}`);
  }
  return parsed.candidates;
}

Code Explanation

Notice the prompt explicitly asks for different strategies — role-based, testId-based, text-based — not just three variations of the same idea. This matters because different strategies fail independently: if ShopSmart's accessible name changes again later, a testId-based candidate from this same batch would still work, while a role-based one might not.

Example — Three Genuine Candidates for the Add-to-Cart Button

const candidates = await generateLocatorCandidates(
  "getByRole('button', { name: 'Add to Cart' })", page
);

Why It Matters

If the page structure genuinely includes a data-testid attribute on this button, that candidate is very likely the most stable of the three — following Chapter 6's own opening page's stability ranking. Having multiple, genuinely different candidates is what makes the next page's ranking step meaningful — ranking one option against nothing is not a real choice.

Common Mistakes

  • Generating three candidates that are all minor variations of the same strategy. Three role-based locators with slightly different name matching don't provide genuine, independent alternatives if the accessible name changes again.
  • Requesting candidates without the real page structure. The same grounding requirement from the previous page still applies — every candidate needs to reference real, current elements.

Best Practices

  • Request genuinely different strategies explicitly, not just "more suggestions" — the prompt's specificity is what produces real diversity.
  • Keep every candidate traceable to real, captured page structure — none of them should be accepted on faith alone.

Hands-On Exercise

Run this page's function for a different ShopSmart element — the cart quantity field, for example. Check whether all three returned candidates genuinely reference real, different elements from your captured structure, or whether any subtly duplicate the same underlying strategy.

Key Takeaways

  • Multiple, genuinely different candidates are meaningfully safer than one suggestion, since different strategies fail independently.
  • Requesting different strategies explicitly — not just "more options" — is what produces real, useful diversity rather than near-duplicates.
