Introduction

MCP (Model Context Protocol) is a standard way for an AI client to discover what tools are available and call them, without needing to know anything about how those tools are actually implemented. This page is about understanding that definition concretely, using Chapter 14's own tools as the example.

How It Works — Before and After MCP

BEFORE MCP (Chapter 14's OWN approach):
  const BROWSER_TOOLS: Anthropic.Tool[] = [...]
  // Defined DIRECTLY in TypeScript, imported DIRECTLY by
  // Chapter 14'S OWN agent class — usable ONLY within THIS
  // exact codebase, by CODE that imports THIS exact file

AFTER MCP:
  A SERVER exposes the SAME tools over a STANDARD protocol.
  ANY MCP-compatible client — a DIFFERENT team'S agent, a
  DIFFERENT AI provider'S tool, even a COMPLETELY different
  PROGRAMMING language — can DISCOVER and CALL these tools,
  WITHOUT ever seeing Chapter 14'S TypeScript source at all

Why It Matters — This Is Standardization, Not New Capability

Nothing about what navigate or click_element actually does changes. What changes is how a client finds out these tools exist and how it calls them — through a standard protocol rather than a direct code import. This is exactly why Chapter 15's opening page was explicit that no new testing concepts are being introduced here.

Example — A Concrete Illustration

Imagine a separate team building their own AI-powered monitoring tool for ShopSmart's production environment — a completely different codebase, possibly a different programming language entirely. Without MCP, they'd need to reimplement browser automation tools from scratch, or copy Chapter 14's TypeScript code directly into their own project. With MCP, they connect to a running MCP server exposing these same tools and use them immediately, with zero code copying and zero dependency on this track's specific TypeScript implementation.

Common Mistakes

  • Assuming MCP tools are somehow more capable than the same tools called directly. The underlying implementation and capability are identical — only the access mechanism changes.
  • Treating this page's definition as more complicated than it actually is. "Standard way to discover and call tools without needing their source code" is the complete, working definition — everything else in this chapter builds on exactly that.

Best Practices

  • Keep this page's before-and-after comparison in mind throughout the rest of this chapter — it's the concrete anchor for every later page's more technical content.
  • Think about MCP in terms of what problem it solves (reusability across codebases) rather than what new capability it might seem to add (none).

Hands-On Exercise

Pick one function from an earlier chapter in this track — Chapter 6's healLocator, for example. Describe concretely what a teammate on a completely different project, in a different codebase, would need to do to use it today, versus what they'd need to do if it were exposed via MCP.

Key Takeaways

  • MCP is a standard protocol for discovering and calling tools without needing their original source code.
  • This is fundamentally a reusability and standardization solution, not a new capability — the underlying tools work identically either way.
  • Chapter 14's tools, once exposed via MCP, become usable by any compatible client, regardless of that client's own codebase or programming language.
