Introduction

Before writing any real server code, it's worth seeing the complete picture — three components, each with a specific, real role, and a concrete mapping to what this track has already built.

How It Works — The Three Real Components

HOST      — the application the HUMAN or SYSTEM actually
             interacts with — Chapter 14'S OWN agent CLASS,
             or any OTHER application that WANTS to use tools

CLIENT       — lives INSIDE the host, manages the ACTUAL
                connection to a server, handles the REAL
                protocol details (discovery, calling, RESULTS)

SERVER          — exposes the ACTUAL tools — THIS chapter's
                   real Playwright browser TOOLS, wrapped and
                   made available over the PROTOCOL

Why It Matters — Mapping This to What Already Exists

Chapter 14's PlaywrightAgent class is genuinely a host — it's the application deciding what objective to pursue and reasoning about next steps. This chapter adds a client inside that agent, and a genuinely new server process exposing the same browser tools. Nothing about the agent's own reasoning changes; only how it reaches its tools does.

Example — Tracing a Real Tool Call Through This Architecture

1. The AGENT (host) decides it needs to CLICK "Add to Cart"
2. The CLIENT, living INSIDE the agent, sends a STANDARDIZED
   tool-call REQUEST over the protocol
3. The SERVER receives it, executes the REAL Playwright
   click_element LOGIC (Chapter 14'S own function, UNCHANGED)
4. The SERVER sends a STANDARDIZED result BACK
5. The CLIENT hands the result BACK to the agent'S reasoning,
   exactly the way Chapter 14'S OWN tool_result format DID

Why This Separation Matters

The host never needs to know how the server actually implements click_element — whether it's calling Playwright directly, running in a container, or proxying to another service entirely. This separation is what makes the reusability from this chapter's earlier pages genuinely possible: a completely different host, written by a completely different team, can use the exact same server without ever seeing its implementation.

Common Mistakes

  • Conflating the client and the server. The client lives inside the host and manages the connection; the server is a separate, standalone process exposing the actual tools — confusing these makes the rest of this chapter's code harder to follow.
  • Assuming the host needs protocol-level knowledge. The client handles all of that — the host, including Chapter 14's agent reasoning, only ever sees tool names, inputs, and results, the same shape it already worked with.

Best Practices

  • Keep this three-part structure in mind as a mental model while reading the rest of this chapter's real server and client code.
  • Think of the server as owning implementation details entirely — the host and client should never need to know how a tool's real work actually happens.

Key Takeaways

  • MCP's architecture has three real components — host, client, and server — each with a distinct, well-defined role.
  • Chapter 14's agent becomes the host; this chapter adds a client and a genuinely new server, without changing the agent's own reasoning.
  • The host never needs implementation knowledge of the server's tools — this separation is exactly what makes cross-team, cross-codebase reuse possible.
