Introduction

Chapter 9's opening page argued that a single failure alone can't distinguish flakiness from a real defect. This page builds the genuine solution — real history, accumulated across many actual runs, using Playwright's own built-in reporting.

Step-by-Step Implementation — Configuring the JSON Reporter

// playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  reporter: [
    ['list'],
    ['json', { outputFile: 'test-results/results.json' }],
  ],
});

Step-by-Step Implementation — Accumulating Real History

// src/collect-test-history.ts
import { readFileSync, existsSync, writeFileSync } from 'fs';

export interface TestRunRecord {
  testName: string;
  filePath: string;
  status: 'passed' | 'failed';
  timestamp: string;
  commitHash: string;
  durationMs: number;
}

const HISTORY_PATH = 'test-data/test-history.json';

export function recordRunResults(
  resultsJsonPath: string, commitHash: string
): void {
  const raw = JSON.parse(readFileSync(resultsJsonPath, 'utf-8'));
  const history: TestRunRecord[] = existsSync(HISTORY_PATH)
    ? JSON.parse(readFileSync(HISTORY_PATH, 'utf-8'))
    : [];

  for (const suite of raw.suites) {
    for (const spec of suite.specs) {
      for (const test of spec.tests) {
        history.push({
          testName: spec.title,
          filePath: suite.file,
          status: test.results[0].status,
          timestamp: new Date().toISOString(),
          commitHash,
          durationMs: test.results[0].duration,
        });
      }
    }
  }

  writeFileSync(HISTORY_PATH, JSON.stringify(history, null, 2), 'utf-8');
}

Code Explanation

This runs after every real CI execution, appending to a growing, genuine history file — the same committed-JSON-file pattern Chapter 8 used for deterministic test data, applied here to build an actual evidentiary record over time. Each record carries the commitHash it ran against, which is what lets later analysis distinguish "flaky across many different commits" from "started failing right after one specific change."

Why It Matters

Two records with the same test name and the same commit hash, but different outcomes, is real, concrete, unambiguous evidence of flakiness — the code genuinely didn't change between these two runs, yet the outcome did. This is exactly the kind of evidence Chapter 12's opening page argued a single failure alone can never provide.

Common Mistakes

  • Only keeping the most recent run's results, overwriting history each time. This page's whole point is accumulating history across runs — a single, overwritten result provides no evidence of a pattern at all.
  • Omitting commitHash from each record. Without it, there's no way to distinguish genuine flakiness (same commit, different outcomes) from a real regression that started at a specific, identifiable commit.

Best Practices

  • Run this collection step after every real CI execution, not just occasionally — genuine history needs consistent, real accumulation.
  • Include commit hash and timestamp on every record — both are what make later analysis genuinely trustworthy.

Hands-On Exercise

Configure your own project's JSON reporter and run this page's collection function after your next few real CI runs. Once you have at least ten real records for one test, look for any case where the same commit hash produced different outcomes.

Key Takeaways

  • Real, accumulated history — not any single run — is the genuine evidence base flakiness detection requires.
  • Recording commit hash alongside each result is what lets later analysis distinguish genuine flakiness from a real regression tied to a specific change.
  • Two identical-commit, different-outcome records are concrete, unambiguous evidence — exactly what a single failure alone could never provide.
