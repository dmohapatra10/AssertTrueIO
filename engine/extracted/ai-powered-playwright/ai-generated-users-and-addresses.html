Introduction

This page directly addresses the previous page's poor-diversity problem — generating genuinely varied users and addresses, rather than reusing the same three hardcoded ones indefinitely.

Step-by-Step Implementation

// src/generate-user-data.ts
import { askClaude } from './ai-client';

export interface GeneratedUser {
  firstName: string;
  lastName: string;
  email: string;
  address: {
    street: string;
    city: string;
    state: string;
    zip: string;
  };
}

export async function generateUsers(
  count: number
): Promise<GeneratedUser[]> {
  const prompt = `Generate ${count} realistic, GENUINELY varied
test users for an e-commerce application — different name
origins, different US states and cities, different street
address formats (some with apartment numbers, some without).
Use example.com email domains only, never real domains.

Respond with ONLY valid JSON:
{"users": [{"firstName": string, "lastName": string,
"email": string, "address": {"street": string, "city": string,
"state": string, "zip": string}}]}`;

  const raw = await askClaude(prompt);
  const parsed = JSON.parse(raw);
  if (!Array.isArray(parsed.users)) {
    throw new Error(`Expected {"users": [...]} but got: ${raw.slice(0, 200)}`);
  }
  return parsed.users;
}

Code Explanation

"Genuinely varied" is doing real work in this prompt — without it, a model tends toward the same statistically common patterns repeatedly, quietly reproducing exactly the poor-diversity problem this chapter opened with. The explicit request for different name origins, address formats, and states is what actually produces the variety the previous page identified as missing.

Wrapping This as a Playwright Fixture

// src/fixtures.ts
import { test as base } from '@playwright/test';
import { generateUsers, GeneratedUser } from './generate-user-data';

export const test = base.extend<{ testUser: GeneratedUser }>({
  testUser: async ({}, use) => {
    const [user] = await generateUsers(1);
    await use(user);
  },
});

export { expect } from '@playwright/test';

Example — Using the Fixture in a Real Test

import { test, expect } from './fixtures';

test('registration succeeds with a realistic, varied user', async ({ page, testUser }) => {
  await page.goto('/register');
  await page.getByLabel('First Name').fill(testUser.firstName);
  await page.getByLabel('Email').fill(testUser.email);
  await page.getByLabel('Street Address').fill(testUser.address.street);
  // A REAL, freshly-generated, varied user — NOT the same
  // hardcoded "Jane Doe" every single test run has used
});

Common Mistakes

  • Asking for generic "realistic user data" without emphasizing variety explicitly. This tends to reproduce the same statistically common patterns repeatedly, quietly recreating the poor-diversity problem.
  • Generating a fresh user for every single assertion within one test. One user per test, via the fixture, is usually the right granularity — regenerating mid-test adds unnecessary AI calls for no benefit.

Best Practices

  • Request explicit variety dimensions — name origin, address format, region — rather than a vague "realistic" request alone.
  • Wrap generation in a Playwright fixture, the way this page does, so any test can request a real user without repeating generation logic.

Hands-On Exercise

Generate 10 users with this page's function and review them by eye. Check whether they genuinely span different name origins, address formats, and states — or whether they cluster around a narrower pattern than the prompt intended.

Key Takeaways

  • Explicit variety requests in the prompt are what actually produce diverse data — a vague "realistic" request tends to converge on common patterns.
  • Wrapping generation as a Playwright fixture makes varied test data available to any test with zero added complexity per test.
