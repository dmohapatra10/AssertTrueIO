Introduction

This page builds the real, working server and client shell from the previous page's architecture. It's deliberately minimal — the genuinely interesting work, wrapping Chapter 14's actual browser tools, happens on the next page.

Step-by-Step Implementation — A Real, Minimal Server

// src/mcp-server.ts
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { StdioServerTransport } from '@modelcontextprotocol/sdk/server/stdio.js';

export const server = new McpServer({
  name: 'shopsmart-playwright-tools',
  version: '1.0.0',
});

export async function startServer() {
  const transport = new StdioServerTransport();
  await server.connect(transport);
}

Code Explanation

This is the entire server shell — genuinely just a few lines. StdioServerTransport is the simplest real transport, communicating over standard input and output, which is exactly enough for a server running locally alongside the agent that connects to it. Nothing here defines any actual tools yet — that's deliberately the next page's job, kept separate so this plumbing stays easy to follow.

Step-by-Step Implementation — A Real, Minimal Client

// src/mcp-client.ts
import { Client } from '@modelcontextprotocol/sdk/client/index.js';
import { StdioClientTransport } from '@modelcontextprotocol/sdk/client/stdio.js';

export async function connectToPlaywrightServer() {
  const transport = new StdioClientTransport({
    command: 'node',
    args: ['dist/mcp-server.js'],
  });

  const client = new Client({ name: 'shopsmart-qa-agent', version: '1.0.0' });
  await client.connect(transport);
  return client;
}

Code Explanation

The client's job here is equally simple — connect to the server process and hand back a real, usable client object. Notice this client lives inside whatever process needs to use the tools — in this chapter's case, that's Chapter 14's agent, which becomes the genuine MCP host once this client is embedded inside it.

Example — Discovering Available Tools

const client = await connectToPlaywrightServer();
const { tools } = await client.listTools();

console.log(tools.map((t) => t.name));

Why It Matters — Discovery Is a Real, Genuine Capability

Notice listTools() requires nothing hardcoded on the client side — it genuinely asks the server what's available, at runtime. This is meaningfully different from Chapter 14's BROWSER_TOOLS constant, which any client had to already know about in advance. A new client connecting to this server for the first time discovers the complete tool set without any prior knowledge of what exists.

Common Mistakes

  • Defining tools directly in this server/client setup code. Keeping tool definitions separate, as the next page does, is what keeps this plumbing genuinely minimal and easy to reason about on its own.
  • Assuming the client needs to know tool names in advance. Real discovery via listTools() is one of MCP's genuine advantages over Chapter 14's hardcoded constant — it's worth actually using, not working around.

Best Practices

  • Keep server setup, tool definitions, and client connection logic in separate files — exactly as this page and the next demonstrate.
  • Use real tool discovery via listTools() rather than hardcoding a client's expectations about what a server exposes.

Key Takeaways

  • Server and client setup code is deliberately minimal — a few lines each — with the genuinely interesting work reserved for actual tool definitions.
  • Real tool discovery via listTools() is a genuine capability beyond Chapter 14's hardcoded constant, letting any client learn what's available at runtime.
  • Keeping plumbing and tool definitions in separate files is what keeps each piece easy to reason about independently.
