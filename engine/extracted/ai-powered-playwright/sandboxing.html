Introduction — The Same Principle, a Bigger Scope

Chapter 11's validatePatchInIsolation copied a single file to a temporary directory before testing a candidate fix — a small, real act of isolation. This page applies the same principle to something bigger: the entire environment an autonomous agent runs in.

How It Works — What Genuinely Needs Isolating

NETWORK isolation — an EXPLORING agent should reach ONLY
  ShopSmart'S OWN staging environment, NEVER the real, open
  internet OR production systems it has NO genuine reason to
  touch

FILESYSTEM isolation — an agent'S container or SANDBOX should
  have NO access to the REAL, host machine'S filesystem beyond
  what its ACTUAL task genuinely requires

PROCESS isolation — running the agent in a REAL, separate
  container or VM means a GENUINE failure or compromise stays
  CONTAINED, rather than affecting the HOST system directly

Step-by-Step Implementation — A Real, Containerized Agent Run

# Dockerfile.agent-sandbox
FROM mcr.microsoft.com/playwright:v1.48.0-jammy

WORKDIR /agent
COPY package.json package-lock.json ./
RUN npm ci

COPY src/ ./src/

# NO access to the host filesystem beyond this COPIED code —
# the container'S OWN isolated filesystem is ALL this agent
# can genuinely SEE or MODIFY
ENTRYPOINT ["node", "dist/run-agent.js"]
# docker run, with EXPLICIT, real network restriction:
docker run \
  --network shopsmart-staging-only \
  --read-only \
  --tmpfs /tmp \
  -e ANTHROPIC_API_KEY \
  agent-sandbox

Code Explanation

--network shopsmart-staging-only is the real, concrete network isolation from this page's list — a custom Docker network that can only reach the staging environment, genuinely unable to reach production or the open internet regardless of what the agent's own reasoning decides to attempt. --read-only combined with a tmpfs mount for temporary files means the container's own filesystem can't be permanently modified, even by a compromised or malfunctioning process.

Why It Matters — This Matters More for Open-Ended Exploration

Chapter 5's fixed-sequence agent has a genuinely bounded, predictable set of actions. Chapter 13's exploratory agent, by design, generates novel hypotheses and explores paths nobody explicitly planned — exactly the kind of genuine unpredictability that makes real, structural isolation more valuable, not less. Sandboxing doesn't replace Chapter 13's own safety controls; it's a real, independent layer beneath them.

Common Mistakes

  • Running an autonomous agent directly on a developer's own machine, with full network and filesystem access. This page's whole point is that genuine isolation is worth the real setup cost, especially for anything with Chapter 13's open-ended behavior.
  • Assuming Chapter 13's action allowlist alone makes sandboxing unnecessary. They're independent, both-necessary layers — an allowlist governs what the agent intends to do; sandboxing limits what's genuinely possible even if something slips through.

Best Practices

  • Run any autonomous agent — especially Chapter 13's exploratory kind — in a genuinely isolated container or VM, never directly on a trusted, unrestricted machine.
  • Restrict network access explicitly to only the specific environment an agent's real task requires.

Hands-On Exercise

Key Takeaways

  • Sandboxing extends Chapter 11's single-file isolation principle to an entire agent's real runtime environment — network, filesystem, and process.
  • Genuine isolation matters more for Chapter 13's open-ended exploration than for a bounded, fixed-sequence agent, precisely because its actions are less predictable by design.
  • Sandboxing and action-level safety controls are independent, both-necessary layers — neither one substitutes for the other.
