AI Failure Analysis in CI

Introduction

Chapter 9 built a complete pipeline — evidence capture, classification, root cause, confidence, recommendation. This page's only real job is triggering it automatically the moment a CI run fails, rather than a human running it manually after noticing the failure.

Step-by-Step Implementation

# .github/workflows/ai-playwright-tests.yml (extended from
# Chapter 16's own opening page)
      - name: Run Playwright tests
        id: run_tests
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: npx playwright test
        continue-on-error: true

      - name: Analyze failures with AI
        if: steps.run_tests.outcome == 'failure'
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: node scripts/analyze-ci-failures.js

      - name: Upload failure analysis
        if: steps.run_tests.outcome == 'failure'
        uses: actions/upload-artifact@v4
        with:
          name: ai-failure-analysis
          path: test-results/failure-analysis.md

      - name: Fail the job if tests failed
        if: steps.run_tests.outcome == 'failure'
        run: exit 1

Code Explanation

continue-on-error: true on the test step is deliberate — it lets the workflow proceed to the analysis step even after a failure, rather than stopping immediately. The final step still fails the overall job, so CI correctly reports failure; the analysis simply runs first, in between.

Step-by-Step Implementation — The Analysis Script, Reusing Chapter 9 Directly

// scripts/analyze-ci-failures.js
import { analyzeFailureCompletely } from '../src/complete-failure-analysis';
import { generateMarkdownReport } from '../src/generate-failure-report';
import { readFileSync, writeFileSync } from 'fs';
import glob from 'glob';

const resultsFiles = glob.sync('test-results/**/*.json');
const reports = [];

for (const file of resultsFiles) {
  const testInfo = JSON.parse(readFileSync(file, 'utf-8'));
  if (testInfo.status !== 'failed') continue;

  const analysis = await analyzeFailureCompletely(testInfo, [], []);
  reports.push(generateMarkdownReport(testInfo.title, analysis, testInfo));
}

writeFileSync('test-results/failure-analysis.md', reports.join('\n---\n'));

Why It Matters — What Actually Changes for a Developer

Without this, a developer opening a failed CI run sees raw Playwright output — an error, maybe a stack trace — and starts investigating from scratch. With this, the same run's artifacts already contain Chapter 9's full analysis: classification, root cause, confidence, and a specific recommendation, generated automatically before anyone even opens the run.

Common Mistakes

  • Running failure analysis only when a human manually triggers it. This page's whole point is automating exactly that trigger — analysis that requires someone to remember to run it loses most of its real value.
  • Reimplementing analysis logic inside the CI script instead of calling Chapter 9's functions. analyzeFailureCompletely already exists, tested and explained — this page's script is deliberately just a thin CI wrapper around it.

Best Practices

  • Trigger failure analysis automatically on any test failure — never rely on a human remembering to run it manually.
  • Save the resulting report as a real, accessible CI artifact, so it's available to anyone reviewing the failed run later.

Hands-On Exercise

Add this page's failure analysis step to a real CI workflow, deliberately breaking a test to trigger it. Confirm the resulting artifact contains a genuine, complete analysis — not just the raw Playwright error output.

Key Takeaways

  • This page automates exactly one thing — the trigger — while reusing Chapter 9's complete analysis pipeline entirely unchanged.
  • Automatic analysis changes what a developer sees the moment they open a failed run, from raw output to a structured, reasoned explanation.
  • Saving analysis as a CI artifact makes it available to the whole team, not just whoever happened to run it manually.
