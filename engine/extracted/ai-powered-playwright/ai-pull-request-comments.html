Prerequisites: AI Failure Analysis in CI

What You'll Learn

Introduction

The previous page's analysis lives in a CI artifact — genuinely useful, but requiring a developer to navigate to it deliberately. This page moves the same content to where a developer is already looking: the pull request itself.

Step-by-Step Implementation

# .github/workflows/ai-playwright-tests.yml (extended further)
      - name: Post failure analysis as PR comment
        if: steps.run_tests.outcome == 'failure' && github.event_name == 'pull_request'
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const report = fs.readFileSync('test-results/failure-analysis.md', 'utf-8');

            const { data: comments } = await github.rest.issues.listComments({
              owner: context.repo.owner,
              repo: context.repo.repo,
              issue_number: context.issue.number,
            });
            const existing = comments.find(c => c.body.includes('<!-- ai-failure-analysis -->'));

            const body = '<!-- ai-failure-analysis -->\n## 🤖 AI Failure Analysis\n\n' + report;

            if (existing) {
              await github.rest.issues.updateComment({
                owner: context.repo.owner, repo: context.repo.repo,
                comment_id: existing.id, body,
              });
            } else {
              await github.rest.issues.createComment({
                owner: context.repo.owner, repo: context.repo.repo,
                issue_number: context.issue.number, body,
              });
            }

Code Explanation

The hidden <!-- ai-failure-analysis --> marker is the genuinely important detail — it's how the script recognizes its own previous comment on a later push, updating it in place rather than posting a new comment every single time. Without this, a PR with several pushes would accumulate a growing wall of near-duplicate comments, which teams learn to scroll past rather than read.

Why It Matters — Placement Genuinely Changes Whether Analysis Gets Read

An artifact a developer has to deliberately seek out competes with everything else demanding their attention during a busy day; a comment already sitting in the PR they're already reviewing does not. This isn't a cosmetic difference — it's the real, practical reason this page exists as a separate step from the previous one, rather than treating the artifact as sufficient on its own.

Common Mistakes

  • Posting a new comment on every push without checking for an existing one. This page's marker-based update logic exists specifically to prevent comment spam that trains a team to ignore these comments entirely.
  • Posting the full, raw analysis with no formatting. Markdown rendering in the PR comment (headers, emoji, links) is what makes this genuinely scannable — the same discipline Chapter 9's report page established.

Best Practices

  • Always check for and update an existing comment rather than posting a new one on every run — the marker-comment pattern this page uses is a reliable way to do this.
  • Keep the comment itself as scannable as Chapter 9's original markdown report — this is the same content, just relocated to somewhere more visible.

Hands-On Exercise

Add this page's PR comment step to a real workflow, triggering it with a deliberately failing test across two separate pushes to the same PR. Confirm the second push updates the existing comment rather than creating a duplicate.

Key Takeaways

  • Posting analysis directly as a PR comment puts it where a developer is already looking, rather than requiring a separate, deliberate navigation step.
  • A hidden marker comment is what enables updating in place across multiple pushes, preventing comment spam that would otherwise get ignored.
  • Where analysis appears is not a cosmetic detail — it's a real, practical factor in whether it actually gets read at all.
