Why It Matters — Explicit Ownership Prevents Real Confusion

Once the checkout team, search team, and a platform team all depend on the same shared MCP server, "who fixes it when the server itself breaks" needs a real, unambiguous answer. This table is exactly that — every component has one clear owner, traceable to the chapter that actually built it, rather than a shared system nobody feels individually responsible for.

Example — A Real, Concrete Ownership Model for ShopSmart

PLATFORM team owns: MCP Server, CI/CD Pipeline, Evidence
  Storage, Audit Log — the SHARED infrastructure every team
  depends ON

EACH product team owns: its OWN agent's objectives, its OWN
  tool allowlist SCOPE, its OWN human approval QUEUE for its
  OWN team's proposed CHANGES

BOTH share responsibility for: the human APPROVAL discipline
  itself — no team GETS an exception to Chapter 11'S rule,
  regardless of WHICH team's infrastructure a change touches

Common Mistakes

  • Leaving shared infrastructure ownership ambiguous "since everyone uses it." This page's ShopSmart example shows why that's exactly backwards — shared infrastructure needs a clearer owner, not a less clear one, since no single team feels naturally responsible for it otherwise.
  • Assuming a product team can bypass the shared approval discipline for their own agent's proposed changes. Chapter 11's rule applies to every proposed change, regardless of which team's agent generated it — this is explicitly a shared, non-negotiable responsibility.

Best Practices

  • Write down an explicit ownership model for your own system, following this page's platform-team-versus-product-team split as a starting template.
  • Keep the human-approval discipline itself as a shared, universal responsibility no team gets to opt out of.

Hands-On Exercise

For your own real or planned system, following this page's overview diagram, write down who genuinely owns each component. Identify any component where ownership is currently ambiguous, and consider what would happen if it broke.

Key Takeaways

  • Every component in this track's system traces to a specific chapter, and deserves an equally specific, real owner in any actual deployment.
  • Shared infrastructure needs clearer ownership than team-specific components, not less — ambiguity here is a real, common failure mode.
  • The human-approval discipline from Chapter 11 remains a shared, universal responsibility across every team, with no exceptions based on whose agent proposed a change.
