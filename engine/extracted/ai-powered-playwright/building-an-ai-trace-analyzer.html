Step-by-Step Implementation

// src/trace-analyzer.ts
import { extractTraceActions } from './extract-trace-data';
import { extractNetworkEvents } from './extract-trace-network';
import { findFailedAction, resolveAmbiguousFailurePoint } from './find-failed-action';
import { analyzeTraceTimeline } from './analyze-trace-with-ai';
import { askClaude } from './ai-client';

export interface TraceAnalyzerResult {
  failedActionIndex: number;
  timelineSummary: string;
  rootCause: string;
  recommendation: string;
}

export async function analyzeTrace(
  traceZipPath: string
): Promise<TraceAnalyzerResult> {
  // Trace → structured data
  const actions = extractTraceActions(traceZipPath);
  const networkEvents = extractNetworkEvents(traceZipPath);

  // Find the failed step — deterministic first, AI only if
  // genuinely ambiguous (Chapter 10's own rule)
  const errorActions = actions
    .map((a, i) => ({ a, i }))
    .filter(({ a }) => a.error);

  let failedActionIndex: number;
  if (errorActions.length === 1) {
    failedActionIndex = errorActions[0].i;
  } else {
    const resolved = await resolveAmbiguousFailurePoint(
      actions, errorActions.map(({ i }) => i)
    );
    failedActionIndex = resolved.primaryFailureIndex;
  }

  // AI Analysis, across the full sequence
  const timelineAnalysis = await analyzeTraceTimeline(actions);

  // Root Cause + Recommendation
  const recommendationPrompt = `Failed action: ${JSON.stringify(actions[failedActionIndex])}
Timeline analysis: ${timelineAnalysis.likelyCause}
Related network events: ${JSON.stringify(networkEvents.slice(0, 5))}

Give ONE specific, concrete recommended action for a developer
investigating this failure.

Respond with ONLY the recommendation text.`;
  const recommendation = await askClaude(recommendationPrompt);

  return {
    failedActionIndex,
    timelineSummary: timelineAnalysis.summary,
    rootCause: timelineAnalysis.likelyCause,
    recommendation,
  };
}

Common Mistakes

  • Skipping the deterministic-first check and always calling AI for failure-point resolution. Most real traces have exactly one failed action — this chapter's own rule exists specifically to keep the common case fast and free of unnecessary AI calls.
  • Discarding the extracted network events after finding the failed action. They remain genuinely useful context for the final recommendation, as this page's recommendationPrompt shows.

Best Practices

  • Keep every stage of this pipeline calling this chapter's own, already-built, tested functions — resist rewriting logic inline during assembly.
  • Log intermediate results (which action failed, the timeline summary) even when only the final recommendation is what a report ultimately surfaces — useful for debugging the analyzer itself.

Interview Questions

Beginner: What is the genuine difference between a trace file and a single failure screenshot?▾

A screenshot captures one moment — what the page looked like at the instant of failure. A trace captures an entire, ordered timeline — every action, its timing and duration, every network request, and DOM snapshots at multiple points throughout the run. A screenshot shows the outcome; a trace shows the full sequence that led there.

Beginner: Why does this chapter recommend finding the failed action with a deterministic search rather than an AI call, in the common case?▾

When exactly one action in the timeline has a recorded error, finding it is an exact operation with one correct answer — searching for the action where the error field is populated. This is the same kind of deterministic question Chapter 5 established doesn't need AI reasoning; using AI here would add real cost and latency for a question the data already answers directly.

Intermediate: Explain why sequence-aware trace analysis can rule out explanations that Chapter 9's single-error analysis couldn't.▾

Chapter 9's analysis worked from an error message and a few stack frames — it had no visibility into what happened before the failure. Trace analysis sees the full sequence, so if every action before the failure completed normally, with no errors and typical durations, that directly rules out a cascading earlier problem as the cause. This kind of elimination is only possible because the full timeline, not just the final error, is available for reasoning.

Intermediate: Why does correlateNetworkWithActions check for network failures within a time window of an action's timestamp, rather than requiring an exact timestamp match?▾

A network request that's genuinely related to a given action rarely completes at the exact same millisecond — a click might trigger a request that resolves shortly after, or a request might be in flight when a subsequent action begins. Requiring an exact match would miss almost every genuinely related failure. A reasonable time window (this page uses 500ms) captures requests that are plausibly connected to an action without being so wide that it correlates clearly unrelated events happening to occur near each other in time.

Advanced: Why does resolveAmbiguousFailurePoint explicitly ask the model to consider whether some candidate failures are "downstream consequences," rather than just asking it to pick the most severe one?▾

Severity alone doesn't indicate causation. An early network failure and a later timeout might both look like genuine problems, but the later one could simply be a consequence of the earlier one — the page never loaded correctly because a request failed, and everything after that was doomed regardless of how it's individually described. Asking specifically about downstream consequences directs the model's reasoning toward the actual causal structure of the sequence, rather than toward whichever failure happens to sound worse in isolation — a genuinely different and more useful question for identifying where a fix actually needs to be applied.

Scenario-based: A teammate wants to skip Chapter 10's manual trace-viewer exercise and go straight to building the automated analyzer, reasoning it's faster. How would you respond?▾

I'd point to why this chapter placed that exercise first: building real intuition for what's genuinely valuable inside a trace — an unexpectedly long action, a network failure near a specific step, an earlier screenshot revealing an unexpected modal — is what shapes good judgment about what the automated pipeline should extract and prioritize. Skipping straight to automation risks building an analyzer around assumptions about trace data that were never actually verified against a real, messy trace. The manual exercise costs a small amount of time upfront and pays for itself the first time the automated analyzer produces a result that doesn't match what a human would have concluded — at that point, having actually explored a trace by hand makes it much easier to tell whether the analyzer or the assumption behind it is what's wrong.
