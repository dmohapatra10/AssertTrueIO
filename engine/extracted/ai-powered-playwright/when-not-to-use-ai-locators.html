How It Works — Real Cases Where Healing Is the Wrong Call

1. WRITING a NEW test for the FIRST time
   → Just WRITE a good locator, following Chapter 6's OWN
     opening page. Healing exists for locators that BREAK
     later — it's not a substitute for writing one WELL now.

2. The SAME locator needs healing REPEATEDLY, on EVERY run
   → This is a genuine SIGNAL the underlying locator strategy
     is FUNDAMENTALLY unstable, not that healing needs to run
     MORE often. Fix the ROOT locator; don't keep patching it.

3. A CRITICAL, high-stakes flow (payment, checkout)
   → A HEALED locator here deserves EXTRA human scrutiny, not
     LESS — Chapter 19's later security chapter treats
     payment-adjacent code with EXACTLY this kind of extra
     care.

4. The APPLICATION genuinely has a BUG, not a locator problem
   → If the "Add to Cart" button is GENUINELY missing, no
     locator strategy will EVER find it — healing can't fix a
     REAL application defect, only a CHANGED, but STILL
     present, element.

Why It Matters — Frequent Healing Is a Warning Sign

A healthy test suite heals locators rarely — an occasional, genuine application change. A suite that heals the same locator every single run is telling you something real: the underlying strategy is fundamentally unstable, likely a text-based locator on frequently-changing content, exactly the kind of choice Chapter 6's opening page warned against. The fix there is writing a better locator, following that page's stability ranking — not running healing more aggressively.

Example — Case 4, Concretely

ShopSmart's checkout genuinely has a bug: the payment submit button fails to render under a specific combination of discount codes. Running this chapter's healing pipeline against the resulting locator failure will correctly report "no candidate validated" — because there's genuinely nothing to find. This is the pipeline working correctly, not failing — a locator healing tool that always finds SOMETHING, even when the application is genuinely broken, would be actively hiding a real defect.

Common Mistakes

  • Reaching for AI locator suggestions as the default way to write new tests. This chapter's opening page's fundamentals are the right starting point every time — healing is specifically for locators that later break.
  • Treating frequent healing activity as evidence the pipeline is working well. It's usually the opposite — a genuine signal of an unstable underlying locator strategy worth fixing directly.

Best Practices

  • Track how often healing runs, and on which locators — frequent healing on the same element is a real, actionable signal, not background noise.
  • Give extra scrutiny to any healed locator on a critical flow — the cost of a wrong locator there is genuinely higher than elsewhere.

Hands-On Exercise

Review your own test suite's locator failures, if you're tracking them, or think through your recent testing experience. Identify whether any recurring failure fits this page's case 2 (same locator, healed repeatedly) — and if so, write the better, more stable locator that should replace it, rather than relying on continued healing.

Key Takeaways

  • Locator healing is a genuine safety net for good locators that occasionally break — never a substitute for writing them well in the first place.
  • Frequent healing on the same locator is a real warning sign pointing at an unstable strategy, not evidence the healing pipeline is succeeding.
  • Healing correctly reports failure when an application genuinely has a bug — that's the pipeline working as intended, not a limitation to work around.

Interview Questions

Beginner: Why does this chapter open with a page on Playwright locator best practices, with no AI involved at all?▾

Because locator healing exists to handle locators that break after being written well — it's a safety net, not a starting point. Understanding what a genuinely stable locator looks like first is what makes the rest of the chapter's healing techniques make sense as a backup, rather than as the default way to write a new locator in the first place.

Beginner: What is the real difference between locator ranking and locator validation in this chapter's pipeline?▾

Ranking is a prediction based on strategy type — testId-based locators are ranked higher because they're generally more stable. Validation is an empirical check against the real, current page — confirming a specific candidate actually exists and uniquely matches one element right now. Ranking says what's likely best; validation confirms what's actually true.

Intermediate: Why does locator candidate generation explicitly request different strategies (role-based, testId-based, text-based), rather than simply asking for "three suggestions"?▾

Different strategies fail independently. If three candidates were all minor variations of the same role-based approach, a single underlying cause — like another accessible-name change — could break all three at once. Genuinely different strategies mean that if one breaks again later, the others likely still work, providing real, independent alternatives rather than the illusion of choice.

Intermediate: Why does validateCandidate check both existence and uniqueness as two separate conditions, rather than one combined check?▾

They're genuinely different failure modes with different implications. A locator matching zero elements means the candidate is wrong or stale — nothing to interact with. A locator matching several elements means the candidate is too broad — Playwright would either throw a strict-mode error or, worse, interact with an unintended element. Separating these into exists and isUnique means a failure's specific cause is immediately clear, rather than hidden behind one generic "invalid" result.

Advanced: Why does healLocator deliberately stop at returning a working locator, rather than automatically updating the test file that used the broken one?▾

Automatically rewriting source code is a meaningfully bigger, riskier decision than suggesting a replacement — it means trusting the entire pipeline's output enough to modify a file without human review, silently. Even with genuine, empirical validation at each stage, this chapter's pipeline can still be wrong in ways validation doesn't catch — a uniquely-matching element that happens to be the wrong one for reasons the validation logic can't detect, for instance. Keeping the human review step explicit and separate, as Chapter 11 does deliberately, means a mistake surfaces as a suggestion a person can reject, not a silent, automatic change to test code.

Scenario-based: A teammate notices the healing pipeline runs successfully on the same "Submit Order" button locator every single day and considers this a sign the system is working well. How would you respond, using this chapter's own reasoning?▾

I'd point directly to this page's own warning: healing succeeding doesn't mean the same thing as healing being unnecessary. A locator that needs healing every single day isn't a stable locator being occasionally rescued — it's a fundamentally unstable one being continuously patched over, and given this is described as a critical "Submit Order" button, that instability deserves real concern, not reassurance. The right response is investigating why this specific locator keeps breaking — likely a text-based or otherwise fragile strategy on frequently-changing content — and replacing it with something genuinely stable, following this chapter's opening page's ranking, rather than treating repeated healing as a success metric for a high-stakes checkout flow.
