Deterministic AI Test Data

Introduction

Every generation function in this chapter so far returns something genuinely different each time it's called — that's the whole point of AI-generated variety. This page is about the real problem that creates: a test that fails today, using data generated fresh, may be impossible to reproduce tomorrow, because tomorrow's generated data is different.

Why It Matters — A Concrete Debugging Problem

MONDAY: test fails with a GENERATED user whose LAST name
        contains an apostrophe ("O'Brien") — a REAL, genuine
        bug in ShopSmart's name-handling logic

TUESDAY: a developer tries to REPRODUCE the failure, runs the
         SAME test — a NEW user gets GENERATED, WITHOUT an
         apostrophe this time — the test PASSES, and the REAL
         bug looks like it "went AWAY" on its OWN

The bug never actually went away — the specific data that triggered it simply wasn't generated again. This is a genuine, real cost of using fresh AI generation for every test run, worth solving deliberately rather than accepting as an unavoidable tradeoff.

Step-by-Step Implementation — Generate Once, Cache, Reuse

// src/cached-test-data.ts
import { readFileSync, writeFileSync, existsSync } from 'fs';
import { generateUsers, GeneratedUser } from './generate-user-data';

const CACHE_PATH = 'test-data/cached-users.json';

export async function getCachedUsers(
  count: number, forceRegenerate = false
): Promise<GeneratedUser[]> {
  if (existsSync(CACHE_PATH) && !forceRegenerate) {
    const cached = JSON.parse(readFileSync(CACHE_PATH, 'utf-8'));
    if (cached.length >= count) return cached.slice(0, count);
  }

  const fresh = await generateUsers(count);
  writeFileSync(CACHE_PATH, JSON.stringify(fresh, null, 2), 'utf-8');
  return fresh;
}

Code Explanation

This is deliberately simple — no database, no special infrastructure, just a JSON file checked into the same repository as the tests that use it. That's a real, intentional choice: the cached data becomes reviewable and versioned alongside the code, the same way any other test fixture would be, and forceRegenerate gives an explicit, deliberate way to refresh it when genuinely needed.

Example — Reproducing Monday's Failure, Reliably

// MONDAY, first run — generates FRESH, caches the result:
const users = await getCachedUsers(5);
// Includes the "O'Brien" user that TRIGGERED the bug

// TUESDAY, a developer investigating:
const sameUsers = await getCachedUsers(5);
// Returns the EXACT SAME cached data — "O'Brien" is STILL
// there, the bug reproduces RELIABLY, every single time

Why It Matters — Committing the Cache Deliberately

Checking test-data/cached-users.json into version control means the whole team shares the same test data, and a git diff shows exactly when and why it changed — genuinely different from silent, fresh generation on every run, where nobody can tell whether today's data matches yesterday's without checking by hand.

Common Mistakes

  • Regenerating fresh data on every single test run "to maximize variety." This page's Monday/Tuesday example shows the real cost — genuine bugs that look like they disappeared on their own.
  • Never regenerating the cache at all. Stale cached data eventually recreates the original staleness problem from this chapter's first page — forceRegenerate exists for deliberate, periodic refresh.

Best Practices

  • Cache generated data once, commit it to version control, and reuse it deterministically across runs — reserve fresh generation for deliberate refresh cycles.
  • When a test fails against cached data, keep the exact failing cache alongside the bug report — it's the most direct way to reproduce the issue later.

Hands-On Exercise

Apply this page's caching pattern to one of your own generation functions from earlier in this chapter. Run it twice and confirm the second run returns identical data. Then call it with forceRegenerate: true and confirm it genuinely produces something new.

Key Takeaways

  • Fresh AI generation on every run makes test failures genuinely hard to reproduce — a real, practical cost worth solving deliberately.
  • Caching generated data once and committing it to version control makes test data reviewable, shared, and genuinely reproducible.
  • Regeneration should be a deliberate, explicit choice, not an automatic default on every run.
