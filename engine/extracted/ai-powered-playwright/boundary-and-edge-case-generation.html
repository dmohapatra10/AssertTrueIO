Boundary and Edge Case Generation

Prerequisites: Happy Path and Negative Test Generation

What You'll Learn

  • Why boundary and edge cases are genuinely distinct from negative tests, not a subset of them
  • Generating boundary values for ShopSmart's cart quantity field
  • Generating edge cases — unusual but genuinely valid combinations

Introduction

The previous page's negative tests used clearly invalid input — an empty field, a wrong password. Boundary and edge cases are different: the input is genuinely valid, just at an extreme or unusual point most people don't think to test. This distinction matters because it changes what "correct behavior" even means — a boundary case should usually still succeed, not fail.

How It Works — Boundary Values

export async function generateBoundaryCases(
  fieldName: string, validRange: string, featureContext: string
): Promise<TestCase[]> {
  const prompt = `Field: "${fieldName}", valid range: ${validRange}
Feature context: ${featureContext}

Generate BOUNDARY test cases — values AT the edges of the
valid range, and just OUTSIDE it. For a range of 1 to 99:
include 1, 99 (should succeed), and 0, 100 (should fail).
Don't generate deep-interior values like 50 — this is
specifically about the EDGES.

Respond with ONLY valid JSON: {"testCases": [...]}
Each: {"id": string, "category": "boundary", "name": string,
"steps": string[], "expected": string}`;

  const raw = await askClaude(prompt);
  const parsed = JSON.parse(raw);
  if (!Array.isArray(parsed.testCases)) {
    throw new Error(`Expected {"testCases": [...]} but got: ${raw.slice(0, 200)}`);
  }
  return parsed.testCases;
}

Example — ShopSmart's Cart Quantity Field

const cases = await generateBoundaryCases(
  'cart item quantity', '1 to 99',
  'ShopSmart limits quantity per item to 99 to prevent bulk-order abuse.'
);

// Real output includes:
// { name: "Quantity of 1 (minimum valid)", expected: "Succeeds,
//   item added with quantity 1" }
// { name: "Quantity of 99 (maximum valid)", expected: "Succeeds,
//   item added with quantity 99" }
// { name: "Quantity of 0", expected: "Rejected with a clear
//   validation message" }
// { name: "Quantity of 100", expected: "Rejected with a clear
//   validation message" }

How It Works — Edge Cases

export async function generateEdgeCases(
  requirement: string, featureContext: string
): Promise<TestCase[]> {
  const prompt = `Requirement: "${requirement}"
Feature context: ${featureContext}

Generate EDGE cases — unusual but genuinely VALID combinations
a typical tester might not think of first. NOT invalid input —
combinations of otherwise-valid actions or states that are
uncommon. Example shape: applying a discount code to an
already-discounted item, or adding the same product twice in
quick succession.

Respond with ONLY valid JSON: {"testCases": [...]}
Each: {"id": string, "category": "edge-case", "name": string,
"steps": string[], "expected": string}`;

  const raw = await askClaude(prompt);
  const parsed = JSON.parse(raw);
  if (!Array.isArray(parsed.testCases)) {
    throw new Error(`Expected {"testCases": [...]} but got: ${raw.slice(0, 200)}`);
  }
  return parsed.testCases;
}

Why It Matters

ShopSmart's checkout might correctly handle "apply one discount code" and correctly handle "add an item twice" separately — but genuinely mishandle applying a discount code, then removing and re-adding the discounted item, because nobody tested that specific, unusual-but-valid combination. This is exactly the category edge-case generation targets, and exactly why it's kept genuinely distinct from negative testing — the goal isn't rejection, it's correct handling of a real, valid, uncommon path.

Common Mistakes

  • Merging boundary and negative categories. A boundary value at the valid edge should succeed — treating it like a negative case leads to writing the wrong expected result.
  • Generating edge cases with a vague prompt like "find weird bugs." This page's example shape ("applying a discount code to an already-discounted item") gives the model something concrete to reason from, directly following Chapter 2's specificity principle.

Best Practices

  • Keep boundary, negative, and edge-case generation as separate requests with separate, category-appropriate expected results — don't conflate what "correct" means across them.
  • Give edge-case generation a concrete example of the kind of unusual combination you mean — abstract requests produce abstract, less useful results.

Hands-On Exercise

Identify a numeric or bounded field in your own application (a quantity, a character limit, a date range). Run this page's generateBoundaryCases against it, then write, by hand, one edge case combining that field with another feature — compare it against what generateEdgeCases produces for the same area.

Key Takeaways

  • Boundary and edge cases use genuinely valid input, unlike negative tests — the expected result is usually success, not rejection.
  • Boundary testing targets the edges of a defined range; edge-case testing targets unusual but valid combinations across features.
  • Concrete examples in the generation prompt meaningfully improve edge-case quality, the same specificity principle from Chapter 2 applied here.
