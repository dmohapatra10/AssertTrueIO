Step-by-Step Implementation

// src/capstone-pipeline.ts (stage 4)
import { analyzeRootCause } from './root-cause-analysis';
import { proposeAssertionFix } from './generate-assertion-fix';
import { buildCandidatePatch, formatAsDiff } from './build-candidate-diff';

export async function findRootCauseAndProposeFix(
  payload: AnalysisPayload, classification: Classification
) {
  const rootCause = await analyzeRootCause(payload, classification);

  // THIS is a genuine APPLICATION bug, not an assertion that
  // needs updating — Chapter 11'S own assertion-healing page
  // exists PRECISELY to distinguish this from a legitimate
  // business CHANGE, and the evidence here points CLEARLY to
  // a real DEFECT, not a business RULE update
  const patch = buildCandidatePatch(
    [], // no LOCATOR fix needed here
    [], // this is NOT an assertion-healing case — it's a REAL
        // application code fix, handled by the DEVELOPMENT
        // team, not this FRAMEWORK
    'src/discount-calculator.ts'
  );

  return { rootCause, patch: formatAsDiff(patch) };
}

Code Explanation

Notice this stage's honest limit: Chapter 11's self-healing pipeline was built for test-file fixes — locators and assertions — not application source code. The discount-stacking bug lives in ShopSmart's own discount-calculator.ts, genuinely outside this framework's real, intended scope. This stage's real, honest output is a complete diagnosis and a clear report for the development team, not an automatic application-code patch this framework was never built to safely generate.

Why It Matters — An Honest Boundary, Not a Limitation to Hide

This capstone could have pretended to generate an automatic application-code fix, the way Chapter 11's pipeline does for test files. Being honest about this real boundary — this framework diagnoses and reports application defects, it doesn't autonomously patch application source code — is exactly the same honesty this track has practiced since Chapter 1's treatment of what AI can and cannot do.

Common Mistakes

  • Extending Chapter 11's self-healing pipeline to autonomously patch application source code. This chapter's own boundary is deliberate — application logic fixes belong to the development team, with this framework's real, honest job being diagnosis and clear reporting.
  • Treating a thorough root cause analysis as equivalent to an actual fix. The diagnosis is genuinely valuable on its own — it doesn't need to pretend to be more than that.

Best Practices

  • Be explicit about what an autonomous framework can and cannot safely fix — test-file issues versus application source code are genuinely different scopes.
  • Deliver a complete, evidence-grounded diagnosis even when an automatic fix isn't appropriate — this is real, valuable output on its own.
