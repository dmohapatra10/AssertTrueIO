Intelligent Test Selection

Prerequisites: AI Pull Request Comments

What You'll Learn

  • Why running the entire suite on every single pull request is a genuine, real cost
  • Selecting only the tests a specific change actually affects
  • Being honest about the real risk this technique introduces

Introduction

Running the full AI-powered suite on every pull request is safe but genuinely wasteful — a one-line copy change to a checkout error message doesn't need the wishlist, profile, and newsletter tests re-run alongside it. This page is about selecting deliberately, not running everything by default.

Step-by-Step Implementation

// src/select-affected-tests.ts
import { execSync } from 'child_process';
import { askClaude } from './ai-client';

export function getChangedFiles(baseBranch: string): string[] {
  const output = execSync(`git diff --name-only ${baseBranch}...HEAD`, { encoding: 'utf-8' });
  return output.split('\n').filter(Boolean);
}

export async function selectAffectedTests(
  changedFiles: string[], allTestFiles: string[]
): Promise<string[]> {
  const prompt = `Changed files in this pull request:
${JSON.stringify(changedFiles)}

Available test files:
${JSON.stringify(allTestFiles)}

Select ONLY the test files that genuinely test functionality
related to these changes. Err toward including a test if you're
GENUINELY uncertain whether it's related.

Respond with ONLY valid JSON: {"testFiles": [string, ...]}`;

  const raw = await askClaude(prompt);
  return JSON.parse(raw).testFiles;
}

Code Explanation

"Err toward including a test if you're genuinely uncertain" is a deliberate, important instruction — the real cost of running one unnecessary test is small; the real cost of skipping a test that would have caught a genuine regression is much larger. This asymmetry shapes the whole prompt, biasing selection toward safety over minimal runtime.

Example — A Real Selection for a ShopSmart Change

const changed = getChangedFiles('main');
// ["src/components/DiscountCodeField.tsx", "src/api/discount-validate.ts"]

const selected = await selectAffectedTests(changed, allTestFiles);
// ["tests/cart.spec.ts", "tests/checkout.spec.ts"]
// NOT selected: tests/wishlist.spec.ts, tests/profile.spec.ts,
// tests/newsletter.spec.ts — GENUINELY unrelated to a discount
// code CHANGE

Why It Matters — Being Honest About the Real Risk

This technique genuinely trades some safety for real speed and cost savings — a wrong selection could miss a test that would have caught a real, genuine bug, in a way that "run everything" never could. This is worth stating plainly rather than glossing over: intelligent selection is a real tradeoff, appropriate for fast pull-request feedback, not necessarily for a release-gating run where the cost of missing something is much higher.

Common Mistakes

  • Using intelligent selection for every single CI run, including release gates. This page's own honesty about the tradeoff matters here — a release gate deserves the full, safer suite, not a selected subset.
  • Trusting selection without ever validating it against a known case. Periodically running the full suite alongside a selected one, and comparing results, is a real way to catch a selection strategy that's missing something important.

Best Practices

  • Use intelligent selection for fast, per-push feedback; run the complete suite for anything release-gating, following this page's own honest risk assessment.
  • Periodically validate selection accuracy by comparing it against full-suite runs, rather than trusting it indefinitely without checking.

Key Takeaways

  • Running the entire suite on every pull request is safe but genuinely wasteful — most changes only affect a small, identifiable part of the application.
  • Biasing selection toward inclusion when genuinely uncertain reflects the real asymmetry between the cost of an unnecessary test and the cost of a missed regression.
  • Intelligent selection is an honest tradeoff appropriate for fast feedback, not a safe substitute for the full suite on a release-gating run.
