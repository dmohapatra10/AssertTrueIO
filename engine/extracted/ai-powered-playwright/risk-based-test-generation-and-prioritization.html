How It Works — Ranking by Genuine Business Risk

export interface PrioritizedCase extends TestCase {
  riskScore: number;
  riskReason: string;
}

export async function prioritizeByRisk(
  testCases: TestCase[], businessContext: string
): Promise<PrioritizedCase[]> {
  const prompt = `Business context: ${businessContext}

Test cases to prioritize:
${JSON.stringify(testCases, null, 2)}

For each test case, assign a riskScore from 1 (low) to 5
(high) based on: how central this is to revenue, how often
this path is used by real users, and how severe a real
failure here would genuinely be. Include a one-sentence
riskReason for each score.

Respond with ONLY valid JSON:
{"prioritized": [{"id": string, "riskScore": number,
"riskReason": string}]}`;

  const raw = await askClaude(prompt);
  const parsed = JSON.parse(raw);
  const scoreMap = new Map(
    parsed.prioritized.map((p: any) => [p.id, p])
  );
  return testCases
    .map((tc) => ({
      ...tc,
      riskScore: scoreMap.get(tc.id)?.riskScore ?? 1,
      riskReason: scoreMap.get(tc.id)?.riskReason ?? 'Not scored',
    }))
    .sort((a, b) => b.riskScore - a.riskScore);
}

Code Explanation

The ?? 1 fallback matters more than it looks — if the model's response is missing a score for some test case (a genuine, real possibility with any AI-generated response), that case defaults to the lowest risk rather than crashing the whole function or silently vanishing from the list. This is the same defensive validation discipline from Chapter 3, applied to a new failure mode.

Example — Applying It to Checkout's Negative Cases

const ranked = await prioritizeByRisk(
  negativeCheckoutCases,
  'ShopSmart is an e-commerce app; checkout directly drives revenue. A broken checkout with a large user base losing money is the highest-severity category of failure.'
);

// A REAL, plausible ranking:
// riskScore 5: "Attempt checkout with invalid payment card
//   number" — directly blocks revenue if handled wrong
// riskScore 3: "Attempt checkout with expired session" —
//   real, but recoverable, less frequent
// riskScore 2: "Attempt checkout with unusually long address
//   field" — real edge case, low real-world frequency

Why It Matters — Combining Priority with a Real Constraint

function selectWithinBudget(
  ranked: PrioritizedCase[], maxCases: number
): PrioritizedCase[] {
  return ranked.slice(0, maxCases);
}

// A CI run with only 10 minutes of budget for THIS feature's
// negative tests runs the TOP-ranked cases first — genuinely
// prioritizing what matters most, not just running the FIRST
// ten cases that happened to be GENERATED

Common Mistakes

  • Running test cases in generation order rather than risk order. Generation order reflects nothing about real importance — it's just the order the model happened to produce them in.
  • Treating a low riskScore as "don't ever test this." It means "not always, every run" — Chapter 16's intelligent test selection covers exactly how to decide when a lower-priority case still deserves a run.

Best Practices

  • Give the model real business context — revenue impact, usage frequency — the same way you'd brief a new team member on what actually matters most.
  • Always include a defensive fallback for a missing score, the same discipline Chapter 3 established for any AI response your code depends on.

Hands-On Exercise

Take the boundary and edge cases you generated in this chapter's earlier pages and run them through prioritizeByRisk, with real business context for your own application. Check whether the ranking matches your own intuition — and if it doesn't, consider whether your businessContext was specific enough.

Key Takeaways

  • Generation across five categories easily outpaces what's realistic to run every time — prioritization is a genuinely separate, necessary skill.
  • Risk-based ranking uses real business context — revenue impact, usage frequency, failure severity — not arbitrary generation order.
  • Combining a risk ranking with an execution budget is what actually makes generation practical at scale, setting up Chapter 16's CI-specific test selection.
