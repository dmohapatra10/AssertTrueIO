Introduction — Where AI Genuinely Earns Its Place

The previous page confirmed a test is genuinely flaky, deterministically. This page tackles the harder question that deterministic code can't answer alone: why. This is where AI reasoning belongs in this chapter, and this page's real technique goes further than a text-based guess — it compares actual trace data from a real passing run against a real failing run of the same test.

Step-by-Step Implementation — Reusing Chapter 10's Extraction

// src/diff-flaky-traces.ts
import { extractTraceActions, TraceAction } from './extract-trace-data';
import { askClaude } from './ai-client';

export interface TraceDiff {
  actionsOnlyInFailing: TraceAction[];
  durationDifferences: { actionType: string; passingMs: number; failingMs: number }[];
}

export function diffTraces(
  passingTracePath: string, failingTracePath: string
): TraceDiff {
  const passing = extractTraceActions(passingTracePath);
  const failing = extractTraceActions(failingTracePath);

  const actionsOnlyInFailing = failing.filter((f) =>
    !!f.error && !passing.some((p) => p.type === f.type && p.selector === f.selector)
  );

  const durationDifferences = passing
    .map((p, i) => {
      const matching = failing[i];
      if (!matching || matching.type !== p.type) return null;
      return { actionType: p.type, passingMs: p.durationMs, failingMs: matching.durationMs };
    })
    .filter((d): d is NonNullable<typeof d> => d !== null && Math.abs(d.passingMs - d.failingMs) > 500);

  return { actionsOnlyInFailing, durationDifferences };
}

Code Explanation

This directly reuses extractTraceActions from Chapter 10 — nothing new for reading trace files, only new logic for comparing two of them. durationDifferences specifically looks for actions that took meaningfully longer in the failing run, a genuine, concrete signal for network variance or animation timing, two of Chapter 12's own recurring causes.

Step-by-Step Implementation — Classification Using the Real Diff

export type FlakyCause =
  | 'race-condition' | 'animation-timing' | 'network-variance'
  | 'test-order-dependence' | 'shared-state';

export interface FlakyClassification {
  cause: FlakyCause;
  severityScore: number;
  reasoning: string;
}

export async function classifyFlakyTest(
  diff: TraceDiff, testName: string
): Promise<FlakyClassification> {
  const prompt = `Flaky test: "${testName}"

Trace comparison between a passing and failing run of the
SAME test:
Actions with errors only in the failing run: ${JSON.stringify(diff.actionsOnlyInFailing)}
Actions with meaningfully different durations: ${JSON.stringify(diff.durationDifferences)}

Classify the likely cause as ONE of: race-condition,
animation-timing, network-variance, test-order-dependence,
shared-state. Score severity 1-5 based on how often this
appears to occur and how central the affected action is.

Respond with ONLY valid JSON:
{"cause": string, "severityScore": number, "reasoning": string}`;

  const raw = await askClaude(prompt);
  return JSON.parse(raw);
}

Example — A Real, Trace-Grounded Classification

const diff = diffTraces('traces/checkout-pass.zip', 'traces/checkout-fail.zip');
const classification = await classifyFlakyTest(diff, 'completes checkout with valid payment');

Why It Matters

This classification isn't a guess from a text description of the problem — it's grounded in an actual, measured difference between two real runs of the same test. This is genuinely more trustworthy than analysis based on a single failure's error message alone, and it's a technique unique to this track, made possible by Chapter 10's trace extraction work.

Common Mistakes

  • Classifying a flaky test from a single failing trace alone. Without a passing trace for comparison, there's no genuine baseline — this page's whole technique depends on having both.
  • Ignoring duration differences under the threshold. This page's 500ms threshold is a reasonable default, but a suite with tighter timing margins might need a smaller one to catch genuinely meaningful variance.

Best Practices

  • Save at least one passing trace for every test that ends up flagged as flaky — without it, this page's real diffing technique isn't possible.
  • Adjust the duration-difference threshold to your own suite's actual timing characteristics, rather than trusting this page's default blindly.

Hands-On Exercise

For a real or simulated flaky test in your own project, capture both a passing and a failing trace. Run this page's diffTraces function and review the results by eye before running the AI classification — confirm the classification's reasoning genuinely matches what you see in the diff yourself.

Key Takeaways

  • Diagnosing why a test is flaky is where AI reasoning genuinely earns its place, after deterministic code already confirmed the test is flaky at all.
  • Comparing actual passing and failing traces, reusing Chapter 10's extraction, grounds this diagnosis in real, measured evidence rather than a guess.
  • Severity scoring lets a team prioritize which flaky tests to investigate first, based on how central and how frequent the underlying issue appears to be.
