Mapping Actions to Playwright

Prerequisites: AI Action Planning

Introduction

A PlannedAction like { actionType: "click", target: "Log In button" } is structured, but it's still not Playwright code. This page closes that gap — and does it deterministically, not with another AI call, which is a deliberate, important design choice this page explains.

Step-by-Step Implementation

// src/map-to-playwright.ts
import { Page, Locator } from '@playwright/test';
import { PlannedAction } from './plan-action';

export interface LocatorMap {
  [target: string]: (page: Page) => Locator;
}

export const SHOPSMART_LOCATORS: LocatorMap = {
  'Email field': (page) => page.getByLabel('Email'),
  'Password field': (page) => page.getByLabel('Password'),
  'Log In button': (page) => page.getByRole('button', { name: 'Log In' }),
  'Search box': (page) => page.getByPlaceholder('Search products...'),
  'Cart total': (page) => page.getByTestId('cart-total'),
};

export async function executeAction(
  action: PlannedAction, page: Page
): Promise<void> {
  const locatorFn = SHOPSMART_LOCATORS[action.target];
  if (!locatorFn) {
    throw new Error(
      `No known locator for target: "${action.target}". ` +
      `Refusing to guess — add it to SHOPSMART_LOCATORS first.`
    );
  }
  const locator = locatorFn(page);

  switch (action.actionType) {
    case 'navigate':
      await page.goto(action.target);
      break;
    case 'fill':
      await locator.fill(action.value ?? '');
      break;
    case 'click':
      await locator.click();
      break;
    case 'assert':
      await locator.waitFor({ state: 'visible' });
      break;
  }
}

Code Explanation

This is deliberately plain TypeScript — a lookup table and a switch statement, no AI call anywhere in this function. That's the whole point of this page: mapping a known, constrained actionType to a real Playwright method is an exact, deterministic operation with one genuinely correct answer per input, exactly Chapter 2's own rule for when a deterministic check is the right tool, not AI reasoning.

Why It Matters — Refusing to Guess

Notice executeAction throws immediately if action.target isn't in SHOPSMART_LOCATORS, rather than falling back to some invented selector. This mirrors Chapter 3's system prompt instruction to "never invent a selector" — but enforced here in actual, deterministic code, not just requested of the model. A missing locator becomes a clear, immediate error, not a silent, wrong guess.

Expected Result

const action = {
  stepOrder: 1, actionType: 'fill' as const,
  target: 'Email field', value: 'test@shopsmart.example.com',
};
await executeAction(action, page);
// The real email field on the real, current page gets filled —
// no AI call happened in this specific function at all

Common Mistakes

  • Asking AI to generate the Playwright call for each action. Once actionType and target are known and constrained, the mapping to a Playwright call has exactly one correct answer — reaching for AI here adds cost, latency, and risk for zero genuine benefit.
  • Silently falling back to a generic selector when the target isn't in the map. This page's explicit, thrown error is what keeps a missing locator visible and fixable, rather than producing a confusing runtime failure deep inside Playwright.

Best Practices

  • Keep the mapping from structured action to Playwright call as plain, deterministic code — no AI call belongs in this specific step.
  • Fail loudly and immediately on an unknown target, the same defensive discipline Chapter 3 established for missing configuration.

Key Takeaways

  • Mapping a structured action to a real Playwright call is a deterministic operation with one correct answer — plain code, not another AI call.
  • This directly applies Chapter 2's core rule: AI belongs where genuine judgment is needed, and this specific mapping step doesn't need it.
  • Refusing to guess at an unknown target, with a clear thrown error, keeps failures visible rather than silently wrong.
