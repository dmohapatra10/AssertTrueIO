Happy Path and Negative Test Generation

Prerequisites: Requirement to Test Cases

What You'll Learn

  • The genuine difference between happy-path and negative test cases
  • Why asking for both explicitly, in one request, produces better coverage than asking for either alone
  • Filtering the previous page's generic output by category

Introduction

Happy path confirms a feature works when used correctly. Negative testing confirms it fails correctly when used incorrectly — the wrong password, an expired session, a network error mid-checkout. Both matter, and this page's real point is that requesting them together, explicitly, produces more balanced results than requesting either alone.

How It Works — Requesting Both Explicitly

// Extending the previous page's generateTestCases with an
// EXPLICIT category split, rather than trusting the model to
// balance categories on its own
export async function generateHappyAndNegative(
  requirement: string,
  featureContext: string
): Promise<{ happyPath: TestCase[]; negative: TestCase[] }> {
  const prompt = `Requirement: "${requirement}"
Feature context: ${featureContext}

Generate test cases in TWO explicit groups:
1. HAPPY PATH — at least 2 cases where everything is used
   correctly and the feature should work as intended
2. NEGATIVE — at least 3 cases where something is used
   incorrectly, and the feature should fail SAFELY and
   CLEARLY, not crash or behave unpredictably

Respond with ONLY valid JSON:
{"happyPath": [...], "negative": [...]}
Each test case: {"id": string, "category": string,
"name": string, "steps": string[], "expected": string}`;

  const raw = await askClaude(prompt);
  const parsed = JSON.parse(raw);
  if (!Array.isArray(parsed.happyPath) || !Array.isArray(parsed.negative)) {
    throw new Error(`Expected both categories but got: ${raw.slice(0, 200)}`);
  }
  return { happyPath: parsed.happyPath, negative: parsed.negative };
}

Why It Matters — Explicit Requests Beat Implicit Balance

Asking simply "generate test cases for checkout" tends to produce mostly happy-path scenarios — the model, like a human tester relying on intuition, gravitates toward the expected flow first. Explicitly requesting a minimum count in each category, in the same prompt, is what actually produces balanced coverage — directly applying Chapter 2's specificity lesson to this exact, real problem.

Example — ShopSmart's Checkout

const checkoutContext = `Checkout: cart review, shipping
address, payment method, order confirmation. Requires a valid
address and payment method to proceed. Session expires after
30 minutes of inactivity.`;

const { happyPath, negative } = await generateHappyAndNegative(
  'Test ShopSmart\\'s checkout flow', checkoutContext
);

// happyPath includes: "Complete checkout with valid address
//   and payment"
// negative includes: "Attempt checkout with expired session",
//   "Attempt checkout with invalid payment card number",
//   "Attempt checkout with empty shipping address"

Common Mistakes

  • Assuming a generic "generate test cases" request naturally balances both categories. This page's own point is that it usually doesn't — explicit requests genuinely change the result.
  • Treating "negative" as synonymous with "the feature is broken." A negative case passes when the feature fails safely and clearly — an unhandled crash is the actual failure, not the rejection itself.

Best Practices

  • Request explicit minimum counts per category rather than trusting a general request to balance itself.
  • Write negative case expectations around safe, clear failure — a specific error message, not just "doesn't work."

Hands-On Exercise

Run this page's function for ShopSmart's registration form (email, password, confirm password). Check whether the negative cases it generates cover genuinely different failure modes — mismatched passwords, a duplicate email, a weak password — rather than several variations of the same one.

Key Takeaways

  • Happy path confirms correct use works; negative testing confirms incorrect use fails safely and clearly — both are genuinely necessary categories.
  • Explicitly requesting both, with minimum counts, produces meaningfully more balanced coverage than an unstructured request.
  • A negative test's real success condition is safe, clear failure — not simply "the feature rejected it."
