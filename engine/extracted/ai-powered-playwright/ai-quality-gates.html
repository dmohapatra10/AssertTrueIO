Introduction — Not Every Failure Deserves the Same Response

A traditional CI gate treats every failure identically: any red test blocks the merge. This is safe but genuinely costly — a test failing because of Chapter 12's own flakiness, not a real application problem, blocks a legitimate change for no real reason, training a team to routinely re-run CI rather than trust it.

Step-by-Step Implementation

// src/ai-quality-gate.ts
import { classifyFailure } from './classify-failure';
import { detectFlakyCandidates } from './detect-flaky-candidates';
import { TestRunRecord } from './collect-test-history';

export interface GateDecision {
  testName: string;
  shouldBlock: boolean;
  reason: string;
}

export async function evaluateGate(
  failedTests: { testName: string; payload: any }[], history: TestRunRecord[]
): Promise<GateDecision[]> {
  const knownFlaky = new Set(
    detectFlakyCandidates(history).map((c) => c.testName)
  );

  const decisions: GateDecision[] = [];
  for (const { testName, payload } of failedTests) {
    if (knownFlaky.has(testName)) {
      decisions.push({
        testName, shouldBlock: false,
        reason: 'Known flaky test (Chapter 12) — not blocking, but flagged for investigation',
      });
      continue;
    }

    const classification = await classifyFailure(payload);
    const shouldBlock = ['Application Defect', 'Test Defect'].includes(classification.category);
    decisions.push({
      testName, shouldBlock,
      reason: `Classified as ${classification.category}: ${classification.reasoning}`,
    });
  }
  return decisions;
}

Code Explanation

Notice the flaky check happens first, and short-circuits the rest — a test already known to be flaky doesn't need fresh classification to justify not blocking. For everything else, only Application Defect and Test Defect genuinely block; Locator Failure, Timeout, and the other categories from Chapter 9 get flagged without stopping the merge, since they're often about test maintenance rather than a real application problem.

Example — A Real Gate Decision for ShopSmart

const decisions = await evaluateGate(failedTests, history);

// [
//   { testName: "completes checkout with valid payment",
//     shouldBlock: false,
//     reason: "Known flaky test (Chapter 12) — not blocking..." },
//   { testName: "rejects invalid credit card number",
//     shouldBlock: true,
//     reason: "Classified as Application Defect: validation
//       logic accepts a clearly malformed card number" }
// ]

const blockers = decisions.filter((d) => d.shouldBlock);
if (blockers.length > 0) {
  console.error('Merge blocked:', blockers);
  process.exit(1);
}

Why It Matters — This Genuinely Changes Team Behavior

A gate that blocks on every failure, including known flakiness, teaches a team to distrust CI and re-run it reflexively rather than investigate. A gate that blocks specifically on genuine defects, while still surfacing everything else for visibility, keeps the signal meaningful — a blocked merge genuinely means something worth stopping for.

Common Mistakes

  • Never blocking on anything, to avoid false positives entirely. This defeats the whole purpose of a gate — genuine application defects need to actually stop a merge, not just get logged somewhere.
  • Treating this gate's decisions as final without any human visibility. Non-blocking failures should still be surfaced clearly, via Chapter 16's own PR comment technique, not silently discarded.

Best Practices

  • Check known flakiness first, before spending a classification call on a failure that's already understood.
  • Surface every decision, blocking or not, in the PR — a non-blocking failure is still worth a human's attention, just not a stopped merge.

Key Takeaways

  • Blocking every failure identically is safe but genuinely costly — it treats known flakiness the same as a real application defect.
  • Combining Chapter 12's flaky detection with Chapter 9's classification lets a gate block specifically on genuine defects, not on noise.
  • A meaningful gate keeps a blocked merge genuinely significant — the alternative trains a team to distrust and routinely bypass CI.
