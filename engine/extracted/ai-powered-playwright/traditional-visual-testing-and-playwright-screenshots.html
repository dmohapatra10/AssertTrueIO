Introduction

Before reaching for AI, it's worth being clear about what Playwright's own visual testing already does — no model involved, genuinely reliable, and worth understanding on its own terms first.

How It Works — Real, Deterministic Pixel Comparison

import { test, expect } from '@playwright/test';

test('product page matches baseline', async ({ page }) => {
  await page.goto('/products/probook-15');
  await expect(page).toHaveScreenshot('product-page.png', {
    maxDiffPixels: 100,
  });
});

// FIRST run: SAVES a baseline image
// EVERY later run: compares PIXEL BY pixel against that
// baseline — EXACTLY reproducible, EXACTLY deterministic

Why It Matters — Genuinely Reliable for What It Checks

A pixel diff either matches within the allowed tolerance or it doesn't — there's no judgment call, no possibility of the check itself being wrong about whether two images are pixel-identical. This is exactly the kind of exact, deterministic question this track has valued since Chapter 2 — and it's a genuinely strong foundation worth keeping regardless of anything this chapter adds.

Example — What This Genuinely Catches

// A REAL, deterministic pixel diff correctly catches:
//   - a button that SHIFTED position by 20 pixels
//   - a color that changed from #22c55e to #16a34a
//   - a font that RENDERED differently after a CSS change
//   - ANY visual regression where the BASELINE and the
//     CURRENT page genuinely differ, pixel for pixel

Why It Matters — The Real, Specific Gap

What a PIXEL diff CANNOT tell you:
  - WHY two images differ — only THAT they do
  - whether a DIFFERENT-but-still-CORRECT layout (a genuinely
    intentional REDESIGN) is a REAL bug or an EXPECTED change
  - whether the PAGE, despite matching its BASELINE exactly,
    is showing something GENUINELY wrong that was ALSO wrong
    in the baseline — a bug BAKED into the reference image
    itself

A pixel diff is honest about exactly one thing: whether two images are identical. It has no opinion about whether either one is actually correct — that judgment has always belonged to whoever approved the baseline in the first place.

Common Mistakes

  • Assuming a passing pixel-diff test means the page is genuinely correct. It only means the page matches its baseline — if the baseline itself contained a bug, the test will keep passing forever.
  • Treating every pixel-diff failure as a genuine bug. An intentional redesign fails a pixel diff exactly as loudly as a real regression — the diff alone can't distinguish them.

Best Practices

  • Keep pixel-diff testing as your default for catching unintentional visual regressions — it's genuinely reliable and deserves to remain the foundation.
  • Review baseline images carefully when first approving them — a pixel diff can only ever be as correct as the baseline it's compared against.

Hands-On Exercise

Set up a real toHaveScreenshot test against a page in your own application. Deliberately approve a baseline, then make a small, genuine visual change and confirm the test correctly fails — then consider: would this same test have caught a bug that already existed when you approved the baseline?

Key Takeaways

  • Playwright's pixel-diff comparison is genuinely reliable and deterministic — no AI needed for exact, reproducible visual matching.
  • It answers "did this change" honestly, but has no way to answer "is this correct" — that judgment lives entirely in whoever approved the baseline.
  • This real, specific gap — distinguishing intentional change from genuine regression, and catching bugs baked into an approved baseline — is exactly what this chapter's remaining pages address.
