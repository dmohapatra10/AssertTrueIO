Introduction

Every earlier page in this chapter assumed a known, exact expected value. This page is about content that genuinely doesn't have one — where "correct" is a matter of judgment, not string matching. Recognizing this honestly is what this page is really about; the actual AI call comes on the next page.

Why It Matters — A Concrete Contrast

HAS an EXACT correct value — Chapter 7's traditional methods:
  "The heading says 'Order Confirmed'" → toHaveText('Order Confirmed')
  ONE correct string. Anything else is simply WRONG.

GENUINELY has NO single correct value:
  "ShopSmart rejected an invalid promo code with a HELPFUL
  error message" → what COUNTS as "helpful"? "Invalid promo
  code" and "This promo code has expired or doesn't exist —
  double-check the code and try again" are BOTH genuinely
  valid, CORRECT, DIFFERENT strings — there's no ONE right
  answer to match EXACTLY.

How It Works — What Makes Content Genuinely This Way

Content lacks a single correct string when the application's real, legitimate implementation could reasonably produce several different, equally acceptable versions — different wording, different phrasing, different levels of detail — all satisfying the actual requirement. This is genuinely different from content that's simply unpredictable; ShopSmart's error message is deterministic once written, but which specific wording counts as "helpful enough" is a judgment call no single string capture correctly.

Example — Distinguishing "Wrong" From "Unhelpful"

// WRONG — this is a BUG, catchable with a SIMPLE, exact check:
"undefined is not a function" showing to a REAL user

// TECHNICALLY correct, but genuinely UNHELPFUL — THIS is
// where judgment, not exact matching, is what's needed:
"Error 400" showing after an invalid promo code submission

// GENUINELY helpful — but NOT the only acceptable wording:
"This promo code has expired or doesn't exist — double-check
the code and try again"

A deterministic check can catch the first case easily — "does the page show a raw JavaScript error" has an exact, correct answer: no, never. It cannot meaningfully distinguish the second case from the third, because both are syntactically valid strings; the real difference is genuinely about clarity and helpfulness to a real user.

Common Mistakes

  • Treating "the message changed" as automatically meaning "the test should judge it with AI." A message that changed from correct to a raw error is still a deterministic, catchable bug — judgment is for distinguishing between multiple valid options, not catching outright breakage.
  • Skipping this recognition step and reaching straight for AI judgment on everything content-related. Many content checks genuinely do have one correct value — a specific, required legal disclaimer text, for instance.

Best Practices

  • Before reaching for AI judgment, ask explicitly: could a legitimate, correct implementation produce more than one valid version of this content? If not, a deterministic check is still the right tool.
  • Keep a clear line between "this is broken" (deterministic, catchable) and "this could be better" (a genuine judgment call) — they're different problems.

Hands-On Exercise

Review five pieces of user-facing content from your own application — error messages, confirmation text, validation feedback. For each, decide honestly whether it has one correct value or genuinely could vary while still being correct. Set aside the ones that genuinely vary for this chapter's next page.

Key Takeaways

  • Content genuinely lacks a single correct value when multiple different, legitimate versions could all satisfy the real requirement.
  • "Wrong" and "unhelpful" are different problems — the first is usually still deterministically catchable; the second is where genuine judgment belongs.
  • Recognizing this distinction honestly, before reaching for AI, is the real skill — the next page's actual AI call is the easy part by comparison.
