Common Causes of Flakiness

Prerequisites: What is a Flaky Test?

What You'll Learn

  • Five real, recurring causes of flakiness specific to browser automation
  • Why each one produces inconsistent, not consistent, failures
  • How each cause maps to something this chapter's later pages will actually detect

Introduction

Flakiness isn't random in the sense of being uncaused — it has real, recurring, identifiable sources. Knowing them in advance is what makes this chapter's later detection and diagnosis pages recognizable rather than mysterious.

How It Works — Five Real, Recurring Causes

RACE CONDITIONS
  An action fires BEFORE the page is GENUINELY ready for it —
  Playwright's own auto-waiting REDUCES this, but doesn't
  eliminate it for EVERY possible timing scenario

ANIMATION TIMING
  A CSS transition or animation MEANS an element is
  TECHNICALLY present but not yet STABLE — clicking DURING
  a transition can hit the WRONG coordinates

NETWORK VARIANCE
  A REAL API call SOMETIMES resolves in 100ms, SOMETIMES in
  2 seconds — a FIXED timeout that's usually enough OCCASIONALLY
  isn't

TEST ORDER DEPENDENCE
  A test PASSES when run AFTER test B, but FAILS run in
  ISOLATION or after a DIFFERENT test — hidden, SHARED state

SHARED STATE
  TWO tests modify the SAME database ROW, browser STORAGE, or
  GLOBAL variable — whichever runs SECOND behaves
  UNPREDICTABLY depending on TIMING and ORDER

Why It Matters — Each Cause Produces a Genuinely Different Pattern

These aren't just an abstract list — each one leaves a real, different fingerprint in test history and trace data. A race condition tends to fail at the same action, inconsistently. Test order dependence tends to fail specifically when run in a different sequence or in isolation. Recognizing which pattern you're looking at is most of the diagnostic work this chapter's later pages formalize.

Example — ShopSmart's Genuine Causes, Concretely

RACE CONDITION: clicking "Add to Cart" before the product
  page's JavaScript has finished attaching its click handler

ANIMATION TIMING: clicking a menu item while a dropdown is
  still SLIDING into its final position

NETWORK VARIANCE: ShopSmart's discount-code validation API
  occasionally takes 3+ seconds under real load, exceeding a
  test's 2-second wait

TEST ORDER DEPENDENCE: a cart test assumes an EMPTY cart, but
  FAILS when run after another test that left an item in it

SHARED STATE: two tests both modify the SAME test user's
  saved address, and whichever runs SECOND sees the WRONG one

Common Mistakes

  • Assuming Playwright's auto-waiting eliminates all timing-related flakiness. It genuinely helps a great deal, but animation timing and network variance can still slip past it in real, specific ways.
  • Debugging a flaky test without considering test order or shared state. These causes are easy to miss because the failing test's own code looks completely correct in isolation.

Best Practices

  • Keep this page's five categories in mind explicitly when investigating a flaky test — they narrow the search meaningfully.
  • Test in isolation and in full-suite order deliberately, to specifically rule test order dependence in or out.

Hands-On Exercise

Pick a real or suspected flaky test from your own suite. Run it in isolation, then as part of the full suite, then twice in immediate succession. Note any difference in behavior — this simple experiment often narrows which of this page's five categories is genuinely responsible.

Key Takeaways

  • Flakiness has real, identifiable, recurring causes — race conditions, animation timing, network variance, test order dependence, and shared state.
  • Each cause leaves a genuinely different pattern in test history and trace data, which is what makes diagnosis possible rather than guesswork.
  • Simple experiments — running in isolation versus full order — often narrow the likely cause before any deeper analysis is needed.
