Introduction — No Baseline Needed

Every earlier page in this chapter compared something — a page against a requirement, or two screenshots against each other. This page checks a single screenshot on its own, for genuine visual problems that would be wrong regardless of what any baseline says.

Step-by-Step Implementation

// src/detect-visual-bugs.ts
import { anthropic } from './ai-client';

export type VisualBugCategory =
  | 'overlapping-elements' | 'cut-off-text' | 'broken-image'
  | 'misaligned-layout' | 'unreadable-contrast' | 'none';

export interface VisualBugReport {
  bugsFound: { category: VisualBugCategory; description: string; location: string }[];
}

export async function detectVisualBugs(
  base64Image: string
): Promise<VisualBugReport> {
  const response = await anthropic.messages.create({
    model: 'claude-sonnet-4-6',
    max_tokens: 600,
    messages: [{
      role: 'user',
      content: [
        { type: 'image', source: { type: 'base64', media_type: 'image/png', data: base64Image } },
        { type: 'text', text: `Examine this screenshot for
GENUINE visual bugs in these specific categories: overlapping
elements, cut-off or truncated text, broken or missing images,
misaligned layout, unreadable text contrast. Only report
something you can point to CONCRETELY — do not guess.

Respond with ONLY valid JSON:
{"bugsFound": [{"category": string, "description": string,
"location": string}]}` },
      ],
    }],
  });

  const textBlock = response.content.find((b) => b.type === 'text');
  return JSON.parse((textBlock as any).text);
}

Code Explanation

The five named categories are doing real work here — a vague "find any bugs" prompt tends to produce vague, unfocused results, while these specific categories give the model concrete things to actually look for. 'none' as a valid category matters too: an empty bugsFound array is a genuine, honest result when a screenshot has no visual bugs, not something to force output around.

Why It Matters — Genuinely Different From Every Earlier Page

This check needs no requirement to validate against and no prior screenshot to compare with — it's looking for problems that would be genuinely wrong on any page, in any context. This makes it a useful, standalone check to run against any screenshot, including ones from Chapter 13's exploratory testing, where no specific requirement or baseline exists yet at all.

Common Mistakes

  • Using a vague, open-ended "find any bugs" prompt instead of named categories. This page's whole point is that concrete categories produce concrete, useful findings — vagueness produces vague, less actionable output.
  • Treating every report entry as equally certain. "Do not guess" in the prompt helps, but this check still benefits from a human confirming a flagged bug is real before treating it as confirmed — the next page addresses this honestly.

Best Practices

  • Name specific, concrete bug categories in the prompt rather than asking generically for problems.
  • Run this check on screenshots without a natural baseline — exploratory testing, new pages, first-time visual checks — where the previous pages' comparative approaches don't apply.

Hands-On Exercise

Deliberately introduce one real visual bug into a test page — truncate some text with a tight CSS overflow rule, or overlap two elements with absolute positioning. Run this page's function against a screenshot of it and confirm the report correctly identifies and locates the bug.

Key Takeaways

  • This check needs no baseline or stated requirement — it looks for problems that would be genuinely wrong in any context.
  • Naming specific, concrete bug categories in the prompt produces meaningfully more useful results than an open-ended request.
  • This is a natural fit for screenshots with no existing baseline, including Chapter 13's exploratory testing output.
