What is a Flaky Test?

Prerequisites: AI-Powered Flaky Test Detection overview

What You'll Learn

  • A precise, working definition of flakiness
  • Why a single failure is never sufficient evidence on its own
  • The genuine difference between "flaky" and "recently broken"

Introduction

A flaky test is one whose outcome genuinely varies across runs, with no corresponding change in the code being tested. Getting this definition precise matters — it's what separates genuine flakiness from a test that's simply broken, or one that failed once for an unrelated, real reason.

How It Works — The Precise Definition

GENUINELY FLAKY:
  SAME test, SAME code, SAME environment — sometimes PASSES,
  sometimes FAILS, with NO real, external explanation each time

NOT flaky — GENUINELY broken:
  A test that ALWAYS fails, consistently, SINCE a specific
  code CHANGE — this is Chapter 9's "Application Defect" OR
  "Test Defect" category, NOT flakiness at all

NOT flaky — ONE real, external FAILURE:
  A test failed ONCE because a THIRD-party service GENUINELY
  had an OUTAGE — a real, ONE-TIME environmental cause, not
  evidence of RECURRING, unpredictable BEHAVIOR

Why It Matters — A Single Failure Proves Nothing

Seeing one failure and immediately labeling a test "flaky" is a genuine, common mistake. A single failure is equally consistent with a real, one-time cause (a network blip, a genuine environment issue) as with true flakiness. The difference only becomes visible across multiple runs — which is exactly why this chapter's next several pages are about collecting and analyzing real history before drawing any conclusion.

Example — Two ShopSmart Failures That Look Similar But Aren't

CASE A: ShopSmart's checkout test fails. Investigation shows
this SAME test has failed 12 TIMES out of the LAST 50 runs,
with NO pattern tied to any SPECIFIC code change — GENUINELY
flaky.

CASE B: ShopSmart's checkout test fails. Investigation shows
THIS is the FIRST failure EVER, and it started IMMEDIATELY
after YESTERDAY's deployment — NOT flaky; this is Chapter 9's
"Application Defect" category, a REAL, consistent regression.

Common Mistakes

  • Calling a test "flaky" after a single failure, without checking history. This page's Case A versus Case B comparison shows why that single data point alone can't distinguish them.
  • Assuming flaky and broken are the same underlying problem, treated differently only by convention. They have genuinely different real causes and need genuinely different responses — this distinction shapes everything else in this chapter.

Best Practices

  • Never conclude a test is flaky from a single failure — this chapter's remaining pages exist specifically to make that judgment on real, sufficient evidence.
  • Keep "flaky" and "broken" as genuinely distinct categories in your own mental model, not interchangeable labels for "test failed."

Hands-On Exercise

Look at your own project's recent test failure history, if it's tracked. Pick two real failures and classify each, honestly, as more consistent with genuine flakiness or a real, one-time or ongoing cause — using this page's Case A and Case B as your model.

Key Takeaways

  • Genuine flakiness means the same test, same code, same environment produces inconsistent outcomes with no real external explanation.
  • A single failure alone can never distinguish genuine flakiness from a real, one-time cause or a consistent new regression.
  • This precise distinction is what the rest of this chapter's history-based techniques are built to establish reliably.
