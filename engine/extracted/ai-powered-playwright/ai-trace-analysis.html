Introduction — Genuinely Deeper Than Chapter 9

Chapter 9's analysis worked from an error message and a few stack frames. This page sends the entire, ordered sequence of actions leading up to a failure — letting the model reason about what happened across the whole run, not just at the final, failing moment.

Step-by-Step Implementation

// src/analyze-trace-with-ai.ts
import { askClaude } from './ai-client';
import { TraceAction } from './extract-trace-data';

export interface TraceAnalysis {
  summary: string;
  suspiciousActions: number[];
  likelyCause: string;
}

export async function analyzeTraceTimeline(
  actions: TraceAction[]
): Promise<TraceAnalysis> {
  // Chapter 9's OWN selective-sending discipline, applied HERE:
  // send the FULL sequence, but TRIM verbose selector strings,
  // which add real TOKEN cost without adding real SIGNAL
  const summarized = actions.map((a, i) => ({
    index: i, type: a.type, durationMs: a.durationMs,
    hasError: !!a.error,
  }));

  const prompt = `Full action timeline from a failed Playwright
test, in order:
${JSON.stringify(summarized)}

Analyze the SEQUENCE, not just the final failure. Look for
actions with unusually long durations, or a pattern across
MULTIPLE actions that suggests what went wrong.

Respond with ONLY valid JSON:
{"summary": string, "suspiciousActions": [number, ...],
"likelyCause": string}`;

  const raw = await askClaude(prompt);
  return JSON.parse(raw);
}

Code Explanation

Notice summarized deliberately strips full selector strings before sending — Chapter 9's token-cost discipline applied here to a genuinely larger evidence source than a single error message. suspiciousActions returns indices, not full descriptions, letting the calling code look up full detail from the original actions array only for the specific steps flagged as worth investigating.

Why It Matters — Sequence Reveals What a Single Error Can't

Chapter 9's analysis, working from the error alone, could reasonably suspect several causes. This chapter's sequence-aware analysis can rule some out directly — since every action before the failing one completed with no errors and normal timing, a cascading earlier problem becomes much less likely, narrowing the genuinely plausible explanations before the next page even looks at a screenshot.

Common Mistakes

  • Sending the full, unsummarized action array, selectors included, for every analysis. This repeats exactly the cost problem Chapter 9's selective-sending page addressed — genuinely necessary here too, at a larger scale.
  • Only looking at the failing action, ignoring the sequence before it. This throws away exactly the information that makes trace analysis genuinely more powerful than Chapter 9's single-error approach.

Best Practices

  • Summarize verbose fields (like full selector strings) before sending a full timeline — the same cost discipline from Chapter 9, applied at trace scale.
  • Return indices for flagged actions, not full descriptions, letting calling code look up detail only when genuinely needed.

Key Takeaways
