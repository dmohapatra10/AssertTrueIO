Introduction — How This Differs From Chapter 4

Chapter 4 generated a negative test CASE: "Attempt registration with an invalid email," complete with steps and an expected result. This page generates the actual invalid VALUE that case would use — a real, concrete string like "not-an-email" or "missing@domain". Chapter 4 answers "what should we test"; this page answers "what data makes that test real."

Step-by-Step Implementation

// src/generate-invalid-data.ts
import { askClaude } from './ai-client';

export async function generateInvalidValues(
  fieldName: string, validationRules: string, count: number
): Promise<string[]> {
  const prompt = `Field: "${fieldName}"
Validation rules: ${validationRules}

Generate ${count} genuinely DIFFERENT invalid values for this
field — different KINDS of invalidity (wrong format, missing
required part, wrong length), not minor variations of the
SAME mistake.

Respond with ONLY valid JSON: {"values": [string, ...]}`;

  const raw = await askClaude(prompt);
  const parsed = JSON.parse(raw);
  if (!Array.isArray(parsed.values)) {
    throw new Error(`Expected {"values": [...]} but got: ${raw.slice(0, 200)}`);
  }
  return parsed.values;
}

export async function generateBoundaryValues(
  fieldName: string, validRange: string
): Promise<{ atMin: number; belowMin: number; atMax: number; aboveMax: number }> {
  const prompt = `Field: "${fieldName}", valid range: ${validRange}

Give the EXACT minimum valid value, ONE below it, the EXACT
maximum valid value, and ONE above it.

Respond with ONLY valid JSON:
{"atMin": number, "belowMin": number, "atMax": number, "aboveMax": number}`;

  const raw = await askClaude(prompt);
  return JSON.parse(raw);
}

Using This Data in a Real, Data-Driven Test

import { test, expect } from '@playwright/test';
import { generateInvalidValues } from './generate-invalid-data';

test('registration rejects genuinely varied invalid emails', async ({ page }) => {
  const invalidEmails = await generateInvalidValues(
    'registration email', 'Must contain @ and a domain with a dot', 4
  );

  for (const email of invalidEmails) {
    await page.goto('/register');
    await page.getByLabel('Email').fill(email);
    await page.getByRole('button', { name: 'Register' }).click();
    await expect(page.getByRole('alert')).toBeVisible();
    // ONE test, looping over MULTIPLE real, DIFFERENT invalid
    // values — genuinely more coverage than ONE hardcoded
    // "not-an-email" string, checked ONCE
  }
});

Why It Matters

A single hardcoded invalid email tests exactly one kind of malformation, forever. This page's generated values genuinely cover different failure modes — missing the @ symbol, missing the domain, an empty local part, an over-length address — catching a validation bug specific to one of those cases that a single fixed value would never reveal.

Common Mistakes

  • Confusing this page's data generation with Chapter 4's scenario generation. They're genuinely complementary — Chapter 4 decides to test invalid emails at all; this page provides the actual, varied values.
  • Generating invalid values that are all minor variations of the same mistake. Four emails all missing just the @ symbol don't provide the genuine coverage four DIFFERENT kinds of invalidity would.

Best Practices

  • Request genuinely different kinds of invalidity explicitly, the same variety discipline this chapter has applied since its second page.
  • Loop a data-driven test over several generated values, rather than writing one test per hardcoded invalid string.
