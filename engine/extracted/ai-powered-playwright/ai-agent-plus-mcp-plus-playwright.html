Introduction

Every earlier page in this chapter built one real piece — server, client, tools. This page connects them to Chapter 14's actual agent, and confirms directly what changes and what doesn't.

Step-by-Step Implementation — The Rewired Execution Layer

// src/agent-execute-via-mcp.ts
import { Client } from '@modelcontextprotocol/sdk/client/index.js';

export async function executeAgentToolViaMcp(
  toolName: string, toolInput: any, client: Client
): Promise<string> {
  const result = await client.callTool({ name: toolName, arguments: toolInput });
  const textBlock = result.content.find((c: any) => c.type === 'text');
  return textBlock?.text ?? '';
}

Code Explanation

Compare this against Chapter 14's original executeAgentTool — same input, same conceptual output, genuinely different only in how the call actually reaches the tool. Everything upstream of this function — the Planner choosing what to do, the Evaluator deciding if the objective is met — never needs to know this change happened at all.

Step-by-Step Implementation — The One Real Change in the Main Loop

// src/playwright-agent-mcp.ts (Chapter 14's runPlaywrightAgent, rewired)
import { connectToPlaywrightServer } from './mcp-client';
import { executeAgentToolViaMcp } from './agent-execute-via-mcp';
// ... all OTHER Chapter 14 imports UNCHANGED

export async function runPlaywrightAgentViaMcp(objective: string) {
  const client = await connectToPlaywrightServer();
  let state = createInitialState(objective);
  const limits = { maxSteps: 30, maxDepthFromStart: 4, maxDurationMs: 5 * 60 * 1000 };

  while (true) {
    const toolCall = await planNextStep(state); // UNCHANGED

    const guard = guardToolCall(toolCall.name, toolCall.input, ''); // UNCHANGED
    if (!guard.allowed) {
      return { outcome: 'blocked-by-guardrail' as const, reason: guard.reason };
    }

    if (toolCall.name === 'report_objective_complete') { // UNCHANGED
      const evaluation = await evaluateProgress(state);
      if (evaluation.objectiveLikelyMet) return { outcome: 'success' as const, evaluation };
    }

    try {
      // THE ONE REAL CHANGE — executeAgentTool → executeAgentToolViaMcp
      const result = await executeAgentToolViaMcp(toolCall.name, toolCall.input, client);
      recordObservation(state, toolCall.id, result); // UNCHANGED
    } catch (error: any) {
      // Recovery, limits — ALL UNCHANGED from Chapter 14
    }
    state.stepCount++;
  }
}

Why It Matters — Confirming the Real Result

Exactly one function call changed — executeAgentTool became executeAgentToolViaMcp. Planning, guardrails, evaluation, observation recording, recovery, and limits are all completely untouched. This confirms Chapter 15's opening claim concretely: MCP is a genuinely different way of reaching the same tools, not a different way of reasoning about when to use them.

Common Mistakes

  • Rewriting the Planner or Evaluator to accommodate MCP. This page's whole point is that neither needs to change at all — if you find yourself modifying them, something's gone wrong with the rewiring.
  • Passing the MCP client into functions that never needed it before. Only the execution layer needs the client — threading it further than that adds unnecessary coupling.

Best Practices

  • Isolate the MCP-specific change to the execution layer alone, exactly as this page's code does — resist the urge to touch anything upstream.
  • Keep a working, direct (non-MCP) version of the agent available, the way Chapter 14 left it — useful for local testing without a running server.

Key Takeaways

  • Rewiring an agent to use MCP requires changing exactly one function — the execution layer — while planning, evaluation, guardrails, and recovery stay completely untouched.
  • This concretely confirms MCP is a different access mechanism for the same tools, not a different reasoning architecture.
  • Keeping the MCP-specific change isolated to one layer is what makes this rewiring safe and easy to verify.
