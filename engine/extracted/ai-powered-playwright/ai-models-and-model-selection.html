Introduction

Different testing tasks genuinely warrant different models. A quick, simple classification ("is this a login-related failure or a network failure?") doesn't need the same capability as generating a comprehensive, nuanced set of edge-case test scenarios. Model selection is a real, recurring decision, not a one-time setup step.

How It Works — The Genuine Tradeoffs

CAPABILITY
  More capable models handle NUANCED, OPEN-ENDED reasoning
  better — generating GENUINELY creative edge cases, analyzing
  a COMPLEX failure with multiple possible causes

SPEED
  Smaller, faster models respond QUICKER — genuinely valuable
  for high-frequency tasks, like classifying EVERY test
  failure in a large CI run

COST
  Every model call has a REAL, measurable cost — covered
  fully in Chapter 18 — and more capable models generally
  cost MORE per call

Example — Two Genuinely Different ShopSmart Tasks

TASK 1: "Classify this ShopSmart test failure as either
'locator issue' or 'application bug', in one word."
  A SMALL, FAST model handles this WELL — the task is
  NARROW and doesn't need deep, nuanced reasoning

TASK 2: "Generate a comprehensive set of edge-case test
scenarios for ShopSmart's checkout, considering unusual
combinations of discounts, shipping methods, and payment
failures."
  This GENUINELY benefits from a MORE capable model — the
  task requires GENUINE, nuanced reasoning across MULTIPLE
  interacting factors

Using the same, most-capable model for both tasks would work — but it would mean paying the higher cost and latency of Task 2's model for Task 1's genuinely simpler need, over and over, across every failure in a real CI run.

Why This Tutorial Stays Vendor-Neutral

Specific model names and providers change quickly. This tutorial focuses on the underlying concepts — capability, speed, cost tradeoffs — that remain true regardless of which specific provider or model you're using. When a concrete code example needs a real model name, it's identified explicitly as one example among several reasonable choices, not a requirement.

Common Mistakes

  • Using the single most capable model for every task by default. This page's two-task comparison shows why that's often genuinely wasteful, not just occasionally suboptimal.
  • Treating model choice as a one-time decision made at project setup. Different tasks within the SAME project genuinely warrant different models — this is a recurring, task-by-task decision.

Best Practices

  • Match model capability to what a specific task genuinely requires, not to what's most powerful available.
  • Revisit model choice when a task's real requirements change — a classification task that grows more nuanced may warrant reconsidering.

Key Takeaways

  • Model selection is a genuine, recurring, task-by-task decision — not a one-time setup choice.
  • Capability, speed, and cost are real, competing tradeoffs, and the right balance depends on what a specific task actually needs.
  • This tutorial's concepts stay vendor-neutral because the underlying tradeoffs remain true regardless of which specific provider you use.
