Semantic Visual Validation

Introduction — The Real Contrast With Pixel Diffing

Chapter 17's opening page established what pixel diffing can't do: distinguish an intentional redesign from a genuine regression. This page is the direct answer — checking whether a page genuinely satisfies a real requirement, regardless of exactly how it's laid out.

Step-by-Step Implementation

// src/semantic-visual-validation.ts
import { Page } from '@playwright/test';
import { anthropic } from './ai-client';

export interface VisualValidation {
  meetsRequirement: boolean;
  reasoning: string;
}

export async function validatePageVisually(
  page: Page, requirement: string
): Promise<VisualValidation> {
  const buffer = await page.screenshot();
  const base64Image = buffer.toString('base64');

  const response = await anthropic.messages.create({
    model: 'claude-sonnet-4-6',
    max_tokens: 500,
    messages: [{
      role: 'user',
      content: [
        { type: 'image', source: { type: 'base64', media_type: 'image/png', data: base64Image } },
        { type: 'text', text: `Requirement: "${requirement}"

Does this page genuinely satisfy this requirement? Judge based
on what a real user would see and understand, not exact layout.

Respond with ONLY valid JSON:
{"meetsRequirement": boolean, "reasoning": string}` },
      ],
    }],
  });

  const textBlock = response.content.find((b) => b.type === 'text');
  return JSON.parse((textBlock as any).text);
}

Code Explanation

This reuses the exact content-block structure from the previous page, with one real difference — the text instruction now asks for a judgment against a stated requirement, mirroring Chapter 7's own validateContentSemantically pattern, applied here to a real image instead of text content.

const result = await validatePageVisually(

Why It Matters — Genuine Tolerance for Layout Change

If ShopSmart's team moves the Add to Cart button from below the price to beside it, as part of a genuine, intentional redesign, this check still passes — because the actual requirement (a visible button exists) is still satisfied. Chapter 17's opening page's pixel diff would fail loudly on this exact same redesign, correctly detecting a difference but with no way to know it was intentional.

Common Mistakes

  • Writing a vague requirement like "the page looks good." This gives the model nothing concrete to check against — a specific, stated requirement, the way this page's example does, is what makes the judgment actually meaningful.
  • Using semantic validation for a check with one exact correct layout. This is the same Chapter 7 lesson, applied visually — if there's genuinely only one correct appearance, a pixel diff remains the right, deterministic tool.

Best Practices

  • State requirements specifically and concretely — name the actual elements that need to be present, not a vague overall impression.
  • Reach for semantic validation specifically where layout is expected to vary or evolve — not as a blanket replacement for pixel diffing everywhere.

Hands-On Exercise

Key Takeaways

  • Semantic visual validation checks whether a page satisfies a real requirement, not whether it matches an exact prior layout.
  • This genuinely tolerates intentional redesign in a way pixel diffing structurally cannot — the same real gap Chapter 17's opening page identified.
  • Specific, concrete requirements are what make this judgment meaningful — the same lesson Chapter 7 established for text-based semantic checks, now applied to real images.
