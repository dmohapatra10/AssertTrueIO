Introduction — A Different Scale of Problem

Every earlier page in this chapter handled one broken thing at a time — one locator, one assertion. A genuine UI redesign can break several related elements at once, and healing each in isolation misses something real: they're often symptoms of one underlying, coordinated change, not several independent problems.

Why It Matters — A Concrete ShopSmart Case

ShopSmart REDESIGNS checkout, adding a NEW "Gift wrap this
order?" step BETWEEN shipping and payment. This BREAKS:

  - a locator EXPECTING payment to be the THIRD step
  - an assertion EXPECTING a SPECIFIC step count
  - a locator for the "Continue" button, now POSITIONED
    differently in the NEW flow

THREE separate FAILURES, ONE real, underlying CAUSE — healing
each INDEPENDENTLY, with NO awareness of the OTHERS, would
MISS this connection entirely.

Step-by-Step Implementation — Detecting a Shared Cause

// src/detect-related-failures.ts
import { askClaude } from './ai-client';
import { Classification } from './classify-failure';

export interface FailureGroup {
  relatedFailureIndices: number[];
  sharedCauseHypothesis: string;
}

export async function detectRelatedFailures(
  failures: { testName: string; classification: Classification; errorMessage: string }[]
): Promise<FailureGroup[]> {
  const prompt = `These test failures occurred in the SAME run:
${JSON.stringify(failures)}

Group any failures that likely share ONE underlying cause —
like a single UI redesign breaking multiple tests. For each
group, state the shared cause hypothesis. Failures with no
clear relationship should NOT be grouped together.

Respond with ONLY valid JSON:
{"groups": [{"relatedFailureIndices": [number, ...],
"sharedCauseHypothesis": string}]}`;

  const raw = await askClaude(prompt);
  return JSON.parse(raw).groups;
}

Code Explanation

The prompt explicitly instructs against grouping failures with no clear relationship — this matters as much as the grouping itself. Without it, a model might force a connection between genuinely unrelated failures just because they occurred in the same run, producing a false, misleading shared-cause story that sends a human's investigation in the wrong direction.

Why It Matters — A Coordinated Fix Beats Several Disconnected Ones

Once ShopSmart's three failures are recognized as one underlying cause, the candidate fix this chapter's earlier pages generate can be proposed together, with shared context — "these three changes all stem from the new gift-wrap step" — rather than as three separate, seemingly unrelated pull requests a human reviewer would need to piece together themselves.

Common Mistakes

  • Healing each failure from a UI redesign in complete isolation. This page's ShopSmart example shows real, useful context gets lost when related failures aren't recognized as connected.
  • Forcing every failure in a run into some group, even when no genuine relationship exists. The prompt's explicit "should NOT be grouped" instruction exists specifically to prevent this.

Best Practices

  • Run failure grouping across an entire batch of results before generating individual fixes — grouping first changes what a good fix proposal looks like.
  • Present grouped failures to a human reviewer together, with the shared cause hypothesis stated explicitly, rather than as disconnected individual items.

Hands-On Exercise

Simulate three related test failures from a single, hypothetical UI change in your own application. Run them through this page's detectRelatedFailures function and confirm it correctly identifies them as one group, with a reasonable shared-cause hypothesis.

Key Takeaways

  • A broader UI redesign can break several related tests at once — a genuinely different scale of problem than one isolated failure.
  • Detecting a shared underlying cause, rather than healing each failure independently, produces more useful, coordinated fix proposals.
  • Explicitly allowing "no relationship" as a valid outcome prevents false, misleading connections between genuinely unrelated failures.
