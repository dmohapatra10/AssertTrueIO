Introduction

Every generation function in this chapter has used example.com email domains and clearly synthetic values — not by accident. This page makes that choice explicit, and covers the one genuine way this discipline can quietly break down: real data leaking in through context.

Why It Matters — The Real Risk Isn't Generation Itself

AI generation, on its own, produces synthetic data — it has no access to ShopSmart's real customer database. The genuine risk is different: a developer debugging a real, specific customer issue might paste a real customer's actual email or address into a prompt as "context" for generating a similar test case — and from that point, real, sensitive data has entered a system this chapter's own techniques never intended to touch.

Step-by-Step Implementation — A Real Guard

// src/prevent-real-data-leakage.ts

const REAL_DOMAIN_PATTERN = /@(?!example\.com)[\w-]+\.[a-z]{2,}/i;

export function scanPromptForRealData(prompt: string): string[] {
  const warnings: string[] = [];
  const emailMatches = prompt.match(REAL_DOMAIN_PATTERN);
  if (emailMatches) {
    warnings.push(
      `Prompt contains an email NOT using example.com — possible real data: ${emailMatches[0]}`
    );
  }
  return warnings;
}

export async function askClaudeSafely(prompt: string): Promise<string> {
  const warnings = scanPromptForRealData(prompt);
  if (warnings.length > 0) {
    throw new Error(
      `Refusing to send prompt — possible real data detected:\n${warnings.join('\n')}`
    );
  }
  return askClaude(prompt);
}

Code Explanation

This is a real, if imperfect, safeguard — it catches the specific, common mistake from this page's example (a real-looking email domain), not every conceivable form of sensitive data. That's honest and worth stating plainly: this check reduces risk, it doesn't eliminate it, the same honest framing this tutorial has used since Chapter 1 for every technique that helps without guaranteeing safety.

Common Mistakes

  • Assuming AI generation is inherently safe because it's "just making things up." The genuine risk isn't the generation itself — it's real data entering a prompt as context, exactly this page's example.
  • Treating a guard like scanPromptForRealData as a complete solution. It catches one common, real pattern — it's not a comprehensive sensitive-data detector, and shouldn't be trusted as one.

Best Practices

  • Default to synthetic data throughout — every generation function in this chapter already does, deliberately.
  • Never paste real customer data into a prompt, even for a seemingly helpful, well-intentioned reason like generating a "similar" test case.

Interview Questions

Beginner: What is the genuine difference between the test data this chapter generates and the test cases Chapter 4 generates?▾

Chapter 4 generates test cases — descriptions of what to test, like "registration with a duplicate email," including steps and an expected result. This chapter generates the actual data values that fill in a case like that — a real, concrete email string, a realistic address, a believable product price. Chapter 4 decides what to test; this chapter provides what to test it with.

Beginner: Why does this chapter's generateUsers function explicitly request "genuinely varied" users rather than just "realistic" ones?▾

A vague request for "realistic" data tends to produce the same statistically common patterns repeatedly, quietly recreating the poor-diversity problem this chapter opened with. Explicitly requesting variety across name origins, address formats, and regions is what actually produces the diversity needed to exercise genuinely different code paths — realism alone doesn't guarantee variety.

Intermediate: Explain, using the Denver ZIP code example, why field-by-field validation isn't sufficient for generating realistic test data.▾

A ZIP code like "33139" is validly formatted and genuinely real — it just belongs to Miami Beach, not Denver. Checking each field independently (is this a valid city name? is this a valid ZIP format?) would accept this combination without complaint, since each field passes its own check. The problem only appears when checking whether the fields are consistent with each other, which is a genuinely separate requirement from each field's individual validity — exactly why context-aware generation needs to produce related fields together, in one call, rather than independently.

Intermediate: Why does this chapter recommend caching generated test data and committing it to version control, rather than generating fresh data on every test run?▾

Fresh generation on every run means a test failure triggered by specific, unusual data — like a last name containing an apostrophe — may be impossible to reproduce later, since the next run generates different data that may not trigger the same bug. This makes debugging genuinely harder, since the bug appears to "disappear" even though it never was fixed. Caching once and committing the result makes test data reproducible across runs and reviewable via version control, the same way any other test fixture would be, while forceRegenerate still allows deliberate refresh when genuinely needed.

Advanced: Why does this chapter frame the real privacy risk in AI-generated test data as being about "context," rather than about the generation process itself?▾

AI generation, left to itself, produces synthetic data — it has no access to a real customer database and nothing to leak on its own. The genuine risk enters through a different path: a developer, trying to be helpful, pastes real customer information into a prompt as context for generating something similar. At that point, real, sensitive data has been sent to an external AI provider, a completely different exposure than anything generation itself creates. Framing the risk this way is what correctly points the mitigation at prompt hygiene and developer discipline, rather than at the generation functions themselves, which were never where the actual risk lived.

Scenario-based: A teammate wants to skip this chapter's caching approach for a "quick, one-off test," reasoning that determinism only matters for tests that run repeatedly in CI. How would you respond?▾

I'd point to this chapter's own Monday/Tuesday example: the value of caching isn't about how often a test runs in CI — it's about being able to reproduce a specific failure after the fact, whenever that need arises. A "quick, one-off test" that happens to fail today, using freshly-generated data, creates exactly the same reproduction problem the moment someone tries to investigate it tomorrow — the failure wasn't one-off, but the data that triggered it was, and now it's gone. If a test is worth running at all, the data it used when it failed is worth being able to reproduce; the caching approach costs very little and removes a real, avoidable source of debugging difficulty regardless of how the test is categorized.
