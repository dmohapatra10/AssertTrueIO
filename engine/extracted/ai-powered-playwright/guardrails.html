Step-by-Step Implementation — Guardrails, Reusing Chapter 13 Directly

// src/agent-guardrails.ts
import { isActionSafe, verifyExplorationEnvironment } from './exploration-safety-controls';

export function guardToolCall(
  toolName: string, toolInput: any, baseUrl: string
): { allowed: boolean; reason?: string } {
  const envCheck = verifyExplorationEnvironment(baseUrl);
  if (!envCheck.safe) return { allowed: false, reason: envCheck.reason };

  const actionCheck = isActionSafe(`${toolName} ${JSON.stringify(toolInput)}`);
  if (!actionCheck.safe) return { allowed: false, reason: actionCheck.reason };

  return { allowed: true };
}

Step-by-Step Implementation — The Complete, Assembled Agent

// src/playwright-agent.ts
import { Page } from '@playwright/test';
import { createInitialState } from './agent-state';
import { planNextStep } from './agent-planner';
import { executeAgentTool } from './agent-execute';
import { recordObservation } from './agent-observe';
import { evaluateProgress } from './agent-evaluator';
import { attemptRecovery } from './agent-recovery';
import { guardToolCall } from './agent-guardrails';
import { shouldStopExploring } from './exploration-limits';

export async function runPlaywrightAgent(objective: string, page: Page) {
  let state = createInitialState(objective);
  const limits = { maxSteps: 30, maxDepthFromStart: 4, maxDurationMs: 5 * 60 * 1000 };

  while (true) {
    const toolCall = await planNextStep(state);

    const guard = guardToolCall(toolCall.name, toolCall.input, page.url());
    if (!guard.allowed) {
      return { outcome: 'blocked-by-guardrail' as const, reason: guard.reason };
    }

    if (toolCall.name === 'report_objective_complete') {
      const evaluation = await evaluateProgress(state);
      if (evaluation.objectiveLikelyMet) {
        return { outcome: 'success' as const, evaluation };
      }
    }

    try {
      const result = await executeAgentTool(toolCall.name, toolCall.input, page);
      recordObservation(state, toolCall.id, result);
    } catch (error: any) {
      const recovery = await attemptRecovery(toolCall.name, page);
      if (!recovery.recovered) {
        return { outcome: 'unrecoverable-failure' as const, error: String(error) };
      }
      recordObservation(state, toolCall.id, `Recovered: ${recovery.newApproach}`);
    }

    state.stepCount++;
    const limitCheck = shouldStopExploring(
      { stepCount: state.stepCount, currentDepth: 0, startTime: state.startTime }, limits
    );
    if (limitCheck.stop) {
      return { outcome: 'limit-reached' as const, reason: limitCheck.reason };
    }
  }
}

Common Mistakes

  • Checking guardrails only occasionally, or after execution rather than before. This page's loop checks every single tool call before it executes — a guardrail that runs too late has already failed at its one job.
  • Treating this chapter's code as something to memorize rather than trace. The real value is recognizing how every earlier chapter's work fits together — not the specific lines of this final assembly.

Best Practices

  • Guard every single tool call, unconditionally, before execution — never skip this check for calls that "seem obviously safe."
  • When extending this agent, ask which existing chapter's function already solves your new need before writing anything new.

Interview Questions

Beginner: What are the three properties this chapter uses to define a genuine agent, and which one did earlier chapters not yet have?▾

A genuine agent is persistent (maintains state across many steps), tool-using (chooses among real available actions via actual tool calling), and objective-driven (receives one high-level goal and decides its own path). Earlier chapters had genuine objective-driven behavior in pieces — Chapter 5's planning, Chapter 13's exploration — but lacked real persistence across a continuous, multi-capability run, and used JSON-prompting rather than actual tool calling.

Beginner: Why did this track wait until Chapter 14 to use Anthropic's real tool-calling API, after Chapter 2 introduced the concept?▾

The simpler JSON-in-prose pattern used since Chapter 3 was easier to reason about while this track built up its real techniques one at a time — generation, locators, assertions, failure analysis, and more. Real tool calling genuinely earns its place specifically in an agent architecture, where a model needs to choose among several distinct actions repeatedly within one continuous run — exactly the scenario Chapter 14 introduces for the first time in this track.

Intermediate: Explain why the Evaluator is described as the one genuinely new capability in this chapter's architecture, while the other five boxes are reused.▾

Chapter 5's loop finished once a known, finite sequence of steps completed — it never needed to ask "is the goal actually achieved" as a separate question, since finishing the steps WAS the definition of done. Chapter 13's exploration stopped when a limit was hit, again without needing to evaluate genuine success. This chapter's agent, with an open-ended objective and no natural stopping point, genuinely needs a dedicated step that asks whether the actual goal has been met — a question with no earlier equivalent to reuse.

Intermediate: Why does evaluateProgress run as a separate step from the action that was just taken, rather than having the model assess success immediately after each tool call?▾

Bundling self-assessment into the same reasoning step that just took an action risks the same overconfidence problem Chapter 9 addressed for failure-analysis confidence — a model reasoning about whether its own recent action succeeded may not have fully considered the full conversation history and genuine alternative explanations. A separate, dedicated evaluation step, instructed explicitly toward honesty, produces a more reliable judgment specifically because it isn't entangled with the action that just happened.

Advanced: Why does runPlaywrightAgent distinguish between limit-reached and unrecoverable-failure as separate outcomes, rather than treating both as "the agent stopped without success"?▾

These represent genuinely different situations requiring different responses. A limit-reached outcome means the agent simply ran out of allotted steps, depth, or time — the objective might still be achievable with more budget, or the limits might need adjusting; this doesn't necessarily indicate anything is wrong with the application under test. An unrecoverable-failure outcome means something genuinely broke and Chapter 6's healing couldn't find a working alternative — this is much more likely to represent a real, reportable problem worth a developer's attention. Collapsing these into one generic "stopped" status would force a human reviewer to redo the investigation the agent's own outcome could have told them directly.

Scenario-based: A teammate suggests removing the guardrail check from inside the main loop and instead validating the entire planned sequence of actions once, upfront, before execution begins. How would you respond, using this chapter's own reasoning?▾

I'd point out that this agent, unlike Chapter 5's fixed sequence, doesn't have a full planned sequence to validate upfront — each tool call is chosen one at a time, informed by what happened in the previous step, exactly the open-endedness this chapter's own architecture is built around. There is no "the whole plan" to check in advance, since the model may choose a completely different next action depending on what it just observed, including a hypothesis generated mid-run the way Chapter 13 described. Checking guardrails only upfront would leave every single subsequent tool call unguarded, which defeats the entire purpose of a mandatory, per-call safety check. The guardrail belongs inside the loop, checked before every individual tool call, precisely because the agent's next action is never fully known until the moment it's chosen.
