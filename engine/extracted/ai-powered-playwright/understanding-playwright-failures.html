Introduction

Before building anything, it's worth being honest about what Playwright already hands you on a failure — considerably more than most teams actually use.

How It Works — What TestInfo Actually Contains

test('checkout completes successfully', async ({ page }, testInfo) => {
  // ... test steps ...

  // WHEN this test FAILS, testInfo genuinely contains:
  console.log(testInfo.status);       // 'failed'
  console.log(testInfo.error);        // the REAL error object,
                                        // with message AND stack
  console.log(testInfo.attachments);  // screenshot, video, and
                                        // trace file PATHS, if
                                        // configured to capture them
  console.log(testInfo.duration);     // how LONG it ran before
                                        // failing
});

Why It Matters — Most of This Goes Unread

In everyday practice, a failing test's error message gets read, and everything else — the video, the trace, the full attachment list — often goes unopened unless the failure is confusing enough to justify the extra effort. That's a real, understandable habit under time pressure, and it's also exactly why genuinely useful evidence sits unused on most failures, not just the hard ones.

Example — A Failure With More Available Than Used

// A REAL, typical failure log:
// Error: expect(locator).toBeVisible() failed
//   Locator: getByRole('heading', { name: 'Order Confirmed' })
//   Expected: visible
//   Received: <element not found>

// What TYPICALLY gets read: this message, ALONE
// What's ALSO available, genuinely, but often UNUSED:
//   - the FULL stack trace (which test STEP, exactly)
//   - a SCREENSHOT at the moment of failure
//   - a VIDEO of the ENTIRE test run leading up to it
//   - a TRACE file with EVERY action and network REQUEST
//   - console LOGS from the page itself

Common Mistakes

  • Reading only the error message and moving on, even for a confusing failure. This page's example shows real, additional evidence usually sits one click away, genuinely available every time.
  • Assuming richer evidence collection requires new tooling. Playwright's config already supports capturing all of this — the next page covers exactly how to configure and collect it.

Best Practices

  • Treat every failure as having genuinely more available evidence than the error message alone — the habit of stopping there is worth deliberately resisting.
  • Configure comprehensive evidence capture by default, covered on the next page — cheap to collect, valuable when genuinely needed.

Hands-On Exercise

Pick a recent test failure from your own project. Open every piece of evidence Playwright captured for it — not just the error message — and note anything the video or trace revealed that the error message alone didn't make clear.

Key Takeaways

  • Playwright's TestInfo object already contains considerably more evidence than most teams use day to day.
  • Reading only the error message is an understandable habit under time pressure, not a limitation of what's actually available.
  • This chapter's remaining pages turn this already-available evidence into something systematically captured, analyzed, and reported — not new data Playwright doesn't already provide.
