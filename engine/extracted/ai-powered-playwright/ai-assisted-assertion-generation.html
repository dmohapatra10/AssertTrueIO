AI-Assisted Assertion Generation

Prerequisites: Traditional Playwright Assertions

What You'll Learn

  • Using AI to write real, deterministic assertion code from a plain description
  • Why this is Role 1 from this chapter's overview — the AI's job ends the moment the code is written
  • Generating expected results as concrete values, not vague descriptions

Introduction

This page is about AI helping write an assertion — not judging anything at runtime. Once the code below is generated, it's exactly as deterministic as anything from the previous page. This distinction matters enough that it's worth stating plainly before the code: nothing here becomes fuzzy just because AI helped write it.

Step-by-Step Implementation

// src/generate-assertion.ts
import { askClaude } from './ai-client';

export async function generateAssertionCode(
  expectedBehavior: string, pageContext: string
): Promise<string> {
  const prompt = `Expected behavior: "${expectedBehavior}"
Real, known page structure: ${pageContext}

Generate ONE Playwright assertion using Chapter 7's traditional
methods (toBeVisible, toHaveText, toHaveURL, toHaveCount,
toBeDisabled) that verifies this EXACTLY. Use ONLY elements
from the real structure given — never invent a selector.

Respond with ONLY the assertion code, nothing else.`;

  return askClaude(prompt);
}

Example — Generating ShopSmart's Order Confirmation Assertion

const code = await generateAssertionCode(
  'After checkout completes, the page shows an Order Confirmed heading',
  "Order confirmation page: heading (getByRole('heading', { name: 'Order Confirmed' }))"
);

// Real output:
// "await expect(page.getByRole('heading', { name: 'Order Confirmed' })).toBeVisible();"

Why It Matters — What Makes This Genuinely Safe

The generated line above is checked into a real test file, reviewed by a human the same way any generated code from Chapter 3 was, and from that point on, it behaves exactly like a hand-written assertion — auto-retrying, exact, deterministic. The AI's involvement was entirely at authoring time. This is precisely why Role 1 carries meaningfully less risk than Role 2: once written and reviewed, there's no ongoing AI judgment happening every time the test runs.

Common Mistakes

  • Skipping Chapter 3's validation discipline because "it's just an assertion." Generated assertion code deserves the same syntax and locator-existence checks as any other generated Playwright code.
  • Confusing this page's approach with Role 2. Nothing here runs AI judgment at test-execution time — that's a genuinely different, later page in this chapter.

Best Practices

  • Review generated assertion code the same way you'd review any generated Playwright code, using Chapter 3's validation functions before trusting it.
  • Keep the expected behavior description specific and concrete — a vague description produces an assertion that might check the wrong thing entirely.
