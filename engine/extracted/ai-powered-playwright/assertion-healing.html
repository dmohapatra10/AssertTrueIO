Assertion Healing

Prerequisites: Locator Healing

What You'll Learn

Introduction — A Genuinely Different, Higher-Risk Category

A locator either finds the right element or it doesn't — Chapter 6's runtime validation genuinely confirms this. An assertion's expected value is different: changing toHaveText('$49.98') to toHaveText('$54.98') can be a legitimate fix for a genuine, intentional price change, or it can be quietly papering over a real pricing bug. Existence on the page doesn't validate correctness here the way it does for a locator.

Why It Matters — The Real Danger, Concretely

A LOCATOR healing MISTAKE: the test still FAILS, just with a
DIFFERENT error — GENUINELY visible, GENUINELY safe to catch

An ASSERTION healing MISTAKE: the test now PASSES — SILENTLY
accepting a VALUE that might be a REAL, GENUINE application
BUG, not a legitimate change — the WORST possible outcome:
a test that LOOKS healthy while HIDING a real REGRESSION

Step-by-Step Implementation — A Deliberately Cautious Approach

// src/generate-assertion-fix.ts
import { askClaude } from './ai-client';

export interface AssertionFixCandidate {
  originalAssertion: string;
  proposedAssertion: string;
  requiresBusinessRuleConfirmation: boolean;
  reasoning: string;
}

export async function proposeAssertionFix(
  originalAssertion: string, actualObservedValue: string,
  businessContext: string
): Promise<AssertionFixCandidate> {
  const prompt = `A test asserts: ${originalAssertion}
The application actually shows: "${actualObservedValue}"
Business context: ${businessContext}

Propose an updated assertion ONLY if this change is CLEARLY
explainable by a legitimate business reason stated in the
context. If you cannot confirm this is legitimate rather than
a possible bug, set requiresBusinessRuleConfirmation to TRUE.

Respond with ONLY valid JSON:
{"proposedAssertion": string,
"requiresBusinessRuleConfirmation": boolean, "reasoning": string}`;

  const raw = await askClaude(prompt);
  const parsed = JSON.parse(raw);
  return { originalAssertion, ...parsed };
}

Code Explanation

requiresBusinessRuleConfirmation is this page's real, deliberate safeguard — it defaults toward caution rather than confidence. Unlike locator healing, where Chapter 6's runtime existence check provides genuine, independent confirmation, no equivalent check exists for "is this new expected value actually correct." The prompt is written to make the model admit uncertainty explicitly, rather than confidently proposing a fix it can't actually verify.

Example — A Genuinely Ambiguous ShopSmart Case

const fix = await proposeAssertionFix(
  "toHaveText('$49.98')", "$54.98",
  "ShopSmart occasionally runs promotional pricing, but no
  active promotion is documented for this product currently."
);

Common Mistakes

  • Applying assertion healing with the same confidence as locator healing. This page's whole point is that they carry genuinely different risk — existence on a page and correctness of a value are not the same kind of confirmation.
  • Treating requiresBusinessRuleConfirmation: true as a technicality to route around. It's the single most important field this function returns — the honest admission that automated confirmation genuinely isn't possible here.

Best Practices

  • Always route assertion healing with requiresBusinessRuleConfirmation: true to a human with real, specific business context — never treat it as equivalent to a validated locator fix.
  • Provide genuine, specific business context in the prompt — vague context makes it harder for the model to honestly distinguish a legitimate change from a possible bug.

Hands-On Exercise

Find a real assertion in your own test suite whose expected value has changed at least once before. Write out, honestly, what business context would have been needed to confirm that change was legitimate rather than a bug — and consider whether that context was actually available at the time.

Key Takeaways

  • Assertion healing carries genuinely higher risk than locator healing — a wrong fix here can silently hide a real regression rather than producing a visible failure.
  • No equivalent to Chapter 6's runtime existence check confirms an assertion's new value is correct — this gap is real and can't be automated away.
  • Defaulting to explicit uncertainty, via requiresBusinessRuleConfirmation, is the honest, correct response to this gap, not a limitation to work around.
