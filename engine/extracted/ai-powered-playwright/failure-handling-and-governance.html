Every earlier chapter addressed one test failing, one agent hitting a limit, one action getting blocked. This page addresses something different: the shared infrastructure itself — the MCP server every team depends on — genuinely failing.

Why It Matters — These Failures Affect Every Team at Once

A single agent hitting Chapter 13's own step limit affects one objective, one run. The MCP server going down affects every team's agent simultaneously — a genuinely different scale of impact that needs its own, real response plan, not just a retry.

Step-by-Step Implementation — A Real Fallback

// src/mcp-server-health-check.ts
import { Client } from '@modelcontextprotocol/sdk/client/index.js';

export async function checkServerHealthWithFallback(
  client: Client
): Promise<{ healthy: boolean; fallbackMode: boolean }> {
  try {
    await client.listTools();
    return { healthy: true, fallbackMode: false };
  } catch (error) {
    console.error('MCP server unreachable — entering fallback mode');
    // FALLBACK: pause ALL agents, alert the PLATFORM team
    // (Chapter 20'S own ownership model), and REFUSE new runs
    // until the SERVER is confirmed healthy AGAIN
    return { healthy: false, fallbackMode: true };
  }
}

Code Explanation

The real, deliberate choice here is refusing new runs during an outage, rather than letting agents fail individually and confusingly. A clean, explicit fallback state is genuinely easier for a team to diagnose and recover from than dozens of agents each failing in their own, separate, less-obvious way.

Why It Matters — A Real Governance Question This Track's Rules Don't Fully Answer

This track's earlier chapters gave clear, individual answers — Chapter 11 for code changes, Chapter 19 for security concerns. But what happens when Chapter 12's flaky-detection says a failure is known and safe to ignore, while Chapter 9's classification, on the same failure, says it's a genuine Application Defect? This is a real, genuine disagreement between two of this track's own systems, and it needs an explicit, human escalation path — not an automatic tiebreaker either safeguard imposes on its own.

Common Mistakes

  • Letting agents fail individually and silently during a shared infrastructure outage. This page's health-check fallback exists specifically to make an outage visible and diagnosable, rather than a confusing scatter of unrelated-looking individual failures.
  • Having no defined escalation path when this track's own systems genuinely disagree. Chapter 12's flaky detection and Chapter 9's classification can legitimately conflict — pretending this never happens leaves a real gap in governance.

Best Practices

  • Build an explicit health check and fallback mode for shared infrastructure, rather than relying on individual agents to fail gracefully on their own.
  • Define a real, human escalation path for genuine disagreement between this track's own automated systems — don't assume they'll always agree.

Interview Questions

Beginner: Why does this chapter operate at a genuinely different level than Chapter 14, even though both are architecture chapters?▾

Chapter 14 assembled one agent's internal architecture — Planner, Browser Tools, Observation, Evaluator, and Recovery, all within a single process pursuing one objective. This chapter operates one level up: multiple agents from different teams, sharing one real MCP server, CI/CD pipeline, evidence storage, and audit log, as one deployed system an entire organization depends on. The scale and the questions genuinely change — from "how does one agent reason" to "how does a shared system serve many agents safely."

Beginner: Why does explicit component ownership matter more for shared infrastructure than for something only one team uses?▾

When only one team uses something, that team naturally feels responsible for it by default. Shared infrastructure, used by multiple teams, doesn't have this natural default — without an explicit owner, it's easy for every team to assume someone else is responsible, especially when something breaks. Writing down clear ownership, as this chapter's second page argues, prevents this ambiguity from becoming a real problem exactly when it matters most, during an actual failure.

Intermediate: Explain why three individually well-behaved agents can still cause a real problem for shared infrastructure, using this chapter's own example.▾

Each agent respecting its own Chapter 13 rate limits only bounds that one agent's own individual load — it says nothing about what happens when multiple agents' individually-reasonable loads combine at the same shared server simultaneously. Three agents each staying within their own limits can still sum to three times the load the server was actually sized for, since no single agent's self-imposed limit accounts for other agents' concurrent activity. This is exactly why the chapter argues for a genuinely separate, server-wide limit independent of any individual agent's own restrictions.

Intermediate: Why does this chapter argue that system-wide observability requires aggregation rather than new instrumentation?▾

Chapter 18 and Chapter 19 already produce real, structured logs — per-call usage data and per-agent audit entries. The genuine gap isn't a lack of data; it's that this data sits in separate, per-agent or per-call records that no single log reveals the whole picture from. Aggregating existing logs by agent, as this chapter's example does, surfaces real, organization-level patterns — like one agent dominating system-wide cost — that were always present in the underlying data but invisible until combined. Building new, separate instrumentation would duplicate effort the existing logs already accomplish.

Advanced: Why does this chapter treat disagreement between Chapter 12's flaky detection and Chapter 9's failure classification as a genuine governance gap, rather than something to resolve with an automatic rule?▾

Both systems produce genuinely real, evidence-based conclusions from their own real data — flaky detection from accumulated history across many runs, classification from the specific evidence of one failure. Neither conclusion is inherently more authoritative than the other; picking one automatically (always trust flaky detection, or always trust classification) would be arbitrary and could be wrong in either direction. This is exactly the kind of genuine ambiguity Chapter 7 and Chapter 9 established belongs to real human judgment, not automated resolution — the disagreement itself is meaningful information a person should actually look at, not a tiebreak to automate away.

Scenario-based: A teammate proposes that during an MCP server outage, each affected agent should just retry with exponential backoff individually, rather than implementing this chapter's shared fallback mode. How would you respond?▾

I'd point to this chapter's own reasoning about scale of impact: an outage affects every connected agent simultaneously, and having each one retry independently, with its own backoff timing, produces a confusing scatter of individually-failing agents rather than one clear, diagnosable signal that the shared infrastructure itself is down. A human investigating would need to notice the pattern across many separate agent logs rather than seeing one clear "server unreachable, fallback mode active" state. Independent retries might also mean the server, if it's struggling rather than fully down, gets hit with a wave of retry traffic right as it's trying to recover — exactly the kind of uncoordinated load this chapter's server-wide thinking argues against. A shared, explicit fallback mode is both easier to diagnose and less likely to compound the original problem.
