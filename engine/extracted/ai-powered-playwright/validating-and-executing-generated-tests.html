Step-by-Step Implementation — Validation

// src/validate-test.ts
import { readFileSync } from 'fs';
import * as ts from 'typescript';
import { chromium } from '@playwright/test';

export interface ValidationResult {
  syntaxValid: boolean;
  syntaxError?: string;
  locatorsFound: string[];
  locatorsMissing: string[];
}

export function checkSyntax(filePath: string): {
  valid: boolean; error?: string
} {
  const code = readFileSync(filePath, 'utf-8');
  const result = ts.transpileModule(code, {
    compilerOptions: { module: ts.ModuleKind.CommonJS },
    reportDiagnostics: true,
  });
  const errors = result.diagnostics?.filter(
    (d) => d.category === ts.DiagnosticCategory.Error
  );
  if (errors && errors.length > 0) {
    return { valid: false, error: ts.flattenDiagnosticMessageText(
      errors[0].messageText, '\n'
    ) };
  }
  return { valid: true };
}

export async function checkLocatorsExist(
  filePath: string, pageUrl: string
): Promise<{ found: string[]; missing: string[] }> {
  const code = readFileSync(filePath, 'utf-8');
  const roleMatches = [...code.matchAll(
    /getByRole\('(\w+)', \{ name: '([^']+)' \}\)/g
  )];

  const browser = await chromium.launch();
  const page = await browser.newPage();
  await page.goto(pageUrl);

  const found: string[] = [];
  const missing: string[] = [];
  for (const [, role, name] of roleMatches) {
    const count = await page.getByRole(
      role as any, { name }
    ).count();
    (count > 0 ? found : missing).push(`${role}: ${name}`);
  }
  await browser.close();
  return { found, missing };
}

Code Explanation

Two genuinely independent checks happen here, matching Chapter 2's own distinction between exact checks and judgment calls — both are exact, deterministic checks, deliberately. checkSyntax confirms the generated code is even valid TypeScript before anything else happens. checkLocatorsExist goes further, extracting every getByRole call the AI generated and confirming each one genuinely matches something on the real, live ShopSmart page — not trusting the earlier "never invent a selector" instruction blindly, but actually verifying it held.

Step-by-Step Implementation — Execution

// src/validate-and-run.ts
import { checkSyntax, checkLocatorsExist } from './validate-test';
import { execSync } from 'child_process';

async function validateAndRun(filePath: string, pageUrl: string) {
  const syntax = checkSyntax(filePath);
  if (!syntax.valid) {
    console.error(`Syntax check FAILED: ${syntax.error}`);
    return;
  }

  const locators = await checkLocatorsExist(filePath, pageUrl);
  if (locators.missing.length > 0) {
    console.error(`Missing locators, NOT running: ${locators.missing.join(', ')}`);
    return;
  }

  console.log('Validation passed — executing against a real browser.');
  execSync(`npx playwright test ${filePath}`, { stdio: 'inherit' });
}

validateAndRun(
  'tests/generated/login-valid.spec.ts',
  'https://shopsmart.example.com/login'
);

Common Mistakes

  • Running generated code directly, skipping validation "just this once." The whole point of this page is that "just this once" is exactly when a hallucinated locator or a syntax error slips through.
  • Treating a passing syntax check as sufficient on its own. Code can be perfectly valid TypeScript and still reference a locator that doesn't exist on the real page — checkLocatorsExist exists specifically because syntax validity and correctness are genuinely different things.

Best Practices

  • Run both checks — syntax and locator existence — before ever executing generated code, never just one.
  • Keep validation and execution as separate, sequential steps, exactly as this page does, so a validation failure never silently proceeds to execution.

Interview Questions

Beginner: Why does this chapter's AI client store the system prompt once, rather than including it in every individual request?▾

A system prompt sets standing behavior for the entire session — instructions like "never invent a selector" that should apply to every single response. Setting it once, in the client module, guarantees this behavior applies consistently everywhere the client is used, without relying on every individual call site to remember to repeat it.

Beginner: What real problem does explicitly asking for "ONLY valid JSON, no other text" solve?▾

Without this instruction, models often add a friendly introductory or closing sentence around the JSON — which breaks JSON.parse, since it expects the entire string to be valid JSON. This single, explicit instruction meaningfully reduces how often a response fails to parse at all.

Intermediate: Why does checkLocatorsExist actually launch a real browser and check the live page, rather than just trusting that the system prompt's "never invent a selector" instruction worked?▾

An instruction in a prompt shapes the model's behavior — it doesn't guarantee it. This is the same reasoning Chapter 1 established about hallucination: a confidently-generated locator can still be wrong, regardless of how clearly it was instructed not to be. Actually launching a browser and checking whether each generated locator matches something real on the live page is genuine, empirical verification — not just trusting that an instruction was followed.

Intermediate: Why are syntax checking and locator-existence checking implemented as two separate functions, rather than one combined validation step?▾

They check genuinely different things and can fail independently. Code can be syntactically perfect TypeScript while still referencing a locator that doesn't exist on the real page — and, less commonly, malformed code could theoretically still contain locator strings a naive check might extract. Keeping them separate means a syntax failure is reported clearly as a syntax failure, and a locator failure is reported clearly as a locator failure, rather than one vague "validation failed" message that doesn't say which problem actually occurred.

Advanced: Why does validateAndRun check syntax first and return early on failure, rather than running both checks and reporting all problems at once?▾

checkLocatorsExist needs to parse the generated code with a regular expression to extract getByRole calls — if the code isn't even syntactically valid TypeScript, this extraction could behave unpredictably or simply be meaningless, since there's no guarantee malformed code's structure matches what the regex expects. Checking syntax first, and stopping immediately on failure, avoids running a second check against code that's already known to be broken — the same "cheap check before more expensive, less certain investigation" ordering principle worth applying generally, not just here.

Scenario-based: A teammate proposes skipping locator validation for "simple" generated tests to save time, reasoning "the AI already has the real locators in its prompt." How would you respond, using this chapter's own reasoning?▾

I'd point to this chapter's own distinction between an instruction shaping behavior and a guarantee. Providing real locators in the prompt genuinely reduces the chance of a hallucinated selector — it doesn't eliminate it, the same way Chapter 1's system prompt telling the model to "never invent a selector" doesn't guarantee it never will. The actual cost of skipping validation is a test that fails at execution time with a confusing "element not found" error, or worse, silently matches the wrong element — genuinely harder to debug than a validation failure with a clear, specific message would have been. The validation step is cheap, fast, and exists specifically to catch the cases where the prompt's instructions, however well-written, didn't fully hold.
