Why This Is Genuinely Bigger Than Chapter 6

Chapter 6's locator healing found a working locator so one test run could proceed — it never touched the actual test file. This chapter is about something meaningfully more consequential: proposing an actual change to source code, checking it doesn't break anything else in the suite, and only then presenting it for a human to accept or reject. The stakes are real, which is exactly why the architecture above has three real safety stages — Validation, Regression, and Approval — before anything reaches a committed file.

The Rule This Entire Chapter Is Built Around

Never silently modify the source code and declare the test successful. Every page in this chapter respects this rule — even the pages that generate and validate a fix stop short of applying it. The final page makes this explicit and non-negotiable.

Common Mistakes

  • Confusing this chapter's approach with Chapter 6's runtime healing. They're genuinely different in scope and risk — this chapter's later pages are explicit about the distinction.
  • Treating a validated, regression-free fix as ready to merge automatically. Passing every automated check is necessary, not sufficient — this chapter's final page explains why human approval remains non-negotiable regardless.

Best Practices

  • Read this chapter in order — each safety stage in the architecture above depends on the one before it.
  • Keep Chapter 6's locator healing and this chapter's self-healing mentally separate — they solve genuinely different problems at genuinely different levels of risk.

Key Takeaways

  • Self-healing proposes actual source code changes — a meaningfully bigger, riskier capability than Chapter 6's runtime-only locator substitution.
  • This chapter's architecture has three real safety stages — validation, regression testing, and human approval — before any change reaches committed code.
  • The rule against silent modification is non-negotiable throughout this chapter, not just a closing caveat.
