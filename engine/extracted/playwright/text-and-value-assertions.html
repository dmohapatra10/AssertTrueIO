Text & Value Assertions

Prerequisites: Assertions overview, Visibility & State Assertions

What is this?

These assertions check the actual content of an element or input: toHaveText(), toContainText(), toHaveValue(), and toHaveAttribute(). Where the visibility/state assertions ask "is this here and usable," these ask "does this say or hold the right thing."

Why it's important

Content is what most tests actually verify — a confirmation message, a calculated total, a filled-in field. Getting the exact-match-vs-substring choice right (the most common early confusion here) determines whether a test is meaningfully strict or just brittle.

toHaveText() vs. toContainText()

// toHaveText() — exact match of the FULL text content (whitespace-normalized)
await expect(page.getByRole('status')).toHaveText('Order confirmed');
// Fails if the element actually reads "Order confirmed — thank you!"

// toContainText() — substring match
await expect(page.getByRole('status')).toContainText('Order confirmed');
// Passes for "Order confirmed — thank you!" too

Use toHaveText() when the full, exact copy matters to the test (e.g., a strict legal disclaimer). Use toContainText() when only a key phrase matters and the surrounding copy is expected to vary or isn't the point of the test — this is the more common case in practice.

Basic Example — toHaveValue()

await page.getByLabel('Coupon code').fill('SAVE20');
await expect(page.getByLabel('Coupon code')).toHaveValue('SAVE20');

toHaveValue() checks an input, textarea, or select's current value — not its visible label or placeholder, which are different things entirely (see the Locators chapter's getByPlaceholder page for that distinction).

Detailed Example — toHaveAttribute()

// Confirm a link opens in a new tab, and a disabled button is really disabled
// at the DOM level, not just visually styled
await expect(page.getByRole('link', { name: 'Terms of Service' })).toHaveAttribute('target', '_blank');
await expect(page.getByRole('button', { name: 'Save' })).toHaveAttribute('disabled', '');

This is also how you'd verify accessibility-relevant attributes directly — aria-expanded, aria-current, aria-label — when the test's actual concern is the attribute itself, not an interaction outcome.

Real-World Example — Dynamic Total

test('cart total updates when quantity changes', async ({ page }) => {
  await page.goto('/cart');
  await page.getByLabel('Quantity').fill('3');

  await expect(page.getByTestId('line-total')).toHaveText('$44.97');
  await expect(page.getByTestId('cart-total')).toContainText('$44.97');
});

Regex Matching

// Match a dynamic order number without hardcoding it
await expect(page.getByText(/Order #ORD-\d+ confirmed/)).toBeVisible();
await expect(page.getByTestId('order-id')).toHaveText(/ORD-\d{5}/);

Both toHaveText() and toContainText() accept a regular expression instead of a string — the right tool whenever the exact value is dynamic (timestamps, generated IDs, counts) but its shape is predictable.

❌ Fragile vs. ✅ Recommended

// ❌ Brittle — breaks the moment unrelated copy around the number changes
await expect(page.getByTestId('order-id')).toHaveText('Order #ORD-10492 placed just now');

// ✅ Only asserts the part that actually matters to this test
await expect(page.getByTestId('order-id')).toContainText('ORD-10492');

Common Mistakes

  • Defaulting to toHaveText() everywhere — makes tests brittle against unrelated copy changes; reserve it for when the full exact text is genuinely the point.
  • Using toHaveText() on an element containing nested children and being surprised the match includes all their concatenated text too — this is correct behavior, but easy to forget when a component has more structure than expected.
  • Asserting toHaveValue() on a non-form element — it's specifically for input/textarea/select; use toHaveText() for a <div> or <span> instead.

Edge Cases

  • Whitespace-only differences — toHaveText() normalizes whitespace (collapsing multiple spaces/newlines), so minor formatting differences in the source HTML don't cause false failures.
  • Case sensitivity — both assertions are case-sensitive by default; pass a regex with the i flag when case shouldn't matter.

Debugging

A failed text assertion's error message shows both the expected and actual value side by side — read it closely before assuming the locator is wrong; often the locator is correct and the copy simply doesn't match what was assumed.

Best Practices

  • Default to toContainText() unless the full exact text is specifically what's under test.
  • Use regex for any value with dynamic, unpredictable-but-shaped content (IDs, timestamps, counts).
  • Reserve toHaveAttribute() for attributes the test genuinely cares about — don't use it as a roundabout way to check visible text.

Practice Exercise

Summary

toHaveText() is an exact, full-content match; toContainText() is a substring match and the more commonly correct default. toHaveValue() checks form control values specifically, and toHaveAttribute() checks raw DOM attributes — all support regex for dynamic content.

Interview Questions

When would you choose toHaveText() over toContainText(), given the latter is more forgiving?▾
When the full, exact copy is itself the requirement being tested — a legal disclaimer, a precise error message mandated by spec, or any case where extra or missing text would itself be a bug. In most everyday assertions, only a key phrase matters and the surrounding copy is expected to change independently, which is why toContainText() is the more common default.
When would you choose toHaveText() over the more forgiving toContainText()?▾
When the full, exact copy is itself the requirement — like a precise legally-mandated message — rather than just a key phrase within changeable surrounding text.
Does toHaveText() work correctly when the text is split across nested child elements?▾
Yes — it matches the full concatenated text content of the element, whitespace-normalized, regardless of nested markup.
What's the right assertion for a form input's current value?▾
toHaveValue() — toHaveText() is for element text content, not form control values.
How would you assert on a dynamic order number without hardcoding it?▾
Pass a regex to toContainText() or toHaveText() instead of a plain string, matching the pattern rather than an exact value.
