POST Requests

Prerequisites: GET Requests

What is this?

request.post(url: string, options?: { data?, headers?, multipart? })

POST creates a new resource (or triggers a non-idempotent action) by sending a request body. This is the most common method for API-based test data setup — creating an order, registering a user, submitting a form — exactly the pattern the API Testing overview page's "API for setup, UI for verification" principle relies on.

Why it's important

Almost every UI-focused test that uses the API for fast setup is making a POST request somewhere. Getting the payload shape and validation right here is what makes that whole pattern reliable rather than a source of confusing, hard-to-debug setup failures.

Basic Example

const response = await request.post('/api/orders', {
  data: { item: 'Wireless Mouse', quantity: 2 },
});

expect(response.status()).toBe(201); // 201 Created, not 200 — a common validation detail
const order = await response.json();
expect(order.id).toBeDefined();

Checking specifically for 201 rather than just response.ok() is worth being deliberate about — ok() is true for any 2xx status, but a well-behaved creation endpoint should specifically return 201 Created, and asserting on the exact code catches an API that's technically succeeding but not following its own contract.

The data Option — Request Payload

// Playwright automatically serializes a plain object to JSON and sets
// Content-Type: application/json — no manual JSON.stringify() needed
await request.post('/api/orders', {
  data: { item: 'Keyboard', quantity: 1, giftWrap: true },
});

// For non-JSON payloads, pass a string or Buffer directly
await request.post('/api/webhooks/raw', {
  data: 'raw-plain-text-payload',
  headers: { 'Content-Type': 'text/plain' },
});

Detailed Example — multipart/form-data

// File uploads via API use the multipart option, not data
const response = await request.post('/api/documents', {
  multipart: {
    title: 'Q3 Report',
    file: {
      name: 'report.pdf',
      mimeType: 'application/pdf',
      buffer: fs.readFileSync('fixtures/report.pdf'),
    },
  },
});
expect(response.status()).toBe(201);

This is the API-level equivalent of the Actions chapter's setInputFiles() — same underlying goal (get a file to the server), completely different mechanism, since here there's no browser or file input involved at all, just a raw HTTP multipart body.

Real-World Example — Validating the Full Response Shape

test('creating an order returns the full expected shape', async ({ request }) => {
  const response = await request.post('/api/orders', {
    data: { item: 'Wireless Mouse', quantity: 2 },
  });

  expect(response.status()).toBe(201);
  const order = await response.json();

  expect(order).toMatchObject({
    item: 'Wireless Mouse',
    quantity: 2,
    status: 'pending',
  });
  expect(order.id).toEqual(expect.stringMatching(/^ORD-\d+$/));
  expect(order.createdAt).toBeDefined();
});

toMatchObject() checks that the listed fields match without requiring an exact match on every field in the response — the right tool when a response has server-generated fields (an ID, a timestamp) you want to validate the shape of, not an exact value.

Why POST Isn't Idempotent

// Calling this twice creates TWO separate orders — POST has no built-in
// protection against duplicate submission, unlike PUT (covered on the next page)
await request.post('/api/orders', { data: { item: 'Mouse', quantity: 1 } });
await request.post('/api/orders', { data: { item: 'Mouse', quantity: 1 } }); // a second, distinct order

This matters directly for test design: if a test retries a POST request after a timeout without knowing whether the first attempt actually succeeded, it risks creating duplicate data. Some APIs support an idempotency key header for exactly this scenario — worth checking your API's documentation for one if retry-safety around POST is a genuine concern for your suite.

❌ Fragile vs. ✅ Recommended

// ❌ Only checking response.ok(), missing that the API returned the wrong status
const response = await request.post('/api/orders', { data: { /* ... */ } });
expect(response.ok()).toBeTruthy(); // true for 200 OR 201 — doesn't catch a wrong-but-passing status

// ✅ Assert the specific expected status for a creation endpoint
expect(response.status()).toBe(201);

Common Mistakes

  • Using response.ok() instead of an exact status check when the specific code (201 vs. 200) actually matters to the contract being tested.
  • Manually calling JSON.stringify() on the data option — Playwright already serializes plain objects; double-stringifying sends malformed JSON.
  • Not validating the response body at all, only the status code — a 201 with a malformed or incomplete body is still a real bug.
  • Assuming POST requests are safe to blindly retry without considering duplicate-creation risk.

Edge Cases

  • Validation errors — POST-ing invalid data (missing required field, wrong type) should return a 4xx with a useful error body; testing this path is as important as testing successful creation.
  • Large payloads — some APIs cap request body size; a test intentionally exceeding it can verify the API rejects it gracefully rather than crashing.

Debugging

If a POST unexpectedly fails, log both the status code and the full response body — a 400 response almost always includes a useful validation error message that immediately explains what was wrong with the payload, and reading it is faster than guessing.

Best Practices

  • Assert the specific expected status code for creation endpoints, not just ok().
  • Use toMatchObject() to validate response shape while allowing for server-generated fields.
  • Test validation-error paths (missing/invalid fields), not just the happy path.
  • Use the multipart option specifically for file uploads — never try to encode file content into the data option.

Practice Exercise

Write a test that POSTs an order with a missing required field (e.g., no quantity) and asserts the API returns a 400 with a validation error message mentioning the missing field.

Summary

POST creates resources via a request body — Playwright's data option handles JSON serialization automatically, and multipart handles file uploads. Assert the specific expected status code (usually 201) rather than just ok(), validate the response shape, and remember POST has no built-in protection against duplicate creation on retry.

Interview Questions

Why might it be risky to automatically retry a failed POST request in a test, and what's a safer approach?▾
POST isn't idempotent — if the first request actually succeeded on the server but the response was lost (a timeout, a network blip), retrying creates a second, duplicate resource. A safer approach is to first check whether the resource already exists (e.g., a GET by some natural key) before retrying, or to rely on an idempotency key if the API supports one, rather than blindly resubmitting the same POST.
Why check for status 201 specifically, not just response.ok()?▾
ok() is true for any 2xx status; asserting the exact code catches an API that's technically succeeding but not following its documented contract.
How does Playwright handle serializing the data option?▾
It automatically converts a plain object to JSON and sets the Content-Type header — no manual JSON.stringify() needed.
How do you upload a file via a POST request?▾
Use the multipart option, not data — passing file content as name/mimeType/buffer.
Why is POST considered non-idempotent?▾
Calling the same POST twice creates two separate resources, unlike PUT, which has no built-in protection against duplicate submission on retry.
