Chapter 16: Playwright Test Runner

Prerequisites: Getting Started

What is this?

Every example so far has used test() and expect() from @playwright/test without much explanation of what that package actually does. This chapter is the deliberate deep dive: what the test runner manages, how it discovers and organizes tests, and why it exists as a separate concern from the automation library itself.

Why it's important

Playwright is really two things bundled together: a browser automation library (everything covered in earlier chapters — locators, actions, contexts) and a test runner (@playwright/test) built on top of it. Understanding that split clarifies which problems each part solves — automation vs. organizing, running, retrying, and reporting on tests.

Mental Model

@playwright/test  (the test runner)
   │
   ├── Discovers test files
   ├── Manages fixtures (setup/teardown)
   ├── Runs files in parallel across workers
   ├── Retries failed tests
   ├── Generates reports
   │
   └── playwright-core  (the automation library underneath)
          Browser, BrowserContext, Page, locators, actions

None of the runner's responsibilities are part of core browser automation — a raw script using chromium.launch() directly gets none of it for free, which is why the Getting Started chapter recommended @playwright/test from the very first line.

What the Test Runner Provides

  • Test discovery — finds every file matching the configured pattern (default: *.spec.ts) under testDir
  • Fixtures — automatic setup/teardown, like the page fixture used throughout this course (its own chapter)
  • Parallelization — runs test files concurrently across workers by default
  • Retries — automatic re-running of failed tests, configurable per environment
  • Reporting — HTML, JSON, JUnit, and other output formats
  • Projects — running the same suite across multiple browsers/devices/configs

Basic Example — test() and describe()

import { test, expect } from '@playwright/test';

test.describe('checkout flow', () => {
  test('completes with a valid card', async ({ page }) => {
    // ...
  });

  test('shows an error for a declined card', async ({ page }) => {
    // ...
  });
});

test.describe() groups related tests — mainly for reporting clarity and for scoping shared hooks (covered in the next chapter), not for sharing state between tests, which remain fully isolated from each other regardless of grouping.

Detailed Example — test.step() for Readable Reports

test('completes checkout end to end', async ({ page }) => {
  await test.step('add item to cart', async () => {
    await page.goto('/products/wireless-mouse');
    await page.getByRole('button', { name: 'Add to cart' }).click();
  });

  await test.step('fill shipping details', async () => {
    await page.getByLabel('Address').fill('221B Baker Street');
    await page.getByLabel('City').fill('London');
  });

  await test.step('complete payment', async () => {
    await page.getByLabel('Card number').fill('4242 4242 4242 4242');
    await page.getByRole('button', { name: 'Pay now' }).click();
  });

  await expect(page.getByText('Order confirmed')).toBeVisible();
});

test.step() doesn't change execution at all — it's purely for organizing the HTML report and Trace Viewer timeline into named, collapsible sections, which makes a long end-to-end test's failure point immediately obvious ("failed during 'complete payment'") instead of requiring a full read of the test body.

Test Modifiers — skip, fixme, slow, only, fail

test.skip('not yet implemented', async ({ page }) => { /* ... */ });

test.fixme('known broken, tracked in JIRA-4821', async ({ page }) => { /* ... */ });

test('slow legacy page', async ({ page }) => {
  test.slow(); // triples the timeout for this test only
  // ...
});

test.only('debugging this one test in isolation', async ({ page }) => {
  // when present, only .only tests run — remove before committing
});

test.fail('known browser bug, tracked upstream', async ({ page }) => {
  // this test is EXPECTED to fail — the suite reports an error only if it unexpectedly passes
  await expect(page.getByText('Never actually shows')).toBeVisible();
});

test.skip() and test.fixme() look similar but signal different things: skip is for tests that shouldn't run right now for a deliberate reason (an unsupported browser, a feature flag), while fixme specifically marks a test that's currently failing due to a known bug — useful for keeping the bug visible in the report rather than silently excluding it. test.only() is useful while actively writing or debugging a single test, but it's also a common source of an accidentally-skipped CI suite if left in a commit — most teams lint against it being merged. test.fail() is the least common of the five: it marks a test as expected to fail (a known upstream bug, a not-yet-supported browser quirk) — the test still runs, but the suite only reports a problem if it unexpectedly starts passing, which is a useful signal that the underlying issue was fixed and the annotation can be removed.

Annotations and Test Metadata

Beyond the five modifiers above, Playwright has a separate, more general annotation mechanism for attaching arbitrary metadata to a test — a JIRA ticket link, an owning team, a category — that shows up in the HTML report but doesn't change how the test runs at all.

test('refund flow matches PCI compliance rules', async ({ page }, testInfo) => {
  testInfo.annotations.push({
    type: 'ticket',
    description: 'https://jira.example.com/browse/PAY-482',
  });
  // ...
});

This is different from test.skip()/test.fixme(), which are also technically annotations under the hood but specifically ones the runner acts on (skipping execution, marking expected failure). A custom annotation like the one above is purely informational — it's for humans reading the report, not for the runner itself.

Tags — the Dedicated tag Option

Putting @smoke directly in a test's title (shown earlier) works and is common, but Playwright also has a dedicated tag option that keeps the title itself clean and is what most newer projects reach for:

test('completes checkout', { tag: '@smoke' }, async ({ page }) => {
  // ...
});

// A test can carry more than one tag
test('admin can refund an order', { tag: ['@smoke', '@admin'] }, async ({ page }) => {
  // ...
});
# Filtering works exactly the same way regardless of which approach was used
npx playwright test --grep @smoke

Functionally, title-based tags and the tag option filter identically with --grep — the dedicated option's advantage is purely readability: a test's title stays a plain English sentence instead of getting cluttered with @smoke @admin @regression appended to the end of it.

Real-World Example — Organized Suite Structure

import { test, expect } from '@playwright/test';

test.describe('order management', () => {
  test.describe('as an admin', () => {
    test('can cancel any order', async ({ page }) => { /* ... */ });
    test('can issue a refund', async ({ page }) => { /* ... */ });
  });

  test.describe('as a customer', () => {
    test('can cancel their own pending order', async ({ page }) => { /* ... */ });
    test('cannot cancel a shipped order', async ({ page }) => { /* ... */ });
  });
});

Nested describe blocks like this produce a readable HTML report tree (order management → as an admin → can cancel any order) and let role-specific setup live in a hook scoped to just that nested block — covered fully in the Hooks chapter.

Tags for Selective Runs

test('completes checkout @smoke', async ({ page }) => { /* ... */ });
# Run only tests tagged @smoke
npx playwright test --grep @smoke

Tagging tests in their title (or via the newer dedicated tag option) and filtering with --grep is how most teams implement a fast "smoke suite" that runs on every commit, separate from a slower full regression suite that runs less frequently.

❌ Fragile vs. ✅ Recommended

// ❌ Sharing mutable state between tests via a describe-scoped variable
let createdOrderId;
test.describe('orders', () => {
  test('creates an order', async ({ page }) => { createdOrderId = '...'; });
  test('can view the created order', async ({ page }) => { /* uses createdOrderId — fragile! */ });
});

// ✅ Each test is fully self-contained, using a fixture or setup step for shared needs
test('can view an order', async ({ page, createTestOrder }) => {
  const order = await createTestOrder();
  // ...
});

Common Mistakes

  • Committing a test.only() that was left in from local debugging, silently disabling the rest of the suite in CI.
  • Using describe blocks to share mutable state between tests (a variable set in one test, read in another) — tests should stay independent regardless of grouping, since parallel execution makes ordering assumptions unreliable anyway.
  • Writing automation scripts with a raw chromium.launch() instead of @playwright/test, then manually reimplementing parallelization or retries that the test runner already provides.
  • Confusing skip and fixme — using skip for a genuinely broken test hides it from bug-tracking visibility that fixme preserves.

Edge Cases

  • Conditional skipping based on project/browser — test.skip(browserName === 'webkit', 'not supported on Safari yet') lets a single test file skip only for specific configured projects rather than needing entirely separate files.
  • Nested test.step() calls — steps can be nested inside other steps, useful for breaking a long step down further without flattening the report structure.

Debugging

UI Mode (Chapter 2) shows test.step() boundaries directly in its timeline, making it easy to jump straight to the step that failed rather than scrubbing through a flat list of every individual action.

Best Practices

  • Use describe blocks primarily for report readability and scoped hooks, not as a substitute for well-named individual tests.
  • Wrap logical phases of a long test in test.step() for report and trace clarity.
  • Lint or CI-check against committed test.only() calls.
  • Default to @playwright/test for anything that will run more than once or needs CI integration — reach for the raw library API only for one-off scripts.

Practice Exercise

Write a test for a multi-step registration flow (account info → profile details → confirmation) using test.step() for each phase, and tag it @smoke so it can be selectively run with --grep.

Summary

@playwright/test is the layer that turns browser automation into an organized, parallel, retryable, reportable test suite — discovery, fixtures, parallelization, retries, and reporting are all its responsibility, distinct from the automation library underneath it. describe groups tests for readability and scoped hooks without sharing state between them, and test.step()/tags help organize both reports and selective test runs.
