Network Mocking

Prerequisites: API Testing, waitForRequest() & waitForResponse()

What is this?

page.route() intercepts network requests before they reach the real server, letting a test fulfill them with custom data, modify them, or block them entirely. This is a different tool from waitForResponse() (which observes real traffic) — route() actively controls what the page receives.

Why it's important

Mocking lets you test UI states that are hard or slow to produce with a real backend — an empty state, an error state, a specific edge-case payload — without needing the actual server to cooperate. It's also essential for isolating a UI test from a flaky or slow third-party dependency.

Basic Example — Mocking a Response

await page.route('**/api/orders', (route) => {
  route.fulfill({
    status: 200,
    contentType: 'application/json',
    body: JSON.stringify([{ id: 1, item: 'Wireless Mouse', status: 'shipped' }]),
  });
});

await page.goto('/orders');
await expect(page.getByText('Wireless Mouse')).toBeVisible();

The route handler must be registered before the navigation/action that triggers the request — the same before-not-after ordering rule covered for waitForResponse() and dialogs earlier in this course.

route.continue() — Modifying a Real Request

// Let the request go to the real server, but modify it first —
// e.g., inject a header every request needs during testing
await page.route('**/api/**', (route) => {
  route.continue({
    headers: { ...route.request().headers(), 'X-Test-Session': 'true' },
  });
});

Unlike fulfill() (which fully replaces the response), continue() lets the real request proceed with modifications — useful for injecting headers or altering a request without faking the entire response.

route.abort() — Simulating Network Failure

test('shows an error state when the orders API fails', async ({ page }) => {
  await page.route('**/api/orders', (route) => route.abort('failed'));

  await page.goto('/orders');
  await expect(page.getByText('Failed to load orders')).toBeVisible();
});

This tests a UI state that's genuinely difficult to reliably produce with a real backend — the network literally failing — and it's one of the more valuable, otherwise-hard-to-reach cases mocking unlocks.

Detailed Example — Testing an Empty State

test('shows an empty state when there are no orders', async ({ page }) => {
  await page.route('**/api/orders', (route) =>
    route.fulfill({ status: 200, contentType: 'application/json', body: '[]' })
  );

  await page.goto('/orders');
  await expect(page.getByText('No orders yet')).toBeVisible();
  await expect(page.getByRole('link', { name: 'Browse products' })).toBeVisible();
});

Getting a real backend into a genuinely empty state for a test can require careful, fragile setup (deleting all existing data) — mocking sidesteps that entirely and makes the empty-state test trivially reliable.

Real-World Example — Modifying Part of a Real Response

test('discount banner appears when a promo is active', async ({ page }) => {
  await page.route('**/api/promotions/active', async (route) => {
    const response = await route.fetch(); // get the real response first
    const json = await response.json();
    json.discountPercent = 25; // override just this one field
    await route.fulfill({ response, json });
  });

  await page.goto('/');
  await expect(page.getByText('25% off today only!')).toBeVisible();
});

route.fetch() retrieves the real response so you can modify part of it rather than fully fabricating the whole payload — useful when most of a response is realistic and only one field needs to be forced to a specific test value.

❌ Fragile vs. ✅ Recommended

// ❌ Mocking everything, including flows the test is actually meant to verify end-to-end
await page.route('**/api/**', (route) => route.fulfill({ /* fake everything */ }));
// This "checkout" test no longer proves checkout actually works against a real backend

// ✅ Mock only what's needed to reach a specific hard-to-produce state;
// keep genuine end-to-end tests hitting the real API
await page.route('**/api/inventory/wireless-mouse', (route) =>
  route.fulfill({ status: 200, body: JSON.stringify({ stock: 0 }) })
);

When Mocking Is the Wrong Choice

Mocking is powerful, but a suite that mocks everything stops verifying that the frontend and backend actually work together — it only proves the frontend renders correctly for data shapes you assumed were correct. Keep a meaningful set of genuine end-to-end tests hitting the real API alongside targeted mocked tests for states that are otherwise hard to reach.

Common Mistakes

  • Mocking core happy-path flows that should be verified against the real backend, losing genuine end-to-end confidence.
  • Registering the route handler after the triggering navigation — like other event-based patterns in this course, this must happen first.
  • Hardcoding a mocked response shape that drifts from the real API over time, silently passing tests against data the backend no longer actually returns.
  • Using an overly broad route pattern ('**/*') when a narrower one would avoid accidentally intercepting unrelated requests.

Edge Cases

  • Multiple route handlers matching the same request — the most recently registered matching handler takes precedence; be deliberate about registration order if a test needs layered behavior.
  • Requests that should sometimes pass through and sometimes be mocked — call route.continue() conditionally inside the handler based on request properties, rather than registering/unregistering separate handlers.

Debugging

If a route handler doesn't seem to fire, double-check the glob pattern actually matches the real request URL — Trace Viewer's Network tab (Chapter 15) shows the exact URLs requested, which is the fastest way to spot a pattern mismatch.

Best Practices

  • Reserve mocking for states that are genuinely hard to produce with a real backend — errors, empty states, edge-case payloads — not as a default for all tests.
  • Keep a core set of unmocked, real end-to-end tests to catch actual frontend/backend integration issues.
  • Use narrow, specific route patterns rather than broad catch-alls, to avoid accidentally intercepting unrelated traffic.
  • Prefer route.fetch() plus a partial override over fully fabricating a response, when most of the real data is fine and only one part needs to be forced.

Practice Exercise

Write a test that mocks a slow-loading API (using route.fulfill() with a deliberate delay before responding) and verifies a loading spinner appears while the request is pending, then disappears once it resolves.

Summary

page.route() intercepts requests before they reach the real server — fulfill() fakes a response entirely, continue() modifies a real request in flight, and abort() simulates network failure. Mocking is valuable for otherwise-hard-to-reach UI states, but should complement, not replace, genuine end-to-end tests against the real backend.

Interview Questions

What's the risk of mocking every API call in your entire test suite?▾
A fully mocked suite only proves the frontend renders correctly for the specific data shapes you assumed — it stops verifying that the frontend and backend actually agree on their contract. A backend change that alters a response shape could break production while every mocked test keeps passing, since the mocks were never updated to reflect the real change. A healthy suite mixes targeted mocking for hard-to-reach states with genuine end-to-end coverage against the real API.
