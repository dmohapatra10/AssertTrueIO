Chapter 7: Waiting and Synchronization

Prerequisites: Actions, Assertions

What is this?

This chapter goes deeper into exactly what Playwright waits for automatically, and — more importantly — what it does not wait for, since that gap is where most remaining flakiness in a Playwright suite tends to live. Each piece gets its own dedicated page:

  1. Auto-Waiting Explained — what's already covered, and where it stops
  2. waitForURL() & waitForLoadState() — navigation-driven waiting
  3. waitForRequest() & waitForResponse() — network-driven waiting
  4. waitForSelector() & waitForTimeout() — the legacy method and the anti-pattern

Why is it important?

Actions and assertions cover waiting for elements. They don't know about your application's specific async behavior — a toast that appears after a debounced API call, a chart that renders after a WebSocket message, an animation your app fires manually. Knowing the right tool for those cases is what separates a genuinely reliable suite from one that's flaky "sometimes, for reasons nobody's tracked down."

What's already automatic

  • Actions wait for actionability (attached, visible, stable, enabled, receives events) — see the Actions chapter.
  • Web-first assertions retry until they pass or time out — see the Assertions chapter.
  • page.goto() waits for navigation to complete by default.
  • Playwright waits for the page to fire the load event and for network activity to settle in most navigation scenarios.

Given all of that, explicit waiting is the exception, not the default — reach for it only when the situation below genuinely applies.

When you still need to wait explicitly

Waiting for a specific network response — useful when an action triggers a background request and the UI update depends on its result, but there's no visible loading indicator to key off:

const [response] = await Promise.all([
  page.waitForResponse((res) => res.url().includes('/api/orders') && res.status() === 200),
  page.getByRole('button', { name: 'Place order' }).click(),
]);

Waiting for a specific state beyond default load — for pages with heavy client-side rendering after the initial load:

await page.goto('/dashboard');
await page.waitForLoadState('networkidle'); // no network requests for 500ms

networkidle is useful but should be a deliberate, occasional choice — not a reflexive habit, since some pages (analytics beacons, polling widgets) never truly go idle.

Waiting on a custom condition — for state that isn't expressible as a locator or a network call, such as a value in a JS variable set by the page itself:

await page.waitForFunction(() => window.appReady === true);

What to never do: hard-coded sleeps

// Anti-pattern — do not do this
await page.getByRole('button', { name: 'Submit' }).click();
await page.waitForTimeout(3000); // guessing how long is "enough"
await expect(page.getByText('Success')).toBeVisible();

A fixed sleep is both unreliable and slow: too short and it fails intermittently on a slow CI run; too long and it wastes real time on every single test, every single run, even when the condition was ready in 100ms. page.waitForTimeout() exists mainly for debugging — it's a deliberate escape hatch, not a synchronization strategy.

Real-world example: waiting for an async search

import { test, expect } from '@playwright/test';

test('debounced search shows filtered results', async ({ page }) => {
  await page.goto('/products');

  await page.getByRole('searchbox').fill('headphones');

  // The search is debounced client-side and fires an API call —
  // wait for that specific response instead of guessing a delay.
  await page.waitForResponse((res) => res.url().includes('/api/search'));

  await expect(page.getByRole('listitem')).toHaveCount(12);
});

Common mistakes

  • Adding waitForTimeout() as a first response to any flaky test, instead of identifying what specific condition the test is actually waiting on.
  • Using networkidle as a default habit on every navigation, even for simple pages where the default load wait is already sufficient.
  • Waiting for a network response by URL substring that's too generic, causing the wait to resolve on the wrong request.

Best practices

  • Treat any hard-coded sleep in a PR as a signal to ask "what is this actually waiting for?" rather than accepting it.
  • Prefer waiting for a visible UI change (an assertion) over waiting for a network response, when both are available — the UI is what the user actually experiences.
  • Reserve waitForFunction() for state genuinely not exposed any other way; it's the least readable and hardest-to-debug option.

Summary

Playwright automatically handles the waiting that actions and assertions need. Explicit waiting — for a specific network response, a load state, or a custom condition — is for cases outside that default coverage, and hard-coded sleeps should almost never appear in a Playwright test.

Interview Questions

Why is page.waitForTimeout() considered an anti-pattern in most Playwright tests?▾
It waits a fixed duration regardless of actual page state, which makes tests both unreliable (too short on a slow run) and slow (too long on a fast run, on every execution). Playwright's actionability checks and web-first assertions already provide dynamic, condition-based waiting for almost every scenario a fixed sleep would be used for.
What three things does Playwright wait for automatically?▾
Actionability before actions, retrying web-first assertions, and initial page navigation via goto().
What's a case Playwright's automatic waiting can't cover?▾
Application-specific async behavior with no DOM or navigation signal — a WebSocket-driven update or a value set only in a JS variable, for example.
Why is networkidle risky on a dashboard with live polling widgets?▾
The network may never go fully idle for 500ms, causing the wait to run out its full timeout rather than resolving quickly.
What's the single biggest reason waitForTimeout() is discouraged?▾
It's both unreliable (too short under load) and wasteful (too long when the real condition resolves faster) — a fixed guess instead of a real signal.
