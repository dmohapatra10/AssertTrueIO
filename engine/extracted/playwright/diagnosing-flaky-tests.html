Diagnosing Flaky Tests

Prerequisites: Parallel Execution & Workers, Trace Viewer

What is this?

A flaky test passes and fails inconsistently with no code change in between. This chapter is a systematic checklist for finding the real cause — pulling together nearly every earlier chapter's failure modes into one diagnostic process, since flakiness is rarely a new category of bug, just an unaddressed instance of one already covered.

Why it's important

Flaky tests are worse than tests that simply fail — they erode trust in the whole suite. Once a team starts assuming "it's probably just flaky" and re-running failures without investigating, real bugs start slipping through disguised as flakiness. Retries (Configuration chapter) can absorb genuine environmental noise, but should never be the first or only response to a newly flaky test.

Step 1 — Reproduce in Isolation

npx playwright test flaky-test.spec.ts --workers=1 --repeat-each=10

--repeat-each runs the same test multiple times in a row — if it fails even running alone, repeatedly, the cause is internal to the test itself (a race condition, a hard wait) rather than cross-test interference. If it only fails as part of the full parallel suite, revisit the Parallel Execution chapter's shared-state checklist.

Step 2 — Read the Trace, Not Just the Error

npx playwright test flaky-test.spec.ts --trace on

Force tracing on for every run (not just on-first-retry) while actively diagnosing — you want a trace from a passing run and a failing run to compare, not just the eventual failure. Open both in Trace Viewer and look for where they diverge.

Detailed Example — Diagnosing a Real Case

// The symptom: this test fails about 1 in 10 runs, always at the same assertion
test('search results update after typing', async ({ page }) => {
  await page.goto('/search');
  await page.getByRole('searchbox').fill('mouse');
  await expect(page.getByText('12 results')).toBeVisible(); // fails intermittently here
});

Working through the checklist: not shared state (fails even with workers: 1). Not a hard wait (there isn't one). Locator looks specific enough. That leaves race conditions — and indeed, this search is debounced, and fill() doesn't fire the same keystroke events a debounce timer listens for (a case covered on the fill() vs. pressSequentially() page). The fix:

await page.getByRole('searchbox').pressSequentially('mouse', { delay: 100 });
await expect(page.getByText('12 results')).toBeVisible();

This is the point of the checklist — flakiness almost always maps back to a specific, already-covered mechanism once you work through it systematically, rather than being a mysterious new category of problem.

Real-World Example — CI-Only Flakiness

// playwright.config.ts — temporarily, for diagnosis only
export default defineConfig({
  workers: 1,          // rule out shared-state/parallelism
  retries: 0,           // don't let a retry hide the failure
  use: { trace: 'on' }, // capture every run, not just failures
});

When flakiness only appears in CI, deliberately narrow the config like this temporarily to isolate whether it's a parallelism issue, then download and inspect the resulting traces — this is almost always faster than guessing from CI logs alone.

❌ Fragile vs. ✅ Recommended Response to Flakiness

// ❌ Silencing the symptom
test('search results update after typing', async ({ page }) => {
  test.retry(3); // just try more times and hope
  // ...
});

// ✅ Diagnosing and fixing the actual mechanism
await page.getByRole('searchbox').pressSequentially('mouse', { delay: 100 });

Common Mistakes

  • Adding retries as the first response to a newly flaky test instead of diagnosing it — this can mask a real, worsening problem for a long time.
  • Assuming "it's just flaky" without following the checklist — nearly every real case maps to one of the six causes above; "no identifiable cause" is rare once you actually look.
  • Diagnosing with the same parallel/worker settings as production CI, making it hard to isolate whether the cause is shared state versus something internal to the test.
  • Not comparing a passing trace against a failing trace — the difference between the two is often exactly where the bug lives.

Edge Cases

  • Flakiness tied to time of day (a batch job that runs at a specific hour, affecting data the test depends on) — genuinely real, and easy to dismiss as random; check for any time-based external dependency before ruling this out.
  • Flakiness that only appears after many consecutive runs (a resource leak, an accumulating side effect) — --repeat-each with a high count can surface this even when a single isolated run looks fine.

Debugging

The fastest path through most flaky-test investigations: reproduce with --repeat-each and workers=1 first (isolating internal-to-the-test causes from cross-test causes), then read a failing trace side-by-side with a passing one — the checklist above covers the great majority of what that comparison will reveal.

Best Practices

  • Treat flakiness as a bug to diagnose, not noise to retry past.
  • Use retries in CI to absorb genuine environmental variance, never as a substitute for fixing a known-flaky test.
  • Keep a flaky-test triage habit — a test that fails intermittently should be investigated within the checklist above before being dismissed.
  • Force full tracing temporarily while diagnosing, even though on-first-retry is the right permanent CI setting.

Practice Exercise

Given a test that fails roughly 1 in 20 runs immediately after clicking a "Save" button, write out the diagnostic steps you'd take in order, and identify which of the six checklist causes each step is designed to rule in or out.

Summary

Flaky tests almost always trace back to one of six causes already covered elsewhere in this course: poor locators, hard waits, shared state, race conditions, unstable test data, or environment differences. A systematic process — reproduce in isolation, compare traces, work through the checklist — resolves the great majority of cases, and retries should absorb genuine noise, never substitute for that diagnosis.

Interview Questions

A teammate suggests just adding retries to a newly flaky test and moving on. Why might you push back?▾
Retries can mask a genuine, worsening problem — a real race condition or shared-state bug that happens to pass on a second attempt today might fail more often as the codebase changes, and by then the original signal that something was wrong has been silenced. Diagnosing the actual cause (using the checklist and traces) fixes the problem rather than hiding it, and retries should be reserved for absorbing truly random environmental noise in CI, not as a first response to newly observed flakiness.
