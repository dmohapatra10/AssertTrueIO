Framework Folder Structure

Prerequisites: Page Object Model

What is this?

Every pattern in this course — locators, fixtures, page objects, API testing, mocking — needs a home in an actual project layout as a suite grows past a handful of files. This chapter is that layout: a folder structure that scales, and the responsibility each folder holds.

Why it's important

A suite with no consistent structure becomes hard to navigate as it grows — new tests get placed inconsistently, page objects and fixtures duplicate each other, and onboarding a new engineer takes longer than it should. A clear, consistent layout solves all of this cheaply, as long as it's adopted early.

The Structure

playwright-framework/
├── tests/              # test files (*.spec.ts) — organized by feature area
│   ├── auth/
│   ├── checkout/
│   └── orders/
├── pages/              # Page Object Model classes
│   ├── base-page.ts
│   ├── login-page.ts
│   └── checkout-page.ts
├── components/         # reusable UI component objects (nav bar, modal, etc.)
│   └── nav-bar.ts
├── fixtures/           # custom fixtures — page objects, auth, test data
│   └── index.ts
├── api/                # API client helpers, separate from UI page objects
│   └── orders-api.ts
├── test-data/           # static fixture files (sample CSVs, images, JSON)
│   └── sample-resume.pdf
├── utils/               # small shared helper functions (formatting, random data)
│   └── generate-email.ts
├── types/                # shared TypeScript types/interfaces
│   └── order.ts
├── config/               # environment-specific config files (.env.qa, .env.staging)
├── setup/                 # global setup scripts (auth, seeding)
│   └── global.setup.ts
└── playwright.config.ts

What Belongs Where

FolderResponsibility
tests/Test files only — no locators, no business logic, calls page objects/fixtures
pages/Locators and actions for a specific page — no assertions (Page Objects chapter)
components/Shared UI pieces reused across multiple pages
fixtures/Custom fixtures composing page objects, auth, and other setup (Fixtures chapter)
api/API client helpers, kept separate from UI page objects even when used together
test-data/Static files a test needs — not generated code
utils/Small, pure helper functions with no Playwright dependency

Basic Example — A Feature-Organized Test File

// tests/checkout/checkout-payment.spec.ts
import { test, expect } from '../../fixtures';

test.describe('checkout payment', () => {
  test('completes with a valid card', async ({ page, checkoutPage }) => {
    await checkoutPage.goto();
    await checkoutPage.fillShippingDetails({ /* ... */ });
    await checkoutPage.fillPayment({ cardNumber: '4242 4242 4242 4242' });
    await checkoutPage.submit();

    await expect(page.getByText('Order confirmed')).toBeVisible();
  });
});

Organizing tests/ by feature area (not by test type or page) tends to scale best — it mirrors how a team actually thinks about the product and makes it obvious where a new test for a given feature belongs.

Detailed Example — Centralized Fixture Composition

// fixtures/index.ts — the ONE place that wires everything together
import { test as base } from '@playwright/test';
import { LoginPage } from '../pages/login-page';
import { CheckoutPage } from '../pages/checkout-page';
import { OrdersApi } from '../api/orders-api';

type Fixtures = {
  loginPage: LoginPage;
  checkoutPage: CheckoutPage;
  ordersApi: OrdersApi;
};

export const test = base.extend<Fixtures>({
  loginPage: async ({ page }, use) => { await use(new LoginPage(page)); },
  checkoutPage: async ({ page }, use) => { await use(new CheckoutPage(page)); },
  ordersApi: async ({ request }, use) => { await use(new OrdersApi(request)); },
});
export { expect } from '@playwright/test';

Every test file imports test/expect from this one fixtures/index.ts instead of directly from @playwright/test — the single choke point that makes every custom fixture available everywhere consistently.

Real-World Example — Combining API and Page Objects

// tests/orders/order-cancellation.spec.ts
import { test, expect } from '../../fixtures';

test('customer can cancel a pending order', async ({ page, ordersApi }) => {
  const order = await ordersApi.create({ item: 'Wireless Mouse', quantity: 1 });

  await page.goto(`/orders/${order.id}`);
  await page.getByRole('button', { name: 'Cancel order' }).click();

  await expect(page.getByText('Order cancelled')).toBeVisible();
});

This is the API Testing chapter's setup pattern, made concrete within the folder structure — ordersApi lives in api/, is exposed as a fixture, and the test combines it with direct UI interaction without needing a full page object for a page this simple.

utils/generate-email.ts

Common Mistakes

  • Mixing helper code directly into the tests/ folder instead of separating it into pages/, utils/, or api/ — makes it unclear at a glance what's a test versus supporting code.
  • Organizing tests/ by test type (a smoke/ folder, a regression/ folder) instead of by feature — this scatters related tests for one feature across multiple folders; use project-level testMatch/tags for that distinction instead (Projects & Environments chapter).
  • No centralized fixture file — every test file importing @playwright/test directly and manually instantiating page objects, duplicating the wiring that a single fixtures/index.ts should handle once.
  • Putting API client code inside pages/ — keep API helpers separate, even when a test uses both together, since they serve different purposes and often have different maintainers in larger teams.

Edge Cases

  • Monorepos with multiple apps under test — consider a pages//tests/ subfolder per app rather than merging everything into one flat structure, especially once app-specific page objects start colliding in name.
  • Very small projects — a handful of tests may not need the full structure; introduce folders as genuine need arises rather than scaffolding all of them from day one for a two-test project.

Debugging

If it's unclear where a piece of new code belongs, ask: does it interact with the DOM (→ pages/ or components/), does it make an HTTP call (→ api/), is it pure logic with no Playwright dependency (→ utils/), or does it wire fixtures together (→ fixtures/)? Nearly everything falls cleanly into one of these.

Best Practices

  • Organize tests/ by feature area, matching how the product itself is structured.
  • Centralize all custom fixtures in one file that every test imports test/expect from.
  • Keep API helpers, page objects, and pure utilities in clearly separate folders, even when a single test combines all three.
  • Introduce structure incrementally as a project genuinely grows, rather than over-scaffolding a small suite.

Summary

A scalable Playwright framework separates tests (organized by feature), page objects, reusable components, fixtures (the central wiring point), API helpers, and pure utilities into distinct folders — each with one clear responsibility. This structure is what makes every pattern from earlier chapters (POM, fixtures, API testing) actually compose cleanly as a suite grows from a handful of files into a real framework.

Interview Questions

Why keep API client helpers in a separate api/ folder instead of inside the pages/ folder, even for tests that use both together?▾
Page objects and API helpers serve different purposes — one drives browser interaction, the other makes direct HTTP calls with no DOM involved at all. Keeping them separate makes each folder's responsibility unambiguous, avoids page objects accumulating unrelated HTTP logic, and scales better in larger teams where UI and API testing concerns are sometimes owned by different people.
