Chapter 3: Playwright Architecture

Prerequisites: Introduction to Playwright, Getting Started

What is this?

This chapter explains the layers Playwright is built from — Browser, BrowserContext, and Page — and how they relate to each other. Understanding this model isn't optional trivia: it's what explains why Playwright tests are fast, isolated, and able to simulate multiple users without opening multiple browsers.

Why is it important?

Almost every confusing Playwright bug traces back to a misunderstanding of this hierarchy — state leaking between tests, cookies persisting when they shouldn't, or slow tests from launching a fresh browser too often. Once the model clicks, those problems mostly stop happening.

The three layers

Browser — a single running instance of Chromium, Firefox, or WebKit. Launching a browser is relatively expensive (hundreds of milliseconds), so Playwright is designed to launch it once and reuse it across many tests.

BrowserContext — an isolated, incognito-like session within that browser. Each context has its own cookies, local storage, cache, and permissions, completely separate from every other context — even though they all share the same underlying browser process. Creating a new context is cheap (a few milliseconds), unlike launching a new browser.

Page — a single tab or window within a context. A context can hold multiple pages, which is exactly how Playwright tests multi-tab flows (e.g., a link that opens a new tab).

   ├── BrowserContext
   │       │

One Browser process at the root. Any number of isolated BrowserContexts inside it — the diagram shows two, but there can be as many as a test needs. Each context holds any number of Pages — the first context above has three tabs open simultaneously, the second has just one. Every branch is independent: closing, navigating, or setting a cookie in one context's pages has zero effect on the other context or its pages.

Why this matters: test isolation

The Playwright Test Runner gives every single test a brand-new BrowserContext (and by extension, a fresh page) by default — while reusing the same underlying Browser process across the whole run. That's what makes parallel, isolated tests fast: you get the isolation of "one browser per test" without the cost of actually launching one browser per test.

import { test, expect } from '@playwright/test';

// Each test below automatically gets its own isolated context + page.
// Cookies set in one test never leak into another.
test('user A sees empty cart', async ({ page }) => {
  await page.goto('/cart');
  await expect(page.getByText('Your cart is empty')).toBeVisible();
});

test('user B logs in independently', async ({ page }) => {
  await page.goto('/login');
  // no session state from the test above exists here
});

Simulating multiple users in one test

Because contexts are cheap and isolated, you can create several inside a single test to simulate multiple simultaneous users — useful for chat apps, collaborative editors, or admin/customer role-based flows.

import { test, expect, chromium } from '@playwright/test';

test('admin approves a request submitted by a customer', async () => {
  const browser = await chromium.launch();

  const customerContext = await browser.newContext();
  const adminContext = await browser.newContext();

  const customerPage = await customerContext.newPage();
  const adminPage = await adminContext.newPage();

  await customerPage.goto('/requests/new');
  await customerPage.getByLabel('Reason').fill('Refund request');
  await customerPage.getByRole('button', { name: 'Submit' }).click();

  await adminPage.goto('/admin/requests');
  await adminPage.getByRole('button', { name: 'Approve' }).click();
  await expect(adminPage.getByText('Approved')).toBeVisible();

  await browser.close();
});

Each context has completely independent cookies and login state, so customerPage and adminPage behave like two different people on two different computers — without spinning up two actual browser processes.

How Playwright talks to the browser

Playwright doesn't automate browsers through the W3C WebDriver protocol the way Selenium does. Instead, each browser is patched with a small out-of-process driver that exposes a bidirectional WebSocket connection. Commands and events flow over that single persistent connection, which is why Playwright can push instructions and receive events (console logs, network requests, page navigations) with very low latency, instead of the request/response-per-command overhead WebDriver has.

Browser vs. BrowserContext vs. Page vs. Locator

There's a fourth layer worth placing explicitly alongside the three above, because it's a fundamentally different kind of thing, not just a smaller version of a Page: a Locator. The first three are all real, live objects — a running process, an open session, an open tab, each of which exists whether or not you're doing anything with it right now. A Locator is not that. It's a lazy, re-usable description of how to find something — it doesn't need a matching element to exist at the moment you create it, and every time you act on it, Playwright re-resolves it fresh against the live page rather than holding onto a stale reference.

ConceptWhat it actually is
BrowserA running process — expensive, reused across many tests
BrowserContextAn open, isolated session inside that process — cheap, one per test
PageAn open tab inside that session — exists as long as the tab is open
LocatorNot a live object at all — a re-resolvable description of how to find an element, created instantly, valid even before the element exists
 
// Creating this locator does NOT require the button to exist yet —
// nothing is "found" until an action or assertion actually uses it
const submitButton = page.getByRole('button', { name: 'Submit' });

await page.goto('/checkout'); // the button doesn't exist until this navigation completes
await submitButton.click();    // only NOW does Playwright resolve the locator against the live DOM

This is why a locator can be declared once (in a Page Object constructor, for instance — see the Page Objects chapter) long before the page it targets has even loaded: it's inert until used, and re-resolves from scratch on every single interaction, which is also the underlying reason actionability and auto-waiting (Actions and Waiting chapters) work at all — there's no stale reference that could go out of date.

Common mistakes

  • Creating a new Browser for every test instead of a new BrowserContext — this works but is unnecessarily slow.
  • Assuming page.context().clearCookies() is needed between tests — the test runner already isolates you by giving each test its own context.
  • Sharing one page across unrelated tests to "save time," which reintroduces the state-leakage bugs isolation exists to prevent.

Best practices

  • Let the Test Runner manage contexts for you via the page fixture — reach for manual browser.newContext() only for multi-actor scenarios like the admin/customer example above.
  • Use storageState (covered in the Authentication chapter) to reuse a logged-in session across contexts without re-running login every test.

Summary

Playwright's architecture has three layers: one Browser process, many cheap and isolated BrowserContexts inside it, and one or more Pages inside each context. The Test Runner uses this to give every test full isolation without the cost of launching a new browser each time, and the same model lets you simulate multiple simultaneous users within a single test.

Interview Questions

What's the difference between a Browser and a BrowserContext in Playwright, and why does that distinction matter for test performance?▾
A Browser is one running browser process — expensive to start. A BrowserContext is an isolated, cookie/storage-separated session inside that browser — cheap to create. Reusing one Browser across many tests while giving each test its own BrowserContext gives full test isolation at a fraction of the cost of launching a fresh browser per test.
Why is a new BrowserContext per test cheaper than a new Browser per test?▾
A Browser is a full process, expensive to start; a BrowserContext is just an isolated session inside an already-running process, created in milliseconds.
What are the three layers in Playwright's architecture, from largest to smallest?▾
Browser (the process) → BrowserContext (isolated session) → Page (a tab within that session).
Why is a Locator a fundamentally different kind of thing than a Page?▾
A Page is a real, live object that exists whether or not you act on it; a Locator is a lazy, re-resolvable description that doesn't require a matching element to exist yet.
How does Playwright communicate with the browser under the hood?▾
Over a persistent, bidirectional WebSocket connection to a small out-of-process driver, not the W3C WebDriver protocol Selenium uses.
