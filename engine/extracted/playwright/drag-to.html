dragTo()

Prerequisites: Actions overview, click() and dblclick()

What is dragTo()?

sourceLocator.dragTo(targetLocator: Locator, options?: {
  sourcePosition?: { x: number, y: number },
  targetPosition?: { x: number, y: number },
  force?: boolean,
})

dragTo() performs a full drag-and-drop gesture from one element to another: mouse down on the source, move to the target, mouse up — dispatching the same sequence of pointer/drag events a real drag would.

Why it's important, and why it's one of the trickier actions

Drag-and-drop implementations vary a lot in the wild — native HTML5 drag-and-drop (draggable attribute, dragstart/drop events) behaves differently under the hood than a library-driven drag built purely on mouse events (common in kanban boards, sortable lists, file-upload dropzones). dragTo() handles the common cases well, but understanding which kind of drag implementation you're testing is often necessary to get a reliable result.

Basic Example

await page.getByTestId('task-1').dragTo(page.getByTestId('column-in-progress'));

Detailed Example — Kanban Board

test('dragging a task card moves it to the In Progress column', async ({ page }) => {
  await page.goto('/board');

  const task = page.getByTestId('task-card-fix-login-bug');
  const targetColumn = page.getByTestId('column-in-progress');

  await task.dragTo(targetColumn);

  await expect(targetColumn.getByText('Fix login bug')).toBeVisible();
  await expect(page.getByTestId('column-todo').getByText('Fix login bug')).toBeHidden();
});

Manual Drag Sequence — When dragTo() Isn't Enough

Some drag implementations (especially custom sliders, or libraries with strict intermediate-position requirements) need finer control than a single dragTo() call provides. Break it into explicit steps:

const slider = page.getByRole('slider', { name: 'Price range max' });
const box = await slider.boundingBox();

await page.mouse.move(box.x + box.width / 2, box.y + box.height / 2);
await page.mouse.down();
await page.mouse.move(box.x + 150, box.y + box.height / 2, { steps: 10 }); // gradual movement
await page.mouse.up();

await expect(slider).toHaveAttribute('aria-valuenow', '750');

The steps option on mouse.move() dispatches intermediate mousemove events along the path, which some drag implementations require to register the movement correctly — a single instantaneous jump (what a plain dragTo() effectively does) can be missed by drag logic that expects continuous movement.

Real-World Example — Reordering a List

test('dragging a list item reorders the list', async ({ page }) => {
  await page.goto('/playlist');

  const items = page.getByRole('listitem');
  await expect(items.nth(0)).toHaveText('Song A');

  await page.getByText('Song C').dragTo(items.nth(0)); // drag Song C to the top

  await expect(items.nth(0)).toHaveText('Song C');
});

❌ Fragile vs. ✅ Recommended

// ❌ Assuming dragTo() will work on every drag implementation without verifying
await page.getByTestId('task-1').dragTo(page.getByTestId('column-done'));
// (fails silently on some custom drag libraries with no clear error)

// ✅ If dragTo() doesn't register, fall back to a manual mouse sequence with steps
await page.mouse.move(...);
await page.mouse.down();
await page.mouse.move(..., { steps: 10 });
await page.mouse.up();

Common Mistakes

  • Assuming dragTo() works identically across all drag implementations — it's reliable for standard cases but some heavily custom drag libraries need the manual mouse-sequence approach with intermediate steps.
  • Not asserting on the actual resulting order/position — a drag action "succeeding" (no error thrown) doesn't confirm the drop actually landed in the intended place; always assert on the resulting DOM state.
  • Dragging too fast for libraries with debounced or threshold-based drag detection — adding steps to intermediate mouse movement (as in the manual example) often resolves this.

Edge Cases

  • Native HTML5 drag-and-drop (using the draggable attribute and dataTransfer API) can behave differently across browser engines; test drag-and-drop features across all your configured browser projects (Chapter 10), not just Chromium, since this is an area with real cross-browser variance.
  • Auto-scrolling containers during a drag (dragging a card toward the edge of a scrollable list to trigger auto-scroll) — this typically requires the manual mouse sequence with a pause near the edge, since dragTo() alone doesn't simulate a sustained hover at a boundary.

Debugging

Use Trace Viewer (Chapter 15) to visually confirm where the drag actually landed — a drag that appears to succeed in code but produces the wrong DOM order is easier to diagnose from the recorded DOM snapshots than from log output alone.

Best Practices

  • Start with dragTo() for simplicity; drop down to a manual mouse sequence with steps only if it doesn't register correctly.
  • Always assert on the resulting state (new order, new column, new value) — never just that the drag call didn't throw.
  • Test drag-and-drop across all relevant browser projects, given known cross-engine differences in native drag-and-drop behavior.

Practice Exercise

Given a kanban board with three columns, write a test that drags a card from "To Do" directly to "Done" (skipping "In Progress"), and asserts it appears in the correct column and no longer appears in the original one.

Summary

dragTo() automates the common drag-and-drop case in one call; more demanding drag implementations sometimes need a manual mouse.down()/mouse.move()/mouse.up() sequence with intermediate steps to register correctly. Always assert on the resulting state, not just that the action completed.

Interview Questions

A dragTo() call completes without error, but the item doesn't end up in the expected position. What would you investigate first?▾
First, whether the app's drag implementation is a custom library that expects gradual mouse movement rather than an instantaneous jump — switching to a manual mouse.down()/move()/up() sequence with steps often resolves this. Second, whether the assertion is checking the right thing — a drag "succeeding" (no thrown error) only means the mouse events were dispatched, not that the app's drop-handling logic actually processed them as intended.
