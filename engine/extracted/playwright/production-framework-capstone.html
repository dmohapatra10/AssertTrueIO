Building the Framework

Prerequisites: Every previous chapter — this is the capstone that assembles them all.

What is this?

This chapter doesn't introduce new APIs. It's a complete walkthrough of a small but genuinely production-style framework, built for a realistic e-commerce application, showing exactly how every earlier chapter's piece fits into one working whole — the destination all thirteen chapters before this were building toward.

Why it's important

Knowing each individual concept — locators, fixtures, POM, API testing, config, CI — is different from knowing how they compose into a single coherent project. This is the missing piece: seeing the whole shape at once.

The Application

A small e-commerce app: browse products, add to cart, check out, view order history. Enough surface area to exercise UI testing, API testing, authentication, and framework structure meaningfully, without being an unwieldy example.

Step 3 — Authentication Setup

// setup/global.setup.ts
import { test as setup } from '@playwright/test';

setup('authenticate', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill(process.env.TEST_USER_EMAIL!);
  await page.getByLabel('Password').fill(process.env.TEST_USER_PASSWORD!);
  await page.getByRole('button', { name: 'Sign in' }).click();
  await page.waitForURL('/dashboard');
  await page.context().storageState({ path: 'playwright/.auth/user.json' });
});

Step 4 — Page Objects and API Helper

// pages/checkout-page.ts
export class CheckoutPage extends BasePage {
  readonly cardNumberInput: Locator;
  readonly payButton: Locator;

  constructor(page: Page) {
    super(page);
    this.cardNumberInput = page.getByLabel('Card number');
    this.payButton = page.getByRole('button', { name: 'Pay now' });
  }

  async payWithTestCard() {
    await this.cardNumberInput.fill('4242 4242 4242 4242');
    await this.payButton.click();
  }
}
// api/orders-api.ts
import { APIRequestContext } from '@playwright/test';

export class OrdersApi {
  constructor(private request: APIRequestContext) {}

  async create(data: { item: string; quantity: number }) {
    const res = await this.request.post('/api/orders', { data });
    return res.json();
  }

  async delete(id: string) {
    await this.request.delete(`/api/orders/${id}`);
  }
}

Step 5 — Fixture Wiring

import { test as base } from '@playwright/test';
import { CheckoutPage } from '../pages/checkout-page';
import { OrdersApi } from '../api/orders-api';

type Fixtures = { checkoutPage: CheckoutPage; ordersApi: OrdersApi };

export const test = base.extend<Fixtures>({
  checkoutPage: async ({ page }, use) => { await use(new CheckoutPage(page)); },
  ordersApi: async ({ request }, use) => { await use(new OrdersApi(request)); },
});
export { expect } from '@playwright/test';

Step 6 — A Complete Test, Using Everything Together

// tests/orders/order-cancellation.spec.ts
import { test, expect } from '../../fixtures';

test.describe('order cancellation', () => {
  let orderId: string;

  test.beforeEach(async ({ ordersApi }) => {
    const order = await ordersApi.create({ item: 'Wireless Mouse', quantity: 1 });
    orderId = order.id;
  });

  test.afterEach(async ({ ordersApi }) => {
    await ordersApi.delete(orderId).catch(() => {}); // already cancelled is fine
  });

  test('customer can cancel a pending order', async ({ page }) => {
    await test.step('navigate to the order', async () => {
      await page.goto(`/orders/${orderId}`);
    });

    await test.step('cancel it', async () => {
      await page.getByRole('button', { name: 'Cancel order' }).click();
    });

    await expect(page.getByText('Order cancelled')).toBeVisible();
  });
});

Trace this one test back through the course: ordersApi fixture (Fixtures, Framework Structure) using API setup (API Testing) for speed, beforeEach/afterEach (Hooks) for clean setup/teardown, test.step() (Test Runner) for report clarity, role-based locators (Locators) for the interaction, and a web-first assertion (Assertions) to finish. Nothing here is a new concept — it's the composition that makes it a framework rather than a script.

Step 7 — CI/CD

# .github/workflows/playwright.yml
name: Playwright Tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test
        env:
          BASE_URL: ${{ secrets.STAGING_BASE_URL }}
          TEST_USER_EMAIL: ${{ secrets.TEST_USER_EMAIL }}
          TEST_USER_PASSWORD: ${{ secrets.TEST_USER_PASSWORD }}
      - if: always()
        uses: actions/upload-artifact@v4
        with: { name: playwright-report, path: playwright-report/ }

What Makes This "Production-Style," Not Just a Working Script

  • No hardcoded URLs or credentials anywhere — everything environment-driven, per the Configuration and Projects chapters.
  • Setup and teardown are symmetric and automatic — every created order gets cleaned up, per the Hooks chapter.
  • API used for speed, UI used for verification — per the API Testing chapter's core principle.
  • A single fixture file wires everything — no test manually constructs a page object or API client, per Framework Structure.
  • CI failure produces a debuggable artifact, not just a red X, per the Reporting chapter.

Common Mistakes at This Scale

  • Skipping the fixture layer "since the project is still small" — this is exactly the debt that makes a growing suite painful; introduce it from the start, it costs little.
  • Letting test data accumulate without teardown, eventually polluting a shared staging environment other teams also use.
  • Copy-pasting a whole test file to make a small variation instead of parameterizing or extracting shared setup — a sign the framework's abstractions need to grow with the suite.

Where to Go From Here

This framework is intentionally small enough to hold in your head — a real production suite grows the same structure outward: more page objects, more API helpers, more projects (mobile, tablet, additional browsers), a smoke/regression split, and probably a visual regression suite alongside the functional one. None of that requires new concepts beyond this course; it's the same pieces, more of them, composed the same way.

Summary

A production-style Playwright framework is not a single advanced technique — it's the disciplined composition of everything covered in this course: locators and actions for reliable interaction, fixtures for clean setup, page objects for maintainability, API testing for speed, environment-driven configuration for portability, and CI/CD with real reporting for continuous confidence. Every piece traces back to a specific earlier chapter; the skill this capstone teaches is fitting them together.

Interview Questions

What separates a "framework" from a folder of individual Playwright test scripts?▾
A framework has consistent, reusable structure — shared fixtures instead of per-test setup duplication, page objects instead of repeated locators, environment-driven configuration instead of hardcoded values, and a CI pipeline producing debuggable artifacts on failure. A folder of scripts might individually work, but each new test re-solves problems (login, navigation, data setup) that a framework solves once and makes available everywhere — which is what actually lets a test suite scale to hundreds of tests without becoming unmaintainable.
What actually separates a 'framework' from a folder of individual test scripts?▾
Consistent, reusable structure — shared fixtures instead of duplicated setup, page objects instead of repeated locators, environment-driven config instead of hardcoded values.
Why does the capstone framework use the API for setup but the UI for the actual workflow being tested?▾
Speed and reliability for the parts that aren't the point of the test, while still genuinely exercising the UI for what the test is actually meant to verify.
Why does every created order get deleted in afterEach, even if the test's own logic already deleted it?▾
Because DELETE is idempotent and the cleanup call is wrapped in .catch(), making the repeat call a safe no-op rather than a failure.
What would 'growing' this capstone framework for a larger real product typically involve?▾
More page objects, more API helpers, more projects (mobile, additional browsers), a smoke/regression split — the same pieces, more of them, not new concepts.
