Count, URL & Title Assertions

Prerequisites: Assertions overview, Text & Value Assertions

What is this?

toHaveCount() checks how many elements a locator matches; toHaveURL() and toHaveTitle() check page-level navigation state rather than anything about a specific element.

Why it's important

These three answer questions the element-level assertions can't: "did the right number of things render," and "did we actually end up on the page we expected." Both come up constantly in list/table testing and in any flow involving navigation.

Basic Example — toHaveCount()

const results = page.getByRole('listitem');
await expect(results).toHaveCount(12);

// A count of zero is a clean way to assert absence, with full auto-retry
await expect(page.getByText('Out of stock')).toHaveCount(0);

Because toHaveCount() retries, it correctly handles a list that renders progressively — it waits until the count settles at the expected value instead of checking prematurely mid-render.

Basic Example — toHaveURL() and toHaveTitle()

await page.getByRole('link', { name: 'Settings' }).click();
await expect(page).toHaveURL('/settings');
await expect(page).toHaveTitle('Account Settings — Acme');

// Both accept a regex for dynamic/partial matching
await expect(page).toHaveURL(/\/orders\/ORD-\d+/);
await expect(page).toHaveTitle(/Settings/);

Notice these are called on page, not a locator — a meaningful difference from every other assertion in this chapter, since URL and title are properties of the page itself, not of any element within it.

Detailed Example — Pagination

test('pagination shows 10 items per page', async ({ page }) => {
  await page.goto('/products');

  await expect(page.getByRole('listitem')).toHaveCount(10);
  await page.getByRole('button', { name: 'Next page' }).click();

  await expect(page).toHaveURL(/page=2/);
  await expect(page.getByRole('listitem')).toHaveCount(10);
});

Real-World Example — Post-Login Redirect

test('successful login redirects to the dashboard', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('user@example.com');
  await page.getByLabel('Password').fill('correct-horse-battery-staple');
  await page.getByRole('button', { name: 'Sign in' }).click();

  await expect(page).toHaveURL('/dashboard');
  await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
});

Asserting both the URL and a piece of visible content is a stronger check than either alone — the URL confirms navigation happened, and the heading confirms the destination page actually rendered correctly rather than showing a blank or error state at the right address.

❌ Fragile vs. ✅ Recommended

// ❌ Hardcoding the full origin makes the test fail the moment it runs against
// a different environment (staging vs. production vs. local)
await expect(page).toHaveURL('https://app.example.com/dashboard');

// ✅ Relative path — works across environments when baseURL is configured
await expect(page).toHaveURL('/dashboard');

Common Mistakes

  • Hardcoding a full absolute URL instead of a relative path — breaks the moment the same test runs against a different baseURL (local, staging, production).
  • Asserting an exact count for a genuinely dynamic list without accounting for real variability (e.g., a live inventory count) — consider asserting a minimum or a range instead when exact counts aren't stable.
  • Checking page.url() manually and comparing with a plain equality instead of using toHaveURL() — loses auto-retry, which matters because navigation isn't always instantaneous.

Edge Cases

  • Query parameter order — toHaveURL() with a string does an exact match including query string order; use a regex when parameter order isn't guaranteed or doesn't matter to the test.
  • Single-page apps with client-side routing — toHaveURL() still works correctly since it reads the browser's current URL regardless of whether navigation was a full page load or client-side route change.

Debugging

If toHaveURL() times out, check whether the navigation is genuinely happening but slowly (a real network wait) versus not happening at all (e.g., a click that silently failed) — Trace Viewer's network panel distinguishes these quickly.

Best Practices

  • Use relative paths with toHaveURL() so tests remain environment-agnostic.
  • Pair toHaveURL() with a content assertion on the destination page rather than treating URL alone as proof the navigation fully succeeded.
  • Prefer a regex over an exact count when a list's size can legitimately vary for reasons unrelated to the feature under test.

Practice Exercise

Write a test that searches for a product, asserts the results count is greater than zero (without hardcoding an exact number), and asserts the URL contains the search query as a parameter.

Summary

toHaveCount() checks how many elements match a locator, with full auto-retry for progressively rendering lists. toHaveURL() and toHaveTitle() check page-level state and are called on page rather than a locator — both accept regex for dynamic or partial matching.

Interview Questions

Why should toHaveURL() generally use a relative path rather than a full absolute URL?▾
A relative path lets the exact same test run unchanged against local, staging, and production environments, since Playwright resolves it against the configured baseURL. Hardcoding a full URL ties the test to one specific environment and breaks the moment it's run anywhere else.
Why does toHaveCount() work reliably even on a progressively-rendering list?▾
Because it retries, it waits until the count settles at the expected value instead of checking prematurely mid-render.
Why should toHaveURL() generally use a relative path rather than a full domain?▾
A relative path resolves against the configured baseURL, letting the same test run unchanged across local, staging, and production.
What's a stronger check than toHaveURL() alone after a navigation?▾
Pairing it with a content assertion on the destination page, confirming it actually rendered correctly, not just that the address changed.
How do you handle a URL with unpredictable query parameter order?▾
Use a regex with toHaveURL() instead of an exact string match, which requires an exact match including order.
