Chapter 1: Introduction to Playwright

What is Playwright?

Playwright is an open-source browser automation and end-to-end testing framework created by Microsoft. It lets you write scripts that control real browsers — Chromium, Firefox, and WebKit — to test web applications the way a real user would: clicking buttons, filling forms, navigating pages, and verifying what appears on screen.

Unlike older automation tools that talk to the browser through a slow, flaky bridge, Playwright communicates with the browser over a persistent WebSocket connection, giving it fast, reliable control over pages, network traffic, and browser state — the full mechanics of this are covered in the Architecture chapter.

Why Playwright Exists

Web applications became more dynamic — single-page apps, client-side routing, asynchronous rendering — and older tools struggled to keep pace. Playwright was built to handle modern web apps, true cross-browser testing, flakiness (via auto-waiting), and multi-context testing, all through one consistent API.

Mental Model

Three ideas underpin almost everything else in this course, each get their own full chapter later, but it's worth naming them up front:

  • Locators are lazy descriptions, not live references — a locator describes how to find an element; it doesn't need that element to exist yet, and re-resolves fresh every time it's used.
  • Actions and assertions wait automatically — Playwright polls for the right condition (visible, enabled, stable) before acting, instead of assuming the page is already in the state you expect.
  • A BrowserContext is an isolated "profile" — cookies, storage, and permissions inside one context never leak into another, which is what makes parallel and multi-user testing possible without interference.

Basic Example

import { test, expect } from '@playwright/test';

test('homepage has the right title', async ({ page }) => {
  await page.goto('https://playwright.dev');
  await expect(page).toHaveTitle(/Playwright/);
});

Even this small example demonstrates the core shape every test in this course follows: navigate, interact, assert — with Playwright handling the waiting in between.

Real-World Example — Why Auto-Waiting Matters

// A button that's disabled until an async validation check finishes
await page.getByLabel('Email').fill('user@example.com');
// No manual wait needed — click() automatically waits for the button
// to become enabled before attempting to click it
await page.getByRole('button', { name: 'Continue' }).click();

A tool without built-in auto-waiting would need an explicit wait or a retry loop here; Playwright's actionability checks (covered fully in the Actions chapter) handle this transparently for essentially every action.

// ❌ "Playwright is just a Selenium wrapper with nicer syntax"

// ✅ Playwright is a from-scratch architecture: a different browser

Common Mistakes (Even at the Intro Stage)

  • Assuming Playwright is "just another Selenium wrapper." The underlying protocol, architecture, and feature set are genuinely different, not a thin compatibility layer.
  • Treating it as UI-only when its API testing (via APIRequestContext) is a first-class feature, not an afterthought.
  • Skipping the built-in Test Runner in favor of a plain script, then manually reimplementing parallelization, retries, and reporting that @playwright/test already provides.

Edge Cases

  • Testing against a browser Playwright doesn't ship (real, non-Chromium-based Edge; older browsers) — Playwright can connect to some external browsers via connect(), but its own downloaded binaries only cover Chromium, Firefox, and WebKit.
  • Native mobile app testing — Playwright automates mobile web (via emulated viewports/devices), not native iOS/Android apps; that's a different category of tool entirely (e.g., Appium).

Debugging

When something about Playwright's behavior seems surprising for the first time, the most common root cause is one of the three mental-model ideas above — check whether the issue is really about locator laziness, missing auto-wait coverage, or context isolation before assuming it's a bug.

Best Practices

  • Start every new project with @playwright/test, not the raw automation library, unless you have a specific reason not to.
  • Treat API testing as equally available to UI testing from day one — many suites benefit from mixing both.
  • Don't port Selenium habits (explicit waits everywhere, WebDriver-style selectors) forward unexamined — several of them are actively unnecessary in Playwright.

Summary

Playwright is a modern, cross-browser automation and testing framework built to handle today's dynamic web apps reliably, with auto-waiting, multi-context support, and built-in API testing — architected differently from Selenium and Cypress, not just styled differently.

Interview Questions

What are the main architectural differences between Playwright and Selenium?▾
Playwright drives browsers over a persistent WebSocket connection, giving it lower latency and native support for multiple browser contexts within one browser process. Selenium uses the WebDriver protocol (HTTP requests per command) and generally needs one browser instance per session. Playwright also ships auto-waiting and a built-in test runner, both of which Selenium requires external tooling or manual code to approximate.
Is Playwright a wrapper around Selenium's WebDriver protocol?▾
No — it uses a fundamentally different architecture: a persistent WebSocket connection, not WebDriver's per-command HTTP requests.
Does Playwright only support UI testing?▾
No — APIRequestContext makes API testing a first-class feature, not an afterthought bolted onto UI automation.
What's a Playwright limitation worth knowing upfront?▾
It automates mobile web via emulated viewports, not native iOS/Android apps — that's a different category of tool (e.g. Appium).
Name one built-in feature Selenium requires external tooling to approximate.▾
Auto-waiting — Selenium generally needs manual/explicit waits, where Playwright handles this automatically via actionability checks.
