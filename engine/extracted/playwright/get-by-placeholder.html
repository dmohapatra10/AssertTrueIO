getByPlaceholder()

Prerequisites: Locators overview, getByLabel()

What is getByPlaceholder()?

page.getByPlaceholder(text: string | RegExp, options?: { exact?: boolean })

getByPlaceholder() finds an input by its placeholder attribute — the greyed-out hint text shown inside an empty field.

Why it exists (and why it's ranked below getByLabel)

Placeholder text is visible to sighted users but disappears the moment a field has a value, and it's not a reliable accessible name for all assistive technology in the way a real <label> is. Playwright still ranks it above getByText() because it's specific to one field, but below getByLabel() for exactly this reason: a placeholder is a hint, not a proper label.

Basic Example

await page.getByPlaceholder('Search products').fill('wireless mouse');

Detailed Example

// A search bar that intentionally has no visible label, only placeholder text
await page.getByPlaceholder('Search by order number').fill('ORD-10492');
await page.keyboard.press('Enter');
await expect(page.getByRole('heading', { name: 'Order #ORD-10492' })).toBeVisible();

Real-World Example — Filter Bar

test('user can filter the inventory table by SKU', async ({ page }) => {
  await page.goto('/inventory');
  await page.getByPlaceholder('Filter by SKU').fill('SKU-2291');
  await expect(page.getByRole('row')).toHaveCount(1); // header row was excluded elsewhere
  await expect(page.getByText('Wireless Mouse')).toBeVisible();
});

❌ Fragile vs. ✅ Recommended

// ❌ Reaching for CSS when the field genuinely has a real label
await page.locator('input.search-input').fill('wireless mouse');

// ✅ If there's a real label, prefer it — placeholder is the fallback
await page.getByLabel('Search products').fill('wireless mouse');
// only use getByPlaceholder() when no real label exists

Common Mistakes

  • Using getByPlaceholder() when the field also has a real label — check for a <label> first; if one exists, getByLabel() is the better locator even if a placeholder is also present.
  • Asserting on placeholder text as if it were the field's current value — placeholder text and value are different things; toHaveValue() checks the value, not the placeholder.
  • Relying on placeholder text alone to convey a field's purpose in the app itself — this is a UX/accessibility anti-pattern independent of testing; the test surfacing it is a useful signal.

Edge Cases

  • Placeholder text that changes dynamically (e.g., "Search 1,204 products") — prefer a regex or partial match rather than hardcoding a count that will drift: page.getByPlaceholder(/Search \d+ products/).

Debugging

If the locator doesn't match, confirm the exact placeholder text via browser DevTools — placeholder text with trailing punctuation or slightly different casing than what's visually rendered (due to CSS text-transform) is a common source of mismatch, since Playwright reads the actual attribute value, not the rendered/styled text.

Best Practices

  • Check for a real label before defaulting to placeholder — only use this locator when no label exists.
  • Use a regex when placeholder text includes dynamic content like counts or dates.

Practice Exercise

Given a search field with placeholder "Search 342 items," write a locator that matches regardless of the current item count.

Summary

getByPlaceholder() targets a field's placeholder attribute — useful when no real label exists, but a weaker signal than getByLabel() since placeholder text vanishes once a field has a value and isn't a fully reliable accessible name.

Interview Questions

Why does Playwright rank getByPlaceholder() below getByLabel() in its locator priority?▾
Placeholder text disappears once the field has a value and isn't a robust accessible name across all assistive technology, whereas a real <label> is a persistent, standard, accessibility-recognized association — placeholder is a fallback for fields that genuinely lack a proper label.
Why is getByPlaceholder() ranked below getByLabel() in locator priority?▾
Placeholder text disappears once a field has a value and isn't a fully reliable accessible name, while a real label persists and is standard.
When is getByPlaceholder() actually the right choice?▾
When a field genuinely has no real label — only then should it be reached for, ideally alongside a note to add a proper label to the app.
How would you match a placeholder that includes a changing count, like 'Search 342 items'?▾
Use a regex instead of a plain string, e.g. page.getByPlaceholder(/Search \d+ items/).
Does getByPlaceholder() check the field's current value?▾
No — it matches the placeholder attribute specifically, not the value; toHaveValue() is the correct assertion for a field's actual content.
