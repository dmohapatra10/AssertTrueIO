hover()

Prerequisites: Actions overview, click() and dblclick()

What is hover()?

locator.hover(options?: { force?: boolean, position?: { x: number, y: number }, timeout?: number })

hover() moves the (virtual) mouse over an element's center, triggering any CSS :hover styles and JavaScript mouseover/mouseenter listeners — without clicking.

Why it's important, and why it's inherently trickier

Hover-triggered UI (tooltips, dropdown menus, "reveal on hover" action buttons) is common, but genuinely harder to test than click-based UI for a structural reason: hover has no persistent "state" the way a checked checkbox does — the moment the virtual mouse moves elsewhere (including as a side effect of a subsequent action), the hover state can disappear. Tests involving hover need to assert on the hover-triggered UI immediately, before doing anything else that might move focus or the mouse.

Basic Example

await page.getByText('Wireless Mouse').hover();
await expect(page.getByRole('tooltip')).toBeVisible();

Detailed Example — Reveal-on-Hover Action Buttons

test('hovering a table row reveals its action buttons', async ({ page }) => {
  await page.goto('/inventory');

  const row = page.getByRole('row').filter({ hasText: 'Wireless Mouse' });

  // Action buttons are visually hidden until the row is hovered
  await expect(row.getByRole('button', { name: 'Edit' })).toBeHidden();
  await row.hover();
  await expect(row.getByRole('button', { name: 'Edit' })).toBeVisible();

  await row.getByRole('button', { name: 'Edit' }).click();
});

Note the click at the end happens immediately after the hover reveals the button, within the same locator chain scope — minimizing the chance of the hover state being lost between steps.

Real-World Example — Navigation Mega-Menu

test('hovering the Products nav item opens the mega menu', async ({ page }) => {
  await page.goto('/');

  await page.getByRole('link', { name: 'Products' }).hover();
  await expect(page.getByRole('navigation', { name: 'Products menu' })).toBeVisible();

  await page.getByRole('link', { name: 'Wireless Mice' }).click();
  await expect(page).toHaveURL(/\/products\/wireless-mice/);
});

❌ Fragile vs. ✅ Recommended

// ❌ Forcing a click on a hover-revealed button without hovering first —
// works only if the button happens to already be interactable despite being visually hidden
await row.getByRole('button', { name: 'Edit' }).click({ force: true });

// ✅ Actually trigger the hover state the feature depends on
await row.hover();
await row.getByRole('button', { name: 'Edit' }).click();

Common Mistakes

  • Reaching for { force: true } to click a hover-hidden element instead of hovering first — this bypasses the actual interaction being tested, and can pass even if the real hover mechanism is broken.
  • Assuming hover state persists across unrelated subsequent actions — navigating, clicking elsewhere, or even some assertions can implicitly move focus and dismiss a hover-triggered element; act on hover-revealed UI promptly.
  • Testing hover-only interactions without a keyboard-accessible equivalent in the app itself — if a feature is genuinely only reachable via mouse hover, that's often an accessibility gap worth raising, independent of the test.

Edge Cases

  • Touch devices/mobile emulation — hover has no real equivalent on touch interfaces; if a project's mobile project (Chapter 10) tests the same UI, hover-dependent features need a documented alternative interaction, or should be explicitly skipped for mobile projects.
  • Nested hover targets (a submenu that appears on hovering a menu item, which itself has further hoverable items) — chain hover() calls in sequence, verifying each level's UI appears before hovering the next.

Debugging

If a hover-triggered assertion fails intermittently, check whether the hover-revealed element has a CSS transition delay — Playwright's actionability/assertion auto-waiting handles the wait, but a very long intentional delay (for UX polish) may need the assertion's timeout extended rather than treating it as a flaky test.

Best Practices

  • Assert on hover-revealed UI immediately after the hover() call, before any other action that might shift focus.
  • Avoid { force: true } as a substitute for actually triggering the hover state — it tests a different thing than what the feature requires.
  • Flag hover-only, keyboard-inaccessible interactions as a product concern, not just something to work around in tests.

Practice Exercise

A product card shows a "Quick view" button only on hover. Write a test that hovers the card, clicks "Quick view," and asserts a modal with the product's details opens.

Summary

hover() simulates moving the mouse over an element to trigger CSS :hover and JS mouse-enter behavior. Because hover state isn't persistent the way a checked box or a URL is, tests should act on hover-revealed UI promptly rather than relying on it surviving unrelated subsequent steps.

Interview Questions

Why is testing hover-triggered UI generally trickier than testing click-triggered UI?▾
A click typically produces a persistent state change (a class toggled, a URL changed, a value set) that stays true until something explicitly changes it again. Hover produces a transient state tied to the mouse's current position — it can disappear the instant the mouse conceptually "moves" elsewhere, including as a side effect of another action — so hover-dependent assertions need to happen immediately after the hover, not later in the test.
Why is hover state described as more fragile to test than a checked checkbox?▾
A checked box is a persistent state; hover is tied to the mouse's current position and can disappear the instant focus conceptually moves elsewhere.
What's wrong with using { force: true } to click a hover-hidden button instead of hovering first?▾
It bypasses the actual interaction being tested and can pass even if the real hover mechanism is broken.
Does hover() have a meaningful equivalent on touch/mobile devices?▾
Not really — hover has no true touch equivalent, so hover-dependent features need a documented alternative for mobile projects.
Why should assertions on hover-revealed content happen immediately after hover()?▾
Because subsequent actions or even some assertions can implicitly shift focus and dismiss the hover state before you get to check it.
