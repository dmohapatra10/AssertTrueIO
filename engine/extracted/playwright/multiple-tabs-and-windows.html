Chapter 11: Multiple Tabs and Windows

Prerequisites: Playwright Architecture, Pages and Navigation

What is this?

Some interactions open a new tab or window — a link with target="_blank", a "sign in with Google" popup, a print preview. Recall from the Architecture chapter that a BrowserContext can hold multiple Pages: a new tab is just another Page within the same context, and Playwright exposes it through an event rather than a return value.

Why it's important

The original page object your test started with never becomes the new tab — the two coexist as separate Page instances. Missing this is the most common reason engineers new to Playwright get stuck: they keep interacting with the original page and wonder why nothing happens on the new tab.

Mental Model

BrowserContext
   │
   ├── page       (original tab — still open, still usable)
   │
   └── newPage    (the tab that just opened — a distinct object)

Both pages are alive simultaneously and share the same context (same cookies, same login session) — but every locator, action, and assertion has to be called on the specific Page object that represents the tab you actually mean.

Capturing a New Tab With the popup Event

const [newPage] = await Promise.all([
  context.waitForEvent('page'),
  page.getByRole('link', { name: 'Open in new tab' }).click(),
]);

await newPage.waitForLoadState();
await expect(newPage).toHaveTitle(/Documentation/);

The Promise.all pattern matters here: the click that triggers the new tab and the wait for that tab's page event have to be started together, not sequentially — otherwise there's a race where the event could fire before you start listening for it. This mirrors the same race-condition pattern covered for network waits in the Waiting & Synchronization chapter.

Basic Example — Switching Focus Between Tabs

// Do something in the new tab, then come back to the original
await newPage.getByRole('button', { name: 'Download PDF' }).click();
await page.bringToFront(); // switch focus back to the original tab
await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();

bringToFront() doesn't affect what a test can interact with (both pages remain fully scriptable regardless of visual focus) — it's mainly useful when running headed for visual debugging, or for apps that behave differently based on tab visibility.

Real-World Example — OAuth Login Popup

import { test, expect } from '@playwright/test';

test('signs in through a Google OAuth popup', async ({ page, context }) => {
  await page.goto('/login');

  const [popup] = await Promise.all([
    context.waitForEvent('page'),
    page.getByRole('button', { name: 'Sign in with Google' }).click(),
  ]);

  await popup.waitForLoadState();
  await popup.getByLabel('Email').fill('user@example.com');
  await popup.getByRole('button', { name: 'Next' }).click();
  await popup.getByLabel('Password').fill('correct-horse-battery-staple');
  await popup.getByRole('button', { name: 'Sign in' }).click();

  // The popup closes itself after auth completes; assert back on the main page
  await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
});

Notice the test interacts with popup while the OAuth flow is happening, then switches back to asserting on the original page once control returns there — each Page object is used only for the tab it actually represents.

Working With Several Open Pages at Once

const allPages = context.pages();
console.log(`${allPages.length} tabs currently open`);

// Find a specific tab among several by its URL or title
const settingsTab = allPages.find((p) => p.url().includes('/settings'));

Closing Tabs Explicitly

await popup.close();
// The context and original page remain open and usable afterward

Playwright doesn't require you to close extra tabs — the context is cleaned up automatically at the end of the test — but explicitly closing a popup once you're done with it keeps a test with many tabs easier to reason about, and matches what a real user would typically do.

❌ Fragile vs. ✅ Recommended

// ❌ Click first, listen for the event after — race condition
await page.getByRole('button', { name: 'Sign in with Google' }).click();
const popup = await context.waitForEvent('page'); // may already have fired

// ✅ Register the listener and trigger the action together
const [popup] = await Promise.all([
  context.waitForEvent('page'),
  page.getByRole('button', { name: 'Sign in with Google' }).click(),
]);

Common Mistakes

  • Continuing to call actions on the original page after a new tab opens, expecting them to affect the new tab.
  • Triggering the click and then calling waitForEvent('page') afterward instead of together in Promise.all, creating a race condition that's intermittent rather than reliably broken.
  • Forgetting to call waitForLoadState() on the new page before interacting with it — a freshly opened tab may not have finished loading yet.

Edge Cases

  • Popup blockers — Playwright's browsers don't apply real popup-blocking behavior the way a default browser profile might, so a window.open() call reliably produces a page event in tests even if it might be blocked for real users; this is a deliberate difference worth knowing about, not a bug.
  • Tabs that open and close very quickly (some OAuth flows) — if a popup closes itself before your test finishes interacting with it, actions on the closed page throw a clear "page has been closed" error rather than hanging silently.
  • Print preview and other browser-native dialogs that aren't real pages — these are handled differently, via the Dialogs chapter's page.on('dialog') pattern, not the page event covered here.

Debugging

If a test seems to "do nothing" after an action that should open a new tab, check whether it's still acting on the original page variable — this single mistake accounts for a large share of confused multi-tab test failures. Trace Viewer (Chapter 15) shows every page in the context as a separate tab in its own timeline, making this easy to spot visually.

Best Practices

  • Always pair the triggering action and waitForEvent('page') inside the same Promise.all.
  • Give each Page object a clear name (popup, newTab) rather than reusing page for multiple tabs, to avoid confusing which tab a given line is acting on.
  • Close popups explicitly with await popup.close() if the application under test doesn't close them itself, to keep the context tidy for the rest of the test.

Practice Exercise

Write a test that opens three separate tabs by clicking three different links, uses context.pages() to find the one whose URL matches a specific pattern, and asserts content on that specific tab only.

Summary

A new tab or window is a separate Page within the same BrowserContext, captured via the context's page event rather than returned from the action that opened it. Pair the triggering click with waitForEvent('page') in a Promise.all, and keep track of which Page object represents which tab throughout the test.

Interview Questions

Why do you need Promise.all() when capturing a new tab, instead of clicking first and then calling waitForEvent('page')?▾
If the click happens first, the new tab's page event could fire and complete before the test starts listening for it, causing the wait to hang or miss the event entirely. Wrapping both in Promise.all starts listening for the event and performs the triggering action at the same time, eliminating that race condition.
Why does clicking a link that opens a new tab seem to 'do nothing' if you keep using the original page variable?▾
The new tab is a separate Page object — the original page reference never becomes it, so actions on the old variable have no effect on the new tab.
Why must the page event listener be registered before the triggering click?▾
Otherwise there's a race — the new tab could open and its event could fire before the listener starts, causing the wait to hang.
Does closing a popup page affect the rest of the browser context?▾
No — the context and its other pages remain open and usable; popups can be closed independently.
How would you find one specific tab among several open ones?▾
Use context.pages() to get all open pages, then find the one matching a specific URL or title.
