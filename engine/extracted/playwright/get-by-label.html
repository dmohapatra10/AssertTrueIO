Beginner

getByLabel()

Prerequisites: Locators overview, getByRole()

What is getByLabel()?

page.getByLabel(text: string | RegExp, options?: { exact?: boolean })

getByLabel() finds a form control (input, select, textarea) by the text of its associated <label> — the same association a browser uses when you click a label and focus jumps to its field.

Why it's important

Forms are one of the highest-value places to use a semantic locator: label text is stable (it's user-facing copy, not implementation detail) and, like getByRole(), using it forces the form to actually be accessible — if getByLabel() can't find a field, neither can a screen reader user tabbing through the form.

Mental Model: how label association works

Playwright recognizes three ways a label can be tied to a field, mirroring how browsers themselves compute it:

<!-- 1. Wrapping -->
<label>Email <input type="email" /></label>

<!-- 2. Explicit `for`/`id` -->
<label for="email">Email</label>
<input id="email" type="email" />

<!-- 3. aria-label (no visible <label> element at all) -->
<input aria-label="Email" type="email" />

All three are matched by the same page.getByLabel('Email') call — Playwright doesn't care which mechanism is used, only that the browser resolves the association.

Basic Example

await page.getByLabel('Email').fill('user@example.com');

Detailed Example — A Full Form

await page.getByLabel('Full name').fill('Debashish Rout');
await page.getByLabel('Email').fill('debashish@example.com');
await page.getByLabel('Password', { exact: true }).fill('correct-horse-battery-staple');
await page.getByLabel('Confirm password').fill('correct-horse-battery-staple');
await page.getByLabel('I agree to the terms').check();
await page.getByRole('button', { name: 'Create account' }).click();

Note { exact: true } on "Password" — without it, the substring match would also match a "Confirm password" field, since "Password" is a substring of "Confirm password."

Real-World Example — Checkout Address Form

test('checkout form accepts a valid address', async ({ page }) => {
  await page.goto('/checkout');

  await page.getByLabel('Street address').fill('221B Baker Street');
  await page.getByLabel('City').fill('London');
  await page.getByLabel('Postal code').fill('NW1 6XE');
  await page.getByLabel('Country').selectOption('United Kingdom');

  await page.getByRole('button', { name: 'Continue to payment' }).click();
  await expect(page.getByRole('heading', { name: 'Payment' })).toBeVisible();
});

❌ Fragile vs. ✅ Recommended

// ❌ Fragile — tied to a generated or arbitrary id
await page.locator('#field-7f3a2').fill('user@example.com');

// ✅ Recommended — tied to what the user actually reads
await page.getByLabel('Email').fill('user@example.com');

Common Mistakes

  • Using it on fields with no real label — a placeholder is not a label. <input placeholder="Email"> with no <label> won't be found by getByLabel(); use getByPlaceholder() instead, and flag the missing label as an accessibility gap.
  • Not using exact when one label's text is a substring of another's ("Password" vs. "Confirm password"), causing an unexpected strict-mode violation.
  • Assuming visual proximity means association — a label sitting next to a field in the layout with no for/wrapping relationship is not programmatically linked, even though it looks connected on screen.

Edge Cases

  • Custom-styled checkboxes/radios built from a hidden native input plus a styled sibling — getByLabel() still works as long as the native input keeps its label association; verify this holds after any visual redesign of form controls.
  • Multi-line or icon-decorated labels — Playwright matches on the label's full accessible text, so an icon with alt text inside the label counts toward the matched string.

Debugging

If getByLabel() can't find a field that clearly has visible label text next to it, inspect the DOM for a real for/id pair or wrapping relationship — the visual layout can be deceptive; the association Playwright reads is structural, not positional.

Best Practices

  • Reach for getByLabel() as the default for any form field — it's second only to getByRole() in Playwright's recommended priority.
  • Use exact: true proactively on short label text likely to be a substring of a longer one nearby.
  • Treat a getByLabel() failure as a signal to check the form's actual accessibility, not just to switch locator strategy.

Practice Exercise

Given a form with fields labeled "Name," "Email," "Phone," and "Phone (work)," write locators for each that avoid strict-mode ambiguity.

Summary

getByLabel() finds form controls the same way a browser resolves label-to-field association — via wrapping, for/id, or aria-label. It's a top-priority locator for forms specifically, and a failure to match is often a real accessibility issue worth fixing in the app.

Interview Questions

A form field has a placeholder that says "Email" but getByLabel('Email') can't find it — why?▾
A placeholder is not a label. Unless the field also has a real <label> (wrapping, for/id, or aria-label), there's no programmatic association for getByLabel() to read — getByPlaceholder() is the correct locator here, and the missing label is worth flagging to the team as an accessibility gap.
Name the three ways a label can be associated with a field that getByLabel() recognizes.▾
Wrapping the input, a for/id pair, or an aria-label attribute.
Why would getByLabel('Password') accidentally match a 'Confirm Password' field?▾
Matching is substring-based by default, so 'Password' matches inside 'Confirm Password' unless exact: true is used.
Is a placeholder the same as a label for getByLabel() purposes?▾
No — a placeholder has no programmatic label association, so getByLabel() can't find a field that only has a placeholder and no real label.
Why is a getByLabel() failure often worth investigating in the app itself?▾
It usually means the field lacks a real accessible label, which is an accessibility gap for real users too, not just a test problem.
