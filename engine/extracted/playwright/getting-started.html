Chapter 2: Getting Started

Prerequisites: Introduction to Playwright

What is this?

This chapter walks through installing Playwright, understanding the project it scaffolds for you, and running your first automated test — from an empty folder to a passing test in a few minutes.

Why is it important?

Playwright's official installer doesn't just add a dependency — it sets up a working project structure, downloads browser binaries, and generates a sample test and config. Understanding what it creates (and why) means you're not just copy-pasting commands blindly; you know what each file does before you start customizing it.

Prerequisites

Before installing Playwright, you need three things in place:

  • Node.js 18 or later — Playwright's installer and CLI are Node-based tooling; run node --version to check what you have.
  • npm (or yarn/pnpm) — installed automatically alongside Node.js, used to run the initializer and manage the project's dependencies.
  • A code editor — any editor works, but VS Code has first-party Playwright tooling (covered later in this chapter) that makes the day-to-day experience noticeably smoother.

No prior Playwright or browser-automation experience is assumed — this chapter starts from a genuinely empty folder.

Installation

Playwright requires Node.js 18 or later. From an empty project folder, run the official initializer:

npm init playwright@latest

This single command:

  • Installs @playwright/test, the official test runner
  • Downloads browser binaries for Chromium, Firefox, and WebKit
  • Creates a playwright.config.ts file (or .js, if you decline TypeScript)
  • Generates a tests/ folder with an example test
  • Optionally sets up a GitHub Actions workflow for CI

Choose TypeScript when prompted — this tutorial series uses TypeScript throughout, since typed autocomplete for locators and assertions catches mistakes before you ever run a test.

What gets created

my-project/
├── tests/
│   └── example.spec.ts
├── tests-examples/
│   └── demo-todo-app.spec.ts
├── playwright.config.ts
├── package.json
└── package-lock.json

playwright.config.ts is the central configuration file — base URL, browsers to test against, timeouts, and reporters all live here. You'll customize this heavily in the Configuration chapter later in this course.

tests/example.spec.ts is a working sample test, useful as a syntax reference for your first week.

tests-examples/demo-todo-app.spec.ts is a longer, more realistic reference test against a live public demo app — worth reading once for patterns, but it's not meant to become part of your real suite; most teams delete or ignore this folder once they've skimmed it.

package.json lists your project's dependencies (including @playwright/test) and can hold a convenience script, e.g. "test": "playwright test", so npm test works too.

package-lock.json pins the exact installed dependency versions — commit this file so every teammate and CI run installs identical versions, not just compatible ones.

Your first test

Replace the contents of tests/example.spec.ts with a small real test:

import { test, expect } from '@playwright/test';

test('homepage has expected title', async ({ page }) => {
  await page.goto('https://playwright.dev');
  await expect(page).toHaveTitle(/Playwright/);
});

Line by line: test() registers a named test case. The { page } parameter is a Playwright fixture — a fresh, isolated browser page provided automatically for every test, with no manual setup. page.goto() navigates to a URL, and Playwright automatically waits for navigation to complete before the next line runs. expect(page).toHaveTitle() is a web-first assertion — it retries automatically for a few seconds until the title matches or the timeout is hit, instead of failing immediately if the page hasn't finished loading.

Running tests

npx playwright test

By default this runs headless across every browser configured in playwright.config.ts, in parallel.

Headless vs. Headed Mode

Headless means the browser runs with no visible window — faster, and what CI always uses, since there's no display to render to anyway. Headed means you actually see the browser window while the test runs, which is occasionally useful for visually confirming what's happening at a specific moment, but isn't something you need for most day-to-day debugging (UI Mode and Trace Viewer, covered shortly, usually answer the same question faster without slowing every run down).

npx playwright test --headed        # watch the browser while it runs

Running a Specific Test or File

Two different things, easy to conflate: running one file versus running one named test within any number of files.

npx playwright test example.spec.ts        # run every test in this one file

npx playwright test -g "homepage has expected title"  # run only tests whose title matches
npx playwright test --grep "homepage"                 # -g and --grep are the same flag

-g/--grep matches against the test's title text (a substring or regex), regardless of which file it lives in — the right tool when you want to run one specific test case while iterating on it, without running everything else in the same file.

Debug Mode

npx playwright test --debug

This opens the Playwright Inspector and pauses before every action, letting you step through a single test line by line, inspect the current state of any locator, and use "Pick locator" to click an element on the page and get its generated selector. It's the most granular way to watch a test execute — slower to work with than UI Mode for a whole suite, but useful when you need to understand exactly what's happening at one specific line.

UI Mode

npx playwright test --ui

UI mode is worth adopting early — it gives you a time-travel debugger, a live locator picker, and a visual pass/fail timeline for your whole suite at once (not just one test), and is generally the fastest way to write and debug new tests day to day.

VS Code Integration

The official Playwright Test for VS Code extension adds a test explorer to the sidebar, inline "Run"/"Debug" buttons directly above each test in your editor, and Codegen — a recorder that generates test code as you click through your app in a real browser. None of this is required (everything it does is also available from the CLI commands above), but it removes a lot of terminal round-tripping during day-to-day authoring, and Codegen in particular is a fast way to get a first draft of a locator or flow before cleaning it up by hand.

Running Against One Browser Only

npx playwright test --project=chromium  # run against one browser only

Common mistakes

  • Skipping the browser download step, then wondering why tests fail with a "browser not found" error — rerun npx playwright install if this happens.
  • Writing tests as plain scripts instead of using test() from @playwright/test — you lose fixtures, retries, parallelization, and reporting.
  • Hardcoding full URLs in every test instead of setting baseURL in the config and using relative paths with page.goto('/login').

Common errors and how to troubleshoot them

  • "browserType.launch: Executable doesn't exist" — browser binaries aren't installed; run npx playwright install.
  • Tests time out on page.goto() — check the URL is reachable and that no corporate proxy/VPN is blocking headless browser traffic.
  • "No tests found" — confirm the file matches the test match pattern (default: *.spec.ts) and lives under the configured testDir.

Best practices

  • Commit playwright.config.ts and the generated CI workflow to version control immediately — don't leave setup half-finished.
  • Use UI mode (--ui) while writing new tests; switch to headless for CI runs.
  • Set a baseURL in the config on day one, even for a single-page prototype — it saves rewriting every test later.

Summary

npm init playwright@latest scaffolds a complete, working test project in one step — config, browsers, and a sample test included. From there, npx playwright test runs your suite, and --ui mode is the fastest way to write and debug new tests as you learn the API.

Interview Questions

What does the page fixture provide, and why does Playwright inject it automatically?▾
page is a fresh, isolated browser page/tab created fresh for each test via Playwright's fixture system. Because it's injected automatically, tests don't need manual browser setup/teardown boilerplate, and each test runs in isolation — one test's page state can't leak into another's, which keeps the suite reliable when tests run in parallel.
What's the difference between npm install playwright and npm init playwright@latest?▾
The latter installs the library, downloads browser binaries, AND scaffolds a working project; a plain install skips the browsers and scaffold entirely.
Why do browser binaries need to be re-downloaded after cloning an existing project?▾
They're cached outside the repo, not committed to git, so every fresh clone or CI runner needs npx playwright install again.
What's the difference between Debug Mode and UI Mode?▾
Debug Mode steps through a single test with the Inspector; UI Mode is a full test-explorer with a timeline, DOM snapshots, and network/console info for the whole suite.
Does Playwright drive the browser already installed on your machine?▾
No — it launches its own separately downloaded, version-pinned browser binaries, independent of your everyday browser.
