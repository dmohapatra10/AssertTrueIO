Actionability Checks and force

Prerequisites: Actions overview, click() and dblclick()

What is this?

Actionability checks are the automatic waiting logic that runs before nearly every action — click(), fill(), check(), and the rest — confirming the target element is genuinely ready to receive that action before Playwright attempts it. force: true is the escape hatch that skips these checks entirely.

Why it's important

This is the single mechanism responsible for most of Playwright's reputation for reliability compared to older tools. Every "flaky test" caused by clicking too early, typing into a disabled field, or interacting with an element hidden behind a loading spinner is a category of bug actionability checks are specifically designed to eliminate — automatically, with no manual wait code required.

The Five Checks

Before most actions, Playwright waits (up to the configured timeout) for the target element to be:

  1. Attached — present in the DOM. An element removed and re-added (common in framework re-renders) needs to be re-attached before an action can proceed.
  2. Visible — has a non-empty bounding box, and isn't display: none, visibility: hidden, or zero-opacity in a way that hides it.
  3. Stable — not actively animating; its bounding box hasn't moved across at least two consecutive animation frames. This specifically catches acting on an element mid-transition, before it settles.
  4. Enabled — not carrying a disabled attribute (for form controls) or otherwise marked non-interactive.
  5. Receives events — not obscured by another element at its target point (a loading overlay, a modal backdrop, a sticky header covering part of the page).

Different actions require different subsets — fill() additionally checks the element is "editable," while a check like isVisible() (an assertion helper, not an action) doesn't wait at all, it just returns the current state immediately.

Basic Example — Waiting Automatically

// No explicit wait needed — Playwright waits for the button to become
// enabled once the form's required fields are filled
await page.getByLabel('Email').fill('user@example.com');
await page.getByLabel('Password').fill('secret123');
await page.getByRole('button', { name: 'Sign in' }).click(); // waits for enabled state automatically

Detailed Example — Reading a Real Timeout Error

// TimeoutError: locator.click: Timeout 30000ms exceeded.
// =========================== logs ===========================
// waiting for getByRole('button', { name: 'Submit' })
//   - element is visible, enabled
//   - element is not stable - waiting...
//   - element is outside of the viewport
// ==============================================================

This is a genuinely useful error message, not a generic failure — it tells you exactly which check is stuck (here, the element keeps moving, likely due to an ongoing CSS animation or a layout shift caused by something loading above it). Reading this log is the fastest way to diagnose the real underlying issue, which almost always exists in the app, not the test.

The force Option

await page.getByRole('button', { name: 'Delete' }).click({ force: true });

force: true skips all actionability checks and performs the action immediately — including on elements that are invisible, disabled, or covered by something else. It exists for narrow, legitimate cases, but it's frequently reached for as a shortcut when a test is flaky, which almost always makes things worse, not better.

❌ Fragile vs. ✅ Recommended

// ❌ Papering over a timeout with force — the underlying problem (an overlay
// blocking the button) is still there; the test now just ignores it
await page.getByRole('button', { name: 'Submit' }).click({ force: true });

// ✅ Investigate what's actually blocking the click, and fix the real cause —
// here, waiting for the loading overlay to disappear first
await expect(page.getByTestId('loading-overlay')).toBeHidden();
await page.getByRole('button', { name: 'Submit' }).click();

When force Is Legitimately Needed

  • Testing a genuinely broken state on purpose — e.g., verifying that clicking a visually-disabled-but-not-actually-disabled-attribute element correctly does nothing, as a regression test for a specific bug.
  • Elements intentionally covered by design for a reason unrelated to the test's concern — rare, and usually better solved by scrolling or dismissing the covering element first rather than forcing through it.
  • Drag-and-drop or canvas-based interactions where the standard visibility model doesn't map cleanly — even here, force should be a deliberate, documented choice, not a default reflex.

Common Mistakes

  • Reaching for force: true the instant a click times out, before reading what the actionability error actually says is wrong.
  • Adding a manual waitForTimeout() before an action "just in case" — this doesn't address actionability at all; it just adds arbitrary delay while hoping the real condition resolves in that window, which is both slower and less reliable than waiting for the actual state.
  • Assuming a longer timeout fixes a stuck actionability check — if the element is genuinely blocked (disabled forever, permanently covered by a bug), no timeout length will help; the fix is in the app or the test's understanding of the flow, not the timeout value.

Edge Cases

  • Elements that are visible but covered by a transparent element (e.g., an invisible click-catcher <div> used for a modal backdrop) — the "receives events" check correctly catches this even though the element looks clickable to the eye; it's testing real click-target overlap, not just visual appearance.
  • Custom elements with non-standard disabled styling (visually greyed out via CSS but no real disabled attribute) — actionability checks only see the real disabled attribute/property, so a "visually disabled" button will still pass the enabled check and get clicked; this is often itself an app bug worth flagging.

Debugging

Always read the full actionability error log before reaching for force — it names the specific check that's failing (not stable, not visible, outside viewport, covered by another element), which almost always points directly at the real cause. Trace Viewer (Chapter 15) additionally shows a visual snapshot at the moment of failure, making "covered by another element" failures especially easy to diagnose at a glance.

Best Practices

  • Treat every actionability timeout as a signal worth investigating, not an obstacle to route around with force.
  • If force is genuinely necessary, leave a comment explaining why — future readers (including future you) shouldn't have to rediscover the reasoning.
  • Never use force as a first response to flakiness — diagnose via the error log and Trace Viewer first.

Summary

Actionability checks (attached, visible, stable, enabled, receives events) run automatically before actions, eliminating the most common category of flaky-test bugs without requiring manual waits. force: true skips all of them and should be reserved for narrow, deliberate, documented cases — not used as a default fix for timeouts, which almost always indicate a real problem worth understanding.

Interview Questions

A test fails in CI with "element is not stable — waiting..." but passes reliably every time you run it locally. A teammate proposes adding force: true to make the flakiness go away. Walk through what's actually happening and why that fix is the wrong one.▾

The "not stable" message means Playwright is watching the element's bounding box across consecutive frames and it's still moving — almost always a CSS transition or animation that hasn't finished settling. This is genuinely more likely to reproduce in CI than locally: CI runners are typically slower and more resource-constrained, so an animation that finishes well within the timeout on a fast local machine may still be mid-transition when Playwright checks in CI.

// The real cause — a card that slides in on page load:
// .card { transition: transform 400ms ease; }
// On a slow CI runner, 400ms of animation can still be running
// when the test's default timeout window starts checking stability.

await page.goto('/dashboard');
await page.getByRole('button', { name: 'Archive' }).click(); // times out: not stable

force: true would make the click happen mid-animation, at whatever coordinates the button happened to occupy at that instant — potentially missing it entirely, or clicking correctly by pure luck. The actual fix addresses the real condition instead: either wait for the animation to genuinely finish, or disable animations in the test environment entirely, which most real teams do specifically for this reason.

// playwright.config.ts
export default defineConfig({
  use: {
    // Disables CSS animations/transitions site-wide for tests
    launchOptions: { args: ['--force-prefers-reduced-motion'] },
  },
});
Write out what each of the five actionability checks — attached, visible, stable, enabled, receives events — actually verifies, and give one concrete real-world bug each one is specifically designed to catch.▾

Each check maps to a genuine, common real-world failure mode:

// ATTACHED — element exists in the DOM
// Bug it catches: a React/Vue re-render removes and recreates a
// component, and the test's old element reference is now a ghost
// pointing at nothing.

// VISIBLE — has a real bounding box, not display:none or 0 opacity
// Bug it catches: a modal that's technically rendered but still
// hidden behind a "loading" class that hasn't been removed yet.

// STABLE — bounding box hasn't moved across 2+ animation frames
// Bug it catches: clicking a button mid-slide-in, landing on the
// wrong coordinates because the element hadn't settled.

// ENABLED — no disabled attribute
// Bug it catches: a submit button correctly disabled until all
// required fields are filled — clicking it "successfully" via
// force would test a state a real user could never reach.

// RECEIVES EVENTS — nothing else is on top of it at that point
// Bug it catches: a cookie-consent banner or sticky header
// covering the actual target element, invisible to the test
// unless something explicitly checks for it.
await page.getByRole('button', { name: 'Submit' }).click();
// "element is not stable" / "is disabled" / "intercepted by <div class='cookie-banner'>" —
// each message names exactly which of the five checks failed
A code reviewer blocks a pull request containing await page.getByRole('button', { name: 'Delete Account' }).click({ force: true }). The PR author argues "it works, the test passes." Make the reviewer's case, with a concrete example of what could go wrong in production if this ships.▾

The reviewer is right to block it — "the test passes" is exactly the problem, not the reassurance the PR author thinks it is. A test's entire value comes from verifying that a real user could actually perform this action; force: true removes that verification while leaving the test green.

// What force: true actually did here, concretely:
// The "Delete Account" button was covered by an unread-notice banner
// ("You have 2 unread messages") that appears above account settings.
// A real user would need to dismiss the banner first — but the banner
// dismiss button had a bug and silently failed to register clicks.

await page.getByRole('button', { name: 'Delete Account' }).click({ force: true });
// passes: force skips the "receives events" check entirely,
// clicking straight through the banner as if it weren't there

// Without force:
await page.getByRole('button', { name: 'Delete Account' }).click();
// TimeoutError: element is outside of the viewport, or another
// element intercepts pointer events — surfaces the REAL bug:
// users are currently unable to delete their account at all

Shipping the force:true version means this genuine, user-facing bug reaches production with a fully green test suite — the worst possible outcome, since the team now has false confidence specifically where they have none.

Is there a legitimate, correct use for force: true, or should it always be treated as a workaround to remove? Give a genuine example where it's the right call.▾

It's rare, but genuine cases exist — specifically when an element is intentionally, correctly hidden from the actionability checks' perspective by design, not by accident.

// A real, defensible case: testing a "skip to main content" link,
// a common accessibility pattern that's visually hidden until
// keyboard focus reveals it (so sighted mouse users don't see
// clutter, but screen reader / keyboard users can access it).

// .skip-link { position: absolute; left: -9999px; }
// .skip-link:focus { left: 0; } /* only visible when focused */

const skipLink = page.getByRole('link', { name: 'Skip to main content' });
await skipLink.focus();          // triggers the CSS that reveals it
await expect(skipLink).toBeVisible(); // now genuinely visible — no force needed

// vs. a case where force is arguably defensible: verifying a
// programmatic click handler fires correctly on an element your
// OWN test setup has deliberately kept hidden for an unrelated
// reason, where visibility genuinely isn't what's being tested.

The distinguishing question is always: "is this element hidden/blocked because of a real condition a genuine user would also face, or because of something incidental to what I'm actually testing?" The skip-link example resolves itself without force at all once you trigger focus correctly — which is usually the better lesson: most apparent "legitimate" cases for force turn out to have a non-force solution once you find the actual right way to reach the element's real state.

You're pair-debugging a flaky test with a colleague. The error log shows "element is visible, enabled — element is not stable — waiting..." followed by a timeout. Your colleague says "let's just increase the timeout." Explain why that might not fix it, and what you'd check first instead.▾

Increasing the timeout only helps if the animation genuinely finishes eventually — it does nothing for an animation that's looping indefinitely, or a layout that never truly settles because something above it keeps reflowing (an image loading without reserved dimensions, a periodically-updating banner, a CSS animation with infinite iteration).

// Before reaching for a longer timeout, check what's ACTUALLY
// still moving — Playwright's own trace viewer shows this directly:
npx playwright show-trace trace.zip

// Or, quickly in the browser console during a paused debug session:
// getComputedStyle(document.querySelector('.card')).animationName
// "pulse-glow" — an infinite decorative animation, not a one-time
// transition — this element will NEVER pass the stable check

If the animation is genuinely a one-time, finite transition that's just slow, a longer timeout is a reasonable, honest fix. But if it's an infinite or looping animation — which a longer timeout can never resolve — the actual fix is either disabling animations in the test environment, or scoping the interaction to happen before the animation starts, not chasing the timeout number upward indefinitely.
