check() and uncheck()

Prerequisites: Actions overview, click() and dblclick()

What is check()?

locator.check(options?: { force?: boolean, timeout?: number })
locator.uncheck(options?: { force?: boolean, timeout?: number })

check() ensures a checkbox or radio button ends up in the checked state; uncheck() ensures it ends up unchecked. Both are idempotent — calling check() on an already-checked box does nothing (no extra click, no toggling off), unlike click(), which would toggle it.

Why it's important

Using click() on a checkbox works, but it toggles — the resulting state depends on whatever state the box happened to be in before, which is fragile if a previous step's behavior ever changes. check()/uncheck() express the actual intent ("this should end up checked") regardless of starting state, which is both clearer and more robust.

Basic Example

await page.getByLabel('I agree to the terms').check();
await expect(page.getByLabel('I agree to the terms')).toBeChecked();

Detailed Example — Idempotence in Practice

// Regardless of the checkbox's current state going in, this test
// guarantees it ends up unchecked — no need to check current state first
await page.getByLabel('Email me promotional offers').uncheck();
await expect(page.getByLabel('Email me promotional offers')).not.toBeChecked();

// Calling check() twice is safe and has no unintended side effect
await page.getByLabel('Remember me').check();
await page.getByLabel('Remember me').check(); // no-op, still checked

Real-World Example — Radio Button Group

test('user can select a shipping method via radio buttons', async ({ page }) => {
  await page.goto('/checkout');

  await page.getByLabel('Express shipping ($12.99)').check();
  await expect(page.getByLabel('Express shipping ($12.99)')).toBeChecked();
  await expect(page.getByLabel('Standard shipping (free)')).not.toBeChecked();

  await expect(page.getByTestId('order-total')).toHaveText('$62.97');
});

Radio buttons in the same group are mutually exclusive by browser behavior — checking one automatically unchecks the others, which the second assertion confirms explicitly rather than assuming.

❌ Fragile vs. ✅ Recommended

// ❌ click() toggles — correctness depends on unknown current state
await page.getByLabel('Remember me').click();

// ✅ check() guarantees the end state regardless of where it started
await page.getByLabel('Remember me').check();

Common Mistakes

  • Using click() on checkboxes out of habit — works today, but silently produces the wrong result if the checkbox's default state ever changes, since click() just toggles whatever's there.
  • Assuming check() works on any visually checkbox-shaped element — it requires the underlying element to genuinely be an <input type="checkbox">/radio or something exposing the correct accessible role and checked state; custom-built toggles need care (see Edge Cases).
  • Not asserting the resulting state — pairing every check()/uncheck() with toBeChecked()/not.toBeChecked() catches cases where the action silently had no effect due to a disabled or JS-blocked control.

Edge Cases

  • Custom-styled toggle switches built from a hidden native checkbox plus a styled visual sibling — check() still works as long as the hidden native input remains the accessible target; if the "toggle" is actually a plain <div> with no real checkbox underneath, use click() with an aria-checked assertion instead, since check()/toBeChecked() require a genuine checkbox role.
  • Checkboxes that trigger async side effects (e.g., an API call to save a preference) — pair the action with a waitForResponse() or a UI confirmation assertion, not just the checked state, if the test cares that the save actually happened.

Debugging

If check() times out, check whether the element is genuinely a checkbox/radio input with the correct role — a common cause is a custom component library rendering something that looks like a checkbox visually but exposes a different underlying role to the accessibility tree.

Best Practices

  • Always use check()/uncheck() over click() for checkboxes and radios — the idempotence is a real correctness benefit, not just style preference.
  • Assert the resulting state with toBeChecked() after every check()/uncheck() call in tests where that state matters to the assertion that follows.

Practice Exercise

A settings page has three notification-preference checkboxes, two initially checked and one unchecked. Write a test that ends with exactly the opposite state for all three, using check()/uncheck() rather than click().

Summary

check() and uncheck() guarantee a checkbox or radio button's end state regardless of its starting state, unlike the toggle behavior of click(). This idempotence makes tests more robust to unrelated changes in default state, and pairing the action with toBeChecked() confirms it actually took effect.

Interview Questions

Why is check() generally preferred over click() for checkboxes, even though both can end up producing a checked checkbox?▾
click() toggles the current state, so its result depends on whatever state the checkbox happened to be in beforehand — correct today, but silently wrong if that starting state ever changes. check() is idempotent: it guarantees the end state is checked regardless of where it started, which better expresses the test's actual intent and is more robust to unrelated changes elsewhere in the flow.
Why is check() described as idempotent?▾
Calling it on an already-checked box does nothing extra — no toggling, no side effect — the end state is guaranteed regardless of the starting state.
What happens if you call check() on something that isn't a genuine checkbox role?▾
It throws, since check()/toBeChecked() require a real checkbox or radio role — a custom-styled non-native toggle needs click() with an aria-checked assertion instead.
Why should you assert toBeChecked() after calling check()?▾
To catch cases where the action silently had no effect, such as a disabled or JS-blocked control.
How does checking a radio button affect its group?▾
Checking one radio in a group automatically unchecks the others, by native browser behavior — worth asserting explicitly rather than assuming.
