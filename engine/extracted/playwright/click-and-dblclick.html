click() and dblclick()

Prerequisites: Actions overview, Locators

What is click()?

locator.click(options?: {
  button?: 'left' | 'right' | 'middle',
  clickCount?: number,
  modifiers?: Array<'Alt'|'Control'|'Meta'|'Shift'>,
  position?: { x: number, y: number },
  force?: boolean,
  timeout?: number,
})

click() performs a real mouse click on an element — moving the (virtual) mouse to its center, then dispatching genuine mousedown/mouseup/click events, exactly as a user's click would. dblclick() is the same, dispatched twice in quick succession to trigger double-click handlers.

Why it's important

Click is the single most common action in UI automation, and also the one most exposed to actionability problems: clicking something not yet rendered, still animating in, or covered by a loading overlay. Playwright's actionability checks (covered fully on the Actionability and Force page) exist specifically to make click() reliable without manual waits.

What happens when you call click()

Under the hood, before the actual click event fires, Playwright:

  1. Waits for the element to be attached, visible, stable, enabled, and not obscured.
  2. Scrolls the element into view if needed.
  3. Computes the element's center point (or the given position).
  4. Dispatches real mousemove, mousedown, mouseup, and click events at that point.

This is meaningfully different from directly invoking a JavaScript onclick handler — Playwright's click genuinely simulates what a real user's mouse does, which is why it also correctly triggers CSS :hover/:active states and any listener attached anywhere in the click's event path, not just a specific handler.

Basic Example

await page.getByRole('button', { name: 'Submit' }).click();

Detailed Example — Click Options

// Right-click to open a context menu
await page.getByTestId('file-row-report.pdf').click({ button: 'right' });
await expect(page.getByRole('menu')).toBeVisible();

// Shift-click to select a range in a multi-select list
await page.getByText('Item 1').click();
await page.getByText('Item 5').click({ modifiers: ['Shift'] });

// Click a specific pixel offset within an element — e.g. a canvas or slider
await page.getByTestId('volume-slider').click({ position: { x: 40, y: 5 } });

Real-World Example — Double-Click to Rename

test('double-clicking a file name enters rename mode', async ({ page }) => {
  await page.goto('/files');

  await page.getByText('Q3 Report.docx').dblclick();
  const renameInput = page.getByRole('textbox', { name: 'File name' });

  await expect(renameInput).toBeVisible();
  await renameInput.fill('Q3 Report Final.docx');
  await page.keyboard.press('Enter');

  await expect(page.getByText('Q3 Report Final.docx')).toBeVisible();
});

❌ Fragile vs. ✅ Recommended

// ❌ Manual wait "just in case" before clicking
await page.waitForTimeout(2000);
await page.getByRole('button', { name: 'Submit' }).click();

// ✅ Actionability checks already handle this — no manual wait needed
await page.getByRole('button', { name: 'Submit' }).click();

Common Mistakes

  • Clicking a styled <div> instead of fixing the markup to a real <button> — works, but skips keyboard accessibility and role-based locators the app should have anyway.
  • Reaching for { force: true } the moment a click times out instead of investigating why — usually there's a genuine reason the element isn't clickable yet (an overlay, a disabled state), and forcing the click just hides a real bug. See Actionability and Force.
  • Assuming clickCount: 2 is the same as dblclick() — they're equivalent in effect, but dblclick() is clearer intent and is what most teams standardize on.

Edge Cases

  • Elements partially off-screen — Playwright auto-scrolls the element into view before clicking, but elements inside a scrollable container with unusual overflow behavior occasionally need that container scrolled manually first.
  • Overlapping elements (a tooltip covering a button on hover) — the "receives events" actionability check catches this and times out with a clear "element is covered by..." message rather than silently clicking the wrong thing.

Debugging

A click that times out with "element is not visible" or "element is covered by" is Playwright telling you exactly what's blocking it — use Trace Viewer (Chapter 15) or run with --debug to see the exact DOM state at the moment of the failed click, rather than guessing.

Best Practices

  • Trust actionability checks; treat a persistent click timeout as a real bug to investigate, not something to force past.
  • Use dblclick() (not two chained click() calls) when double-click behavior is genuinely what's being tested.
  • Follow every click with an assertion confirming its effect — a click that "succeeds" but does nothing is a false-positive test.

Practice Exercise

Write a test that right-clicks a table row to open a context menu, then left-clicks "Delete" from that menu, and asserts the row is gone.

Summary

click() dispatches a real, fully-simulated mouse click after actionability checks pass; dblclick() does the same twice in quick succession. Options like button, modifiers, and position cover right-clicks, shift-clicks, and precise coordinate clicks without needing lower-level workarounds.

Interview Questions

Why does Playwright's click() dispatch real mouse events instead of just calling the element's onclick handler directly?▾
Calling a handler directly bypasses everything a real click triggers — CSS hover/active states, event listeners attached elsewhere in the bubbling path, and any framework-level event delegation. Dispatching genuine mouse events means the test exercises the exact same code path a real user's click would, which is what makes the test meaningful.
What real browser events does click() dispatch, and why does that matter?▾
mousemove, mousedown, mouseup, and click — genuine simulated events, which is why click() also correctly triggers CSS :hover/:active states, unlike directly invoking a JS handler.
How would you shift-click to select a range in a multi-select list?▾
Pass modifiers: ['Shift'] to the click() call on the second item after clicking the first normally.
Is clickCount: 2 the same as calling dblclick()?▾
Functionally equivalent, but dblclick() communicates intent more clearly and is what most teams standardize on.
What does a 'element is covered by...' error during a click actually tell you?▾
Something (an overlay, a sticky header, a modal backdrop) is blocking the click target — a real condition a user would also be blocked by.
