waitForRequest() & waitForResponse()

Prerequisites: waitForURL() & waitForLoadState()

What is this?

page.waitForRequest(urlOrPredicate, options?: { timeout?: number })
page.waitForResponse(urlOrPredicate, options?: { timeout?: number })

These wait for a specific network request to be sent, or a specific response to be received, matched either by URL (string or regex) or a predicate function. This is the right tool whenever a UI update depends on a background API call with no reliable visible signal to wait on instead.

Why it's important

A debounced search, an autosave, a background job kickoff — all of these can update the UI in ways that are hard to pin down with a content assertion alone, especially when the "before" and "after" states look superficially similar. Waiting for the actual network exchange is the most direct, reliable signal available.

Basic Example

const response = await page.waitForResponse((res) =>
  res.url().includes('/api/orders') && res.status() === 200
);
console.log(await response.json());

The Race Condition Trap

// ❌ Race condition — the click might fire the request BEFORE waitForResponse
// starts listening, causing this to hang until timeout
await page.getByRole('button', { name: 'Place order' }).click();
await page.waitForResponse((res) => res.url().includes('/api/orders'));

// ✅ Set up the listener and the triggering action together with Promise.all —
// this guarantees the listener is active before the click can fire the request
const [response] = await Promise.all([
  page.waitForResponse((res) => res.url().includes('/api/orders')),
  page.getByRole('button', { name: 'Place order' }).click(),
]);

This is one of the most common real bugs in Playwright suites that use network waiting — starting the wait after the triggering action is a race that usually works locally (where everything is fast) and fails intermittently in CI (where timing varies more). The Promise.all pattern eliminates the race by registering the listener and firing the action essentially simultaneously.

Detailed Example — Matching by Method and Status

const [response] = await Promise.all([
  page.waitForResponse((res) =>
    res.url().includes('/api/cart/items') &&
    res.request().method() === 'POST' &&
    res.status() === 201
  ),
  page.getByRole('button', { name: 'Add to cart' }).click(),
]);

await expect(page.getByTestId('cart-count')).toHaveText('1');

Matching on method and status, not just URL, avoids accidentally matching a different request to the same endpoint (e.g., an unrelated GET happening around the same time).

Real-World Example — Waiting for a Request (Not the Response)

test('closing the tab triggers an analytics beacon', async ({ page, context }) => {
  await page.goto('/article/123');

  const [request] = await Promise.all([
    page.waitForRequest((req) => req.url().includes('/api/analytics/view')),
    page.waitForTimeout(100), // page fires the beacon shortly after load
  ]);

  expect(request.postDataJSON()).toMatchObject({ articleId: '123' });
});

waitForRequest() is less common than waitForResponse() but useful when what matters is confirming a request was sent at all — analytics/tracking calls being the most typical case — rather than anything about its response.

❌ Fragile vs. ✅ Recommended

// ❌ Guessing how long a background request takes
await page.getByRole('button', { name: 'Save' }).click();
await page.waitForTimeout(1500);
await expect(page.getByText('Saved')).toBeVisible();

// ✅ Wait for the real signal
const [response] = await Promise.all([
  page.waitForResponse((res) => res.url().includes('/api/save')),
  page.getByRole('button', { name: 'Save' }).click(),
]);
await expect(page.getByText('Saved')).toBeVisible();

Common Mistakes

  • Starting the wait after the triggering action instead of using Promise.all — a classic race condition that's intermittent, not consistently broken, which makes it especially confusing to debug.
  • Matching only by URL when multiple requests to the same endpoint happen close together (e.g., polling) — add method/status/payload checks to the predicate for precision.
  • Using this for requests that already have a clear UI signal — if a loading spinner reliably disappears when the request completes, a content assertion is simpler and just as reliable.

Edge Cases

  • Requests that fail or time out server-side — waitForResponse() resolves once any response arrives, including error statuses; check res.status() explicitly in the predicate if only success should satisfy the wait.
  • Multiple similar concurrent requests (e.g., a page firing several analytics calls at once) — a precise predicate checking multiple fields is essential to avoid matching the wrong one.

Debugging

Trace Viewer's Network tab (Chapter 15) shows every request and response in a failed test's timeline — use it to confirm the exact URL, method, and status of the request you're trying to match before finalizing a predicate.

Best Practices

  • Always pair waitForRequest()/waitForResponse() with the triggering action via Promise.all to avoid the race condition.
  • Match on more than just URL when precision matters — method, status, and payload shape are all available on the response/request object.
  • Reserve this for cases with no reliable UI signal to wait on instead — prefer content assertions when one exists.

Practice Exercise

Write a test that clicks a "Refresh" button triggering a GET request to /api/dashboard/stats, using Promise.all to avoid a race condition, and asserts the response status is 200 before checking the updated UI.

Summary

waitForRequest() and waitForResponse() wait for specific network activity matched by URL or a predicate — the most direct tool when a UI update depends on a background call with no reliable visible signal. Always pair them with the triggering action via Promise.all to avoid a race condition where the request fires before the listener is registered.

Interview Questions

This creates a race condition — if the request fires and completes before waitForResponse() starts listening, the wait never sees it and hangs until timeout. Wrapping both the action and the wait in Promise.all registers the listener and triggers the action together, so the listener is guaranteed to be active before the request can be sent.
