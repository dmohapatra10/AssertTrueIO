API Testing

Prerequisites: Authentication & storageState

What is this?

Playwright includes a full HTTP client — APIRequestContext — for making real API calls directly, with no browser involved at all. It shares the same context/cookie model as browser testing, which makes it a natural fit for both pure API test suites and for mixing API calls into UI tests for fast setup and verification. Each HTTP method gets its own dedicated page:

  1. GET Requests — query parameters, headers, pagination
  2. POST Requests — creating resources, payloads, file uploads
  3. PUT & PATCH Requests — full vs. partial updates
  4. DELETE Requests — removal, idempotence, cleanup

Why it's important

Not everything needs a browser. Seeding test data, verifying a backend response shape, or checking that a UI action produced the correct database change are all often faster and more reliable done via a direct API call than by driving the UI to accomplish the same thing.

Making Requests

test('API: creating an order returns 201', async ({ request }) => {
  const response = await request.post('/api/orders', {
    data: { item: 'Wireless Mouse', quantity: 2 },
  });

  expect(response.status()).toBe(201);
  const body = await response.json();
  expect(body).toMatchObject({ item: 'Wireless Mouse', quantity: 2 });
});

The request fixture is built in, just like page — no separate HTTP library needed. Every HTTP method is available the same way: request.get(), .post(), .put(), .patch(), .delete() — see each method's dedicated page above for the details, response validation patterns, and common pitfalls specific to it.

API + UI Workflows

The setup-then-verify pattern shown next covers half of the picture. The fuller, and often more valuable, pattern closes the loop back to the API afterward, to confirm the backend's actual state changed — not just that the UI visually looks right:

API
 ↓
Create test data
 ↓
UI
 ↓
Perform user workflow
 ↓
API
 ↓
Validate backend state

The first API step exists purely for speed (avoiding a slow UI-driven setup); the workflow itself is genuinely exercised through the UI, since that's what the test is actually meant to verify; the final API step exists because some outcomes — a database row's exact final state, a field the UI never displays — aren't fully verifiable by looking at the screen alone.

test('cancelling an order through the UI actually cancels it on the backend', async ({ page, request }) => {
  // API: create test data
  const created = await request.post('/api/orders', {
    data: { item: 'Wireless Mouse', quantity: 1 },
  });
  const { id } = await created.json();

  // UI: perform the user workflow
  await page.goto(`/orders/${id}`);
  await page.getByRole('button', { name: 'Cancel order' }).click();
  await expect(page.getByText('Order cancelled')).toBeVisible();

  // API: validate backend state — not just what the UI happens to display
  const fetched = await request.get(`/api/orders/${id}`);
  const order = await fetched.json();
  expect(order.status).toBe('cancelled');
  expect(order.cancelledAt).not.toBeNull();
});

That final assertion is the point of the pattern: the UI showing "Order cancelled" only proves the frontend rendered a success message — it doesn't prove the backend actually persisted the cancellation, or that a field like cancelledAt got set correctly. A UI bug that shows a false-positive success message would slip past a UI-only test but get caught immediately by the closing API check.

Real-World Example — API Setup, UI Verification

import { test, expect } from '@playwright/test';

test('order created via API appears correctly in the UI', async ({ page, request }) => {
  // Fast, reliable setup — no need to click through a multi-step checkout UI
  const response = await request.post('/api/orders', {
    data: { item: 'Wireless Mouse', quantity: 1, status: 'shipped' },
  });
  const { id } = await response.json();

  // Now use the UI for what's actually being tested — how the order displays
  await page.goto(`/orders/${id}`);
  await expect(page.getByRole('heading', { name: 'Wireless Mouse' })).toBeVisible();
  await expect(page.getByText('Shipped')).toBeVisible();
});

This is the highest-value pattern in this chapter: use the API for setup that isn't itself the point of the test, and the UI only for what genuinely needs UI-level verification. It's dramatically faster than clicking through a full checkout flow just to get an order into a "shipped" state.

Sharing Auth Between API and UI Calls

// The request fixture automatically uses the same storageState as the page fixture,
// so authenticated API calls work without any extra setup once storageState is configured
test('authenticated API call using the same session as the browser', async ({ page, request }) => {
  await page.goto('/dashboard'); // already logged in via storageState
  const response = await request.get('/api/profile'); // shares the same cookies
  expect(response.ok()).toBeTruthy();
});

❌ Fragile vs. ✅ Recommended

// ❌ Clicking through the full UI just to create test data for an unrelated test
await page.goto('/products/wireless-mouse');
await page.getByRole('button', { name: 'Add to cart' }).click();
await page.goto('/checkout');
// ...ten more lines just to get one order into the database...

// ✅ Create it directly via the API in one line
const { id } = await (await request.post('/api/orders', { data: { /* ... */ } })).json();

Common Mistakes

  • Using the UI for setup that isn't what the test is actually verifying — slow and adds unrelated failure points to a test that's supposed to be about something else.
  • Not checking response.ok()/status() before parsing the body — a failed request with an unexpected error format can make .json() throw a confusing parsing error instead of a clear status-code assertion failure.
  • Assuming request and browser page calls never share state — by default they do share cookies/storage within the same test, which is a feature (see the shared-auth example) but can also be a source of confusion if not expected.

Edge Cases

  • APIs requiring multipart/form-data (file uploads via API) — request.post() supports a multipart option for this, separate from the data option used for JSON bodies.
  • Non-JSON responses — use response.text() or response.body() instead of .json() for plain text or binary responses.

Debugging

When an API assertion fails unexpectedly, log response.status() and the raw response text before assuming the JSON shape is wrong — a non-2xx status with an HTML error page body is a very different problem than a 200 with an unexpected JSON structure, and the two produce confusingly similar-looking test failures if you only look at the parsed body.

Best Practices

  • Default to API calls for any setup or teardown that isn't itself the feature under test.
  • Check status codes explicitly rather than only inspecting the response body.
  • Combine API and UI calls within the same test freely — they share context/auth by default, which is a deliberate design choice, not a workaround.
  • Write dedicated pure-API tests for backend contract verification separate from UI-focused tests that happen to also use the API for setup.

Practice Exercise

Write a test that creates three orders via the API with different statuses (pending, shipped, cancelled), then navigates to an orders dashboard in the UI and verifies each order displays with the correct status badge.

Summary

APIRequestContext (the request fixture) provides a full HTTP client sharing the same session/context as browser testing, supporting all standard methods. Its highest-value use is fast, reliable setup and teardown for UI tests — reserving actual browser interaction for what genuinely needs UI-level verification.

Interview Questions

Why would you use the request fixture to create test data instead of clicking through the UI, even in a test that's primarily about the UI?▾
If creating the precondition (an existing order, a user account) isn't itself what the test is verifying, doing it through the UI adds unnecessary time and unrelated failure points — a bug anywhere in that setup flow could fail a test that has nothing to do with it. An API call achieves the same starting state faster and more reliably, letting the UI interaction in the test focus only on the behavior actually being tested.
Why use the API instead of the UI to seed test data?▾
It's faster and decoupled from unrelated UI flows, so a bug in checkout doesn't fail a test that's actually about order history.
Does the request fixture share authentication with the page fixture automatically?▾
Yes — they share the same context/cookie model by default, so an already-authenticated session via storageState covers both.
What's the value of the final API step in the API→UI→API workflow pattern?▾
It confirms the backend's actual state changed, not just that the UI displayed a success message — catching bugs a UI-only check would miss.
What HTTP methods does APIRequestContext support?▾
All standard methods — get(), post(), put(), patch(), and delete() — each available the same way on the request fixture.
