PUT & PATCH Requests

Prerequisites: POST Requests

What is this?

request.put(url: string, options?: { data?, headers? })
request.patch(url: string, options?: { data?, headers? })

Both update an existing resource, but with a different contract: PUT conventionally replaces the entire resource with what you send; PATCH applies a partial update, changing only the fields included. Which one a given endpoint actually expects is a property of that specific API, not something Playwright decides — this page is about testing that contract correctly once you know which one applies.

Why it's important

Using the wrong one against a strict API is one of the more common, confusing API test bugs: send a partial payload to a PUT endpoint that expects the full resource, and fields you didn't include can silently get reset to empty or default values — a bug that looks like "half my update didn't work" rather than "I used the wrong HTTP method."

Basic Example — PATCH (Partial Update)

const response = await request.patch('/api/orders/ORD-10492', {
  data: { quantity: 3 }, // ONLY quantity changes; every other field is untouched
});

expect(response.ok()).toBeTruthy();
const order = await response.json();
expect(order.quantity).toBe(3);
expect(order.item).toBe('Wireless Mouse'); // unchanged, confirming this was a partial update

That last assertion is doing real work — it's not enough to confirm the field you changed actually changed; confirming a field you didn't send is still correct is what proves the update was genuinely partial and didn't accidentally clobber anything else.

Basic Example — PUT (Full Replacement)

const response = await request.put('/api/orders/ORD-10492', {
  data: {
    item: 'Wireless Mouse', // must include EVERY field, even ones that aren't changing
    quantity: 3,
    status: 'confirmed',
  },
});

expect(response.ok()).toBeTruthy();

Detailed Example — The Bug PUT vs. PATCH Confusion Causes

test('demonstrates why PUT with a partial payload can silently lose data', async ({ request }) => {
  const created = await request.post('/api/orders', {
    data: { item: 'Keyboard', quantity: 1, giftNote: 'Happy Birthday!' },
  });
  const { id } = await created.json();

  // ❌ Sending PUT with only the field being changed — on a strict PUT
  // implementation, this can wipe out giftNote and other omitted fields
  await request.put(`/api/orders/${id}`, { data: { quantity: 2 } });

  const fetched = await request.get(`/api/orders/${id}`);
  const order = await fetched.json();

  // On a strict PUT implementation, this fails — giftNote got reset
  console.log(order.giftNote); // may now be null/undefined, not 'Happy Birthday!'
});

This isn't a hypothetical — it's the single most common real bug this pair of methods produces, and it's exactly why testing the omitted-field behavior explicitly (not just the field you intentionally changed) matters for both methods, in opposite directions: PATCH should leave omitted fields alone; PUT conventionally should not.

Real-World Example — Testing Both Contracts on the Same Resource

test.describe('order update contract', () => {
  let orderId: string;

  test.beforeEach(async ({ request }) => {
    const res = await request.post('/api/orders', {
      data: { item: 'Wireless Mouse', quantity: 1, giftNote: 'For Alex' },
    });
    ({ id: orderId } = await res.json());
  });

  test('PATCH updates only the specified field', async ({ request }) => {
    await request.patch(`/api/orders/${orderId}`, { data: { quantity: 5 } });

    const fetched = await request.get(`/api/orders/${orderId}`);
    const order = await fetched.json();

    expect(order.quantity).toBe(5);
    expect(order.giftNote).toBe('For Alex'); // untouched
  });

  test('PUT requires the full resource shape', async ({ request }) => {
    const response = await request.put(`/api/orders/${orderId}`, {
      data: { item: 'Wireless Mouse', quantity: 5, giftNote: 'For Alex' }, // full payload
    });

    expect(response.ok()).toBeTruthy();
  });
});

Idempotence: PUT vs. PATCH

PUT is idempotent by HTTP convention — sending the exact same PUT request twice produces the same end state as sending it once, since you're always replacing with the same full payload. PATCH is often not idempotent in practice — a patch like { increment: 1 } applied twice produces a different result than applying it once, even though most simple field-replacement PATCHes (like the quantity example above) happen to be idempotent too. Don't assume either property without checking what a specific PATCH endpoint actually does.

❌ Fragile vs. ✅ Recommended

// ❌ Using PUT with a partial payload, risking silent data loss on omitted fields
await request.put(`/api/orders/${id}`, { data: { quantity: 3 } });

// ✅ Use PATCH for partial updates; reserve PUT for sending the complete resource
await request.patch(`/api/orders/${id}`, { data: { quantity: 3 } });

Common Mistakes

  • Using PUT with a partial payload against an API that implements strict full-replacement semantics — the most common bug this pair of methods produces.
  • Only asserting the changed field, never the unchanged ones — this misses exactly the "did this silently reset other fields" bug that's the whole point of testing PUT/PATCH carefully.
  • Assuming PATCH is always idempotent — true for simple field-replacement patches, not guaranteed for incrementing or relative-change style patches.
  • Not checking the API's actual documented contract before choosing PUT vs. PATCH — some APIs don't follow the convention strictly, and the only way to know is to check.

Edge Cases

  • APIs that treat PUT as upsert (create if the resource doesn't exist, replace if it does) — this is a real, documented pattern for some APIs; verify whether yours does this before assuming PUT only ever operates on existing resources.
  • PATCH using JSON Patch or JSON Merge Patch formats (structured patch documents, rather than a simple partial object) — some APIs expect a specific patch format (an array of operations) rather than a plain partial object; check the API's documentation for which convention it follows.

Debugging

If a field you didn't intend to change shows up as null/empty after an update, check whether you used PUT with a partial payload against a strict-replacement endpoint — this is the single most common root cause, and switching that specific call to PATCH (or including the full resource in the PUT) resolves it.

Best Practices

  • Confirm each endpoint's actual PUT/PATCH contract from its documentation rather than assuming HTTP convention is followed strictly.
  • For every update test, assert both the changed field(s) and at least one deliberately-omitted field, to catch silent data loss in either direction.
  • Default to PATCH for partial updates in test setup — it's less likely to accidentally clobber fields you didn't mean to touch.

Practice Exercise

Write two tests against the same order resource: one using PATCH to update only the quantity and asserting every other field is unchanged, and one using PUT with a full payload, asserting the update succeeds and all fields reflect the new values.

Summary

PUT conventionally replaces a resource wholesale and is idempotent; PATCH applies a partial update and often isn't idempotent for non-trivial changes. The most common real bug is using PUT with a partial payload against a strict-replacement API, silently resetting omitted fields — testing both the changed and deliberately-unchanged fields on every update test is what catches this.

Interview Questions

A test sends a PUT request with only the fields being changed, and afterward a field that wasn't included comes back empty. What happened, and how would you fix the test?▾
The API's PUT endpoint implements full-replacement semantics — it treats the request body as the complete new state of the resource, so any field not included is reset to empty or default. The fix is either to switch that request to PATCH (which should only touch the specified fields), or, if PUT is genuinely required, to include the full current resource in the payload rather than just the changed fields.
