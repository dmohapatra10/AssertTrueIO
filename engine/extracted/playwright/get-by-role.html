Beginner

getByRole()

Prerequisites: Locators overview

What is getByRole()?

page.getByRole(role: string, options?: {
  name?: string | RegExp,
  exact?: boolean,
  checked?: boolean,
  disabled?: boolean,
  expanded?: boolean,
  level?: number,
  pressed?: boolean,
  selected?: boolean,
})

getByRole() finds elements by their accessibility role — the same information a screen reader uses to announce "button," "link," or "checkbox" to a visually impaired user. It reads from the browser's computed accessibility tree, not from the raw HTML, which is why it works whether an element is a native <button> or a <div role="button"> styled to look like one.

Why it's the recommended default

A role reflects what an element is to a user, not how a developer happened to implement it. That has two consequences: tests stay stable through refactors that change class names or DOM structure but don't change what the element does, and writing role-based tests continuously exercises whether your app is actually accessible — if you can't find a button by role, a screen reader user can't reliably find it either.

Mental Model: the accessibility tree

Every element in the DOM maps to a node in a parallel tree the browser builds specifically for assistive technology — the accessibility tree. A styled <div> with onClick and no role attribute maps to role generic, invisible to getByRole('button'), even though it's visually a button. This is getByRole() reading real browser semantics, not guessing from markup patterns.

Basic Example

await page.getByRole('button', { name: 'Submit' }).click();

Detailed Example — Common Roles

await page.getByRole('textbox', { name: 'Email' }).fill('user@example.com');
await page.getByRole('checkbox', { name: 'Remember me' }).check();
await page.getByRole('link', { name: 'Forgot password?' }).click();
await page.getByRole('heading', { name: 'Sign in', level: 1 }).isVisible();
await page.getByRole('combobox', { name: 'Country' }).selectOption('India');
await page.getByRole('button', { name: 'Sign in' }).click();

level narrows heading roles to a specific <h1>–<h6> level — useful when a page legitimately has multiple headings with similar text at different levels.

Real-World Example — Login Flow

test('user can sign in and reach the dashboard', async ({ page }) => {
  await page.goto('/login');
  await page.getByRole('textbox', { name: 'Email' }).fill('user@example.com');
  await page.getByRole('textbox', { name: 'Password' }).fill('correct-horse-battery-staple');
  await page.getByRole('button', { name: 'Sign in' }).click();

  await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
  await expect(page.getByRole('alert')).not.toBeVisible(); // no error banner
});

Every line reads like the test plan a human would write, and none of it breaks if the underlying markup is refactored from a <table>-based form to a <div>-based one — the roles stay the same either way.

Matching by state: checked, disabled, expanded, pressed, selected

// Disambiguate two "Notifications" toggles by their current state
await page.getByRole('checkbox', { name: 'Email notifications', checked: true }).uncheck();

// Only target the button while it's genuinely disabled — e.g. during a submit
await expect(page.getByRole('button', { name: 'Save', disabled: true })).toBeVisible();

// An accordion header's expanded state
await page.getByRole('button', { name: 'Shipping details', expanded: false }).click();

These state options don't just filter — they also make the test's intent explicit: a reviewer sees at a glance that the test cares about the disabled state, not just the presence of the button.

exact matching

// Matches "Sign in" AND "Sign in to continue" (default: substring, case-insensitive)
await page.getByRole('button', { name: 'Sign in' }).click();

// Matches ONLY the exact text "Sign in"
await page.getByRole('button', { name: 'Sign in', exact: true }).click();

Without exact: true, name matching is a case-insensitive substring match, not an equality check — worth knowing before assuming a name filter is more specific than it actually is.

❌ Fragile vs. ✅ Recommended

// ❌ Fragile — depends on class names that can change for styling reasons alone
await page.locator('.btn.btn-primary.submit-btn').click();

// ✅ Recommended — depends on what the element IS, not how it's styled
await page.getByRole('button', { name: 'Submit' }).click();

Common Mistakes

  • Omitting name when the page has multiple elements with the same role — page.getByRole('button') on a page with five buttons throws a strict-mode violation the moment you act on it.
  • Assuming a styled <div> has a role just because it looks interactive — without an explicit role attribute (or a native element like <button>), it maps to generic and getByRole() won't find it. This is usually a real accessibility bug worth reporting, not just a test problem.
  • Forgetting that name matching is substring by default and being surprised when { name: 'Sign in' } also matches a "Sign in to continue" button elsewhere on the page.

Edge Cases

  • Icon-only buttons with no visible text — the accessible name comes from aria-label, not visible text. If the button has neither, getByRole() can't target it by name at all, and getByTestId() becomes the pragmatic fallback.
  • Custom components from UI libraries (e.g., a React Select) often render an internal <input role="combobox"> — inspect the real DOM rather than assuming the role matches the component's marketing name.

Debugging

Use --debug or UI Mode's "Pick locator" (Chapter 2) to click the actual element and see its resolved role and accessible name — this is far more reliable than guessing from the HTML source, since the accessible name is computed from a chain of rules (aria-label, aria-labelledby, visible text, alt text, in that priority order).

Best Practices

  • Start every new locator decision with "can I write this as getByRole()?" before considering anything else.
  • Add aria-label to icon-only interactive elements in the app itself — it fixes accessibility and testability at the same time.
  • Use state options (checked, disabled, expanded) to make test intent explicit rather than asserting on CSS classes.

Practice Exercise

Given a page with three buttons — "Save," "Save as draft," and a disabled "Save" during submission — write three separate getByRole() locators that unambiguously target each one, using exact and disabled where needed.

Summary

getByRole() reads the browser's real accessibility tree, making it resilient to markup changes and a built-in accessibility check. Use name to disambiguate, exact when substring matching is too loose, and state options when the test cares about more than presence.

Interview Questions

Why might getByRole('button', { name: 'Submit' }) fail to find a visually obvious Submit button?▾
Most likely the element isn't a native <button> and has no explicit role="button" attribute, so it maps to the accessibility tree's generic role instead of button — a real accessibility gap the test just surfaced, not a locator mistake.
Where does getByRole() actually read an element's role from?▾
The browser's computed accessibility tree — the same structure a screen reader uses — not the raw HTML tag name alone.
Why might getByRole('button') fail to find a visually obvious button?▾
If it's a styled <div> with no role='button' and no native button element, it maps to the generic role in the accessibility tree, not button.
What's the default matching behavior for the name option?▾
Case-insensitive substring matching, unless exact: true is passed, which requires a full match.
Name two role state options besides visibility that let you disambiguate elements.▾
checked and disabled (also expanded, pressed, and selected) — useful when multiple elements share a role and name but differ in state.
