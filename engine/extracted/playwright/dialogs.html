Chapter 12: Dialogs

Prerequisites: Actions, Waiting and Synchronization

What is this?

Native browser dialogs — alert(), confirm(), and prompt() — are rendered by the browser itself, outside the normal DOM. They can't be located or clicked with regular locators; Playwright instead exposes them through a dialog event.

Why it's important

An unhandled dialog blocks the page entirely — JavaScript execution pauses until the dialog is dismissed. If a test doesn't set up a handler before triggering one, the test will hang or time out, which is a confusing failure if you don't know dialogs need this special handling.

Mental Model

Dialogs sit outside the page's DOM the same way a native OS file picker does (see the setInputFiles() page in Actions) — they're not elements Playwright's normal locator system can see. Instead of finding and clicking a dialog's buttons, you intercept the event that represents the dialog appearing, and respond programmatically before the browser ever actually shows it.

Automatic Dismissal by Default

Playwright auto-dismisses dialogs by default so a forgotten dialog doesn't hang your entire suite — but auto-dismissal happens silently, which means a test can pass or fail in a way that doesn't reflect what you intended unless you explicitly handle the dialog yourself.

Handling a Dialog Explicitly

The handler must be registered before the action that triggers the dialog, since the event fires synchronously as soon as the page calls e.g. window.confirm():

page.on('dialog', async (dialog) => {
  expect(dialog.message()).toContain('Are you sure you want to delete this item?');
  await dialog.accept();
});

await page.getByRole('button', { name: 'Delete' }).click();

Use dialog.dismiss() instead of accept() to simulate clicking "Cancel," and for a prompt() dialog, pass a value to accept() to simulate typed input: await dialog.accept('some text').

Basic Example — a prompt() Dialog

page.on('dialog', async (dialog) => {
  expect(dialog.type()).toBe('prompt');
  await dialog.accept('My Custom List Name');
});

await page.getByRole('button', { name: 'Create new list' }).click();
await expect(page.getByRole('heading', { name: 'My Custom List Name' })).toBeVisible();

Detailed Example — beforeunload Confirmation

// Some apps warn about unsaved changes when navigating away
page.on('dialog', (dialog) => {
  expect(dialog.type()).toBe('beforeunload');
  dialog.accept(); // proceed with navigation despite unsaved changes
});

await page.getByLabel('Notes').fill('Unsaved draft text');
await page.getByRole('link', { name: 'Go back' }).click();

beforeunload dialogs are triggered differently than the other three (by attempted navigation, not a direct script call) but are handled through the exact same event, which keeps the API consistent even for this less obvious case.

Real-World Example — Confirming a Destructive Action

import { test, expect } from '@playwright/test';

test('deleting an item requires confirmation', async ({ page }) => {
  await page.goto('/inventory');

  page.on('dialog', async (dialog) => {
    expect(dialog.type()).toBe('confirm');
    await dialog.accept();
  });

  await page.getByRole('row', { name: 'Wireless Mouse' })
    .getByRole('button', { name: 'Delete' })
    .click();

  await expect(page.getByText('Wireless Mouse')).toHaveCount(0);
});

test('cancelling the confirmation keeps the item', async ({ page }) => {
  await page.goto('/inventory');

  page.on('dialog', (dialog) => dialog.dismiss());

  await page.getByRole('row', { name: 'Wireless Mouse' })
    .getByRole('button', { name: 'Delete' })
    .click();

  await expect(page.getByText('Wireless Mouse')).toBeVisible();
});

These two tests cover both branches of the same interaction — a good habit for any dialog-gated action, since the dismiss path is exactly the kind of thing that's easy to leave untested and easy to accidentally break.

❌ Fragile vs. ✅ Recommended

// ❌ Handler registered too late — the dialog may already have been auto-dismissed
await page.getByRole('button', { name: 'Delete' }).click();
page.on('dialog', (dialog) => dialog.accept()); // too late

// ✅ Handler registered before the triggering action
page.on('dialog', (dialog) => dialog.accept());
await page.getByRole('button', { name: 'Delete' }).click();

Common Mistakes

  • Registering the dialog handler after the action that triggers it, so the dialog fires (and gets auto-dismissed) before the handler is attached.
  • Relying on default auto-dismissal for a confirm() dialog whose "yes" path the test actually needs to exercise.
  • Never testing the cancel/dismiss path of a confirmation dialog, leaving that behavior completely unverified.
  • Forgetting beforeunload dialogs exist and being surprised when a navigation-triggering test hangs on an app that warns about unsaved changes.

Edge Cases

  • Multiple dialogs in sequence — if an action can trigger more than one dialog, the same page.on('dialog', ...) handler fires for each occurrence; make the handler's logic generic enough to handle repeated calls, or use a counter if each dialog needs different handling.
  • Dialogs triggered by timers, not direct user action — the handler must still be registered in advance, since there's no reliable way to know exactly when a timer-triggered dialog will appear.

Debugging

If a test hangs indefinitely right after an action that should be simple, suspect an unhandled dialog first — check whether the triggering code calls alert()/confirm()/prompt() and add a page.on('dialog', ...) handler before that action.

Best Practices

  • Register the dialog handler as the very next line before the action expected to trigger it, so the ordering is unambiguous when reading the test.
  • Assert on dialog.message() when the exact wording matters (e.g., a legally required confirmation message), not just that a dialog appeared.
  • Write both the accept and dismiss paths as separate tests for any destructive action gated by a confirmation dialog.

Practice Exercise

Write a test for a "Rename" feature that uses prompt() to collect a new name, asserting the renamed item appears with the typed value, and a second test that dismisses the prompt and confirms the original name is unchanged.

Summary

Native browser dialogs live outside the DOM and block execution until dismissed, so Playwright exposes them via a dialog event rather than a locator. Register the handler before triggering the dialog, use accept() or dismiss() to simulate the user's choice, and test both paths for any dialog gating a meaningful action.

Interview Questions

Why must a dialog event handler be registered before the action that triggers the dialog, rather than after?▾
The browser fires the dialog event synchronously the moment alert()/confirm()/prompt() is called, and Playwright auto-dismisses any dialog with no registered handler to avoid hanging the page. If the handler is attached after the triggering action, the dialog may already have appeared and been auto-dismissed before the handler exists to intercept it.
Why does an unhandled native dialog block test execution?▾
Native alert/confirm/prompt dialogs pause JavaScript execution until dismissed, and Playwright auto-dismisses any with no registered handler.
Why must the dialog handler be registered before the action that triggers it?▾
The dialog event fires synchronously the instant the page calls alert()/confirm()/prompt(); a handler added afterward misses it.
How do you simulate typing into a prompt() dialog?▾
Pass a value to dialog.accept('some text') instead of calling it with no argument.
Why is beforeunload handled through the same dialog event as the other three types?▾
It keeps the API consistent even though it's triggered differently — by attempted navigation rather than a direct script call.
