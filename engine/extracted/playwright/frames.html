Chapter 10: Frames

Prerequisites: Locators, Browser and BrowserContext

What is this?

An <iframe> embeds one HTML document inside another — common for payment widgets (Stripe, PayPal), embedded video players, and third-party ads or widgets. Playwright treats the content inside an iframe as its own isolated document tree, which means a plain page.locator() call can't see into it by default.

Why it's important

Payment forms are one of the most common places automation engineers actually run into iframes, and getting this wrong produces a confusing "element not found" error for an element that's clearly visible on screen — because it lives inside a nested document Playwright wasn't told to look inside.

Mental Model

Page (main document)
  │
  ├── Regular elements — reachable via page.getByRole(), etc.
  │
  └── <iframe>
        │
        └── A completely separate document tree —
            only reachable via page.frameLocator()

Think of a frame as a small page nested inside the outer page — it has its own DOM, its own document root, and its own set of elements that share no direct locator path with the outer page's elements.

frameLocator()

page.frameLocator() creates a scoped locator that searches inside a specific iframe, identified the same way you'd identify any other element — by role, test ID, or a CSS selector as a last resort.

const paymentFrame = page.frameLocator('iframe[title="Payment form"]');
await paymentFrame.getByLabel('Card number').fill('4242 4242 4242 4242');
await paymentFrame.getByLabel('Expiry').fill('12/28');
await paymentFrame.getByLabel('CVC').fill('123');

Everything from the Locators, Actions, and Assertions chapters works the same way once you're inside a frameLocator — it behaves like a scoped-down page, not a different API.

Basic Example — Reading Content From a Frame

const videoFrame = page.frameLocator('iframe[title="Product demo video"]');
await expect(videoFrame.getByRole('button', { name: 'Play' })).toBeVisible();
await videoFrame.getByRole('button', { name: 'Play' }).click();

Real-World Example — Checkout With an Embedded Payment Widget

import { test, expect } from '@playwright/test';

test('completes payment through an embedded Stripe frame', async ({ page }) => {
  await page.goto('/checkout');

  await page.getByLabel('Full name').fill('Jordan Lee');

  const stripeFrame = page.frameLocator('iframe[name^="__privateStripeFrame"]');
  await stripeFrame.getByPlaceholder('Card number').fill('4242 4242 4242 4242');
  await stripeFrame.getByPlaceholder('MM / YY').fill('12/28');
  await stripeFrame.getByPlaceholder('CVC').fill('123');

  await page.getByRole('button', { name: 'Pay now' }).click();

  await expect(page.getByText('Payment successful')).toBeVisible();
});

Note the final "Pay now" button and success message live on the main page, not inside the frame — so those lines correctly use page, not stripeFrame. Mixing this up (using the frame locator for main-page elements, or vice versa) is the most common bug in frame-heavy tests.

Nested Frames

Frames inside frames are handled by chaining frameLocator() calls:

const outer = page.frameLocator('#outer-frame');
const inner = outer.frameLocator('#inner-frame');
await inner.getByRole('button', { name: 'Confirm' }).click();

❌ Fragile vs. ✅ Recommended

// ❌ Positional, breaks if a new iframe is added anywhere on the page
await page.frameLocator('iframe').first().getByLabel('Card number').fill('4242...');

// ✅ Identified by a stable, purpose-specific attribute
await page.frameLocator('iframe[title="Payment form"]').getByLabel('Card number').fill('4242...');

Common Mistakes

  • Calling page.getByLabel() for a field that's actually inside an iframe, then not understanding why the element "isn't found" despite being visible.
  • Using the frame locator for elements that are actually on the main page (or vice versa) — always check where an element genuinely lives in the DOM tree first.
  • Targeting an iframe with a fragile index-based selector (page.frameLocator('iframe').first()) instead of a stable identifying attribute like title or name.

Edge Cases

  • Cross-origin iframes (a third-party payment provider's own domain) — Playwright's frameLocator works across origins without special configuration, unlike some older automation tools that required explicit cross-origin permission handling.
  • Frames that load asynchronously after the main page — frameLocator() itself doesn't need the frame to exist yet; actions and assertions within it retry the same way any other locator does, waiting for the frame and its content to become available.
  • Frames with dynamically changing name attributes (common with some payment providers that append random IDs) — a partial match selector like iframe[name^="__privateStripeFrame"] handles this, as shown in the checkout example.

Debugging

When debugging "element not found" on something visibly on screen, check the DOM inspector for an enclosing <iframe> before assuming the locator itself is wrong — this single check resolves a large fraction of frame-related confusion. Trace Viewer's DOM snapshots (Chapter 15) also make the frame boundary visually obvious.

Best Practices

  • Identify the target iframe with the most stable attribute available — a title attribute is often more reliable than an auto-generated name.
  • Treat a frameLocator result exactly like a scoped page — the same locator priority and actionability rules from earlier chapters apply unchanged.
  • When a third-party iframe's structure is entirely outside your control (a payment provider), keep the frame-targeting selector isolated in one place (a fixture or page object) so a provider update only requires one change.

Practice Exercise

Given a page with a nested iframe structure — an outer "widgets" frame containing an inner "chat" frame — write a test that sends a message through the innermost chat input using chained frameLocator() calls.

Summary

Content inside an <iframe> is a separate document that page.locator() can't see by default. page.frameLocator() scopes into that document and behaves like a normal page from there — same locators, actions, and assertions — which makes payment widgets and other embedded content testable without any special-case API, even across origins or several levels of nesting.
