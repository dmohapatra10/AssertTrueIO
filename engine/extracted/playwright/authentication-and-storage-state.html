Authentication & storageState

Prerequisites: Browser & Context, Fixtures

What is this?

Most real applications require a login before anything useful can be tested. Logging in through the UI on every single test works, but is slow and repetitive across hundreds of tests. storageState — introduced briefly in the Browser & Context chapter — lets you log in once, save the resulting session, and reuse it across your entire suite.

Why it's important

If logging in takes 3 seconds and a suite has 300 tests that each need to be authenticated, that's 15 minutes spent on nothing but repeated logins. storageState turns that into a one-time cost paid before the suite runs, not per test.

The Standard Pattern — a Setup Project

The idiomatic approach uses a dedicated "setup" project that runs once, logs in, and saves state — every other project then depends on it and starts already authenticated:

// playwright.config.ts
export default defineConfig({
  projects: [
    { name: 'setup', testMatch: /global\\.setup\\.ts/ },
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'], storageState: 'playwright/.auth/user.json' },
      dependencies: ['setup'],
    },
  ],
});
// global.setup.ts
import { test as setup } from '@playwright/test';

setup('authenticate', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('user@example.com');
  await page.getByLabel('Password').fill('correct-horse-battery-staple');
  await page.getByRole('button', { name: 'Sign in' }).click();
  await page.waitForURL('/dashboard');

  await page.context().storageState({ path: 'playwright/.auth/user.json' });
});

Every test in the chromium project now starts already logged in — no test needs to know authentication happened at all. This is a specific, standard application of the dependencies config option (covered fully in Configuration) combined with the storageState context option.

Basic Example — Verifying It Worked

test('dashboard loads without a login step', async ({ page }) => {
  await page.goto('/dashboard'); // no login code here at all
  await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
});

Detailed Example — Multiple User Roles

// Two setup tests, saving two separate auth states
setup('authenticate as admin', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('admin@example.com');
  await page.getByLabel('Password').fill('admin-password');
  await page.getByRole('button', { name: 'Sign in' }).click();
  await page.context().storageState({ path: 'playwright/.auth/admin.json' });
});

setup('authenticate as customer', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('customer@example.com');
  await page.getByLabel('Password').fill('customer-password');
  await page.getByRole('button', { name: 'Sign in' }).click();
  await page.context().storageState({ path: 'playwright/.auth/customer.json' });
});
// Then in a test file, load a specific role's state deliberately
test.use({ storageState: 'playwright/.auth/admin.json' });

test('admin can access the user management panel', async ({ page }) => {
  await page.goto('/admin/users');
  await expect(page.getByRole('heading', { name: 'User Management' })).toBeVisible();
});

test.use() overrides the project-level storageState for just that file — the mechanism that makes role-based testing practical without needing a separate project per role.

Real-World Example — Testing the Logged-Out State

test.describe('unauthenticated', () => {
  test.use({ storageState: { cookies: [], origins: [] } }); // explicitly empty state

  test('visiting a protected page redirects to login', async ({ page }) => {
    await page.goto('/dashboard');
    await expect(page).toHaveURL('/login');
  });
});

Since every other test in the project defaults to authenticated via config, deliberately testing the logged-out path needs this explicit override — otherwise it's easy to have zero coverage of what happens when a user isn't logged in at all.

Token-Based Authentication (APIs, not cookies)

// Some apps store auth as a token in localStorage rather than a cookie —
// storageState captures both automatically
const state = await context.storageState();
console.log(state.origins[0].localStorage); // includes any auth token stored here

storageState captures cookies and localStorage/sessionStorage per origin, so it works whether an app's session lives in a cookie, a JWT in localStorage, or both.

Authentication Fixtures

The setup-project pattern above is the standard approach and the right default. There's a second, complementary pattern worth knowing: a custom fixture (from the Fixtures chapter) that logs in on demand, inside the test process itself, rather than relying on a pre-generated file. This trades a little speed for flexibility — useful when the role needed varies per test in ways a fixed set of storageState files doesn't cleanly cover.

// auth-fixtures.ts
import { test as base } from '@playwright/test';

type Role = 'admin' | 'customer' | 'guest';

export const test = base.extend<{ loginAs: (role: Role) => Promise<void> }>({
  loginAs: async ({ page }, use) => {
    await use(async (role: Role) => {
      const credentials = {
        admin: { email: 'admin@example.com', password: 'admin-password' },
        customer: { email: 'customer@example.com', password: 'customer-password' },
        guest: null,
      }[role];

      if (!credentials) return; // guest = stay logged out, nothing to do

      await page.goto('/login');
      await page.getByLabel('Email').fill(credentials.email);
      await page.getByLabel('Password').fill(credentials.password);
      await page.getByRole('button', { name: 'Sign in' }).click();
      await page.waitForURL('/dashboard');
    });
  },
});
export { expect } from '@playwright/test';
// role-switch.spec.ts — a single test that genuinely needs two different roles in sequence,
// which pre-generated storageState files can't do within one test
import { test, expect } from './auth-fixtures';

test('admin can impersonate a customer and see their cart', async ({ page, loginAs }) => {
  await loginAs('admin');
  await page.getByRole('button', { name: 'Impersonate customer' }).click();

  await expect(page.getByText('Viewing as: customer@example.com')).toBeVisible();
});

The setup-project approach is faster for the common case — most tests need exactly one fixed role for their whole duration, and paying the login cost once up front beats paying it inside every test. Reach for an authentication fixture like this instead when a test genuinely needs to log in as more than one role within a single test, or needs login behavior that depends on data only known at test-run time (a dynamically created test account, for instance).

❌ Fragile vs. ✅ Recommended

// ❌ Logging in through the UI in every single test file
test.beforeEach(async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('user@example.com');
  // ...repeated in every file...
});

// ✅ Authenticate once via a setup project, reuse storageState everywhere
// (see the config + global.setup.ts pattern above)

Common Mistakes

  • Committing a real storageState JSON file with live credentials to version control — treat auth state files like secrets, generate them fresh in CI rather than committing a long-lived static file.
  • Not regenerating storageState when the underlying session/token expires — a stale file silently produces logged-out behavior that looks like an unrelated test failure.
  • Using UI-based login in every test "to be thorough" — the login flow itself only needs its own dedicated test; every other test just needs to already be logged in.

Edge Cases

  • Short-lived tokens (session expires in minutes) — regenerate storageState as part of each CI run rather than caching it across runs, so tests don't intermittently fail against an expired session.
  • Multi-factor authentication — the setup project's login step needs to handle MFA the same way a real login would (a test-only bypass, a fixed TOTP seed, or a staging environment that skips MFA); this is highly app-specific.

Debugging

If tests that should be authenticated suddenly start behaving as if logged out, check whether the storageState file is stale (an expired session token) before assuming the app itself broke — regenerating it is often the fix.

Best Practices

  • Use the setup-project + dependencies pattern as the default for any suite with more than a handful of authenticated tests.
  • Keep a dedicated, separate test for the actual login UI flow — don't skip testing login itself just because everything else bypasses it.
  • Generate storageState files fresh in CI; never commit real, long-lived credentials to the repository.
  • Maintain one saved state per distinct role/permission level your app has, when role-based access is part of what needs testing.

Practice Exercise

Set up a project with two roles (admin and regular user), each with their own storageState file generated by a setup project, and write one test per role verifying they see different content on the same URL.

Summary

storageState captures a logged-in session's cookies and local/session storage, letting a whole suite skip repeated UI-based logins after one setup step. The standard pattern uses a dedicated setup project with dependencies, and test.use() to override state per file for multi-role testing.

Interview Questions

Why is a dedicated setup project with dependencies preferred over calling login code in beforeEach for every test?▾
Logging in through the UI is slow, and repeating it in every test multiplies that cost across the whole suite for no additional coverage — the login flow itself only needs to be verified once. A setup project authenticates a single time, saves the resulting session via storageState, and every dependent test starts already logged in, cutting total suite time significantly while still keeping a dedicated test for the login flow itself.
Why is the setup-project pattern faster than logging in via UI in every test?▾
Login happens once for the whole suite, not per test — with 300 tests each taking 3 seconds to log in, that's 15 minutes saved.
What does storageState actually capture?▾
Cookies and localStorage/sessionStorage per origin, so it works whether a session lives in a cookie, a JWT in localStorage, or both.
How do you override the project-level authenticated state for just one test file?▾
Call test.use({ storageState: '...' }) at the top of that file, pointing to a different saved state.
Why use a custom authentication fixture instead of the setup-project pattern in some cases?▾
When a single test genuinely needs to log in as more than one role within its own body — something a fixed set of pre-generated storageState files can't do.
