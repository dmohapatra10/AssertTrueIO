Forms

Prerequisites: Locators, Actions, Assertions

What is this?

Forms are the single most common piece of real-world UI a test automation engineer interacts with — login, checkout, signup, settings. This chapter isn't about new APIs; it's about combining everything from the Locators, Actions, and Assertions chapters into reliable patterns for the specific form widgets you'll actually run into.

Why it's important

Individually, filling a text field or checking a box is simple. What actually causes flaky or unreliable form tests is the combination — conditional fields that appear based on another field's value, validation that fires on blur, dropdowns that populate asynchronously. This chapter works through those realistic combinations.

Text Fields and Textareas

await page.getByLabel('Full name').fill('Jordan Lee');
await page.getByLabel('Bio').fill('Automation engineer based in Bengaluru.');

Nothing new here beyond fill() — the main judgment call in a real form is whether any field needs pressSequentially() instead, because something (a character counter, an autocomplete) reacts to individual keystrokes.

Dropdowns — Native vs. Custom

// Native <select>
await page.getByLabel('Country').selectOption({ label: 'India' });

// Custom-built dropdown (a styled <div>, not a real <select>)
await page.getByRole('combobox', { name: 'Country' }).click();
await page.getByRole('option', { name: 'India' }).click();

Telling these apart matters — selectOption() only works on genuine <select> elements (full detail on the selectOption() page). Most modern component libraries (Material UI, Ant Design, custom design systems) build their own dropdown from a button and a list, which needs the click-then-click pattern instead.

Checkboxes and Radio Groups

await page.getByLabel('I agree to the terms').check();
await page.getByLabel('Express shipping').check(); // radio group — selects this option

See check() and uncheck() for the full treatment, including why these are preferred over click() for idempotence.

Date Pickers

// Many date pickers accept direct typed input in a masked field
await page.getByLabel('Check-in date').fill('12/25/2026');

// Calendar-widget pickers need to be driven like any other custom component —
// open it, then click the specific day
await page.getByLabel('Check-in date').click();
await page.getByRole('button', { name: 'December 25, 2026' }).click();

There's no single "date picker API" — every library implements this differently. Inspect the actual markup before assuming either pattern works; some pickers support both typed input and calendar clicks, others only one.

Detailed Example — Conditional/Dynamic Fields

test('shows a company name field only for business accounts', async ({ page }) => {
  await page.goto('/signup');

  await expect(page.getByLabel('Company name')).toBeHidden();

  await page.getByLabel('Account type').selectOption('business');
  await expect(page.getByLabel('Company name')).toBeVisible();

  await page.getByLabel('Company name').fill('Acme Corp');
  await page.getByRole('button', { name: 'Create account' }).click();
});

This pattern — assert the field's absent, trigger the condition, assert it appears — is worth testing explicitly rather than assuming conditional logic works; conditional form fields are a common source of real bugs (a field that should hide but doesn't, or vice versa).

Real-World Example — Full Registration Form

import { test, expect } from '@playwright/test';

test('completes registration with all field types', async ({ page }) => {
  await page.goto('/register');

  await page.getByLabel('Full name').fill('Priya Sharma');
  await page.getByLabel('Email').fill('priya@example.com');
  await page.getByLabel('Password', { exact: true }).fill('correct-horse-battery-staple');
  await page.getByLabel('Country').selectOption({ label: 'India' });
  await page.getByLabel('Date of birth').fill('01/15/1995');
  await page.getByLabel('I agree to the Terms of Service').check();

  await page.getByRole('button', { name: 'Create account' }).click();

  await expect(page.getByText('Welcome, Priya!')).toBeVisible();
});

❌ Fragile vs. ✅ Recommended

// ❌ Assuming every dropdown is a native <select>
await page.getByLabel('Country').selectOption('India'); // throws if it's a custom combobox

// ✅ Check the actual markup first, then use the matching pattern
await page.getByRole('combobox', { name: 'Country' }).click();
await page.getByRole('option', { name: 'India' }).click();

Common Mistakes

  • Assuming a visually dropdown-like element is a native <select> without checking — selectOption() throws a clear error on the wrong element type, which is the fastest way to find out you assumed wrong.
  • Not testing conditional field visibility explicitly, only testing the end-to-end happy path where the condition happens to already be met.
  • Filling fields in an order that doesn't match how validation actually fires — some forms validate on blur, so filling field B before field A's validation has resolved can produce unexpected state.

Edge Cases

  • Auto-formatting inputs (phone numbers, credit cards) — as covered on the fill()/pressSequentially() page, these often need real keystroke events to trigger the formatting logic.
  • Multi-step (wizard) forms — treat each step as its own mini-flow with its own assertions before proceeding, rather than filling everything up front and hoping later steps render correctly.

Debugging

If a field "isn't found" despite being visible, check the Elements panel for whether it's a real form control or a JavaScript-driven custom component — the fix is usually a different interaction pattern, not a different locator strategy.

Best Practices

  • Inspect a form's actual markup before writing its test — don't assume dropdown/date-picker implementation from visual appearance alone.
  • Test conditional field behavior explicitly, not just as a side effect of a happy-path flow.
  • Group related field-filling into a test.step() (Test Runner chapter) for a long form, so a failure points at the specific section, not the whole test.

Practice Exercise

Write a test for a shipping form where selecting "International" as the shipping type reveals a "Customs declaration" textarea that isn't present for "Domestic" — verify both the hidden and visible states explicitly.

Summary

Form testing combines locators, actions, and assertions you already know — the real skill is correctly identifying each widget's actual implementation (native vs. custom dropdown, typed vs. calendar date picker) and testing conditional logic explicitly rather than only through a happy path.

Interview Questions

A dropdown looks identical to a native HTML select, but selectOption() throws an error. What's the likely cause and fix?▾
It's almost certainly a custom-built dropdown component (a styled <div>/<button> with a JavaScript-driven option list), not a genuine <select> element — selectOption() only works on real select elements. The fix is to interact with it like any other custom widget: click to open it, then click the desired option using its accessible role and name.
How do you tell whether a dropdown is a native <select> or a custom component?▾
Inspect the actual markup — selectOption() only works on genuine <select> elements and throws a clear error on the wrong type.
Why is testing a form's conditional field visibility explicitly important?▾
A happy-path test where the condition happens to already be true never verifies the show/hide logic actually works both ways.
What's a common date picker pitfall?▾
Assuming one universal API — some pickers accept typed masked input, others only respond to calendar clicks, and it varies by library.
Why might filling fields out of order cause unexpected form state?▾
Some forms validate on blur, so filling a later field before an earlier one's validation resolves can produce state that doesn't match a real user's flow.
