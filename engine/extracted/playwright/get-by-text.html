getByText()

Prerequisites: Locators overview

What is getByText()?

page.getByText(text: string | RegExp, options?: { exact?: boolean })

getByText() finds an element by its visible text content — matching against the rendered text a user actually sees, not the raw HTML source.

Why it's important, and where it fits

Most page content isn't interactive — status messages, table cells, paragraph text, toast notifications. For that content, there's no meaningful "role" to match on, so getByText() is the natural tool. It sits below getByRole()/getByLabel()/getByPlaceholder() in Playwright's priority precisely because interactive elements usually have a better, more semantic locator available — reach for getByText() once you've confirmed the element isn't interactive, or as a way to scope into a specific area of the page.

Matching modes

// Substring match, case-insensitive (default)
page.getByText('Order confirmed');

// Exact match, case-sensitive
page.getByText('Order confirmed', { exact: true });

// Regex match — most control
page.getByText(/order #\d+ confirmed/i);

Default substring matching is convenient but can over-match: getByText('Order') matches "Order confirmed," "Order #1042," and "Reorder" alike. Prefer the most specific string that still describes intent, and reach for exact or a regex when the page has similar text in multiple places.

Basic Example

await expect(page.getByText('Order confirmed')).toBeVisible();

Detailed Example — Scoping with getByText

// Find a specific table row by its visible content, then act inside it
const row = page.getByText('Wireless Mouse').locator('..').locator('xpath=ancestor::tr');
await row.getByRole('button', { name: 'Remove' }).click();

This pattern — locating a row by unique visible text, then scoping further actions to that row — is one of getByText()'s most common real uses. Chapter 6's table-handling content covers a cleaner version of this using filter().

Real-World Example — Toast and Status Messages

test('adding an item shows a confirmation toast', async ({ page }) => {
  await page.goto('/inventory');
  await page.getByRole('button', { name: 'Add to cart' }).first().click();

  await expect(page.getByText('Added to cart')).toBeVisible();
  await expect(page.getByText('Added to cart')).toBeHidden({ timeout: 5000 }); // toast auto-dismisses
});

❌ Fragile vs. ✅ Recommended

// ❌ Over-broad substring match that could match unrelated text elsewhere on the page
await expect(page.getByText('Order')).toBeVisible();

// ✅ Specific enough to mean exactly one thing
await expect(page.getByText('Order #ORD-10492 confirmed')).toBeVisible();

Common Mistakes

  • Using getByText() on buttons or links out of habit instead of getByRole() — text-based matching on interactive elements throws away the accessibility benefit and is more fragile to copy changes.
  • Under-specifying the string, causing strict-mode violations when the same or similar text appears more than once on the page.
  • Matching against whitespace-sensitive text — Playwright normalizes whitespace when matching, but copy-pasted text with unusual line breaks from the DOM can still cause confusion when debugging a mismatch.

Edge Cases

  • Text split across multiple nested elements — e.g., "Total: $49.99" — getByText() matches the full concatenated text of the nearest common element, so getByText('Total: $49.99') works even though the amount is in a nested <strong>.
  • Internationalized text — hardcoded English strings break the moment the app is localized; consider matching on a stable data-testid alongside or instead of text for content that will be translated.

Debugging

A "no matches found" error is often a whitespace or casing mismatch invisible to the eye — copy the exact string from a DOM inspector rather than retyping it, or switch to a regex with the case-insensitive flag while diagnosing.

Best Practices

  • Prefer role-based locators for anything interactive; reserve getByText() for genuinely non-interactive content or as a scoping anchor.
  • Use the shortest string that's still unambiguous, and add exact or a regex only when the default substring match is genuinely too loose.

Practice Exercise

A page shows "3 items in cart" that updates as items are added. Write a getByText() locator using a regex that matches any item count, not just 3.

Summary

getByText() matches visible, rendered text and is the right tool for non-interactive content and for scoping into a specific section of the page — but interactive elements should almost always use getByRole() instead.

Interview Questions

Why is getByRole() generally preferred over getByText() for buttons and links, even though both could technically find the same element?▾
getByRole() matches on what the element semantically is, which is stable across copy changes, styling changes, and localization, and validates that the element is genuinely accessible. getByText() matches raw visible text, which breaks the moment the copy changes for reasons unrelated to functionality, and can accidentally match unrelated non-interactive text elsewhere on the page.
Why is getByText() generally the wrong choice for buttons and links?▾
It matches raw visible text, which is fragile to copy changes and doesn't validate accessibility the way getByRole() does.
How does getByText() handle text split across nested child elements?▾
It matches against the full concatenated text of the nearest common element, so text inside a nested <strong> or <span> is still included.
What's a legitimate, common use for getByText()?▾
Non-interactive content like status messages or toasts, or as a scoping anchor to find a unique row/section before acting within it.
Why can hardcoded English text in getByText() become a liability over time?▾
If the app is later localized, the hardcoded string breaks; matching on a stable test ID or role is more resilient to translation.
