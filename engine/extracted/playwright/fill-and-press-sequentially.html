Beginner

fill() and pressSequentially()

Prerequisites: Actions overview, click() and dblclick()

What is fill()?

locator.fill(value: string, options?: { force?: boolean, timeout?: number })

fill() sets an input, textarea, or contenteditable element's value directly and instantly — clicking to focus it, clearing any existing value, and setting the new one in a single fast step, then dispatching an input event so the app's state updates.

What is pressSequentially()?

locator.pressSequentially(text: string, options?: { delay?: number })

pressSequentially() types character by character, dispatching real keydown, keypress, and keyup events for each one — the same event sequence a physical keyboard produces.

Why the difference matters

Most form fields only care about the final value, and fill() is the right, fast default for those. But some UI reacts to individual keystrokes — live autocomplete, character counters, input masks (like a phone number formatter), or keystroke-based validation. fill() skips those intermediate events entirely, so if a field's behavior depends on them, fill() will look like it "didn't work" even though the value is technically set.

Basic Example

await page.getByLabel('Email').fill('user@example.com');

Detailed Example — When fill() Silently Isn't Enough

// ❌ This search box shows live suggestions per keystroke — fill() sets the
// value but never fires the keystroke events the suggestion dropdown listens for
await page.getByRole('searchbox').fill('playwright');
await expect(page.getByText('Playwright Test')).toBeVisible(); // fails — dropdown never opened

// ✅ pressSequentially() fires real keystroke events, triggering the dropdown
await page.getByRole('searchbox').pressSequentially('playwright', { delay: 100 });
await expect(page.getByText('Playwright Test')).toBeVisible(); // passes

The delay option (milliseconds between keystrokes) matters here too — some autocomplete implementations debounce input and won't fire a request for keystrokes typed faster than a threshold.

Real-World Example — Masked Phone Input

test('phone number auto-formats as the user types', async ({ page }) => {
  await page.goto('/profile');

  const phoneField = page.getByLabel('Phone number');
  await phoneField.pressSequentially('4155552671', { delay: 50 });

  await expect(phoneField).toHaveValue('(415) 555-2671'); // mask applied live
});

clear() — Removing a Value Without Retyping

await page.getByLabel('Coupon code').clear();
await expect(page.getByLabel('Coupon code')).toHaveValue('');

clear() is a small but useful sibling of fill() — it empties a field's value without needing to pass an empty string to fill(''), and reads more clearly when that's the actual intent of the step.

❌ Fragile vs. ✅ Recommended

// ❌ Using pressSequentially() everywhere out of habit — slower for no benefit
await page.getByLabel('Full name').pressSequentially('Jordan Lee');

// ✅ Plain field with no keystroke-dependent behavior — fill() is faster and just as correct
await page.getByLabel('Full name').fill('Jordan Lee');

Common Mistakes

  • Defaulting to pressSequentially() for every field "to be safe" — this makes the whole suite meaningfully slower for fields that never needed it.
  • Not realizing why an autocomplete test is failing — a field silently not reacting to fill() because it needs real keystroke events is one of the most common sources of confusing action-related test failures.
  • Forgetting fill() clears the existing value first — occasionally surprising when the intent was actually to append text (use pressSequentially() after focusing at the end, or read the current value and concatenate before filling).

Edge Cases

  • Contenteditable elements (rich text editors) — fill() works on many, but complex WYSIWYG editors built on custom key handling sometimes require pressSequentially() or even direct keyboard shortcuts to behave correctly.
  • Fields with client-side validation on blur — fill() focuses and sets the value but doesn't automatically blur; if a test needs blur-triggered validation to run, follow with an explicit page.keyboard.press('Tab') or click elsewhere.

Debugging

If a field's value looks correct via toHaveValue() but dependent UI (a dropdown, a counter) doesn't update, suspect a keystroke-event dependency and try swapping fill() for pressSequentially() as the first diagnostic step.

Best Practices

  • Default to fill(); reach for pressSequentially() only once you've confirmed the field genuinely needs keystroke events.
  • Use clear() when the intent is specifically "empty this field," for readability.
  • Tune delay on pressSequentially() only as high as needed to satisfy a debounce — don't add delay speculatively.

Practice Exercise

A signup form has a username field that shows a live "checking availability..." indicator as you type. Write a test using the correct method to type a username and wait for the availability check to resolve.

Summary

fill() sets a value in one fast step and is the right default for ordinary form fields. pressSequentially() dispatches real per-character keystroke events and is required for autocomplete, input masks, or any UI that reacts to typing as it happens, not just the final value.

Interview Questions

A test using fill() passes, but a related test asserting an autocomplete dropdown appears fails. What's the likely cause and fix?▾
fill() sets the input's value directly without dispatching the individual keydown/keyup events the autocomplete's JavaScript listens for, so the dropdown's trigger logic never fires. Switching that specific action to pressSequentially(), which simulates real keystrokes, resolves it.
Why might fill() appear to 'do nothing' on a search box with live suggestions?▾
fill() sets the value directly without dispatching keystroke events, so listeners waiting for keydown/keyup to trigger a debounced search never fire.
What does the delay option on pressSequentially() control?▾
The pause in milliseconds between simulated keystrokes — useful for satisfying a debounce threshold some inputs require.
How is clear() different from fill('')?▾
Functionally similar, but clear() reads more clearly when the intent is specifically 'empty this field,' not set it to a blank string.
Give an example of UI that specifically needs pressSequentially() instead of fill().▾
An input mask, like a phone number formatter that reformats as you type character by character.
