Chapter 4: Locators

Prerequisites: Playwright Architecture

What is this?

A locator is a description of how to find an element on the page — a name and a strategy, not the element itself. Every locator page in this course is a different strategy for describing that "how":

  1. getByRole() — accessible role and name
  2. getByLabel() — form fields by their label
  3. getByPlaceholder() — inputs by placeholder text
  4. getByText() — non-interactive elements by visible text
  5. getByAltText() — images by alt text
  6. getByTitle() — elements by their title attribute
  7. getByTestId() — a dedicated automation hook
  8. locator() with CSS/XPath — the generic fallback
  9. Filtering and chaining — filter(), has, hasText, first()/last()/nth()

Why is it important?

Locators are the foundation everything else in Playwright is built on — every action (click(), fill()) and every assertion (toBeVisible()) operates on a locator. Getting locator strategy right is the single biggest factor in whether a test suite stays reliable over time or becomes flaky and unmaintainable.

Locators are lazy

Creating a locator does not search the page immediately — it just records the description. The actual search happens only when you call an action or assertion on it, and Playwright re-runs that search every time, right before acting.

// No DOM query happens on this line — it's just a description.
const submitButton = page.getByRole('button', { name: 'Submit' });

// The DOM is queried here, right before clicking, and Playwright
// auto-waits for the element to exist and be actionable first.
await submitButton.click();

This is why locators survive page navigations and re-renders — the element doesn't need to exist yet when you create the locator, only when you use it.

Auto-waiting

Before performing an action, Playwright automatically waits (up to the configured timeout) for the target element to satisfy a set of actionability checks: attached to the DOM, visible, stable (not animating), enabled, and not obscured by another element. This eliminates most of the manual sleep()/explicit-wait code required by older tools.

Strict mode

By default, calling an action on a locator that matches more than one element throws an error rather than silently acting on the first match. This is a deliberate safety feature — it forces you to write a locator specific enough to be unambiguous.

// Throws if the page has more than one button — which one did you mean?
await page.getByRole('button').click();

// Specific enough to match exactly one element.
await page.getByRole('button', { name: 'Submit' }).click();

Recommended locator priority

Playwright's official guidance ranks locator strategies by how closely they reflect what a user actually perceives, from most to least recommended:

  1. getByRole() — accessible role and name (button, link, checkbox)
  2. getByLabel() — form fields associated with visible label text
  3. getByPlaceholder() — inputs identified by placeholder text
  4. getByText() — non-interactive elements identified by visible text
  5. getByAltText() — images identified by alt text
  6. getByTitle() — elements with a title attribute
  7. getByTestId() — a dedicated data-testid attribute, for elements with no accessible name (fallback, not first choice)

CSS or XPath selectors (page.locator('.btn-primary')) sit below all of these — they're an escape hatch for cases none of the above cover, not a default habit. CSS selectors couple your tests to implementation details (class names, DOM structure) that change for reasons unrelated to the feature you're testing.

Chaining and filtering

Locators can be narrowed by chaining or filtering, which is how you handle repeated components like table rows or list items.

// Chaining: search inside a specific row for a button
const row = page.getByRole('row', { name: 'Order #1042' });
await row.getByRole('button', { name: 'Cancel' }).click();

// Filtering: find a list item that CONTAINS certain text
await page.getByRole('listitem')
  .filter({ hasText: 'Out of stock' })
  .getByRole('button', { name: 'Notify me' })
  .click();

Common mistakes

  • Reaching for CSS selectors first out of habit, before checking whether a role/label/text-based locator would work.
  • Fighting strict-mode errors by adding .first() instead of writing a more specific locator — this hides ambiguity rather than resolving it, and can silently click the wrong element later if the page order changes.
  • Re-querying the DOM manually (e.g., storing a raw element handle) instead of trusting locators to re-resolve automatically — this reintroduces the staleness bugs Playwright's model is designed to avoid.

Best practices

  • Default to getByRole(); drop down the priority list only when a role-based locator genuinely isn't available.
  • Reserve getByTestId() for elements with no meaningful accessible role or text — icon-only buttons, decorative containers.
  • When strict mode complains about multiple matches, narrow the locator (scope it to a row/section) rather than picking an index.

Summary

A locator is a lazy, auto-waiting description of how to find an element — not the element itself. Prefer role/label/text-based locators over CSS selectors, respect strict mode as a safety feature rather than working around it, and use chaining/filtering to handle repeated components precisely.

Interview Questions

Why does Playwright throw an error by default when a locator matches multiple elements, instead of just acting on the first one?▾
Silently acting on the first match hides ambiguity that often indicates a locator isn't specific enough — and worse, "first match" can silently change if the page's element order changes, causing the test to click the wrong element without failing. Strict mode surfaces that ambiguity immediately as a clear error instead of a subtle, intermittent bug.
What does it mean that a Playwright locator is 'lazy'?▾
A locator is just a stored description of how to find an element, not a live reference to one. It doesn't need the element to exist when created, and it re-resolves against the live DOM every time it's used.
Why does Playwright rank getByTestId() below getByRole() and getByLabel()?▾
Role and label locators match what a real user or screen reader perceives, so they double as an accessibility check. A test ID has no semantic meaning to a user, so it doesn't provide that benefit.
What's the risk of using CSS class selectors as your default locator strategy?▾
Class names are often tied to styling, not meaning, so a purely visual refactor (renaming a class, changing a layout) can silently break tests that have nothing to do with the actual feature.
If two elements match the same locator, what happens when you act on it?▾
Playwright throws a strict-mode violation rather than silently picking one — this is deliberate, since silently guessing which element you meant would hide real ambiguity bugs.
