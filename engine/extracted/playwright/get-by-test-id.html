getByTestId()

Prerequisites: Locators overview, getByRole()

What is getByTestId()?

page.getByTestId(testId: string | RegExp)

getByTestId() finds an element by a dedicated data-testid attribute — a hook that exists purely for automation, with no meaning to the browser, the user, or assistive technology.

Why it exists — and why it's last on the priority list

Every other locator in this course finds elements the way a user perceives them (a role, a label, visible text). getByTestId() deliberately doesn't — it's a private contract between the app and the test suite. That's exactly why Playwright ranks it last: using it as a default means your tests stop exercising whether the app is actually usable and accessible. It earns its place for the cases nothing else covers cleanly — icon-only elements with no good accessible name, deeply generic containers, or elements you specifically want decoupled from copy/design churn.

Basic Example

await page.getByTestId('checkout-submit-button').click();

Configuring the attribute name

By default Playwright reads data-testid, but this is configurable project-wide:

// playwright.config.ts
export default defineConfig({
  use: {
    testIdAttribute: 'data-qa', // e.g. to match an existing convention
  },
});

Changing this later is a global, one-line config change — not a find-and-replace across every test file — which is part of why standardizing on it early is worth doing deliberately rather than accidentally.

Detailed Example — Icon-Only Toolbar

<button data-testid="toolbar-bold"><svg .../></button>
<button data-testid="toolbar-italic"><svg .../></button>
<button data-testid="toolbar-underline"><svg .../></button>

await page.getByTestId('toolbar-bold').click();
await expect(page.getByTestId('editor-content')).toHaveClass(/bold-active/);

A better long-term fix here is adding aria-label="Bold" to each button so getByRole('button', { name: 'Bold' }) becomes possible — data-testid is a pragmatic bridge, not necessarily the permanent answer.

Real-World Example — Test-Only Container Scoping

test('order summary shows correct total', async ({ page }) => {
  await page.goto('/checkout');

  const summary = page.getByTestId('order-summary');
  await expect(summary.getByText('Subtotal')).toBeVisible();
  await expect(summary.getByTestId('order-total')).toHaveText('$64.98');
});

Using a test ID to scope into a repeated or ambiguous section of the page (here, disambiguating an "order-summary" total from any other dollar amount on the page) is one of the more defensible uses of this locator, even in an otherwise role-first test suite.

❌ Overuse vs. ✅ Deliberate use

// ❌ Reaching for data-testid on an ordinary, clearly-labeled button
await page.getByTestId('submit-btn').click();

// ✅ The button already has a perfectly good accessible name — use it
await page.getByRole('button', { name: 'Submit' }).click();

// ✅ Deliberate use — no meaningful role/label/text exists here
await page.getByTestId('color-swatch-4').click();

Common Mistakes

  • Defaulting to data-testid for every single element as a team convention "to be safe" — this produces tests that pass even when the app has become genuinely inaccessible, since accessibility gaps never surface as locator failures.
  • Auto-generating test IDs from database IDs or array indices — data-testid="item-47" tied to a mutable database row is fragile in a different way than CSS selectors, and just as disconnected from user-facing meaning.
  • Letting test IDs leak into production bundles unminified/unnecessarily when they're only ever needed in test/staging builds — a minor but real performance/cleanliness concern at scale.

Edge Cases

  • Third-party components you don't control (e.g., a vendor widget) — you can't add a data-testid to code you don't own, so this locator simply isn't available there; fall back to whatever stable role/text/CSS the vendor's markup does expose.

Debugging

If a test ID locator stops matching after a deploy, check whether the attribute was accidentally stripped by a build step (some minifiers/production configs strip non-standard data-* attributes) before assuming the element was removed entirely.

Best Practices

  • Ask "does this element have a real role, label, or text I should use instead?" before adding a test ID — treat it as the last resort it's designed to be.
  • Name test IDs after what the element does, not an internal implementation detail (checkout-submit-button, not btn-7).
  • Standardize the attribute name (data-testid or your own convention) via testIdAttribute in config, once, rather than mixing conventions across the codebase.

Practice Exercise

A settings page has five icon-only toggle switches with no visible text and no aria-label. Propose two different fixes — one purely in the test (using data-testid), and one in the app itself that would let you use getByRole() instead. Explain which you'd actually recommend to the team.

Summary

getByTestId() is a deliberate, configurable escape hatch for elements with no meaningful accessible role, label, or text — not a default. Overusing it trades away the accessibility-checking side benefit that role/label/text-based locators provide for free.

Interview Questions

If getByTestId() is the most stable, refactor-proof locator, why isn't it Playwright's recommended default?▾
Stability against refactors is only one axis. Because a test ID has no relationship to what a user or screen reader perceives, a suite built entirely on test IDs can pass in full even when the app has serious accessibility gaps — role, label, and text-based locators double as a continuous accessibility check, which is worth more than raw refactor-stability for most teams.
