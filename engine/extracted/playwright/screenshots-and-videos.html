Chapter 14: Screenshots and Videos

Prerequisites: Assertions, Getting Started

What is this?

Playwright can capture screenshots and record full video of a test run, either on demand or automatically when something goes wrong. This chapter covers manual capture for debugging, configured automatic capture for diagnosing CI failures you can't reproduce locally, and the separate, assertion-based tool for catching visual regressions.

Why it's important

A failing test's error message tells you what assertion failed, but not always why — a screenshot or video of the actual page state at the moment of failure is often the fastest way to understand a bug, especially one that only reproduces in CI and that you can't easily reproduce on your own machine.

Mental Model

There are really two unrelated tools that happen to share the word "screenshot":

  • page.screenshot() — an action that captures an image to a file. It makes no comparison and can't fail a test by itself; it's purely for human debugging.
  • toHaveScreenshot() — a web-first assertion that compares the current render against a stored baseline and fails the test if they differ too much. This is a testing tool, not a debugging aid.

Confusing these two — expecting a plain screenshot() call to "check" anything, or treating toHaveScreenshot() as just a way to save an image — is a common source of misunderstanding for engineers new to this part of Playwright.

Manual Screenshots

// Full page
await page.screenshot({ path: 'screenshots/dashboard.png', fullPage: true });

// A single element
await page.getByRole('table').screenshot({ path: 'screenshots/orders-table.png' });

Automatic Capture on Failure

Rather than adding manual screenshot calls throughout your suite, configure automatic capture in playwright.config.ts so every test failure gets a screenshot, video, and trace for free:

// playwright.config.ts
export default defineConfig({
  use: {
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
  },
});

'only-on-failure' and 'retain-on-failure' are deliberately the common defaults — capturing on every single test ('on') works too, but generates a large volume of artifacts for tests that already passed and told you nothing new.

Basic Example — Visual Regression With toHaveScreenshot()

await expect(page).toHaveScreenshot('dashboard.png');

// Scoped to a single element, more stable than a full-page comparison
await expect(page.getByRole('navigation')).toHaveScreenshot('nav-bar.png');

The first run generates the baseline image (with --update-snapshots); every run after that compares against it and fails if the difference exceeds a configurable threshold. This catches unintended visual changes that functional assertions (checking text or attributes) would never notice — a broken layout, a color regression, missing padding.

Detailed Example — Masking Dynamic Content

// A dashboard with a live "last updated" timestamp would otherwise
// fail every comparison, since the timestamp is always different
await expect(page).toHaveScreenshot('dashboard.png', {
  mask: [page.getByTestId('last-updated-timestamp')],
});

mask covers the specified elements with a solid block before comparing, so genuinely dynamic content (timestamps, live counters, ads) doesn't cause constant false failures while the rest of the layout is still meaningfully checked.

Real-World Example — Catching a Visual Regression

import { test, expect } from '@playwright/test';

test('product card layout matches baseline', async ({ page }) => {
  await page.goto('/products/wireless-headphones');
  await expect(page.getByTestId('product-card')).toHaveScreenshot('product-card.png', {
    maxDiffPixelRatio: 0.02,
  });
});

maxDiffPixelRatio allows a small tolerance — useful because font rendering and anti-aliasing can differ very slightly between machines even when nothing about the actual layout changed.

Video Configuration Options

ValueBehavior
'off'Never record (default)
'on'Record every test, pass or fail
'retain-on-failure'Record every test, but delete the video for tests that passed
'on-first-retry'Only record when a test is being retried after an initial failure

❌ Fragile vs. ✅ Recommended

// ❌ Full-page comparison including a constantly-changing element
await expect(page).toHaveScreenshot('dashboard.png'); // fails on every run

// ✅ Mask the dynamic part, or scope to a stable region
await expect(page).toHaveScreenshot('dashboard.png', {
  mask: [page.getByTestId('live-clock')],
});

Common Mistakes

  • Using full-page toHaveScreenshot() comparisons for content that includes frequently-changing data (timestamps, live prices), causing constant false failures.
  • Generating baseline screenshots on a different OS/browser than CI runs on — font rendering differs enough between platforms to cause consistent, spurious failures.
  • Setting screenshot: 'on' and video: 'on' globally "just in case," bloating CI artifact storage with captures from tests that already passed.
  • Not masking known-dynamic regions before assuming visual regression testing "doesn't work" on a page with live content.

Edge Cases

  • Animations mid-transition at capture time — Playwright's actionability "stable" check (Chapter 5) helps avoid mid-animation captures for actions, but screenshot comparisons can still occasionally catch a CSS transition partway through; consider disabling animations via a test-only CSS override for the most deterministic results.
  • Scrollbars affecting pixel comparison — a full-page screenshot's exact dimensions can shift slightly if a scrollbar appears/disappears due to content length changes; scoping to a specific element instead of the whole page avoids this.

Debugging

When a visual comparison fails, Playwright generates a diff image alongside the actual and expected screenshots, visible in the HTML report (Chapter 13) — always look at the diff image first; it usually makes the actual cause (a shifted element, a color change, a missing icon) immediately obvious rather than needing to eyeball two full screenshots side by side.

Best Practices

  • Scope visual comparisons to a specific stable element rather than the whole page, when only part of the UI is actually the concern.
  • Generate and update baseline screenshots in the same environment (often via CI itself) that will later run the comparisons.
  • Mask any genuinely dynamic content rather than avoiding visual testing on pages that have some.
  • Default to 'only-on-failure' / 'retain-on-failure' for screenshots and video; reserve 'on' for a specific debugging session, not permanent config.

Set up a visual regression test for a page that includes a live-updating "X users online" counter, using mask so the comparison remains stable despite the constantly-changing number.

Summary

Manual screenshots and automatic on-failure capture are debugging tools for understanding what happened. toHaveScreenshot() is a different, assertion-based tool for catching unintended visual regressions against a stored baseline, with masking and tolerance options to handle genuinely dynamic content — both are useful, but for different purposes.
