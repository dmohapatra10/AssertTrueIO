GitHub Actions CI/CD

Prerequisites: Test Reporting, Parallel Execution & Workers

What is this?

This chapter takes everything from Configuration, Reporting, and Parallel Execution and assembles it into one complete, working GitHub Actions pipeline — the practical destination all of those chapters were building toward.

Why it's important

Tests that only run on a developer's laptop provide much less value than tests that run automatically on every pull request. Getting the CI setup right the first time avoids a long tail of environment-specific bugs (missing system dependencies, wrong Node version, no browser binaries) that don't exist locally.

A Complete Working Workflow

# .github/workflows/playwright.yml
name: Playwright Tests
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20

      - name: Install dependencies
        run: npm ci

      - name: Install Playwright browsers
        run: npx playwright install --with-deps

      - name: Run Playwright tests
        run: npx playwright test
        env:
          BASE_URL: ${{ secrets.STAGING_BASE_URL }}
          CI: true

      - name: Upload HTML report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 14

Why --with-deps and npm ci

Two small but essential details, both different from local development habits:

  • npm ci instead of npm install — installs exactly what's in package-lock.json, faster and fully reproducible; npm install can update the lockfile unexpectedly in CI, which you never want.
  • --with-deps on browser install — Linux CI images typically lack the system libraries browsers need (fonts, codecs, graphics libraries); this flag installs them alongside the browser binaries. Omitting it is one of the most common causes of a "works locally, fails in CI" browser-launch error.

Basic Example — Matrix Execution Across Browsers

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        project: [chromium, firefox, webkit]
    steps:
      # ...same setup steps...
      - run: npx playwright test --project=${{ matrix.project }}

This runs the three browser projects (from the Projects & Environments chapter) as three separate parallel CI jobs rather than sequentially within one job — genuinely parallel at the CI infrastructure level, on top of Playwright's own worker parallelism within each job.

Detailed Example — Test Sharding for Very Large Suites

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1, 2, 3, 4]
    steps:
      # ...same setup steps...
      - run: npx playwright test --shard=${{ matrix.shard }}/4

Sharding splits the same test suite across multiple CI machines (shard 1 of 4, 2 of 4, etc.), each running a quarter of the tests — a different, complementary axis of parallelism from the browser matrix above, and the right tool once a suite is large enough that even full worker parallelism on one machine isn't fast enough.

Real-World Example — Combining Matrix, Secrets, and Conditional Retries

name: Playwright Tests
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        project: [chromium, firefox]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test --project=${{ matrix.project }}
        env:
          BASE_URL: ${{ secrets.STAGING_BASE_URL }}
          TEST_USER_EMAIL: ${{ secrets.TEST_USER_EMAIL }}
          TEST_USER_PASSWORD: ${{ secrets.TEST_USER_PASSWORD }}
          CI: true
      - if: always()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-report-${{ matrix.project }}
          path: playwright-report/

fail-fast: false ensures a failure in the Firefox job doesn't cancel the still-running Chromium job — without it, GitHub Actions cancels remaining matrix jobs the moment any one fails, which hides results you'd otherwise want to see. Secrets are read via ${{ secrets.NAME }}, configured in the repository settings — never hardcoded, consistent with the environment-variable pattern from the Configuration and Authentication chapters.

How CI Differs From Local Execution

  • No cached browser binaries — every run installs fresh unless you add explicit dependency caching, unlike a local machine where they persist.
  • Different, often more limited CPU allocation — a fixed workers count (Parallel Execution chapter) is usually more predictable than auto-detection on shared CI hardware.
  • No interactive debugging — --debug and UI Mode aren't practical in CI; traces and the HTML report (Reporting chapter) are how you investigate a CI-only failure after the fact.
  • Retries are more often appropriate — genuine environmental noise (network variance, shared-runner contention) is more common in CI than locally.

❌ Fragile vs. ✅ Recommended

# ❌ Missing --with-deps — will fail to launch browsers on a fresh Ubuntu runner
- run: npx playwright install

# ✅ Installs the system libraries browsers actually need
- run: npx playwright install --with-deps

Common Mistakes

  • Omitting --with-deps, causing browser launch failures that don't reproduce locally where those system libraries already happen to be present.
  • Using npm install instead of npm ci in CI, risking an unexpectedly updated lockfile.
  • Forgetting if: always() on the artifact upload step, losing the report exactly when a failure needs investigating.
  • Not setting fail-fast: false on a matrix build, hiding results from jobs that were cancelled after an unrelated one failed first.
  • Hardcoding credentials directly in the workflow file instead of using repository secrets.

Edge Cases

  • Self-hosted runners with pre-installed browsers — --with-deps and fresh installs may be unnecessary overhead there; cache or skip the install step based on your specific runner setup.
  • Very long-running suites hitting GitHub Actions' job time limits — sharding (shown above) is the standard fix, splitting one long job into several shorter parallel ones.

Debugging

When a CI-only failure needs investigation, download the uploaded HTML report artifact and open it locally with npx playwright show-report path/to/downloaded/report — this gives full access to traces, screenshots, and videos exactly as if you'd run the failing test yourself, without needing to reproduce the CI environment.

Best Practices

  • Always use npm ci and playwright install --with-deps in CI.
  • Upload the HTML report as an artifact with if: always() on every run.
  • Use a browser matrix and/or sharding once a suite is large enough to benefit from CI-level (not just worker-level) parallelism.
  • Store all credentials as repository secrets, referenced via ${{ secrets.NAME }}, never hardcoded.
  • Set fail-fast: false on matrix builds so one project's failure doesn't hide another's results.

Summary

A working Playwright CI pipeline installs dependencies with npm ci, browsers with --with-deps, runs tests with environment-driven config and secrets, and always uploads the HTML report as an artifact regardless of outcome. Browser matrices and sharding are two complementary ways to scale CI-level parallelism once worker parallelism on a single machine isn't enough.

Interview Questions

Why is npx playwright install --with-deps specifically important in CI but often unnecessary locally?▾
A developer's local machine typically already has the system-level libraries (fonts, codecs, graphics dependencies) that browsers need to launch, since it's a general-purpose development environment. A fresh CI runner image is minimal by design and usually lacks them — --with-deps installs those system dependencies alongside the browser binaries, which is why omitting it is a common cause of browser launch failures that only appear in CI.
The workflow uploads the HTML report with if: always(), even though every other step runs only on success by default. A teammate asks why bother — "if the tests failed, isn't the report useless anyway?" How would you respond, with a concrete example of why this matters?▾

The opposite is true — a report from a passing run is rarely looked at, while a report from a failing run is exactly the thing someone needs to actually diagnose what went wrong. Without if: always(), a failing test stops the job before the upload step ever runs (the default fail-fast behavior), which means the one run where the report was actually needed is precisely the run where it never gets published.

steps:
  - run: npx playwright test          # fails — job would normally stop here
  - name: Upload HTML report
    if: always()                        # runs regardless of the line above
    uses: actions/upload-artifact@v4
    with:
      name: playwright-report
      path: playwright-report/

# Without if: always() — a real, common failure mode:
# PR #482 fails in CI. Developer opens the Actions tab to see why.
# No report was ever uploaded, because the test step's failure
# skipped the upload step too. Developer has nothing to look at
# except a bare pass/fail log — has to re-run locally to actually
# see what broke, wasting real time on every single CI failure.

The report itself doesn't change based on outcome — it's the same HTML file either way — but whether it gets published absolutely does, unless always() overrides that default.
