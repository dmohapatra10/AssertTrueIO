Hard vs. Soft Assertions

Prerequisites: Assertions overview, Count, URL & Title Assertions

What is this?

Every assertion used so far is a hard assertion — the moment one fails, the test stops immediately; nothing after it runs. expect.soft() is the alternative: a failing soft assertion is recorded, but the test keeps executing, and all collected failures are reported together at the end.

Why it's important

Hard assertions are right most of the time — if a precondition fails, continuing usually just produces confusing downstream errors. But there's a real, common case where that's the wrong tradeoff: checking several independent, unrelated things on the same page, where you'd rather learn about all of them in one run than fix one, re-run, discover the next, and repeat.

Basic Example

// Hard assertion — stops here if it fails
await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();

// Soft assertion — records failure, test keeps running
await expect.soft(page.getByTestId('welcome-message')).toContainText('Welcome back');
await expect.soft(page.getByTestId('notification-count')).toBeVisible();
await expect.soft(page.getByTestId('user-avatar')).toBeVisible();

// Playwright Test automatically fails the test overall if ANY soft assertion failed,
// but only after the test function finishes running

Detailed Example — Auditing a Dashboard's Widgets

test('dashboard renders all expected widgets', async ({ page }) => {
  await page.goto('/dashboard');

  await expect.soft(page.getByTestId('widget-revenue')).toBeVisible();
  await expect.soft(page.getByTestId('widget-users')).toBeVisible();
  await expect.soft(page.getByTestId('widget-orders')).toBeVisible();
  await expect.soft(page.getByTestId('widget-activity-feed')).toBeVisible();

  // If widget-users is broken, this test still checks the other three
  // and reports ALL failures together instead of stopping at the first
});

This is the canonical soft-assertion use case: several independent checks where a failure in one tells you nothing about the others, and you'd rather have a complete picture from a single test run.

Real-World Example — Form Validation Messages

test('submitting an empty form shows all required-field errors', async ({ page }) => {
  await page.goto('/signup');
  await page.getByRole('button', { name: 'Create account' }).click();

  await expect.soft(page.getByText('Name is required')).toBeVisible();
  await expect.soft(page.getByText('Email is required')).toBeVisible();
  await expect.soft(page.getByText('Password is required')).toBeVisible();
});

If only the email validation is broken, a hard-assertion version of this test would stop after the name check passes and never tell you about email or password — soft assertions surface all three results from one run.

❌ Fragile vs. ✅ Recommended

// ❌ Soft assertions for a sequential flow, where step 2 genuinely depends on step 1
await expect.soft(page.getByRole('heading', { name: 'Checkout' })).toBeVisible();
await expect.soft(page.getByTestId('order-total')).toHaveText('$64.98'); // meaningless if checkout never loaded

// ✅ Hard assertion for the precondition, soft for independent details after it
await expect(page.getByRole('heading', { name: 'Checkout' })).toBeVisible();
await expect.soft(page.getByTestId('order-total')).toHaveText('$64.98');
await expect.soft(page.getByTestId('shipping-estimate')).toBeVisible();

Common Mistakes

  • Using expect.soft() for assertions where a later one depends on an earlier one succeeding — if the page never loaded, every subsequent soft assertion failing is just noise, not useful information.
  • Making every assertion in a suite soft "just in case" — this erodes the fail-fast benefit hard assertions provide for genuinely sequential logic, and makes failures harder to reason about overall.
  • Forgetting that a test with soft-assertion failures still ultimately fails — soft doesn't mean optional, it means "keep gathering information before failing."

Edge Cases

  • An action failing mid-test (not an assertion) — soft assertions don't change how actions behave; a click that times out still throws and stops the test regardless of surrounding soft assertions.
  • Combining with test.step() — grouping related soft assertions into a named step (Chapter 7 / Test Runner) makes the eventual failure report easier to read when several soft checks fail together.

Debugging

When a test with soft assertions fails, the test report lists every failed soft assertion together, each with its own stack trace and diff — read through all of them before fixing anything, since later failures sometimes explain earlier ones.

Best Practices

  • Use hard assertions for preconditions — anything later steps genuinely depend on.
  • Use soft assertions for a batch of independent checks against the same already-confirmed-loaded page.
  • Don't mix philosophies within a single logical check — decide per assertion whether "stop here" or "note and continue" is the more useful behavior.

Practice Exercise

Write a test for a product page that hard-asserts the page loaded (heading visible), then soft-asserts on five independent pieces of content (price, availability, rating, image, add-to-cart button) — deliberately break one and observe that the test report still shows all five results.

Summary

Hard assertions (the default expect()) stop a test immediately on failure — right for preconditions and sequential logic. Soft assertions (expect.soft()) record failures and let the test keep running, collecting a complete picture — right for batches of independent checks against a page already confirmed to have loaded correctly.

Interview Questions

Why wouldn't you just make every assertion in your suite soft, to always get maximum information from a failing test?▾
Many assertions are preconditions for what follows — if a page never loaded, every subsequent soft assertion about its content fails too, but that's just noise restating the same root cause. Hard assertions fail fast exactly where that's useful, giving a single clear signal instead of a wall of failures that all trace back to one problem.
What's the core behavioral difference between expect() and expect.soft()?▾
A failing hard assertion stops the test immediately; a failing soft assertion is recorded but the test keeps running, with all failures reported together at the end.
When is expect.soft() the wrong choice?▾
For a sequential flow where a later assertion genuinely depends on an earlier one succeeding — if the precondition failed, the later soft failures are just noise.
Does a test with only soft-assertion failures still count as failed overall?▾
Yes — soft doesn't mean optional; the test runner still marks it failed if any soft assertion failed, just after gathering all the results.
Give a good real-world use case for expect.soft().▾
Auditing several independent widgets on an already-confirmed-loaded dashboard, where a failure in one shouldn't stop checking the others.
