Chapter 6: Assertions

Prerequisites: Actions

What is this?

Assertions are how a test states what it expects to be true, and Playwright's assertions are "web-first" — built specifically for the reality that a web page keeps changing after an action, instead of assuming state is already final the instant the check runs. Each assertion family gets its own dedicated page:

  1. Visibility & State — toBeVisible(), toBeHidden(), toBeEnabled(), toBeDisabled(), toBeChecked()
  2. Text & Value — toHaveText(), toContainText(), toHaveValue(), toHaveAttribute()
  3. Count, URL & Title — toHaveCount(), toHaveURL(), toHaveTitle()
  4. Hard vs Soft Assertions — expect() vs expect.soft()

Why is it important?

A generic assertion library checks a value once, immediately, and fails if it isn't already correct. On a real web page, a value is often correct half a second later, after a network response resolves or an animation finishes. Web-first assertions close that gap automatically, which removes one of the most common sources of flaky tests.

How web-first assertions work

Every expect(locator).toX() assertion polls the condition repeatedly until it passes or the timeout is reached — it does not check once and immediately fail.

// If the heading takes 300ms to appear after the click, this still passes —
// toBeVisible() retries internally instead of checking only once.
await page.getByRole('button', { name: 'Load results' }).click();
await expect(page.getByRole('heading', { name: 'Results' })).toBeVisible();

This is different from a plain boolean check like if (await locator.isVisible()), which evaluates exactly once with no retry — a common source of flakiness when developers reach for it out of habit instead of an assertion.

What expect() actually does

expect() itself isn't a Playwright invention — it's the same assertion function shape used by Jest and other JS test frameworks. What makes Playwright's version different is what happens when you call expect(locator) specifically (as opposed to expect(someValue)): passing a locator (not an already-resolved value) is what activates web-first, auto-retrying behavior. Passing a plain value — a number, a string returned from an API call — gives you the generic, single-check Jest-style matchers (toEqual(), toContain()) with no retry, because there's nothing on a plain value that would ever change on its own.

// expect(locator) — web-first, retries automatically
await expect(page.getByRole('heading')).toBeVisible();

// expect(plainValue) — generic Jest-style, checks once, no retry
const total = await calculateTotal(items);
expect(total).toBe(64.98);

This is the actual mechanism behind the distinction in the table below — it's not that some matchers happen to retry and others don't, it's that what you pass to expect() determines the behavior.

Assertion timeout

Every web-first assertion has its own timeout — 5 seconds by default — separate from the overall per-test timeout (30 seconds by default, covered in the Configuration chapter). A test can run for up to 30 seconds total while any single assertion within it only gets 5 seconds to become true before that specific assertion fails.

// playwright.config.ts — change the default for every assertion in the suite
export default defineConfig({
  expect: { timeout: 8_000 },
});

// Override for a single assertion that's known to need longer
await expect(page.getByText('Report ready')).toBeVisible({ timeout: 20_000 });

Raising the global timeout does not extend how long an individual assertion waits — that's a separate value, and confusing the two is one of the more common config mistakes (covered further in the Configuration chapter). If one specific assertion genuinely needs longer (waiting on a slow report generation, say), override it locally with the assertion's own timeout option rather than raising the global default for every assertion in the suite.

Why assertions are also synchronization mechanisms

It's easy to think of assertions purely as "the thing that checks if the test passes," with waiting handled separately. In Playwright, that's not quite right: because expect(locator).toX() polls until the condition is true, an assertion is simultaneously a wait. This is why, in a well-written Playwright test, you often don't need any separate waiting step before an assertion — the assertion itself is the synchronization point.

// No separate "wait for the toast" step needed —
// toBeVisible() IS the wait, not just the check
await page.getByRole('button', { name: 'Save' }).click();
await expect(page.getByText('Saved')).toBeVisible();

This dual role — check and wait, in one call — is exactly why the Waiting & Synchronization chapter opens by pointing back here: assertions are the first and most common tool for synchronization in Playwright, and explicit waitFor*() methods exist specifically for the narrower set of cases assertions can't cover on their own (a background request with no visible UI signal, for instance).

toHaveText() vs toContainText()

A common early mixup. toHaveText() requires an exact match of the element's full text content; toContainText() checks for a substring.

// Fails if there's any extra whitespace/text around "Order confirmed"
await expect(page.getByRole('status')).toHaveText('Order confirmed');

// Passes even if the element reads "Order confirmed — thank you!"
await expect(page.getByRole('status')).toContainText('Order confirmed');

Real-world example: a search results page

import { test, expect } from '@playwright/test';

test('search returns matching, in-stock results', async ({ page }) => {
  await page.goto('/search?q=headphones');

  const results = page.getByRole('listitem', { name: /headphones/i });

  await expect(results).toHaveCount(12);
  await expect(results.first()).toBeVisible();
  await expect(page.getByRole('heading', { name: '12 results' })).toBeVisible();
  await expect(page.getByText('Out of stock')).toHaveCount(0);
});

The last line demonstrates a useful pattern: asserting a count of zero is a clean way to confirm something is absent, and it still benefits from auto-retry — important if "out of stock" badges render slightly after the main results.

Common mistakes

  • Using if (await locator.isVisible()) for a check that should be an assertion — this loses auto-retry and produces confusing, timing-dependent failures.
  • Reaching for toEqual() on locator content instead of toHaveText() — generic assertions don't retry, so they need extra manual waiting to be reliable.
  • Chaining several unrelated assertions on the same line before any of them have been given a reason to retry independently — prefer one assertion per meaningful expectation, so failures are easy to pinpoint.

Best practices

  • Always use expect(locator).toX() web-first assertions over manual boolean checks for anything involving the page.
  • Reserve generic assertions (toEqual, toContain) for plain JS values returned from API calls or computed logic, not live page state.
  • Assert on the specific thing that matters (a count, a piece of text) rather than a broad screenshot comparison, unless visual regression is genuinely the point of the test.

Summary

Playwright's web-first assertions retry automatically until they pass or time out, which matches how real pages actually update. Prefer them over manual boolean checks, use the right matcher for exact vs partial text, and reserve generic (non-retrying) assertions for plain values, not live page state.

Interview Questions

Why is expect(locator).toBeVisible() more reliable than if (await locator.isVisible())?▾
toBeVisible() is a web-first assertion that polls the condition repeatedly until it's true or the timeout elapses. isVisible() returns a single boolean at the instant it's called, with no retry — so if the element becomes visible a moment later, the check fails even though the page is behaving correctly.
What determines whether expect() retries or checks once?▾
What's passed to it — expect(locator) activates web-first, auto-retrying behavior; expect(plainValue) gives generic, single-check Jest-style matchers.
What's the default assertion timeout, and how is it different from the test timeout?▾
5 seconds by default, and it applies per-assertion — separate from the overall per-test timeout (30 seconds by default), which covers everything the test does combined.
In what sense is a web-first assertion also a synchronization mechanism?▾
Because it polls until the condition is true, an assertion like toBeVisible() IS the wait, not just a check performed after some other wait.
How would you extend an individual assertion's timeout without changing the global default?▾
Pass { timeout: N } directly to that specific assertion call, e.g. toBeVisible({ timeout: 20000}).
