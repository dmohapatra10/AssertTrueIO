Environment-Based Deployment: The Complete Pipeline

Prerequisites: Deployment Approvals & Protection Rules

What is this?

Time to assemble everything from this chapter — and quite a lot from earlier ones — into one real, complete deployment pipeline for ShopEasy, exactly matching the shape from this chapter's hub page.

The Complete Pipeline

name: ShopEasy Deploy

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with: { name: build-output, path: dist/ }

  test:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npm test

  deploy-test:
    needs: test
    environment: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with: { name: build-output, path: dist/ }
      - run: echo "Deploying to test at ${{ vars.API_BASE_URL }}"

  deploy-production:
    needs: deploy-test
    environment: production
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with: { name: build-output, path: dist/ }
      - run: echo "Deploying to production at ${{ vars.API_BASE_URL }}"

Tracing Exactly Why This Is Deliberately Asymmetric

deploy-test:       no protection rules configured on the "test" environment
                   → runs IMMEDIATELY once test passes, fully automatic

deploy-production: "production" environment has required reviewers configured
                   → PAUSES, waiting for explicit human approval, before running

Nothing in the deploy-production job's own YAML says "wait for approval" — that entire behavior comes from the environment's own protection rules (previous page), invisibly to anyone only reading this file. This is the real, working version of the asymmetry this chapter's hub page introduced conceptually.

🧠 Think About It

Why does deploy-production download the same build-output artifact rather than rebuilding the application from scratch? Rebuilding could genuinely produce a subtly different result than what was actually tested — a different dependency resolution, a different timestamp-sensitive value. Deploying the exact same artifact that was built once and tested is what makes the pipeline's guarantee meaningful: what gets tested is genuinely what gets deployed, not a fresh rebuild that merely resembles it.

⚠️ Common Mistake

Building separately for each deployment stage, rather than building once and reusing that exact artifact throughout the pipeline. Beyond the wasted time, this genuinely weakens the pipeline's core guarantee — you'd be testing one build and deploying a different one, even if they're supposed to be identical.

💡 Quick Tip

This exact "build once, promote the same artifact through environments" pattern is a widely-recognized best practice across the CI/CD industry generally, not something specific to GitHub Actions — worth recognizing the underlying principle as one that applies regardless of which specific CI/CD tool a team happens to use.

Best Practices

  • Build once, and deploy that exact same artifact through every subsequent environment — never rebuild per stage.
  • Let protection rules live on the environment configuration, keeping the workflow file itself simple and environment-agnostic.
  • Design deliberate asymmetry — environments genuinely differing in risk should have genuinely different protection rules, not identical treatment out of habit.

🎯 Key Takeaway

  • A complete deployment pipeline builds once, tests that build, and promotes the exact same artifact through increasingly protected environments.
  • Environment protection rules create real behavioral differences (automatic vs. approval-gated) without any corresponding difference in the workflow file's own YAML.
  • This pipeline is a genuine synthesis of checkout, artifacts, job dependencies, environments, and variables — concepts from across this entire course, not new mechanics.

Interview Questions

Why does this pipeline download the same build-output artifact for both deploy-test and deploy-production, rather than rebuilding for each?▾
Rebuilding separately for each stage risks producing a subtly different result than what was actually tested, weakening the pipeline's core guarantee that what gets tested is genuinely what gets deployed. Reusing the exact same artifact throughout ensures deployment is of the precise thing that was built once and verified, not a fresh rebuild that merely resembles it.
Why does deploy-production pause for approval while deploy-test runs automatically, even though both jobs have nearly identical YAML?▾
The behavioral difference comes entirely from each job's connected environment configuration, not from anything written in the workflow file itself. The production environment has required reviewers configured as a protection rule, while the test environment doesn't — this asymmetry lives in the environment settings, invisible to someone only reading the workflow's YAML.
Why is "build once, deploy that same artifact everywhere" considered a widely-recognized CI/CD best practice, not just a GitHub Actions-specific convention?▾
This principle addresses a genuine, universal concern in any CI/CD system — ensuring the exact thing that was tested is the exact thing that gets deployed, rather than a separately-built artifact that could subtly differ due to dependency resolution, timing, or environment differences during a second build. This concern and its solution apply regardless of which specific CI/CD tool a team happens to use.
What role does needs: play in connecting the four jobs in this pipeline together?▾
needs: establishes the genuine, real ordering this pipeline requires — test must wait for build, deploy-test must wait for test, and deploy-production must wait for deploy-test. Without these explicit dependencies, the jobs would run in parallel by default, breaking the pipeline's actual intended sequence of build, verify, deploy progressively through increasingly protected environments.
Why does ${{ vars.API_BASE_URL }} correctly resolve to a different actual value in deploy-test versus deploy-production without any conditional logic in the workflow?▾
Each job is connected to a different environment via its own environment: key, and since API_BASE_URL is configured as an environment-scoped variable (covered earlier in this chapter) with a different value set for each environment, the same expression automatically resolves differently depending on which environment the job is actually connected to — no branching logic needed in the workflow itself.
