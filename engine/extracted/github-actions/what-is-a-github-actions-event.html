What is a GitHub Actions Event?

Prerequisites: Events & Workflow Triggers overview

What is this?

An event is something that happens in a repository — a push, someone opening a pull request, a scheduled time being reached — that a workflow can be configured to respond to. Chapter 1 already used one event (push) without dwelling on the concept; this page makes it explicit before the rest of this chapter covers each event type in depth.

Why do we need it?

Without events, a workflow would need to be triggered manually every single time, defeating the entire point of automation. Event-driven design means the workflow itself declares what it cares about, and GitHub handles noticing when that thing actually happens — you never have to remember to "go run the tests," because the push itself is what starts them.

Real-World Analogy

Think of a smoke detector — it doesn't need someone to periodically check "is there smoke right now?" It's wired to react automatically the moment smoke actually appears. An event-driven workflow works the same way: it sits quietly until its specific event happens, then reacts immediately, without anyone needing to remember to check.

Where Events Fit in a Workflow

on: push   # this "on:" key is where an event is declared

The on: key is always where a workflow declares which event (or events) it's listening for. Everything else in this chapter is really about the different ways this one key can be configured.

Detailed Example — The Same Event, Different Reactions

Event: a push happens on the repository

Workflow A's reaction: run the full test suite
Workflow B's reaction: send a notification to a chat channel
Workflow C's reaction: nothing at all — it's listening for a different event

The same real-world event can trigger zero, one, or many different workflows, each reacting however its own YAML file defines. A repository isn't limited to one workflow per event type — multiple workflow files can all listen for the same push event and do genuinely different things.

🧠 Think About It

If ShopEasy's repository has three separate workflow files, all with on: push, what happens when someone pushes code? All three trigger, independently and typically in parallel — GitHub doesn't merge them into one, and none of them know about the others by default. This matters once a repository grows to have several genuinely independent automated processes.

⚠️ Common Mistake

Thinking of an event as something you have to actively "check for" inside your workflow's logic. You don't — the event is declared once, in on:, and GitHub Actions itself handles noticing when it occurs. Nothing inside your steps needs to ask "did a push happen?" — by the time any step runs, that's already been established.

💡 Quick Tip

The Actions tab shows exactly which event triggered each specific run — useful for confirming a workflow actually fired for the reason you expected, especially once a workflow responds to more than one event type.

Best Practices

  • Think in terms of "what real-world event should trigger this automation" before writing any YAML — the event choice shapes everything downstream.
  • Remember that multiple workflow files can all react to the same event independently — a repository isn't limited to one response per event type.
  • Use the Actions tab to confirm which event actually triggered a specific run when debugging unexpected behavior.

🎯 Key Takeaway

  • An event is something that happens in a repository that a workflow can react to automatically.
  • The on: key is where a workflow declares which event(s) it's listening for.
  • Multiple independent workflows can all react to the same event, each with its own separate logic.

Interview Questions

Why is event-driven automation preferable to manually triggering every workflow run?▾
Manual triggering depends on someone remembering to do it every single time, which reintroduces exactly the kind of human-dependent unreliability CI/CD exists to eliminate. Event-driven automation means the workflow reacts automatically the moment its declared event actually happens, with no one needing to remember anything.
If a repository has three separate workflow files that all listen for the push event, what happens on a single push?▾
All three workflows trigger independently — GitHub doesn't merge them into one combined workflow, and by default none of them are aware of the others running. Each executes its own separate logic in response to the same underlying event, which means a repository can have several genuinely independent automated processes all reacting to the same kind of event.
Does a workflow's steps need to explicitly check whether its triggering event actually occurred?▾
No — by the time any step in a workflow actually runs, GitHub has already confirmed the declared event occurred; that's the entire reason the workflow started executing at all. The steps themselves don't need any logic to verify this, since the on: declaration and GitHub's own event detection already handled it before the workflow even began.
Where would you look to confirm exactly which event triggered a specific workflow run?▾
The repository's Actions tab shows this directly for every recorded run, which becomes especially useful once a single workflow is configured to respond to more than one type of event, and you need to confirm which specific one actually caused a particular run to start.
What's the practical significance of the on: key in a workflow file?▾
The on: key is specifically where a workflow declares which event or events it's listening for — it's the single point in the YAML file that determines when this workflow will actually be triggered at all. Every other part of the workflow (jobs, steps) only ever runs as a consequence of this declaration being satisfied.
