Running Shell Commands: The run: Key

Prerequisites: GitHub-Hosted Runners & runs-on

What is this?

run: executes a plain shell command as a step — used constantly throughout every example so far, without ever being explained in its own right. This page covers what it actually supports beyond a single one-line command.

A Single Command

- run: npm test

The simplest form — one command, one line, executed by the runner's default shell.

Multi-Line Scripts

- run: |
    echo "Starting build"
    npm ci
    npm run build
    echo "Build complete"

The pipe character (|) tells YAML this is a multi-line string, preserving line breaks — each line runs as a separate shell command, in order, within the same step. This is genuinely different from writing four separate steps: it's one step containing a small script, sharing the same shell session throughout.

Setting a Working Directory

- run: npm test
  working-directory: ./backend

By default, commands run from the repository's root. working-directory changes that for a specific step — useful for a monorepo with multiple sub-projects, where a command needs to run from inside one specific folder.

Choosing a Specific Shell

- run: echo "Hello from PowerShell"
  shell: pwsh

The default shell depends on the runner's operating system (bash on Linux and macOS, PowerShell on Windows) — shell: lets you override this explicitly for a specific step, useful when a command genuinely needs a particular shell's specific syntax regardless of the underlying OS.

Detailed Example — A Real Multi-Line Build Script

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: |
          echo "Installing dependencies..."
          npm ci
          echo "Running build..."
          npm run build
          echo "Build finished — checking output size"
          du -sh dist/

Everything from "Installing dependencies" through the final du -sh command runs as one cohesive step, sharing the same shell session — variables set earlier in the script remain available to later lines, exactly like running these same commands manually, one after another, in a real terminal.

🧠 Think About It

Why might you choose one multi-line run: step over four separate single-command steps doing the same work? A single multi-line step shares one shell session — a variable set on line 2 is genuinely available on line 4. Four separate steps don't share shell state that way by default; each step starts its own fresh shell invocation. The choice matters specifically when later commands depend on something set up by earlier ones within the same shell context.

⚠️ Common Mistake

Assuming a shell variable set in one run: step is automatically available in a later, separate step. It isn't — each step is its own shell invocation, and shell-level variables don't persist across step boundaries this way (passing actual data between steps deliberately, via GitHub's own step-output mechanism, is covered in a later chapter).

💡 Quick Tip

The pipe character (|) preserves line breaks exactly; a related character, the greater-than sign (>), folds a multi-line YAML string into one line with spaces instead — genuinely different behavior, worth knowing both exist even though | is far more commonly what you actually want for a multi-line script.

Best Practices

  • Use a single multi-line run: step when later commands genuinely depend on something set up earlier in the same shell session.
  • Use working-directory explicitly for monorepo-style projects rather than cd-ing manually inside the script itself.
  • Only override shell: when a command genuinely requires a specific shell's syntax — otherwise, trust the sensible per-OS default.

🎯 Key Takeaway

  • run: executes plain shell commands — a single line, or a multi-line script using the | character.
  • Commands within one multi-line run: step share the same shell session; separate steps do not share shell state.
  • working-directory and shell let you override the default folder and shell for a specific step.

🛠️ Try It Yourself

Write a single multi-line run: step that sets a shell variable on its first line and then uses that variable's value on a later line within the same step — confirming for yourself that this genuinely works within one step, unlike across separate steps.

Interview Questions

What's the practical difference between one multi-line run: step and four separate single-line run: steps doing the same commands?▾
A single multi-line step shares one continuous shell session across all its lines — a variable set early in the script remains available to later lines within that same step. Four separate steps each start their own fresh shell invocation, so shell-level state set in one step doesn't automatically carry over to the next, even though they run in the same job.
Why does the pipe character (|) matter when writing a multi-line command in YAML?▾
The pipe character tells YAML's parser that the following indented block is a multi-line string with its line breaks preserved exactly as written. Without it, YAML would need a different (and less convenient) way to represent multiple lines, and a related character, the greater-than sign, would instead fold the lines together into one continuous string, which is a genuinely different, usually less useful behavior for a script.
What does the working-directory setting on a step actually change?▾
It changes which folder that specific step's commands execute from, overriding the default of the repository's root. This is particularly useful in a monorepo containing multiple distinct sub-projects, where a build or test command genuinely needs to run from inside one specific project's folder rather than the overall repository root.
Why might a step need to explicitly set shell: pwsh even on a Windows runner, where PowerShell is already the default?▾
While pwsh is indeed the default shell on Windows runners, explicitly setting shell: can still be useful for clarity, or in situations where a workflow needs consistent, explicit behavior regardless of what the underlying runner's default happens to be — making the workflow's actual behavior clear from reading the YAML itself, rather than depending on an implicit, OS-dependent default.
Why doesn't a shell variable set in one step automatically become available in a later, separate step?▾
Each step is its own independent shell invocation — shell-level variables exist only within the process that step's shell runs in, and that process ends when the step completes. Genuinely passing a value from one step to another requires using GitHub Actions' own dedicated step-output mechanism, which is a deliberate, separate feature from ordinary shell variables, covered in a later chapter on passing information between steps.
