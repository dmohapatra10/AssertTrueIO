GitHub-Hosted Runners & runs-on

Prerequisites: Jobs & Steps: The Execution Model in Depth

What is this?

A GitHub-hosted runner is a virtual machine that GitHub provisions, runs your job's steps on, and then discards — entirely managed for you, with no infrastructure of your own to maintain. This page covers the actual options and what runs-on is really selecting.

The Three Operating System Families

runs-on: ubuntu-latest   # Linux — by far the most common choice
runs-on: windows-latest  # Windows
runs-on: macos-latest    # macOS

Each corresponds to a genuinely different operating system, with different pre-installed tools and different typical use cases — ubuntu-latest is the default choice for most web and backend projects; windows-latest matters for Windows-specific software; macos-latest matters specifically for building iOS or macOS applications, which genuinely require Apple's own toolchain.

What's Actually Pre-Installed

ubuntu-latest typically includes (among much more):
- Git
- Node.js (multiple versions)
- Python
- Java
- Docker
- Common build tools

GitHub-hosted runners come with a genuinely large set of pre-installed software — but it's still finite. A project needing something not pre-installed needs an explicit setup step (covered in the next chapter) to install it.

The "latest" Tag vs. Pinning a Specific Version

runs-on: ubuntu-latest    # always the current latest Ubuntu image
runs-on: ubuntu-22.04     # a specific, pinned version

ubuntu-latest automatically moves forward as GitHub updates their images over time — convenient, but it means the exact environment can subtly change without you changing anything in your own workflow. Pinning a specific version trades that convenience for stability — genuinely useful once a project has a real dependency on specific tool versions being present.

The Runner Lifecycle

1. Your job is scheduled to run.
2. GitHub provisions a fresh virtual machine matching your runs-on choice.
3. Your job's steps execute on that machine, in order.
4. The machine is completely destroyed once the job finishes.

This "fresh every time" lifecycle is exactly why job isolation (covered on the previous page) works the way it does — there's no persistent machine sitting around between runs; every single run starts from a clean, brand-new environment.

Detailed Example — Choosing runs-on for a Real Decision

ShopEasy is a Node.js web application, with no Windows- or macOS-specific
requirements anywhere in the stack.

Correct choice: runs-on: ubuntu-latest

Why: Ubuntu runners are typically the fastest to provision, and Node.js
     is well-supported out of the box — there's no genuine reason to pay
     the (real) performance cost of a Windows or macOS runner for a
     project with no actual dependency on either.

🧠 Think About It

Why might a team deliberately choose to pin a specific Ubuntu version instead of using ubuntu-latest, even though it means missing out on automatic updates? If a project depends on a very specific tool version that happens to be present on one particular image but might change on a future "latest" image, pinning trades away convenience for the certainty that the environment won't silently shift under them.

⚠️ Common Mistake

Choosing windows-latest or macos-latest without a genuine, specific need for that operating system. These runners are typically slower to provision and consume CI minutes at a different (often higher) rate than Ubuntu — reaching for them without an actual requirement adds real cost and time for no corresponding benefit.

💡 Quick Tip

GitHub's own documentation maintains a complete, current, and detailed list of exactly what software and versions come pre-installed on each runner image — worth checking directly rather than assuming, especially for a specific tool version your project depends on.

Best Practices

  • Default to ubuntu-latest unless your project has a genuine, specific reason to need Windows or macOS.
  • Pin a specific runner version deliberately when a project depends on exact tool versions being consistently present — don't pin by default "just in case."
  • Check GitHub's documentation for a runner image's actual pre-installed software rather than assuming.

🎯 Key Takeaway

  • runs-on selects which operating system (and specific image) a job's steps execute on.
  • Each runner is a fresh virtual machine, provisioned for that job and destroyed afterward — nothing persists between runs.
  • -latest tags move forward automatically; pinning a specific version trades that convenience for environment stability.

Interview Questions

What does runs-on actually determine about a job's execution?▾
runs-on selects which operating system, and specifically which runner image, GitHub provisions to execute that job's steps — Ubuntu, Windows, or macOS, with a specific version or the automatically-updating "latest" tag. This choice determines what's pre-installed and available to the job's steps without any additional setup.
Why might a team choose to pin a specific runner version rather than using the "latest" tag?▾
The "latest" tag automatically moves forward as GitHub updates their runner images, which means the exact environment a workflow runs in can subtly change over time without any change to the workflow file itself. Pinning a specific version trades away that automatic update convenience for a guarantee that the environment stays consistent, which matters for a project with a genuine dependency on specific tool versions being present.
Why would a project typically avoid using windows-latest or macos-latest without a specific need for that operating system?▾
Windows and macOS runners are generally slower to provision and often consume CI minutes at a different, typically higher rate compared to Ubuntu runners. Choosing one without an actual platform-specific requirement (like building an iOS app, which genuinely needs macOS) adds real, unnecessary cost and time to a pipeline for no corresponding benefit.
What happens to a GitHub-hosted runner's virtual machine once a job finishes?▾
The virtual machine is completely destroyed after the job completes — it isn't reused, paused, or kept around for a future run. This "provision fresh, then destroy" lifecycle is exactly why each job starts from a genuinely clean environment, with no leftover state from any previous run.
If a project needs a tool that isn't pre-installed on ubuntu-latest, what needs to happen?▾
The workflow needs an explicit step to install that tool before it's actually needed — GitHub-hosted runners come with a large but genuinely finite set of pre-installed software, and anything beyond that set has to be set up deliberately as part of the job's own steps, which is exactly what the next chapter's coverage of setting up languages and installing dependencies addresses.
