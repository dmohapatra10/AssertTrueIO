Downloading Artifacts & Passing Data Between Jobs

Prerequisites: What is an Artifact? & Uploading Artifacts

What is this?

Uploading an artifact is only half the story — this page covers actually retrieving it in a different job, which is exactly how the "job isolation" limitation from Chapter 4 gets deliberately bridged when genuinely needed.

Downloading in a Different Job

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: build-output
          path: dist/

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: build-output
          path: dist/
      - run: echo "Now dist/ exists in THIS job too, thanks to the artifact"

The name in the download step must exactly match the name used when uploading — this is how GitHub knows which specific artifact to retrieve.

Why needs: Is Required Here

jobs:
  deploy:
    needs: build   # ← without this, deploy might start BEFORE build even finishes
    ...

Without an explicit needs: dependency (covered fully in Chapter 9), jobs run in parallel by default — deploy could start trying to download an artifact that build hasn't uploaded yet, because it hasn't even finished running. needs: ensures build genuinely completes (and uploads its artifact) before deploy even starts.

Detailed Example — The Complete ShopEasy Scenario, Now Finished

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with: { name: shopeasy-build, path: dist/ }

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with: { name: shopeasy-build, path: dist/ }
      - run: echo "Deploying the build from dist/"

This is genuinely the complete picture — build produces something, uploads it deliberately, deploy waits for that to finish (via needs:), then downloads exactly what it needs. No shared filesystem, no implicit magic — just an explicit, deliberate hand-off.

🧠 Think About It

Why does this pattern — upload in one job, needs:, download in another — represent a deliberate design choice rather than an inconvenient workaround? Requiring an explicit hand-off means exactly what's shared between jobs is visible directly in the workflow file itself — anyone reading it can see precisely what data flows from build to deploy, rather than having to guess at implicit, invisible shared state.

⚠️ Common Mistake

Adding a download step without the corresponding needs: dependency, then encountering an intermittent failure — sometimes it works (if build happens to finish first anyway), sometimes it doesn't. needs: isn't optional here; without it, correct behavior is a matter of timing luck, not a genuine guarantee.

💡 Quick Tip

If a workflow needs to download every artifact from previous jobs rather than one specific one, omitting the name parameter entirely downloads all of them, each into its own subfolder named after the artifact — useful for a final "publish everything" job that doesn't need to know each artifact's name individually in advance.

Best Practices

  • Always pair a cross-job artifact download with an explicit needs: dependency on the uploading job.
  • Use matching, consistent artifact names between the upload and download steps — a typo here fails silently in confusing ways.
  • Prefer this explicit upload/download pattern over trying to work around job isolation in less obvious ways.

🎯 Key Takeaway

  • actions/download-artifact retrieves an artifact by the exact name it was uploaded under, in a different job.
  • A job downloading another job's artifact must declare a needs: dependency on it — otherwise, correct timing isn't guaranteed.
  • This explicit upload-then-download pattern makes cross-job data flow visible directly in the workflow file, rather than relying on invisible shared state.

Interview Questions

Why does a job downloading another job's artifact specifically need a needs: dependency to work correctly?▾
Jobs run in parallel by default — without an explicit needs: dependency, the downloading job could start executing before the uploading job has even finished (and therefore before the artifact even exists yet). needs: ensures the uploading job genuinely completes first, guaranteeing the artifact is actually available by the time the download step runs.
What happens if the name used in a download-artifact step doesn't exactly match the name used when uploading?▾
The download would fail to find the intended artifact, since GitHub matches artifacts by their exact name. A typo or inconsistency between the upload and download names is a common, easy-to-miss mistake that produces a failure seemingly unrelated to the actual content being transferred.
Why is the explicit upload-then-download artifact pattern considered a deliberate design choice rather than an inconvenient extra step?▾
Requiring an explicit hand-off means exactly what data flows between jobs is directly visible in the workflow file itself — anyone reading it can see precisely what's shared and how, rather than having to reason about invisible, implicit shared state between jobs. This explicitness makes a workflow's actual data dependencies easier to understand and maintain.
What happens if you omit the name parameter when downloading an artifact?▾
Omitting name downloads every artifact produced by the jobs this one depends on, each placed into its own subfolder named after that specific artifact. This is useful for a job that needs to gather multiple different artifacts without needing to know each one's specific name individually in advance.
Why might relying on job timing alone, without needs:, produce an intermittent rather than a consistent failure?▾
Without needs:, whether the download succeeds depends purely on whichever job happens to finish first when run in parallel — sometimes the uploading job might coincidentally finish before the downloading job tries to retrieve the artifact, and sometimes it won't. This kind of timing-dependent behavior is exactly why needs: is necessary for a genuine guarantee rather than an unreliable coincidence.
