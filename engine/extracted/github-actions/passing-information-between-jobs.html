Passing Information Between Jobs

Prerequisites: Passing Information Between Steps

What is this?

The previous page covered passing a value between steps within one job. This page covers the genuinely different mechanism for passing a small value between two entirely separate jobs — distinct from artifacts (Chapter 8), which are for files, not simple values.

Why do we need it?

Job isolation (Chapter 4) means nothing automatically carries from one job to another. A file needs an artifact. A small computed value — a version number, a decision flag — has its own, lighter mechanism: job-level outputs.

Defining a Job Output

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      version: ${{ steps.get_version.outputs.version }}
    steps:
      - id: get_version
        run: echo "version=1.2.3" >> $GITHUB_OUTPUT

A job's outputs: block maps a job-level output name to a step-level output from within that same job — this is genuinely the bridge between the previous page's mechanism and this one: a job output is built from a step output.

Reading a Job Output From a Different Job

jobs:
  build:
    outputs:
      version: ${{ steps.get_version.outputs.version }}
    steps: [...]

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying version ${{ needs.build.outputs.version }}"

needs.build.outputs.version retrieves the value — note that needs: is required here too, for the same reason it's required for artifact downloads: without it, there's no guarantee build has even finished (and produced its output) before deploy tries to read it.

Detailed Example — A Genuinely Useful Real Scenario

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      version: ${{ steps.get_version.outputs.version }}
      should_deploy: ${{ steps.check.outputs.should_deploy }}
    steps:
      - id: get_version
        run: echo "version=$(node -p "require('./package.json').version")" >> $GITHUB_OUTPUT
      - id: check
        run: echo "should_deploy=${{ github.ref == 'refs/heads/main' }}" >> $GITHUB_OUTPUT

  deploy:
    needs: build
    if: needs.build.outputs.should_deploy == 'true'
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying version ${{ needs.build.outputs.version }}"

Here, build computes both a version number and a decision (whether this run is actually on main) once, and deploy reads both — the decision even feeds directly into deploy's own if: condition. This is a genuinely different, complementary tool to what Chapter 6 covered — that chapter's conditional used github.ref directly; this shows a job's own computed decision flowing into a later job's condition instead.

🧠 Think About It

Why use a job output for something like should_deploy rather than just repeating the same github.ref == 'refs/heads/main' check directly in the deploy job's own if:? If the actual decision logic is more complex than a single simple comparison — checking several conditions together, or something computed rather than a direct context lookup — computing it once in build and passing the result keeps that logic in exactly one place, rather than duplicating potentially complex logic across every job that needs to make the same decision.

⚠️ Common Mistake

Trying to use a job output for something that's genuinely a file rather than a small value — job outputs have real size limitations and are meant for simple strings, not file content. A build's actual output files still need an artifact (Chapter 8); a job output is for something like that build's version number or a computed decision, not the files themselves.

💡 Quick Tip

Like step outputs, job outputs are always strings — a boolean-looking value like true passed this way is genuinely the string "true", which is why the example above compares it with == 'true' rather than treating it as a native boolean.

Best Practices

  • Use job outputs for small, simple values — a version, a flag, a computed decision — never for file content.
  • Always pair a job output read with an explicit needs: dependency on the producing job.
  • Compute a decision once in a job output when the same logic would otherwise need to be duplicated across multiple dependent jobs.

🎯 Key Takeaway

  • A job's outputs: block exposes a value (typically built from one of its own step outputs) to jobs that depend on it.
  • needs.<job>.outputs.<name> retrieves it — requiring the same needs: dependency as artifact downloads, for the same underlying reason.
  • Job outputs are for small values, not files — artifacts remain the right tool for actual file content.

🏆 Challenge

Extend the example above with a third job, notify, that needs both build and deploy, and prints a message including the version number from build's output — regardless of whether deploy actually ran (since should_deploy might have been false).

Interview Questions

Why does a job's outputs: block typically reference a step output rather than defining a value directly?▾
A job itself doesn't run commands directly — its steps do. A job output is genuinely built from something one of its own steps already computed and exposed via $GITHUB_OUTPUT, with the job's outputs: block simply exposing that same value one level up, making it accessible to other jobs that depend on this one.
Why does reading needs.build.outputs.version in a different job still require an explicit needs: dependency?▾
Without needs:, jobs run in parallel by default, meaning the job trying to read the output could execute before the producing job has even finished computing and exposing that value. needs: guarantees the producing job has genuinely completed — and its outputs are actually available — before the dependent job starts.
Why is a job output the wrong tool for passing an actual build artifact like a compiled binary between jobs?▾
Job outputs are designed for small, simple string values, with real practical size limitations, not for transferring file content. An actual build artifact — a binary, a bundled application, a folder of files — needs the artifact upload/download mechanism from an earlier chapter, which is specifically built to handle real file content, unlike job outputs.
Why does the example workflow compare needs.build.outputs.should_deploy to the string 'true' rather than treating it as a native boolean?▾
Like step outputs, job outputs are always strings regardless of what the original value looked like — a boolean-looking value written as true is transmitted and read back as the literal string "true", not a native boolean type. Comparing it explicitly against the string 'true' correctly matches how the value is actually represented once passed through this mechanism.
Why might computing a deployment decision once in a build job's output be preferable to repeating the same condition logic in every job that needs it?▾
If the actual decision involves more than a single simple comparison, duplicating that logic across multiple jobs risks it drifting out of sync if one copy is updated but another is missed. Computing the decision once and passing the result via a job output keeps that logic in exactly one place, which every dependent job can then simply read rather than needing to reimplement independently.
