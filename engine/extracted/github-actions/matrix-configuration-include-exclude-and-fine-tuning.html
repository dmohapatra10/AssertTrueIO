Matrix Configuration: include, exclude & Fine-Tuning

Prerequisites: What is a Matrix? Testing Multiple Versions & OSes

What is this?

A plain matrix generates every combination of every dimension — sometimes that's exactly right, and sometimes you genuinely need to exclude a specific, known-incompatible combination, or add one extra combination that doesn't fit the regular pattern. include and exclude handle exactly this.

exclude — Removing Specific Combinations

strategy:
  matrix:
    node-version: [18, 20, 22]
    os: [ubuntu-latest, windows-latest]
    exclude:
      - node-version: 18
        os: windows-latest

This still generates the full 3×2 combinations, then removes exactly the one specified — Node 18 on Windows never actually runs, while the other five combinations proceed normally. Genuinely useful when one specific combination is known to be unsupported or irrelevant.

include — Adding Extra, Non-Standard Combinations

strategy:
  matrix:
    node-version: [18, 20, 22]
    os: [ubuntu-latest]
    include:
      - node-version: 20
        os: macos-latest
        experimental: true

This adds one extra combination — Node 20 on macOS — that doesn't fit the regular pattern of "every Node version × every OS," along with an extra experimental: true flag only present on this specific combination.

fail-fast — Stopping the Whole Matrix on One Failure

strategy:
  fail-fast: true    # DEFAULT — one failure cancels all other matrix jobs
  matrix:
    node-version: [18, 20, 22]

By default, if any single matrix combination fails, GitHub cancels the rest of the still-running combinations immediately, rather than letting them all finish. This saves CI time when a failure is likely to affect every combination anyway, but it also means you might not see results from combinations that were still genuinely running when the cancellation happened.

Setting fail-fast: false

strategy:
  fail-fast: false   # let every combination run to completion, regardless
  matrix:
    node-version: [18, 20, 22]

Genuinely useful when you want complete information from every combination — for instance, discovering that a bug affects Node 18 specifically but not 20 or 22, information you'd lose if the whole matrix stopped early after the first failure.

max-parallel — Limiting Concurrent Matrix Jobs

strategy:
  max-parallel: 2   # only 2 matrix combinations run at once, not all simultaneously
  matrix:
    node-version: [18, 20, 22, 23]

By default, every matrix combination runs simultaneously (subject to your account's overall concurrency limits). max-parallel deliberately throttles this — useful when a matrix's combined resource usage (hitting a shared external service, for instance) could genuinely be a problem if every combination ran at the exact same moment.

Detailed Example — All Four, Combined for a Real Scenario

strategy:
  fail-fast: false        # want to see EVERY combination's actual result
  max-parallel: 3          # limit concurrent runs against a shared test database
  matrix:
    node-version: [18, 20, 22]
    os: [ubuntu-latest, windows-latest]
    exclude:
      - node-version: 18
        os: windows-latest   # known unsupported combination
    include:
      - node-version: 22
        os: macos-latest
        experimental: true    # extra, non-standard combination to also check

This produces a genuinely deliberate, fine-tuned set of combinations — not just "every possible pairing," but exactly the set that reflects what's actually meaningful to test, with controlled concurrency and full visibility into every result.

🧠 Think About It

Why might fail-fast: false be worth its extra CI time cost for a matrix specifically testing compatibility across versions? If the whole point of the matrix is discovering exactly which versions have a problem, stopping early after the first failure defeats that purpose — you'd know something failed, but not whether it's isolated to one version or affects all of them, which is precisely the information a compatibility matrix exists to reveal.

⚠️ Common Mistake

Leaving fail-fast at its default (true) for a matrix genuinely meant to reveal version-specific or OS-specific behavior, then being confused when several combinations show as "cancelled" rather than actually completing — losing exactly the granular information the matrix was built to provide.

💡 Quick Tip

exclude only removes combinations that would otherwise be generated by the matrix's own dimensions — it can't add something new. Anything genuinely outside the regular pattern needs include instead.

Best Practices

  • Use exclude for known-incompatible or irrelevant combinations, keeping the matrix's core dimensions clean.
  • Use include sparingly, for genuinely one-off combinations that don't fit the regular pattern.
  • Set fail-fast: false when the actual goal is discovering which specific combinations have a problem, not just whether any do.

🎯 Key Takeaway

  • exclude removes specific combinations the matrix would otherwise generate; include adds extra, non-standard ones.
  • fail-fast: true (the default) cancels remaining matrix jobs after any single failure; false lets every combination finish.
  • max-parallel deliberately limits how many matrix combinations run simultaneously.

🏆 Challenge

For a matrix testing Python 3.10, 3.11, and 3.12 on Ubuntu and Windows, write the configuration to exclude Python 3.10 on Windows (a known unsupported combination) and add an extra Python 3.13 pre-release combination on Ubuntu only, using include.

Interview Questions

What's the practical difference between exclude and include in a matrix configuration?▾
exclude removes a specific combination that the matrix's own dimensions would otherwise generate — it can only subtract from what already exists. include adds an entirely new, extra combination that doesn't need to fit the regular pattern of the matrix's dimensions at all, potentially introducing values or flags not present anywhere else in the matrix.
Why might fail-fast: false be the right choice for a matrix specifically testing version compatibility?▾
The actual purpose of a compatibility matrix is discovering which specific combinations have a problem, not just whether any combination fails at all. With the default fail-fast: true, a single early failure cancels the remaining combinations, potentially hiding whether the problem is isolated to one version or affects several — exactly the granular information fail-fast: false preserves by letting every combination run to completion.
What does max-parallel actually control, and why might a team deliberately set it lower than the number of matrix combinations?▾
max-parallel limits how many matrix combinations run simultaneously, rather than letting every combination execute at the exact same time by default. A team might set it lower when the combined resource usage of all combinations running at once could genuinely strain a shared resource, like an external test database or a rate-limited third-party service.
Can exclude be used to add a matrix combination that wouldn't otherwise exist from the matrix's own dimensions?▾
No — exclude can only remove combinations that the matrix's dimensions would already generate; it has no capability to introduce something new. Adding a genuinely extra, non-standard combination requires include instead, which is specifically designed to add combinations outside the regular pattern.
What happens to still-running matrix jobs when one combination fails, under the default fail-fast setting?▾
Under the default fail-fast: true, GitHub Actions cancels the remaining, still-running matrix combinations as soon as any single one fails, rather than letting them continue to completion. This saves CI time in situations where a failure likely affects every combination, but it also means results from the cancelled combinations are never actually obtained for that run.
