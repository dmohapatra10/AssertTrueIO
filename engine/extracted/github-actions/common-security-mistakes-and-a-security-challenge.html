Common Security Mistakes & a Security Challenge

Prerequisites: Workflow Permissions & Least Privilege

What is this?

Five specific, genuinely common security mistakes — each one already touched on somewhere in this chapter, gathered here as one deliberate checklist — followed by a real, complete workflow with several of them present at once, for you to actually find and fix.

❌ Mistake 1 — Hardcoded Credentials

env:
  API_KEY: sk_live_abc123def456

Visible to anyone with repository access, permanently, in the commit history — covered fully earlier in this chapter. Fix: ${{ secrets.API_KEY }}, never a literal value.

❌ Mistake 2 — Printing Secrets to Logs

- run: echo "The API key is $API_KEY"

Even though GitHub automatically masks known secret values in log output, deliberately printing a secret for debugging is a genuinely bad habit — a masked value can sometimes still leak through indirect means (a modified or partial value, an unexpected code path), and the instinct itself is worth avoiding entirely rather than relying on masking as a safety net.

❌ Mistake 3 — Excessive Permissions

permissions: write-all

Covered in full depth on the previous page — grants everything, when a specific task almost never genuinely needs everything.

❌ Mistake 4 — Trusting Untrusted Input

- run: echo "${{ github.event.issue.title }}"

This looks harmless, but an issue title is text any user can set — including a malicious user, on a public repository. If that string is interpolated directly into a shell command, a carefully crafted issue title can potentially inject and execute arbitrary commands in that shell, not just print harmless text. User-controlled input flowing directly into a shell command is a genuine, real injection risk.

❌ Mistake 5 — Unvetted Third-Party Actions

- uses: some-random-account/do-something@main

A third-party action runs with the same access your workflow has — an action from an unknown, unmaintained, or untrustworthy source is running real code with real permissions inside your pipeline. Combined with pinning to @main (covered in Chapter 4) rather than a fixed version, this is a genuine, real supply-chain risk.

🔒 Security Challenge — Secure This Workflow

name: Deploy
on: push
permissions: write-all
jobs:
  deploy:
    runs-on: ubuntu-latest
    env:
      DEPLOY_KEY: prod-key-9f8e7d6c5b4a
    steps:
      - uses: actions/checkout@v4
      - uses: some-account/deploy-action@main
        with:
          key: ${{ env.DEPLOY_KEY }}
      - run: echo "Deployed with key $DEPLOY_KEY"
      - run: echo "Triggered by: ${{ github.event.head_commit.message }}"

This single workflow contains every mistake from this page. Before reading further, try to identify all five yourself.

The Fixed Version

name: Deploy
on:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: some-account/deploy-action@v2.1.0   # pinned to a real, reviewed version
        with:
          key: ${{ secrets.DEPLOY_KEY }}            # a real secret, not hardcoded
      - run: echo "Deployment step completed"        # no secret printed

Fixed: the credential is now a genuine secret rather than hardcoded; permissions: write-all is replaced with the actual minimum needed; the third-party action is pinned to a specific, presumably-reviewed version instead of a mutable branch; the secret is never echoed to the log; and the commit message (untrusted user input) is no longer interpolated directly into a shell command at all.

🧠 Think About It

Why does pinning a third-party action to a specific version (rather than @main) address a genuinely different risk than reviewing the action's code once before first using it? Even a thoroughly reviewed action, if pinned to a mutable branch, could have its code changed by its maintainer at any point after your review — pinning to an immutable version tag ensures the exact code you reviewed is what actually keeps running, rather than trusting that nothing changes later without your knowledge.

⚠️ Common Mistake

Treating security review as a one-time task rather than an ongoing practice. A workflow that was genuinely secure when written can become vulnerable later — a pinned action's maintainer account could be compromised, a dependency could introduce a vulnerability, an unrelated permissions change elsewhere could widen access unexpectedly. Periodic review matters, not just a single pass.

💡 Quick Tip

GitHub's own security features — Dependabot alerts, secret scanning, and the security tab in a repository's settings — can automatically flag some of these issues (like an accidentally committed credential) even before a human reviewer catches them. Worth having enabled as a genuine, additional safety net, not a replacement for careful workflow design.

Best Practices

  • Review every workflow against this exact checklist of five mistakes periodically, not just when first written.
  • Treat any value derived from user-controllable input (issue titles, PR descriptions, commit messages) as untrusted before it touches a shell command.
  • Pin every third-party action to a specific, immutable version — never a branch name.

🎯 Key Takeaway

  • Hardcoded credentials, printed secrets, excessive permissions, untrusted input, and unvetted actions are the five most common, genuinely serious GitHub Actions security mistakes.
  • User-controlled text (issue titles, commit messages) flowing directly into a shell command is a real injection risk, not a theoretical one.
  • A third-party action runs with your workflow's own access — pinning to a reviewed, immutable version matters as much as reviewing the code itself.

Interview Questions

Why is directly interpolating something like an issue title into a shell command a genuine security risk, not just bad style?▾
An issue title is text any user can set, including a malicious one, especially on a public repository. If that user-controlled text is interpolated directly into a shell command, a carefully crafted title could potentially inject and execute arbitrary commands within that shell context, not just display as harmless text — this is a real command injection vulnerability, not a theoretical concern.
Why does pinning a third-party action to a specific version matter even after reviewing that action's code once?▾
Pinning to a mutable reference like a branch name means the actual code that runs can change at any point after your review, entirely outside your control or knowledge, if the action's maintainer pushes something new. Pinning to a specific, immutable version tag ensures the exact code you reviewed is what continues running, closing the gap between "reviewed once" and "still running what was reviewed."
Why is deliberately printing a secret's value to the workflow log a bad practice, even though GitHub automatically masks known secrets?▾
Automatic masking is a safety net, not a guarantee — a partial, modified, or unexpectedly formatted version of a secret value can sometimes bypass masking, and relying on masking as the primary safeguard rather than simply never printing the value in the first place is a genuinely riskier habit. Avoiding the practice entirely removes the dependency on masking working correctly in every possible situation.
Why does permissions: write-all represent a real security risk even for a workflow that currently behaves correctly?▾
The risk isn't about the workflow's current, intended behavior — it's about what becomes possible if that workflow, or any dependency or action it uses, is ever compromised. write-all means a compromise would grant an attacker access to everything the token could possibly touch, rather than being contained to the narrow, actual permissions the workflow's real task requires.
Why should security review of a GitHub Actions workflow be treated as an ongoing practice rather than a one-time check?▾
A workflow that was genuinely secure when first written can become vulnerable later through changes entirely outside the workflow file itself — a pinned action's maintainer account could be compromised, a dependency could introduce a new vulnerability, or a broader permissions change elsewhere could unexpectedly widen access. Treating security as a single, one-time pass misses these kinds of changes that can occur well after the original review.
