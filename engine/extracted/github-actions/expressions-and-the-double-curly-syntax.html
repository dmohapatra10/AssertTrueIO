Expressions: The ${{ }} Syntax

Prerequisites: GitHub Actions Contexts Explained

What is this?

An expression is how GitHub Actions actually evaluates a dynamic value — reading a context, comparing two things, combining conditions — wrapped in the ${{ }} syntax that's appeared throughout this course without a dedicated explanation until now.

Why the ${{ }} Wrapper Is Necessary

env:
  BRANCH: github.ref          # ❌ this is treated as the literal TEXT "github.ref"
  BRANCH: ${{ github.ref }}    # ✅ this is EVALUATED, giving the actual branch value

Without ${{ }}, GitHub Actions has no way to know you meant "evaluate this as an expression" rather than "use this exact text" — the wrapper is what signals evaluation should actually happen.

Comparison Operators

github.ref == 'refs/heads/main'    # equals
github.event_name != 'push'         # not equals

Logical Operators

github.ref == 'refs/heads/main' && needs.test.result == 'success'   # AND
github.event_name == 'push' || github.event_name == 'pull_request'   # OR
!contains(github.event.head_commit.message, '[skip ci]')              # NOT

String Concatenation

run: echo "Deploying version ${{ github.sha }} to production"

An expression can sit directly inside a larger string — GitHub Actions evaluates just the ${{ }} portion and inserts the result into the surrounding text.

Useful Built-in Functions

contains(github.event.head_commit.message, 'skip')   # substring/item check
startsWith(github.ref, 'refs/tags/')                    # prefix check
hashFiles('**/package-lock.json')                        # hash a file (seen in caching)
success()                                                  # did every previous step succeed?
failure()                                                   # did any previous step fail?
always()                                                     # run regardless of outcome

success(), failure(), and always() are genuinely important — they're specifically what lets a step run (or not run) based on the outcome of everything before it, which is exactly what's needed for things like "always upload logs, even if a test failed."

Detailed Example — Building Toward the Real Requirement

Requirement (from this chapter's hub page): "Run deployment only when
tests pass and the workflow runs on the main branch."

if: github.ref == 'refs/heads/main' && needs.test.result == 'success'

Every piece of this line is now explainable: github.ref is a context (previous page), == is a comparison operator, && is a logical AND, needs.test.result is another context, and the whole thing is an expression evaluated because it's used inside an if: — which the next page covers in full depth.

🧠 Think About It

Why might always() genuinely matter for something like uploading test logs or screenshots, specifically when a test has already failed? By default, a failed step stops the rest of the job (covered in Chapter 4) — without always(), a cleanup or reporting step would never run precisely when it's most needed: right after a failure, when those logs or screenshots are the most valuable for actually diagnosing what went wrong.

⚠️ Common Mistake

Forgetting the ${{ }} wrapper is sometimes optional and sometimes required, depending on context — inside an if: condition specifically, GitHub Actions often evaluates the expression even without the explicit wrapper, but in most other places (like env:), it's genuinely required. When uncertain, including the wrapper explicitly is always safe and never wrong.

💡 Quick Tip

GitHub Actions expressions support a decent range of built-in functions beyond the ones shown here (string manipulation, JSON parsing, and more) — worth checking the official documentation's expression reference when a specific need arises, rather than assuming a capability doesn't exist.

Best Practices

  • Always wrap an expression in ${{ }} explicitly, even in places where it might technically work without it — clarity and consistency matter more than saving a few characters.
  • Use always() deliberately for genuinely important cleanup or reporting steps that should run regardless of earlier failures.
  • Prefer built-in functions like contains() and startsWith() over trying to replicate the same logic with plain shell commands.

🎯 Key Takeaway

  • ${{ }} signals that GitHub Actions should evaluate what's inside as an expression, not treat it as literal text.
  • Expressions support comparison (==, !=), logical (&&, ||, !) operators, and useful built-in functions.
  • success(), failure(), and always() let a step's execution depend on the outcome of everything before it.

Interview Questions

Why does env: BRANCH: github.ref (without ${{ }}) not actually give you the branch value?▾
Without the ${{ }} wrapper, GitHub Actions has no signal that github.ref should be evaluated as an expression — it's simply treated as the literal string "github.ref". The ${{ }} syntax is specifically what tells GitHub Actions "evaluate what's inside this as an expression," which is required to actually retrieve the real, dynamic value from a context.
Why might a step specifically need the always() function rather than relying on default step behavior?▾
By default, a failed step stops the rest of a job's remaining steps from running at all. A step that should genuinely run regardless of outcome — like uploading diagnostic logs or screenshots, which are often most valuable exactly when something has failed — needs always() specifically to override that default fail-fast behavior and execute no matter what happened before it.
What's the difference between the logical operators && and || in a GitHub Actions expression?▾
&& represents logical AND, requiring both conditions on either side to be true for the overall expression to be true. || represents logical OR, requiring only one of the two conditions to be true. Choosing correctly between them is essential — using && where || was intended (or vice versa) produces a condition that evaluates completely differently from what was actually intended.
Why is hashFiles() specifically useful for cache key configuration, as covered in an earlier chapter?▾
hashFiles() computes a hash based on the actual content of one or more specified files — using it in a cache key means the key automatically changes whenever those files' content changes (like a dependency lock file being updated), correctly invalidating a stale cache without needing any manual intervention to detect that the underlying dependencies have changed.
Why does the expression github.ref == 'refs/heads/main' && needs.test.result == 'success' require understanding both contexts and operators to fully read?▾
The expression combines two separate context lookups (github.ref and needs.test.result) with a comparison operator applied to each, joined together by a logical AND. Fully understanding what this line actually does requires knowing what each context represents, what the comparison operator is checking, and how the logical operator combines the two resulting true/false values into one final condition.
