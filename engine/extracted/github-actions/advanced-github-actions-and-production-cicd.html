The Concepts That Show Up Once a Pipeline Is Genuinely Production-Grade

Everything so far works well on GitHub's own infrastructure, with a single job running alone. This chapter covers what changes once an organization has genuinely specific infrastructure needs, needs a real database running alongside its tests, needs to authenticate to a cloud provider securely, or needs a pipeline that behaves reliably even when things don't go perfectly. Four focused pages:

  1. Self-Hosted Runners — when GitHub's own runners genuinely aren't enough
  2. Containers & Services in GitHub Actions — running a job in a container, with a real database alongside it
  3. OIDC & Cloud Authentication — authenticating to a cloud provider without a long-lived credential at all
  4. Concurrency, Timeouts & Retries — the reliability details that separate a demo pipeline from a genuinely production-grade one

Common Mistakes to Watch For

  • Reaching for a self-hosted runner by default, without a genuine, specific need GitHub's own runners can't meet.
  • Storing a long-lived cloud credential as a secret when OIDC could authenticate securely without one existing at all.
  • Never setting a timeout, letting a genuinely stuck job run (and consume resources) far longer than any real scenario would ever need.

What You'll Be Able to Do

By the end of the four pages that follow, you should be able to decide when self-hosted runners are genuinely justified, run a job in a container with a real service like a database alongside it, authenticate to a cloud provider securely via OIDC instead of a stored credential, and configure concurrency, timeouts, and retries that make a pipeline genuinely reliable in production.
