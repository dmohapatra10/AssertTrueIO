Your First GitHub Actions Workflow

Prerequisites: GitHub Actions Mental Model

What is this?

Time to make everything from this chapter real. This page creates a genuinely working workflow, commits it, triggers it, and looks at the result — the smallest possible version, deliberately, before any real complexity.

Step 1 — Create the File

your-repository/
└── .github/
    └── workflows/
        └── hello.yml

Create exactly this folder structure in your repository, and a file named hello.yml inside it (the filename itself can be anything — it's the folder location that matters).

Step 2 — The Smallest Possible Workflow

name: Hello Automation Academy

on: push

jobs:
  greet:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Hello Automation Academy!"

Explain Every Line

  • name: Hello Automation Academy — a human-readable label for this workflow, shown in the Actions tab.
  • on: push — the event this workflow listens for; here, any push to the repository.
  • jobs: — the start of the jobs section; everything indented below defines one or more jobs.
  • greet: — the name of this specific job (you choose this name; it can be almost anything).
  • runs-on: ubuntu-latest — which runner to use; here, the latest GitHub-provided Ubuntu Linux machine.
  • steps: — the start of this job's steps; everything indented below is one step in order.
  • - run: echo "Hello Automation Academy!" — a single step, running one plain shell command.

Step 3 — Commit and Push It

$ git add .github/workflows/hello.yml
$ git commit -m "Add first GitHub Actions workflow"
$ git push

The moment this push completes, the workflow's on: push trigger fires immediately — there's no separate "activation" step required.

Step 4 — Where to See the Result

Open your repository on GitHub, click the Actions tab, and you should see "Hello Automation Academy" listed as a run, with a status (a spinning icon while running, then a green check or red X). Clicking into it, then into the "greet" job, shows the full log — including the literal text your echo command printed.

Real-World Example — What a Professional Team Would Actually Do Differently

// This tutorial's version: a single echo command
- run: echo "Hello Automation Academy!"

// A real team's first genuine workflow usually looks more like:
- uses: actions/checkout@v4
- run: npm ci
- run: npm test

A real first workflow almost always starts by checking out the actual repository code (using the actions/checkout action, since a fresh runner starts completely empty, with no code on it at all) and then does something meaningful with that code, like installing dependencies and running tests. This tutorial's simplest version deliberately skips that to isolate just the "does a workflow trigger and run at all" question first.

🔍 Debug This — Break It Intentionally

name: Hello Automation Academy
on: push
jobs:
  greet:
  runs-on: ubuntu-latest
    steps:
      - run: echo "Hello Automation Academy!"

This version is broken — runs-on is indented at the wrong level (it should be nested one level deeper, under greet:, matching steps:). YAML is extremely sensitive to indentation; this exact mistake produces a workflow that GitHub can't even parse, often failing before a single step ever runs, with an error message pointing at the YAML structure itself rather than anything you actually intended to test.

🛠️ Fix It

name: Hello Automation Academy
on: push
jobs:
  greet:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Hello Automation Academy!"

The fix is purely about indentation — runs-on and steps both need to be indented consistently, one level deeper than greet:, since they're both properties of the greet job, not siblings of it.

⚠️ Common Mistake

Assuming a workflow failure always means your logic is wrong. A huge fraction of first-workflow failures are pure YAML formatting issues (indentation, a missing colon) that have nothing to do with what you were actually trying to accomplish — the fix is almost always in the structure, not the intent.

💡 Quick Tip

Most code editors (VS Code included) have YAML syntax highlighting and indentation guides built in or available as a lightweight extension — turning this on makes indentation mistakes far easier to spot before you even commit, rather than discovering them from a failed run.

🏆 Challenge

Modify your working workflow so it also prints the current date and time as a second step (hint: another plain run: step, using the shell's own date command), and confirm both lines appear in the correct order in the Actions tab's log output.

🎯 Key Takeaway

  • A workflow file must live in .github/workflows/ and use valid YAML to be recognized and run at all.
  • on: push triggers immediately on the next push — no separate activation step.
  • The Actions tab is where you see whether a run succeeded, and read the full log of every step.
  • YAML indentation errors are a genuinely common first failure — and usually simple to fix once spotted.

Interview Questions

Why does a fresh GitHub Actions runner need an explicit "checkout" step before it can do anything with your repository's code?▾
A GitHub-hosted runner starts as a completely fresh, empty virtual machine with no knowledge of your repository at all — it isn't automatically populated with your code. The actions/checkout step explicitly downloads your repository's code onto that runner, which is why almost every real workflow includes it as one of its very first steps, before anything that needs to read or build the actual code.
Why can a single incorrect indentation level in a workflow file cause the entire workflow to fail before any step even runs?▾
YAML uses indentation to express structure — which properties belong to which job, which steps belong to which job's step list. Incorrect indentation changes what the YAML actually means structurally (or makes it invalid entirely), so GitHub can fail to parse the workflow file at all, before it ever gets to the point of scheduling a runner or executing any step.
What's the fastest way to see why a specific GitHub Actions run failed?▾
The repository's Actions tab, drilling into the specific failed run and then the specific job, shows the complete log output for every step — including exactly which step failed and what error or output it produced. This is the primary, fastest path to understanding a failure, rather than guessing from the workflow file alone.
If a workflow uses on: push with no branch filtering, when does it actually trigger?▾
It triggers on a push to any branch in the repository, with no restriction to a specific branch like main. This is worth noting specifically because unrestricted push triggers can run a workflow far more often than intended once a repository has many active branches — branch filtering (covered in a later chapter) is how you narrow this down deliberately.
Why might a professional team's very first real workflow look noticeably different from the tutorial's single echo-command example?▾
The tutorial's version deliberately isolates just one question — does a workflow trigger and run at all — before introducing any real complexity. A professional team's actual first workflow typically needs to do something meaningful right away, like checking out code and running a real test suite, since the whole point of their pipeline is verifying actual application behavior, not just confirming that automation itself is wired up correctly.
