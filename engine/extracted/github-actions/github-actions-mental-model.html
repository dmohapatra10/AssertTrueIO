GitHub Actions Mental Model

Prerequisites: What is GitHub Actions?

What is this?

The previous page introduced six terms individually. This page connects them into one coherent chain — the actual relationship between a repository, a workflow, an event, a job, a runner, and the steps that finally do real work.

The Full Relationship

Repository
   ↓
Workflow
   ↓
Event
   ↓
Job
   ↓
Runner
   ↓
Steps
   ↓
Actions / Commands

Read top to bottom, this is: a repository contains one or more workflow files; each workflow listens for a specific event; when that event happens, the workflow's jobs are scheduled; each job gets assigned a runner; the runner executes that job's steps, in order; and each step is either a plain command or a reusable action.

Where a Workflow File Actually Lives

your-repository/
└── .github/
    └── workflows/
        └── ci.yml

GitHub looks specifically inside .github/workflows/ for YAML files — this exact folder path is not a convention you can change; it's how GitHub Actions discovers what workflows exist in your repository at all.

Detailed Example — Tracing a Real Push Through the Whole Chain

1. A developer runs `git push` to ShopEasy's repository.
2. GitHub notices this matches a "push" event a workflow is listening for.
3. GitHub reads the workflow file in .github/workflows/, finds the job(s) defined in it.
4. GitHub requests a runner (a fresh virtual machine) to execute that job.
5. The runner starts up, and begins executing the job's steps in order.
6. Step 1 might check out the repository's code.
7. Step 2 might install dependencies.
8. Step 3 might actually run the test suite.
9. The job finishes — success or failure is reported back to GitHub,
   visible in the repository's Actions tab.

Every single piece from the previous page's vocabulary appears somewhere in this trace — this is the whole point of learning the terms first: now they describe something concrete you can actually follow, step by step.

Real-World Example — Multiple Jobs in the Same Workflow

One workflow, triggered by one push event, can define MULTIPLE jobs:

Event: push
  Job 1: "lint" — checks code style
  Job 2: "test" — runs the test suite
  Job 3: "build" — builds the application

By default, GitHub runs jobs 1, 2, and 3 in PARALLEL, on separate runners,
unless you explicitly tell it one job must wait for another.

This default — parallel unless told otherwise — is worth internalizing early, since it directly affects how fast your pipeline finishes and comes up again explicitly once dependent, ordered jobs are introduced later in this course.

🧠 Think About It

If "lint," "test," and "build" all run in parallel by default, and "lint" fails, does that automatically stop "test" and "build" from running? Not by default — each job runs independently unless you've explicitly configured one to depend on another. This is a genuinely common early surprise, and it's exactly why job dependencies (covered later in this course) exist as a deliberate feature, not an automatic behavior.

⚠️ Common Mistake

Assuming a workflow file placed anywhere in the repository will be picked up. GitHub only looks in .github/workflows/ — a YAML file sitting in the repository root, or in any other folder, is simply invisible to GitHub Actions, no matter how correctly it's written.

💡 Quick Tip

The Actions tab in a GitHub repository shows every workflow run, its status, and — critically — the full log output of every single step. This is where you'll spend a huge amount of time once workflows start failing in ways that aren't obvious from the YAML alone.

Best Practices

  • Always place workflow files in exactly .github/workflows/ — there's no alternative location GitHub will recognize.
  • Think deliberately about which jobs genuinely need to run in order versus which can safely run in parallel — don't assume one or the other by default.
  • Get comfortable navigating a repository's Actions tab early — it's the primary tool for understanding what actually happened during a run.

🎯 Key Takeaway

  • A workflow file must live in .github/workflows/ to be recognized at all.
  • The chain is: repository → workflow → event → job → runner → steps → actions/commands.
  • Multiple jobs in one workflow run in parallel by default, not in sequence.

🛠️ Try It Yourself

Without writing any real YAML yet, sketch out (on paper, or in a text file) what jobs a workflow for ShopEasy might need if the requirement is "run tests and check code style whenever code is pushed, and only build the application if both of those succeed." Identify which jobs could run in parallel and which genuinely need to wait for another.

Interview Questions

Why does a workflow file placed in the wrong folder simply never run?▾
GitHub Actions specifically looks inside .github/workflows/ to discover workflow files — this isn't a configurable convention, it's how the platform finds workflows at all. A YAML file anywhere else in the repository, no matter how correctly written, is invisible to GitHub Actions, since it never even gets read as a workflow definition.
If a workflow defines three jobs triggered by the same push event, do they run one after another by default?▾
No — by default, GitHub Actions runs all jobs within a workflow in parallel, on separate runners, unless you explicitly configure one job to depend on another. This default often surprises people expecting jobs to naturally run in the order they're listed in the YAML file.
In the full chain from repository to running steps, what specifically does a runner do?▾
The runner is the actual machine — provided by GitHub or self-hosted by an organization — that gets assigned to a specific job and executes that job's steps in order. It sits between "a job has been scheduled" and "the actual commands or actions in that job are running," providing the real computing environment where the work happens.
Where would you look to see exactly what happened during a specific workflow run, including full output from every step?▾
The repository's Actions tab shows every workflow run along with its status, and drilling into a specific run reveals the complete log output for every individual step within every job. This is the primary tool for understanding what actually happened, especially once something fails in a way that isn't obvious just from reading the workflow's YAML.
If "lint" and "test" are two separate parallel jobs and "lint" fails, does "test" automatically stop?▾
Not by default — each job runs independently unless a dependency between them has been explicitly configured. "Test" will continue running and complete on its own timeline regardless of whether "lint" passed or failed, since nothing in a default parallel setup connects the two jobs' outcomes to each other.
