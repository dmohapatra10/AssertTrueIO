Setting Up Programming Languages: Java, Node.js & Python

Prerequisites: Checking Out Repository Code

What is this?

GitHub-hosted runners come with several language versions pre-installed, but a real project usually needs a specific version — this page covers the official setup actions for the three languages this site's other tracks actually use: Java (RestAssured), Node.js (Playwright, k6), and Python.

Setting Up Java

- uses: actions/setup-java@v4
  with:
    java-version: '17'
    distribution: 'temurin'

distribution matters — Java has several different official builds (Temurin, Corretto, Zulu, and others); temurin (Eclipse Adoptium) is a common, solid default choice unless a project has a specific reason to need a different one.

Setting Up Node.js

- uses: actions/setup-node@v4
  with:
    node-version: 20

Simpler than Java — no distribution choice needed, just the version. setup-node also has a built-in caching option, covered on the next page alongside dependency caching more broadly.

Setting Up Python

- uses: actions/setup-python@v5
  with:
    python-version: '3.12'

Follows the same basic pattern as the other two — specify the version your project actually needs, rather than relying on whatever happens to be pre-installed by default.

Detailed Example — Matching a Real Project's Requirements

ShopEasy's actual stack:
- Backend: Java 17 (for RestAssured-based API tests)
- Frontend: Node.js 20 (for the application itself and Playwright tests)

jobs:
  backend-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
      - run: mvn test

  frontend-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test

These are two entirely separate jobs, each setting up exactly the language it actually needs — neither job installs a language runtime it doesn't use, keeping each one focused and no slower than necessary.

🧠 Think About It

Why does setup-java require a distribution choice while setup-node and setup-python don't ask for anything equivalent? Java genuinely has multiple, meaningfully different official distributions maintained by different organizations, each with slightly different support terms and licensing. Node.js and Python don't have this same kind of ecosystem-level distribution fragmentation, so there's no equivalent choice to make.

⚠️ Common Mistake

Relying on whatever language version happens to be pre-installed on the runner by default, without pinning an explicit version at all. GitHub's default pre-installed versions can change over time as runner images update — a project with a genuine dependency on a specific version should specify it explicitly, not assume the current default will always match.

💡 Quick Tip

All three setup actions accept a version file reference too (like reading from a project's own .node-version or .python-version file) — useful for keeping the CI version and a developer's local version defined in exactly one place, rather than duplicating the version number in the workflow file separately.

Best Practices

  • Always specify an explicit version for whichever language your project uses — never rely on the runner's current default.
  • Match the CI language version to what your project actually targets in production, not an arbitrary or convenient choice.
  • Only set up the specific languages a given job actually needs — don't install Java in a job that never touches Java code.

🎯 Key Takeaway

  • Each language has its own official setup action — setup-java, setup-node, setup-python.
  • Java's setup additionally requires choosing a distribution; Node.js and Python don't have an equivalent choice.
  • Always pin an explicit version matching your project's real requirements.

Interview Questions

Why shouldn't a real project simply rely on whatever language version a GitHub-hosted runner has pre-installed by default?▾
Runner images are updated over time by GitHub, which means the specific pre-installed default version of a language can change without any change to your own workflow file. A project with a genuine dependency on a specific version should explicitly pin it using the appropriate setup action, ensuring consistent behavior regardless of what the runner's current default happens to be.
Why does setting up Java specifically require choosing a distribution, unlike Node.js or Python?▾
Java has several meaningfully different official distributions — Temurin, Corretto, Zulu, and others — maintained by different organizations with different support and licensing terms, even though they all implement the same Java version. Node.js and Python don't have this same kind of distribution-level fragmentation, so setup-node and setup-python don't need an equivalent choice.
Why might a workflow with a Java backend job and a separate Node.js frontend job set up each language in its own distinct job rather than both in one?▾
Each job only needs the language runtime relevant to its own specific task — setting up Java in a job that never touches Java code adds unnecessary time with no benefit. Separating them into distinct jobs also allows both to potentially run in parallel, and keeps each job's setup focused and minimal.
What's a genuine advantage of reading a language version from a project file like .node-version rather than hardcoding it in the workflow YAML?▾
It keeps the version defined in exactly one place, which both the CI workflow and a developer's local development environment can reference consistently. Hardcoding the version separately in the workflow file risks it drifting out of sync with whatever version is actually specified for local development, requiring the same value to be updated in two places whenever it changes.
Why does matching the CI language version to what a project actually targets in production matter beyond just making tests pass?▾
Testing against a different language version than what actually runs in production means CI could pass while missing a genuine, version-specific behavior difference that would only surface in the real production environment. Matching versions ensures the CI pipeline's results are actually representative of how the application will behave once deployed, not just whether it works on an arbitrary, potentially mismatched version.
