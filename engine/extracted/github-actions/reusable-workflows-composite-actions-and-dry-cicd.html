The Duplication Problem, One Level Up

Chapter 10 solved duplication within a single workflow — copy-pasted jobs, replaced by a matrix. This chapter solves the same problem across workflows, and even across entire repositories. Four focused pages:

  1. Why Reusability Matters & Reusable Workflows — the problem, and workflow_call
  2. Calling a Reusable Workflow with Inputs & Outputs — actually using one, parameterized
  3. Composite Actions Explained — a genuinely different, complementary reusability tool
  4. Reusable Workflow vs. Composite Action: Choosing the Right One — a real decision guide

The Real-World Scenario This Chapter Solves

Multiple repositories all need the SAME:
Setup → Build → Test → Report

Right now: this logic is copy-pasted into every single repository's
own workflow file, drifting out of sync over time.

This is exactly the same duplication risk Chapter 4's "shared vs. project-specific logic" discussion and Chapter 10's matrix-vs-copy-paste comparison already warned about — just at organizational scale now, across repositories rather than within one file.

Common Mistakes to Watch For

  • Copy-pasting the same setup-build-test logic into every repository that needs it, rather than centralizing it once.
  • Reaching for a composite action when a reusable workflow was actually the right tool, or vice versa — genuinely different mechanisms, covered explicitly on this chapter's final page.
  • Hardcoding values into a centralized workflow that different calling repositories genuinely need to customize — defeating much of the point of centralizing it.

By the end of the four pages that follow, you should be able to define a reusable workflow with workflow_call, call it with real inputs and outputs from another workflow, build a composite action for smaller, step-level reuse, and confidently choose between the two for any given real need.
