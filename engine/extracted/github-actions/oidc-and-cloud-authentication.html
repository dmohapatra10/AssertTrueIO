OIDC & Cloud Authentication

Prerequisites: Containers & Services in GitHub Actions

What is this?

OIDC (OpenID Connect) lets a GitHub Actions workflow prove its identity directly to a cloud provider (AWS, Azure, GCP) and receive temporary access — without a long-lived credential ever being stored as a secret at all.

Why do we need it?

A long-lived cloud credential stored as a secret (covered as a risk pattern back in Chapter 7) remains valid indefinitely until someone manually rotates it — if it's ever leaked, it's a genuine, ongoing risk until someone notices. OIDC eliminates the stored credential entirely; there's simply nothing long-lived to leak.

How This Genuinely Works, Conceptually

1. Your workflow requests a short-lived, cryptographically signed
   identity token FROM GITHUB ITSELF.
2. Your workflow presents that token to the cloud provider (AWS, say).
3. The cloud provider has been pre-configured to TRUST tokens from
   your specific GitHub repository.
4. The cloud provider verifies the token and issues temporary,
   short-lived cloud credentials in return.
5. Your workflow uses those temporary credentials for this run only.

Genuinely no secret was stored anywhere in this entire flow — the trust relationship is configured once, on the cloud provider's side, between it and your specific repository.

Required Permission

permissions:
  id-token: write   # required for the workflow to request an OIDC token at all
  contents: read

This connects directly to Chapter 7's least-privilege principle — id-token: write is specifically and only what's needed to request this identity token; it doesn't grant broad cloud access itself.

Detailed Example — Authenticating to AWS Without a Stored Credential

jobs:
  deploy:
    runs-on: ubuntu-latest
    permissions:
      id-token: write
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789:role/github-actions-deploy
          aws-region: us-east-1
      - run: aws s3 cp dist/ s3://shopeasy-bucket/ --recursive

Notice: there's no AWS_ACCESS_KEY_ID or AWS_SECRET_ACCESS_KEY secret anywhere in this workflow. The role-to-assume is an AWS-side identity, configured once to trust GitHub's OIDC tokens specifically from this repository — genuinely nothing sensitive is stored in GitHub at all.

🧠 Think About It

Why is OIDC-based authentication genuinely more secure than even a well-managed secret containing cloud credentials? A secret, no matter how carefully managed, is still a long-lived value that exists somewhere and could theoretically be exposed. OIDC's temporary credentials exist only for the duration of a specific workflow run and are never stored anywhere at all — there's no long-lived value that could leak, because none exists in the first place.

⚠️ Common Mistake

Continuing to use long-lived cloud access keys stored as secrets out of habit or unfamiliarity, when the actual cloud provider genuinely supports OIDC-based authentication instead. This is exactly the kind of unnecessary, avoidable risk Chapter 7's entire security chapter was building toward recognizing and eliminating where a genuinely better alternative exists.

💡 Quick Tip

Configuring the trust relationship on the cloud provider's side (an IAM role in AWS, for instance) is a real, one-time setup step outside of GitHub Actions itself — worth consulting your specific cloud provider's current documentation for the exact configuration, since this setup lives entirely on their side, not in your workflow file.

Best Practices

  • Prefer OIDC-based authentication over stored long-lived credentials whenever your cloud provider genuinely supports it.
  • Grant id-token: write only to jobs that genuinely need to authenticate this way — following the same least-privilege principle applied everywhere else.
  • Scope the cloud-side trust configuration narrowly — to a specific repository, or even a specific branch — rather than trusting broadly.

🎯 Key Takeaway

  • OIDC lets a workflow authenticate to a cloud provider using a short-lived, verified identity token — no stored credential exists at all.
  • The trust relationship is configured once on the cloud provider's side, between it and a specific GitHub repository.
  • id-token: write is the specific, minimal permission required to request this identity token.

Interview Questions

Why is OIDC-based cloud authentication considered more secure than even a carefully managed, stored secret?▾
A stored secret, however carefully managed, is still a long-lived value that exists somewhere and could theoretically be exposed or leaked. OIDC's temporary credentials exist only for the specific duration of one workflow run and are never stored anywhere at all — there's simply no long-lived value present that could ever leak, because none exists in the first place.
What does the id-token: write permission specifically allow a workflow to do?▾
It allows the workflow to request a short-lived, cryptographically signed identity token from GitHub itself — this is the specific, minimal permission required for the OIDC authentication flow to begin. It doesn't grant broad cloud access on its own; that access only comes after the cloud provider verifies the token and issues its own temporary credentials in response.
Where does the trust relationship between a specific GitHub repository and a cloud provider actually get configured?▾
This configuration happens on the cloud provider's own side — for AWS, as an IAM role configured to trust tokens from a specific GitHub repository — not within the GitHub Actions workflow file itself. It's a one-time setup step performed in the cloud provider's own console or configuration tools, establishing which repositories are trusted before any workflow can actually use OIDC to authenticate.
Why does a workflow using OIDC-based AWS authentication have no AWS_ACCESS_KEY_ID or AWS_SECRET_ACCESS_KEY secret anywhere in it?▾
Because OIDC eliminates the need for a stored, long-lived credential entirely — instead of presenting a pre-existing secret, the workflow requests a temporary identity token from GitHub and exchanges it for temporary AWS credentials that exist only for that specific run. There's genuinely nothing sensitive stored as a GitHub secret in this authentication flow at all.
Why should a team consider migrating from stored cloud credentials to OIDC even if their current secret has never been exposed?▾
The risk of a stored, long-lived credential isn't that it has been exposed — it's that it genuinely could be, at any point, for as long as it continues to exist. OIDC removes that entire category of risk by eliminating the long-lived credential altogether, which is a real, structural security improvement independent of whether any specific past exposure has actually occurred.
