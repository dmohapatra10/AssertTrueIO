GitHub Actions Contexts Explained

Prerequisites: Environment Variables: env: and Job vs. Step Scope

What is this?

A context is a built-in source of information GitHub Actions automatically makes available to every workflow — which branch triggered the run, what a previous step actually output, which matrix combination is currently executing. This page covers the contexts you'll genuinely use.

github — Information About the Triggering Event

github.ref          # the branch or tag that triggered the run, e.g. refs/heads/main
github.sha           # the exact commit SHA being built
github.actor          # who triggered the workflow
github.event_name      # which event triggered it (push, pull_request, etc.)

This is genuinely the most commonly used context — almost any workflow that needs to know "what actually happened" reaches for github first.

env — Reading Your Own Environment Variables

${{ env.NODE_ENV }}

The same environment variables covered on the previous page, but accessed through expression syntax rather than shell syntax — useful specifically in places (like an if: condition) that aren't inside a run: shell command at all.

vars — Repository or Organization Variables

${{ vars.DEFAULT_REGION }}

Similar to env, but for variables configured at the repository or organization level (through GitHub's own settings, not defined inline in the workflow file) — genuinely useful for values shared consistently across many different workflows without duplicating them in each one.

job — Information About the Current Job

${{ job.status }}   # the current job's status so far

Mostly useful in specific advanced scenarios, like a final cleanup step wanting to know whether the job succeeded or failed up to that point.

steps — Reading a Previous Step's Output

steps:
  - id: get_version
    run: echo "version=1.2.3" >> $GITHUB_OUTPUT
  - run: echo "The version is ${{ steps.get_version.outputs.version }}"

This is how one step reads a value another step deliberately produced — the id: on the first step gives it a name, and steps.<id>.outputs.<name> retrieves the value elsewhere. This exact mechanism is covered in full depth in a later chapter on passing information between steps.

runner — Information About the Runner Itself

${{ runner.os }}     # "Linux", "Windows", or "macOS"
${{ runner.temp }}    # a path to a temporary directory on the runner

Useful for a workflow that needs to behave slightly differently depending on which operating system it's actually running on — for instance, a matrix build (covered in a later chapter) testing across multiple operating systems.

matrix — The Current Matrix Combination

${{ matrix.node-version }}

Only meaningful inside a matrix build (covered fully in Chapter 10) — holds whichever specific combination of values is currently being tested in this particular run.

needs — Outcomes From Jobs This One Depends On

${{ needs.test.result }}   # "success", "failure", "cancelled", or "skipped"

Only available in a job that explicitly depends on another (via needs:, covered fully in Chapter 9) — lets a later job check whether an earlier one it depends on actually succeeded.

Detailed Example — Multiple Contexts in One Real Condition

if: github.ref == 'refs/heads/main' && needs.test.result == 'success'

This combines the github context (checking which branch triggered the run) with the needs context (checking whether a dependency job succeeded) — exactly the two pieces of information this chapter's opening real-world requirement actually needs.

🧠 Think About It

Why does vars exist as a genuinely separate context from env, given that both hold named values? env values are typically defined right in the workflow file itself — visible and version-controlled alongside the code. vars values are configured through GitHub's own settings, outside the workflow file — useful specifically for values that should be shared consistently across many workflows without being duplicated or hardcoded into each one individually.

⚠️ Common Mistake

Trying to use matrix or needs outside the specific situation each one actually requires — matrix only makes sense inside an actual matrix build; needs only works in a job that has genuinely declared a dependency on another job. Using either outside its proper context simply won't have the value you're expecting.

💡 Quick Tip

GitHub's own documentation maintains the complete, authoritative reference for every context and every specific field each one exposes — this page covers the ones worth knowing exist, but the full reference is worth bookmarking for the specific field names you'll need in a real workflow.

Best Practices

  • Reach for github first for almost any "what actually happened" question — it's the most broadly useful context.
  • Use vars (repository/organization-level) for values genuinely shared across many workflows, rather than duplicating the same value in every file's env.
  • Only reference matrix or needs in the specific situations where they're actually populated with meaningful values.

🎯 Key Takeaway

  • github holds information about the triggering event; env and vars hold your own defined values (inline versus repository-level).
  • steps reads a previous step's deliberate output; needs reads a dependency job's outcome.
  • runner and matrix provide information specific to the current execution environment and matrix combination.

Interview Questions

What's the practical difference between the env context and the vars context?▾
env holds environment variables typically defined directly within the workflow file itself, visible and version-controlled alongside the workflow's own code. vars holds variables configured through GitHub's own repository or organization settings, outside the workflow file, making them easy to share consistently across many different workflows without duplicating the same value in each one.
Why is the steps context only useful when a previous step has an explicit id: assigned to it?▾
The steps context retrieves output using the pattern steps.<id>.outputs.<name> — without an explicit id on the step that produced the output, there's no name to reference when trying to retrieve that value from a later step. The id is what makes a specific step's output addressable at all.
In what situation does the needs context actually contain a meaningful value?▾
Only in a job that has explicitly declared a dependency on another job using needs:. Only then does that dependent job have access to information about the outcome (needs.<job-name>.result) of the job or jobs it depends on — a job with no declared dependencies has nothing meaningful to read from this context.
Why would a workflow use runner.os specifically inside a matrix build testing multiple operating systems?▾
Different operating systems sometimes need genuinely different commands or paths — runner.os lets a step check which OS it's currently executing on and branch its behavior accordingly, which is especially relevant in a matrix build deliberately running the same job across several different operating systems in parallel.
Why does the expression github.ref == 'refs/heads/main' && needs.test.result == 'success' combine two different contexts rather than relying on just one?▾
These two contexts answer two genuinely different questions that both need to be true for the intended condition — github.ref confirms which branch triggered the run, while needs.test.result confirms whether a specific dependency job actually succeeded. Neither context alone can answer both questions, so combining them with a logical AND is necessary to express the full, real requirement accurately.
