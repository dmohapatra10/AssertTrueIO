Conditional Execution: if:

Prerequisites: Expressions: The ${{ }} Syntax

What is this?

if: makes a job or step run conditionally — only when the expression it's given evaluates to true. Everything from this chapter (environment variables, contexts, expressions) exists in service of making this one key genuinely useful.

Basic Syntax — On a Step

- run: echo "This only runs on main"
  if: github.ref == 'refs/heads/main'

Basic Syntax — On a Whole Job

jobs:
  deploy:
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying..."

Putting if: at the job level means the entire job is skipped when the condition is false — not just one step within it. Choose job-level versus step-level based on how much of the surrounding logic genuinely depends on the same condition.

Detailed Example — The Complete Real-World Requirement, Fully Built

name: ShopEasy CI/CD
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npm test

  deploy:
    needs: test
    if: github.ref == 'refs/heads/main' && needs.test.result == 'success'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "Deploying ShopEasy to production"

This is the exact requirement from this chapter's opening page, fully realized: deployment only happens when both conditions hold — the workflow is running on main, and the test job (which this job explicitly depends on via needs:, covered fully in Chapter 9) actually succeeded. A pull request build runs tests but never reaches deployment; a push to main only deploys if those tests genuinely passed.

A Genuinely Common Pattern — Always Upload Results

- name: Upload test report
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: test-report
    path: test-results/

Combining if: always() with an upload step means the test report gets published whether the tests passed or failed — genuinely useful, since a failure is often exactly when you most want to actually look at the detailed results.

🧠 Think About It

Why does the deploy job in the detailed example above need both needs: test AND the if: condition checking needs.test.result, rather than just one or the other? needs: test alone would still run deploy after test finishes, even if test failed — by default, GitHub Actions runs a dependent job regardless of whether its dependency succeeded, unless you explicitly check the result. The if: condition is what actually enforces "only if it succeeded."

⚠️ Common Mistake

Assuming needs: test alone is sufficient to prevent deployment after a failed test job. It isn't — needs: only establishes ordering (deploy waits for test to finish), not a success requirement. Without an explicit if: checking needs.test.result == 'success', a failed test job would still let deployment proceed.

💡 Quick Tip

An if: condition doesn't strictly need the ${{ }} wrapper — GitHub Actions specifically evaluates the entire if: value as an expression automatically. Many real workflows omit it here specifically for this reason, even though including it is never wrong.

Best Practices

  • Use job-level if: when an entire job's purpose depends on one condition; step-level when only part of a job does.
  • Always pair needs: with an explicit result check when a dependent job should only proceed after genuine success, not just after completion.
  • Use if: always() deliberately for reporting or cleanup steps that should run regardless of what happened earlier.

🎯 Key Takeaway

  • if: conditionally runs a job or step based on an expression evaluating to true.
  • needs: alone only establishes order, not a success requirement — an explicit if: check is needed to require success specifically.
  • if: always() is the common, deliberate pattern for steps that should run regardless of earlier outcomes.

Interview Questions

Why is needs: test alone not sufficient to prevent a deploy job from running after a failed test job?▾
needs: establishes execution order — it ensures the deploy job waits until the test job has finished — but by default, GitHub Actions still runs the dependent job even if the dependency failed, unless told otherwise. An explicit if: condition checking needs.test.result == 'success' is what actually enforces that deployment only proceeds after genuine success, not just after completion.
What's the practical difference between putting if: at the job level versus the step level?▾
A job-level if: skips the entire job — none of its steps run at all — when the condition is false. A step-level if: only skips that one specific step, while the rest of the job's steps proceed normally. Which to use depends on whether the condition genuinely applies to an entire job's purpose or just one specific action within it.
Why does if: always() specifically matter for uploading test reports or logs?▾
By default, a failing step stops the rest of that job's steps from running — without always(), a reporting or upload step would never execute precisely when a test has failed, which is exactly when the detailed report or logs would be most valuable for diagnosing what went wrong. always() overrides the default fail-fast behavior specifically for that step.
Does an if: condition require the ${{ }} wrapper the way an env: value does?▾
No — GitHub Actions automatically evaluates the entire value given to if: as an expression, without requiring the explicit ${{ }} wrapper, unlike most other places expressions are used. Including the wrapper anyway is never incorrect, but many real-world workflows omit it specifically within if: conditions for this reason.
In the ShopEasy example, why does a pull request never actually reach the deploy job, even though both jobs are defined in the same workflow?▾
The deploy job's if: condition specifically checks github.ref == 'refs/heads/main', which is only true for a push directly to the main branch — a pull request's ref refers to the pull request itself, not main, so this condition evaluates to false for any pull request run. The test job still runs on pull requests (since it has no such restriction), but deploy correctly never executes in that case.
