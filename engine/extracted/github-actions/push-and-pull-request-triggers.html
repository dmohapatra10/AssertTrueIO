Push & Pull Request Triggers

Prerequisites: What is a GitHub Actions Event?

What is this?

The two most commonly used events in any real project: push, which fires when code is pushed to any branch, and pull_request, which fires specifically around pull request activity. They look similar but serve genuinely different purposes.

The push Event

on: push

Fires whenever a commit is pushed to any branch in the repository — with no filtering, this is broader than most real projects actually want.

Filtering push to Specific Branches

on:
  push:
    branches:
      - main

This restricts the trigger to pushes specifically on main — a push to any other branch won't fire this workflow at all. This is genuinely important once a repository has many active feature branches; without filtering, every single push everywhere would trigger the workflow.

Excluding Specific Branches

on:
  push:
    branches-ignore:
      - 'docs/**'

branches-ignore does the opposite — run on every branch except the ones matching this pattern. Useful for excluding branches where running the full pipeline genuinely doesn't make sense (documentation-only branches, for instance).

The pull_request Event

on: pull_request

Fires specifically on pull request activity — by default, when a pull request is opened, when new commits are pushed to it, and a few other related actions. This is genuinely different from push: it's about the pull request itself as a concept, not just "code changed somewhere."

Detailed Example — Why Both Events Matter for Different Reasons

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

This workflow triggers in two genuinely different situations: when code is actually merged into main directly (the push half), and separately, whenever someone opens or updates a pull request targeting main (the pull_request half) — even before that pull request is merged. This combination is extremely common: it verifies proposed changes before they merge, and verifies main itself after they do.

Real-World Example — ShopEasy's Actual Requirement, Half-Built

# "Run tests on every pull request" — this piece, now covered:
on:
  pull_request:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test

This satisfies exactly one part of the three-part ShopEasy requirement from this chapter's hub page — tests now run automatically on every pull request targeting main, catching problems before they're ever merged.

🧠 Think About It

Why might a team specifically want pull_request in addition to push, rather than relying on push alone? A push-only setup only catches problems after code lands on a branch — often after it's already been merged. A pull_request trigger runs checks on the proposed change itself, before it's merged, catching a problem while it's still easy to fix or simply not merge at all.

⚠️ Common Mistake

Using unfiltered on: push in a repository with many active feature branches, then being surprised that the pipeline runs constantly, on every single push to every branch, consuming far more CI resources and time than intended. Branch filtering isn't a minor optimization — for an active repository, it's often the difference between a genuinely useful pipeline and an overwhelming one.

💡 Quick Tip

The pattern branches: [main] can also use wildcards, like branches: ['release/**'], matching any branch name under that pattern — useful for teams with a consistent branch naming convention.

Best Practices

  • Filter push to specific branches (usually main, and any other genuinely important long-lived branches) rather than leaving it unfiltered.
  • Use pull_request specifically to validate proposed changes before merge, separate from validating what's already on a branch.
  • Combine both when a workflow genuinely needs to cover both "before merge" and "after merge" scenarios.

🎯 Key Takeaway

  • push fires on commits to a branch; pull_request fires on pull request activity specifically.
  • Both support branch filtering via branches (include) and branches-ignore (exclude).
  • Combining both is common — pull_request validates before merge, push validates after.

Write the on: block for a workflow that should run on pull requests targeting either main or develop, and also on direct pushes to main only — using both push and pull_request with appropriate branch filtering for each.

Interview Questions

What's the practical difference between the push and pull_request events?▾
push fires whenever a commit is pushed to a branch, regardless of whether a pull request is involved at all. pull_request fires specifically around pull request activity — opening one, pushing new commits to it — and is tied to the concept of a proposed change being reviewed, not just code changing somewhere.
Why might a repository with many active feature branches specifically need branch filtering on its push trigger?▾
Without filtering, an on: push trigger fires on every single push to every branch in the repository, which in an active project with many feature branches means the pipeline runs constantly and consumes far more CI time and resources than intended. Filtering to specific branches (usually main) keeps the trigger firing only for pushes that actually matter for that workflow's purpose.
Why would a team want both push and pull_request triggers on main, rather than just one of them?▾
pull_request validates a proposed change before it's merged, catching problems while they're still easy to fix or simply avoid merging. push (filtered to main) validates the actual state of main after a merge has happened. Together they cover both the "before" and "after" perspectives, which a single trigger alone can't provide.
What does branches-ignore do differently from branches in a trigger configuration?▾
branches specifies which branches the trigger SHOULD fire on — an inclusion list. branches-ignore specifies which branches to explicitly exclude, firing on every branch except the ones matching the given pattern. They represent opposite filtering approaches, and using both together on the same trigger isn't meaningful — you'd choose one or the other based on whether it's easier to list what you want or what you don't want.
Why does branches: ['release/**'] use a wildcard pattern rather than listing exact branch names?▾
A wildcard pattern like release/** matches any branch name that fits that structure (release/1.0, release/2.0, and so on), without needing to update the workflow file every time a new branch matching that pattern is created. This is especially useful for teams with a consistent branch naming convention, where the SET of matching branches naturally grows over time.
