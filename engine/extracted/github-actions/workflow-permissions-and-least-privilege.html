Workflow Permissions & Least Privilege

Prerequisites: GITHUB_TOKEN: The Automatic Token Explained

What is this?

Least privilege means giving something exactly the access it needs to do its job — no more. In GitHub Actions, this is configured through the permissions: key, controlling what GITHUB_TOKEN is actually allowed to do for a given workflow or job.

Why do we need it?

A workflow with excessive permissions is a genuine liability — if that workflow is ever compromised (through a malicious dependency, a vulnerable third-party action, or any other route), the damage is limited by what its token could actually do. A workflow that only ever reads code but has been granted write access to everything is carrying real, unnecessary risk for no benefit.

Setting Permissions at the Workflow Level

permissions:
  contents: read
  pull-requests: write

Placed at the top of a workflow file, this applies to every job within it — here, read-only access to repository contents, and write access specifically to pull requests (for commenting, for instance).

Setting Permissions at the Job Level

jobs:
  comment-only:
    permissions:
      pull-requests: write
    runs-on: ubuntu-latest
    steps:
      - uses: actions/github-script@v7
        with:
          script: echo "commenting..."

Job-level permissions override the workflow-level default for that specific job — useful when different jobs in the same workflow genuinely need different levels of access.

The Restrictive Default — permissions: {}

permissions: {}

This grants no permissions at all — the most restrictive possible starting point. A genuinely disciplined approach starts here and adds back exactly what's actually needed, rather than starting broad and hoping to remember to narrow it later.

Detailed Example — ❌ Excessive vs. ✅ Minimal Permissions

❌ Excessive — this job only needs to run tests, but has full write access:
permissions:
  contents: write
  pull-requests: write
  issues: write
  packages: write

✅ Minimal — matching what the job actually does:
permissions:
  contents: read

A job that only checks out code and runs tests has no genuine need for write access to anything — contents: read is fully sufficient, and everything else in the excessive version is unused, unnecessary risk.

🧠 Think About It

Why might starting from permissions: {} and adding back exactly what's needed be a better habit than starting from a broad default and trying to remember to narrow it later? Starting restrictive forces you to actually think through and justify every single permission a job needs, at the moment you're writing it — starting broad and narrowing later depends on remembering to come back and do that work, which is easy to skip once something is already working.

⚠️ Common Mistake

Granting broad permissions "to avoid dealing with permission errors later," rather than figuring out the actual minimum a workflow needs. This is exactly the kind of shortcut that turns a routine CI pipeline into a genuine security liability if that workflow, or any dependency it uses, is ever compromised.

💡 Quick Tip

If a workflow fails with a permissions-related error, the fix is adding exactly the specific permission it's missing — not reflexively granting broad access "to make the error go away." The error message itself usually names the specific permission that's actually required.

Best Practices

  • Start from the most restrictive permissions possible, adding back only what's genuinely required for that specific workflow or job.
  • Set permissions at the job level when different jobs in the same workflow genuinely need different access levels.
  • Treat a permissions error as a signal to add exactly the missing permission, not an invitation to grant broad access.

🎯 Key Takeaway

  • Least privilege means granting exactly the access a workflow needs — no more, limiting the damage if something ever goes wrong.
  • permissions: can be set at the workflow level (applying to all jobs) or overridden at the job level.
  • Starting from permissions: {} and adding back specific needs is more disciplined than starting broad and narrowing later.

🏆 Challenge

For a workflow with two jobs — one that only runs tests (needing to read repository contents), and another that creates a GitHub release after tests pass (needing to write releases) — write the appropriate permissions: configuration for each job separately, following least-privilege principles throughout.

Interview Questions

What does the principle of least privilege actually mean in the context of GitHub Actions permissions?▾
It means granting a workflow or job exactly the access it needs to perform its actual task, and nothing more. If a job only reads code and runs tests, it should only have read access to contents — granting it write access to issues, packages, or other resources it never actually touches provides no benefit while adding genuine, unnecessary risk.
Why does starting from permissions: {} and adding back specific needs tend to produce more secure workflows than starting broad?▾
Starting restrictive forces a deliberate decision and justification for every single permission actually granted, at the moment the workflow is written. Starting broad and planning to narrow permissions later depends on remembering to actually do that follow-up work, which is easy to overlook once the workflow is already functioning — restrictive-by-default is a more reliable habit than optimistic-then-narrow.
Why might two different jobs within the same workflow need different permissions: configurations?▾
Different jobs often perform genuinely different tasks with different real access needs — a test job might only need to read repository contents, while a separate release job genuinely needs write access to create a release. Setting permissions at the job level, rather than only at the workflow level, allows each job to have exactly the access appropriate to what it actually does.
Why is granting broad permissions "to avoid permission errors" considered a genuinely risky shortcut rather than harmless convenience?▾
Excessive permissions mean that if the workflow itself, or any dependency or third-party action it uses, is ever compromised, the potential damage is limited only by whatever broad access was granted — rather than being genuinely contained to what the task actually needed. This turns a routine convenience shortcut into a real, magnified security exposure if anything ever goes wrong.
If a job-level permissions: block is defined, does it combine with the workflow-level permissions or replace it?▾
A job-level permissions: configuration overrides the workflow-level default for that specific job, rather than combining or merging with it — similar to how job-level and step-level env values override broader scopes rather than merging. This means a job with its own permissions: block is governed entirely by that job-specific configuration, not by whatever the workflow-level setting specifies.
