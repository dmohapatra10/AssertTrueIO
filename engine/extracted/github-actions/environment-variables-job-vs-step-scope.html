Environment Variables: env: and Job vs. Step Scope

Prerequisites: Variables, Contexts & Expressions overview

What is this?

env: defines an environment variable — a named value a step's commands can read. It can be set at three different levels: the whole workflow, a specific job, or a single step, each with a genuinely different scope.

Workflow-Level env

env:
  NODE_ENV: production

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo $NODE_ENV   # available here — "production"

Defined at the very top of the file, a workflow-level env is available to every job and every step throughout the entire workflow.

Job-Level env

jobs:
  build:
    runs-on: ubuntu-latest
    env:
      BUILD_MODE: fast
    steps:
      - run: echo $BUILD_MODE   # available here
  test:
    runs-on: ubuntu-latest
    steps:
      - run: echo $BUILD_MODE   # NOT available — different job

An env defined inside a specific job is available to every step within that job, but not to any other job — this follows the same job-isolation principle covered in Chapter 4.

Step-Level env

steps:
  - run: echo $DEBUG_MODE
    env:
      DEBUG_MODE: verbose

The narrowest scope — available only within that single step, and nowhere else.

Precedence — What Happens When Scopes Overlap

env:
  MODE: workflow-level     # set at the top

jobs:
  build:
    env:
      MODE: job-level       # overrides the workflow-level value, for this job
    steps:
      - run: echo $MODE     # prints "job-level"
      - run: echo $MODE
        env:
          MODE: step-level  # overrides again, only for this one step
        # this step prints "step-level"

The narrowest scope always wins — step-level overrides job-level, which overrides workflow-level. This is genuinely useful: define a sensible default once at the top, then override it exactly where a specific job or step legitimately needs something different.

Detailed Example — ShopEasy's Environment Configuration

env:
  APP_NAME: ShopEasy               # true everywhere — workflow-level

jobs:
  test:
    runs-on: ubuntu-latest
    env:
      TEST_TIMEOUT: 30000           # only test job needs this
    steps:
      - run: echo "Testing $APP_NAME with timeout $TEST_TIMEOUT"

  deploy:
    runs-on: ubuntu-latest
    env:
      TARGET_ENV: production        # only deploy job needs this
    steps:
      - run: echo "Deploying $APP_NAME to $TARGET_ENV"

APP_NAME is genuinely relevant everywhere, so it lives at the workflow level. TEST_TIMEOUT and TARGET_ENV are each relevant to exactly one job, so they're scoped there instead — no job carries configuration it doesn't actually need.

🧠 Think About It

Why might scoping a variable as narrowly as genuinely possible (step-level over job-level, job-level over workflow-level) generally be good practice, rather than just defining everything at the workflow level for convenience? A variable defined more broadly than it's actually used makes a workflow harder to reason about — someone reading a specific job has to check the entire file to know what values might be in play, rather than seeing everything relevant right there in that job's own definition.

⚠️ Common Mistake

Forgetting that a job-level or step-level env genuinely overrides a workflow-level one with the same name, rather than somehow combining with it. If a job defines MODE: job-level and the workflow defines MODE: workflow-level, steps in that job see only job-level — the workflow-level value is fully replaced, not merged in any way.

💡 Quick Tip

Reading an environment variable's value inside a run: command uses your shell's own syntax — $VARIABLE_NAME on Linux/macOS (bash), $env:VARIABLE_NAME on Windows (PowerShell). This is genuinely different from reading a context via ${{ }}, covered later in this chapter — environment variables and contexts are related but distinct mechanisms.

Best Practices

  • Scope a variable to the narrowest level that's actually correct — workflow-level only for values genuinely needed everywhere.
  • Use consistent, clear naming so it's obvious what a variable represents without needing to trace where it's defined.
  • Remember that overlapping scopes override rather than merge — the narrowest scope's value is what a step actually sees.

🎯 Key Takeaway

  • env: can be set at workflow, job, or step level, each with progressively narrower scope.
  • When scopes overlap, the narrowest one wins — step overrides job, job overrides workflow.
  • Reading a variable inside run: uses the shell's own syntax ($VAR on bash, $env:VAR on PowerShell).

🛠️ Try It Yourself

Write a workflow (in YAML) with a workflow-level env value, a job that overrides it, and a single step within that job that overrides it again — then trace through, in writing, exactly what value each step in the workflow would actually see.

Interview Questions

If a workflow-level env and a job-level env both define the same variable name, which value does a step in that job actually see?▾
The job-level value — the narrower scope always overrides the broader one when they define the same variable name. This isn't a merge of the two values; the job-level definition completely replaces the workflow-level one for any step within that specific job.
Why does a job-level environment variable not carry over to a different job in the same workflow?▾
This follows the same job-isolation principle covered when jobs and steps were first explained in depth — each job runs on its own separate, fresh runner, and a job-level env is scoped specifically to that job's own execution context. A different job in the same workflow simply never had that variable defined for it at all.
Why might scoping a variable at the narrowest correct level be preferable to defining everything at the workflow level?▾
Defining a variable more broadly than it's actually used makes a workflow harder to understand — someone reading one specific job has to check the entire file to know what values might apply, rather than finding everything relevant to that job defined right there. Narrow scoping keeps each part of a workflow self-contained and easier to reason about in isolation.
Why is reading an environment variable inside a run: step done differently from reading a context value?▾
An environment variable is read using the shell's own native syntax ($VAR on bash, $env:VAR on PowerShell), since it's a genuine operating-system-level environment variable available to whatever process is actually running. A context value is read through GitHub Actions' own ${{ }} expression syntax, which is evaluated by GitHub Actions itself before the shell command even runs — these are two different mechanisms operating at different points in the process.
In a workflow with env defined at all three levels (workflow, job, step) for the same variable name, which value applies inside that specific step?▾
The step-level value — it's the narrowest scope of the three, and narrowest scope always takes precedence when multiple levels define the same variable name. The job-level and workflow-level definitions still apply to other steps or jobs that don't have their own more specific override, but this particular step sees only its own step-level value.
