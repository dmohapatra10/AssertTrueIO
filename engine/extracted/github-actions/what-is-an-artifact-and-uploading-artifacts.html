What is an Artifact? & Uploading Artifacts

Prerequisites: Artifacts, Caching & Build Outputs overview

What is this?

An artifact is a file or folder produced during a job that GitHub Actions saves and makes available after the job finishes — downloadable from the Actions tab, or retrievable by a different job in the same workflow.

Why do we need it?

Once a job's runner is destroyed (immediately after the job finishes), everything on it is genuinely gone — a built application, a test report, a log file, all of it. Artifacts exist specifically to save something worth keeping before that happens.

Real-World Analogy

Think of a job's runner like a hotel room you're checking out of — anything left behind when you leave is gone for good. An artifact is the specific act of packing something into your suitcase before checkout — a deliberate choice about what's actually worth keeping.

Uploading an Artifact

- uses: actions/upload-artifact@v4
  with:
    name: build-output
    path: dist/

name is what this artifact will be called (used later when downloading it); path is the file or folder to actually save — here, an entire dist/ folder, likely a build's output.

Uploading Multiple Paths

- uses: actions/upload-artifact@v4
  with:
    name: build-and-logs
    path: |
      dist/
      logs/build.log

Multiple paths, one per line, all get bundled into the same named artifact.

Detailed Example — Uploading ShopEasy's Build Output

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: shopeasy-build
          path: dist/

Without this final step, the build's output would exist only briefly, on a runner that's about to be destroyed — completely inaccessible to anything else, including a later job that might genuinely need to deploy it.

🧠 Think About It

Why might a team deliberately choose to upload only dist/ (the actual build output) rather than the entire repository, including source code, node_modules, and everything else? Artifacts have real storage costs and size limits, and most of a repository's full contents (source code already in version control, installed dependencies that can be reinstalled) aren't genuinely worth preserving this way — uploading exactly what's actually needed keeps artifacts small, fast, and meaningful.

⚠️ Common Mistake

Forgetting the upload step entirely, then being confused when a later job or a person downloading from the Actions tab can't find anything from an earlier job's work. If it wasn't explicitly uploaded as an artifact, it simply doesn't exist anywhere once that job's runner is destroyed.

💡 Quick Tip

Artifacts have a retention period (configurable, with a default that varies) after which GitHub automatically deletes them — worth knowing if you're relying on an artifact still being available weeks or months after a specific run, rather than assuming it persists indefinitely.

Best Practices

  • Upload exactly what's genuinely needed later — a build's actual output, not everything that happened to exist on the runner.
  • Use clear, descriptive artifact names, especially in a workflow that uploads more than one artifact across different jobs.
  • Be aware of retention periods if a workflow or process depends on an artifact remaining available for an extended time.

🎯 Key Takeaway

  • An artifact is a deliberately saved file or folder from a job, since everything else on that job's runner is destroyed once it finishes.
  • actions/upload-artifact takes a name (for later retrieval) and a path (what to actually save).
  • Artifacts have a retention period and aren't kept indefinitely by default.

🛠️ Try It Yourself

For a hypothetical Python project that produces a compiled report as report.pdf and a set of log files in a logs/ folder, write the actions/upload-artifact step that would save both under one artifact named build-report.

Interview Questions

Why does a file produced during a job need to be explicitly uploaded as an artifact to survive beyond that job?▾
Each job runs on its own runner, which is completely destroyed once the job finishes — anything on that runner's filesystem, including files the job produced, is genuinely gone at that point unless it was deliberately saved. Uploading as an artifact is the explicit mechanism for preserving something worth keeping before that destruction happens.
What do the name and path parameters in actions/upload-artifact actually control?▾
name is the label this specific artifact will be known by, used later when downloading it (either through the Actions tab or by another job). path specifies which file or folder should actually be saved — the real content being preserved. Together, they determine both what gets kept and how it's identified afterward.
Why might a team deliberately avoid uploading an entire repository's contents as an artifact, including node_modules?▾
Most of a repository's full contents are either already safely stored in version control (source code) or can be regenerated on demand (installed dependencies) — uploading them as an artifact adds real storage cost and time for no genuine benefit. Artifacts are most useful for things that are otherwise genuinely at risk of being lost, like a specific build's actual compiled output.
Why does it matter that artifacts have a retention period rather than being kept indefinitely?▾
A workflow or process that assumes an artifact will remain available far into the future (weeks or months after the run that created it) could break unexpectedly once that artifact is automatically deleted after its retention period expires. Knowing the actual retention period matters for correctly designing any process that depends on retrieving an older artifact later.
Can a single artifact contain more than one file or folder?▾
Yes — the path parameter accepts multiple paths, one per line, all of which get bundled together into the same named artifact. This is useful when several genuinely related outputs (a build folder and a specific log file, for instance) should be grouped and retrieved together as a single unit rather than as separate, individually-named artifacts.
