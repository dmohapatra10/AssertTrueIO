What is CI/CD?

Prerequisites: CI/CD & GitHub Actions Fundamentals overview

What is this?

CI/CD stands for Continuous Integration and Continuous Delivery (or Deployment) — a set of practices for getting code changes from a developer's machine into a real, running application safely and repeatedly, without a human manually performing every step by hand each time.

Why do we need it? — The Problem Before CI/CD

Picture ShopEasy before any of this exists: a developer finishes a feature, manually runs the tests on their own laptop (if they remember to), manually builds the application, manually copies files to a server, and manually restarts the service. Every single step depends on a human doing it correctly, in the right order, every single time. Miss one step, and something breaks — often not on this deploy, but the next one, in a way nobody can quite explain.

Real-World Analogy

Think of a restaurant kitchen with no standard recipe or process — every dish depends entirely on whichever chef happens to be cooking that night remembering every ingredient and every step from memory. It might work most nights. Then one night, someone forgets the salt, or cooks the chicken for the wrong amount of time, and a customer gets a bad meal — not because anyone was careless, but because nothing was actually standardized or checked. CI/CD is the standardized recipe, followed by a machine, every single time, exactly the same way.

Continuous Integration (CI)

Continuous Integration means automatically building and testing code every time it changes — typically on every push or pull request. The goal is catching a problem the moment it's introduced, while it's small and easy to fix, rather than discovering it days or weeks later when it's tangled up with a dozen other changes.

Continuous Delivery vs. Continuous Deployment

These two terms get conflated constantly, and the distinction matters:

  • Continuous Delivery — every change that passes the pipeline is automatically prepared and ready to release, but an actual human still clicks the button to deploy it.
  • Continuous Deployment — every change that passes the pipeline is automatically released to real users, with no human approval step at all.

The "CD" in "CI/CD" is genuinely ambiguous in casual conversation — when someone says their team "does CI/CD," it's worth asking specifically which one they mean, since the difference (a human gate vs. none) is a real, significant design decision, not a minor detail.

Visual Mental Model

Developer → Commit → Build → Test → Deploy

This is the simplest possible shape of a CI/CD pipeline — every stage before "Deploy" is what makes the deploy itself trustworthy. Skip the "Test" stage, and "Deploy" just means "ship whatever we have and hope."

Detailed Example — ShopEasy Before and After

❌ Before CI/CD (manual, error-prone):
Developer finishes feature
  → runs tests locally (maybe, if remembered)
  → manually builds the app
  → manually copies files to the server
  → manually restarts the service
  → discovers something broke, three days later, in production

✅ After CI/CD (automatic, repeatable):
Developer pushes code
  → pipeline automatically builds
  → pipeline automatically runs every test
  → pipeline automatically deploys (or prepares for deployment)
  → a broken change is caught in minutes, not days

🧠 Think About It

ShopEasy's team currently deploys by having one specific engineer manually SSH into the server and run a deploy script. What happens the day that engineer is on vacation and a critical bug needs to ship immediately? This is exactly the kind of single-point-of-failure risk CI/CD is designed to eliminate — the process shouldn't depend on one person's availability or memory.

⚠️ Common Mistake

Treating "we have a CI pipeline" as equivalent to "we're safe from bad deploys." A pipeline that builds and runs tests but has weak or missing tests will happily and automatically ship broken code, just very quickly and consistently. CI/CD makes your existing process faster and more repeatable — it doesn't automatically make a weak testing practice into a strong one.

💡 Quick Tip

If your team is just getting started, Continuous Delivery (automated up to a human approval) is usually the more comfortable first step before Continuous Deployment (fully automatic, no human gate) — it builds trust in the pipeline gradually rather than requiring total confidence on day one.

Best Practices

  • Be precise about which "CD" you mean — Delivery (human approves) or Deployment (fully automatic) — when discussing your own pipeline with a team.
  • Don't treat CI/CD as a substitute for good tests — it's an amplifier of whatever testing discipline already exists, for better or worse.
  • Start with CI (automated build and test) before adding automated deployment — get the foundation trustworthy first.

🎯 Key Takeaway

  • CI/CD replaces error-prone manual steps with an automatic, repeatable process.
  • Continuous Integration catches problems early, while a change is still small.
  • Continuous Delivery keeps a human approval gate before release; Continuous Deployment removes it entirely.
  • A pipeline is only as trustworthy as the tests running inside it.

🛠️ Try It Yourself

Write down, step by step, exactly how your own project (or a hypothetical one) currently gets from "code changed" to "running in production." Circle every step that depends on a specific human remembering to do something correctly — those are exactly the steps CI/CD exists to replace.

Interview Questions

What's the actual difference between Continuous Delivery and Continuous Deployment?▾
Continuous Delivery means every change that passes the pipeline is automatically prepared and ready to release, but a human still has to manually trigger the actual release. Continuous Deployment goes one step further — the change is automatically released to real users with no human approval step at all. The distinction is specifically whether a human gate exists before production.
Why doesn't having a CI pipeline automatically mean a team is protected from shipping broken code?▾
A CI pipeline automates whatever build and test process already exists — if the tests themselves are weak, missing, or don't cover the actual failure modes that matter, the pipeline will run them quickly and consistently, but still let broken code through. CI/CD amplifies the existing testing discipline; it doesn't create testing discipline on its own.
Why is manual deployment considered risky even if it's worked fine for months?▾
Manual deployment depends on a specific person correctly remembering and executing every step, every time, with no automated check that nothing was skipped or done differently. It working fine for months doesn't mean it's safe — it means no one has yet made the mistake, been unavailable at a critical moment, or hit an edge case the manual process wasn't designed to handle.
Why might a team choose Continuous Delivery over Continuous Deployment, even though Deployment is "more automated"?▾
More automation isn't automatically better if the team doesn't yet have enough confidence in their pipeline's tests to trust every passing change with zero human review. Continuous Delivery keeps a deliberate human checkpoint before production, which is often the right, more cautious choice while a team is still building trust in their automated testing — moving to full Continuous Deployment can come later, once that trust is genuinely earned.
In the phrase "Developer → Commit → Build → Test → Deploy," what happens if the Test stage is skipped or extremely weak?▾
The pipeline still runs quickly and "successfully," but the Deploy stage becomes a much riskier bet — you're now automatically shipping code that's only been confirmed to build, not confirmed to actually work correctly. This is exactly the mistake of confusing "we have a pipeline" with "we're safe" — the test stage is what makes everything after it trustworthy.
