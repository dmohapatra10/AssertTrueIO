Matrix + Automation Testing

Prerequisites: Parallel Execution & the Performance Challenge

What is this?

Beyond sharding the same tests across runners, a matrix has a second, genuinely distinct automation-testing use: running the exact same test suite against multiple different real configurations — multiple browsers, multiple target environments — connecting directly to this site's Playwright and RestAssured tracks.

Cross-Browser Testing With Playwright

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        browser: [chromium, firefox, webkit]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npx playwright install --with-deps ${{ matrix.browser }}
      - run: npx playwright test --project=${{ matrix.browser }}

This is genuinely different from sharding — each matrix combination here runs the entire test suite, just against a different browser engine. A real UI bug that only manifests in WebKit (Safari's engine) but not Chromium would be invisible without this kind of cross-browser matrix.

Multi-Environment API Testing With RestAssured

jobs:
  api-tests:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        environment: [staging, qa]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '17', distribution: 'temurin' }
      - run: mvn test -Denv=${{ matrix.environment }}
        env:
          API_KEY: ${{ secrets[format('API_KEY_{0}', matrix.environment)] }}

The same suite of RestAssured API tests runs against two genuinely different environments, each with its own environment-specific secret — secrets[format(...)] dynamically constructs the secret name based on the current matrix value, a genuinely useful pattern once you have per-environment credentials that follow a consistent naming convention.

Detailed Example — Combining Cross-Browser AND Sharding Together

strategy:
  fail-fast: false
  matrix:
    browser: [chromium, firefox]
    shard: [1, 2, 3]

# Produces 2 browsers × 3 shards = 6 total jobs:
# chromium/shard-1, chromium/shard-2, chromium/shard-3,
# firefox/shard-1, firefox/shard-2, firefox/shard-3
- run: npx playwright test --project=${{ matrix.browser }} --shard=${{ matrix.shard }}/3

These two matrix dimensions genuinely combine — this isn't an either/or choice. A real, mature Playwright CI pipeline often does exactly this: both testing across browsers and sharding within each browser for speed, exactly the full depth this site's Playwright track explores in its own dedicated CI/CD coverage.

🧠 Think About It

Why is cross-browser testing genuinely different in purpose from sharding, even though both use the same matrix mechanism? Sharding splits the same tests across runners purely for speed — every shard is checking for the same bugs, just faster in aggregate. Cross-browser testing runs the complete suite multiple times, specifically because a bug can genuinely exist in one browser's rendering or JavaScript engine and not another's — the goal isn't speed, it's coverage of real, different runtime environments.

⚠️ Common Mistake

Assuming that if tests pass on Chromium, they've been meaningfully verified across "the browser" generically. Real browser engines have genuine differences in rendering, JavaScript execution, and API support — a test suite that only ever runs against one engine has a real, meaningful gap in coverage for any project whose actual users use multiple browsers.

💡 Quick Tip

The secrets[format('API_KEY_{0}', matrix.environment)] pattern shown above is a genuinely useful trick for any matrix dimension with a corresponding, consistently-named secret per value — worth remembering whenever a matrix needs to pull different credentials for different combinations.

Best Practices

  • Use cross-browser or cross-environment matrices specifically for genuine coverage concerns, not performance — that's what sharding is for.
  • Combine sharding and cross-browser/cross-environment dimensions when a real pipeline genuinely needs both speed and coverage.
  • Follow a consistent secret-naming convention per environment when using dynamic secret lookup via format().

🎯 Key Takeaway

  • Cross-browser and multi-environment matrices run the complete test suite multiple times, for genuine coverage of real differences — a different purpose from sharding's speed focus.
  • Matrix dimensions can genuinely combine — cross-browser and sharding together produce a full cross product of both.
  • Dynamic secret lookup via secrets[format(...)] is a real, practical pattern for per-environment credentials in a matrix.

Interview Questions

Why is cross-browser testing considered a genuinely different use of a matrix than sharding, even though both use the same underlying mechanism?▾
Sharding splits the same tests across runners purely to reduce total wall-clock time — every shard is looking for the same bugs, just running fewer of them each. Cross-browser testing runs the entire test suite multiple times, specifically because a real bug can exist in one browser engine's rendering or JavaScript behavior and not another's — the goal is genuine coverage of different real environments, not speed.
Can a matrix combine a cross-browser dimension with a sharding dimension in the same workflow?▾
Yes — matrix dimensions genuinely combine, producing every combination of both. A matrix with 2 browsers and 3 shards produces 6 total jobs, each testing one specific browser with one specific portion of the test suite, achieving both genuine cross-browser coverage and the speed benefit of sharding simultaneously.
Why might testing only against Chromium leave a genuine, meaningful gap in a project's real test coverage?▾
Different browser engines have real, genuine differences in how they render pages and execute JavaScript — a bug that only manifests in WebKit (Safari's engine) or Firefox's engine would be completely invisible to a test suite that only ever runs against Chromium. For any project whose actual users use multiple browsers, this represents a real coverage gap, not just a theoretical concern.
What does the secrets[format('API_KEY_{0}', matrix.environment)] pattern actually accomplish?▾
It dynamically constructs the name of the secret to retrieve based on the current matrix value — for a matrix.environment value of "staging", this would look up a secret named API_KEY_staging. This is genuinely useful when different matrix combinations need different, consistently-named credentials, avoiding the need to write separate, hardcoded logic for each possible environment value.
