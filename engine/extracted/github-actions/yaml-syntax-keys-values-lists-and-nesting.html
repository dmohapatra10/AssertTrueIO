YAML Syntax: Keys, Values, Lists & Nesting

Prerequisites: What is YAML? Why GitHub Actions Uses It

What is this?

This page covers every core YAML building block you'll actually use in a GitHub Actions workflow — key-value pairs, strings, booleans, lists, nesting, and comments — each with a real workflow example, not an abstract one.

Key-Value Pairs

name: My Workflow
on: push

The most basic unit — a key, a colon, a space, then a value. The space after the colon is required; name:My Workflow (no space) is actually invalid YAML.

Strings

name: My Workflow          # no quotes needed for most simple strings
description: "Runs tests"  # quotes are fine too, and sometimes necessary

Most strings don't need quotes at all. Quotes become necessary specifically when a value could otherwise be misread — starting with a special character, containing a colon, or being a value that looks like another YAML type (like the word true or a number).

Booleans and Numbers

fail-fast: false
max-parallel: 4

YAML recognizes true/false and plain numbers automatically, without quotes — this matters because "false" (quoted) and false (unquoted) are technically different types, string versus boolean, even though they look almost identical.

Lists

branches: [main, develop]

# equivalent, written as a multi-line list instead:
branches:
  - main
  - develop

A list can be written inline with square brackets, or as multiple lines each starting with a dash. Both mean exactly the same thing — the multi-line form is generally preferred once a list has more than a couple of items, purely for readability.

Nesting via Indentation

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "step 1"

Each deeper level of indentation means "this belongs to the thing above it." build: belongs to jobs:; runs-on: and steps: both belong to build:; the step belongs to steps:. Indentation amount is your choice (2 spaces is the near-universal convention), but it must be consistent at each level.

Comments

name: My Workflow  # this is a comment, ignored entirely
# a comment can also take a whole line by itself

A # starts a comment that runs to the end of the line — genuinely useful for explaining why a specific workflow setting exists, not just what it does.

Detailed Example — Every Building Block in One Real Workflow

name: ShopEasy CI              # string (key-value)
on:
  push:
    branches: [main, develop]  # list, inline form
jobs:
  test:                        # nested under jobs
    runs-on: ubuntu-latest     # string
    strategy:
      fail-fast: false         # boolean
      max-parallel: 4          # number
    steps:                     # list, multi-line form
      - uses: actions/checkout@v4
      - run: npm test

Every single syntax rule from this page appears somewhere in this one realistic example — this is genuinely the complete vocabulary; more complex workflows just combine these same few ideas at greater depth.

🧠 Think About It

Why does fail-fast: false (unquoted) behave differently from fail-fast: "false" (quoted) if they look almost identical? The unquoted version is a genuine boolean value; the quoted version is a string containing the four characters f-a-l-s-e. Depending on what GitHub Actions expects for that specific setting, sending the wrong type can cause a subtle, confusing failure that has nothing to do with your actual intent.

⚠️ Common Mistake

Forgetting the required space after a colon. name:My Workflow (no space) isn't merely bad style — it's invalid YAML, and will fail to parse. This one is easy to miss visually, especially in a font where colons and following characters sit close together.

💡 Quick Tip

When in doubt about whether a value needs quotes, quoting a string never hurts — "main" and main mean the same thing for an ordinary string. Quotes only become meaningfully different from no-quotes for booleans, numbers, and a handful of special characters.

Best Practices

  • Use 2-space indentation consistently — it's the near-universal convention for GitHub Actions YAML, making files instantly familiar to any other contributor.
  • Prefer the multi-line list form once a list has more than two or three items — genuinely easier to scan and to add to later.
  • Use comments to explain why a non-obvious setting exists, not to restate what a self-explanatory line already says.

🎯 Key Takeaway

  • A key-value pair always needs a space after the colon.
  • Lists can be written inline with brackets or as multiple dash-prefixed lines — both are equivalent.
  • Indentation depth expresses "belongs to" relationships — it must be consistent, though the exact number of spaces is your choice (2 is conventional).
  • Quoted and unquoted values aren't always identical — false and "false" are genuinely different types.

🛠️ Try It Yourself

Write a small YAML snippet (not a full workflow, just the data structure) representing a recipe: a name (string), a prep time in minutes (number), whether it's vegetarian (boolean), and a list of at least three ingredients. Use the multi-line list form for the ingredients.

Interview Questions

Why is a space after the colon required in a YAML key-value pair?▾
YAML's parser specifically uses "colon followed by a space" as the signal that separates a key from its value — without that space, the parser can't reliably distinguish where the key ends and the value begins, which is why name:My Workflow (no space) is actually invalid YAML rather than just unconventional formatting.
What's the practical difference between writing a YAML list inline with brackets versus as multiple dash-prefixed lines?▾
Both forms represent exactly the same data — a list of items — and are functionally identical to whatever parses the YAML. The choice between them is purely about readability: inline brackets are compact and fine for a short list, while the multi-line dash form scales better and stays easier to scan once a list grows to more than a couple of items.
Why can fail-fast: false and fail-fast: "false" behave differently even though they look almost the same?▾
Without quotes, false is interpreted as a genuine boolean value. With quotes, "false" is interpreted as a string containing those four characters. Depending on what a specific GitHub Actions setting expects to receive, supplying the wrong type (a string where a boolean was expected, or vice versa) can cause unexpected behavior that has nothing to do with the actual value you intended.
Does the exact number of spaces used for indentation matter in YAML, as long as it's consistent?▾
The specific number of spaces per indentation level is a matter of convention rather than a strict YAML rule — what genuinely matters is that indentation is consistent at each given level throughout the file. Two spaces per level is the near-universal convention for GitHub Actions workflows, chosen for consistency and readability rather than being a technical requirement.
When does a YAML string actually need to be wrapped in quotes?▾
Most ordinary strings don't need quotes at all. Quotes become necessary when a value could otherwise be misinterpreted — starting with certain special characters, containing a colon that could be confused with a key-value separator, or being a value that would otherwise be read as a different type entirely, like the word true or a plain number.
