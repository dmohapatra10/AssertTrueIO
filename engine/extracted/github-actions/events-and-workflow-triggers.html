Every Workflow So Far Has Used the Simplest Possible Trigger

Every example up to this point used on: push — the simplest, least filtered trigger there is. Real projects need more precision: run tests on every pull request, run a nightly regression suite on a schedule, but only deploy when someone deliberately decides to. Five focused pages:

  1. What is a GitHub Actions Event? — the concept underlying everything else in this chapter
  2. Push & Pull Request Triggers — the two most common events, plus branch filtering
  3. Manual Workflows: workflow_dispatch — triggering a workflow deliberately, on demand
  4. Scheduled Workflows & Cron — running something automatically on a schedule
  5. Advanced Triggers — other repository events worth knowing about

The ShopEasy Scenario This Chapter Builds Toward

Requirement: "Run tests on every pull request, run a nightly regression
              suite every night, and only deploy manually."

This single sentence actually requires three different trigger types — pull_request, schedule, and workflow_dispatch — combined thoughtfully in one project. By the end of this chapter, you'll be able to build exactly this.

Common Mistakes to Watch For

  • Using on: push with no branch filtering, triggering a workflow on every branch in the repository, far more often than actually intended.
  • Assuming a workflow can only have one trigger — a single workflow can respond to several different event types at once.
  • Reaching for a scheduled workflow when a manual trigger was actually what was needed, or vice versa — these solve genuinely different problems.
