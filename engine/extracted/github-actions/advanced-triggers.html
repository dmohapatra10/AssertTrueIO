Advanced Triggers

Prerequisites: Scheduled Workflows & Cron

What is this?

Push, pull request, manual, and scheduled triggers cover the vast majority of real-world needs — but GitHub Actions supports many other repository events for more specialized situations. This page introduces the ones worth actually knowing exist.

release — Reacting to a Published Release

on:
  release:
    types: [published]

Fires when a GitHub release is created (or, with the right types filter, specifically when it's published). Genuinely useful for automating a release announcement, publishing a package, or building final release artifacts — actions that specifically belong to "we just shipped a version," distinct from every regular push.

issues — Reacting to Issue Activity

on:
  issues:
    types: [opened]

Fires on issue-related activity — here, specifically when a new issue is opened. Useful for automatically labeling new issues, posting a welcome comment, or routing issues based on their content — automation around project management itself, not code.

workflow_run — Reacting to Another Workflow's Completion

on:
  workflow_run:
    workflows: ["CI Pipeline"]
    types: [completed]

Fires when a different, named workflow finishes running — letting you chain workflows together, where one only starts after another has genuinely completed. This is a real, different mechanism from job dependencies within a single workflow (covered in Chapter 9) — this connects entirely separate workflow files.

repository_dispatch — External Systems Triggering a Workflow

on: repository_dispatch

Lets something outside GitHub entirely — another system, a custom script, a webhook — trigger a workflow via GitHub's API. Useful when the actual triggering event lives in a completely different system that GitHub itself has no native way to observe.

Detailed Example — Choosing the Right Trigger for a Real Scenario

Scenario: "When we publish a new release, automatically build and
           upload the release binaries."

Wrong tool: on: push — this would trigger on every ordinary commit,
            not specifically on releases.

Right tool: on: release: types: [published] — fires exactly when
            it should, and only then.

🧠 Think About It

Why is workflow_run genuinely different from simply adding more jobs to the same workflow file? workflow_run connects two entirely separate, independently-maintained workflow files — useful when different teams own different workflows, or when a downstream process genuinely belongs to a conceptually different pipeline, rather than being just another stage of the same one.

⚠️ Common Mistake

Reaching for an exotic trigger like repository_dispatch or workflow_run when a simpler trigger would have worked fine. These advanced triggers solve genuinely specific problems (external systems, cross-workflow chaining) — using one where push, pull_request, or a job dependency (Chapter 9) would have been simpler adds real, often unnecessary complexity.

💡 Quick Tip

GitHub's own documentation maintains the complete, current list of every supported event and its available types filters — since this list occasionally grows, it's worth checking directly rather than relying purely on memory for a genuinely uncommon event type.

Best Practices

  • Default to the simpler, more common triggers (push, pull_request, workflow_dispatch, schedule) unless a real requirement genuinely needs something more specialized.
  • Use release specifically for release-time automation — distinct from ordinary code changes.
  • Reach for workflow_run only when genuinely connecting separate, independently meaningful workflows, not as a substitute for job dependencies within one workflow.

🎯 Key Takeaway

  • release reacts to a published release, distinct from ordinary commits.
  • issues enables automation around project management, not code changes.
  • workflow_run chains separate workflow files together; repository_dispatch lets external systems trigger a workflow via the API.

Interview Questions

Why would a team use the release event instead of push to automate building release binaries?▾
push fires on every ordinary commit, which would trigger the release-building automation constantly, not just when an actual release happens. The release event (filtered to published) fires specifically at the moment a release is genuinely published, making it the precise, correct trigger for automation that should only run at that specific point, not on every regular code change.
How does workflow_run genuinely differ from simply adding a dependent job within the same workflow file?▾
workflow_run connects two entirely separate workflow files, where one triggers only after another, independently-defined and independently-maintained workflow has completed. A dependent job (using needs:, covered in a later chapter) exists within a single workflow file, coordinating jobs that were designed together from the start. workflow_run is for genuinely separate pipelines; job dependencies are for coordinating steps within one.
What kind of situation specifically calls for repository_dispatch rather than one of the more common triggers?▾
repository_dispatch is for situations where the actual triggering event happens entirely outside GitHub — in another system, service, or custom script — that then needs to trigger a GitHub Actions workflow via GitHub's API. None of the other triggers can respond to something GitHub itself has no native way of observing, which is exactly the gap repository_dispatch fills.
Why is defaulting to simpler, more common triggers generally better than reaching for an advanced one by default?▾
Advanced triggers like workflow_run and repository_dispatch solve genuinely specific problems and add real complexity — extra configuration, another moving piece to understand and maintain. Using one where a simpler trigger (push, pull_request, or a job dependency within a single workflow) would have worked just as well adds unnecessary complexity without any corresponding benefit.
Why might the issues event be useful for automation that has nothing to do with actual code?▾
GitHub Actions isn't limited to code-related automation — the issues event enables automating project management activities themselves, like automatically labeling a new issue based on its content or posting a welcome comment. This reflects that GitHub Actions is a genuinely general automation platform responding to repository events broadly, not just a CI/CD-specific tool limited to code changes.
