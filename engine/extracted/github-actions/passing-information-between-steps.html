Passing Information Between Steps

Prerequisites: Job Dependencies: needs: In Depth

What is this?

Chapter 6 previewed reading a step's output via steps.<id>.outputs.<name>, without showing how that output actually gets produced in the first place. This page covers the real mechanism: $GITHUB_OUTPUT.

Why do we need it?

Chapter 5 established that a plain shell variable set in one step doesn't survive into a later, separate step — each step is its own shell invocation. $GITHUB_OUTPUT is GitHub Actions' own dedicated mechanism specifically for genuinely passing a value across that step boundary.

Producing a Step Output

- id: get_version
  run: echo "version=1.2.3" >> $GITHUB_OUTPUT

id: get_version names this step so it can be referenced later. The run command writes name=value into the special $GITHUB_OUTPUT file — this isn't printing to the log; it's writing to a file GitHub Actions itself reads afterward.

Reading a Step Output Elsewhere

- run: echo "The version is ${{ steps.get_version.outputs.version }}"

This works in any later step within the same job — the id from the producing step, plus .outputs.<name>, retrieves exactly the value that was written.

Producing Multiple Outputs From One Step

- id: build_info
  run: |
    echo "version=1.2.3" >> $GITHUB_OUTPUT
    echo "commit=$(git rev-parse --short HEAD)" >> $GITHUB_OUTPUT

A single step can write as many separate outputs as needed, each read later as steps.build_info.outputs.version and steps.build_info.outputs.commit respectively.

Detailed Example — A Real, Practical Use

steps:
  - id: get_version
    run: echo "version=$(node -p "require('./package.json').version")" >> $GITHUB_OUTPUT

  - name: Tag the release
    run: echo "Tagging release v${{ steps.get_version.outputs.version }}"

  - name: Notify
    run: echo "Deployed version ${{ steps.get_version.outputs.version }} to production"

The version is read once, directly from the project's own package.json, then reused consistently across two later steps — genuinely more reliable than hardcoding the version separately in multiple places, or trying to pass it through a plain shell variable that wouldn't actually survive between these steps.

🧠 Think About It

Why does $GITHUB_OUTPUT use a special file rather than something simpler, like just printing the value to standard output? A file-based mechanism keeps a step's actual output cleanly separated from its ordinary log output (which might contain many other lines of genuinely unrelated text) — GitHub Actions can reliably parse exactly the name=value pairs written to this specific file, without needing to guess which line of a step's potentially large log output was actually meant to be a genuine output value.

⚠️ Common Mistake

Forgetting the id: on the producing step. Without it, there's no name to reference — steps.<nothing>.outputs.<name> doesn't work, since id is specifically what makes a step's outputs addressable at all.

💡 Quick Tip

A step output's value is always a string, even if it looks numeric — the same type consideration that applies to __ENV values and environment variables generally. If a later step genuinely needs a number, it may need explicit conversion depending on context.

Best Practices

  • Always give a step a clear, descriptive id when it produces something later steps will reference.
  • Use $GITHUB_OUTPUT specifically for genuinely small, simple values — a version number, a computed flag — not for large content, which belongs in an artifact instead.
  • Prefer computing a value once and reading it via output in later steps, rather than recomputing the same thing redundantly in each step that needs it.

🎯 Key Takeaway

  • $GITHUB_OUTPUT is the dedicated mechanism for passing a value from one step to a later step within the same job.
  • A step needs an id to be addressable; outputs are read via steps.<id>.outputs.<name>.
  • A single step can produce multiple named outputs by writing multiple lines to $GITHUB_OUTPUT.

🛠️ Try It Yourself

Write a step that reads the current date and writes it as an output named build_date, and a later step that uses that output in an echo statement — confirming for yourself that this genuinely works across the step boundary, unlike a plain shell variable would.

Interview Questions

Why can't a plain shell variable be used to pass a value from one step to a later step, the way $GITHUB_OUTPUT can?▾
Each step is its own separate shell invocation, and a plain shell variable only exists within the process that step's shell runs in — it doesn't persist once that step completes. $GITHUB_OUTPUT is GitHub Actions' own dedicated mechanism specifically designed to survive across that step boundary, which an ordinary shell variable was never designed to do.
Why is the id: field on a step required for its outputs to be readable later?▾
The steps.<id>.outputs.<name> syntax needs an actual name to reference which step's outputs are being retrieved — without an explicit id, there's no way to address that specific step's outputs from elsewhere in the workflow. The id is what makes a step's outputs genuinely retrievable at all.
Why does GitHub Actions use a dedicated file mechanism ($GITHUB_OUTPUT) rather than parsing a step's regular log output for values?▾
A step's ordinary log output can contain many lines of genuinely unrelated text, making it unreliable to guess which line was actually meant to be a real output value. Writing explicitly to a dedicated file keeps the actual output data cleanly separated from general log noise, letting GitHub Actions reliably parse exactly the intended name=value pairs.
Can a single step produce more than one named output?▾
Yes — a step can write multiple separate name=value lines to $GITHUB_OUTPUT, each becoming its own independently retrievable output. Later steps can reference each one individually using steps.<id>.outputs.<name> with the specific name that corresponds to the value they need.
Why might reading a version number once via a step output be more reliable than hardcoding it separately in multiple steps?▾
Hardcoding the same value in multiple places creates a real risk of the values drifting out of sync if one instance is updated but another is missed. Computing it once and reading it consistently via a step output from a single source of truth (like the project's own package.json) ensures every step referencing it always sees the same, currently-correct value.
