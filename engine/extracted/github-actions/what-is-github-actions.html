What is GitHub Actions?

Prerequisites: What is CI/CD?

What is this?

GitHub Actions is GitHub's built-in automation platform — it lets you run code automatically in response to things happening in your repository, like a push, a pull request, or a schedule. It's genuinely general-purpose: testing is a common use, but it can build, deploy, send notifications, or run almost any automated task.

Why do we need it?

Without it, ShopEasy's team would need a completely separate service just to run automated tests and deployments — something to watch the repository for changes, something to actually execute the build, somewhere to see the results. GitHub Actions lives directly inside the same platform the code already lives in, with no separate service to set up.

The Vocabulary, With Analogies

Each of these terms is genuinely simple once you have the right mental picture — the confusion usually comes from encountering them all at once, in DevOps-flavored jargon, with no everyday comparison.

  • Workflow — the whole automated process, defined in one YAML file. Like a recipe — the complete set of instructions for making one dish.
  • Event — whatever triggers the workflow to start, like a push or a pull request. Like the moment you decide to start cooking — a guest arriving, a specific time of day.
  • Job — one distinct stage of the workflow, which can run independently. Like one stage of cooking — preparing the sauce, separate from grilling the meat.
  • Step — one single instruction inside a job. Like one line in the recipe — "chop the onions," "add to the pan."
  • Runner — the actual machine that executes the job's steps. Like the kitchen itself — the physical place where the cooking happens.
  • Action — a pre-built, reusable step someone else already wrote, that you can just use. Like a pre-made sauce you buy instead of making from scratch — someone already solved this specific small problem.

Detailed Example — Naming Every Piece in a Real Scenario

ShopEasy scenario: "Whenever someone pushes code, automatically run the tests."

Event:    the push itself
Workflow: the YAML file describing the whole automated process
Job:      "run-tests" — one distinct stage
Steps inside that job: "check out the code," "install dependencies," "run the tests"
Runner:   the actual GitHub-provided machine executing those steps
Action:   a reusable step like "check out the code" that GitHub already provides,
          so you don't write that logic yourself

🧠 Think About It

Why might you want two separate jobs — say, "run-tests" and "build-app" — instead of putting every single step into one giant job? Jobs can run independently and even in parallel, and if one job's steps have nothing to do with another's, splitting them lets GitHub potentially run them at the same time, and lets a failure in one be understood without wading through unrelated steps.

⚠️ Common Mistake

Assuming an "action" (a reusable step someone else built) is the only way to do anything in a workflow. A huge amount of real workflow logic is just plain shell commands — actions are for genuinely reusable, common tasks (checking out code, setting up a language runtime); your own project-specific logic is often just a regular command, no action needed.

💡 Quick Tip

You don't need to memorize every term perfectly before moving on — the mental model above (push → workflow → runner → job → steps) is the one shape that everything else in this course builds on. If a later page mentions a term that feels fuzzy, it's worth coming back here.

Best Practices

  • Reach for an existing, well-maintained action for common tasks (checking out code, setting up a language) rather than reinventing that logic yourself.
  • Split genuinely independent work into separate jobs, especially once a workflow starts doing several unrelated things.
  • Get comfortable with the six core terms (workflow, event, job, step, runner, action) before worrying about anything more advanced — they're the foundation every later chapter assumes.

🎯 Key Takeaway

  • A workflow is the whole automated process; an event is what starts it.
  • A job is one independent stage; a step is one instruction inside that stage.
  • A runner is the actual machine doing the work; an action is a reusable step someone else already built.

Interview Questions

What's the practical difference between a job and a step in GitHub Actions?▾
A job is a distinct, independently-runnable stage of a workflow — like preparing a sauce as one stage of cooking. A step is one single instruction inside a job, like one line in a recipe. Jobs can run in parallel with each other by default (unless configured otherwise), while steps within a single job always run in order, one after another.
What is a runner, and why does a workflow need one?▾
A runner is the actual machine — physical or virtual — that executes a job's steps. Just as a recipe needs an actual kitchen to be cooked in, a workflow's steps need an actual computer to run on; the runner is that computer, whether it's a machine GitHub provides or one an organization manages itself.
Why would you use an action instead of writing a shell command yourself?▾
An action is a pre-built, reusable step someone has already written and tested for a common task — like checking out repository code or setting up a specific language runtime. Using it means not reinventing and re-testing that same logic yourself; it's the same reasoning as buying a pre-made sauce instead of making one from scratch when the sauce itself isn't the interesting or unique part of your dish.
What actually triggers a workflow to start running?▾
An event — something happening in the repository that the workflow is configured to respond to, like a push, a pull request being opened, or a scheduled time being reached. Without a matching event, a workflow file just sits in the repository, defined but never actually triggered.
Why might a team split "run tests" and "build the application" into two separate jobs rather than one combined job?▾
If the two tasks are genuinely independent of each other, separate jobs can potentially run in parallel, reducing overall pipeline time, and a failure in one is easier to understand in isolation without needing to read through an unrelated task's steps mixed into the same job. Splitting work into distinct jobs is a deliberate design choice once tasks don't actually depend on each other's output.
