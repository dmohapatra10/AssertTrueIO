Using Actions: uses:, with:, and run vs. uses

Prerequisites: Running Shell Commands: The run: Key

What is this?

uses: runs a pre-built, reusable action instead of a plain command — actions/checkout@v4 has appeared in nearly every example so far. This page covers how it actually works, and — genuinely important — exactly when to reach for it instead of run:.

The Basic Syntax

- uses: actions/checkout@v4

This references a specific action (actions/checkout), published by a specific owner (actions, GitHub's own official organization), at a specific version (@v4).

Passing Inputs With with:

- uses: actions/setup-node@v4
  with:
    node-version: 20

with: passes configuration into the action — here, telling setup-node which Node.js version to install. Each action defines its own specific set of accepted inputs, documented on its own page (usually on the GitHub Marketplace or the action's own repository).

Version Pinning — Why @v4 Matters

- uses: actions/checkout@v4        # a major version tag — gets minor updates automatically
- uses: actions/checkout@v4.1.1    # an exact version — never changes
- uses: actions/checkout@main      # the action's own main branch — genuinely risky

Pinning to a major version tag (like @v4) is the common, sensible default — you get bug fixes and minor improvements automatically, without unexpected breaking changes. Pinning to @main (or any other branch) means your workflow could break the moment the action's own maintainer pushes an unrelated change — genuinely risky for anything beyond quick experimentation.

The Real Decision: run vs. uses

Detailed Example — Applying the Decision Directly

Task 1: "Get the repository's code onto the runner."
Decision: uses: actions/checkout@v4
Why: This exact problem is universally common, and GitHub's own
     official action handles every edge case correctly already.

Task 2: "Print a custom deployment summary specific to ShopEasy."
Decision: run: echo "Deployed ShopEasy version $VERSION to $ENVIRONMENT"
Why: This is genuinely project-specific logic that no general-purpose
     action could reasonably anticipate or handle for you.

🧠 Think About It

Why might pinning to an exact version (@v4.1.1) rather than a major version tag (@v4) sometimes be the right choice, even though it means missing automatic minor updates? For a workflow where absolute reproducibility genuinely matters — a regulated environment, a release pipeline where any unexpected change is a real risk — trading away convenient automatic updates for guaranteed, exact reproducibility can be a deliberate, correct choice.

⚠️ Common Mistake

Pinning an action to a branch name (like @main) instead of a version tag. This means your workflow's behavior can change unexpectedly whenever the action's maintainer pushes anything to that branch — completely outside your own control, and often without any warning at all.

💡 Quick Tip

The GitHub Marketplace is a searchable catalog of publicly available actions — before writing custom logic with run: for a genuinely common task, it's worth a quick search there first; there's a real chance someone has already built and maintained exactly what you need.

Best Practices

  • Default to a well-maintained existing action for common, well-understood tasks — checking out code, setting up a language runtime, uploading an artifact.
  • Pin actions to a major version tag by default; consider an exact version pin specifically when reproducibility is a genuine, deliberate requirement.
  • Never pin a third-party action to a branch name — only to a proper, immutable version reference.

🎯 Key Takeaway

  • uses: runs a pre-built action; with: passes configuration into it.
  • Version pinning matters — major version tags balance safety and convenience; branch names are genuinely risky.
  • The real decision between run: and uses: comes down to whether your task is common enough that someone else has already solved it well.

Interview Questions

What's the real, practical basis for deciding between run: and uses: for a given step?▾
The decision comes down to whether the task is common and well-understood enough that a well-maintained existing action already solves it correctly, versus whether it's specific enough to your own project that no general-purpose action could reasonably anticipate it. Common infrastructure tasks (checking out code, setting up a language) favor uses:; project-specific logic favors run:.
Why is pinning an action to a branch name like @main considered genuinely risky?▾
A branch name is not a fixed, immutable reference — it points to whatever the latest commit on that branch happens to be at any given moment. If the action's maintainer pushes any change to that branch, every workflow pinned to it picks up that change immediately and automatically, with no warning, potentially breaking previously-working workflows through no action of your own.
What's the practical tradeoff between pinning to a major version tag (@v4) versus an exact version (@v4.1.1)?▾
A major version tag automatically incorporates bug fixes and minor, non-breaking improvements as the action's maintainer releases them, offering convenience with reasonable safety. An exact version pin never changes at all, offering complete reproducibility at the cost of needing to manually update the pin yourself to receive any fixes or improvements — the right choice depends on how much a workflow specifically values reproducibility versus staying automatically current.
Why does with: exist as a separate key from uses:, rather than passing configuration directly on the uses: line?▾
Separating with: as its own key lets an action accept a genuinely flexible, potentially large set of named inputs in a clear, structured way — each input clearly labeled with its own name and value, rather than trying to encode multiple pieces of configuration into a single line. This structure also matches how the action's own documentation describes its accepted inputs, making it straightforward to look up and apply.
Why would checking the GitHub Marketplace before writing custom run: logic for a common task be a reasonable first step?▾
A genuinely common task — setting up a specific tool, uploading a specific kind of report, integrating with a specific external service — has a real chance of already being solved by a well-maintained, widely-used action published on the Marketplace. Checking first can save real time writing and testing custom logic that essentially reinvents something the broader community has already built, tested, and maintained.
