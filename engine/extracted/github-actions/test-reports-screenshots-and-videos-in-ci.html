Test Reports, Screenshots & Videos in CI

Prerequisites: Downloading Artifacts & Passing Data Between Jobs

What is this?

Test artifacts — an HTML report, a failure screenshot, a recorded video — are arguably the single most valuable, most commonly used application of everything covered in this chapter. This page applies the upload pattern specifically to automation test output, tying directly into this site's Playwright track.

Publishing a Playwright HTML Report

- name: Run Playwright tests
  run: npx playwright test

- name: Upload Playwright report
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: playwright-report
    path: playwright-report/
    retention-days: 14

The if: always() here is genuinely essential, not optional — without it, a failing test stops the job (default fail-fast behavior from Chapter 4), and the upload step never runs at all, meaning the exact run that most needed investigating leaves no report behind whatsoever.

Screenshots and Videos on Failure

- name: Upload failure screenshots
  if: failure()
  uses: actions/upload-artifact@v4
  with:
    name: failure-screenshots
    path: test-results/**/*.png

if: failure() (rather than always()) specifically uploads only when something genuinely failed — appropriate here, since screenshots are typically only generated on failure in the first place, so uploading them unconditionally wouldn't find anything to upload on a successful run anyway.

Detailed Example — A Complete Playwright CI Job

jobs:
  ui-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npx playwright install --with-deps
      - name: Run tests
        run: npx playwright test
      - name: Upload report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 14

🧠 Think About It

Why might a team specifically set retention-days: 14 rather than leaving the artifact at whatever the repository's default retention is? Test reports genuinely accumulate — dozens of runs a day across an active project — and most are never actually looked at again once a run is confirmed passing. A shorter, deliberate retention period for test reports specifically balances "keep it long enough to investigate a recent failure" against "don't accumulate an unbounded amount of rarely-needed storage."

⚠️ Common Mistake

Forgetting if: always() on a test report upload step, then discovering — precisely during the incident where it would have mattered most — that no report was ever actually published, because the default fail-fast behavior skipped the upload step entirely.

💡 Quick Tip

Uploaded HTML reports (like Playwright's) can be downloaded and opened locally, but some teams additionally deploy them to a genuinely browsable location (like GitHub Pages) for easier access without needing to download and unzip an artifact first — worth considering for a team that reviews test reports frequently.

Best Practices

  • Always use if: always() for test reports specifically — a report from a failing run is often the most valuable one.
  • Use if: failure() for artifacts (like screenshots) that are genuinely only meaningful or only generated when something went wrong.
  • Set a deliberate, shorter retention period for high-volume test artifacts rather than relying on a long default.

🎯 Key Takeaway

  • if: always() is essential for test report uploads — without it, a failing run's most valuable evidence never gets published.
  • if: failure() is appropriate specifically for artifacts that only exist or matter when something failed.

Interview Questions

Why is if: always() specifically essential for a test report upload step, rather than optional polish?▾
By default, a failing step stops the rest of a job's remaining steps, which would mean the report-upload step never runs at all when tests actually fail. Since a failing run's report is often exactly the one worth investigating, if: always() ensures the upload happens regardless of the test outcome, rather than silently skipping it in precisely the situation where it matters most.
Why would if: failure() be more appropriate than if: always() for uploading failure screenshots specifically?▾
Failure screenshots are typically only generated by the test framework when something actually fails in the first place — on a successful run, there's usually nothing to upload. Using if: failure() correctly reflects this reality, only attempting the upload when it's actually meaningful, rather than running unconditionally and finding nothing there on successful runs.
Why might a team set a shorter, explicit retention period specifically for test report artifacts?▾
Test reports accumulate quickly in an active project with many runs per day, and most are never revisited once a run is confirmed successful. A deliberately shorter retention period balances keeping recent reports available long enough to investigate a failure against not accumulating an ever-growing, rarely-needed volume of stored artifacts over time.
Why does this page connect to the Playwright track's own GitHub Actions coverage rather than fully repeating it?▾
The Playwright track already covers its own complete CI/CD pipeline in depth, including topics like test sharding and multi-browser execution strategies that go beyond this chapter's general artifact-publishing focus. This page's role is applying this chapter's general artifact concepts specifically to test reporting, then pointing to the deeper, framework-specific coverage that already exists rather than duplicating it.
Why might some teams deploy an uploaded HTML test report to a location like GitHub Pages instead of only relying on the artifact itself?▾
An artifact must be downloaded and unzipped before an HTML report can actually be viewed, which adds friction for a team that reviews test reports frequently. Deploying the same report to a genuinely browsable location provides immediate, direct access without that extra download-and-extract step, which can matter for a team's actual day-to-day workflow around reviewing test results.
