What is a Matrix? Testing Multiple Versions & OSes

Prerequisites: Matrix Builds & Parallel Execution overview

What is this?

A matrix runs the same job definition multiple times, automatically, once for each combination of values you specify — instead of writing five nearly-identical jobs by hand, you describe the variation once and let GitHub Actions generate every combination.

Real-World Analogy

Think of ordering coffee with size and milk options — small/medium/large, crossed with regular/oat/almond milk. Rather than writing out all nine possible orders individually, you just specify the two dimensions (size, milk) and every combination is understood automatically. A matrix works exactly this way with build or test configurations.

Testing Multiple Node.js Versions

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: [18, 20, 22]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
      - run: npm ci
      - run: npm test

This single job definition actually runs three times — once each for Node 18, 20, and 22 — with ${{ matrix.node-version }} substituting the current value each time. GitHub's Actions tab shows all three as separate, individually-tracked runs.

Testing Multiple Operating Systems

jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test

Note that runs-on itself now reads from the matrix — this job genuinely runs on three different operating systems, not just three times on the same one.

Combining Two Dimensions

strategy:
  matrix:
    node-version: [18, 20, 22]
    os: [ubuntu-latest, windows-latest]

This produces every combination of the two dimensions — 3 Node versions × 2 operating systems = 6 total jobs, all running in parallel by default.

Detailed Example — Why This Genuinely Matters for ShopEasy

❌ Without a matrix — 6 nearly-identical, copy-pasted jobs:
jobs:
  test-node18-ubuntu: [...]
  test-node20-ubuntu: [...]
  test-node22-ubuntu: [...]
  test-node18-windows: [...]
  test-node20-windows: [...]
  test-node22-windows: [...]

✅ With a matrix — one job definition, same 6 actual runs:
jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      matrix:
        node-version: [18, 20, 22]
        os: [ubuntu-latest, windows-latest]
    steps: [...]

Both produce the exact same six actual test runs — but the matrix version is one job definition to read, maintain, and update, rather than six separately-drifting copies.

🧠 Think About It

Why might a team genuinely need to test against multiple Node.js versions rather than just testing against whatever version their own developers happen to use locally? If ShopEasy is a published library or package other teams depend on, those consumers might run different Node versions than ShopEasy's own developers — testing across multiple versions catches a genuine compatibility problem before it reaches someone else's project, not just before it reaches your own.

⚠️ Common Mistake

Copy-pasting a job multiple times for each variation instead of using a matrix. Beyond the redundant typing, copy-pasted jobs genuinely drift apart over time — a fix applied to one copy is easy to forget applying to the others, exactly the kind of duplication problem a matrix eliminates entirely.

💡 Quick Tip

A matrix dimension isn't limited to versions or operating systems — it can be any set of values genuinely relevant to your testing needs (a set of API endpoints, a set of configuration flags, a set of target environments) — the mechanism is generic, even though version and OS are the two most common real-world uses.

Best Practices

  • Use a matrix whenever you'd otherwise copy-paste a job for each variation of a value.
  • Reference matrix values through ${{ matrix.<dimension> }} everywhere the job's behavior should actually change per combination.
  • Remember that combining multiple matrix dimensions multiplies the total number of actual jobs — two dimensions of 3 and 4 values produce 12 total runs, not 7.

🎯 Key Takeaway

  • A matrix runs the same job definition once per combination of specified values, generated automatically.
  • Multiple dimensions multiply together — every combination of every dimension's values gets its own actual job run.
  • This replaces error-prone, drifting copy-pasted jobs with one maintained definition.

Interview Questions

How many actual job runs does a matrix with 3 Node versions and 2 operating systems produce?▾
Six total runs — a matrix produces every combination of its specified dimensions, multiplying together rather than adding. Three Node versions combined with two operating systems means each Node version gets tested on each operating system, resulting in 3 × 2 = 6 distinct job runs.
Why might a published library or package specifically need matrix testing across multiple language versions, more so than an internal-only application?▾
A published package is used by other teams and projects that may run genuinely different versions of the language than the package's own developers use locally. Testing across multiple versions catches compatibility problems before they reach an external consumer's project, which matters far less for an internal application where the actual runtime version is fully controlled by the same team building it.
Why does copy-pasting a job multiple times for each configuration variation create a genuine, ongoing maintenance risk?▾
Copy-pasted jobs are separate, independent definitions that can easily drift apart over time — a bug fix or configuration change applied to one copy is easy to forget applying to the others, since nothing enforces they stay in sync. A matrix expresses the same variation through one maintained job definition, eliminating this drift risk entirely.
In a matrix testing across operating systems, why does runs-on need to reference ${{ matrix.os }} rather than a fixed value?▾
If runs-on were fixed to a single value like ubuntu-latest, every matrix combination would still run on Ubuntu regardless of what the matrix's os dimension specified, defeating the actual purpose of testing across different operating systems. Referencing ${{ matrix.os }} lets each generated job actually use the specific operating system value for that particular combination.
Is a matrix dimension limited to only versions or operating systems?▾
No — a matrix dimension can be any set of values genuinely relevant to a project's testing needs, such as a set of configuration flags, target environments, or API endpoints. Versions and operating systems are simply the two most common real-world examples, but the underlying mechanism works generically with any set of values a job's behavior should vary across.
