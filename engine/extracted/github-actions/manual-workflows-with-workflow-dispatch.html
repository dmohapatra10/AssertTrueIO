Manual Workflows: workflow_dispatch

Prerequisites: Push & Pull Request Triggers

What is this?

workflow_dispatch is an event that lets a human deliberately trigger a workflow on demand, from GitHub's own interface — no push, no pull request, no schedule, just a person deciding "run this now."

Why do we need it?

Not everything should run automatically. Deploying to production is the classic example: you generally don't want that happening automatically on every push, even if every automated check passed — a genuine human decision to deploy right now is often exactly what's wanted instead.

Real-World Analogy

Think of a manual fire alarm pull station versus an automatic smoke detector — most safety systems should react automatically, but some actions genuinely need a deliberate human decision at the exact right moment, not an automatic trigger. Deployment to production is often that kind of action.

The Basic Syntax

on: workflow_dispatch

This alone adds a "Run workflow" button, visible in the repository's Actions tab, for this specific workflow — clicking it triggers a run immediately, with no other event needed.

Adding Input Parameters

on:
  workflow_dispatch:
    inputs:
      environment:
        description: 'Which environment to deploy to'
        required: true
        default: 'staging'
        type: choice
        options:
          - staging
          - production

Inputs let the person triggering the workflow provide real information at the moment they trigger it — here, a dropdown choosing between staging and production, shown directly in GitHub's "Run workflow" interface.

Using an Input Inside the Workflow

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying to ${{ github.event.inputs.environment }}"

The value the person actually selected is accessible via github.event.inputs.<name> — this specific expression syntax (${{ }}) is covered properly in Chapter 6, but this is a genuine, working preview of what it looks like in practice.

Detailed Example — A Real Manual Deployment Workflow

name: Deploy ShopEasy
on:
  workflow_dispatch:
    inputs:
      environment:
        description: 'Target environment'
        required: true
        default: 'staging'
        type: choice
        options: [staging, production]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "Deploying ShopEasy to ${{ github.event.inputs.environment }}"
      # real deployment steps would go here

This directly satisfies the third part of ShopEasy's original requirement — deployment happens only when someone deliberately clicks "Run workflow" and picks an environment, never automatically.

🧠 Think About It

Why might a workflow combine workflow_dispatch with other events, rather than using it exclusively? A workflow can genuinely have more than one trigger — for instance, running tests automatically on every push, and also being manually runnable on demand for a one-off situation, like re-running a diagnostic check without needing to make a new commit just to trigger it.

⚠️ Common Mistake

Forgetting that workflow_dispatch only shows the "Run workflow" button once the workflow file itself has already been merged into the repository's default branch — a workflow file that only exists on a feature branch typically won't show this manual trigger option until it reaches the branch GitHub considers default.

💡 Quick Tip

Input types beyond choice include string (free text), boolean (a checkbox), and environment (picks from configured GitHub Environments, covered in Chapter 12) — pick whichever genuinely matches the kind of value you need from the person triggering the run.

Best Practices

  • Reach for workflow_dispatch specifically for actions that genuinely warrant a deliberate human decision at the moment of triggering, not as a default for everything.
  • Use meaningful input descriptions and sensible defaults — the person triggering the workflow should understand exactly what each input controls without needing to read the YAML.
  • Combine workflow_dispatch with other triggers when a workflow genuinely serves both an automated and an on-demand purpose.

🎯 Key Takeaway

  • workflow_dispatch adds a manual "Run workflow" trigger, visible in the Actions tab.
  • Inputs let the person triggering a run supply real values at that moment — choices, text, booleans.
  • The workflow file needs to exist on the repository's default branch before the manual trigger button appears.

Interview Questions

Why might production deployment specifically be a good candidate for a manual, workflow_dispatch-triggered workflow rather than an automatic one?▾
Deploying to production is often a decision that genuinely warrants deliberate human judgment at a specific moment — even if every automated check has passed, a team may want a person to consciously decide "deploy now," rather than having it happen automatically the instant checks succeed. workflow_dispatch is specifically designed for this kind of deliberate, on-demand action.
How does a value entered through a workflow_dispatch input actually get used inside the workflow's steps?▾
The value is accessed through an expression using the github.event.inputs.<name> syntax, wrapped in ${{ }}. This lets a step reference whatever the person triggering the workflow actually selected or typed at that moment, making the workflow's behavior dynamic based on that specific manual trigger.
Can a single workflow file combine workflow_dispatch with an automatic trigger like push?▾
Yes — a workflow can be configured to respond to multiple event types at once. This is useful when the same underlying logic (like running a diagnostic check) should both happen automatically on certain triggers and also be available for a person to run manually on demand, without needing two separate workflow files.
Why might the "Run workflow" button not appear for a workflow file that was just added on a feature branch?▾
GitHub typically only surfaces the manual workflow_dispatch trigger button for workflow files that exist on the repository's default branch. A workflow file sitting only on a feature branch, not yet merged, generally won't show this option in the Actions tab until it actually reaches the default branch.
What's the practical purpose of setting a default value on a workflow_dispatch input, like defaulting environment to "staging"?▾
A sensible default reduces the chance of an accidental mistake — someone triggering the workflow without thinking carefully gets the safer option (staging) unless they deliberately choose otherwise (production). It's a small design choice that meaningfully reduces the risk of an unintended production action triggered by an oversight.
