Conditional Jobs & Failure Handling

Prerequisites: Passing Information Between Jobs

What is this?

Chapter 6 introduced success(), failure(), and always(). This page completes the picture — the full set of status values a job or step can actually have, and designing real pipeline behavior around all of them deliberately, not just the two obvious ones.

The Complete Status Vocabulary

success   — completed without error
failure   — completed, but something went wrong
cancelled — someone or something stopped it before it finished
skipped   — never ran at all, because a condition prevented it

needs.<job>.result can be any of these four — not just success or failure. Designing conditional logic that only accounts for two of the four is a genuinely common, incomplete approach.

continue-on-error — Allowing a Step to Fail Without Stopping the Job

- name: Run experimental linter
  run: npm run experimental-lint
  continue-on-error: true

Normally, a failing step stops the rest of the job (Chapter 4's default). continue-on-error: true overrides this for one specific step — genuinely useful for something like an experimental or non-critical check that shouldn't block the entire pipeline if it fails.

Checking Whether a Dependency Was Skipped

if: needs.optional-check.result == 'skipped' || needs.optional-check.result == 'success'

This deliberately treats "skipped" the same as "success" for this specific decision — appropriate when a job being skipped (because its own condition wasn't met) shouldn't itself block something downstream, distinct from that job having genuinely run and failed.

Detailed Example — The Real Pipeline, With Deliberate Failure Handling

jobs:
  build:
    runs-on: ubuntu-latest
    steps: [...]

  unit-tests:
    needs: build
    runs-on: ubuntu-latest
    steps: [...]

  api-tests:
    needs: build
    runs-on: ubuntu-latest
    steps: [...]

  ui-tests:
    needs: build
    runs-on: ubuntu-latest
    steps: [...]

  deploy:
    needs: [unit-tests, api-tests, ui-tests]
    if: needs.unit-tests.result == 'success' && needs.api-tests.result == 'success' && needs.ui-tests.result == 'success'
    runs-on: ubuntu-latest
    steps: [...]

  notify:
    needs: [unit-tests, api-tests, ui-tests, deploy]
    if: always()
    runs-on: ubuntu-latest
    steps:
      - run: echo "Pipeline finished — check individual job results for details"

This is the complete, real pipeline from this chapter's hub page, now with deliberate failure handling: deploy explicitly requires all three test categories to have genuinely succeeded (not just completed), and notify runs regardless of what happened anywhere else in the pipeline — exactly the always-run pattern from Chapter 6, now applied at the job level across an entire multi-job pipeline.

🧠 Think About It

Why might deploy's condition explicitly check each test job's result individually, rather than just relying on needs: alone to prevent it from running after a failure? As covered back in Chapter 6, needs: alone only establishes order, not a success requirement — without the explicit if: check here, deploy would still attempt to run even if one of the three test jobs had genuinely failed, since GitHub Actions doesn't automatically skip a dependent job just because a dependency failed.

⚠️ Common Mistake

Writing conditional logic that only distinguishes success and failure, forgetting that "skipped" and "cancelled" are genuinely different, real states a dependency can be in. A job's result being skipped (because an earlier condition wasn't met) is a fundamentally different situation from that same job actually running and failing — treating them identically can produce incorrect pipeline behavior.

💡 Quick Tip

continue-on-error: true on a step still shows that step's actual failure in the log and in the job's summary — it doesn't hide the failure, it just prevents that specific failure from stopping the rest of the job. This distinction matters: the failure is still visible and worth investigating, just not blocking.

Best Practices

  • Design conditional logic accounting for all four possible states — success, failure, cancelled, and skipped — not just the two most obvious ones.
  • Use continue-on-error: true deliberately for genuinely non-blocking checks, not as a way to silence a failure that should actually be addressed.
  • Combine if: always() at the job level with an explicit result check when a "notify regardless of outcome" job needs to also report what actually happened.

🎯 Key Takeaway

  • A job or step's result can be success, failure, cancelled, or skipped — four genuinely distinct states, not just two.
  • continue-on-error: true lets a specific step fail without stopping the rest of its job, while still showing that failure clearly.
  • A real pipeline's deploy and notify logic should account for the complete status vocabulary, not just the success case.

Interview Questions

What are the four possible result values a job or step can have, beyond just success and failure?▾
The complete set is success, failure, cancelled, and skipped. Cancelled means something stopped the job or step before it finished (like a manual cancellation), while skipped means it never ran at all because a condition prevented it from starting. Designing conditional logic around only success and failure misses these two genuinely distinct states.
Why does a deploy job need an explicit if: condition checking each dependency's result, rather than relying on needs: alone to prevent deployment after a test failure?▾
needs: only establishes execution order — it ensures deploy waits for its dependencies to finish, but doesn't automatically prevent deploy from running if one of those dependencies actually failed. An explicit if: condition checking that every dependency's result equals 'success' is what genuinely enforces that deployment only proceeds after real success, not just after completion.
What does continue-on-error: true actually do, and what does it NOT do?▾
It allows a specific step to fail without stopping the rest of that job's remaining steps from running — overriding the default fail-fast behavior for just that one step. It does NOT hide or suppress the failure itself; the step's actual failure is still visible in the log and job summary, just no longer blocking subsequent steps.
Why might treating a skipped dependency the same as a failed one produce incorrect pipeline behavior?▾
A skipped job never actually ran — often because its own condition legitimately wasn't met, which may be entirely expected and fine. A failed job genuinely ran and encountered a real problem. Treating these identically could incorrectly block a downstream job in a situation where a dependency being skipped was actually the correct, intended outcome, not a problem requiring the same response as a genuine failure.
Why does the notify job in the pipeline example use if: always() combined with needs: on every other job?▾
if: always() ensures notify runs regardless of what happened in any other job — success, failure, or otherwise — which is exactly the intended behavior for a job whose entire purpose is reporting the pipeline's outcome no matter what that outcome actually was. Combining it with needs: on the relevant jobs ensures notify still waits for them to genuinely finish first, so it has real, final results to actually report on.
