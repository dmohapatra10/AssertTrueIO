Going Deeper Than the Vocabulary

Chapter 1 introduced jobs, steps, and runners as terms, with the recipe analogy. This chapter is where that vocabulary becomes real, working knowledge — exactly what actually executes, in what order, on what machine, and the genuine, practical difference between running a plain command and using someone else's pre-built action. Four focused pages:

  1. Jobs & Steps: The Execution Model in Depth — what actually happens, in what order, and what a job failure does to the rest of a run
  2. GitHub-Hosted Runners & runs-on — the actual machines your steps run on, and how to pick one
  3. Running Shell Commands: The run: Key — plain commands, multi-line scripts, and shell selection
  4. Using Actions: uses:, with:, and run vs. uses — reusable steps, and the real decision between the two

Every step in this diagram is either a plain command (run:) or a pre-built action (uses:) — this chapter's final page exists specifically to make that choice a deliberate one, not a guess.

Common Mistakes to Watch For

  • Assuming a runner comes with everything pre-installed that a project might need — GitHub-hosted runners have a genuinely large but still finite set of pre-installed tools.
  • Reaching for a custom action when a plain shell command would have been simpler, or vice versa — reaching for a raw command when a well-maintained action already solves the exact problem.
  • Not realizing each job gets a completely fresh runner — nothing from one job automatically carries over to another without deliberate effort (covered fully in a later chapter on job dependencies and data flow).

What You'll Be Able to Do

By the end of the four pages that follow, you should be able to explain exactly what happens when a job runs, choose an appropriate GitHub-hosted runner for a given project, write both simple and multi-line shell steps correctly, and make a deliberate, informed choice between a plain command and a reusable action.
