Job Dependencies: needs: In Depth

Prerequisites: Job Dependencies, Conditions & Data Flow overview

What is this?

By default, every job in a workflow runs in parallel (established back in Chapter 1's mental model). needs: is the deliberate override — it makes a job wait for one or more other jobs to finish first.

A Single Dependency

jobs:
  build:
    runs-on: ubuntu-latest
    steps: [...]

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps: [...]

deploy won't even start until build has finished — this is the exact pattern already used in earlier chapters for artifact download and conditional deployment.

Multiple Dependencies

jobs:
  build: [...]
  unit-tests: [...]
  api-tests: [...]

  deploy:
    needs: [build, unit-tests, api-tests]
    runs-on: ubuntu-latest
    steps: [...]

deploy now waits for all three listed jobs to finish — not just one. This is genuinely different from three separate single-dependency chains; all three run in parallel with each other, and deploy waits for the slowest of them.

Detailed Example — Deciding What's Actually Parallel in the Real Pipeline

jobs:
  build:
    runs-on: ubuntu-latest
    steps: [...]

  unit-tests:
    needs: build
    runs-on: ubuntu-latest
    steps: [...]

  api-tests:
    needs: build          # runs in PARALLEL with unit-tests — both only need build
    runs-on: ubuntu-latest
    steps: [...]

  ui-tests:
    needs: build           # ALSO runs in parallel with the other two
    runs-on: ubuntu-latest
    steps: [...]

  deploy:
    needs: [unit-tests, api-tests, ui-tests]   # waits for ALL THREE
    runs-on: ubuntu-latest
    steps: [...]

This is genuinely different from the hub page's simple linear diagram — unit-tests, api-tests, and ui-tests all only depend on build, not on each other, so they run in parallel once build finishes. deploy is the only job that needs to wait for all three. This structure finishes noticeably faster than a strict sequential chain, without sacrificing any genuine ordering requirement.

🧠 Think About It

Why is deliberately identifying genuine independence between jobs (rather than just chaining everything sequentially "to be safe") worth the extra thought? A strictly sequential chain of five jobs takes the sum of all five durations. The parallelized version above takes roughly build + the slowest of the three test jobs + deploy — often a significant, real time savings, especially as a pipeline grows more test jobs over time.

⚠️ Common Mistake

Adding needs: between two jobs that don't actually have a genuine dependency, purely out of caution. This needlessly serializes work that could have run in parallel, slowing the pipeline down for no real correctness benefit — needs: should reflect an actual, genuine requirement, not a defensive habit.

💡 Quick Tip

A job with needs: runs by default only if every job it depends on succeeded — this default (and how to deliberately override it, for instance to run cleanup regardless of outcome) is covered fully on this chapter's final page.

Best Practices

  • Base needs: relationships on genuine data or ordering requirements, not caution — ask "does this job actually need something the other one produces or guarantees?"
  • Look for genuine independence between jobs (like separate test suites that don't depend on each other) and let them run in parallel.
  • Use a list (needs: [job1, job2]) when a job genuinely depends on more than one other job finishing first.

🎯 Key Takeaway

  • needs: overrides the default parallel-jobs behavior, making a job wait for one or more specific others.
  • Multiple dependencies run in parallel with each other; the dependent job waits for the slowest of them.
  • Deliberately identifying genuine independence between jobs can meaningfully reduce a pipeline's total runtime.

🛠️ Try It Yourself

For a pipeline with a lint job, a build job, a unit-tests job (needing build), and an integration-tests job (needing build), sketch out (in plain English) which jobs could run in parallel with each other and which must wait, assuming lint is genuinely independent of everything else.

Interview Questions

What does needs: [build, unit-tests, api-tests] actually require before the dependent job starts?▾
The dependent job waits until all three listed jobs have finished — not just one of them. Those three jobs themselves run in parallel with each other (assuming no dependency exists between them), and the dependent job specifically waits for whichever of the three takes the longest to complete.
Why might a pipeline with three independent test jobs, each only depending on a build job, finish faster than one with the same three jobs chained sequentially?▾
When each test job only depends on build (not on each other), all three can run simultaneously once build finishes, and the total added time is just the duration of the slowest one. A sequential chain instead adds up the full duration of every single job one after another, which takes meaningfully longer overall for no genuine correctness benefit.
Why is adding needs: between two jobs "just to be safe" considered a genuine mistake rather than harmless caution?▾
An unnecessary needs: relationship forces two genuinely independent jobs to run sequentially instead of in parallel, needlessly increasing the pipeline's total runtime without providing any real correctness benefit. needs: should reflect an actual, genuine requirement — one job truly depending on another's output or completion — not a defensive habit applied without real justification.
By default, does a job with needs: run if one of its dependencies fails?▾
By default, no — a job with needs: only runs if every job it depends on succeeded. This default behavior, and how to deliberately override it for situations like cleanup or notification jobs that should run regardless of outcome, is covered in full on the final page of this chapter.
In the real pipeline example on this page, why does deploy specifically need all three test jobs listed, rather than just one?▾
Deployment should genuinely only happen once every category of testing (unit, API, UI) has actually confirmed success — depending on only one of the three would mean deployment could proceed even if one of the other test suites hadn't finished or had failed, which defeats the purpose of running all three categories of tests before deploying in the first place.
