Composite Actions Explained

Prerequisites: Calling a Reusable Workflow with Inputs & Outputs

What is this?

A composite action bundles several steps into a single, reusable unit — used with uses:, exactly like any other action, but one you define yourself rather than a pre-built third-party one.

Why do we need it?

Some genuinely shared logic is smaller than a whole workflow — a specific setup sequence, a repeated multi-step pattern used across several jobs or workflows. A reusable workflow is a genuinely heavier tool for this; a composite action is the lighter-weight equivalent for step-level reuse.

Defining a Composite Action

# .github/actions/setup-project/action.yml
name: 'Setup Project'
description: 'Checks out code and sets up Node.js with caching'
inputs:
  node-version:
    description: 'Node.js version'
    required: false
    default: '20'
runs:
  using: 'composite'
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with:
        node-version: ${{ inputs.node-version }}
        cache: 'npm'
    - run: npm ci
      shell: bash

The genuinely distinguishing detail is runs: using: 'composite' — this tells GitHub Actions this action's actual logic is a sequence of steps, not a single script or a Docker container (other action types this course hasn't needed to cover).

Using a Composite Action

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: ./.github/actions/setup-project
        with:
          node-version: '18'
      - run: npm run build
      - run: npm test

Three steps — checkout, Node.js setup with caching, dependency install — collapsed into one, reusable line. Note the local path (./.github/actions/setup-project) — a composite action living in the same repository is referenced this way, rather than an org/repo@version reference used for a third-party or externally-shared action.

Detailed Example — Before and After

❌ Repeated in every job that needs this setup:
jobs:
  build:
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: 'npm' }
      - run: npm ci
      - run: npm run build
  test:
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: 'npm' }
      - run: npm ci
      - run: npm test

✅ The shared setup, extracted into one composite action:
jobs:
  build:
    steps:
      - uses: ./.github/actions/setup-project
      - run: npm run build
  test:
    steps:
      - uses: ./.github/actions/setup-project
      - run: npm test

The genuinely repeated checkout-setup-install sequence now lives in exactly one place — a fix or improvement to that shared setup only needs to happen once.

🧠 Think About It

Why does a composite action's own steps each need an explicit shell: (like shell: bash on the run step above), when an ordinary workflow step usually doesn't need to specify this? A composite action can genuinely be used across different operating systems and contexts, so it can't safely assume the same default shell an ordinary workflow step running directly on a known runner would have — being explicit here removes that ambiguity.

⚠️ Common Mistake

Forgetting that a composite action referenced locally (./.github/actions/...) needs the calling workflow to have already checked out the repository first — unlike a third-party action referenced by org/repo@version, a local composite action's own files need to physically exist on the runner, which only happens after actions/checkout has run.

💡 Quick Tip

A composite action's own action.yml file can itself be version-controlled and reviewed like any other code in the repository — genuinely useful for tracking exactly how a shared setup sequence has evolved over time, the same way any other meaningful code change would be reviewed.

Best Practices

  • Extract a composite action when the same small sequence of steps genuinely repeats across multiple jobs or workflows.
  • Always specify shell: explicitly on a composite action's own run steps, since it can't safely assume a specific default.
  • Remember a locally-referenced composite action requires the repository to already be checked out before it can be used.

🎯 Key Takeaway

  • A composite action bundles multiple steps into one reusable unit, defined with runs: using: 'composite'.
  • It's referenced with uses:, exactly like any other action — a local path for same-repository reuse, or org/repo@version for shared, external ones.
  • Composite action steps need explicit shell: specification, since they can't assume a specific default.

🛠️ Try It Yourself

For a repeated sequence of "checkout, set up Python 3.11, install dependencies from requirements.txt" used across several jobs, write the action.yml for a composite action that bundles this sequence.

Interview Questions

What does runs: using: 'composite' actually tell GitHub Actions about an action?▾
It specifies that this action's actual logic is defined as a sequence of ordinary steps, rather than a single script file or a Docker container (the other possible action types). This is what allows a composite action to bundle multiple checkout, setup, and command steps together into one reusable unit that other workflows can invoke with a single uses: line.
Why does a composite action's run steps need an explicit shell: specification, unlike most ordinary workflow steps?▾
A composite action is designed to be genuinely reusable across different workflows and potentially different operating systems, so it can't safely assume the same default shell an ordinary step running directly on a specific, known runner would have. Being explicit about the shell removes this ambiguity, ensuring the action behaves consistently regardless of where it's actually used.
Why does using a locally-defined composite action require the repository to already be checked out first?▾
A composite action referenced by a local path (like ./.github/actions/setup-project) needs its actual action.yml file and any associated files to physically exist on the runner's filesystem. Since a fresh runner starts with no code at all, actions/checkout must run first to bring the repository's files — including the composite action's own definition — onto the runner before it can be used.
What's the practical benefit of extracting a repeated three-or-four-step sequence into a composite action?▾
The repeated logic now exists in exactly one place rather than being duplicated across every job or workflow that needs it, meaning a fix or improvement only needs to be made once. This directly parallels the same duplication-avoidance reasoning behind matrices (for job-level repetition) and reusable workflows (for whole-workflow repetition), just applied at the smaller, step-sequence level.
How is a locally-defined composite action referenced differently from a third-party action published elsewhere?▾
A composite action living in the same repository is referenced by a local path, like ./.github/actions/setup-project, pointing to where its action.yml file actually lives within the checked-out repository. A third-party or externally-shared action is instead referenced by an org/repo@version pattern, pointing to a specific, separate repository and version rather than a local file path.
