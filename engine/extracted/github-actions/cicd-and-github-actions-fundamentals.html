CI/CD & GitHub Actions Fundamentals

Prerequisites: Basic Git/GitHub familiarity — no CI/CD or YAML experience required.

Understand Before You Automate

It's tempting to jump straight into writing YAML — copy a workflow file from somewhere, tweak it, hope it works. This chapter deliberately resists that. Before touching a single line of configuration, you should understand why CI/CD exists as an idea, and what GitHub Actions actually is as a system. Four focused pages:

  1. What is CI/CD? — the problem automated pipelines actually solve
  2. What is GitHub Actions? — workflows, events, jobs, steps, runners, actions — the vocabulary
  3. GitHub Actions Mental Model — how a push to GitHub actually becomes a running pipeline
  4. Your First GitHub Actions Workflow — a real, working workflow, from nothing

The Imaginary Project This Whole Course Uses

Throughout this tutorial, we're building CI/CD for ShopEasy — a small web application. The pipeline grows gradually as the course goes on:

Push Code → Run Tests → Build Application → Publish Artifact
→ Deploy to Test → Run Automation Tests → Deploy to Production

Right now, ShopEasy has no pipeline at all — every deploy is manual, error-prone, and depends entirely on someone remembering every step correctly. That's exactly the problem the next page exists to name properly.

Common Mistakes to Watch For

  • Copy-pasting a workflow file without understanding what it does — works until it doesn't, and then you have no idea why.
  • Confusing CI with CD — treating "we have a pipeline" as if it automatically means "we deploy automatically," when a huge number of real pipelines only cover the CI half.
  • Assuming GitHub Actions is just "a place to run tests" — it's a genuinely general automation platform; testing is one common use, not the whole picture.

What You'll Be Able to Do

By the end of the four pages that follow, you should be able to explain why CI/CD exists to someone who's never heard of it, correctly use the core GitHub Actions vocabulary (workflow, job, step, runner, action), trace exactly what happens between a git push and a running pipeline, and have a genuinely working workflow file committed to a real repository.
