Common YAML Mistakes That Break Workflows

Prerequisites: YAML Syntax: Keys, Values, Lists & Nesting

What is this?

This page is a deliberate collection of broken YAML — the specific mistakes responsible for a huge share of real "why won't my workflow even start" problems — each one shown broken, explained, and fixed.

🔍 Mistake 1 — Incorrect Indentation

jobs:
  build:
  runs-on: ubuntu-latest
    steps:
      - run: echo "hi"

runs-on is indented at the same level as build: instead of one level deeper — meaning it isn't recognized as belonging to the build job at all.

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "hi"

Fix: runs-on needs to be indented one level deeper than build:, matching steps:, since both are properties of the build job.

🔍 Mistake 2 — Missing Colon

name My Workflow
on: push

The colon after name is simply missing — without it, YAML has no way to know this line is meant to be a key-value pair at all.

name: My Workflow
on: push

Fix: add the colon (and the required space after it).

🔍 Mistake 3 — Incorrect List Syntax

steps:
  run: echo "hi"
  run: echo "bye"

Without the leading dash, these lines look like two key-value pairs both trying to use the same key (run) — not a list of two separate steps at all. This is invalid, and even if it were technically parseable, it wouldn't mean what was intended.

steps:
  - run: echo "hi"
  - run: echo "bye"

Fix: each list item needs its own leading dash.

🔍 Mistake 4 — Wrong Nesting Level

jobs:
  build:
    runs-on: ubuntu-latest
  steps:
    - run: echo "hi"

steps is indented at the same level as build:, making it a sibling of the build job rather than a property inside it — this defines a job with only runs-on and nothing else, plus a separate, meaningless top-level steps key that GitHub Actions doesn't know what to do with.

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "hi"

Fix: steps needs to be indented under build:, at the same level as runs-on.

🔍 Mistake 5 — Quoting Issues

run: echo "It's a great day"

Mixing quote types carelessly — a double-quoted string containing an unescaped apostrophe is usually fine in YAML, but the reverse (a single-quoted string containing an unescaped single quote) genuinely breaks, since YAML uses that same character to end the string early.

# This breaks — the apostrophe in "It's" prematurely ends the single-quoted string:
run: 'echo "It's a great day"'

# Fixed — use double quotes for the outer string instead:
run: echo "It's a great day"

Fix: be deliberate about which quote character wraps a string, especially when the string's own content contains a quote character of either kind.

⚠️ Common Mistake

Reading a YAML parse error and assuming it points to a logic problem with what you were trying to accomplish. These errors are almost always about the file's structure — indentation, a missing colon, a stray character — not about whether your intended automation makes sense.

💡 Quick Tip

Most online YAML validators (and your editor's built-in YAML support) can catch these exact mistakes before you even commit — pasting a suspicious snippet into a validator is often faster than staring at indentation trying to count spaces by eye.

🏆 Challenge

name: Broken Workflow
on push
jobs:
  test:
   runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - run npm test

This snippet has three separate mistakes from this page, all at once. Find and fix all three before reading further. (Hint: check the colon after "on", the indentation of "runs-on" and "steps", and the colon after "run" in the last step.)

Best Practices

  • When a workflow fails to even start (rather than failing partway through a step), suspect YAML structure first, not your actual logic.
  • Use the line and column number in a parse error message directly — it's usually precise enough to go straight to the problem.
  • Validate YAML with a linter or editor extension before committing, rather than discovering a formatting mistake only after pushing.

🎯 Key Takeaway

  • Indentation mistakes (wrong level, or a line indented at the same level as something it should belong to) are the single most common category of YAML failure.
  • A missing colon, missing space after a colon, or missing dash on a list item are all genuinely invalid YAML, not just bad style.
  • Parse errors point to structural problems, not logic problems — read them as "something about the file's shape is wrong," not "your intent is wrong."

Interview Questions

Why does a YAML parse error typically not mean there's a logic problem with what the workflow is trying to do?▾
A parse error means the YAML parser couldn't even successfully read the file's structure — it never got far enough to evaluate whether the intended automation makes sense. These errors are almost always caused by structural issues like incorrect indentation, a missing colon, or a missing list dash, which need to be fixed before the file can be parsed at all, regardless of what the workflow was actually meant to accomplish.
Why does writing two steps without a leading dash on each one fail, rather than just being unconventional?▾
Without the dash, YAML doesn't interpret the lines as separate list items — it reads them as key-value pairs, and having two lines attempt to use the identical key (like run) within the same mapping is invalid. The dash is the actual syntactic signal for "this is one item in a list," not an optional stylistic marker.
Why can mixing single and double quotes carelessly around a string containing an apostrophe cause a real problem?▾
YAML uses matching quote characters to mark where a quoted string begins and ends. If a string is wrapped in single quotes but its own content contains an unescaped single quote (like an apostrophe in a contraction), YAML interprets that apostrophe as the end of the string prematurely, breaking the intended value. Using double quotes for a string containing an apostrophe avoids this specific collision.
If a workflow fails immediately, before any step's log output even appears, what does that suggest about where to look for the problem?▾
A failure before any step output appears strongly suggests the YAML file itself couldn't be parsed successfully — the workflow never actually reached the point of executing any step. This points directly at the file's structure (indentation, missing colons, malformed lists) rather than anything about the actual commands or actions the steps were meant to run.
Why is checking the line and column number in a YAML parse error usually faster than re-reading the whole file?▾
YAML parsers generally report fairly precise location information about where parsing broke down, since that's where the file's structure stopped making sense to the parser. Going directly to that specific line and column is usually far faster than manually scanning an entire file for a subtle indentation or punctuation mistake, especially once a workflow grows to dozens of lines.
