What is YAML? Why GitHub Actions Uses It

Prerequisites: YAML Fundamentals for GitHub Actions overview

What is this?

YAML ("YAML Ain't Markup Language") is a human-readable data format used for configuration files across a huge range of tools — GitHub Actions, Docker Compose, Kubernetes, and many others all use it for exactly the same reason.

Why do we need it?

A workflow needs to describe structured information — a name, a list of steps, nested settings — in a way that's both machine-parseable and genuinely readable by a human without special tooling. YAML is designed specifically for that middle ground.

Real-World Analogy

Think of YAML like a well-organized outline you'd write by hand — headings, sub-points indented underneath, bullet lists where something has multiple items. You don't need special software to read a good outline; the structure is visible just from how it's laid out on the page. YAML applies that same idea to configuration a computer needs to parse.

YAML vs. JSON — The Same Information, Two Formats

// The same data, in JSON:
{
  "name": "My Workflow",
  "on": "push",
  "jobs": {
    "build": {
      "runs-on": "ubuntu-latest"
    }
  }
}
# The same data, in YAML:
name: My Workflow
on: push
jobs:
  build:
    runs-on: ubuntu-latest

Both represent identical structured data. YAML drops the braces, brackets, and most of the quotation marks, relying on indentation and line breaks instead — genuinely easier to read at a glance, especially once a file grows to dozens or hundreds of lines, which is exactly the situation a real CI/CD workflow eventually reaches.

Detailed Example — Why Readability Actually Matters Here

# A real, growing workflow — still readable specifically BECAUSE of YAML's format
name: CI Pipeline
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test

Even without knowing every specific key yet, this is genuinely readable just from its shape — you can see there's a checkout step, a Node.js setup step, then two commands. That readability is a direct, deliberate consequence of YAML's design, not an accident.

🧠 Think About It

If GitHub Actions had chosen JSON instead of YAML, workflows would still technically work — the underlying information is the same. What would genuinely be lost? Mostly readability and ease of hand-editing: JSON's mandatory braces, commas, and quotes add real visual noise for a human reading or writing the file, even though a computer parses either format equally well.

⚠️ Common Mistake

Assuming YAML is "just like" other config formats you might know (like .ini files or Python) and guessing at syntax rather than learning YAML's actual specific rules. YAML has genuine, precise syntax — most notably around indentation — that doesn't forgive guessing the way some more permissive formats do.

💡 Quick Tip

YAML files conventionally use a .yml or .yaml extension — both are valid and mean the same thing; GitHub Actions accepts either for workflow files.

Best Practices

  • Treat YAML's readability as a real asset, not just a stylistic preference — write workflows that stay genuinely easy to scan, not just technically valid.
  • Don't assume familiarity with another configuration format transfers directly — learn YAML's actual specific rules, covered in depth on the next page.
  • Either .yml or .yaml works for GitHub Actions files — pick one convention and stay consistent within a project.

🎯 Key Takeaway

  • YAML is a human-readable data format, chosen for GitHub Actions specifically for its readability at scale.
  • YAML and JSON can represent identical structured data — YAML just does it with less visual noise.
  • YAML's specific syntax rules (especially indentation) need to be learned properly, not guessed from other formats.

🛠️ Try It Yourself

Take a small JSON object you're familiar with (or write one) representing a person's name, age, and a list of hobbies, and manually convert it into YAML by hand, using the examples on this page as a reference.

Interview Questions

Why did GitHub Actions choose YAML over a format like JSON for workflow files?▾
YAML represents the same structured data as JSON with significantly less visual noise — no mandatory braces, brackets, or quotes for most values — relying instead on indentation and line breaks. This makes workflow files genuinely easier for a human to read and hand-edit, which matters enormously for a format people are expected to write and maintain directly, not just have a computer parse.
Can the same configuration data be represented in both YAML and JSON?▾
Yes — YAML and JSON can represent identical structured data; they're just different textual representations of the same underlying information (key-value pairs, nested structures, lists). The choice between them is about readability and ergonomics for humans, not about what kind of data can be expressed.
Why is it a mistake to assume YAML syntax rules transfer directly from a language like Python?▾
While both use indentation meaningfully, YAML has its own specific, precise syntax rules — around exactly how lists are denoted, how strings are quoted (or not), and how nesting levels work — that don't perfectly mirror any other single language. Assuming familiarity transfers directly, rather than learning YAML's actual rules, is a common source of subtle formatting mistakes.
Does it matter whether a GitHub Actions workflow file uses a .yml or .yaml extension?▾
No — both extensions are valid and are treated identically by GitHub Actions; they're simply two common conventions for the same file type. What matters is that the file itself contains valid YAML and lives in the correct .github/workflows/ folder, not which of the two equivalent extensions it uses.
Why might a workflow file's readability matter beyond just "looking nice"?▾
A workflow file is something real people need to read, understand, and safely modify over time, often under time pressure while debugging a failing pipeline. A genuinely readable structure — which YAML's design specifically supports — makes it faster to spot what a workflow actually does and where a problem might be, which is a real, practical benefit, not merely an aesthetic one.
