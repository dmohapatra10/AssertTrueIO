Jobs & Steps: The Execution Model in Depth

Prerequisites: Jobs, Steps & Runners overview

What is this?

Chapter 1 defined a job as "one distinct stage" and a step as "one instruction inside it." This page goes past the definition into what actually, mechanically happens — step order, what a failure does, and job isolation.

Steps Run Sequentially, Always

steps:
  - run: echo "first"
  - run: echo "second"
  - run: echo "third"

Unlike jobs (which can run in parallel by default), steps within a single job always execute strictly in order, one completing before the next begins. There's no parallel-steps concept within a job — if you need genuine parallelism, that happens at the job level, not the step level.

What Happens When a Step Fails

steps:
  - run: echo "step 1"
  - run: exit 1          # this step fails
  - run: echo "step 3"   # this step is SKIPPED, not run

By default, a failing step stops the rest of that job immediately — subsequent steps in the same job are skipped, and the whole job is marked as failed. This default can be changed (using continue-on-error, worth knowing exists even before its full depth is covered in a later chapter on failure handling), but the default is fail-fast within a job.

Job Isolation — Each Job Gets a Fresh Runner

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "hello" > message.txt
  test:
    runs-on: ubuntu-latest
    steps:
      - run: cat message.txt   # this FAILS — message.txt doesn't exist here

Each job runs on its own separate, fresh runner — nothing from one job's filesystem automatically exists in another's. This surprises people who assume jobs share an environment the way steps within one job do; they genuinely don't, by default. (Passing data or files between jobs deliberately is covered fully in a later chapter — this page is specifically about understanding why it doesn't happen automatically.)

Detailed Example — Tracing a Job That Partially Fails

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4     # ✅ succeeds
      - run: npm ci                    # ✅ succeeds
      - run: npm test                  # ❌ fails — tests don't pass
      - run: npm run build             # ⏭️ SKIPPED — never runs
      - run: echo "Build complete"     # ⏭️ SKIPPED — never runs

Result: the "test" job is marked FAILED, having stopped at the
        failing test step.

This is exactly the behavior worth expecting by default — a failed test step correctly prevents a build step from running afterward, since building on top of failing tests usually isn't meaningful.

🧠 Think About It

Why might job isolation (each job getting a completely fresh environment) actually be a genuinely good default, rather than an inconvenience? It prevents one job's leftover state — a stray file, a modified environment variable, a partially-installed dependency — from silently affecting another job's results. Each job starting clean means a job's outcome depends only on what it actually, deliberately did, not on accumulated side effects from something that happened to run before it.

⚠️ Common Mistake

Assuming that because steps within a job share state naturally, jobs must too. This is a genuinely common early misunderstanding — steps do share the same runner and filesystem throughout a single job, but that sharing stops entirely at the job boundary.

💡 Quick Tip

A step's name (an optional name: field) shows up directly in the Actions tab's log view — using descriptive step names makes reading through a long job's execution log significantly faster than relying on the raw command text alone.

Best Practices

  • Design steps within a job assuming strict, sequential order — never rely on later steps somehow running before earlier ones.
  • Don't assume any state automatically carries between jobs — treat each job as starting from a genuinely clean slate.
  • Use descriptive step names for anything beyond the most trivial single command, to make log-reading easier later.

🎯 Key Takeaway

  • Steps within a job always run sequentially — never in parallel with each other.
  • A failing step, by default, stops the rest of that job's remaining steps and marks the job failed.
  • Each job gets a completely fresh runner — nothing automatically carries over from one job to another.

🛠️ Try It Yourself

Write out (in YAML, without necessarily running it) a job with four steps where the second step deliberately fails (using something like run: exit 1), and predict exactly which of the remaining steps would actually execute versus be skipped, before checking your prediction against this page's explanation.

Interview Questions

Can two steps within the same job ever run in parallel with each other?▾
No — steps within a single job always execute strictly in sequential order, one completing before the next begins. Genuine parallelism in GitHub Actions happens at the job level (multiple jobs running simultaneously on separate runners), not at the step level within one job.
By default, what happens to the remaining steps in a job after one step fails?▾
By default, a failing step immediately stops execution of that job — every subsequent step is skipped, not run, and the entire job is marked as failed. This fail-fast behavior can be changed for specific steps using continue-on-error, but the default assumes that continuing past a failure usually doesn't make sense.
Why does a file created in one job typically not exist when a different job in the same workflow tries to read it?▾
Each job in a workflow runs on its own separate, freshly-provisioned runner — there's no shared filesystem between jobs by default. A file written during one job's steps exists only on that job's specific runner, which is discarded once the job completes; a different job has no access to it unless data is deliberately passed between jobs using a mechanism designed for that purpose.
Why might job isolation — each job starting completely fresh — actually be a beneficial design rather than a limitation?▾
Job isolation prevents leftover state from one job (a stray file, a modified environment variable, a partially completed install) from silently influencing a different job's outcome. This means each job's result depends only on what that job itself explicitly did, which makes a workflow's overall behavior far more predictable and easier to reason about than if jobs implicitly shared an environment.
In a job with five steps where the third one fails, how many total steps actually execute?▾
Three steps execute — the first two run normally, the third one runs and fails, and the fourth and fifth are both skipped as a direct consequence of the default fail-fast behavior within a job. The job as a whole is then marked as failed, reflecting that it didn't complete all of its intended steps.
