Self-Hosted Runners

Prerequisites: Advanced GitHub Actions & Production CI/CD overview

What is this?

A self-hosted runner is a machine you (or your organization) provide and maintain yourselves, rather than a GitHub-hosted virtual machine provisioned fresh for every job. It runs the exact same GitHub Actions runner software, just on infrastructure you control.

Why do we need it?

GitHub-hosted runners genuinely can't meet every real requirement — specific hardware (a GPU, for instance), access to a private internal network GitHub's own infrastructure has no route to, or license restrictions on certain software that require running on infrastructure the license holder controls.

Using a Self-Hosted Runner

jobs:
  build:
    runs-on: self-hosted   # instead of ubuntu-latest, windows-latest, etc.
    steps:
      - uses: actions/checkout@v4
      - run: npm test

Genuinely simple from the workflow's own perspective — the actual complexity lives entirely in setting up and maintaining the runner machine itself, not in the workflow YAML.

Real Advantages

  • Specific hardware — a GPU for machine learning workloads, specialized processors GitHub doesn't offer.
  • Private network access — reaching an internal service, database, or resource with no public route.
  • Cost, at genuine scale — for an organization running an enormous volume of CI minutes, self-hosted infrastructure can become more economical than paying per-minute for GitHub-hosted runners.
  • Persistent state between runs — a self-hosted runner isn't automatically destroyed after each job, which can genuinely help with some caching-heavy workloads (though this also introduces the risk covered below).

Real Risks

  • You own the security — GitHub-hosted runners are provisioned fresh and destroyed after every job; a self-hosted runner, left running, is a genuine, ongoing attack surface you're responsible for securing.
  • Persistent state can leak between runs — the exact "fresh runner every time" guarantee (Chapter 4) that keeps jobs isolated doesn't automatically hold for a self-hosted runner unless you deliberately maintain it.
  • Genuine, ongoing maintenance — someone has to keep the machine patched, updated, and actually running — this is real, ongoing operational work GitHub otherwise handles for you entirely.

Detailed Example — A Genuine, Justified Use Case

ShopEasy's actual scenario: their integration tests need to connect
to an internal database that lives on a private company network,
with no public internet route to it at all.

GitHub-hosted runner: genuinely CANNOT reach this database — no route exists.
Self-hosted runner (on the same private network): CAN reach it directly.

This is a genuinely justified case — no configuration change to a GitHub-hosted runner could solve this; the actual network topology requires infrastructure with real access to that private network.

🧠 Think About It

Why might a team decide against self-hosted runners even after establishing a genuine technical justification exists? The real, ongoing security and maintenance burden is a genuine cost, not a one-time setup task — a team needs to weigh whether that ongoing operational responsibility is actually worth taking on, versus finding another way to solve the underlying problem (like establishing a secure tunnel or gateway that a GitHub-hosted runner could use instead).

⚠️ Common Mistake

Reaching for self-hosted runners as a default "more control is always better" choice, without a genuine, specific requirement GitHub-hosted runners can't meet. This takes on real, ongoing security and maintenance responsibility for a benefit that, in many cases, GitHub-hosted runners would have provided just as well, with none of that operational burden.

💡 Quick Tip

A self-hosted runner used for a public repository carries genuine additional risk — anyone who can open a pull request against that repository could potentially get code to execute on your own infrastructure through a workflow triggered by that PR. GitHub's own documentation covers this specific risk and mitigation approaches in real depth, worth reviewing carefully before using self-hosted runners on a public repository.

Best Practices

  • Reach for self-hosted runners only after confirming a genuine, specific requirement GitHub-hosted runners truly can't meet.
  • Treat a self-hosted runner's security and maintenance as real, ongoing operational responsibility, not a one-time setup task.
  • Be especially cautious using self-hosted runners with public repositories, given the genuine risk of executing untrusted code from external contributors.

🎯 Key Takeaway

  • A self-hosted runner is infrastructure you provide and maintain, running the same GitHub Actions software as a GitHub-hosted one.
  • Genuine justifications include specific hardware, private network access, and cost at real scale — not general preference for control.
  • The real cost is ongoing security and maintenance responsibility that GitHub-hosted runners otherwise handle entirely.

🛠️ Try It Yourself

For each of these three scenarios, decide whether self-hosted runners are genuinely justified, and explain why: (1) a team wants slightly faster job startup times, (2) a team needs to run tests against a GPU-accelerated machine learning model, (3) a team is simply curious about self-hosted runners with no specific problem to solve.

Interview Questions

Why might a team need a self-hosted runner to reach an internal database with no public network route?▾
GitHub-hosted runners operate on GitHub's own infrastructure, with no route into a private, internal company network. A self-hosted runner, running on infrastructure that's actually part of (or has access to) that private network, can reach resources a GitHub-hosted runner structurally cannot, regardless of any workflow configuration.
What genuine security responsibility does a team take on by using self-hosted runners that GitHub-hosted runners otherwise handle automatically?▾
A GitHub-hosted runner is provisioned fresh and completely destroyed after every single job, providing genuine isolation and a clean state automatically. A self-hosted runner, left running across multiple jobs, requires the team to deliberately maintain its security and ensure state doesn't leak between runs — responsibilities GitHub otherwise handles entirely for hosted runners.
Why is using a self-hosted runner on a public repository considered a genuinely higher risk than on a private one?▾
Anyone who can open a pull request against a public repository can potentially trigger a workflow that executes code on the self-hosted runner's own infrastructure, depending on how the workflow and runner are configured. This means external, untrusted contributors could gain a path to executing something on infrastructure the organization actually owns and controls, a risk that doesn't exist the same way on a private repository with controlled contributors.
Why might cost only become a genuine justification for self-hosted runners "at scale," rather than for a small project?▾
GitHub-hosted runners are billed per minute of usage, which is often the most economical choice for a small or moderate volume of CI activity, given the maintenance-free convenience they provide. Self-hosted infrastructure requires real upfront and ongoing investment (hardware, maintenance, security) that only becomes cost-effective relative to per-minute billing once an organization's actual CI usage reaches a genuinely large volume.
Why should a team weigh the ongoing maintenance burden of self-hosted runners even after confirming a genuine technical need exists?▾
A genuine technical justification (like needing private network access) confirms self-hosted runners could solve the problem, but doesn't automatically mean they're the best solution — the real, ongoing security and maintenance cost is a separate, continuing consideration. A team might reasonably decide an alternative approach, like a secure gateway a GitHub-hosted runner could use, is worth exploring before committing to the ongoing operational responsibility self-hosted infrastructure requires.
