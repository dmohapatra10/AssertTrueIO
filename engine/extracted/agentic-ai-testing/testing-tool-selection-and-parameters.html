Testing Tool Selection and Parameters

Prerequisites: Testing Agent Planning

What is this?

Every single tool call an agent makes has two genuinely separate ways to go wrong — calling the WRONG tool entirely, or calling the RIGHT tool with WRONG parameters. Both need their own, distinct tests.

Testing Tool Selection — Did It Pick the Right Tool?

def test_tool_selection(observation_context, expected_tool_category, client):
    prompt = f"""Given this situation an agent is reasoning
about: {observation_context}

The agent has these tools available: click_element, fill_field,
get_page_text. Which tool SHOULD it use next, and does this
match the EXPECTED category: {expected_tool_category}?"""
    result = client.messages.create(
        model="claude-sonnet-4-6", max_tokens=200,
        messages=[{"role": "user", "content": prompt}]
    )
    return result.content[0].text

# A genuine test case:
test_tool_selection(
    observation_context="Currently on the login page, email "
        "field is empty, need to authenticate.",
    expected_tool_category="fill_field (to enter credentials)",
    client=client
)

Testing Tool Parameters — Called Correctly?

def test_tool_parameters(actual_tool_call, page_context):
    # This part is GENUINELY deterministic — checking whether
    # the SPECIFIC parameters used actually correspond to
    # something REAL on the page, exactly Chapter 5's own
    # AI Locator Selection verification approach
    if actual_tool_call["tool"] == "click_element":
        role = actual_tool_call["input"]["role"]
        name = actual_tool_call["input"]["name"]
        matches = page_context.locator(f"[role='{role}']", has_text=name)
        return {
            "valid": matches.count() >= 1,
            "issue": None if matches.count() >= 1 else
                f"No element found matching role='{role}', name='{name}'",
        }

A Genuine Case Where Selection Passes but Parameters Fail

Situation: on the checkout page, ready to place the order.

TOOL SELECTION check: PASSES — the agent correctly chose
  click_element (the right CATEGORY of tool for this situation).

TOOL PARAMETERS check: FAILS — it called click_element(role=
  'button', name='Place Order'), but the REAL page's button is
  actually labeled 'Confirm Purchase' — the RIGHT TOOL, called
  with a PARAMETER that doesn't correspond to anything real.

This is exactly why BOTH checks are genuinely necessary —
selection testing alone would have reported this as fully
correct, completely missing the real, parameter-level problem.

🧠 Think About It

Why does tool-parameter testing use deterministic, exact checking (locating a real page element) rather than an LLM reasoning about whether the parameters "seem right"? Whether a specific role and name combination matches a real, existing element on the actual page is a genuinely exact, checkable fact — exactly the same exact-vs-fuzzy distinction from Chapter 5 onward. Reasoning about whether parameters "seem plausible" would be strictly weaker than actually checking them against the real page, exactly the same principle that made Chapter 5's AI Locator Selection page use deterministic strategies rather than asking an LLM to guess whether a locator seems reasonable.

⚠️ Common Mistake

Testing only tool selection (did it choose the right category of action) without also testing tool parameters (did it call that tool with values that actually correspond to something real). This page's checkout example shows these are genuinely independent failure points — passing one doesn't confirm the other.

💡 Quick Tip

Tool-parameter testing can often reuse the exact same locator-verification logic already built into an agent's own tools (Chapter 5's find_and_click pattern) — if a tool call would have failed to find a matching element at execution time, that's the same signal this kind of test should also catch, just verified independently before or alongside actual execution.

Best Practices

  • Test tool selection and tool parameters as two genuinely separate checks — passing one never confirms the other.
  • Use exact, deterministic verification for parameters wherever a real, checkable fact exists (like whether an element genuinely exists), not LLM judgment about plausibility.
  • Reuse an agent's own tool-level verification logic where possible, rather than building entirely separate parameter-checking code.

🎯 Key Takeaway

  • Tool selection (right category of action) and tool parameters (correct values for that action) are genuinely independent failure points needing separate tests.
  • Parameter testing should use exact, deterministic verification against real page state wherever possible, not fuzzy plausibility judgment.
  • A tool call can pass selection testing while completely failing parameter testing, exactly this page's own checkout-button example.

Whether a specific role/name combination matches a REAL element is a genuinely exact, checkable fact — an LLM asked to judge "plausibility" would be doing STRICTLY WEAKER verification than actually checking against the real page, exactly the same reasoning Chapter 5 applied to locator strategy design.

What an LLM "does this SEEM correct" judgment could MISS:
"role='button', name='Place Order'" SOUNDS entirely plausible
  as a checkout button's parameters — an LLM with NO ACCESS to

  completely missing that the ACTUAL page uses different text.

What DETERMINISTIC lookup catches RELIABLY, every time:
matches.count() >= 1 — this DIRECTLY checks reality, not
  PLAUSIBILITY. If the REAL page doesn't have a MATCHING

  access to verify against the actual, current page.

This is exactly the same principle from Chapter 5's own locator-strategy design — when a genuinely exact, checkable fact is available (does a real element exist), use deterministic verification; reserve LLM reasoning for questions that genuinely require judgment, which "does this element exist" simply isn't.

Explain why "the right tool, called with wrong parameters" and "the wrong tool entirely" represent genuinely different underlying agent problems, not just two flavors of the same mistake.▾

These point to genuinely different parts of the agent's reasoning process — wrong TOOL selection suggests a failure in understanding WHAT KIND of action the situation calls for; wrong PARAMETERS with the RIGHT tool suggests the agent understood the action type correctly but failed at GROUNDING it in the actual, current page state.

WRONG tool selection — a HIGHER-LEVEL reasoning problem:
Choosing fill_field when the situation actually calls for
  click_element suggests the agent MISUNDERSTOOD what KIND of
  interaction the situation requires — a problem with its
  OVERALL situational understanding.

RIGHT tool, WRONG parameters — a DIFFERENT, more SPECIFIC
problem:
Correctly choosing click_element, but with parameters that
  don't match anything real, suggests the agent understood
  WHAT to do (click something) but failed specifically at
  IDENTIFYING WHICH real element to target — a problem with
  GROUNDING its correct high-level understanding in the actual,
  current page.

Recognizing this distinction matters practically — fixing a TOOL SELECTION problem might mean improving how the agent reasons about SITUATIONS broadly, while fixing a PARAMETER problem might mean improving how it OBSERVES or GROUNDS itself in the CURRENT page specifically — genuinely different fixes for genuinely different underlying issues.

Why might tool-parameter testing be considered MORE directly reusable from an agent's own production code than tool-selection testing?▾

Parameter verification (does a real element exist matching these values) is EXACTLY the same check Chapter 5's own tools already perform when actually executing — this page's testing logic can literally reuse that same verification, while tool-SELECTION testing needs a genuinely separate, dedicated evaluation the production agent doesn't otherwise perform.

Why PARAMETER testing logic OVERLAPS directly with PRODUCTION
code:
Chapter 5's find_and_click already CHECKS "does a MATCHING
  element exist" as PART OF its normal, real EXECUTION — this
  page's test_tool_parameters is essentially performing the
  SAME check, just POTENTIALLY run INDEPENDENTLY for
  VERIFICATION purposes, rather than as PART of actual
  execution.

Why SELECTION testing needs GENUINELY separate logic:
The PRODUCTION agent doesn't normally ASK ITSELF "was choosing
  fill_field over click_element THE RIGHT CATEGORY of choice
  here" as a DISTINCT, explicit step — it just REASONS and
  ACTS. Evaluating SELECTION QUALITY requires a GENUINELY NEW,
  DEDICATED evaluation process this page's test_tool_selection
  function specifically adds.

This is a genuinely useful practical distinction for implementation effort — parameter testing can often be BUILT CHEAPLY by reusing existing production verification logic, while selection testing typically requires building genuinely NEW evaluation capability specifically for testing purposes.

How would you design a test specifically for the case where an agent selects the RIGHT tool, with PARAMETERS that match a REAL element — but the WRONG real element (a genuine ambiguity case from Chapter 5)?▾

This connects directly to Chapter 5's own multiple-matches scenario — testing this specifically requires checking not just "does SOME matching element exist" but "does the SPECIFIC element that would be targeted genuinely correspond to what the SITUATION actually calls for."

def test_correct_specific_element(actual_tool_call, page_context,
                                     intended_target_description, client):
    role = actual_tool_call["input"]["role"]
    name = actual_tool_call["input"]["name"]
    matches = page_context.locator(f"[role='{role}']", has_text=name)

    if matches.count() > 1:
        # Chapter 5's OWN multiple-matches scenario — genuinely
        # ambiguous, needs REASONING to check if the RIGHT one
        # was likely targeted, not just that SOME match exists
        prompt = f"""Multiple elements match role='{role}',
name='{name}'. The agent needed to target: {intended_target_description}.
Without additional context in the tool call, can we confirm
which SPECIFIC element would actually be clicked, and is this
GENUINELY ambiguous?"""
        result = client.messages.create(model="claude-sonnet-4-6",
            max_tokens=200, messages=[{"role": "user", "content": prompt}])
        return result.content[0].text
    return {"valid": matches.count() == 1, "issue": None}

This extends this page's deterministic parameter-checking to explicitly handle the genuinely harder case Chapter 5 identified — MULTIPLE matches existing means simple existence-checking (this page's main approach) isn't sufficient; genuinely determining whether the CORRECT specific element would be targeted needs additional REASONING about the actual, intended target, exactly the kind of nuanced verification this chapter's overall approach to agent testing is built to handle.
