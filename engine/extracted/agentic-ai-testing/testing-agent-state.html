Testing Agent State

Prerequisites: Testing Agent Memory

What is this?

Chapter 2's Agent State page described a real, concrete bug: an agent's tracked state (current_page: "product") drifting out of sync with what's actually true (already on the cart page). This page turns that concept into an actual, repeatable test.

A Direct State-vs-Reality Comparison

def test_state_matches_reality(agent, page):
    report = agent.run(page)

    # Reconstruct what the agent's TRACKED state believed at
    # each step from its own history, then compare against
    # what page.url ACTUALLY was at that same moment — this
    # requires the agent to log its BELIEVED state alongside
    # each action, an addition to Chapter 3's original code
    discrepancies = []
    for step in report["full_history"]:
        tracked_url = step.get("tracked_current_page")
        actual_url = step.get("actual_url_at_time")
        if tracked_url != actual_url:
            discrepancies.append({
                "step": step["step"],
                "agent_believed": tracked_url,
                "actually_was": actual_url,
            })
    return {"state_accurate": len(discrepancies) == 0,
            "discrepancies": discrepancies}

🧠 Think About It

Why does this test require the agent's code to explicitly log its "believed" state alongside each action, rather than inferring it after the fact? State drift is, by definition, a mismatch between what the agent's INTERNAL tracking says and what's actually true — if you only ever observe the ACTUAL page state after the run completes, you have no record of what the agent BELIEVED at each intermediate point to compare against. Testing for state drift requires the agent to make its internal belief explicit and observable at each step, not just its final, real-world outcome.

⚠️ Common Mistake

Testing an agent only by its final report, assuming that if the final outcome is correct, state must have stayed accurate throughout. State could genuinely drift mid-run and still self-correct by the final step (a fresh observation eventually overwriting stale tracked state) — the final report alone wouldn't reveal that drift happened at all, even though it represents real, if temporary, risk during the steps where it occurred.

💡 Quick Tip

Logging both "tracked" and "actual" state at every step (this page's approach) adds real, genuine overhead to an agent's execution — a reasonable practice for TEST runs specifically, even if a production agent doesn't always need this level of instrumentation for every single real task.

Best Practices

  • Instrument agents to log their believed state alongside each action, specifically to make state-drift testing possible.
  • Compare tracked state against actual, real state at every step, not just at the final outcome.
  • Treat temporary state drift that later self-corrects as a genuine finding worth investigating, not just something the final "success" outcome excuses.

🎯 Key Takeaway

  • State testing directly compares an agent's tracked belief against real, actual page state at each step, turning Chapter 2's conceptual drift warning into a concrete, repeatable test.
  • State drift can occur and even self-correct within a run without ever showing up in the final report, making step-by-step comparison genuinely necessary.
  • Testing state accuracy requires an agent to explicitly log its internal beliefs, not just its final, observable outcome.

Why does this page argue that testing state accuracy requires the agent's code to be modified, rather than being purely an external, black-box testing technique?▾

State drift is fundamentally about a mismatch between an INTERNAL belief and EXTERNAL reality — without access to what the agent internally BELIEVED at each step, there's genuinely nothing to compare the external reality AGAINST.

Why PURE black-box testing genuinely can't catch THIS
specific problem:
From OUTSIDE the agent, you can observe the REAL, actual page
  state at any point — but you have NO visibility into what
  the agent's OWN internal tracking BELIEVES that state to be,
  UNLESS the agent itself EXPOSES this information explicitly.

Why THIS page's approach GENUINELY requires instrumentation:
Comparing "believed" against "actual" is IMPOSSIBLE without
  BOTH sides of the comparison being OBSERVABLE — the "actual"
  side is externally visible, but the "believed" side ONLY
  exists INSIDE the agent's own internal state, requiring
  DELIBERATE logging to make it externally CHECKABLE at all.

This is a genuinely important, practical limitation worth recognizing — SOME testing techniques (like this one) fundamentally require GREY-BOX access (instrumenting the system under test), not PURE black-box observation, and state-drift testing is a clear, concrete example of exactly this kind of need.

Why might logging both tracked and actual state at every step be reasonable for TEST runs specifically, but not necessarily for every production run, as this page's "Quick Tip" suggests?▾

This instrumentation adds genuine, real overhead (an extra observation call at every step) — reasonable to accept during DELIBERATE testing where verifying correctness IS the goal, but potentially unnecessary cost for EVERY real, production task where the agent is simply trying to get real work done efficiently.

Why the OVERHEAD is GENUINELY worth it during TESTING:
The WHOLE POINT of a test run is VERIFYING correctness — an
  EXTRA observation call at each step, specifically to CONFIRM
  actual_url_at_time, is a REASONABLE, DELIBERATE cost for
  GENUINELY valuable verification information.

Why this SAME overhead might be UNNECESSARY for EVERY
production run:
A production agent handling ROUTINE, ALREADY-WELL-TESTED
  tasks doesn't NEED this EXTRA verification on EVERY SINGLE
  run — the ARCHITECTURE has already been VALIDATED through
  DEDICATED testing; adding the SAME overhead to EVERY
  production execution would be a REAL, ongoing cost for
  DIMINISHING additional value, once genuine confidence has
  already been established.

This is a genuinely practical, real trade-off — INSTRUMENTATION appropriate for DELIBERATE, periodic TESTING isn't automatically the RIGHT default for EVERY production execution, a distinction worth making explicitly rather than assuming ALL instrumentation should ALWAYS be present everywhere.

How would you extend this page's approach to test whether state drift specifically correlates with certain KINDS of actions (e.g., navigation actions specifically, versus fill/click actions)?▾

A genuinely useful extension would group the discrepancies this page's function already collects by the ACTION TYPE that preceded each one, revealing whether drift clusters around a SPECIFIC kind of action rather than occurring uniformly.

def analyze_drift_by_action_type(discrepancies, full_history):
    from collections import Counter
    drift_action_types = []
    for d in discrepancies:
        preceding_step = next(
            (s for s in full_history if s["step"] == d["step"] - 1), None)
        if preceding_step:
            action_type = preceding_step["action"].split("(")[0]
            drift_action_types.append(action_type)

    counts = Counter(drift_action_types)
    return (f"State drift occurred following these action types: "
            f"{dict(counts)} — worth investigating whether ONE "
            f"SPECIFIC action type is disproportionately "
            f"responsible for state going stale.")

This directly extends this page's own core technique to answer a MORE SPECIFIC, genuinely useful diagnostic question — rather than JUST confirming state drift OCCURRED, this reveals WHETHER it's concentrated around a PARTICULAR kind of action (perhaps NAVIGATION actions specifically don't reliably trigger a state REFRESH), pointing toward a much MORE TARGETED, ACTIONABLE fix than "state sometimes drifts" alone would provide.
