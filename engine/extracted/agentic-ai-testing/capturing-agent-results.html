Capturing Agent Results

Prerequisites: Agent Execution Loop in Code

What is this?

The loop from the previous page already calls self._build_report(...) at every exit point — this page writes what that function actually does, and why a genuinely useful report is more than just the raw history list dumped as-is.

Why Raw History Isn't Enough

Raw history (what the loop already tracks):
[
  {"step": 0, "action": "fill_field(label='Email', value='...')",
   "result": "Filled field labeled 'Email'"},
  {"step": 1, "action": "fill_field(label='Password', value='...')",
   "result": "Filled field labeled 'Password'"},
  {"step": 2, "action": "click_element(role='button', name='Log In')",
   "result": "Clicked element with role='button', name='Log In'"},
  ...
]

Genuinely useful to a human? Only partially — it shows WHAT
happened mechanically, but not clearly whether the objective
was actually achieved, or what specifically to pay attention
to if something looks worth a second look.

A Genuinely Useful Report, Built From the Same History

def _build_report(self, history, success, final_text):
    return {
        "objective": self.objective,
        "success": success,
        "summary": final_text,
        "steps_taken": len(history),
        "full_history": history,   # kept for anyone who wants
                                     # to inspect the actual detail
    }

Genuinely simple — the real work is in what gets fed into final_text, which comes directly from the LLM's own "TASK COMPLETE" summary (success case) or the specific stopping reason (failure case), both already captured by the loop from the previous page.

Distinguishing Observed Fact From Inference

❌ A report that blurs fact and inference together:
  "Login works correctly."

  Worth asking: did the agent verify EVERY aspect of "works
  correctly," or just the one specific path it happened to try?

✅ A report that's explicit about what was actually checked:
  "Verified: a user with valid credentials can log in and
  reaches the account dashboard. NOT verified: behavior with
  invalid credentials, or behavior if the login form is
  submitted with empty fields — outside this task's objective."

This connects directly to the instructions page's ambiguity-handling rule — a genuinely trustworthy report is explicit about its own actual scope, not just its conclusion.

Running the Complete Agent

# main.py — putting every piece from this chapter together
from playwright.sync_api import sync_playwright
from agent import QAAgent
import os

agent = QAAgent(api_key=os.environ["ANTHROPIC_API_KEY"])
agent.set_objective(
    "Verify that a user with valid credentials can successfully "
    "log into ShopEasy, ending up on their account dashboard."
)

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.goto("https://staging.shopeasy.example.com/login")

    report = agent.run(page)

    print(f"Success: {report['success']}")
    print(f"Summary: {report['summary']}")
    print(f"Steps taken: {report['steps_taken']}")

    browser.close()

🧠 Think About It

Why might a report that only says "Login works correctly" — with no mention of what specifically was checked — actually be worse than a report that's honest about a genuine limitation in what it verified? A confident, unqualified "works correctly" can create false confidence in coverage the agent never actually had — a human reading it might reasonably assume invalid-credential handling was also checked, when it wasn't. An honest report about scope, even if it sounds less impressively complete, gives a human reviewer an accurate picture of what's genuinely been verified versus what still needs separate coverage.

⚠️ Common Mistake

Treating the raw history list as the report itself, without a genuine summary a human can quickly read. Full history matters and should be kept (this page's _build_report retains it), but a report that's ONLY raw history forces every reviewer to manually reconstruct what actually happened and whether it succeeded — exactly the summarization work the agent itself is well-positioned to do.

💡 Quick Tip

Include steps_taken in every report, even successful ones. A task that succeeded in 4 steps versus one that barely squeaked by at 14 (against a 15-step limit) are genuinely different outcomes worth distinguishing — the second is worth a closer look even though it technically succeeded.

Best Practices

  • Build a genuine, human-readable summary from the agent's own final output, not just a raw dump of mechanical action history.
  • Instruct the agent (via the instructions page's guidance) to be explicit about what was and wasn't actually verified, not just its overall conclusion.
  • Retain full history alongside the summary — useful for anyone who wants to inspect the actual detail behind a given result.

🎯 Key Takeaway

  • A genuinely useful report combines a clear, human-readable summary with the full underlying history, not one or the other alone.
  • Reports should be explicit about what was actually verified versus what's outside a task's scope, not just state a confident conclusion.
  • Metrics like steps taken are worth capturing even on success — a narrow, near-limit success is meaningfully different from a clean, efficient one.

Interview Questions

A stakeholder reads an agent's report saying "Checkout works correctly" and concludes the feature is fully tested. What questions would you ask before agreeing with that conclusion?▾

I'd specifically ask what the underlying objective actually was, and check the full history for what was genuinely exercised — a confident-sounding summary doesn't tell you the actual scope of what was checked, exactly this page's core point.

Genuinely important questions to ask:
- What was the EXACT objective given to the agent? ("verify
  checkout works with valid payment info" is much narrower
  than "checkout" broadly)
- Does the report explicitly state what was NOT covered
  (invalid payment methods, out-of-stock items, discount
  codes)? If not, that's a gap worth investigating directly
- How many steps did it take, and does the full history show
  it genuinely exercised the real flow, or did something
  perhaps complete "successfully" in a way that doesn't
  reflect thorough coverage?

"Works correctly" as a bare conclusion, without explicit scope, is exactly the kind of report this page argues against — the right response isn't to distrust the agent, but to insist on the explicit-scope reporting standard this page recommends before treating any conclusion as complete.

Why does this page's _build_report function retain full_history even though summary already provides a human-readable conclusion?▾

Because the summary and the full history serve genuinely different purposes — the summary is for quick review, while the full history is for genuinely verifying or investigating a result when something's worth a closer look, and discarding it would make that impossible.

What the SUMMARY is good for:
Quick, everyday review — "did this pass, and what was the
  general conclusion" — genuinely sufficient for routine,
  successful runs that don't need deeper scrutiny.

What FULL HISTORY is good for, that summary alone can't provide:
- Debugging a FAILED run — exactly which step went wrong, and
  what the agent actually observed at that point
- Auditing a SUSPICIOUSLY fast or slow success — did it
  genuinely exercise the real flow, or take a shortcut?
- Building genuine trust over time — reviewing several runs'
  full histories to confirm the agent's summaries are actually
  accurately reflecting what happened underneath

Keeping both, rather than discarding history once a summary exists, directly supports the incremental-trust-building principle from Chapter 1 — genuine verification requires being able to actually look underneath a summary when needed, not just trust it by default.

Why might instructing the agent to explicitly state what it did NOT verify be considered more important than instructing it to describe what it DID verify?▾

Both matter, but the "did NOT verify" half addresses a genuinely more dangerous failure mode — a human silently assuming broader coverage than what actually happened, which the "DID verify" half alone doesn't prevent.

A report ONLY describing what WAS verified:
"Verified: valid credentials successfully log in and reach the
  dashboard." — accurate, but says NOTHING about invalid
  credentials, empty fields, or other realistic scenarios — a
  reader could reasonably but WRONGLY assume broader coverage.

A report that ALSO states what was NOT verified:
"...NOT verified: invalid credential handling, empty-field
  submission — outside this task's objective." — actively
  PREVENTS the reader from assuming broader coverage than
  genuinely happened, closing exactly the gap the first
  version leaves dangerously open.

The "DID verify" half tells you what to trust; the "did NOT verify" half tells you what NOT to mistakenly trust — and it's the second one that most directly prevents the false-confidence risk this page's opening "Think About It" section specifically raises.

How would you modify this chapter's report structure to also capture the real, actual cost (in API calls or tokens) of a given agent run, and why might that matter?▾

def _build_report(self, history, success, final_text, total_tokens):
    return {
        "objective": self.objective,
        "success": success,
        "summary": final_text,

This matters because Chapter 1 was explicit that agentic testing has real, genuine cost trade-offs compared to traditional automation — capturing actual token usage per run turns that abstract trade-off into a concrete, trackable number a team can genuinely monitor and make informed decisions about, rather than a vague sense that "it's more expensive."

Trace through what this chapter's complete agent (main.py) would actually do, end to end, if the login form on the real staging page had genuinely changed since the agent's instructions were written.▾

Because this chapter's agent uses genuine reasoning grounded in real, current observation (not a fixed script), it should adapt to a real, moderate UI change — this is exactly the practical payoff of everything built across this chapter's earlier pages.

What actually happens, step by step:
1. agent.run(page) starts the loop; page.url and get_page_text
   give the REAL, current page content — not what the agent's
   instructions assumed the page would look like
2. The reasoner, seeing the ACTUAL current form (even if
   fields are labeled or arranged differently than expected),
   uses genuine reasoning to identify the email and password
   fields based on their real, current labels
3. fill_field and click_element execute against whatever the
   REAL page actually presents, not a hardcoded assumption
4. The loop continues normally, genuinely adapting to the real,
   current UI throughout

This is the concrete, practical version of Chapter 1's core argument for agentic testing — a traditional Playwright script with hardcoded locators would have simply failed outright at the first changed element, while this chapter's agent, built on real observation and reasoning rather than fixed instructions, has a genuine chance of adapting to a reasonable, moderate change without needing to be rewritten first.
