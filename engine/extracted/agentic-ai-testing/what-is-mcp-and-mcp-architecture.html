What is MCP? MCP Architecture

Prerequisites: MCP for QA Automation overview

What is this?

MCP (Model Context Protocol) is an open protocol for connecting AI applications to external tools and data sources — a standard way for an LLM-based client to discover and call capabilities exposed by a server, regardless of which specific client or server implementation is involved.

The Basic Architecture

┌─────────────┐         MCP Protocol         ┌─────────────┐
│  MCP CLIENT   │◄──────(JSON-RPC 2.0)───────►│  MCP SERVER   │
│               │                               │               │
│ Hosts the LLM,│   1. discover capabilities    │ Exposes:      │
│ decides WHEN  │   2. call a tool               │  - Tools      │
│ to call what  │   3. read a resource            │  - Resources  │
└─────────────┘                                 └─────────────┘

This is genuinely the same shape as Chapter 3's agent architecture — a reasoning side deciding what to do, and a tool-execution side actually doing it — except MCP formalizes the boundary between them as a real, standardized protocol, not code living inside one agent.

Why Standardization Is the Genuine Point

Chapter 3's tools, WITHOUT MCP:
  TOOL_DEFINITIONS is PYTHON-specific, SHAPED around THIS
  agent's OWN particular prompt-building code — genuinely
  useful, but tightly COUPLED to ONE specific implementation.

The SAME capability, EXPOSED as an MCP server:
  ANY MCP-compliant CLIENT — written in ANY language, built by
  ANY team — can DISCOVER and CALL this SAME tool, WITHOUT
  needing to understand OR reimplement ANYTHING about HOW it's
  actually IMPLEMENTED internally.

🧠 Think About It

Why might separating "the tool's implementation" from "how a client discovers and calls it" be genuinely valuable, beyond just code reuse across multiple agents? A standardized protocol means a tool built once — say, a genuinely reliable ShopEasy checkout-testing tool — can be improved, fixed, or extended in ONE place, and every client using it benefits immediately, without needing coordinated updates across every agent that happens to use it. This is the same value proposition as any well-designed API boundary: decoupling implementation from consumption lets each evolve independently.

⚠️ Common Mistake

Treating MCP as an entirely new concept unrelated to what Chapter 2 and 3 already taught. The reasoning-vs-tools separation, the description-driven tool discovery, the structured call-and-response pattern — every core idea is already familiar; MCP is the standardized, shareable version of it.

Why does this page argue that "MCP client" and "the reasoning side of QAAgent" are directly analogous, rather than genuinely different concepts?▾

Both play EXACTLY the same architectural ROLE — deciding WHAT to do and WHEN, based on a goal and available capabilities — the only genuine difference is WHICH PROTOCOL they use to actually CALL those capabilities.

Chapter 3's QAAgent (the REASONING side specifically):
DECIDES, based on the OBJECTIVE and CURRENT observation,
  WHICH tool to call NEXT — using DIRECT, IN-PROCESS Python
  function calls to actually EXECUTE that decision.

An MCP CLIENT, playing the SAME role:
DECIDES, based on the SAME KIND of objective and observation,
  WHICH tool to call NEXT — using the MCP PROTOCOL (JSON-RPC)
  to COMMUNICATE that decision to a SEPARATE server PROCESS,
  rather than a DIRECT, in-process function call.

The DECISION-MAKING role is IDENTICAL; only the MECHANISM for actually EXECUTING that decision differs — exactly why this page argues these are the SAME underlying concept, with MCP simply FORMALIZING the communication LAYER between reasoning and execution into an actual, STANDARDIZED protocol.

Explain why decoupling "the tool's implementation" from "how a client calls it" genuinely enables independent evolution, using a concrete example.▾

A concrete example: if the underlying click_element tool's implementation improves (say, adopting Chapter 5's own multi-strategy locator fallback), every client using it via MCP benefits IMMEDIATELY, without any client-side code changes at all.

Server-side IMPROVEMENT, with NO client-side changes needed:
The MCP SERVER'S internal implementation of "click_element"
  gets UPGRADED to use Chapter 5's fuller, multi-strategy
  locator approach INSTEAD of a single, fragile strategy — a
  GENUINE, real improvement.

What happens on the CLIENT side:
NOTHING needs to CHANGE — every CLIENT calling this tool
  through the STANDARD MCP interface AUTOMATICALLY benefits
  from the IMPROVED, more RELIABLE implementation, since the
  PROTOCOL BOUNDARY between "what the tool DOES" and "HOW a
  client CALLS it" means internal improvements are ENTIRELY
  invisible to, and INDEPENDENT of, the CLIENT'S own code.

This is EXACTLY the value of a well-designed API boundary generally, now APPLIED specifically to AI tool-calling — the SERVER can genuinely IMPROVE its OWN internals FREELY, as long as it CONTINUES honoring the SAME external PROTOCOL contract, WITHOUT requiring ANY coordinated update across EVERY client that happens to USE it.
