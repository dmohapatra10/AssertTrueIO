Agent Reasoning

Prerequisites: Agent Planning

What is this?

If planning is sketching the route before a trip, reasoning is deciding, right now, how to handle the actual road in front of you. Reasoning takes the current plan step, the real, current observation, and whatever's in memory, and decides one specific, concrete next action.

Reasoning in Action

Current plan step: "Authenticate with valid test credentials"

Current observation (what the agent actually sees right now):
  A form with two visible fields, one labeled "Email or username"
  and one labeled "Password", and a button labeled "Log In".
  No CAPTCHA, no other visible obstacles.

Reasoning process (the "why" behind the decision):
  "The plan step is 'authenticate.' I can see a genuine login
  form with clearly labeled fields. There's nothing blocking
  me. The specific next action: fill the email field first,
  since it's positioned above the password field and typically
  needs to be filled first in a standard login flow."

Resulting SPECIFIC action:
  fill('Email or username', 'testuser@shopeasy.example.com')

Notice how much more concrete this is than the plan step it came from — "authenticate" became one specific, executable action, chosen based on what's genuinely, currently true about the page.

Reasoning Under Genuine Ambiguity

A harder, more realistic case — the observation isn't clean:

Current observation: TWO forms are visible on the page — one
labeled "Sign in" and one labeled "Create an account", both
with email and password fields, positioned side by side.

Reasoning process:
  "The plan step is 'authenticate' — this implies an EXISTING
  account, so the correct form is 'Sign in', not 'Create an
  account'. I'll target the fields within the 'Sign in' section
  specifically, not just any email/password field on the page."

This is genuine reasoning, not simple pattern-matching — it
required understanding what 'authenticate' actually implies
and applying that understanding to disambiguate two visually
similar options.

How Reasoning Differs From Planning, Concretely

PlanningReasoning
Happens largely before real observationHappens using the current, real observation
Produces a rough, multi-step sequenceProduces one specific, immediate action
Revised occasionally (re-planning)Happens fresh at essentially every single step
"What are the rough phases of this task?""Given what I see right now, what do I do next?"

🧠 Think About It

Why might an agent with excellent planning but genuinely weak reasoning still fail at real tasks, even on a well-understood application like ShopEasy? A rough plan like "authenticate, then add to cart" is only useful if something can correctly translate "authenticate" into the actual right action given the real page in front of it — including handling exactly the kind of genuine ambiguity in this page's two-forms example. A great plan executed by weak, careless reasoning at each step produces the same poor real-world result as no plan at all.

⚠️ Common Mistake

Building reasoning that only pattern-matches on surface-level text ("see a button labeled 'Log In', click it") without genuinely reasoning about context. This breaks exactly in cases like the two-forms example above, where surface pattern-matching alone can't distinguish "Sign in" from "Create an account" — both have superficially similar-looking form fields.

💡 Quick Tip

When reviewing or debugging an agent's reasoning, it's genuinely useful to ask it (or examine its logged reasoning trace) to explain WHY it chose a specific action, not just what it chose. A reasonable-sounding "why" that's based on a genuine misunderstanding is a very different, more diagnosable problem than reasoning that was actually sound but happened to be executed incorrectly.

Best Practices

  • Give the reasoning step genuinely sufficient, real observation to work with — vague or incomplete context is a common, real cause of poor decisions.
  • Log an agent's reasoning (its "why"), not just its final action — this makes debugging genuinely tractable later.
  • Test reasoning specifically against cases with real ambiguity, not just clean, unambiguous happy paths.

🎯 Key Takeaway

  • Reasoning takes the current plan step, real observation, and memory, and decides one specific, immediate action — distinct from planning's broader, rougher sequence.
  • Genuine reasoning handles real ambiguity by understanding context, not just matching surface-level text patterns.
  • Reasoning happens fresh at essentially every step, using the most current, real information available — unlike planning, which is revised only occasionally.

Interview Questions

An agent correctly identifies a "Sign in" form among two visually similar forms, but a teammate says this is "just pattern matching, not real reasoning." How would you respond?▾

I'd distinguish between matching on SURFACE features (button color, position, generic label text) versus understanding what the actual goal implies and using that understanding to disambiguate — the second is genuine reasoning, even if the final action looks similar to what simple pattern matching might occasionally produce by coincidence.

Surface pattern-matching (NOT genuine reasoning):
"I see a form with email and password fields — click its
  submit button." — this would pick RANDOMLY between the two
  visually similar forms, since both match this shallow pattern

Genuine reasoning (what actually happened):
"The plan step implies an EXISTING account ('authenticate'),
  which specifically means 'Sign in', not 'Create an account'
  — I'll target the fields within that specific section."
  — this correctly disambiguates BECAUSE it understood what
  the goal actually implies, not because of surface features

The test for "is this genuine reasoning": does it correctly handle a case where surface pattern-matching would fail or guess randomly? The two-forms example is specifically designed to make that distinction concrete and testable.

Why does this page argue that logging an agent's reasoning (the "why"), not just its final action, matters for real debugging?▾

Because the same final action can result from genuinely different underlying reasoning — some sound, some flawed — and only the "why" reveals which one actually happened, which determines what (if anything) actually needs fixing.

Same action, two very different underlying causes:
Action taken: clicked the "Create an account" form's submit
  button instead of "Sign in"

Possible reasoning A (a genuine misunderstanding worth fixing):
  "I'll use whichever form appears first on the page" — reveals
  a real reasoning gap that needs a prompt/context fix

Possible reasoning B (a correct decision, wrong INPUT):
  "The plan explicitly said to create a new test account" —
  reveals the reasoning was actually FINE; the problem is
  upstream, in what the plan itself specified

Without the logged "why," both cases look identical from the outside — the same wrong-seeming action — but they need completely different fixes. This is exactly why reasoning traces, not just action logs, matter for genuinely diagnosing agent behavior.

Give an example of a plan step that would require GENUINELY difficult reasoning to execute correctly, and explain specifically what makes it hard.▾

A genuinely hard example: plan step "verify the discount was applied correctly," on a checkout page showing a subtotal, a line labeled "Promotional discount: -$5.00," and a total — where the discount code applied was supposed to be 15% off a $40 item.

Why this is genuinely hard reasoning, not simple lookup:
The agent needs to independently CALCULATE what 15% of $40
  actually is ($6.00), compare that to what's actually shown
  (-$5.00), and recognize this is a GENUINE DISCREPANCY worth
  flagging — not just confirm that SOME discount line exists.

A shallow, insufficient version of "reasoning":
"A line labeled 'discount' is present with a negative dollar
  amount — checkout looks correct." — this would completely
  MISS the actual, real bug (wrong discount amount applied),
  despite superficially looking like it verified something

This example is deliberately chosen to show reasoning doing genuine verification work — actually checking that a real value is CORRECT, not just present — which is meaningfully harder than simply confirming an element exists on the page.

Why might giving the reasoning step MORE observation detail than it actually needs be counterproductive, not just harmless?▾

Excess, irrelevant detail can genuinely dilute an LLM's attention and increase the chance it focuses on something irrelevant to the actual decision at hand — more context isn't free, and isn't always strictly better.

Focused, relevant observation for "find the login form":
"A form with email and password fields, labeled 'Sign in',
  and a submit button labeled 'Log In'."

Excessively bloated observation for the SAME decision:
[the entire page's raw HTML, including unrelated footer links,
  a cookie consent banner's full legal text, unrelated product
  recommendations, hidden analytics scripts, etc.]

The bloated version doesn't help the reasoner make a BETTER
decision about the login form specifically — it genuinely
risks the reasoning process getting distracted by, or
mis-weighting, entirely irrelevant surrounding content.

The practical lesson: constructing what the reasoner actually sees is itself a real design decision worth real care — relevant, focused context tends to produce more reliable reasoning than simply including everything available "just in case."

How would you test whether an agent's reasoning is genuinely robust, rather than just happening to work on the happy-path cases you've tried so far?▾

Deliberately construct cases with real ambiguity or edge conditions — similar to this page's two-forms example — rather than only testing against the clean, expected scenario, and check whether the reasoning's stated "why" genuinely reflects correct understanding, not just a lucky correct guess.

Genuinely useful test cases to construct deliberately:
- Two visually similar elements where only ONE is semantically
  correct for the current goal (the two-forms example)
- A page state that's TECHNICALLY valid but unusual (an empty
  search results page, a partially-loaded page)
- Conflicting signals (a button that's visually enabled but
  has a disabled attribute, or vice versa)

For each, check: did the agent choose correctly, AND does its
logged reasoning show genuine understanding of WHY, or does it
look like a coincidentally-correct guess that got lucky?

Testing only happy-path scenarios can hide reasoning that's actually shallow or coincidentally correct — genuinely robust reasoning needs to be verified specifically against cases designed to distinguish real understanding from surface-level pattern luck.
