MCP Security

Prerequisites: AI Agent + MCP

What is this?

The hub page was explicit: MCP doesn't replace the guardrail thinking from Chapter 2. This final page is about what genuinely changes once a server can be used by multiple, possibly untrusted clients — a real, honest look at the new risks this reusability introduces.

The Core Shift — Trust Was Implicit, Now It's Explicit

Chapter 3's HARDCODED tools were called ONLY by Chapter 3's
OWN agent — the SAME code, WRITTEN by the SAME team, with
IMPLICIT trust baked in by CONSTRUCTION.

An MCP server, by DESIGN, can be CALLED by ANY compliant
CLIENT — possibly WRITTEN by a DIFFERENT team, possibly
CONNECTED with LESS oversight than the ORIGINAL developer
INTENDED. The SAME server-side GUARDRAILS Chapter 2 taught
(scope discipline, INPUT validation) now need to be
GENUINELY, EXPLICITLY enforced, since they can NO LONGER rely
on "ONLY my OWN code CALLS this."

A Real, Concrete Risk — Overly Broad Server Scope

❌ A SERVER exposing GENUINELY dangerous scope:
@mcp.tool()
def run_shell_command(command: str) -> str:
    """Runs an ARBITRARY shell command on the server."""
    import subprocess
    return subprocess.run(command, shell=True, capture_output=True).stdout

ANY client CONNECTING to this server can EXECUTE arbitrary
code on WHATEVER machine the SERVER runs on — EXACTLY the
kind of OVER-BROAD tool scope Chapter 2's Guardrails page
warned against, now with a GENUINELY larger BLAST RADIUS,
since ANY client (not JUST the ORIGINAL developer's OWN
agent) can REACH it.

✅ The SAME underlying NEED, scoped SAFELY:
@mcp.tool()
def run_smoke_test(environment: str) -> dict:
    """Runs ONLY the ShopEasy smoke test suite against 'staging'
    or 'production' — NO arbitrary commands."""
    if environment not in ("staging", "production"):
        return {"error": f"Unknown environment: {environment}"}
    # ... runs a SPECIFIC, KNOWN test suite, NOTHING else ...

A Real, Concrete Risk — Tool Poisoning

A GENUINELY documented MCP-specific risk: a MALICIOUS or
COMPROMISED server could DESCRIBE a tool DECEPTIVELY —
CLAIMING to do ONE thing in its DOCSTRING, while ACTUALLY
doing something ELSE entirely (or ADDITIONALLY) when CALLED.

Since a CLIENT'S reasoning TRUSTS the DESCRIPTION (EXACTLY
Chapter 2's OWN point that DESCRIPTIONS are the ONLY
information AVAILABLE), a DECEPTIVE description could
GENUINELY mislead an AGENT into CALLING a tool it WOULDN'T
have chosen if it KNEW what the tool ACTUALLY did.

🧠 Think About It

Why does tool poisoning specifically exploit the same property that makes MCP tools genuinely useful in the first place? A client's reasoning has to trust a tool's description to make any decision at all — this chapter's own earlier pages relied on this repeatedly, treating well-written docstrings as load-bearing. Tool poisoning is the adversarial flip side of that same necessary trust: if a client could independently verify every tool's actual behavior before ever calling it, descriptions wouldn't need to be trusted at all — but then tools wouldn't be usable through reasoning alone either. This is a genuine, structural tension, not a simple oversight to patch.

⚠️ Common Mistake

Connecting an agent to an MCP server without any consideration of where that server actually comes from or who controls it — treating "it speaks the MCP protocol correctly" as equivalent to "it's safe to connect to." Protocol compliance says nothing about a server's actual trustworthiness.

💡 Quick Tip

Chapter 2's original scope-guardrail principle — expose the narrowest capability that genuinely satisfies the need — applies with MORE force for MCP servers than for a single hardcoded agent's tools, precisely because the audience calling them is genuinely wider and less controllable.

Best Practices

  • Scope every server-exposed tool to the narrowest genuine capability needed, since the audience calling it is wider and less controllable than a single hardcoded agent's own tools.
  • Only connect agents to MCP servers whose source and maintainer are genuinely trusted, not just servers that happen to speak the protocol correctly.
  • Recognize tool poisoning as a real, structural risk inherent to trusting descriptions at all, not a simple bug to eliminate entirely.

🎯 Key Takeaway

  • MCP's reusability genuinely widens who can call a server's tools, making Chapter 2's scope-discipline guardrails more, not less, important.
  • Tool poisoning exploits the same necessary trust in descriptions that makes tool-calling through reasoning possible at all — a genuine, structural tension.
  • Protocol compliance alone says nothing about a server's actual trustworthiness — connecting to an MCP server is a genuine trust decision, not just a technical one.

How would you design a genuine safeguard specifically against tool poisoning, given that a client can't directly inspect a server's actual implementation?▾

A GENUINELY useful SAFEGUARD, given a CLIENT CAN'T inspect IMPLEMENTATION directly, is BEHAVIORAL verification — RUNNING a NEWLY-connected SERVER'S tools AGAINST KNOWN test CASES BEFORE trusting it FOR real work, checking WHETHER ACTUAL behavior MATCHES the CLAIMED description.

async def verify_tool_matches_description(session, tool_name, test_cases):
    """Before trusting a NEWLY-connected server's tool for REAL
    work, run it against KNOWN test cases and confirm its
    ACTUAL behavior matches what its description CLAIMS."""
    results = []
    for case in test_cases:
        actual_result = await session.call_tool(tool_name, case["input"])
        matches_expectation = case["expected_check"](actual_result)
        results.append({
            "input": case["input"],
            "matched_description": matches_expectation,
        })
    if not all(r["matched_description"] for r in results):
        return "WARNING: tool behavior does NOT match its claimed description — do NOT trust for production use."
    return "Tool behavior CONFIRMED to match its description across test cases."

This DIRECTLY applies Chapter 3's OWN "TEST the SIMPLEST piece FIRST" and Chapter 12's OWN BEHAVIORAL-verification PRINCIPLES to a GENUINELY new context — rather than TRUSTING a description BLINDLY, RUNNING it AGAINST KNOWN, EXPECTED cases FIRST provides GENUINE, EMPIRICAL evidence about WHETHER a SERVER'S claimed BEHAVIOR matches its ACTUAL behavior, BEFORE that TRUST is EXTENDED to REAL, CONSEQUENTIAL use — a PRACTICAL, CONCRETE way to PARTIALLY address the STRUCTURAL tension this PAGE'S earlier discussion IDENTIFIED.
