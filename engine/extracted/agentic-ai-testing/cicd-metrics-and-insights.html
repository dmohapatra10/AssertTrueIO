A Genuine Pipeline Dashboard

def compute_pipeline_metrics(recent_runs):
    from statistics import mean
    return {
        "avg_pipeline_duration_s": mean(r["duration_s"] for r in recent_runs),
        "selection_efficiency": mean(
            r["tests_selected"] / r["tests_total"] for r in recent_runs),
        "triage_urgent_rate": mean(
            len(r["triage"]["urgent"]) / max(len(r["failures"]), 1)
            for r in recent_runs if r["failures"]),
        "retry_success_rate": mean(
            1 if r["retry_outcome"] == "resolved" else 0
            for r in recent_runs if r.get("retried")),
        "genuine_flaky_retry_avoidance": mean(
            1 if not r.get("retried_flaky_classified", False) else 0
            for r in recent_runs),  # should be VERY close to 1.0 —
            # confirms Chapter 9's warning is genuinely being honored
    }

🧠 Think About It

Why does this page treat genuine_flaky_retry_avoidance as more important to monitor closely than, say, avg_pipeline_duration_s, even though speed is this chapter's most visible, celebrated result? A duration regression is genuinely visible and self-correcting — a team notices the pipeline got slower and investigates. A silent violation of Chapter 9's retry warning is genuinely invisible in the moment — it looks like the pipeline is working fine, green and fast, while quietly masking a real, unresolved race condition. The metric that catches an invisible, dangerous drift deserves more vigilance than the one that catches a visible, self-announcing regression.

⚠️ Common Mistake

Reporting a single, blended "pipeline health score" that averages across duration, selection efficiency, triage accuracy, and retry behavior. This page's own example shows exactly why — a genuinely dangerous drift in flaky-retry avoidance could be completely hidden behind an otherwise-strong blended number, the same mistake Chapters 11 and 12 already warned against in their own domains.

💡 Quick Tip

Setting an automated alert specifically on genuine_flaky_retry_avoidance dropping below 1.0 — rather than waiting to notice it during a periodic dashboard review — treats this chapter's most safety-critical metric with the urgency its underlying risk actually warrants.

Best Practices

  • Track pipeline metrics per category — duration, selection, triage, retry — never as one blended pipeline-health score.
  • Give the metric that guards against Chapter 9's specific, known risk (flaky-retry avoidance) more monitoring urgency than metrics tracking visible, self-correcting concerns like duration.
  • Set automated alerts on safety-critical metrics specifically, rather than relying on periodic manual review to catch a silent drift.
