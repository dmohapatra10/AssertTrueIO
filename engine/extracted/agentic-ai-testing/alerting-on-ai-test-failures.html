Alerting on AI Test Failures

Prerequisites: Monitoring AI Test Systems

What is this?

Chapter 8's own Understanding Test Failures page already named the risk: treating every failure with maximum urgency trains a team to tune out alerts entirely, eventually missing genuine ones. This chapter has introduced TWO new signal sources — system health (previous page) and traced reasoning (two pages back) — and this page is about applying that same discipline to them, not doubling the noise.

A Genuine Alert Rule Set, Calibrated Deliberately

def evaluate_alert_worthiness(signal_type, signal_data):
    if signal_type == "system_health":
        # Chapter 8's OWN cheap-check-first principle: a SINGLE
        # slow reading is likely NORMAL variance; a SUSTAINED
        # pattern is what GENUINELY warrants a human's attention
        if signal_data["consecutive_degraded_readings"] >= 3:
            return {"alert": True, "urgency": "high",
                    "reason": "System health degraded across 3+ consecutive checks."}
        return {"alert": False, "reason": "Single reading, within normal variance."}

    if signal_type == "traced_reasoning_anomaly":
        # Reusing Chapter 12's OWN unusual-step-count technique —
        # a STATISTICAL outlier, not just "this run took extra steps"
        if signal_data["step_count_zscore"] > 2:
            return {"alert": True, "urgency": "medium",
                    "reason": "Step count is a statistical outlier vs. baseline."}
        return {"alert": False, "reason": "Step count within normal range."}

Why These Specific Thresholds — Not "Alert on Anything Unusual"

NOTICE neither RULE fires on a SINGLE data POINT alone.
System health REQUIRES three CONSECUTIVE degraded readings —
Chapter 8's OWN "a SINGLE fluke among many RUNS produces a
similar-looking RATE to what real, LOW-grade flakiness would
SHOW" reasoning, applied HERE to system-HEALTH signals
INSTEAD of test PASS rates. The REASONING-anomaly rule REUSES
Chapter 12's OWN statistical OUTLIER approach, NOT a raw
STEP-count threshold that would FIRE on ordinary, EXPECTED
variation.

🧠 Think About It

Why does this page apply Chapter 8's alert-fatigue reasoning to system health and traced reasoning specifically, rather than treating those as fundamentally different from the traditional test failures Chapter 8 originally discussed? The underlying mechanism Chapter 8 identified — indiscriminate urgency training a team to eventually discount even genuine alerts — has nothing to do with WHAT is being alerted on. It applies equally to a system-health degradation alert as to a test-failure alert. Introducing two new signal sources without applying this same discipline would simply recreate the exact problem Chapter 8 already diagnosed, in a new domain.

⚠️ Common Mistake

Alerting on every single degraded reading or every run with an above-average step count, treating the new observability data this chapter introduced as inherently more alert-worthy than ordinary test failures. The same discipline Chapter 8 established applies here — a single data point rarely justifies interrupting a human.

💡 Quick Tip

When adding a new observability signal to an alerting system, explicitly ask "would this fire on ordinary, expected variation?" before deploying it — exactly the question this page's consecutive_degraded_readings >= 3 and statistical z-score thresholds are designed to answer correctly.

Best Practices

  • Apply Chapter 8's alert-fatigue discipline to every new observability signal this chapter introduces, not just traditional test failures.
  • Require sustained or statistically significant patterns before alerting, never a single data point in isolation.
  • Explicitly test whether a new alert rule would fire on ordinary, expected variation before deploying it.

🎯 Key Takeaway

  • Chapter 8's alert-fatigue warning applies equally to this chapter's new signal sources — system health and traced reasoning anomalies — not just traditional test failures.
  • Genuine alert rules require sustained patterns or statistical significance, never firing on a single, potentially-normal data point.

A GENUINELY useful VERIFICATION tracks the RATIO of alerts that TURNED OUT to be GENUINE problems VERSUS alerts that TURNED OUT to be FALSE positives OVER time — DIRECTLY measuring WHETHER the CURRENT thresholds are PRODUCING a REASONABLE signal-to-NOISE ratio in PRACTICE.

def audit_alert_calibration(alert_history):
    """Tracks whether recent alerts genuinely corresponded to
    real, actionable problems, or were false positives —
    providing empirical evidence about threshold calibration."""
    total_alerts = len(alert_history)
    if total_alerts == 0:
        return "No alerts yet to evaluate."

    genuine_problems = sum(
        1 for a in alert_history if a["confirmed_genuine_issue"])
    false_positive_rate = 1 - (genuine_problems / total_alerts)

    if false_positive_rate > 0.5:
        return (f"WARNING: {false_positive_rate:.0%} of recent "
                f"alerts were false positives — thresholds may "
                f"be miscalibrated, risking the exact "
                f"alert-fatigue pattern Chapter 8 warned about.")
    return (f"Alert calibration appears reasonable: "
            f"{false_positive_rate:.0%} false positive rate.")

This TURNS this page's ABSTRACT concern about CALIBRATION into a CONCRETE, MEASURABLE audit — RATHER than ASSUMING the THRESHOLDS are CORRECT indefinitely, THIS check PROVIDES ongoing, EMPIRICAL evidence about WHETHER the SYSTEM is GENUINELY achieving a REASONABLE balance, DIRECTLY connecting to Chapter 8's OWN alert-FATIGUE mechanism by MEASURING the SPECIFIC false-positive RATE that DRIVES it.
