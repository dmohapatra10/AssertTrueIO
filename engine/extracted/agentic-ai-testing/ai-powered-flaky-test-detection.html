One Failure vs. a Pattern of Failures

Chapter 8 diagnosed a single failure using evidence from a single run. Flakiness is genuinely different — it's only visible ACROSS many runs, and the previous chapter's "flaky behavior" category gets its own full chapter here specifically because detecting and prioritizing it is real, distinct work. The Running Example for This Chapter

test('cart total updates after adding an item', async ({ page }) => {
  await page.goto('/cart');
  await page.getByRole('button', { name: 'Add Wireless Mouse' }).click();
  await expect(page.getByTestId('cart-total')).toHaveText('$27.50');
});

This test passes roughly 80% of the time and fails the other
20% — never for the SAME reason twice, per Chapter 8's own
analysis, but genuinely, measurably inconsistent across many
runs. Perfect material for this chapter's actual subject.

A Deliberate Note on This Chapter's Own "Root Cause Analysis" Page

This chapter has a page asking why a specific test is flaky — worth distinguishing explicitly from Chapter 8's Root Cause Analysis page, which diagnosed a single failure using evidence from one run. This chapter's version asks a genuinely different question: given that a test fails inconsistently across MANY runs, what property of the test or application causes that inconsistency itself?

Common Mistakes to Watch For

  • Calling a test "flaky" after a single unexplained failure — Chapter 8's own classification requires genuine repeated evidence, not a one-off guess.
  • Fixing flaky tests by adding retries or longer timeouts — this chapter's fixes page is explicit about why this usually hides the real problem rather than solving it.
  • Treating every flaky test as equally worth fixing right now — exactly what this chapter's scoring page exists to address.
