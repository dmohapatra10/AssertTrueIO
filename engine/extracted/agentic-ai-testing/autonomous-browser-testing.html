Autonomous Browser Testing

Prerequisites: AI Assertions

What is this?

This page is the synthesis — navigation (deciding where to go), locator selection (finding elements robustly), and assertions (deciding what's actually correct) all operating together in one real, complete autonomous exploration of ShopEasy's search flow.

The Goal

"Explore ShopEasy's search and filtering functionality. Verify
that search results are relevant, filters actually narrow
results correctly, and report anything that seems broken or
inconsistent."

Notice this is genuinely open-ended — exactly the kind of exploratory goal Chapter 1 identified as agentic testing's real strength, not a fixed, predetermined checklist.

A Genuine, Complete Run

Step 1 — NAVIGATION: search(query="wireless mouse")
  → "Searched for 'wireless mouse'"

Step 2 — LOCATOR-BACKED tool: get_search_results()
  → 3 structured results (from earlier pages' example)

Step 3 — FUZZY ASSERTION: assess_relevance("wireless mouse", results)
  → All 3 results judged HIGH confidence relevant. No issues.

Step 4 — NAVIGATION (continuing the open-ended exploration):
  apply_filter(filter_name="Price", value="Under $20")
  → "Applied filter: Price = Under $20"

Step 5 — LOCATOR-BACKED tool: get_search_results()
  → [{"name": "Basic Wireless Mouse", "price": "$18.99", "in_stock": false}]

Step 6 — EXACT ASSERTION (genuinely has one correct answer here):
  "Filter claims 'Under $20' — is $18.99 actually under $20?
  Yes. Filter is working correctly for this result."

Step 7 — REASONING catches something the goal asked to watch for:
  "Only ONE result remains after filtering, and it's OUT OF
  STOCK. This isn't necessarily a bug, but worth noting: a
  user filtering for budget wireless mice currently has zero
  genuinely purchasable options. Flagging as a real, if minor,
  finding."

FINAL REPORT: "Search relevance: no issues found. Price filter:
working correctly. Finding worth reviewing: filtering to
'Under $20' currently leaves only an out-of-stock item — not a
bug, but a genuine gap in available inventory a real user
would encounter."

Tracing Which Chapter Piece Powered Each Step

Nothing in this run introduces a new capability — it's every piece from this chapter's earlier pages, and Chapter 2's underlying architecture, working together on one genuinely open-ended, realistic task.

⚠️ Common Mistake

Designing an "autonomous" browser test that's actually a fixed sequence of steps with no genuine open-endedness at all — technically using an agent, but not actually benefiting from its real capacity to notice unanticipated things. This page's example genuinely explores beyond a fixed checklist (step 7's finding wasn't explicitly pre-specified), which is what makes it a genuine example of this chapter's title, not just automation with extra steps.

💡 Quick Tip

When reviewing a genuinely autonomous browser test's report, it's worth explicitly checking whether ANY finding wasn't something you'd have thought to write as an explicit assertion in advance — if every single finding was fully anticipated, the exploration may not actually be adding value beyond what a traditional, fixed test would have already covered.

Best Practices

  • Give genuinely open-ended goals room to surface unanticipated findings, rather than constraining exploration to a fixed, predetermined checklist.
  • Combine exact and fuzzy assertions within the same run, using each where it genuinely fits, as this page's steps 3 and 6 do.
  • Review a final report specifically for findings that weren't explicitly anticipated — this is where genuine exploratory value shows up most clearly.

🎯 Key Takeaway

  • Autonomous browser testing combines navigation, locator selection, and assertions into one coherent exploration, not three separate, disconnected capabilities.
  • A genuinely open-ended goal can surface findings nobody explicitly asked for in advance — this is the concrete, practical payoff of everything this chapter has built.
  • Reviewing whether a report contains any genuinely unanticipated finding is a real, useful test of whether an exploration actually delivered agentic value, beyond what a fixed test would have found anyway.

Interview Questions

A stakeholder reviews this page's example run and asks "why not just write a fixed Playwright test checking these exact same things?" How would you respond?▾

I'd point specifically to step 7's finding — a fixed Playwright test could only check things someone explicitly thought to write an assertion for in advance, and nobody would have anticipated "filtering could leave only an out-of-stock item" as a specific thing to check for ahead of time.

What a FIXED test genuinely COULD have caught here:
Steps 3 and 6's checks — relevance and filter correctness —
  COULD theoretically be written as fixed assertions, if
  someone had specifically thought to check them in advance.

What a fixed test structurally CANNOT catch:
Step 7's finding requires REASONING about a specific,
  UNANTICIPATED combination of circumstances (a legitimate
  filter, correctly applied, that happens to leave a genuinely
  unfortunate business outcome) — nobody writes an assertion
  for "check if filtering ever accidentally leaves only
  out-of-stock results" without ALREADY knowing to look for it,
  which defeats the entire purpose of EXPLORATORY testing.

The honest answer: a fixed test is genuinely better for steps 3 and 6 specifically (faster, cheaper, more predictable, exactly Chapter 1's traditional-automation strengths) — but ONLY an exploratory, reasoning-based approach could have surfaced step 7's finding at all, which is precisely the genuine, real value this page's combined approach demonstrates.

Why does this page's run use an EXACT assertion in step 6 ("is $18.99 under $20") rather than a fuzzy one, given that most of this chapter emphasizes AI's reasoning capabilities?▾

Because "is $18.99 under $20" has exactly one correct, determinable answer — this is precisely the kind of check the AI Assertions page argued belongs to exact comparison, not fuzzy judgment, even within an otherwise exploratory, agentic run.

Why fuzzy reasoning would be UNNECESSARY here:
There's no genuine ambiguity or judgment call in "$18.99 is
  numerically less than $20" — a SIMPLE, deterministic
  comparison settles this completely and reliably, with zero
  benefit from AI-style reasoning over a plain numeric check.

Why this STILL happens within an "autonomous" run:
Autonomous testing doesn't mean EVERY SINGLE check must be
  fuzzy or AI-reasoned — it means the OVERALL exploration is
  genuinely open-ended and adaptive. Individual steps within
  that exploration should still use whichever assertion type
  (exact or fuzzy) genuinely fits each specific check, exactly
  matching the previous page's own guidance.

This is a deliberate, important detail: "autonomous" describes the overall exploration's adaptive, goal-driven nature, not a blanket requirement that every individual check must be AI-reasoned rather than a simple, direct comparison where one is genuinely sufficient.

Why might it be reasonable to run this kind of exploratory autonomous test LESS frequently than a traditional regression suite, even though both are testing the same general area of the application?▾

This connects directly back to Chapter 1's honest cost comparison between traditional and agentic testing — genuine exploration has real, ongoing cost (LLM calls, longer runtime) that a fixed regression suite doesn't, making a different cadence genuinely reasonable for each.

Why a TRADITIONAL regression suite runs on every commit:
Fast, cheap, deterministic — the marginal cost of running it
  AGAIN is genuinely low, and catching a regression immediately
  (rather than days later) has real, direct value worth that
  low marginal cost.

Why THIS kind of exploratory run might reasonably run LESS
often (say, weekly, or before a major release):
Real, non-trivial cost per run (several LLM calls, genuine
  reasoning time) — running it on EVERY commit would multiply
  this cost by however many commits happen daily, without a
  correspondingly proportional increase in genuine, new value,
  since the KIND of finding this catches (like step 7's
  discovery) doesn't typically change meaningfully between
  every single small commit.

The practical lesson: matching CADENCE to genuine cost-benefit, not running every kind of test at the same frequency by default, is itself a real, practical skill this course expects you to develop — exactly the kind of deliberate, non-hyped thinking about autonomous QA's real trade-offs that Chapter 1 established as this entire course's actual standard.
