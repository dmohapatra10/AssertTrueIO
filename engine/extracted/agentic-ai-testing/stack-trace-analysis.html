Stack Trace Analysis

Prerequisites: Failure Classification

What is this?

A stack trace is the first, cheapest evidence source available for any failure — this page is about reading one genuinely well, not just glancing at the top line and guessing.

A Real Stack Trace, From This Chapter's Login Test

Error: Timed out 30000ms waiting for expect(locator).toBeVisible()

Locator: getByText('Welcome back')
Expected: visible
Received: <element(s) not found>

Call log:
  - expect.toBeVisible with timeout 30000ms
  - waiting for getByText('Welcome back')

    at /tests/login.spec.ts:8:44
    at TestCase.run (/node_modules/@playwright/test/lib/worker/testInfo.js:245:7)
    at TestRunner.runTest (/node_modules/@playwright/test/lib/worker/testRunner.js:112:3)

What This Trace Genuinely Tells You — and Doesn't

GENUINELY tells you:
  - The failure is at line 8 (the 'Welcome back' assertion)
  - The three PRECEDING steps (fill, fill, click) completed
    WITHOUT throwing — the failure is specifically AFTER login
    was attempted, not before
  - This is a Playwright-level timeout, not an application-
    thrown error (no server error message appears here at all)

Does NOT tell you:
  - WHY the text never appeared — broken login, wrong selector,
    slow server, or something else entirely
  - Whether this is CONSISTENT or a one-off — this is ONE run's
    trace, with no history attached

This directly narrows the six categories from the previous page without fully resolving any of them — application defect, locator problem, environment problem, network problem, and flaky behavior all remain genuinely possible from this trace alone; only "test defect involving an earlier step" is reasonably ruled out, since the earlier steps completed cleanly.

The Frame That Actually Matters

❌ Reasoning from only the TOP line of the trace:
  "Error: Timed out 30000ms waiting for..." — genuinely
  uninformative on its own; every one of the six categories
  could produce this exact same top line.

✅ Reasoning about WHICH frame represents the LAST successful
   action before failure:
  The call log shows exactly THREE prior actions succeeded
  (fill email, fill password, click login) before the timeout
  — this SPECIFIC detail is what narrows the investigation to
  "something after clicking login," not a vague, undifferentiated
  guess at the whole test.

🧠 Think About It

Why might it be a genuine mistake to conclude "this is definitely a locator problem" purely from seeing getByText('Welcome back') fail to match, without any further evidence? A locator failing to match its target is exactly what happens for EVERY SINGLE one of the six failure categories from the previous page — a broken app never shows the text (application defect), a changed page shows different text at a different location (locator problem), a slow server means the text hasn't rendered YET (flaky/network), and so on. The specific WORDING of a Playwright error message ("element not found," "timed out") is largely the SAME regardless of which underlying category actually caused it — the stack trace alone narrows WHERE to look, not WHY it happened.

⚠️ Common Mistake

Treating the stack trace as sufficient evidence on its own to reach a final classification. This page's own trace genuinely narrows the investigation (something went wrong after the login click) without resolving which of five remaining categories actually applies — the next several pages exist specifically because a stack trace alone usually isn't enough.

💡 Quick Tip

When an agent reads a stack trace, having it explicitly state which specific actions are CONFIRMED to have succeeded (based on what appears before the failure point) is genuinely useful — this positive information (what's known to have worked) is often as diagnostically valuable as the failure itself.

Best Practices

  • Read a stack trace for what specifically succeeded before the failure point, not just the failure message itself.
  • Treat a stack trace as narrowing an investigation, not resolving it — most traces alone can't distinguish between several of the six genuine categories.
  • Note explicitly which categories a trace rules OUT, not just what it might suggest — this is often the trace's most reliable, useful contribution.

🎯 Key Takeaway

  • A stack trace reliably shows where in a test's sequence a failure occurred, narrowing but rarely resolving which of the six failure categories applies.
  • The specific wording of a timeout or not-found error is largely identical across most failure categories — the trace's real value is in what it confirms succeeded beforehand.
  • Stack trace analysis is genuinely the first, cheapest evidence source, not the last or only one needed for reliable classification.

Interview Questions

An agent reads this page's stack trace and immediately concludes "test defect — the selector is wrong." What's the actual problem with jumping to this conclusion from the trace alone?▾

The trace alone genuinely cannot distinguish a wrong selector from four of the other five categories — "element not found" is exactly what a broken application, a stale selector, a slow environment, or a network issue would ALL produce, with no way to tell them apart from this evidence alone.

What the trace ACTUALLY supports:
"The failure occurred at the final assertion, after the
  preceding three steps succeeded" — a genuinely narrow,
  well-supported conclusion.

What it does NOT support:
"The SELECTOR specifically is wrong" — this requires evidence
  the trace doesn't provide: is 'Welcome back' genuinely the
  WRONG text (test defect), the RIGHT text but the wrong
  SELECTOR strategy (locator problem), or is the text simply
  NEVER appearing because login is broken (application defect)?
  The trace's error message looks IDENTICAL in all three cases.

Jumping to "test defect" specifically, rather than any of the other equally-plausible categories, isn't supported by anything unique in the trace — it's an unjustified guess dressed up as a conclusion, exactly the premature-certainty mistake this chapter has warned against since its opening page.

Why does this page emphasize that the three PRECEDING steps (fill, fill, click) completing successfully is genuinely useful diagnostic information, not just "nothing interesting happened there"?▾

Because it genuinely rules out an entire category of possible explanations — anything that would have caused an EARLIER step to fail is no longer a plausible cause, meaningfully narrowing where the actual problem must be.

What confirming the EARLIER steps succeeded genuinely rules OUT:
- The login PAGE itself failing to load correctly (the email
  field fill() wouldn't have succeeded if the page were broken)
- The FORM fields having genuinely wrong locators (both fill()
  calls succeeded, meaning THOSE specific selectors are fine)
- The login BUTTON itself being missing or unclickable (the
  click() call succeeded)

What this NARROWS the investigation to:
Something specifically happening AFTER the click — the
  server's response to the login attempt, or the PAGE'S
  reaction to that response — rather than needing to
  re-investigate the ENTIRE test from scratch.

This is a genuinely important, often under-appreciated diagnostic principle: confirming what DIDN'T go wrong is just as valuable as identifying what did, since it eliminates entire branches of investigation that would otherwise need to be separately ruled out.

Explain why the ABSENCE of a server-side error message in this page's trace is itself a meaningful piece of evidence, not just "no additional information."▾

A genuine application-level error (like a server returning a 500 status with an error body) would typically surface SOMEWHERE in a comprehensive trace or network log — its absence here is a real, if not conclusive, signal worth noting rather than ignoring.

What a GENUINE application error might look like, if present:
The trace or network log would likely show something like a
  failed POST request with a 500 status code, or an explicit
  error response body — CONCRETE evidence of the application
  itself reporting a problem.

What THIS page's trace shows instead:
NOTHING resembling a server-side error — just a Playwright-
  level TIMEOUT waiting for an element. This is consistent
  with several categories (locator problem, environment issue,
  flakiness) where the SERVER may have responded NORMALLY, but
  something else prevented the expected text from appearing —
  though it doesn't fully RULE OUT a subtler application issue
  either.

The lesson: absence of evidence isn't proof of absence, but it IS genuine, real evidence worth weighing — a trace with no server error is meaningfully different from one WITH a clear server error, even though neither alone gives a complete, final answer.

Why might reading ONLY the topmost line of a stack trace ("Error: Timed out 30000ms...") be a genuinely common, real mistake, even for experienced engineers?▾

The topmost line is often the LEAST specific, most generic part of a trace — it describes the TYPE of failure (a timeout) rather than the SPECIFIC context (what came before it, what was being waited for, at what point in the test) that actually carries the diagnostic value.

What the TOP LINE alone provides:
"Timed out 30000ms waiting for..." — this exact phrasing
  would appear for genuinely ANY of the six failure categories
  hitting a timeout-style failure — essentially uninformative
  on its own, despite LOOKING like the trace's "headline."

What the FULL call log and context provide:
The SPECIFIC locator being waited for, the SPECIFIC line
  number, and — critically — what ACTIONS are confirmed to
  have happened BEFORE this point, per the earlier answer in
  this page's own FAQ.

The genuinely common mistake is treating the top line as if it were a SUMMARY of the whole trace's diagnostic value, when it's actually closer to a generic HEADER — the real, useful information lives in the full call log and surrounding context, which is easy to skim past when the top line looks superficially like "the answer."

How would you design a prompt for an agent to reliably extract "what's confirmed to have succeeded" from a raw stack trace, rather than just summarizing the failure itself?▾

A genuinely useful prompt should explicitly ask for BOTH halves — what failed AND what's confirmed to have worked — since this page's own analysis shows the second half is often just as diagnostically valuable as the first.

def analyze_stack_trace(trace_text, client):
    prompt = f"""Here is a test failure's stack trace:

{trace_text}

Identify: (1) the SPECIFIC point of failure — what was
expected, what actually happened; (2) what actions or steps,
if any, are CONFIRMED to have completed successfully BEFORE
this failure point, based on the call log; (3) which of the
following categories this evidence RULES OUT, if any:
application defect, test defect, locator problem, environment
problem, network problem, flaky behavior. Do NOT guess at
which category IS correct if the trace alone doesn't
genuinely support one specific conclusion."""
    result = client.messages.create(
        model="claude-sonnet-4-6", max_tokens=512,
        messages=[{"role": "user", "content": prompt}]
    )
    return result.content[0].text

The explicit instruction to identify what's RULED OUT, rather than pushing for a single confident classification, directly reflects this page's own honest conclusion — a stack trace alone typically narrows the field without fully resolving it, and a good prompt should reflect that genuine limitation rather than pressuring the model into an unsupported, overconfident guess.
