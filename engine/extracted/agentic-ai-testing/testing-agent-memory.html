Testing Agent Memory

Prerequisites: Testing Tool Selection and Parameters

What is this?

Chapter 3's history list is only genuinely useful memory if it actually influences later reasoning. This page tests that specific link — not whether history is RECORDED (trivially true by construction), but whether it's genuinely USED.

The Real Bug This Catches — Recorded but Ignored

A GENUINELY realistic memory bug: history is correctly
appended to at every step (Chapter 3's own code does this) —
but if _build_prompt has a subtle bug truncating or
mishandling that history, the reasoner might never actually
SEE it, despite it being technically "recorded."

def test_memory_influences_reasoning(agent, page, client):
    # Deliberately cause a REPEATED failure, checking whether
    # the agent's THIRD attempt shows awareness of the FIRST
    # TWO, or repeats the IDENTICAL mistake
    history = []
    for attempt in range(3):
        prompt = agent._build_prompt(history, page)
        response = agent.client.messages.create(
            model=agent.model, max_tokens=300,
            system=agent.instructions,
            messages=[{"role": "user", "content": prompt}]
        )
        history.append({"step": attempt, "action": "click_element(...)",
                         "result": "FAILED: element not found"})

    # Check whether the prompt for attempt 3 GENUINELY includes
    # the two prior FAILURES, and whether the reasoning shows
    # AWARENESS of the repeated pattern:
    final_prompt = agent._build_prompt(history, page)
    return "FAILED: element not found" in final_prompt  # EXACT,
        # deterministic check — either history is GENUINELY in
        # the prompt, or it isn't

Why This Needs Both an Exact Check and a Reasoning Check

EXACT check (shown above): "is the history TEXT genuinely
  present in the built prompt?" — deterministic, catches the
  RECORDED-BUT-NEVER-INCLUDED bug directly.

REASONING check (a genuinely separate question): "given that
  the history IS present, does the agent's THIRD attempt
  actually BEHAVE differently, showing awareness of the
  repeated failure — or does it repeat the IDENTICAL failed
  action a THIRD time despite having the information available?"

BOTH matter: history could be technically PRESENT in the
prompt while the agent's reasoning still fails to genuinely
USE it — memory that's included but not meaningfully acted
upon is barely better than memory that's missing entirely.

🧠 Think About It

Why is checking whether history text appears in the prompt insufficient on its own to confirm memory is working correctly? Presence in the prompt confirms the DATA reached the reasoner — it says nothing about whether the reasoner actually USED that data in its decision. An agent could have perfectly complete history in every prompt while still repeating an identical failed action a third time, genuinely ignoring information that was technically available to it. This is exactly why this page's test needs both layers — one confirming memory reaches the reasoner, one confirming the reasoner's behavior actually reflects it.

⚠️ Common Mistake

Testing agent memory only by checking whether history data is technically recorded and included in prompts, without ever verifying the agent's actual behavior changes based on that history. This page's two-layer approach exists specifically because these are genuinely separate questions with separate failure modes.

💡 Quick Tip

A deliberately repeated failure (this page's own three-attempt pattern) is a genuinely reliable way to test memory's behavioral effect — if an agent's reasoning would sensibly try something different after seeing the SAME failure twice, but doesn't, that's a concrete, observable memory-usage problem, not a subtle or ambiguous one.

Best Practices

  • Test both whether history data reaches the reasoner and whether the reasoner's actual behavior reflects it — these are genuinely separate checks.
  • Use a deliberately repeated failure scenario to make memory-usage problems concretely observable in agent behavior.
  • Treat memory that's technically present but behaviorally unused as close to as serious a problem as memory that's missing entirely.

🎯 Key Takeaway

  • Testing agent memory means verifying it's both recorded AND genuinely used in later reasoning — two separate, both-necessary checks.
  • History technically present in a prompt doesn't guarantee the agent's reasoning actually acts on it.
  • A deliberately repeated failure scenario provides a concrete, observable way to test memory's real behavioral effect, not just its technical presence.

Interview Questions

A team confirms their agent's history list correctly grows with each step and concludes "memory is working." What genuine gap does this page argue this conclusion leaves open?▾

Confirming the LIST grows correctly only verifies the RECORDING half of memory — it says nothing about whether that recorded history actually reaches the reasoner's prompt, or whether the reasoner's behavior genuinely reflects it, exactly this page's two-layer distinction.

What "the history list grows correctly" GENUINELY confirms:
Chapter 3's history.append(...) call is executing as expected
  — a real, but NARROW confirmation.

What it does NOT confirm:
Whether _build_prompt CORRECTLY includes that FULL history
  (a subtle bug could TRUNCATE or MISHANDLE it) — AND
  separately, whether the AGENT'S REASONING actually USES the
  included history to behave differently, rather than
  IGNORING information that's technically present.

"The list grows correctly" is a genuinely necessary but NOT sufficient confirmation — this page's full test specifically checks the ADDITIONAL steps (inclusion in the prompt, behavioral effect) that "the list grows" alone leaves completely unverified.

Why does this page use a DELIBERATELY repeated failure as its test scenario, rather than a scenario where the agent succeeds on the first attempt?▾

A first-attempt success genuinely can't reveal anything about whether memory affects LATER behavior, since there IS no later attempt to compare against — testing memory's actual EFFECT requires a scenario where PRIOR history should genuinely change what happens NEXT.

Why a FIRST-ATTEMPT SUCCESS scenario reveals NOTHING about
memory:
If the agent succeeds immediately, there's no OPPORTUNITY to
  observe whether it would have BEHAVED DIFFERENTLY given
  PRIOR history — there simply ISN'T any prior history YET
  at the point of a first, successful attempt.

Why a REPEATED FAILURE scenario is SPECIFICALLY designed to
reveal this:
By the THIRD attempt, there's a GENUINE, real opportunity to
  observe: does the agent's behavior show it's LEARNED from
  the two PRIOR failures (memory working), or does it repeat
  the IDENTICAL action a third time DESPITE having that
  information available (memory not genuinely influencing
  behavior)?

This is a deliberate, well-designed test scenario — it specifically creates the CONDITIONS under which memory's actual EFFECT becomes OBSERVABLE, rather than testing a scenario where memory's presence or absence wouldn't make any VISIBLE difference either way.

Explain why "history text is present in the prompt" is a genuinely exact, deterministic check, while "the agent's behavior shows awareness of the history" needs reasoning-based evaluation.▾

These map directly onto the exact-vs-fuzzy distinction from Chapter 5 onward — text presence is a simple, unambiguous string-matching fact, while "shows awareness" requires genuine judgment about whether a specific response reflects understanding of prior context.

Why TEXT PRESENCE is genuinely EXACT:
"FAILED: element not found" in final_prompt — either this
  EXACT string appears in the prompt or it doesn't. A SIMPLE,
  unambiguous, deterministic check with ONE correct answer,
  needing ZERO genuine reasoning.

Why "SHOWS AWARENESS" genuinely needs REASONING:
Determining whether the agent's THIRD response GENUINELY
  reflects understanding that TWO prior attempts failed — versus
  COINCIDENTALLY trying something DIFFERENT for UNRELATED
  reasons — requires JUDGMENT about the RESPONSE'S actual
  CONTENT and REASONING, not a simple text-matching check.

This is a direct, concrete application of Chapter 5's original distinction, now applied specifically to memory testing — recognizing WHICH of this page's TWO checks is genuinely exact versus genuinely fuzzy is exactly the kind of calibration this course has built toward since that chapter.

Why might it be a mistake to assume that if the exact "history present in prompt" check passes, the reasoning-based "shows awareness" check will automatically pass too?▾

These check genuinely independent things — one confirms DATA DELIVERY, the other confirms DATA USE — and a system can reliably deliver data to a reasoner while that reasoner still fails to meaningfully incorporate it into its actual decisions.

A GENUINELY realistic scenario where ONE passes and the OTHER
fails:
History IS correctly, completely included in every prompt
  (the EXACT check passes reliably). But the REASONER'S actual
  decision-making might STILL, for various reasons (a
  genuinely imperfect model, an INSUFFICIENTLY clear
  INSTRUCTION about USING history, or simply GENUINE reasoning
  limitations), FAIL to meaningfully ADAPT its behavior based
  on that AVAILABLE information — repeating the SAME failed
  action DESPITE the history being RIGHT THERE in the prompt.

This is exactly why BOTH checks are genuinely, independently necessary — passing the DATA-DELIVERY check is a real, useful confirmation, but it's NOT sufficient evidence that the REASONING is actually working as intended; only the SEPARATE, reasoning-based check can confirm THAT.

How would you extend this page's approach to test LONG-TERM memory (Chapter 2's own distinction) rather than the short-term, within-task memory this page's example focuses on?▾

Testing long-term memory genuinely requires the SAME two-layer approach (presence AND behavioral effect), but applied ACROSS separate agent RUNS rather than within a single task's own history — checking whether a fact learned in one run genuinely influences behavior in a LATER, SEPARATE run.

def test_long_term_memory_effect(agent, long_term_fact, new_run_page):
    # Layer 1 — EXACT: was the fact genuinely INCLUDED in the
    # NEW run's prompt, pulled from LONG-TERM storage?
    prompt = agent._build_prompt([], new_run_page,
                                    long_term_memory=long_term_fact)
    assert long_term_fact in prompt

    # Layer 2 — REASONING: does the agent's BEHAVIOR in this
    # NEW, otherwise UNRELATED run actually REFLECT having this
    # PRIOR knowledge, e.g. handling a KNOWN recurring obstacle
    # (Chapter 2's OWN newsletter-modal example) MORE EFFICIENTLY
    # than an agent with NO such prior knowledge would?
    report = agent.run(new_run_page)
    return report["steps_taken"]  # fewer steps EXPECTED if the
        # long-term fact ("dismiss the modal via the X button")
        # is genuinely being USED, not just STORED

This directly extends this page's SAME two-layer philosophy to Chapter 2's OTHER memory category — the CORE principle (verify both DELIVERY and genuine USE, not just STORAGE) applies IDENTICALLY, just measured ACROSS separate runs rather than WITHIN a single task's own execution history, confirming that LONG-TERM memory provides the SAME kind of genuine, VERIFIABLE value this page established for SHORT-term memory.
