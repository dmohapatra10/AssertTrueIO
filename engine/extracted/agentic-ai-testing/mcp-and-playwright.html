What is this?

The Genuine Complication — Shared, Persistent Browser State

Earlier tools in this chapter (get_page_title, check_status_code)
were STATELESS — each call was independent, needing nothing
from a PREVIOUS call. Browser tools are GENUINELY different: a
click needs to happen on the SAME page a PREVIOUS navigation
opened, not a fresh page each time.

def get_browser_page():
    # A module-level Playwright instance, GENUINELY shared
    # across tool calls within this server's lifetime — the
    # SAME real complication Chapter 3's QAAgent handled by
    # keeping ONE page object alive across its WHOLE run loop
    global _shared_page
    if _shared_page is None:
        from playwright.sync_api import sync_playwright
        playwright = sync_playwright().start()
        browser = playwright.chromium.launch()
        _shared_page = browser.new_page()
    return _shared_page

Chapter 5's Tools, Wrapped as MCP

@mcp.tool()
def navigate_to(url: str) -> str:
    """Navigates the shared browser page to the given URL."""
    page = get_browser_page()
    page.goto(url)
    return f"Navigated to {url}"

@mcp.tool()
def find_and_click(role: str, name: str) -> str:
    """Clicks an element matching the given ARIA role and
    accessible name, using Chapter 5's multi-strategy fallback
    (role+name, then text, then aria-label)."""
    page = get_browser_page()
    # ... reuses Chapter 5's ACTUAL find_and_click implementation ...
    return find_and_click_impl(page, role, name)

@mcp.resource("shopeasy://browser/current-page-summary")
def get_current_page_summary() -> str:
    """A trimmed summary of the CURRENT browser page's
    interactive elements, using Chapter 5's own get_page_summary
    approach."""
    page = get_browser_page()
    return get_page_summary_impl(page)

🧠 Think About It

Why does this page make get_current_page_summary a resource rather than a tool, even though it involves real computation (trimming the page structure)? Applying the previous page's "ten times in a row" test: calling it repeatedly doesn't change anything about the page — it's a pure, read-only reflection of current state, genuinely more like a resource than an action. The trimming computation is real but cheap, and the result is deterministic given the current page state — it fits the resource category's spirit even though it's not simply reading a static file.

⚠️ Common Mistake

Treating each browser-related MCP tool as independent and stateless, the way earlier, simpler tools in this chapter were. Browser automation genuinely needs shared, persistent state across calls — a navigate, then a click, then a read all need to operate on the SAME live page, not a fresh one each time.

💡 Quick Tip

Reusing Chapter 5's actual, already-tested implementation functions (rather than rewriting the logic inside the MCP tool wrappers) is genuinely the right approach — the MCP layer should be a thin wrapper exposing existing, proven capabilities, not a place to reimplement browser automation logic from scratch.

Best Practices

  • Maintain shared, persistent browser state across tool calls within a server's lifetime, rather than treating each call as independent.
  • Reuse existing, proven implementation logic from earlier chapters as the actual work behind MCP tool wrappers.
  • Apply the tool-vs-resource test from the previous page even to browser capabilities that involve real, if cheap, computation.

🎯 Key Takeaway

  • Browser automation tools genuinely need shared, persistent state across MCP calls, unlike the simpler, stateless tools earlier in this chapter.
  • MCP tool wrappers should reuse Chapter 5's actual, proven implementation logic, not reimplement browser automation from scratch.
  • A page summary is genuinely closer to a resource than a tool, despite involving real computation, since repeated calls don't change anything and results reflect current, read-only state.

How would you extend this page's shared-browser-state approach to handle MULTIPLE, CONCURRENT clients connecting to the SAME MCP server, each needing their OWN, INDEPENDENT browser session?▾

A GENUINELY correct solution needs to move FROM a SINGLE, GLOBAL shared PAGE to a PER-SESSION page, KEYED by SOME identifier that DISTINGUISHES which CLIENT'S request is CURRENTLY being HANDLED.

_session_pages = {}  # keyed by session ID, NOT a single global

def get_browser_page(session_id: str):
    if session_id not in _session_pages:
        from playwright.sync_api import sync_playwright
        playwright = sync_playwright().start()
        browser = playwright.chromium.launch()
        _session_pages[session_id] = browser.new_page()
    return _session_pages[session_id]

@mcp.tool()
def navigate_to(url: str, session_id: str) -> str:
    """Navigates THIS session's browser page to the given URL.
    session_id should be a STABLE identifier for the CURRENT
    client connection."""
    page = get_browser_page(session_id)
    page.goto(url)
    return f"Navigated to {url}"

This directly ADDRESSES a GENUINE limitation of THIS page's ORIGINAL, SIMPLIFIED single-GLOBAL-page approach — WITHOUT session ISOLATION, TWO CONCURRENT clients would GENUINELY INTERFERE with EACH other's browser STATE, ONE client's navigate_to POTENTIALLY DISRUPTING ANOTHER'S in-PROGRESS task. MOVING to PER-session state PREVENTS this INTERFERENCE, a GENUINELY important CONSIDERATION for ANY MCP server EXPECTED to serve MULTIPLE, INDEPENDENT clients SIMULTANEOUSLY rather than JUST the SINGLE-client SCENARIO this page's SIMPLER example ASSUMED.
