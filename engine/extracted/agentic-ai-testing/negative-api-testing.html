Negative API Testing

Prerequisites: Schema and Response Validation

What is this?

Chapter 4's Negative Test Cases page generated negative scenarios by reasoning about a prose requirement. This page generates them mechanically from the spec's own declared constraints — comprehensive by construction, not by however thoroughly an LLM happened to brainstorm.

One Negative Test Per Required Field, Generated Systematically

def generate_missing_field_tests(schema):
    base_request = generate_request_body(schema)  # from the
                                                      # Request
                                                      # Generation page
    tests = []
    for field in schema.get("required", []):
        modified = dict(base_request)
        del modified[field]
        tests.append({
            "description": f"Request missing required field '{field}'",
            "body": modified,
            "expected_status": "400",
        })
    return tests

One Negative Test Per Declared Constraint Violation

def generate_constraint_violation_tests(schema):
    base_request = generate_request_body(schema)
    tests = []
    for field, definition in schema["properties"].items():
        if "enum" in definition:
            modified = dict(base_request)
            modified[field] = "NOT_A_VALID_ENUM_VALUE"
            tests.append({"description": f"'{field}' set to an invalid enum value",
                          "body": modified, "expected_status": "400"})
        if "minimum" in definition:
            modified = dict(base_request)
            modified[field] = definition["minimum"] - 1
            tests.append({"description": f"'{field}' below declared minimum",
                          "body": modified, "expected_status": "400"})
    return tests

Why This Is Genuinely Comprehensive, Not Just Thorough

Chapter 4's prose-based negative generation, even done well,
depends on an LLM correctly ANTICIPATING which negative cases
matter — genuinely good, but per that chapter's own honest
discussion, potentially variable between runs.

THIS page's approach doesn't anticipate anything — it
MECHANICALLY visits every declared required field and every
declared constraint, generating a corresponding negative test
for EACH ONE. Missing a required field's negative test here
isn't possible unless the field ISN'T in the spec's own
required list — the coverage is complete BY CONSTRUCTION.

🧠 Think About It

Why does this page's mechanical approach still need Chapter 4's Negative Test Cases page for genuinely complete negative coverage, rather than fully replacing it? Mechanical generation from the spec catches every violation of something the spec EXPLICITLY declares — a missing required field, an out-of-range value. It structurally cannot catch a negative case the spec never encodes as a formal constraint at all, like Chapter 4's own example of attempting to apply a second discount code — a business RULE, not a schema-level TYPE or REQUIRED constraint. The two approaches are complementary for exactly the same reason OpenAPI-Based Test Generation's own FAQ concluded spec-driven and exploratory approaches are complementary.

⚠️ Common Mistake

Assuming mechanical, spec-driven negative testing makes Chapter 4's reasoning-based negative case generation unnecessary. This page catches everything the spec formally declares as a constraint; it cannot catch a business rule violation the spec's schema never encodes, exactly the gap Chapter 4's reasoning-based approach still fills.

💡 Quick Tip

Running this page's mechanical generators against a real spec is a genuinely fast way to gauge how much a spec formally encodes versus leaves to prose or implicit convention — a spec with rich declared constraints (enums, minimums, patterns) yields much richer mechanical negative coverage than one that mostly just declares bare types.

Best Practices

  • Generate one negative test per declared required field and per declared constraint mechanically, guaranteeing complete coverage of what the spec formally encodes.
  • Keep Chapter 4's reasoning-based negative generation for business rules and scenarios the spec's schema doesn't formally capture.
  • Use the richness of mechanically-generated negative coverage as a rough signal for how much the spec itself formally encodes versus leaves implicit.

🎯 Key Takeaway

  • Spec-driven negative testing generates one test per declared required field and constraint mechanically, complete by construction rather than by however thoroughly an LLM brainstormed.
  • This approach structurally cannot catch business-rule violations the spec's formal schema never encodes — Chapter 4's reasoning-based approach remains necessary for those.
  • The two approaches are genuinely complementary, covering formally-declared constraints and implicit business rules respectively.

Interview Questions

A teammate argues this page's mechanical generation makes Chapter 4's negative-case work obsolete for API testing specifically. How would you respond, using a concrete example?▾

I'd point to Chapter 4's own second-discount-code example directly — this page's mechanical generators have no way to produce that test, since "only one discount code per order" is a business rule, not a schema-level type or required-field constraint.

What THIS page's generators CAN produce, mechanically:
Missing required fields, values outside declared min/max,
  invalid enum values, pattern mismatches — all DIRECTLY
  derivable from the schema's own FORMAL declarations.

What THIS page's generators STRUCTURALLY CANNOT produce:
"Attempt to apply a SECOND discount code after one is already
  applied" — nothing in a TYPICAL OpenAPI schema for a SINGLE
  request would encode this MULTI-STEP, STATEFUL business
  rule. The schema for the discount-application ENDPOINT alone
  has no way to express "but only if one hasn't ALREADY been
  applied to THIS order."

This is a concrete, genuine gap mechanical generation cannot close — the teammate's claim is specifically wrong for exactly this category of negative case, confirming the "genuinely complementary, not competing" conclusion this page's own "Think About It" section reaches.

Why does this page describe its coverage as "comprehensive by construction," and is this claim genuinely accurate or overstated?▾

The claim is accurate but genuinely SCOPED — it's comprehensive relative to what the spec formally declares, not comprehensive in any absolute sense; the previous FAQ answer's business-rule example shows exactly where this scoping matters.

Where "comprehensive by construction" IS genuinely accurate:
For EVERY field the spec marks as required, and EVERY
  constraint (enum, minimum, pattern) it declares, this page's
  functions GUARANTEE a corresponding negative test — there's
  NO way to accidentally skip one, since the generation
  MECHANICALLY visits the schema's own declared structure.

Where the claim would be OVERSTATED, if taken too broadly:
"Comprehensive" here does NOT mean "covers every possible way
  this endpoint could receive invalid input" — only every way
  the SCHEMA ITSELF formally declares as invalid. Business
  rules, cross-field validation, and stateful constraints
  (like the discount-code example) fall OUTSIDE this
  guarantee entirely.

The honest, precise framing: "comprehensive by construction" relative to the SCHEMA'S declared constraints specifically — a genuinely strong, real guarantee within that scope, but not a claim that this page's mechanical approach alone constitutes complete negative testing in any broader sense.

Explain why generate_constraint_violation_tests uses definition["minimum"] - 1 specifically, rather than some arbitrarily small negative number, to violate a minimum constraint.▾

This directly connects to Chapter 4's Boundary Testing page — the value JUST BELOW the declared minimum is the single most diagnostically valuable violation, since it specifically tests whether the boundary comparison itself is correct, not just whether "very wrong" values get rejected.

Why minimum - 1 SPECIFICALLY, rather than an arbitrary very
small number:
Exactly matches Chapter 4's own boundary-testing principle —
  a value JUST outside the valid range reveals whether the
  ACTUAL comparison logic (>= vs >) is correct, in a way
  a wildly invalid value (like -999999) wouldn't necessarily
  distinguish.

What an ARBITRARY very-negative value would MISS:
If the real implementation has an off-by-one bug (accepting
  ONE value below the true intended minimum), an ARBITRARILY
  small test value would STILL correctly get REJECTED,
  completely missing that specific, real bug — exactly the
  boundary-testing lesson from Chapter 4 applied here.

This is a direct, deliberate application of Chapter 4's own boundary-testing principle within this chapter's mechanical generation — the CHOICE of exactly minimum - 1, rather than any invalid value, is precisely what makes this negative test genuinely diagnostic rather than just "technically invalid."

Why might it be useful to ALSO generate a test using exactly the declared minimum value itself (not violating it), alongside this page's minimum - 1 negative test?▾

These are genuinely complementary POSITIVE and NEGATIVE boundary tests — minimum - 1 confirms the boundary correctly REJECTS just-below values; the exact minimum itself confirms the boundary correctly ACCEPTS the legitimately valid edge case, and only running one leaves the other direction unverified.

What minimum - 1 ALONE verifies:
"Does the system correctly REJECT a value just below the
  valid range?" — a NEGATIVE boundary test, exactly what this
  page's function currently generates.

What EXACTLY minimum, ALSO tested, would verify:
"Does the system correctly ACCEPT the value AT the boundary
  itself?" — a POSITIVE boundary test, directly connecting to
  Chapter 4's OWN "the exact boundary value is the single most
  valuable boundary test" argument — testing ONLY the invalid
  side leaves the EQUALLY important valid-boundary case
  completely unverified.

This is exactly Chapter 4's own three-point boundary standard (at, just-below, just-above) — this page's negative-testing function currently only generates ONE of those three points, and a genuinely complete implementation would generate all three, treating negative and positive boundary testing as the complementary pair Chapter 4 established they should be.

How would you extend this page's approach to generate a negative test for a TYPE mismatch specifically — sending a string where the schema declares an integer — given the current functions don't cover this case?▾

A genuinely useful addition mechanically substitutes a value of the WRONG type for each declared field, systematically covering this entire category the same way the existing functions cover required-field omission and constraint violation.

def generate_type_mismatch_tests(schema):
    base_request = generate_request_body(schema)
    tests = []
    wrong_type_values = {
        "integer": "not-a-number",
        "string": 12345,
        "array": "not-an-array",
        "object": "not-an-object",
    }
    for field, definition in schema["properties"].items():
        field_type = definition["type"]
        if field_type in wrong_type_values:
            modified = dict(base_request)
            modified[field] = wrong_type_values[field_type]
            tests.append({
                "description": f"'{field}' sent as wrong type "
                                f"(expected {field_type})",
                "body": modified, "expected_status": "400",
            })
    return tests

This follows the exact same mechanical pattern as this page's other two functions — visiting the schema's own declared structure systematically (this time, the declared TYPE of each field) and generating one corresponding negative test per field, extending this chapter's "comprehensive by construction" guarantee to cover type mismatches as their own genuine category too.
