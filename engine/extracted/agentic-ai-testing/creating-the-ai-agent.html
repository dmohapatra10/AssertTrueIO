What is this?

With the project set up, this page writes the actual, minimal code that talks to an LLM — the genuine starting point every other piece in this chapter builds on top of.

The Simplest Possible Version

# agent.py
import os
from anthropic import Anthropic
from dotenv import load_dotenv

load_dotenv()

client = Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])

def ask_agent(prompt):
    response = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=1024,
        messages=[{"role": "user", "content": prompt}]
    )
    return response.content[0].text

# A quick, genuine sanity check
if __name__ == "__main__":
    result = ask_agent("What's the very first step in testing a login form?")
    print(result)

Run this file directly, and you should get back a real, genuine text response from the LLM. This is deliberately the smallest possible working piece — no tools, no instructions shaping its testing behavior yet, no loop. Just confirming the actual connection works before building anything on top of it.

A real, practical reason to verify this exact piece first:

Turning This Into an Actual Agent Object

# agent.py — growing this into something the rest of the
# chapter can build on

class QAAgent:
    def __init__(self, api_key):
        self.client = Anthropic(api_key=api_key)
        self.model = "claude-sonnet-4-6"

    def think(self, prompt):
        response = self.client.messages.create(
            model=self.model,
            max_tokens=1024,
            messages=[{"role": "user", "content": prompt}]
        )
        return response.content[0].text

# Usage:
agent = QAAgent(api_key=os.environ["ANTHROPIC_API_KEY"])
result = agent.think("What's the very first step in testing a login form?")

This is genuinely the same functionality as the simple version above, reshaped into a class — a deliberate, small step that gives later pages (instructions, tools, memory) a natural place to actually live, as the agent's own attributes and methods.

🧠 Think About It

Why might verifying this minimal piece in isolation — before adding instructions, tools, or a loop — genuinely save real debugging time later, even though it feels like an unnecessary extra step for something this simple? Once multiple pieces are combined, a failure could originate from any of them — a bad API key, a malformed tool definition, a loop bug. Confirming the most basic piece works FIRST means any later failure can be more confidently attributed to whatever was added most recently, rather than re-debugging the entire stack from scratch every time something breaks.

⚠️ Common Mistake

Writing the full agent — instructions, tools, loop, everything — before ever running a single, minimal test of the basic LLM connection. If something's wrong, this makes it genuinely hard to tell whether the problem is in the connection itself, the prompt construction, the tool calling, or the loop logic — exactly the debugging difficulty this page's incremental approach is designed to avoid.

💡 Quick Tip

Keep max_tokens genuinely modest (1024 is plenty for early testing) while building and debugging — a runaway prompt or an unexpected loop, covered later in this chapter, costs less to discover and fix when each individual call is capped at a reasonable size.

Best Practices

  • Verify the most basic piece — a working LLM connection — in complete isolation before adding any other complexity on top of it.
  • Structure the agent as a class early, even in a simple form, giving later pieces (instructions, tools, memory) a genuine, natural place to live.
  • Keep token limits modest during development, adjusting upward deliberately once the basic pieces are confirmed working.

🎯 Key Takeaway

  • The genuine starting point for any agent is a minimal, verified connection to an LLM — confirmed working before anything else is layered on top.
  • Structuring this as a class from early on gives later chapter pages a natural, organized place to add instructions, tools, and state.
  • Isolating and verifying each new piece as it's added makes debugging a growing agent genuinely tractable, rather than an all-or-nothing guessing game.

Why does this page reshape the simple ask_agent() function into a QAAgent class, rather than just adding more functions alongside it as the chapter progresses?▾

A class gives later additions — instructions, tools, memory, state — a genuine, shared place to live as attributes and methods on the SAME object, rather than as separate, loosely-connected functions that would need to pass shared context between them manually.

As separate functions (harder to manage as complexity grows):
def ask_agent(prompt, instructions, tools, memory, state):
  # every single call needs ALL of this passed in manually,
  # and callers need to track and pass all this state themselves

As methods on a class (this page's actual approach):
agent = QAAgent(...)
agent.instructions = "..."      # set once
agent.memory = []                  # lives on the object itself
agent.think(prompt)                  # can access self.instructions,
                                        # self.memory directly, no
                                        # need to pass them explicitly
                                        # every single call

This isn't just style preference — it directly anticipates the genuine growth this chapter's remaining pages add (instructions, tools, memory, loop state), giving each one an obvious, natural place to belong on the agent object itself.

Why might keeping max_tokens modest during development be a genuinely practical habit, beyond just controlling cost?▾

A lower token limit also bounds how much can go wrong, or how expensive a single mistake can be, while you're actively debugging code that might contain genuine bugs — like the unbounded loops covered in Chapter 2, before those safeguards are even built yet at this early stage.

This is a genuinely practical, low-cost habit specifically for the development and debugging phase — not a permanent constraint, but a sensible default while things are still being built and tested, before the guardrails covered later in this chapter and the previous one are fully in place.

What's the practical difference between the response object's structure (response.content[0].text) and just getting a plain string back — why does this matter for building an agent?▾

A real LLM API response is typically a structured object containing more than just the text — metadata like token usage, a stop reason, sometimes multiple content blocks — and understanding this structure matters once an agent needs to do anything beyond just printing the response.

Why the structure matters, concretely, for later chapter pages:
Capturing Agent Results (later in this chapter) will genuinely
  benefit from ALSO capturing token usage for cost tracking,
  and Tool Calling in Practice will need to inspect the
  response for tool-use content blocks specifically, not just
  plain text — both of these need access to the FULL response
  object's structure, not just an extracted text string.

If ask_agent() only ever returned a bare string, later pages
  would need to go back and change this early function's
  return type — worth understanding the full structure now,
  even though this page only extracts the text portion.

This is a small but genuinely practical detail: understanding what the API actually gives you back, even if you're only using part of it right now, avoids having to refactor foundational code once later pieces need more of that structure.
