Understanding Test Failures

Prerequisites: AI-Powered Failure Analysis overview

What is this?

A failing test reliably tells you ONE thing: an assertion didn't hold. It genuinely tells you almost nothing else on its own — not whether the application is broken, not whether the test is wrong, not whether it's worth anyone's time at all. That gap is this entire chapter's subject.

The Running Example for This Chapter

ONE test, reused across every page in this chapter, failing
for a genuinely DIFFERENT reason each time:

test('user can log in with valid credentials', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('test@shopeasy.example.com');
  await page.getByLabel('Password').fill('correct-password');
  await page.getByRole('button', { name: 'Log In' }).click();
  await expect(page.getByText('Welcome back')).toBeVisible();
});

Same test. Same assertion. Six genuinely different real causes,
covered across this chapter's pages — the SAME red X in a CI
dashboard, meaning something completely different each time.

Why "It Failed" Is Genuinely Not Useful on Its Own

Six DIFFERENT real situations, all producing the IDENTICAL
surface-level signal ("test failed, expected element not found"):

1. Login is GENUINELY broken — a real, urgent bug
2. The test's SELECTOR is stale — the label text changed
3. STAGING is down for maintenance — nothing to do with the code
4. A NETWORK blip caused one request to time out — pure chance
5. The page is GENUINELY slow today — a timing/flakiness issue
6. The TEST ITSELF has a typo in the expected text

Every one of these needs a COMPLETELY different response — file
an urgent bug, fix a selector, wait and re-run, do nothing,
investigate flakiness, or fix the test file. "It failed" alone
gives a human ZERO information about which one actually happened.

The Real Work — Closing the Gap

SIGNAL:     "Expected element with text 'Welcome back' to be
             visible. Timed out after 30000ms."

DIAGNOSIS:  requires looking at MORE than the assertion itself —
             the stack trace, a screenshot at the moment of
             failure, the network log, maybe the application's
             own server logs — reasoned about TOGETHER, which
             is exactly what this chapter's remaining pages
             build up, piece by piece.

🧠 Think About It

Why might treating every test failure with the same urgency — investigate immediately, escalate as a potential production issue — actually be a worse practice than genuinely trying to classify each one first? Not every failure deserves the same response: a genuine application defect needs urgent attention, while a network blip needs essentially none. Treating everything as equally urgent either wastes real time investigating non-issues, or — more dangerously — trains a team to tune out failure alerts entirely once they notice most of them turn out to be nothing, exactly the kind of alert fatigue that causes a GENUINE defect to eventually get missed among the noise.

⚠️ Common Mistake

Treating a passing re-run as proof the original failure "wasn't real." A test that fails once and passes on retry could genuinely be flaky (worth investigating, per this chapter's later pages) — simply re-running until green and moving on discards exactly the diagnostic information this chapter is about capturing.

💡 Quick Tip

Before diagnosing WHY a test failed, it's genuinely worth confirming WHAT actually failed — the specific assertion, the specific line, the specific expected-versus-actual values — since jumping straight to root-cause reasoning from a vague sense of "the login test is red" skips real, available information.

Best Practices

  • Treat a failure as a signal requiring investigation, not a self-explanatory diagnosis on its own.
  • Resist applying the same urgency to every failure — genuine classification determines the appropriate response, covered in depth on the next page.
  • Capture and examine what a re-run's outcome (pass or fail) actually reveals, rather than treating a passing retry as automatically dismissing the original failure.

🎯 Key Takeaway

  • A test failure reliably indicates only that an assertion didn't hold — everything else about WHY requires genuine investigation.
  • The identical surface-level failure signal can represent six genuinely different real situations, each needing a different response.
  • Closing the gap between "it failed" and "here's what's actually wrong" is the real, valuable work this entire chapter builds toward.

Interview Questions

A teammate says "we don't need failure classification — if a test is red, someone just needs to go look at it." What would you say, using this page's own reasoning?▾

I'd point out that "someone goes and looks" is exactly the manual version of the classification work this chapter is about automating — the question isn't whether classification happens, it's whether a human does it from scratch every time, or an agent does the first pass reliably.

What "just go look" actually involves, IMPLICITLY:
A human reads the error, checks the screenshot, maybe checks
  if staging is up, maybe re-runs it once — they're ALREADY
  doing informal classification, just without a structured,
  consistent process, and spending real, repeated time doing
  it fresh for every single failure.

What structured classification adds:
The SAME diagnostic work, done consistently and FIRST, so the
  human's actual time goes to the failures that genuinely need
  it — exactly the failure-TRIAGE value Chapter 1 identified
  as a genuine, real strength of autonomous QA.

The teammate isn't wrong that failures need investigation — they're just describing the CURRENT, unstructured, manual version of exactly what this chapter is proposing to make faster and more consistent, not replacing genuine investigation with something else entirely.

Why does this page argue that treating every failure with maximum urgency could actually make a team WORSE at catching genuine defects, not just less efficient?▾

This is the alert-fatigue mechanism — if most "urgent" alerts turn out to be nothing, people genuinely start discounting them, meaning a real, urgent signal eventually gets the same reduced attention as the routine noise surrounding it.

The genuine, real mechanism:
Team gets 20 "URGENT" failure notifications a week. 18 turn
  out to be flaky tests or environment blips, only 2 are real
  bugs. Over time, the team LEARNS (even unconsciously) that
  "urgent" notifications are usually noise — and starts
  responding more slowly, or skimming rather than
  investigating, EVEN for the genuinely urgent 2 out of 20.

Why CLASSIFICATION specifically helps here:
If failures are reliably SORTED by genuine likely severity
  BEFORE reaching a human, the "real bug" alerts stand out
  clearly instead of being buried in a flood of equally-labeled
  noise — preserving the team's actual ability to respond
  quickly to what's genuinely urgent.

This is a real, well-documented phenomenon in operational alerting broadly, not unique to testing — and it's exactly why this page argues indiscriminate urgency is a genuine liability, not just a minor inefficiency.

Explain why the SAME error message ("Timed out after 30000ms waiting for element") could come from a genuine application defect or a purely flaky, transient issue, and why this ambiguity matters.▾

Both a genuinely broken feature and a one-off timing hiccup produce the exact identical surface symptom — an element that Playwright expected to appear within the timeout simply didn't, for reasons the error message itself genuinely can't distinguish.

Genuine APPLICATION DEFECT scenario:
Login is ACTUALLY broken — the "Welcome back" text will NEVER
  appear, no matter how many times or how long you wait,
  because the underlying feature has a real, persistent bug.

Genuine FLAKY/TRANSIENT scenario:
Login works CORRECTLY, but on THIS particular run, a slow
  server response pushed the "Welcome back" text's appearance
  to 31 seconds instead of the usual 2 — ONE SECOND past the
  timeout, on an otherwise perfectly functional feature.

BOTH produce the IDENTICAL error text. The message alone gives
  NO way to distinguish "will never work" from "worked 1 second
  too slowly, this one time."

This ambiguity is exactly why this page insists the raw error message alone is insufficient — distinguishing these two genuinely different situations requires the ADDITIONAL evidence sources (screenshots, traces, retry behavior, logs) this chapter's remaining pages build up specifically to resolve.

Why does this page insist on confirming WHAT failed (the specific assertion and values) before reasoning about WHY, rather than jumping straight to root-cause analysis?▾

Because skipping this step means potentially reasoning about the wrong problem entirely — a vague sense of "the login test failed" could actually mean several different assertions within that same test failed, each pointing toward a genuinely different investigation.

Vague starting point (RISKY to reason from directly):
"The login test is red." — WHICH assertion, specifically,
  failed? There are actually FOUR steps in this chapter's
  running example (fill email, fill password, click login,
  check welcome text) — the FAILURE could be at ANY of these,
  each implying a genuinely different investigation.

Specific starting point (this page's actual recommendation):
"The assertion at LINE 6 failed — expected 'Welcome back' to
  be visible, timed out after 30000ms. The PRECEDING three
  steps (fill, fill, click) all completed without error." —
  this SPECIFIC detail immediately narrows the investigation
  to what happened AFTER the login button was clicked,
  rather than needing to re-verify the earlier steps too.

Confirming the specific failure point first isn't just a formality — it directly determines WHICH subsequent evidence (which part of a trace, which screenshot moment, which log entries) is actually relevant to examine, making the rest of the diagnostic process genuinely more efficient and accurate.

How would you design a genuinely useful first-pass triage rule using only the information available at the moment a test fails, before any deeper investigation happens?▾

A genuinely useful first-pass rule checks a few cheap, immediately-available signals that can quickly rule SOME categories in or out, before committing to the more expensive, deeper investigation this chapter's later pages cover.

A reasonable, CHEAP first-pass triage, before deeper analysis:
1. Is the STAGING environment's health-check endpoint
   currently responding normally? (rules environment problems
   in/out almost instantly, at very low cost)
2. Did OTHER, UNRELATED tests running around the same time
   ALSO fail? (a sudden cluster of unrelated failures often
   points to environment or network issues, not a specific
   application defect in just THIS one feature)
3. Has this EXACT test failed before, and if so, did it pass
   on a SIMPLE re-run? (a genuine, quick signal for flakiness,
   without needing full root-cause analysis yet)

None of these cheap checks provide a FINAL, confident classification — but they can quickly and cheaply rule out or strongly suggest certain categories BEFORE committing to the more expensive, thorough analysis this chapter's remaining pages describe, exactly the kind of efficient triage-before-deep-investigation approach a mature failure-analysis process should include.
