The Standardized Version of Something You Already Built

Chapter 3's TOOL_DEFINITIONS list and execute_tool dispatch function were a genuine, working tool system — hand-built, specific to that one agent. MCP (Model Context Protocol) is an open standard for exactly that same idea: describing tools an AI can call, in a way any compliant agent can use, not just the one you wrote it for. Why This Genuinely Matters, Not Just as New Syntax

Chapter 3's tools were HARDCODED into ONE agent's own code —
genuinely useful, but NOT reusable by any OTHER agent without
copying and adapting that same code.

An MCP server exposing the SAME capabilities can be used by
ANY MCP-compliant client — Claude Desktop, a custom agent,
someone ELSE'S tooling entirely — without EACH ONE reimplementing
the SAME tool logic independently. This is a genuine, real
shift from "tools baked into one agent" to "tools as a shared,
reusable service."

Common Mistakes to Watch For

  • Treating MCP as a fundamentally different concept from Chapter 2's tool-calling architecture — it's the same underlying idea, standardized and made shareable.
  • Exposing an MCP server's capabilities without genuine scope discipline — Chapter 2's tool-scoping guardrail principle applies with even more force once a server can be used by multiple, possibly untrusted clients.
  • Assuming MCP itself handles safety — this chapter's final page is explicit that the protocol doesn't replace the guardrail thinking from earlier chapters.
