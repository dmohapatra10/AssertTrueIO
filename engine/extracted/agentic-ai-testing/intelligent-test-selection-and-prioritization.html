Intelligent Test Selection and Prioritization

Prerequisites: AI-Powered Pipeline Design

What is this?

Two genuinely related but distinct questions: SELECTION asks which tests to run at all; PRIORITIZATION asks, among the selected tests, which order surfaces real problems fastest. This page covers both, since they're two halves of the same "run what matters, efficiently" concern this chapter's opening page raised.

Selection — Mapping a Change to Relevant Tests

def select_relevant_tests(changed_files, test_coverage_map):
    """Given files changed in a commit and a mapping of which
    tests exercise which files, return only genuinely relevant
    tests — this is deterministic, not reasoning-based."""
    relevant = set()
    for file in changed_files:
        relevant.update(test_coverage_map.get(file, []))
    return relevant

# changed_files = ["src/checkout/discount_validator.py"]
# test_coverage_map maps files to tests that EXERCISE them —
# built from real coverage data, e.g. pytest-cov's output
selected = select_relevant_tests(
    changed_files=["src/checkout/discount_validator.py"],
    test_coverage_map=coverage_data,
)
# → {"test_discount_code_validation", "test_checkout_flow",
#    "test_discount_stacking_rejected"} — genuinely fewer than
# all 488, with real coverage evidence backing each inclusion

Why Selection Is Deterministic, Not Reasoning-Based

Notice select_relevant_tests uses REAL coverage data — WHICH
tests actually EXERCISE which files, MEASURED, not GUESSED —
exactly the SAME exact-vs-fuzzy PRINCIPLE from Chapter 5
onward. An LLM GUESSING "which tests seem RELATED to discount
validation" would be STRICTLY weaker than ACTUAL coverage
data confirming EXACTLY which tests TOUCH that code.

Prioritization — Ordering the Selected Tests

def prioritize_tests(selected_tests, historical_data):
    """Orders tests to surface real problems FASTEST — tests
    that fail MORE often, and tests that run FASTER, both get
    priority, using genuine historical data."""
    def priority_score(test_name):
        stats = historical_data.get(test_name, {})
        fail_rate = stats.get("fail_rate", 0)
        duration_s = stats.get("avg_duration_s", 60)
        # Higher fail rate AND lower duration both increase
        # priority — surface likely problems fast and cheaply
        return fail_rate / max(duration_s, 1)

    return sorted(selected_tests, key=priority_score, reverse=True)
# Applied to this page's selected tests:
test_discount_stacking_rejected: fail_rate=0.15, duration_s=3
  → priority_score = 0.05
test_discount_code_validation:   fail_rate=0.08, duration_s=2
  → priority_score = 0.04
test_checkout_flow:              fail_rate=0.03, duration_s=45
  → priority_score = 0.0007

Running discount_stacking_rejected FIRST means a genuine
problem in the discount-code change surfaces in 3 seconds,
not after waiting 50 seconds for checkout_flow to finish too.

🧠 Think About It

Why does the priority score divide fail rate by duration, rather than just sorting by fail rate alone? A test with a high fail rate but a long duration doesn't surface problems as fast as a test with a moderate fail rate and a short duration — the genuine goal is fast feedback, not just running the historically riskiest test first regardless of cost. Dividing by duration directly encodes "likely to fail, AND cheap to find out" into a single score, matching this chapter's opening page's own emphasis on speed as a genuine, real value, not just thoroughness for its own sake.

⚠️ Common Mistake

Using an LLM to guess test relevance from file names or descriptions rather than real coverage data. This is exactly the kind of exact-vs-fuzzy mistake Chapter 5 warned against — coverage data provides a genuinely exact answer to "which tests exercise this file," making reasoning-based guessing strictly weaker and unnecessary.

💡 Quick Tip

Selection and prioritization should be run in that order specifically — selecting the relevant subset first, then prioritizing within it — rather than prioritizing the entire 488-test suite and truncating, since the latter risks cutting off genuinely relevant tests that simply score lower on historical fail rate.

Best Practices

  • Use real, measured coverage data for test selection, never LLM-based guessing about relevance from names or descriptions alone.
  • Prioritize selected tests by a combination of fail rate and duration, optimizing for fast feedback, not just historical risk alone.
  • Select the relevant subset before prioritizing within it, rather than prioritizing the full suite and truncating.

🎯 Key Takeaway

  • Test selection and prioritization are two related but distinct pipeline-scale decisions — which tests to run, and in what order to run them.
  • Selection should be deterministic, grounded in real coverage data, not reasoning-based guessing about relevance.
  • Prioritization should optimize for fast, cheap detection of real problems, combining fail rate and duration rather than either alone.

COVERAGE data can ITSELF be STALE or INCOMPLETE — a GENUINELY subtle, INDIRECT dependency (say, a SHARED configuration VALUE two SEEMINGLY unrelated MODULES both DEPEND on) might NOT be CAPTURED by STANDARD code-coverage TOOLING, meaning SELECTION based PURELY on coverage COULD miss a GENUINELY relevant test.

STANDARD coverage TOOLS (like pytest-COV) track WHICH lines

  MODULES rely ON) might NOT be REFLECTED in LINE-level
  coverage AT ALL, EVEN though a CHANGE could GENUINELY break
  a TEST that appears COMPLETELY "unrelated" by COVERAGE

safeguard:

How would you extend THIS page's prioritize_tests function to ALSO account for a test's RECENCY of last FAILURE, not JUST its overall HISTORICAL fail rate?▾

A GENUINELY useful extension would WEIGHT recent FAILURES more HEAVILY than OLDER ones, since a test that FAILED YESTERDAY is ARGUABLY MORE likely to be GENUINELY problematic RIGHT NOW than ONE whose ONLY historical FAILURE was SIX months AGO, DESPITE both POTENTIALLY having the SAME OVERALL fail RATE.

def priority_score_with_recency(test_name, historical_data,
                                   current_date):
    stats = historical_data.get(test_name, {})
    fail_rate = stats.get("fail_rate", 0)
    duration_s = stats.get("avg_duration_s", 60)
    last_failure_date = stats.get("last_failure_date")

    recency_boost = 1.0
    if last_failure_date:
        days_since = (current_date - last_failure_date).days
        if days_since < 7:
            recency_boost = 2.0  # RECENT failures GENUINELY
                # warrant MORE attention than OLD, POSSIBLY
                # already-RESOLVED ones

    return (fail_rate * recency_boost) / max(duration_s, 1)

This GENUINELY extends this PAGE'S own scoring LOGIC with a REALISTIC, PRACTICAL refinement — a test's OVERALL historical fail RATE treats a FAILURE from SIX months AGO (POSSIBLY already FIXED) the SAME as ONE from YESTERDAY (POSSIBLY still an ACTIVE, ONGOING problem) — WEIGHTING recent FAILURES more HEAVILY produces a GENUINELY more USEFUL priority ORDERING, directly EXTENDING this page's ORIGINAL "FAST, cheap DETECTION of REAL problems" GOAL with a MORE nuanced, TIME-aware SIGNAL.
