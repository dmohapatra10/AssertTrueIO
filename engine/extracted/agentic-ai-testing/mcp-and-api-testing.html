What is this, and why it's genuinely simpler than browser tools

API testing tools are genuinely stateless in a way browser tools aren't — each request is independent, with no shared "current page" to maintain across calls. This page wraps Chapter 6 and 10's capabilities as MCP tools, without the previous page's persistence complication.

Chapter 6 and 10's Capabilities, Wrapped as MCP

@mcp.tool()
def make_api_request(method: str, endpoint: str, json_body: dict = None) -> dict:
    """Makes an HTTP request to ShopEasy's staging API. Method
    must be GET, POST, PATCH, or DELETE. Endpoint should start
    with '/', e.g. '/orders/1042'."""
    import requests
    if method not in ("GET", "POST", "PATCH", "DELETE"):
        return {"error": f"Method '{method}' not allowed"}
    response = requests.request(
        method, f"https://staging.shopeasy.example.com/api{endpoint}",
        json=json_body, timeout=10
    )
    return {"status_code": response.status_code,
            "body": response.json() if response.content else None}

@mcp.tool()
def validate_against_schema(response_body: dict, openapi_schema: dict) -> dict:
    """Validates a response body against a given OpenAPI JSON
    schema, using Chapter 10's own jsonschema-based approach."""
    import jsonschema
    try:
        jsonschema.validate(instance=response_body, schema=openapi_schema)
        return {"valid": True, "errors": []}
    except jsonschema.ValidationError as e:
        return {"valid": False, "errors": [str(e)]}

@mcp.resource("shopeasy://api/openapi-spec")
def get_openapi_spec() -> dict:
    """ShopEasy's current OpenAPI specification, for use with
    Chapter 10's spec-driven generation techniques."""
    import json
    with open("shopeasy_openapi.json") as f:
        return json.load(f)

The One Genuine Subtlety — What Should Be a Tool vs. a Resource Here

Notice get_openapi_spec is a RESOURCE, not a tool — applying
the "ten times in a row" test directly: reading the SAME spec
file repeatedly is genuinely safe and cheap, no different from
Chapter 5's own get_return_policy example. But make_api_request
and validate_against_schema are GENUINELY tools — one has real
network effects (a POST or DELETE could genuinely change real
data), and the other, while read-only in effect, performs real
per-call computation against ARBITRARY input, not a fixed file.

🧠 Think About It

Why might make_api_request deserve MORE caution from a client's reasoning than the browser tools from the previous page, even though both are "just" tools? A GET request is genuinely safe to repeat, but this single tool ALSO handles POST, PATCH, and DELETE — methods with real, potentially destructive side effects on ShopEasy's actual order data. Unlike the previous page's browser tools, where each individual tool (navigate, click) has a narrower, more predictable effect, this one tool's risk profile depends entirely on which method a client's reasoning chooses to pass — making the method-level validation inside the tool genuinely load-bearing, not just defensive boilerplate.

⚠️ Common Mistake

Treating all API-related MCP tools as equally low-risk because "it's just an API call." A GET request and a DELETE request through the same tool carry genuinely different real consequences — a well-designed tool needs to account for this range, not treat every call as equivalently safe.

💡 Quick Tip

Exposing the OpenAPI spec itself as a resource (this page's approach) lets a client's reasoning consult it directly when deciding how to call make_api_request — rather than the tool needing to somehow embed or duplicate schema knowledge, the client can read the resource and reason about the right request shape itself.

Best Practices

  • Recognize that API tools are genuinely stateless, unlike browser tools, simplifying their MCP implementation.
  • Account for the full range of risk a single tool might carry when it handles multiple HTTP methods with different real consequences.
  • Expose reference material like an OpenAPI spec as a resource, letting client reasoning consult it directly rather than duplicating that knowledge inside tools.

🎯 Key Takeaway

  • API testing tools are genuinely simpler to expose via MCP than browser tools, since they don't need shared, persistent state across calls.
  • A single tool handling multiple HTTP methods carries a genuinely wider risk range than the previous page's narrower, single-purpose browser tools.
  • Reference material like a formal spec belongs as a resource, letting client reasoning consult it directly when constructing tool calls.

Interview Questions

A teammate argues browser and API tools should be architected identically since "they're both just MCP tools." What genuine difference does this page identify that argues against this?▾

Browser tools genuinely need shared, persistent state across calls (the previous page's core complication); API tools are genuinely stateless, each call independent — treating them identically would either add unnecessary complexity to API tools or miss the real state-management need browser tools have.

Why BROWSER tools GENUINELY need shared state:
navigate_to and find_and_click need to operate on the SAME
  live PAGE — WITHOUT persistence, EACH call would work on a
  FRESH, UNRELATED browser instance, EXACTLY the FAILURE mode
  the PREVIOUS page's FIRST interview question DESCRIBED.

Why API tools GENUINELY don't need this:
make_api_request(method="GET", endpoint="/orders/1042") is
  COMPLETELY self-CONTAINED — it needs NOTHING from a PREVIOUS
  call to WORK correctly, UNLIKE find_and_click's DEPENDENCE
  on a PRIOR navigate_to having ALREADY set up the PAGE.

The teammate's INSTINCT toward CONSISTENCY is REASONABLE, but "BOTH are MCP tools" DOESN'T mean "BOTH need the SAME architecture" — the UNDERLYING NATURE of the CAPABILITY (STATEFUL browser AUTOMATION vs. STATELESS API calls) GENUINELY determines WHAT'S actually NEEDED, exactly THIS page's OWN opening ARGUMENT.

Why does this page argue make_api_request deserves MORE caution than the previous page's browser tools, even though "it's just an API call"?▾

A SINGLE tool handling FOUR different HTTP METHODS has a WIDER risk RANGE than EACH of the PREVIOUS page's NARROWER, single-PURPOSE tools — a CLIENT choosing DELETE through THIS one tool carries GENUINELY different, HIGHER stakes than choosing GET, and the TOOL itself must ACCOUNT for this ENTIRE range.

Why EACH browser tool (find_and_click, navigate_to)
individually carries a NARROWER, more PREDICTABLE risk:
EACH tool does ONE thing — click AN element, or NAVIGATE to a
  URL. The RISK PROFILE of EACH individual TOOL is RELATIVELY
  narrow and PREDICTABLE.

Why make_api_request's RISK profile is GENUINELY wider:
ONE tool HANDLES GET (safe, READ-only), POST (creates REAL
  data), PATCH (MODIFIES real DATA), and DELETE (REMOVES real
  data) — a SINGLE tool call COULD range from COMPLETELY
  harmless to GENUINELY destructive, DEPENDING ENTIRELY on
  WHICH method the CLIENT'S reasoning HAPPENS to choose.

This is EXACTLY why THIS page's "Try It YOURSELF" exercise SUGGESTS SPLITTING this INTO separate TOOLS — a SINGLE tool COVERING such a WIDE risk RANGE is GENUINELY harder for a CLIENT'S reasoning (and a HUMAN reviewer) to REASON about SAFELY than SEVERAL, NARROWER tools EACH with a MORE PREDICTABLE, CONSISTENT risk LEVEL.

Explain why exposing the OpenAPI spec as a RESOURCE, rather than EMBEDDING schema knowledge INSIDE make_api_request itself, is a GENUINELY better design.▾

EMBEDDING schema KNOWLEDGE inside the TOOL would COUPLE the TOOL'S implementation to a SPECIFIC spec VERSION, and would HIDE that KNOWLEDGE from the CLIENT'S own REASONING — exposing it SEPARATELY as a RESOURCE lets the CLIENT consult it DIRECTLY when DECIDING how to CONSTRUCT a request.

Why EMBEDDING schema logic INSIDE the tool would be GENUINELY
worse:
The TOOL would need to somehow VALIDATE or GUIDE requests
  based on a SCHEMA it INTERNALLY knows about — but the
  CLIENT'S reasoning, DECIDING what REQUEST to CONSTRUCT in
  the FIRST place, would have NO direct ACCESS to that SAME
  schema KNOWLEDGE, making it HARDER for the client to
  CONSTRUCT a GENUINELY well-formed request BEFORE ever
  CALLING the tool.

Why EXPOSING it as a SEPARATE resource (THIS page's ACTUAL
approach) is GENUINELY better:
The CLIENT can READ get_openapi_spec DIRECTLY, using Chapter
  10's OWN generation techniques to CONSTRUCT a well-FORMED
  request BEFORE calling make_api_request — the SCHEMA
  knowledge is AVAILABLE to BOTH the tool (for VALIDATION,
  via THIS page's SEPARATE validate_against_schema tool) AND
  the CLIENT'S own REASONING (for CONSTRUCTION).

This is a GENUINELY important design PRINCIPLE — making RELEVANT KNOWLEDGE (the SCHEMA) DIRECTLY accessible to the REASONING side, rather than BURYING it inside a TOOL'S internal IMPLEMENTATION, lets the CLIENT make BETTER-INFORMED decisions BEFORE ever CALLING a tool, not JUST react to VALIDATION failures AFTER the FACT.

Why might validate_against_schema be classified as a TOOL rather than a RESOURCE, despite BEING read-only in EFFECT (it doesn't MODIFY anything)?▾

This DIRECTLY mirrors the PREVIOUS page's get_current_page_summary REASONING — being READ-only ISN'T the SAME as being a RESOURCE; the DISTINGUISHING factor is WHETHER it performs GENUINE, per-CALL computation on ARBITRARY input, WHICH validate_against_schema CLEARLY does.

Why "READ-only" ALONE doesn't QUALIFY something as a
resource:
validate_against_schema doesn't MODIFY anything, TRUE — but
  it ALSO doesn't just RETURN a FIXED, EXISTING piece of DATA
  the WAY get_openapi_spec does. It performs REAL, meaningful
  COMPUTATION (SCHEMA validation LOGIC) against WHATEVER
  ARBITRARY response_body and SCHEMA the CLIENT happens to
  PROVIDE.

Why this MAKES it GENUINELY more TOOL-like:
The "TEN times in a ROW" test, applied CAREFULLY: calling it
  TEN times with TEN DIFFERENT (response_body, schema) PAIRS
  would GENUINELY produce TEN DIFFERENT, MEANINGFUL results —
  UNLIKE a TRUE resource, WHERE repeated CALLS with the SAME
  implicit "input" (JUST read the FILE) always RETURN the SAME
  thing.

This is a GENUINELY useful, PRECISE refinement of the TOOL-vs-resource TEST — "READ-only" and "RESOURCE" are NOT SYNONYMS; the REAL distinguishing QUESTION is WHETHER the CAPABILITY performs GENUINE, PARAMETERIZED computation (TOOL-like) VERSUS simply RETURNING FIXED, EXISTING data (RESOURCE-like), REGARDLESS of WHETHER either ONE happens to MODIFY anything.
