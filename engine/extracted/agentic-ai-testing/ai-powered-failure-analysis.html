A Different Kind of Problem

Every chapter so far had an agent doing something and checking whether it worked. This chapter is about what happens AFTER something doesn't — a red test tells you almost nothing on its own; figuring out WHY is genuinely the harder, more valuable half of the work. Seven focused pages:

  1. Understanding Test Failures — what a failure signal actually tells you, and doesn't
  2. Failure Classification — six genuinely different reasons a test can fail
  3. Stack Trace Analysis — reading what the code itself reports
  4. Analyzing Screenshots and Traces for Failure Diagnosis — using what Chapter 5 introduced, now for diagnosis rather than assertion
  5. Log Analysis — what application and system logs add that a stack trace can't
  6. Root Cause Analysis — combining every evidence source into one genuine diagnosis
  7. AI-Generated Failure Reports — turning a diagnosis into something a human can immediately act on

The Six Categories This Chapter Teaches

Every test failure genuinely falls into one of these — the
CORE skill this chapter builds is distinguishing them reliably:

1. Application defect  — the app is genuinely broken
2. Test defect          — the test itself has a bug
3. Locator problem        — the UI changed, the test didn't
4. Environment problem      — staging/config issue, not a real bug
5. Network problem            — a request genuinely failed to complete
6. Flaky behavior                — genuinely inconsistent, timing-dependent

A Deliberate Note on Overlap With Chapter 5

Chapter 5's Screenshot and Trace Analysis page used screenshots and traces to check whether something looked CORRECT during a live run. This chapter uses the exact same underlying artifacts for a genuinely different purpose — diagnosing WHY something already went WRONG. Same tools, deliberately different job.

Common Mistakes to Watch For

  • Assuming every red test means the application has a real bug — this chapter's whole point is that this is often not true.
  • Diagnosing from a stack trace alone — genuinely reliable diagnosis usually needs multiple evidence sources reasoned about together.
  • Reporting "it failed" without a genuine classification — this wastes a human's time re-doing diagnostic work an agent should have already done.

What You'll Be Able to Do

By the end of the seven pages that follow, you should be able to reliably distinguish six genuinely different failure categories, read a stack trace, screenshot, trace, and log file for real diagnostic signal, combine them into one coherent root-cause diagnosis, and produce a failure report a human can act on immediately rather than re-investigate from scratch.
