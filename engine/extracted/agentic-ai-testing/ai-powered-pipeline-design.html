What is this?

ShopEasy's pipeline structure (lint → unit → integration → E2E → deploy) wasn't arbitrary — it reflects genuine dependencies and genuine cost tradeoffs. This page is about using AI reasoning to evaluate and suggest that structure, grounded in real data about the pipeline, not just plausible-sounding advice.

Reasoning About Structure From Real Data

def analyze_pipeline_structure(stage_history, client):
    prompt = f"""Here is real historical data about this CI
pipeline's stages: {stage_history}

Given each stage's typical duration and failure rate, does the
CURRENT ordering (lint, unit, integration, E2E, deploy) make
sense? Are there stages that could run in PARALLEL rather than
sequentially, given what you can tell about their actual
dependencies from this data?"""
    result = client.messages.create(
        model="claude-sonnet-4-6", max_tokens=500,
        messages=[{"role": "user", "content": prompt}]
    )
    return result.content[0].text
# Real data, and a genuinely useful finding:
stage_history = {
    "lint": {"avg_duration_s": 25, "failure_rate": 0.02},
    "unit_tests": {"avg_duration_s": 120, "failure_rate": 0.08},
    "integration_tests": {"avg_duration_s": 360, "failure_rate": 0.05},
    "e2e_tests": {"avg_duration_s": 1080, "failure_rate": 0.12},
}

"Lint and unit tests both have low duration and don't appear
to depend on each other's output based on this data — running
them in PARALLEL rather than sequentially could save roughly
25 seconds per run with no apparent loss of signal. E2E tests
have both the HIGHEST duration and the HIGHEST failure rate —
worth confirming this stage's placement LAST is genuinely
intentional (catching real problems only after cheaper stages
already passed) rather than simply historical convention."

Why This Needs Real Data, Not Just Plausible Reasoning

Without the ACTUAL duration and failure-rate numbers, an LLM
asked "how should this pipeline be structured" would be
REASONING from GENERAL software engineering conventions —
GENUINELY useful, but NOT grounded in THIS SPECIFIC pipeline's
ACTUAL behavior. The REAL numbers (25s lint, 12% E2E failure
rate) are what let the SUGGESTION above be GENUINELY specific
and ACTIONABLE, not just generically plausible advice.

🧠 Think About It

Why does this page's example specifically flag the E2E stage's placement as worth CONFIRMING rather than just recommending a change? The data shows E2E has both the highest cost and highest failure rate — this is CONSISTENT with either a deliberate, sound design (catch problems only after cheaper stages already passed, minimizing wasted E2E runs on changes that would have failed lint or unit tests anyway) or an unexamined default that happens to look reasonable. The reasoning can't tell these apart from the data alone — flagging it for confirmation, rather than asserting a change, respects that genuine uncertainty rather than overstating confidence.

⚠️ Common Mistake

Asking an LLM to suggest pipeline structure without providing real, current data about the pipeline's own actual stages. This produces genuinely plausible-sounding but ungrounded advice — exactly the same gap Chapter 11's LLM-as-a-Judge page warned about for evaluation without reference information.

💡 Quick Tip

When a pipeline-design suggestion flags something as worth "confirming" rather than asserting a definite recommendation, that phrasing itself is a genuinely useful signal — it distinguishes findings the data can directly support from ones that need additional context a human actually has.

Best Practices

  • Ground pipeline-design reasoning in real, current data about the specific pipeline being analyzed, not generic conventions.
  • Let genuinely ambiguous findings be flagged as worth confirming rather than asserted as definite recommendations.
  • Treat this as a tool for generating well-reasoned suggestions a human reviews, not an automatic restructuring authority.

🎯 Key Takeaway

  • Pipeline-design reasoning needs real, specific data about the pipeline's actual stages to produce genuinely actionable suggestions, not generic advice.
  • A finding that's consistent with multiple explanations should be flagged for human confirmation, not asserted with unwarranted confidence.
  • This technique generates suggestions for human review, not an automated authority to restructure a pipeline unilaterally.

How would you extend this page's approach to specifically check WHETHER lint and unit tests GENUINELY have no dependency on each OTHER, rather than just ASSUMING this from DURATION data alone?▾

A GENUINELY rigorous check would EXAMINE the ACTUAL pipeline configuration (WHICH stage's OUTPUT, if any, FEEDS into the OTHER) rather than INFERRING independence PURELY from DURATION and FAILURE-rate NUMBERS, which DON'T directly CAPTURE dependency INFORMATION at ALL.

def verify_stage_independence(pipeline_config, stage_a, stage_b):
    """Checks whether stage_a's OUTPUTS are actually CONSUMED
    as INPUTS by stage_b, or vice versa, using the pipeline's
    OWN configuration — NOT inferred from duration/failure
    data ALONE, which says NOTHING about genuine dependencies."""
    stage_a_outputs = pipeline_config[stage_a].get("outputs", [])
    stage_b_inputs = pipeline_config[stage_b].get("inputs", [])
    stage_b_outputs = pipeline_config[stage_b].get("outputs", [])
    stage_a_inputs = pipeline_config[stage_a].get("inputs", [])

    shared = (set(stage_a_outputs) & set(stage_b_inputs)) | \
             (set(stage_b_outputs) & set(stage_a_inputs))
    return {
        "genuinely_independent": len(shared) == 0,
        "shared_artifacts": list(shared),
    }

This EXPLICITLY addresses a GENUINE gap in THIS page's ORIGINAL example — the LLM's suggestion was BASED on duration and FAILURE-rate data, which is USEFUL for COST reasoning but SAYS NOTHING DIRECTLY about ACTUAL dependencies; a GENUINELY rigorous pipeline-DESIGN process should VERIFY independence AGAINST the pipeline's OWN real CONFIGURATION, not just INFER it from UNRELATED metrics, EXACTLY the KIND of additional, DELIBERATE verification a HUMAN reviewer (per the PREVIOUS question's OWN argument) should APPLY before ACTUALLY implementing a PARALLELIZATION suggestion.
