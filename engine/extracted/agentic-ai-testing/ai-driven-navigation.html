A Real Navigation Trace

GOAL: "Find a wireless mouse under $30 with good stock
availability."

REASONER's rough plan (Chapter 2's Agent Planning, in action):
  1. Search for "wireless mouse"
  2. Review results for ones under $30
  3. Check stock status of qualifying results
  4. Identify one that's genuinely in stock

Step 1: search(query="wireless mouse")
  → "Searched for 'wireless mouse'"

Step 2: get_search_results()
  → [{"name": "Wireless Mouse Pro", "price": "$34.99", "in_stock": true},
     {"name": "Basic Wireless Mouse", "price": "$18.99", "in_stock": false},
     {"name": "Ergo Wireless Mouse", "price": "$27.50", "in_stock": true}]

Step 3: REASONING over structured results (no new tool call
  needed — this is genuine reasoning over data already in hand):
  "Filtering for under $30: 'Basic Wireless Mouse' ($18.99) and
  'Ergo Wireless Mouse' ($27.50) qualify. Of these, 'Basic
  Wireless Mouse' is out of stock. 'Ergo Wireless Mouse' is
  genuinely in stock and meets both criteria."

RESULT: "Ergo Wireless Mouse" identified — no further browser
action needed, since the goal was to FIND a match, not
necessarily purchase it.

Why This Is Planning, Not Pure Improvisation

❌ Pure, step-by-step improvisation (no upfront plan at all):
  Would require a full LLM reasoning call after EVERY single
  tiny action, even ones that don't genuinely need independent
  judgment — genuinely wasteful and slower than necessary.

✅ This page's actual approach — a rough plan, THEN reasoning
   within it (Chapter 2's real pattern):
  The RESEARCH plan ("search, review, check stock, identify")
  is decided largely upfront. Individual REASONING happens
  where it's actually needed — interpreting search results,
  applying the price/stock criteria — not for every trivial
  mechanical step along the way.

Handling Navigation That Doesn't Go as Planned

What if step 2's search returns ZERO results at all?

REASONER, encountering this genuinely unplanned situation:
  "The search for 'wireless mouse' returned no results — this
  wasn't anticipated by the original plan. Possible causes:
  the exact phrase might not match ShopEasy's indexing, or
  wireless mice may genuinely not be in stock currently. I'll
  try a broader search term, 'mouse', before concluding no
  match exists."

This is exactly Chapter 2's Agent Planning re-planning

🧠 Think About It

Why might treating every single browser action as requiring an independent, full LLM reasoning call be genuinely wasteful, given this page's example? Steps like "read the structured search results and check which ones are under $30" are simple, mechanical comparisons the reasoner can do within a SINGLE reasoning pass, using data it already has — forcing a separate LLM call for each individual comparison would add real cost and latency without adding any genuine decision-making value, since nothing about "is $27.50 less than $30" requires fresh, real-time observation of the live page.

⚠️ Common Mistake

Writing an agent's rough navigation plan so specifically that it can't adapt when reality diverges even slightly — exactly Chapter 2's Agent Planning warning about overly rigid plans, now shown in a concrete browser-navigation context where "the exact search term didn't match" is a genuinely common, real occurrence.

💡 Quick Tip

When a navigation goal involves genuine comparison or filtering logic (like "under $30"), it's often more efficient to fetch structured data ONCE via a tool call, then let the reasoner work through the comparison entirely within its own reasoning — rather than making a separate tool call for every individual filtering decision.

Best Practices

  • Let the reasoner produce a rough navigation plan upfront, reserving individual LLM reasoning calls for points that genuinely need fresh observation or judgment.
  • Build genuine re-planning into navigation, since real search terms and real page structures won't always match initial assumptions.
  • Fetch structured data once and reason over it directly, rather than making a separate tool call for every small filtering or comparison step.

🎯 Key Takeaway

  • AI-driven navigation genuinely follows Chapter 2's plan-then-reason pattern — a rough upfront plan, with reasoning applied where real judgment is actually needed.
  • Not every mechanical step needs an independent LLM call — comparisons over data already in hand can happen within a single reasoning pass.
  • Genuine re-planning (trying a broader search term, for instance) is a real, expected part of navigation, not a failure state.

Interview Questions

A junior engineer's agent makes a separate LLM call to check the price of EACH individual search result one at a time, rather than reasoning over all of them together. What would you suggest, and why?▾

I'd suggest fetching all results in one structured call, then reasoning over the complete set in a single pass — exactly this page's approach — since checking each price individually adds real cost and latency without adding genuine decision-making value.

The inefficient pattern (per-result LLM calls):
For EACH of the 3 search results, a separate LLM call asking
  "is this one under $30?" — genuinely wasteful, since this is
  a SIMPLE numeric comparison the reasoner could do for ALL
  three within one single reasoning pass, using data it
  already has in hand.

The efficient pattern (this page's actual approach):
ONE call to get_search_results() returns all 3 results
  structured. ONE subsequent reasoning step evaluates "which
  of these are under $30 AND in stock" across the ENTIRE set
  at once — genuinely equivalent decision quality, at a
  fraction of the real cost and latency.

The general principle: reserve separate reasoning steps for points that genuinely need them (a new observation, a real decision point) — batching data retrieval and reasoning over the full set together, when the data doesn't change between individual comparisons, is a genuine, practical efficiency gain.

Why does this page's agent try a broader search term ("mouse" instead of "wireless mouse") rather than immediately reporting failure when the first search returns zero results?▾

Because zero results could genuinely mean several different things — a real, correct absence of matching products, or simply a search-term mismatch — and immediately reporting failure without distinguishing between these would be a premature, potentially incorrect conclusion.

Why immediately reporting failure would be premature:
"No results for 'wireless mouse'" doesn't necessarily mean
  ShopEasy has NO wireless mice in stock — it might mean the
  SEARCH INDEXING doesn't exactly match that specific phrase
  (perhaps products are tagged "cordless mouse" instead), a
  genuinely different, more mundane explanation.

Why trying a broader term first is more genuinely useful:
If "mouse" (broader) DOES return results, this confirms the
  issue was specifically the exact phrase, not a genuine
  absence of matching products — a MORE ACCURATE, useful
  finding than a premature "no wireless mice available" report
  would have been.

This connects directly to Chapter 1's honest-limitations discussion — jumping to a confident conclusion without genuinely investigating alternative explanations first is exactly the kind of shallow, premature judgment a genuinely careful agent (and a careful human tester) should avoid.

Why might an agent's rough navigation plan genuinely need to change if ShopEasy's search results page structure changed (e.g., results loading via infinite scroll instead of all at once)?▾

The PLAN's actual content ("search, review, check stock, identify") stays genuinely valid at a high level — but the specific TOOLS available and how the reasoner uses them would need to account for the new loading behavior, connecting directly to the previous page's scroll_to_bottom tool.

What stays the SAME with the structural change:
The rough plan itself — search, review results, check stock,
  identify a match — remains genuinely valid regardless of
  HOW results happen to load on the page.

What genuinely NEEDS to adapt:
The reasoner would need to recognize (from a fresh, current
  observation) that only a PARTIAL set of results is initially
  visible, and decide to call scroll_to_bottom() BEFORE trusting
  get_search_results() to have the complete picture — exactly
  the kind of real, current-observation-driven decision that
  belongs in REASONING, not something the original rough plan
  needed to have anticipated in advance.

This is a genuinely good illustration of why plans stay appropriately rough (Chapter 2's own argument) — a plan specifying exact mechanics upfront would have needed REWRITING for this structural change, while a rough, goal-oriented plan combined with real-time reasoning adapts naturally without needing to be rewritten at all.

How would you modify this page's example to handle a genuinely ambiguous goal, like "find a good mouse" (with no explicit price or stock criteria stated at all)?▾

This connects directly back to Chapter 2's Agent Instructions page — genuine ambiguity should be explicitly noted, not silently resolved by guessing at unstated criteria, and the agent's actual behavior should reflect this.

What a GOOD response to this ambiguous goal looks like:
Rather than silently deciding "good" means "cheapest" or
  "highest-rated" or "most in-stock" (all plausible but
  genuinely DIFFERENT interpretations), a well-instructed
  agent should EXPLICITLY surface this: "The goal 'a good
  mouse' doesn't specify what makes it 'good' — price? Rating?
  Stock availability? I found several wireless mice; without
  more specific criteria, here's what's currently available:
  [list], but I'd recommend clarifying what 'good' should
  actually mean before treating any one choice as definitive."

This directly applies Chapter 2's instructions guidance
  ("note ambiguity explicitly rather than silently guessing")
  to a concrete NAVIGATION scenario, rather than silently
  picking one interpretation and presenting it as if it were
  the obviously correct one.

This is a genuinely important pattern worth internalizing: an ambiguous GOAL should produce an agent response that surfaces the ambiguity, not one that silently resolves it and reports a confident-sounding but arbitrary result.
