Tracing Agent Decisions

Prerequisites: Structured Logging for AI Agents

What is this, and how it differs from Chapter 12

Chapter 12's Testing Agent Planning page evaluated ONE plan, for ONE deliberately chosen test scenario. A trace does the same KIND of capture — the full plan-reason-act-observe chain — but for EVERY real production run, continuously, not a single controlled test.

A Genuine Trace, One Real Production Run

{
  "run_id": "run-88213",
  "objective": "Verify a user can add an item to their cart.",
  "initial_plan": [
    "Navigate to product page",
    "Click 'Add to Cart'",
    "Confirm cart total reflects the new item"
  ],
  "steps": [
    {"step": 1, "reasoning": "Starting with navigation, per plan step 1.",
     "action": "navigate_to", "result": "success"},
    {"step": 2, "reasoning": "Product page loaded; clicking Add to Cart.",
     "action": "click_element", "result": "success"},
    {"step": 3, "reasoning": "Checking cart total to confirm success.",
     "action": "get_page_text", "result": "cart-total: $27.50"}
  ],
  "replanning_events": [],
  "final_outcome": "success",
  "total_duration_ms": 3420
}

Why This Needs to Happen for EVERY Run, Not Just Test Runs

Chapter 12's PLAN evaluation ran ONCE, on ONE test SCENARIO,
DELIBERATELY constructed. A TRACE captures the SAME kind of
information but for EVERY SINGLE production RUN — hundreds
per DAY — because the PREVIOUS page's ENTIRE argument was that
UNANTICIPATED problems ONLY reveal themselves ACROSS many
REAL runs, not ONE controlled test.

WITHOUT continuous TRACING, if a PRODUCTION run's REASONING
GENUINELY goes wrong in a way NOBODY tested for, THERE'S
simply no RECORD of WHAT the agent was THINKING when it
happened — exactly Chapter 12's OWN "duplicate click" problem,
but NOW happening in PRODUCTION with NO evidence to
INVESTIGATE it AFTERWARD.

🧠 Think About It

Why does this trace include the replanning_events field even when it's empty for this particular run? Chapter 2's own architecture discussion established that re-planning is a real, expected agent behavior when observations don't match expectations. Capturing this field — even as an empty list — means a future query can distinguish "this run never needed to re-plan" from "we simply didn't record whether it did." An absent field is genuinely ambiguous; an explicitly empty field is a confirmed, positive fact worth having on record.

⚠️ Common Mistake

Reserving detailed reasoning traces for test runs and deliberate debugging sessions only, treating full tracing as too expensive for routine production use. This misses the previous page's central point — the problems worth catching are specifically the ones that occur in real, ordinary production runs nobody deliberately investigated.

💡 Quick Tip

Storing the full reasoning text for every step (not just the action taken) costs real storage space, but it's exactly what makes a later investigation like Chapter 12's duplicate-click analysis possible after the fact — trimming reasoning text to save space defeats much of tracing's genuine purpose.

Best Practices

  • Trace every production run, not just deliberate test scenarios, since unanticipated problems specifically emerge from routine, real usage.
  • Capture fields explicitly, even when empty, to distinguish a confirmed absence from an unrecorded unknown.
  • Preserve full reasoning text, not just actions taken, since reasoning is what makes later investigation of unsound decisions possible.

🎯 Key Takeaway

  • Tracing captures the same plan-reason-act-observe information Chapter 12 evaluated for one test scenario, but for every real production run continuously.
  • Without continuous tracing, an unanticipated production reasoning failure leaves no record to investigate after the fact.
  • Explicitly recording fields like re-planning events, even when empty, preserves a confirmed fact rather than an ambiguous absence.

Why does this page argue an EXPLICITLY empty replanning_events field is MEANINGFULLY different from the FIELD simply being ABSENT?▾

An ABSENT field is GENUINELY ambiguous — it COULD mean "NOTHING happened" or IT could mean "we SIMPLY didn't RECORD this" — an EXPLICITLY EMPTY field REMOVES that AMBIGUITY, CONFIRMING the POSITIVE fact that NO re-planning GENUINELY occurred.

What an ABSENT field GENUINELY leaves UNCERTAIN:
IF replanning_events simply DOESN'T appear in a TRACE, a
  FUTURE analyst has NO way to DISTINGUISH "this run NEVER
  needed to RE-plan" FROM "our LOGGING system FAILED to
  CAPTURE this field FOR this particular run" — a GENUINE,
  meaningful AMBIGUITY.

What an EXPLICITLY EMPTY field CONFIRMS instead:
"replanning_events": [] is a POSITIVE, CONFIRMED statement —
  the SYSTEM actively CHECKED for re-PLANNING events and
  FOUND none, REMOVING the AMBIGUITY entirely and PROVIDING
  a GENUINE, reliable FACT for future ANALYSIS to build
  ON.

This is a GENUINELY important, PRACTICAL distinction in OBSERVABILITY design — DELIBERATE, explicit RECORDING of a NEGATIVE or EMPTY result is MEANINGFULLY different FROM simply NOT recording ANYTHING, and CONFLATING the TWO removes GENUINE, useful INFORMATION from the TRACE.

Explain why THIS page insists on preserving FULL reasoning TEXT, not just the ACTIONS taken, connecting DIRECTLY to Chapter 12's OWN duplicate-click EXAMPLE.▾

Chapter 12's INVESTIGATION SPECIFICALLY needed to know WHAT the agent was REASONING at the MOMENT of the DUPLICATE click — WITHOUT the reasoning TEXT itself, ONLY the ACTION (click_element, TWICE) would be RECORDED, with NO way to DETERMINE whether it WAS a genuine ERROR-recovery attempt OR unexplained, UNSOUND repetition.

What TRACING only the ACTION (without REASONING) would
GENUINELY lose:
"click_element(role='button', NAME='Log In')" appearing
  TWICE tells you WHAT happened, but NOTHING about WHY —
  EXACTLY the GAP Chapter 12's OWN example STRUGGLED with,
  needing to INVESTIGATE separately WHETHER this was a
  GENUINE recovery ATTEMPT or UNEXPLAINED repetition.

What PRESERVING the REASONING text GENUINELY provides:
"the PREVIOUS click may NOT have registered; ATTEMPTING
  again" — this DIRECTLY answers the QUESTION Chapter 12's
  investigation NEEDED to ask, WITHOUT requiring SEPARATE,
  after-the-FACT investigation to RECONSTRUCT what the AGENT
  was actually THINKING.

This is a DIRECT, deliberate CONNECTION to Chapter 12's OWN foundational EXAMPLE — TRACING exists SPECIFICALLY to make THIS kind of investigation POSSIBLE without needing to RECONSTRUCT reasoning AFTER the fact, which is EXACTLY why TRIMMING reasoning text to SAVE storage space WOULD genuinely UNDERMINE tracing's CORE purpose.

This MIRRORS the SAME "recurring LOGS need a CADENCE, not an ARCHIVE" principle FROM this COURSE'S own MEMORY-management GUIDANCE — GENUINE value JUSTIFIES CAPTURING full DETAIL, but a REASONABLE, BOUNDED retention POLICY is STILL a SENSIBLE, PRACTICAL complement, not a CONTRADICTION of THIS page's ARGUMENT.
