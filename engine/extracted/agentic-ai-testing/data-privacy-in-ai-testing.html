Prerequisites: Prompt Injection Risks

What is this?

Chapter 15 argued for capturing full reasoning text and every prompt's content, for good reasons — genuine debugging and observability value. This page is about the real tension that creates: that same captured data can genuinely contain personally identifiable information, and it now exists in two new places it didn't before.

When Real Data Genuinely Can't Be Avoided

SOME testing GENUINELY requires real production DATA — a
BUG that ONLY reproduces with a SPECIFIC, real customer's
ACTUAL order history. For THESE cases, REDACTION at the
LOGGING layer (Chapter 15's OWN structured-FIELD approach)
is the GENUINE fallback:

def redact_pii_before_logging(trace_entry):
    trace_entry["objective"] = re.sub(
        r'[\w.+-]+@[\w-]+\.[\w.-]+', '[EMAIL REDACTED]',
        trace_entry["objective"]
    )
    return trace_entry

🧠 Think About It

Why does this page treat synthetic test data as the genuinely PREFERRED solution, with redaction only as a fallback for cases where real data truly can't be avoided? Redaction happens AFTER data has already reached the logging system and, more importantly, after it's already been sent to the Claude API as part of a prompt — the exposure has already occurred by the time redaction runs. Synthetic data prevents the exposure from ever happening in the first place, genuinely eliminating the risk rather than cleaning up after it. This mirrors a consistent principle: preventing a problem at its source beats detecting and correcting it downstream.

⚠️ Common Mistake

Applying redaction only at the point of storing logs, while still sending real, unredacted PII to the LLM API as part of the original prompt. This misses that the exposure to a third-party API already occurred before any redaction step — redaction after the fact doesn't undo data that's already been transmitted.

💡 Quick Tip

A genuinely useful test for whether test data handling is adequate: trace a piece of real customer data forward through the entire system — does it reach an LLM prompt, a trace log, a dashboard? Each point it reaches is a point requiring either synthetic substitution or redaction before that point, not after.

Best Practices

  • Prefer synthetic, realistic test data over real customer data wherever testing can genuinely be accomplished with it.
  • Recognize that redaction after data reaches a logging system doesn't undo exposure that already occurred when that same data was sent to an LLM API.
  • Trace real data forward through the entire system to identify every point requiring synthetic substitution or redaction before that point.

🎯 Key Takeaway

  • Chapter 15's valuable logging and tracing practices create a genuine tension: rich, debuggable detail can also be genuine personal data, now stored and transmitted in new places.
  • Synthetic test data is the genuinely preferred solution, since it prevents exposure at the source rather than cleaning up after it occurs.
  • Redaction remains a necessary fallback for cases where real data genuinely can't be avoided, but it only addresses storage, not the earlier exposure to the LLM API itself.

How would you DESIGN a genuine AUDIT to VERIFY that a TEAM'S testing SYSTEM never ACCIDENTALLY sends REAL customer PII to an LLM API, DESPITE having a SYNTHETIC-data policy in PLACE?▾

A GENUINELY useful audit SCANS actual, REAL prompts SENT to the API, CHECKING for PATTERNS that would ONLY appear in REAL customer data (a REAL email DOMAIN, a REAL-looking phone NUMBER format) that SHOULDN'T be PRESENT if the SYNTHETIC-data policy is GENUINELY being followed.

def audit_for_real_pii_leakage(recent_prompts, known_synthetic_domain):
    """Scans recent prompts for patterns suggesting real
    customer PII slipped through despite a synthetic-data
    policy being in place."""
    suspicious = []
    email_pattern = re.compile(r'[\w.+-]+@[\w-]+\.[\w.-]+')
    for prompt in recent_prompts:
        found_emails = email_pattern.findall(prompt["content"])
        for email in found_emails:
            if known_synthetic_domain not in email:
                suspicious.append({
                    "prompt_id": prompt["id"],
                    "concerning_email": email,
                    "reason": "Email domain doesn't match the "
                              "established synthetic-data domain — "
                              "possible real PII leakage.",
                })
    return suspicious

This TURNS this page's ABSTRACT synthetic-data POLICY into a CONCRETE, VERIFIABLE audit — RATHER than SIMPLY trusting that a TEAM'S synthetic-data PRACTICE is being FOLLOWED consistently, THIS check provides ONGOING, EMPIRICAL evidence about WHETHER real CUSTOMER data is GENUINELY, ACCIDENTALLY slipping THROUGH, exactly the KIND of evidence-BASED verification this COURSE has CONSISTENTLY favored OVER assuming a POLICY is being HONORED.
