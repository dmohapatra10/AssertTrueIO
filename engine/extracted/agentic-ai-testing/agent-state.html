Agent State

Prerequisites: Tools and Tool Calling

What is this?

State answers a genuinely different question than memory: not "what has the agent seen and learned," but "where, specifically, is the agent right now in its current task." Memory is history; state is the current snapshot.

State, Concretely

At any given moment during the checkout task, the agent's
STATE might be:

{
  current_plan_step: 5,          // "proceed to checkout"
  current_page: "cart",           // where it actually is right now
  task_status: "in_progress",       // not yet complete or failed
  last_action_result: "success",     // did the last action work?
  retry_count: 0                       // has this step failed before?
}

Compare this to what MEMORY holds at the same moment (from the
previous page): the full history of every step taken so far.
State is a much smaller, current-moment SNAPSHOT — not history.

Why This Distinction Matters in Practice

A reasoner deciding "what do I do next" genuinely needs BOTH,
answering different questions:

"What page am I actually on right now?" → STATE
  (current_page: "cart" — I need to navigate to checkout next)

"Have I already tried this and failed?" → MEMORY
  (step 5 was attempted once before, blocked by a modal,
  which was then dismissed)

Using memory where you need state (or vice versa) causes real
confusion — memory tells you "here's everything that's
happened," but doesn't clearly answer "where exactly am I,
right now, in this task" without additional work extracting
that from the full history.

What Happens When State Gets Lost or Corrupted

A genuinely realistic state-tracking bug:

Agent's actual, real position: on the CART page, item added
  successfully, about to navigate to checkout.

Agent's TRACKED state (due to a bug): still shows
  current_page: "product", from an earlier, stale update that
  was never correctly refreshed.

Result: reasoner, trusting the STALE tracked state, decides
  "I need to click Add to Cart" — AGAIN — because it genuinely
  believes it's still on the product page. This produces a
  duplicate cart item, or a confusing error, neither of which
  reflects what actually, truly happened.

This is a genuinely common, real class of bug — state tracking that falls out of sync with the actual, real situation, leading the agent to make decisions based on a snapshot that's no longer true.

🧠 Think About It

Why might state specifically need to be refreshed from a REAL observation at each step, rather than simply updated by the agent's own internal bookkeeping after each action? An action that the agent believes succeeded might not have — a click might silently fail, a page might not navigate as expected due to a real bug in the application itself. State based purely on "what I intended to happen" rather than "what I actually, currently observe" can drift from reality in exactly the way the example above illustrates, which is exactly why grounding state in fresh observation, not just assumption, matters.

⚠️ Common Mistake

Treating memory and state as interchangeable, or building only one and assuming it covers both needs. A reasoner that only has full history (memory) but no clear, current snapshot (state) has to re-derive "where am I right now" from scratch at every step — genuinely more error-prone and slower than maintaining a clear, current state directly.

💡 Quick Tip

A genuinely useful habit when designing or debugging an agent: whenever something goes wrong, explicitly check "did the agent's TRACKED state match its ACTUAL, real situation at that moment?" A surprising number of confusing agent failures trace back to exactly this kind of drift, not to a genuine reasoning error.

Best Practices

  • Keep state as a small, current-moment snapshot — distinct from memory's full history — refreshed from real observation, not assumption.
  • Verify an action's actual result before updating state to reflect it as successful, rather than assuming success based on intent.
  • When debugging unexpected agent behavior, explicitly check whether tracked state matches real, current reality.

🎯 Key Takeaway

  • State is a current-moment snapshot of where an agent is in its task; memory is the accumulated history of what's happened so far — genuinely different, complementary things.
  • State should be grounded in fresh, real observation at each step, not just updated based on what the agent assumed or intended to happen.
  • State drifting out of sync with real, actual reality is a genuine, common source of confusing agent failures.

Interview Questions

An agent duplicates a cart item because it believes it's still on the product page when it's actually already on the cart page. Using this page's concepts, diagnose what likely went wrong.▾

This is a textbook example of state drift — the agent's TRACKED state (current_page: "product") no longer matches its ACTUAL, real situation (already navigated to the cart page), leading the reasoner to make a decision based on stale, incorrect information.

Likely root cause:
After the successful "add to cart and navigate" action, state
  was either never updated, or was updated based on an
  ASSUMPTION ("this action should have navigated me to cart")
  rather than a FRESH, real observation confirming it actually
  did.

The fix, per this page's best practices:
After EVERY action, explicitly re-observe reality (what page
  is ACTUALLY showing right now?) and update state FROM that
  fresh observation — never purely from what the action was
  supposed to accomplish.

This diagnosis directly follows from distinguishing state (a snapshot needing to stay accurate) from memory (a history log) — the bug is specifically in HOW state gets updated, not in what the agent remembers about earlier steps.

Why can't an agent simply re-derive "where am I right now" from its full memory history, instead of maintaining separate, explicit state?▾

Technically it's possible, but it's genuinely more error-prone and computationally wasteful than maintaining an explicit, current snapshot directly — and re-derivation from history is itself vulnerable to the exact same "what actually happened vs. what was assumed" problem.

Re-deriving state from history, at every single step:
"Let me review all 8 previous actions... step 6 attempted to
  navigate to cart, which appeared to succeed based on the
  action's own reported result... so I'm PROBABLY on the cart
  page now." — this is slower, and STILL relies on trusting
  what earlier actions reported, not fresh verification.

Maintaining explicit state, refreshed from observation:
Immediately after step 6, check what page is ACTUALLY showing
  RIGHT NOW, and store that directly as current state. No
  re-derivation needed at step 7 — the answer is already
  there, and it's grounded in a genuinely fresh observation.

Explicit state isn't just a convenience — done correctly (refreshed from real observation), it's genuinely more reliable than re-deriving a snapshot from a history that itself might contain unverified assumptions.

Give an example of information that belongs in state but would be genuinely awkward or wrong to store as part of memory instead.▾

"retry_count: 2 for the current step" is a clean example — it's meaningful specifically as a CURRENT, transient value tied to the step happening right now, not as a historical fact worth remembering after the task ends.

As STATE (correct):
{ current_step: 5, retry_count: 2 }
Clearly meaningful RIGHT NOW — "I've retried this specific
  step twice, if it fails again I should try a different
  approach or give up." Directly informs the immediate decision.

As MEMORY (awkward, wrong fit):
"Step 5 was retried 2 times" sitting in a growing history log
  makes sense as a RECORD of what happened, but memory alone
  doesn't cleanly answer "is retry_count STILL at 2 right now,
  or has something reset it?" — that's a current-state question,
  not something a history log directly, cleanly answers.

The distinguishing test: does this value need to be immediately, directly available for the NEXT decision (state), or is it primarily useful as a record of what already happened (memory)? Retry counters, current position, and current status all lean firmly toward state.

Why might grounding state in "fresh observation" rather than "the agent's own intent" matter more for agentic testing specifically than it might for some other kinds of software?▾

Because the entire point of agentic testing is often to catch cases where the application DOESN'T behave as intended — an agent that trusts its own intent over real observation would systematically miss exactly the kind of genuine bugs it's supposed to be finding.

If state trusted INTENT over observation:
Agent clicks "Place Order," assumes (based on intent) that
  state should now be "order_placed: true" — even if the
  ACTUAL page shows a genuine error that the click silently
  failed to handle. The agent would proceed as if the order
  succeeded, completely missing a real, genuine bug.

If state is grounded in FRESH OBSERVATION (correct):
Agent clicks "Place Order," then ACTUALLY CHECKS what the
  page currently shows before updating state — correctly
  catching the real failure, exactly the kind of discovery
  agentic testing exists to provide.

This connects directly back to Chapter 1's discussion of agentic testing's genuine value — an agent that only tracks its own intentions rather than real, observed reality would lose exactly the capability (noticing genuinely unexpected things) that makes agentic testing worth using in the first place.

How would you design a test specifically to catch state-drift bugs in a real agent implementation, before they cause a confusing production failure?▾

A genuinely effective approach: deliberately introduce a scenario where an action's REPORTED result and its ACTUAL real-world effect diverge, and check whether the agent's state correctly reflects reality rather than the (potentially wrong) reported result.

A deliberate test case:
Simulate an action that REPORTS success but where the real
  underlying effect actually FAILED silently (a genuinely
  realistic case — a click event registers, but a subsequent
  network request the click triggered fails without a clear
  on-page error).

Check: does the agent's state correctly reflect the REAL
  outcome (still on the same page, action didn't truly
  complete) by re-observing reality, or does it incorrectly
  trust the surface-level "click succeeded" signal and update
  state to reflect an outcome that didn't actually happen?

This kind of test directly targets whether state updates are genuinely grounded in real, current observation (this page's core recommendation) or are quietly trusting assumed outcomes — exactly the gap that produces the confusing, hard-to-diagnose failures this page uses as its running example.
