Prerequisites: Tracing Agent Decisions

What is this?

The previous two pages captured data ABOUT what an agent does. This page is about a genuinely different subject — the health of the AI testing SYSTEM itself. A testing system that's silently degraded can't be trusted to accurately report on the application it's testing.

The Genuine Problem — Monitoring the Watcher, Not Just What It Watches

ShopEasy's QA agent depends on the Claude API, an MCP server
(Chapter 13), and a real browser instance. If the API starts
returning slower responses, or the MCP server's connection
degrades, the AGENT'S test results become GENUINELY unreliable
— not because ShopEasy's APPLICATION broke, but because the
TESTING SYSTEM itself is COMPROMISED. Monitoring the
APPLICATION alone completely misses this.

🧠 Think About It

Why is it genuinely important to distinguish "the application is broken" from "the testing system is degraded" as two separate possible explanations for a bad result? These call for completely different responses — an application problem needs Chapter 8's own investigation into ShopEasy's code; a testing-system problem needs investigation into the Claude API, the MCP server, or the browser infrastructure. Conflating them risks either chasing a phantom application bug that doesn't exist, or worse, dismissing a genuine application problem as "probably just the testing system acting up again" when it's actually real.

⚠️ Common Mistake

Monitoring only the application under test, assuming the testing system itself is a fixed, reliable constant that never needs its own observation. This page's own example shows a genuinely real failure mode — the testing system degrading independently of the application it tests — that application-only monitoring completely misses.

💡 Quick Tip

Running this page's health check periodically and independently of actual test execution — not just inferred from test results — provides a genuinely cleaner signal, since a degraded testing system might still produce passing tests some of the time, masking the underlying issue if you only ever look at pass/fail rates.

Best Practices

  • Monitor the testing system's own health — API latency, connectivity, infrastructure reliability — as a genuinely separate concern from application health.
  • Treat test results from a period of degraded testing-system health with appropriate suspicion, rather than trusting them at face value.
  • Run system-health checks independently of actual test execution, since inferring system health purely from test pass/fail rates can mask a genuine underlying degradation.

🎯 Key Takeaway

  • The AI testing system's own health — API latency, MCP connectivity, browser reliability — is a genuinely separate concern from the application it's testing.
  • A degraded testing system can produce unreliable results even when the application itself is completely healthy, and vice versa.
  • Distinguishing these two categories correctly determines whether an investigation should point at Chapter 8's application-focused techniques or at the testing infrastructure itself.

How would you EXTEND this page's health CHECK to distinguish a GENUINELY DEGRADED API from ONE that's simply EXPERIENCING normal, EXPECTED variance in RESPONSE time?▾

A GENUINELY useful extension APPLIES the SAME statistical BASELINE-and-outlier APPROACH this COURSE has USED consistently SINCE Chapter 7 and CHAPTER 9 — COMPARING a NEW reading AGAINST a HISTORICAL distribution, RATHER than a SINGLE fixed THRESHOLD.

def check_api_latency_with_baseline(recent_latency_readings,
                                       historical_readings):
    from statistics import mean, stdev
    if len(historical_readings) < 20:
        return "Insufficient history to establish a reliable baseline yet."

    baseline_mean = mean(historical_readings)
    baseline_stdev = stdev(historical_readings)
    current_mean = mean(recent_latency_readings)

    if current_mean > baseline_mean + (3 * baseline_stdev):
        return (f"GENUINELY concerning: current latency "
                f"{current_mean:.0f}ms is a statistical outlier "
                f"relative to the established baseline "
                f"{baseline_mean:.0f}ms — worth investigating.")
    return "Current latency is within normal, expected variance."

This DIRECTLY reuses the SAME statistical BASELINE-and-OUTLIER technique FROM Chapter 7's TREND detection and CHAPTER 9's flaky-TEST detection — RATHER than a SINGLE, FIXED "4200ms is BAD" threshold (WHICH might be TOO sensitive OR too LENIENT depending on GENUINE, normal VARIANCE), COMPARING against an ESTABLISHED historical DISTRIBUTION provides a GENUINELY more RELIABLE way to DISTINGUISH real DEGRADATION from ORDINARY, expected FLUCTUATION.
