AI Flaky Test Detection

Prerequisites: Detecting Failure Patterns

What is this?

The previous page's deterministic math produces a clean list of flaky candidates. This page is about the genuinely fuzzy work that math can't do — interpreting borderline statistics, and checking whether failures within a "flaky" candidate genuinely look alike or actually represent several different problems bundled together.

A Genuinely Borderline Case the Math Alone Can't Resolve

Test A: 6 runs under identical conditions, 1 fail (fail_rate ≈ 0.17)
Test B: 6 runs under identical conditions, 3 fails (fail_rate = 0.5)

Both technically satisfy "0 < fail_rate < 1" — the previous
page's function flags BOTH as flaky candidates. But are they
EQUALLY worth a human's attention right now, with only 6 data
points each? The raw math alone doesn't say.

Reasoning Over the Borderline Case

def assess_flaky_confidence(candidate, client):
    prompt = f"""A test shows this flakiness pattern:
{candidate}

Given the SAMPLE SIZE and FAIL RATE, how confident should we
genuinely be that this represents real flakiness rather than
statistical noise from a small sample? Would you recommend
gathering more data before treating this as confirmed?"""
    result = client.messages.create(
        model="claude-sonnet-4-6", max_tokens=400,
        messages=[{"role": "user", "content": prompt}]
    )
    return result.content[0].text
# A genuinely useful response for Test A (1 fail out of 6):
"With only 6 runs and 1 failure, this is a GENUINELY small
sample — a single fluke among 6 runs produces a similar-looking
rate to what real, low-grade flakiness would show. I'd recommend
gathering at least 15-20 more runs before treating this as
confirmed, rather than acting on it now."

# For Test B (3 fails out of 6):
"A 50% fail rate, even from a modest sample, is a genuinely
strong, unlikely-to-be-coincidental signal — worth treating as
a confirmed flaky candidate now, though more data would still
strengthen confidence further."

Checking Whether "Flaky" Failures Genuinely Look Alike

def check_failure_similarity(failure_messages, client):
    prompt = f"""These are the failure messages from a test
flagged as flaky, across its recent failing runs:

{failure_messages}

Do these failures genuinely look like the SAME underlying
issue occurring inconsistently, or do they look like SEVERAL
DIFFERENT problems that happen to affect the same test?"""
    result = client.messages.create(
        model="claude-sonnet-4-6", max_tokens=400,
        messages=[{"role": "user", "content": prompt}]
    )
    return result.content[0].text
# A genuinely important finding this can catch:
"Two of these three failures show 'Timed out waiting for
cart-total text' — consistent with a single, recurring race
condition. But the THIRD shows 'Network error: ECONNRESET' —
a genuinely DIFFERENT kind of failure. This test may actually
have TWO separate issues bundled under one 'flaky' label: a
race condition AND an occasional, unrelated network problem."

🧠 Think About It

Why might treating "3 fails out of 6 runs" as a single, uniform flakiness statistic obscure a genuinely important finding, as this page's failure-similarity example shows? A fail rate alone tells you HOW OFTEN a test fails — it says nothing about WHETHER every failure shares the same underlying cause. Two genuinely different problems, each occurring rarely, can combine to produce the exact same aggregate fail rate as one problem occurring more often — but they need completely different fixes, which the aggregate statistic alone can never reveal.

⚠️ Common Mistake

Treating every test flagged by the previous page's deterministic function as equally confirmed and equally uniform in cause. This page's two examples show real, genuine value in reasoning further — about sample-size confidence and about whether failures genuinely share a cause — beyond what the raw fail-rate number alone communicates.

💡 Quick Tip

When checking failure-message similarity, it's genuinely useful to include the ACTUAL error text from each failing run, not just a summary — subtle differences (a timeout versus a connection error, as this page's example shows) are exactly the kind of detail a summary might accidentally flatten away.

Best Practices

  • Reserve AI reasoning specifically for genuinely fuzzy questions — sample-size confidence, failure-message similarity — not for recomputing what deterministic code already handles exactly.
  • Check whether failures within a "flaky" candidate genuinely share a cause before assuming a single fix will resolve all of them.
  • Treat borderline statistical cases (small samples, moderate fail rates) as needing more data or careful judgment, not an automatic confirmed classification.

🎯 Key Takeaway

  • AI reasoning adds genuine value specifically where the previous page's deterministic math leaves real ambiguity — sample-size confidence and cause similarity.
  • A single aggregate fail rate can obscure multiple genuinely different underlying problems bundled under one "flaky" label.
  • This page's two reasoning tasks are deliberately fuzzy, complementing rather than duplicating the previous page's exact arithmetic.

Interview Questions

A team's dashboard shows a test as "flaky, 50% fail rate" based on 3 fails out of 6 runs. A teammate immediately assigns someone to fix it. What would you want to check first, using this page's own reasoning?▾

I'd want to check whether the 3 failures genuinely share the same underlying cause before assigning a fix — this page's own failure-similarity example shows a "flaky" test can actually represent two genuinely separate problems bundled under one statistic.

Why checking similarity matters BEFORE assigning a fix:
If the 3 failures are ACTUALLY two different issues (say, 2
  race-condition timeouts and 1 unrelated network error, per
  this page's own example), assigning ONE person to "fix the
  flaky test" might result in them fixing ONLY the race
  condition, while the SEPARATE network issue remains,
  continuing to cause occasional failures that get
  MISATTRIBUTED to "the fix didn't fully work."

The genuinely correct first step:
Run failure-message similarity analysis FIRST — if it reveals
  TWO distinct issues, this should become TWO separate,
  properly-scoped fixes, not one undifferentiated "fix the
  flaky test" assignment that might only address half the
  actual problem.

This is exactly the value this page's second reasoning task adds — a single aggregate statistic invites treating the underlying problem as more uniform than it might actually be, and checking BEFORE assigning work avoids a genuinely common, real inefficiency.

Why does this page recommend gathering MORE data for Test A (1 fail out of 6) before treating it as confirmed, while treating Test B (3 fails out of 6) as reasonably confirmed already?▾

The genuine difference is how UNLIKELY each pattern would be to occur purely by chance from a stable, non-flaky test — a 50% fail rate is a much stronger signal than roughly 17%, even from the same small sample size.

Why 1-out-of-6 is GENUINELY more ambiguous:
A perfectly STABLE test occasionally producing ONE unlucky
  failure out of 6 runs (due to some entirely unrelated,
  genuinely rare fluke) isn't implausible — small samples
  naturally have more RANDOM VARIATION, making a single
  failure less definitively distinguishable from noise.

Why 3-out-of-6 is a GENUINELY stronger signal, even at the
SAME sample size:
A 50% fail rate is a much LARGER deviation from "consistently
  stable" — it's considerably LESS likely to occur purely by
  chance in a genuinely non-flaky test, making it reasonably
  treated with more confidence even without additional data,
  though (as this page notes) more data would still help.

This is a genuinely important, practical distinction — sample size and effect size (how far the observed rate is from 0% or 100%) both matter for how confident a conclusion should be, and treating every "0 < fail_rate < 1" result with identical confidence, regardless of these factors, would be a real oversimplification.

Explain why this page's assess_flaky_confidence prompt asks specifically about "sample size and fail rate" together, rather than just asking "is this test flaky?"▾

Asking the specific, structured question forces genuine reasoning about statistical confidence, rather than inviting a simple yes/no that could collapse a genuinely nuanced, borderline situation into an overconfident binary answer.

A vague prompt: "is this test flaky, yes or no?"
Risks producing an OVERCONFIDENT binary answer even for a
  genuinely borderline case like Test A (1 fail out of 6) —
  forcing a decision the underlying evidence doesn't actually
  support with high confidence yet.

This page's ACTUAL, structured prompt:
Explicitly asks about sample size, fail rate, AND whether MORE
  DATA should be gathered — this structure genuinely invites
  the nuanced, honest "not yet confident, here's why, here's
  what would help" answer this page's OWN example response
  for Test A actually demonstrates.

This mirrors the same structured-prompting principle from Chapter 4 onward — asking for the SPECIFIC reasoning process (confidence given sample size, whether more data would help) produces genuinely more honest, useful answers than a vague binary question that invites false, premature certainty.

Why might it be a mistake to run failure-similarity analysis (this page's second technique) on EVERY flaky candidate, regardless of how many failing runs are actually available to compare?▾

Similarity analysis genuinely needs MULTIPLE failure messages to compare against each other — running it on a candidate with only ONE recorded failure provides nothing to check for similarity against, making the analysis genuinely meaningless in that specific case.

Why similarity analysis NEEDS multiple failures:
"Do these failures look alike" is fundamentally a COMPARISON
  question — it requires AT LEAST two failure instances to
  meaningfully compare. Running this check on a test with
  only ONE recorded failure has nothing to compare it AGAINST,
  making the question itself not genuinely answerable yet.

The practical implication:
Similarity analysis should be reserved for candidates with a
  GENUINELY sufficient number of recorded failures (say, 3 or
  more) — for candidates with fewer, the more relevant question
  is STILL the sample-size confidence question from this page's
  FIRST technique, not similarity, since there isn't yet enough
  failure data to meaningfully compare.

This is a genuinely practical scoping consideration: not every AI reasoning technique this page introduces is relevant to every flaky candidate — matching the RIGHT question to the ACTUALLY available evidence, rather than running every possible check regardless of whether it's genuinely answerable, is itself part of using these tools well.

How would you design a combined workflow using BOTH of this page's techniques together for a newly-flagged flaky candidate with 8 recorded failures?▾

A genuinely sensible order runs similarity analysis FIRST — since it might reveal the "one flaky test" is actually several distinct issues, each of which then needs its OWN separate confidence assessment, rather than treating the combined statistic as one undifferentiated question.

Step 1: Run failure-message SIMILARITY analysis on all 8
  failures.
  Result: "6 of these show the SAME timeout pattern; 2 show a
  DIFFERENT network-error pattern — likely TWO separate issues."

Step 2: SPLIT the analysis accordingly, running confidence
  assessment SEPARATELY for each apparent issue:
  Issue A (timeout pattern): 6 failures out of the test's total
    runs — assess confidence for THIS specific sub-pattern.
  Issue B (network-error pattern): 2 failures out of the
    test's total runs — assess confidence for THIS smaller,
    separate sub-pattern, likely needing MORE data before
    being treated as confirmed on its OWN.

Running similarity analysis first, THEN confidence assessment on each genuinely distinct pattern separately, avoids the mistake the first interview question on this page identified — treating a combined, potentially multi-cause statistic as if it were one uniform phenomenon needing one uniform confidence assessment and one uniform fix.
