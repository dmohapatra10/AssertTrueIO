Log Analysis

Prerequisites: Analyzing Screenshots and Traces for Failure Diagnosis

What is this?

Every evidence source so far has been observable from the CLIENT side — what the browser saw, what request was sent. Server-side logs are genuinely different: they show what the APPLICATION itself was doing internally, information no client-side evidence can ever reveal.

A Scenario Where Client-Side Evidence Genuinely Runs Out

From the previous page's honest escalation example: screenshot
shows the EXPECTED state, trace shows a NORMAL 200 response —
yet the 'Welcome back' text still never appeared. Client-side
evidence is genuinely exhausted; server logs are the next step.

Reading a Real Server Log

def analyze_server_logs(log_entries, request_timestamp, client):
    prompt = f"""Here are server log entries around the time of
a login request at {request_timestamp}, which returned a
normal 200 status code:

{log_entries}

Does anything in these logs suggest the request was processed
DIFFERENTLY than a fully successful login — for example, a
warning, a partial failure, or a fallback path being taken,
even though the HTTP status code itself was 200?"""
    result = client.messages.create(
        model="claude-sonnet-4-6", max_tokens=512,
        messages=[{"role": "user", "content": prompt}]
    )
    return result.content[0].text
# A genuinely real server log excerpt:
[INFO] POST /api/login - credentials validated for user 4821
[WARN] Session cache write failed: connection pool exhausted
[WARN] Falling back to database-only session storage
[INFO] POST /api/login - 200 OK (187ms)
# A genuinely useful finding:
"The login request itself succeeded (credentials validated,
200 returned) — but the log shows a WARNING: the session cache
write FAILED, falling back to database-only storage. This is
consistent with the symptom — if the frontend's 'Welcome back'
text depends on reading session data from the CACHE
specifically, a cache write failure could explain why the
expected UI state didn't render, DESPITE a fully successful
200 response. This points toward a genuine, real infrastructure
issue (cache connectivity) as a plausible root cause — worth
confirming with whoever owns the caching layer."

Why This Genuinely Couldn't Have Been Found Earlier

The STACK TRACE showed only a client-side timeout.
The SCREENSHOT showed only what rendered (or didn't).
The NETWORK TRACE showed only a normal 200 response.

NONE of these client-side sources could show an INTERNAL
server warning about a cache write failure — this information
GENUINELY only exists in the server's own logs, which is
exactly why this evidence source belongs in the diagnostic
process at all, not as a redundant repeat of earlier pages.

🧠 Think About It

Why might a request that returns a completely normal 200 status code still be worth investigating through server logs, rather than treating "200 OK" as proof nothing went wrong on the server side? An HTTP status code reflects whether the SERVER successfully processed and responded to a request at the PROTOCOL level — it says nothing about whether every INTERNAL step the server took while handling that request went smoothly. A server can return a perfectly valid 200 response while having silently taken a degraded fallback path internally, exactly this page's example — the status code and the internal health of the request's handling are genuinely separate questions.

⚠️ Common Mistake

Treating a successful HTTP status code as sufficient confirmation that a request was handled correctly, without checking whether server logs reveal any warnings or fallback behavior that occurred internally despite the successful-looking response.

💡 Quick Tip

When correlating server logs with a specific failure, matching on TIMESTAMP and REQUEST-SPECIFIC identifiers (a request ID, a user ID) is genuinely more reliable than trying to match on vague context alone — this page's example specifically anchors the log search to the request's known timestamp.

Best Practices

  • Reach for server logs specifically when client-side evidence (trace, screenshot, stack trace) has been genuinely exhausted without a clear explanation.
  • Never treat a successful status code alone as proof a request was handled without any internal issue.
  • Anchor log analysis to specific, known identifiers (timestamp, request ID) rather than searching vaguely.

🎯 Key Takeaway

  • Server logs reveal internal application behavior that no client-side evidence source — stack trace, screenshot, or network trace — can ever show.
  • A successful HTTP status code doesn't guarantee every internal step of handling that request went smoothly.
  • Log analysis is genuinely the escalation point when client-side evidence has been exhausted, not a redundant repeat of earlier diagnostic steps.

Interview Questions

A teammate says "the request returned 200, so the server side is fine — the bug must be in the frontend." Using this page's example, is this reasoning sound?▾

Not necessarily — this page's own example shows a 200 response coexisting with a genuine, real server-side issue (a cache write failure) that just happened not to affect the HTTP status code itself, meaning "200 = server side is fine" is too strong a conclusion.

What "200 status code" actually confirms:
The server successfully PROCESSED the request and returned a
  response at the PROTOCOL level — a genuine, real confirmation,
  but SCOPED specifically to that layer.

What it does NOT confirm, per this page's own example:
Whether EVERY internal step (like writing to a session cache)
  ALSO succeeded — the log excerpt shows a WARNING about a
  failed cache write, coexisting with a perfectly normal 200
  response. The teammate's conclusion would have INCORRECTLY
  ruled out a genuine server-side issue based on a status code
  that doesn't actually confirm what they're assuming it does.

The correct response: "200 OK" rules out certain KINDS of server-side failure (a crash, a rejected request) — it doesn't rule out ALL possible server-side issues, exactly the gap this page's log-analysis example is designed to illustrate concretely.

Why does this page argue that log analysis specifically belongs AFTER stack trace, screenshot, and network trace analysis, rather than being checked first for every failure?▾

This mirrors the same cost-ordering principle from the Failure Classification page — client-side evidence is typically cheaper and faster to check, and often sufficient on its own, making server logs a reasonable escalation point rather than a universal first step.

Why CLIENT-SIDE evidence often suffices, without needing logs:
Many failures (a genuinely broken selector, a clear 401
  rejection with a visible error message) are FULLY explained
  by the stack trace, screenshot, and network trace alone —
  reaching for server logs in EVERY case would be unnecessary
  extra work for failures already clearly explained.

Why THIS page's specific example genuinely NEEDED to escalate:
The client-side evidence was GENUINELY exhausted — screenshot
  showed the expected state, trace showed a normal response —
  with NO remaining client-side explanation. ONLY at this
  point does reaching for server logs become the reasonable,
  necessary next step, not a default first move.

This is a direct, consistent continuation of the "check cheaper evidence sources first" principle established on the Failure Classification page — server logs are genuinely valuable, but reserved for when they're actually needed, not checked reflexively for every single failure regardless of whether cheaper evidence already explains it.

Explain why this page's log-analysis prompt specifically anchors to "around the time of a login request at {request_timestamp}" rather than asking the agent to search all recent logs generally.▾

Server logs from a real, active application can be genuinely enormous — anchoring to a specific, known timestamp dramatically narrows what's relevant, exactly the same focused-context principle from the previous page's trace-analysis prompt, now applied to logs specifically.

Why UNANCHORED log search would be genuinely impractical:
A busy production or staging server might log THOUSANDS of
  entries per minute across MANY unrelated requests from OTHER
  users and OTHER features — searching "all recent logs"
  without a specific anchor would bury the relevant few lines
  among a genuinely overwhelming amount of irrelevant content.

Why the TIMESTAMP anchor genuinely solves this:
Knowing the EXACT request time (from the stack trace or
  network trace already gathered) lets the log search focus
  on a NARROW, specific window — exactly the entries that
  could plausibly relate to THIS SPECIFIC failure, not the
  application's entire log history.

This is the same "focused context beats exhaustive context" principle this course has applied consistently since Chapter 2's Reasoning page, now shown solving a genuinely practical, real problem — without an anchor, log analysis at real-world scale would be genuinely impractical, not just less elegant.

Why might it be risky for an agent to have direct, unrestricted access to production server logs, connecting this to Chapter 2's guardrails discussion?▾

Production logs can genuinely contain sensitive information — user data, internal system details, sometimes credentials or tokens accidentally logged — meaning broad log access represents a real, meaningful scope-guardrail concern, not just a technical convenience question.

The GENUINE risk of unrestricted log access:
Server logs, especially from a REAL production system, can
  contain PERSONALLY IDENTIFIABLE information, session tokens,
  or other sensitive data that a QA-focused agent genuinely
  has no legitimate need to access broadly — exactly the kind
  of over-broad tool access Chapter 2's Tools page warned
  against.

A genuinely appropriate scope guardrail:
Restrict an agent's log access to STAGING environment logs
  specifically, and/or to log entries matching ONLY a specific,
  known request ID or timestamp window — narrowing access to
  exactly what's needed for the CURRENT diagnostic task,
  rather than broad, standing access to an entire log stream.

This is a direct, concrete application of Chapter 2's scope-guardrail principle to a genuinely new context — log access is powerful and useful for diagnosis, but exactly the kind of capability that should be deliberately scoped, not granted broadly by default.

How would you design a follow-up investigation specifically to CONFIRM the cache-write-failure hypothesis from this page's example, rather than treating it as a final, settled conclusion?▾

The genuinely rigorous next step is checking whether the SAME pattern (cache write failure warning + missing welcome text) appears CONSISTENTLY across multiple failure instances, not just this one — a single correlated instance is suggestive, not yet confirmed.

A genuinely useful confirmation approach:
1. Check whether OTHER, recent instances of this same test
   failing ALSO show the identical cache-write-failure warning
   in their corresponding server logs — a CONSISTENT pattern
   across multiple instances is much stronger evidence than
   one single correlated occurrence.
2. Check whether the connection-pool-exhaustion issue
   correlates with load — does it happen MORE during periods
   of higher traffic, supporting the "exhaustion" explanation
   specifically?
3. If possible, check whether MANUALLY reproducing a cache
   write failure (in a safe, staging-only way) produces the
   SAME missing-welcome-text symptom, providing direct,
   causal confirmation rather than just correlation.

This connects directly to Chapter 4's validation discipline and Chapter 1's honest-uncertainty principle — a single instance of correlated evidence supports a genuine, reasonable HYPOTHESIS, but treating it as a CONFIRMED root cause without this kind of further verification would overstate what's actually been established.
