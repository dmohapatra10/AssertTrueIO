Converting AI-Generated Scenarios into Automated Tests

Prerequisites: Test Data Generation

What is this?

Every scenario generated so far is genuinely useful, but it's still just text — a description of what to test, not a running test. This page turns one into real, executable Playwright code, directly connecting this chapter's AI generation work to the automation skills taught in this site's own Playwright track.

Starting From a Real, Reviewed Scenario

BOUNDARY CASE (from earlier in this chapter, already reviewed
by a human per this chapter's own standards):

"Order value exactly at the minimum threshold ($50.00) —
should qualify for the discount code SUMMER23 (15% off, min
order $50)."

The Conversion, Step by Step

1. Identify the ACTUAL PAGE ACTIONS needed to set up this state
   (an order totaling exactly $50.00)
2. Identify the ACTUAL ASSERTION that confirms the expected
   outcome (the discount is genuinely applied)
3. Write REAL Playwright code implementing both
import { test, expect } from '@playwright/test';

test('discount code applies at exact minimum order value', async ({ page }) => {
  await page.goto('/cart');

  // Set up an order totaling EXACTLY $50.00 — the actual
  // boundary value from the reviewed scenario
  await page.getByTestId('add-item-49-99').click();
  await page.getByLabel('Quantity').fill('1');
  // (a genuinely realistic cart setup would use real ShopEasy
  // products whose prices combine to exactly $50.00)

  await page.getByLabel('Discount code').fill('SUMMER23');
  await page.getByRole('button', { name: 'Apply' }).click();

  // The actual assertion, directly from the scenario's own
  // stated expected outcome
  await expect(page.getByText('Discount applied: -$7.50')).toBeVisible();
});

This is genuinely ordinary Playwright — exactly what's taught in this site's own Playwright track — the AI-generated scenario simply supplied the WHAT and the expected outcome; converting it into real code is the same skill as writing any other automated test.

Can AI Help With the Conversion Itself Too?

Genuinely, yes — the same LLM that generated the scenario can
draft the Playwright code too, given the scenario text and
enough context about the actual application's real selectors
and structure. But this is EXACTLY where the next page's
validation discipline matters most:

AI-drafted CODE needs the SAME review AI-drafted SCENARIOS
needed — does the assertion actually check what the scenario
claims to verify? Are the selectors genuinely correct for the
real application, not just plausible-looking guesses?

🧠 Think About It

Why might converting a scenario into code be a genuinely good moment to catch problems with the scenario itself, even though the scenario was already reviewed once before conversion? Writing actual, concrete code forces a level of specificity a written scenario doesn't require — "an order exactly at the minimum" is clear as English, but writing the real Playwright code means deciding EXACTLY which products, in exactly what combination, genuinely produce that precise $50.00 total. This concrete specificity sometimes reveals that a reviewed scenario was still subtly ambiguous in a way that only becomes obvious once you try to implement it for real.

⚠️ Common Mistake

Converting a scenario's expected outcome loosely, asserting something adjacent to what the scenario actually specified rather than exactly what it said. If the scenario says "discount applied: -$7.50," the test should assert exactly that specific text or value — not just "some discount text appears somewhere," which would pass even if the wrong amount were shown.

💡 Quick Tip

Keep a direct, traceable link between a converted test and its original scenario — a comment referencing which generated scenario a test implements makes it much easier to later confirm the test still genuinely matches its original intent, especially if the scenario gets revised.

Best Practices

  • Convert a scenario's expected outcome into a precise, specific assertion — not a loose approximation of what it described.
  • Treat the conversion step as a legitimate opportunity to catch remaining scenario ambiguity, not just a mechanical translation exercise.
  • Apply the same review discipline to AI-drafted code that this chapter has applied to AI-drafted scenarios throughout.

🎯 Key Takeaway

  • Converting a scenario into a real test uses exactly the same Playwright skills taught elsewhere on this site — AI generation and conversion don't require a fundamentally different automation skill set.
  • The conversion step itself can reveal remaining ambiguity in a scenario, even one that's already been reviewed once.
  • A converted test's assertions should precisely match the scenario's stated expected outcome, not a loose approximation of it.

Interview Questions

A converted test asserts page.getByText('discount').toBeVisible() for a scenario that specifically stated "discount applied: -$7.50" as the expected outcome. What's wrong with this conversion?▾

This is exactly the "loose approximation" mistake this page warns against — the assertion checks for the word "discount" appearing ANYWHERE, which would pass even if the WRONG amount were displayed, completely failing to verify the specific outcome the scenario actually claimed.

Why the loose assertion is genuinely insufficient:
page.getByText('discount').toBeVisible() would PASS even if
  the page incorrectly showed "Discount applied: -$5.00"
  (the WRONG amount) — as long as the word "discount" appears
  somewhere, this test reports success, completely missing a
  genuine, real bug in the discount CALCULATION itself.

The correct, precise conversion:
await expect(page.getByText('Discount applied: -$7.50')).toBeVisible();
  — this specifically verifies the EXACT amount the scenario
  claimed, catching a wrong-calculation bug the loose version
  would silently let through undetected.

The fix directly follows this page's own standard: convert the scenario's PRECISE stated expected outcome into an equally precise assertion, not a vague approximation that happens to be easier to write.

Why does this page argue that converting a scenario to code can reveal ambiguity the scenario review process already missed?▾

Because writing real code demands a level of concrete specificity that reviewing English text doesn't force — a scenario can sound completely clear in prose while still leaving genuinely open questions that only surface once you try to implement it exactly.

The scenario, reviewed and approved as clear:
"An order exactly at the minimum threshold ($50.00)."

What implementing this ACTUALLY requires deciding:
Which SPECIFIC products, in what combination, genuinely sum
  to exactly $50.00? Is this a single item priced at $50.00
  exactly, or multiple items totaling that amount? Does this
  matter for the test's actual validity? The scenario's REVIEW
  never had to answer this, since English doesn't force this
  level of concrete specificity — but the ACTUAL CODE does.

This is a genuinely valuable, real property of the conversion step — it's not just mechanical translation, it's an additional layer of forced precision that can catch gaps a purely textual review might reasonably miss.

Why does this page suggest keeping a traceable comment linking a converted test back to its original generated scenario?▾

Because a test's code and its original intent can genuinely drift apart over time — someone might later modify the test's implementation without realizing it's no longer accurately testing what the original scenario specified, and a traceable link makes this drift much easier to catch.

Without a traceable link:
Months later, a developer modifies this test (perhaps to fix
  a flaky selector), and in the process, subtly changes what
  it actually asserts — with NOTHING connecting it back to the
  original scenario's INTENT, there's no easy way for anyone
  to notice the test has drifted from what it was meant to verify.

WITH a traceable link:
// Implements: Boundary case — order exactly at $50 minimum
  A reviewer modifying this test later has an immediate,
  concrete reference point to check against — "does my change
  still genuinely match THIS specific scenario's original
  intent" becomes a direct, answerable question, not a vague
  guess based on the test's current code alone.

This is a genuinely practical habit that pays off specifically over TIME, as tests get modified and maintained — the traceability cost is small (one comment), but the value compounds every time someone needs to verify a test still matches its original, intended purpose.

The page suggests AI can help draft the Playwright code itself, not just the scenario. Why does this page treat that possibility cautiously, rather than as an unambiguous additional time-saver?▾

Because AI-drafted code introduces the exact same category of risk as AI-drafted scenarios — plausible-looking output that might not actually be correct — and this risk doesn't disappear just because the output happens to be code instead of English text.

The GENUINE risk with AI-drafted Playwright code specifically:
A plausible-looking selector, like page.getByTestId('add-item-
  49-99'), might not actually correspond to anything real on
  the ACTUAL ShopEasy page — the AI is GUESSING at a
  reasonable-looking selector based on the scenario's own
  text, not verifying against the real, live application.

Why this matters MORE than it might for scenario text:
A wrong SCENARIO description is caught easily by a human
  reading it. A wrong SELECTOR in generated code might not
  fail loudly and obviously — it could silently target the
  WRONG element, or fail in a way that's genuinely harder to
  immediately recognize as "the AI guessed wrong" versus
  "there's a real bug in the application."

This is exactly why the page explicitly connects this risk to the NEXT page's validation discipline — AI-assisted code generation is genuinely useful, but treating its output as automatically correct, without the same review rigor applied to scenarios, would be a real, inconsistent double standard.

How would you explain the relationship between this chapter's test generation work and Chapter 3's QA agent to someone confused about how they're different?▾

They solve genuinely different problems that happen to both use an LLM — Chapter 3's agent EXECUTES a task autonomously against a real, live application; this chapter's generation work DRAFTS scenarios and code that a human then reviews and typically runs through traditional, deterministic automation, not an agent's own live reasoning loop.

Chapter 3's QA agent:
Given a GOAL, it REASONS in real time against the REAL, live
  application, deciding its own next actions as it goes —
  genuinely autonomous EXECUTION, with real-time adaptability.

THIS chapter's test generation:
Given a REQUIREMENT (just text, no live application involved
  at generation time), it DRAFTS scenarios and code — a human
  REVIEWS this draft, and the RESULTING test typically runs as
  ORDINARY, deterministic Playwright automation (like this
  page's own converted example) — no agent reasoning happens
  at TEST-RUN time at all, just at DRAFT-GENERATION time.

The genuinely useful distinction: Chapter 3's agent is autonomous at RUN TIME; this chapter's generation is AI-ASSISTED at DRAFTING TIME, producing something that then runs the traditional, deterministic way — two different, complementary uses of AI in a real QA practice, not competing or redundant approaches.
