What is this, and how it differs from Chapter 8

Chapter 8 went DEEP on ONE failure — stack trace, screenshot, network trace, logs, a full root-cause investigation. That's genuinely too expensive to do for every failure in a pipeline run with twenty failures at once. This page is about a faster, first-pass question: given MANY failures, which ones need a human's attention RIGHT NOW, and which can wait?

A Genuine, Fast Triage Pass

def triage_pipeline_failures(failures, known_flaky_tests, client):
    triaged = {"urgent": [], "likely_known": [], "needs_review": []}
    for failure in failures:
        if failure["test_name"] in known_flaky_tests:
            # Chapter 9's OWN flaky-test detection, reused directly
            # — a CHEAP, deterministic check, no reasoning needed
            triaged["likely_known"].append(failure)
            continue
        if failure["stage"] == "e2e" and "checkout" in failure["test_name"]:
            # A CHEAP, RULE-based signal: checkout failures are
            # BUSINESS-critical, per Chapter 9's OWN importance-
            # weighting principle — flag URGENT without waiting
            # for a full investigation
            triaged["urgent"].append(failure)
            continue
        triaged["needs_review"].append(failure)
    return triaged

🧠 Think About It

Why does this triage function reuse Chapter 9's known-flaky-tests list rather than re-running flakiness detection from scratch for every pipeline failure? Chapter 9's detection process is itself genuinely expensive — it requires historical data across many runs, grouped by commit and environment. Triage needs to be fast, a first pass across potentially dozens of failures in seconds. Reusing an already-computed, standing list of known-flaky tests lets triage benefit from Chapter 9's deeper work without repeating it on every single pipeline run — exactly the kind of "don't redo expensive work unnecessarily" principle this course has applied consistently since its early chapters.

⚠️ Common Mistake

Running Chapter 8's full root-cause investigation on every single failure in a pipeline run with many failures, before any triage happens. This is genuinely expensive at scale — triage exists specifically to make Chapter 8's deeper investigation something applied selectively, to failures that genuinely warrant it, not universally to every failure regardless of urgency.

💡 Quick Tip

A genuinely useful triage rule set grows over time as a team learns which cheap signals reliably predict urgency — this page's "checkout tests are urgent" rule reflects real, accumulated knowledge about ShopEasy's business priorities, not a universal rule that would transfer unchanged to a different application.

Best Practices

  • Run a fast, cheap triage pass across all failures in a pipeline run before committing to Chapter 8's deeper investigation for any individual one.
  • Reuse existing, already-computed signals — like Chapter 9's known-flaky-tests list — rather than recomputing expensive analysis for every triage pass.
  • Let triage rules reflect a team's real, accumulated knowledge about business priorities, not generic, one-size-fits-all urgency heuristics.

🎯 Key Takeaway

  • Triage is a fast, first-pass sort across many simultaneous failures, genuinely different from Chapter 8's deep, single-failure root-cause investigation.
  • Reusing existing signals — like Chapter 9's flaky-test detection — lets triage be fast without repeating expensive analysis for every pipeline run.
  • Triage determines WHICH failures deserve Chapter 8's deeper investigation, making that expensive process selective rather than universal.

How would you extend this page's triage function to flag a failure as URGENT if it's a GENUINELY new failure — one that's NEVER been seen BEFORE in this test's HISTORY — REGARDLESS of which STAGE or AREA it's in?▾

A GENUINELY useful ADDITIONAL rule checks whether THIS test has EVER failed BEFORE, using HISTORICAL data — a COMPLETELY novel FAILURE (NEVER seen BEFORE) is ARGUABLY worth URGENT attention REGARDLESS of business AREA, since it COULD represent a GENUINELY new, UNDIAGNOSED problem.

def triage_pipeline_failures_v2(failures, known_flaky_tests,
                                    historical_pass_rates):
    triaged = {"urgent": [], "likely_known": [], "needs_review": []}
    for failure in failures:
        if failure["test_name"] in known_flaky_tests:
            triaged["likely_known"].append(failure)
            continue
        if failure["test_name"] not in historical_pass_rates:
            # NEVER seen this test FAIL before — a GENUINELY
            # NOVEL failure, worth URGENT attention regardless
            # of business area, since it could be a REAL, NEW
            # problem no existing rule ACCOUNTS for
            triaged["urgent"].append(failure)
            continue
        if failure["stage"] == "e2e" and "checkout" in failure["test_name"]:
            triaged["urgent"].append(failure)
            continue
        triaged["needs_review"].append(failure)
    return triaged

This GENUINELY extends THIS page's TRIAGE logic with an IMPORTANT, ADDITIONAL signal — business CRITICALITY (the ORIGINAL checkout RULE) and NOVELTY (this NEW addition) are TWO genuinely DIFFERENT, both-VALID reasons a FAILURE might WARRANT urgent ATTENTION, and a MATURE triage SYSTEM should ACCOUNT for BOTH, rather than RELYING on JUST ONE kind of SIGNAL to DETERMINE what's GENUINELY worth a HUMAN'S immediate FOCUS.
