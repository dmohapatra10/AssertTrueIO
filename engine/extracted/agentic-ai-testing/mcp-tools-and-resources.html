MCP Tools and Resources

Prerequisites: MCP Client and Server

What is this?

An MCP server can expose two genuinely different kinds of capability — tools, which the client invokes to DO something, and resources, which the client reads to GET something. Conflating these leads to a genuinely worse server design.

Tools — Actions With Real Effects or Computation

@mcp.tool()
def run_smoke_test(environment: str) -> dict:
    """Runs the ShopEasy smoke test suite against the given
    environment ('staging' or 'production') and returns pass/fail
    counts. This ACTUALLY EXECUTES tests — has real side effects
    and takes real time."""
    # ... actually runs pytest, or similar ...
    return {"passed": 42, "failed": 1}

Resources — Data the Client Can Read

@mcp.resource("shopeasy://policies/return-policy")
def get_return_policy() -> str:
    """The current, authoritative ShopEasy return policy text."""
    with open("policies/return_policy.md") as f:
        return f.read()

Notice the genuine difference: run_smoke_test DOES something (executes real tests, takes real time, has real effects); get_return_policy just RETURNS existing data — closer to a read-only lookup than an action.

Why the Distinction Is Genuinely Consequential

A CLIENT reasoning about WHEN to call each of these should
GENUINELY treat them differently:

Calling get_return_policy MULTIPLE times is CHEAP and SAFE —
it's just a READ, with NO side effects, NO real cost beyond
the LOOKUP itself.

Calling run_smoke_test MULTIPLE times is GENUINELY expensive
and potentially DISRUPTIVE — it ACTUALLY EXECUTES tests
against a REAL environment EACH time, exactly the kind of
"real side effect" Chapter 2's TOOLS discussion warned needs
GENUINE consideration before REPEATED, casual use.

🧠 Think About It

Why might exposing something that's genuinely just data — like the return policy — as a TOOL instead of a RESOURCE lead to worse client behavior, even though a tool CAN technically just return static text? If a client's reasoning treats every tool call as potentially having real cost or side effects (a genuinely reasonable default, given Chapter 2's own warnings), it might unnecessarily hesitate to call get_return_policy repeatedly, or batch its calls awkwardly to minimize invocations — genuinely unnecessary caution for something that's actually a cheap, safe, read-only lookup. The resource/tool distinction lets a client reason correctly about cost and safety without needing to inspect each capability's actual implementation.

⚠️ Common Mistake

Exposing every capability as a tool, regardless of whether it performs a genuine action or simply returns existing data. This collapses a real, useful distinction that helps a client reason correctly about cost, safety, and repeatability.

💡 Quick Tip

A genuinely useful test for whether something belongs as a tool or a resource: "if I called this ten times in a row with the same input, would anything bad happen, or would I just get the same data back ten times?" The latter is a resource; the former is very likely a tool.

Best Practices

  • Expose genuine actions — anything with real side effects, real cost, or real execution time — as tools.
  • Expose genuine, static or lookup-style data as resources, not tools, so clients can reason correctly about repeatability and cost.
  • Use the "ten times in a row" test to decide which category a new capability genuinely belongs in.

🎯 Key Takeaway

  • Tools represent genuine actions with real effects or cost; resources represent genuine, readable data with no meaningful side effects.
  • This distinction lets a client reason correctly about repeatability and cost without needing to inspect each capability's actual implementation.
  • Exposing data as a tool when it should be a resource can lead to unnecessarily cautious or awkward client behavior.

A client's reasoning might treat repeated catalog lookups with the same caution Chapter 2 recommends for genuine tool actions — unnecessarily hesitating to call it multiple times, or trying to minimize calls, when the catalog is genuinely just static data safe to read as often as needed.

What EXPOSING the catalog as a TOOL might CAUSE:
A client REASONING about efficiency might THINK "I shouldn't
  call THIS tool REPEATEDLY, since tool calls MIGHT have real
  cost or SIDE EFFECTS" — even though get_product_catalog is
  ACTUALLY just a SAFE, cheap, READ-ONLY lookup with NO
  genuine downside to CALLING it AS OFTEN as needed.

What EXPOSING it as a RESOURCE would communicate INSTEAD:
The RESOURCE category ITSELF signals "this is DATA, safe to
  READ freely" — letting the CLIENT'S reasoning CORRECTLY
  treat it as CHEAP and REPEATABLE, WITHOUT needing to
  INSPECT the underlying IMPLEMENTATION to figure THIS out.

This is exactly this page's own core argument made concrete — the CATEGORY itself (tool vs. resource) carries GENUINE, useful information for a CLIENT'S reasoning, and MISCATEGORIZING something UNDERMINES that signal, even when the UNDERLYING implementation happens to be HARMLESS either way.

Why does this page argue run_smoke_test genuinely belongs as a tool, using the "ten times in a row" test specifically?▾

Applying the test directly: calling run_smoke_test ten times in a row would ACTUALLY EXECUTE the full test suite ten SEPARATE times — real, repeated cost and real, repeated time, clearly failing the "just get the same data back" bar the test uses to identify resources.

Applying THIS page's OWN test DIRECTLY:
"If I called run_smoke_test TEN times in a row... would
  anything BAD happen?" — YES: ten SEPARATE, REAL test-suite
  EXECUTIONS, each taking REAL time and consuming REAL
  resources against a REAL environment. This is CLEARLY an
  ACTION with GENUINE cost, not a SAFE, repeatable LOOKUP.

Contrasting with get_return_policy, PASSING the SAME test:
Calling IT ten times would JUST return the SAME text content
  ten times — NO real cost beyond the TRIVIAL lookup itself,
  CLEANLY fitting the RESOURCE category instead.

This is a genuinely useful, PRACTICAL way to APPLY the tool-vs-resource DISTINCTION to a NEW, UNFAMILIAR capability — rather than reasoning ABSTRACTLY about "is this an action," the CONCRETE "ten times in a row" test gives a QUICK, RELIABLE way to CHECK which category something GENUINELY belongs in.

Why might a capability that SEEMS like a simple lookup — like "get current inventory count for a product" — actually belong as a TOOL rather than a resource, despite superficially resembling get_return_policy?▾

Applying the "ten times in a row" test carefully reveals a genuine difference — if checking inventory involves a REAL, possibly EXPENSIVE query against a LIVE, FREQUENTLY-CHANGING system (unlike the STATIC return-policy text), repeated calls might carry GENUINE, real cost or even risk of INCONSISTENT results across calls, unlike a TRULY static resource.

Why get_return_policy CLEANLY fits "resource":
The POLICY text is GENUINELY static — it CHANGES rarely, and
  READING it repeatedly has ESSENTIALLY zero MARGINAL cost or
  RISK of inconsistency between CALLS.

Why "current inventory count" might be LESS clearly a
resource:
INVENTORY data CHANGES FREQUENTLY and in REAL TIME — REPEATED
  calls might hit a LIVE, POSSIBLY rate-limited OR expensive
  database QUERY EACH time, and the VALUE itself might
  GENUINELY DIFFER between TWO calls made MOMENTS apart (unlike
  the return POLICY, which is ESSENTIALLY guaranteed to be
  IDENTICAL across REPEATED reads).

This is a genuinely useful, NUANCED extension of this page's OWN test — "would anything BAD happen" needs to CONSIDER not JUST obvious SIDE EFFECTS, but ALSO genuine COST and CONSISTENCY concerns; a capability that's technically READ-ONLY can STILL be BETTER modeled as a TOOL if it involves GENUINE, real-time computation OR carries a MEANINGFUL cost per CALL, rather than being a TRULY static, CHEAP lookup.

How would you design the ShopEasy QA server to expose BOTH a resource AND a tool for the SAME underlying data — the current smoke-test suite's PASS RATE — serving two genuinely different client needs?▾

A genuinely useful design exposes the LAST KNOWN pass rate as a cheap, resource-style read, while keeping the ACT of running a FRESH smoke test as its own separate, tool-style action — letting a client choose based on whether it needs FRESH data or is fine with the MOST RECENT known result.

@mcp.resource("shopeasy://qa/last-smoke-test-result")
def get_last_smoke_test_result() -> dict:
    """The MOST RECENT smoke test result on record (may be
    STALE — does NOT run a NEW test). Cheap, safe to READ
    repeatedly."""
    with open("last_smoke_test_result.json") as f:
        return json.load(f)

@mcp.tool()
def run_smoke_test(environment: str) -> dict:
    """ACTUALLY EXECUTES the smoke test suite AGAINST the given
    environment and returns FRESH results. Has REAL cost and
    takes REAL time — use get_last_smoke_test_result INSTEAD
    if a POSSIBLY-stale, but FREE, result is SUFFICIENT."""
    # ... runs tests, ALSO updates last_smoke_test_result.json ...
    return {"passed": 42, "failed": 1}

This directly applies this page's own distinction to serve TWO genuinely different, REAL client needs — a client that JUST wants a QUICK STATUS check can use the CHEAP resource; a client that SPECIFICALLY needs FRESH, CURRENT results can PAY the REAL cost of the TOOL — exactly the kind of THOUGHTFUL, NUANCED server design this page's underlying distinction is meant to ENABLE.
