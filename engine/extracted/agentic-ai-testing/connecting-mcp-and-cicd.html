@mcp.tool()
def run_capstone_verification(objective: str) -> dict:
    """Runs the full capstone QA agent — multi-surface testing,

    return report

🧠 Think About It

Why does run_capstone_verification return the classification inline, computed within the tool itself, rather than exposing classification as a genuinely separate MCP tool a client would call afterward? This is a real design choice worth examining: keeping classification inside means every caller automatically gets a classified result without needing to know to ask for it — genuinely convenient. The tradeoff, following Chapter 13's own tool-vs-resource reasoning, is that this couples two capabilities (running a test, classifying a failure) into one tool call rather than two independently reusable ones. Either design is defensible; the choice should be made deliberately, not by default.

⚠️ Common Mistake

Treating MCP wrapping as the final step of the capstone, rather than recognizing it as the point where the system genuinely transitions from "something one engineer runs" to "infrastructure other people and systems depend on." This shift carries real implications — Chapter 16's access control and audit trail requirements become genuinely necessary starting exactly here, not as an afterthought.

💡 Quick Tip

Before wiring this MCP server into a real, live pipeline, running Chapter 13's own isolated-tool-testing verification — calling run_capstone_verification directly, without the pipeline, and confirming it behaves correctly — is a genuinely useful sanity check before adding the additional complexity of CI/CD integration on top.
