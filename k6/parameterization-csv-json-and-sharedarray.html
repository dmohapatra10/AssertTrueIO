Parameterization: CSV, JSON & SharedArray

Beginner 8 min read

Prerequisites: Unique Test Data & Avoiding Collisions

What is this?

Generated unique values (from the previous page) work well for data the system doesn't care about the specifics of, like a placeholder email. But some tests genuinely need real, varied external data — a list of actual product IDs, realistic names, valid postal codes. This page covers feeding that kind of data into a test efficiently.

Loading JSON Data

import { SharedArray } from 'k6/data';

const users = new SharedArray('users', function () {
  return JSON.parse(open('./users.json'));
});

export default function () {
  const user = users[__VU % users.length];
  // cycles through the loaded data set based on VU number
}

open() reads a local file at init time; wrapping it in SharedArray (more on why below) makes the parsed data available to every VU without each one loading and parsing the file independently.

Loading CSV Data

import { SharedArray } from 'k6/data';
import papaparse from 'https://jslib.k6.io/papaparse/5.1.1/index.js';

const products = new SharedArray('products', function () {
  return papaparse.parse(open('./products.csv'), { header: true }).data;
});

export default function () {
  const product = products[__ITER % products.length];
}

k6 doesn't parse CSV natively, so a small external parsing library (like papaparse, loaded directly from a URL — a common k6 pattern) handles converting the raw CSV text into usable JavaScript objects, one per row.

Why SharedArray Matters — The Memory Problem It Solves

❌ Without SharedArray — data loaded fresh inside the default function,
   or as a plain array in init code:
   Each of 500 VUs holds its OWN independent copy of the entire data set
   in memory → 500x the actual memory footprint of the raw data

✅ With SharedArray:
   ALL 500 VUs share ONE single copy of the data set in memory
   → the memory footprint stays roughly constant regardless of VU count

This is a genuinely important efficiency concern at real scale — a large data set (thousands of realistic user records, for instance) duplicated once per VU can become a serious memory problem well before any actual load-related bottleneck is reached. SharedArray exists specifically to prevent the load generator itself from becoming the bottleneck, directly connecting to the principle Chapter 12 covers explicitly.

Detailed Example — Cycling Through Data Correctly

const users = new SharedArray('users', function () {
  return JSON.parse(open('./users.json')); // suppose this has 50 users
});

export default function () {
  // Using __VU ensures each VU consistently uses "their" user across iterations
  const user = users[__VU % users.length];

  // Using __ITER instead would cycle through users differently —
  // appropriate when each ITERATION should use fresh, different data,
  // rather than each VU consistently representing the same simulated identity
  const product = products[__ITER % products.length];
}

Whether to index by __VU or __ITER (or a combination) is a deliberate choice depending on what you're modeling — a persistent simulated identity across a VU's whole session (index by __VU) versus fresh data on every single action (index by __ITER).

Real-World Example — A Realistic Login Test Using Real Credentials

const credentials = new SharedArray('credentials', function () {
  return JSON.parse(open('./test-users.json'));
  // [{ "username": "user1", "password": "pass1" }, ...]
});

export default function () {
  const cred = credentials[__VU % credentials.length];

  const response = http.post('https://api.example.com/login',
    JSON.stringify({ username: cred.username, password: cred.password }),
    { headers: { 'Content-Type': 'application/json' } });

  check(response, { 'login succeeded': (r) => r.status === 200 });
}

This is more realistic than a single generated or hardcoded credential — real systems often behave differently for different accounts (different permission levels, different amounts of existing data associated with the account), and testing against a genuinely varied set of real credentials surfaces problems a single test account never would.

❌ Fragile vs. ✅ Recommended

// ❌ Loading and parsing the same file inside the default function —
// happens on EVERY iteration, wastefully, and isn't shared across VUs
export default function () {
  const users = JSON.parse(open('./users.json')); // re-parsed every iteration!
}

// ✅ Loaded once, shared efficiently across every VU
const users = new SharedArray('users', function () {
  return JSON.parse(open('./users.json'));
});
export default function () {
  const user = users[__VU % users.length];
}

Common Mistakes

  • Loading and parsing a data file inside the default function — repeats the expensive parse operation on every single iteration, and prevents any sharing across VUs.
  • Not using SharedArray for a large data set at high VU counts — can cause the load generator's own memory usage to become the actual bottleneck, corrupting results.
  • Indexing data inconsistently (mixing up when to use __VU vs. __ITER) without a deliberate reason, producing a data-cycling pattern that doesn't actually match what the test is trying to model.

Edge Cases

  • A data set smaller than the number of VUs — the modulo pattern (users[__VU % users.length]) correctly wraps around and reuses entries, which may or may not be acceptable depending on whether reused data would itself cause a collision problem covered on the previous page.
  • Very large data files — even with SharedArray's efficiency, an extremely large data set still needs to be loaded once at init time; for genuinely massive data sets, consider whether the test truly needs that much unique data or whether a smaller, well-designed set (combined with the unique-ID generation from the previous page) would serve the same purpose.

Debugging

If a k6 test's own memory usage climbs unexpectedly at high VU counts, check whether any data loading happens inside the default function (re-executed every iteration) or as a plain array outside SharedArray (duplicated per VU) — either pattern can turn the load generator itself into the actual resource constraint.

Best Practices

  • Load and parse external data once, in init code, wrapped in SharedArray whenever the data set is genuinely shared across VUs.
  • Choose __VU vs. __ITER indexing deliberately based on whether you're modeling a persistent simulated identity or fresh data per action.
  • Use real, varied external data (not just generated unique placeholders) when the system's behavior genuinely differs across different real accounts or records.

Practice Exercise

Given a JSON file of 100 realistic customer records, write a k6 script using SharedArray that has each virtual user consistently represent the same customer throughout its whole run (across all its iterations), and explain why __VU rather than __ITER is the correct indexing choice for this specific requirement.

Summary

SharedArray is k6's mechanism for loading external data (JSON, or CSV via a small parsing library) once and sharing it efficiently across every virtual user, rather than each VU independently loading and duplicating the same data in memory. Indexing that shared data by __VU or __ITER is a deliberate modeling choice — persistent simulated identity versus fresh data per action — and getting this efficiency and indexing right is what keeps a data-heavy test from becoming memory-bound on the load generator itself before it ever meaningfully stresses the target system.

Interview Questions

What memory problem does SharedArray specifically solve?▾
Without SharedArray, a data set loaded as a plain array in init code gets duplicated once per virtual user — 500 VUs would each hold their own independent copy of the entire data set, multiplying memory usage by the VU count. SharedArray instead makes one single copy of the data available to every VU, keeping memory usage roughly constant regardless of how many virtual users the test runs.
Why is loading and parsing a data file inside the default function a mistake?▾
The default function runs repeatedly — once per iteration, per virtual user — so loading and parsing a file inside it repeats that expensive operation on every single iteration, wasting resources that could instead be spent generating actual load. Loading the data once, in init code (ideally wrapped in SharedArray), does the expensive work exactly once regardless of how many iterations follow.
What's the practical difference between indexing shared data by __VU versus by __ITER?▾
Indexing by __VU gives each virtual user a consistent data entry across all of its iterations — modeling a persistent simulated identity, like one customer using the system repeatedly. Indexing by __ITER instead cycles through the data set differently on every iteration, appropriate when each individual action should use fresh, different data rather than representing one consistent identity throughout.
Why might a test use real external data (via SharedArray) instead of generated unique placeholder values?▾
Generated placeholder values (like a unique but meaningless email) work fine when the system doesn't care about the specific content of the data. But real systems often behave differently for genuinely different real accounts — different permission levels, different amounts of associated data — and testing against a realistic, varied external data set can surface behavioral differences and problems that a single generated or hardcoded value would never reveal.
How does k6 handle CSV files differently from JSON files when it comes to parsing?▾
k6 doesn't include native CSV parsing — JSON.parse() handles JSON directly, but CSV requires an external parsing library (commonly papaparse, loaded from a URL) to convert the raw CSV text into usable JavaScript objects. Both approaches are typically wrapped in SharedArray afterward for the same efficiency reasons, but the parsing step itself differs based on the source file format.
