Installing k6 & Your First Test

Beginner 8 min read

Prerequisites: What is k6? Architecture & Tool Comparison

What is this?

This page gets k6 running on your machine and walks through a genuinely complete first test, line by line — the goal is a working test you actually understand, not just one you copy-pasted.

Installation

# macOS (Homebrew)
brew install k6

# Windows (Chocolatey)
choco install k6

# Linux (Debian/Ubuntu)
sudo gpg -k
sudo gpg --no-default-keyring --keyring /usr/share/keyrings/k6-archive-keyring.gpg --keyserver hkp://keyserver.ubuntu.com:80 --recv-keys C5AD17C747E3415A3642D57D77C6C491D6AC1D69
echo "deb [signed-by=/usr/share/keyrings/k6-archive-keyring.gpg] https://dl.k6.io/deb stable main" | sudo tee /etc/apt/sources.list.d/k6.list
sudo apt-get update
sudo apt-get install k6

# Verify installation
k6 version

k6 ships as a single, standalone binary — no runtime dependency to install separately (it doesn't need Node.js installed, despite scripts being written in JavaScript), which keeps setup genuinely simple across platforms.

JavaScript/TypeScript Considerations

// This works fine — k6 supports modern JavaScript syntax
import http from 'k6/http';
export default function () {
  const response = http.get('https://test-api.example.com');
}

// TypeScript requires a build step — k6 doesn't execute .ts files directly
// Common approach: write in TypeScript, compile to JavaScript with a bundler
// (like webpack or esbuild) before running with k6

k6 natively executes JavaScript, not TypeScript — if your team prefers TypeScript for its type safety, you'll need a compilation step in your workflow (most commonly via a bundler) that produces plain JavaScript k6 can actually run. This is a real, practical setup decision worth making early, not something to discover partway through building a larger test suite.

Project Structure

k6-tests/
├── scripts/
│   └── smoke-test.js
├── package.json          (optional, if using npm packages/bundling)
└── README.md

A single k6 script can be genuinely just one file to start — there's no mandatory project scaffolding the way some frameworks require. Chapter 11 (Framework Architecture) is where this simple starting structure grows into something built for a real, maintained test suite; don't over-structure a project before you actually need to.

Your First Test, Explained Line by Line

import http from 'k6/http';
import { sleep } from 'k6';

export default function () {
  http.get('https://test-api.example.com/products');
  sleep(1);
}
  • import http from 'k6/http' — k6's built-in HTTP module, giving you get(), post(), and the rest of the HTTP verbs (covered fully in Chapter 5).
  • import { sleep } from 'k6' — a pause function, simulating the natural gap a real user takes between actions (reading a page before clicking the next thing).
  • export default function () { ... } — this is the actual test logic — the code every virtual user repeatedly executes, once per iteration. This specific function is what Chapter 2's next page (the test lifecycle) calls the "VU code."
  • http.get(...) — sends a real HTTP GET request to the target URL and returns a response object (not used further in this minimal example, but this is exactly what later chapters build on for validation).
  • sleep(1) — pauses for 1 second before the function completes and (depending on configuration) potentially runs again.

k6 run is the core command that executes a script — with no additional options, it defaults to a single virtual user running the default function exactly once, which is exactly what this output shows. The metrics reported here (http_req_duration, iterations) are the same core measurements from Chapter 1, now produced by a real tool instead of discussed in the abstract.

Detailed Example — Running With More Than One Iteration

$ k6 run --iterations 5 --vus 1 script.js

This runs the same test five times sequentially with one virtual user — a useful sanity check before scaling up to real concurrent load (which Chapter 4 covers properly), confirming the script itself behaves correctly and consistently across repeated runs before you start reasoning about it under genuine load.

Real-World Example — A Slightly More Realistic First Test

import http from 'k6/http';
import { check, sleep } from 'k6';

export default function () {
  const response = http.get('https://test-api.example.com/products');

  check(response, {
    'status is 200': (r) => r.status === 200,
  });

  sleep(1);
}

Adding check() (covered fully in Chapter 3) turns this from "a request that happens" into "a request that's actually being verified" — confirming the response was genuinely successful, not just that a request was sent. Even a first test benefits from this small addition, since a script that only sends requests without checking anything can silently run against a completely broken endpoint without ever reporting a problem.

❌ Fragile vs. ✅ Recommended

// ❌ A "test" with no verification at all
export default function () {
  http.get('https://test-api.example.com/products'); // succeeds or fails silently
}

// ✅ A test that actually confirms something
export default function () {
  const response = http.get('https://test-api.example.com/products');
  check(response, { 'status is 200': (r) => r.status === 200 });
}

Common Mistakes

  • Writing TypeScript and expecting k6 to run it directly — k6 executes JavaScript; TypeScript needs a compilation step first.
  • Treating a "test" with no check() calls as meaningful — a script that only sends requests without verifying anything can run against a broken endpoint indefinitely without ever reporting a failure.
  • Jumping straight to high concurrency before confirming the script itself works correctly at low, simple settings (like --vus 1 --iterations 1) first.

Edge Cases

  • Testing an endpoint that requires authentication — a first test against a protected endpoint will simply fail with a 401/403 until authentication is added (covered fully in Chapter 9); don't assume the test itself is broken.
  • Running k6 in an environment with restricted outbound network access — k6 needs to reach the target system directly; a corporate proxy or firewall can silently prevent this in ways that look like a script problem but aren't.

Debugging

If k6 run produces no HTTP metrics at all, check whether the request actually succeeded at the network level first — a DNS failure, a connection refusal, or a firewall block can prevent a request from ever completing, which shows up very differently in the output than a script or logic error would.

Best Practices

  • Start with a minimal script (--vus 1 --iterations 1) to confirm correctness before scaling up to real load.
  • Include at least one check() in every test, even a simple one — a test with zero verification isn't really testing anything.
  • Decide on your JavaScript vs. TypeScript workflow early, before a larger test suite makes that decision more disruptive to change.

Practice Exercise

Install k6, write a script that sends a GET request to a public test API of your choice, add a check() confirming the status code is 200, and run it with k6 run --vus 1 --iterations 3 — then read the output and identify which metric corresponds to which part of the request cycle.

Summary

k6 installs as a single standalone binary and executes plain JavaScript directly (TypeScript needs a compilation step). A minimal test is genuinely just a few lines — an HTTP call, an optional check, an optional sleep — run via k6 run. Starting simple (one VU, one iteration) and confirming correctness before scaling up to real concurrency is the right sequence, not the reverse.

Interview Questions

Why can't you run a .ts file directly with k6 run?▾
k6 natively executes JavaScript, not TypeScript — there's no built-in TypeScript compilation step inside k6 itself. A team wanting to write tests in TypeScript needs a separate build step (typically using a bundler like webpack or esbuild) that compiles TypeScript down to plain JavaScript before k6 ever sees the file.
Why does a k6 script with no check() calls still technically "run successfully" even against a broken endpoint?▾
Without a check(), the script is only sending requests, not verifying anything about the responses — k6 will report that requests were sent and how long they took, but it has no instruction to flag whether the response was actually correct. A request that returns a 500 error still "completes" from k6's execution perspective; only an explicit check() call turns that into a meaningful pass/fail signal.
Why is it good practice to run a new k6 script with --vus 1 --iterations 1 before scaling up to real load?▾
This confirms the script itself is logically correct — hitting the right URL, handling the response properly, passing its checks — under the simplest possible conditions. If a script has a bug, it's far easier to diagnose with one virtual user running once than debugging the same issue while genuine concurrent load is also happening, which adds noise and complexity to any investigation.
Why doesn't k6 require Node.js to be installed, even though test scripts are written in JavaScript?▾
k6 ships as a single, standalone binary with its own embedded JavaScript engine (goja) built into the Go executable — it doesn't rely on Node.js or any external JavaScript runtime to execute your script. This is exactly why k6 installation is a single binary install with no separate runtime dependency, unlike many JavaScript-based tools that assume Node.js is already present.
A first test against a protected API endpoint fails immediately. What should you check before assuming the script itself is broken?▾
Check whether the endpoint requires authentication first — a request with no credentials against a protected endpoint will correctly fail with a 401 or 403, which is the API behaving correctly, not a bug in the test script. Authentication is covered separately in a later chapter; a basic first test against a protected resource is expected to fail exactly this way until credentials are added.
