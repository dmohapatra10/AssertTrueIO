Designing Every Test Type From One Script

Beginner 8 min read

Prerequisites: Tags & Environment Variables

What is this?

Chapter 1 defined smoke, load, stress, spike, soak, and regression testing conceptually. This page shows the practical payoff: one well-built script — reusing the realistic shopping journey from Chapter 9 — reconfigured six distinct ways, never rewritten, to serve as every one of those test types.

The Base Script (Unchanged Across All Six)

export default function () {
  ensureLoggedIn();
  group('Shopping Journey', function () {
    browseProducts();
    const productId = searchProducts('wireless headphones');
    if (productId) {
      addToCart(productId);
      checkout();
    }
  });
}

This function never changes below. Everything that follows is a different options block wrapped around this exact same logic.

Smoke Test — Does It Work at All?

export const options = {
  vus: 1,
  iterations: 5,
  thresholds: {
    checks: ['rate>0.99'],
  },
};

A smoke test runs at minimal, almost trivial load — its only job is confirming the script itself is correct and the basic workflow functions, before spending real time and resources on anything bigger. Always run this first; a script with a genuine bug wastes far less time failing here than failing 10 minutes into an expensive stress test.

Load Test — Does It Hold Up at Expected Traffic?

export const options = {
  scenarios: {
    expected_load: {
      executor: 'ramping-vus',
      startVUs: 0,
      stages: [
        { duration: '3m', target: 200 },
        { duration: '15m', target: 200 },
        { duration: '3m', target: 0 },
      ],
    },
  },
  thresholds: {
    http_req_duration: ['p(95)<800'],
    checks: ['rate>0.97'],
  },
};

This is the exact configuration from Chapter 9's final example — 200 VUs, representing genuinely expected peak traffic, sustained realistically. Confirming a known, realistic requirement.

Stress Test — Where Does It Actually Break?

export const options = {
  scenarios: {
    find_the_limit: {
      executor: 'ramping-vus',
      startVUs: 0,
      stages: [
        { duration: '5m', target: 500 },
        { duration: '5m', target: 1000 },
        { duration: '5m', target: 2000 },
        { duration: '5m', target: 4000 },
      ],
    },
  },
  // Deliberately no strict thresholds here — the GOAL is finding where
  // it breaks, not enforcing a pass/fail bar prematurely
};

Same script, pushed far beyond expected traffic in escalating stages — the goal is discovering the actual ceiling, not confirming a known number. Thresholds are often deliberately loose or absent here, since failing is the expected, informative outcome at some point in the ramp.

Spike Test — Does It Survive a Sudden Shock?

export const options = {
  scenarios: {
    sudden_spike: {
      executor: 'ramping-vus',
      startVUs: 0,
      stages: [
        { duration: '30s', target: 50 },   // brief normal baseline
        { duration: '10s', target: 1500 }, // sudden, sharp jump
        { duration: '3m', target: 1500 },  // hold at the spike
        { duration: '30s', target: 50 },   // sudden drop back down
      ],
    },
  },
  thresholds: {
    http_req_failed: ['rate<0.10'], // more lenient — a spike is expected to hurt somewhat
  },
};

The defining feature here is the 10-second jump from 50 to 1,500 — sudden, not gradual, testing resilience to a shock rather than a smooth ramp.

Soak Test — Does It Degrade Over Time?

export const options = {
  vus: 100,
  duration: '4h',
  thresholds: {
    http_req_duration: ['p(95)<800'],
    checks: ['rate>0.97'],
  },
};

Moderate, sustained load — not extreme, but held for hours rather than minutes, specifically to give memory leaks and slow resource exhaustion (Chapter 1) time to actually appear.

Regression Test — Compared Against a Real Baseline

export const options = {
  scenarios: {
    regression_check: {
      executor: 'constant-vus',
      vus: 200,
      duration: '10m',
    },
  },
  thresholds: {
    // Values derived directly from last week's actual measured baseline (Chapter 7)
    http_req_duration: ['p(95)<520'], // last week: 480ms, some buffer
    http_req_failed: ['rate<0.008'],  // last week: 0.5%, some buffer
  },
};

The configuration itself looks like a load test — the distinguishing feature is that its thresholds are deliberately set from a specific historical baseline (Chapter 7's threshold-derivation techniques), specifically to catch a regression relative to last week's real, measured performance, not just a generic pass/fail bar.

Detailed Example — Same Script, Same Checks, Genuinely Different Purpose

Every configuration above ran the IDENTICAL ensureLoggedIn() → browse →
search → cart → checkout logic. What changed each time was purely the
shape and scale of the load, and (for regression) which threshold values
were used. Six genuinely different questions, one script.

Real-World Example — Why Rewriting the Script Six Times Would Be Worse

❌ Six separate scripts: the checkout logic drifts out of sync over time
   — someone updates the smoke test script after an API change, forgets
   the stress test script still uses the old, now-broken request shape.

✅ One script, six configurations: an API change gets fixed in exactly
   one place, and every test type automatically reflects it.

This is the same principle Chapter 3's "reusable functions" and Chapter 11's framework architecture apply at a smaller scale — duplication drifts out of sync; a single source of truth doesn't.

❌ Fragile vs. ✅ Recommended

// ❌ smoke-test.js, load-test.js, stress-test.js — three separate,
// slowly-diverging copies of nearly the same workflow logic

// ✅ workflow.js (the shared logic) + options passed via -e or separate
// config files, all pointing at the same underlying script

Common Mistakes

  • Maintaining separate scripts per test type instead of one script with different configurations — real, ongoing maintenance burden as the underlying workflow evolves.
  • Setting strict thresholds on a stress test — the point is finding the breaking point, not enforcing a premature pass/fail bar before it's found.
  • Skipping the smoke test and going straight to an expensive stress or soak run — wastes real time discovering a basic bug the hard way.

Edge Cases

  • A workflow that genuinely needs different logic for different test types (a stress test that skips a slow, non-essential step to push pure request volume higher) — this is a legitimate exception, but should be a deliberate, documented divergence, not accidental drift.
  • Regression thresholds that go stale — a regression test's thresholds are only as good as how recently they were derived from a real baseline (Chapter 7); revisit them periodically, the same as any threshold.

Debugging

If a stress test never actually finds a breaking point within a reasonable duration, check whether the ramping stages actually reach a high enough target — the same diagnostic principle from Chapter 1's stress-testing coverage, now applied to a script that's otherwise proven correct via its smoke test.

Best Practices

  • Build one well-designed script per real workflow, and reconfigure it via options for each test type — never maintain parallel, slowly-diverging copies.
  • Always run a smoke test first, before any larger, more expensive test type.
  • Keep stress-test thresholds loose or absent — the goal is discovery, not premature pass/fail enforcement.
  • Derive regression-test thresholds from a real, recent baseline, and revisit them periodically.

Practice Exercise

Using the checkout workflow built across this course, write the options configuration for a spike test simulating a flash-sale scenario — normal baseline traffic suddenly jumping tenfold for two minutes before returning to normal — and explain what threshold (if any) would be appropriate for this specific test type.

Summary

A single, well-built script can serve as a smoke, load, stress, spike, soak, or regression test purely through different options configurations — never through separate, parallel copies of the underlying workflow logic. This is the practical realization of Chapter 1's conceptual test-type definitions, Chapter 4's executor mechanics, and this course's repeated emphasis on avoiding duplicated logic, all converging into one deliberate testing strategy built around a single source of truth.

Interview Questions

Why should a smoke test always run before a stress or soak test, rather than jumping straight to the larger test?▾
A smoke test runs at minimal load specifically to confirm the script itself is correct before investing real time and resources into a much larger, longer-running test. If the script has a basic bug, discovering it via a 1-VU, few-iteration smoke test costs almost nothing; discovering the same bug 3 hours into a soak test wastes significant time that could have been avoided.
Why are strict thresholds typically inappropriate for a stress test?▾
A stress test's actual purpose is discovering an unknown breaking point, not confirming a known requirement — expecting it to "pass" a strict threshold contradicts the test's own goal, since failing at some point during the ramp is the informative, expected outcome. Thresholds here are often deliberately loose or omitted, letting the test genuinely find the limit rather than stopping prematurely at an artificial bar.
What's the practical risk of maintaining six separate scripts, one per test type, instead of one script with six configurations?▾
Separate scripts inevitably drift out of sync over time — a change to the actual API or workflow (a new required field, an updated endpoint) gets applied to whichever script someone happens to be updating, while the others silently fall behind and start testing an outdated version of the real workflow. One shared script with different configurations means any change is made in exactly one place and automatically applies to every test type built around it.
What specifically distinguishes a regression test's configuration from a standard load test's configuration, if both might use similar VU counts and durations?▾
The distinguishing feature isn't the load shape — it's that a regression test's thresholds are deliberately derived from a specific, real historical baseline (last week's actual measured performance, for instance), specifically to catch a meaningful regression relative to that known-good point, rather than checking against a generic target the way a standard load test's thresholds typically would.
Why does a spike test's configuration specifically need a sudden, sharp jump rather than the smooth ramp used in a load test?▾
A spike test exists specifically to test resilience to a sudden shock — a flash sale, a viral moment — which is a genuinely different stress on a system than gradually increasing traffic. A smooth ramp gives auto-scaling, connection pools, and caches time to adjust; a sudden jump tests whether the system can handle that adjustment happening almost instantly instead, which only a genuinely sharp, non-gradual jump in the configuration can actually simulate.
