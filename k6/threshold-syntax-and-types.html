Threshold Syntax & Types

Beginner 8 min read

Prerequisites: Thresholds & Performance Criteria overview

What is this?

Every threshold lives inside the thresholds key of the options object, keyed by metric name, with an array of condition strings — this page covers every variation of that syntax you're likely to need.

The Basic Shape

export const options = {
  thresholds: {
    'metric_name': ['condition1', 'condition2'],
  },
};

Each metric can have one or more conditions, all of which must pass for that metric's threshold to be considered passed overall.

Response-Time Thresholds

export const options = {
  thresholds: {
    http_req_duration: ['p(95)<500', 'p(99)<1500'],
  },
};

Multiple conditions on the same metric — here, both p95 and p99 must be under their respective targets. This directly encodes something Chapter 6 established: a healthy p95 alone doesn't guarantee a healthy p99, so checking both catches a problem either alone might miss.

Error-Rate Thresholds

export const options = {
  thresholds: {
    http_req_failed: ['rate<0.01'], // less than 1% failure rate
  },
};

Since http_req_failed is implemented internally as a Rate metric (Chapter 6), its threshold condition uses rate, not a percentile — this is the direct, automated implementation of the error-rate half of a requirement like "error rate should remain below 1%."

Thresholds on Custom Metrics

const ordersCreated = new Counter('orders_created');

export const options = {
  thresholds: {
    orders_created: ['count>1000'], // at least 1000 orders created during the test
  },
};

Thresholds aren't limited to built-in metrics — any custom metric from Chapter 6 (Counter, Rate, Trend, Gauge) can have its own threshold, using whichever condition makes sense for that metric type: count for a Counter, rate for a Rate, percentiles for a Trend.

Percentage-Based Thresholds on Checks

export const options = {
  thresholds: {
    checks: ['rate>0.99'], // at least 99% of all checks must pass
  },
};

k6 automatically tracks a built-in checks metric representing the pass rate across every check() call in the script — this threshold turns "checks are mostly passing" into an explicit, enforced requirement, rather than something only visible by eye in the summary.

Multiple Thresholds Across Different Metrics

export const options = {
  thresholds: {
    http_req_duration: ['p(95)<500'],
    http_req_failed: ['rate<0.01'],
    checks: ['rate>0.99'],
  },
};

A real test typically defines several thresholds together, each covering a genuinely different dimension of health — response time, error rate, and functional correctness (via checks) — exactly the multi-signal analysis Chapter 6 established as necessary, now made into an automated, enforced gate rather than something a human has to remember to check manually.

Abort Conditions — Stopping Early on a Clear Failure

export const options = {
  thresholds: {
    http_req_failed: [{ threshold: 'rate<0.01', abortOnFail: true }],
  },
};

By default, a threshold failure is only reported at the end of the test — the test still runs to completion. Setting abortOnFail: true stops the test immediately once that specific threshold is violated, which is useful for a clearly catastrophic failure (like an error rate spiking far past any reasonable target) where continuing to generate load serves no purpose and only wastes time.

Detailed Example — A Complete, Realistic Threshold Configuration

export const options = {
  scenarios: { /* ... */ },
  thresholds: {
    http_req_duration: ['p(95)<500', 'p(99)<1500'],
    http_req_failed: [{ threshold: 'rate<0.05', abortOnFail: true }],
    checks: ['rate>0.99'],
    order_creation_success: ['rate>0.98'], // custom metric from Chapter 6
  },
};

This encodes several genuinely different requirements at once — tail latency (both p95 and p99), a hard abort condition for a catastrophic error rate, functional correctness via the built-in checks metric, and business-specific correctness via a custom metric. This is what a mature, real threshold configuration actually looks like — not a single number, but several distinct signals enforced together.

Real-World Example — Why Abort Conditions Need to Be Used Carefully

// ❌ An overly aggressive abort condition
thresholds: {
  http_req_duration: [{ threshold: 'p(95)<500', abortOnFail: true }],
}
// A single brief spike early in a ramp-up (before the system has stabilized)
// could abort the ENTIRE test prematurely, before it ever reached its
// actual intended peak load.

abortOnFail is most appropriate for genuinely catastrophic, unambiguous failures (an error rate far beyond any acceptable range) — using it on a response-time threshold during a ramping test risks stopping the test on a transient early-stage fluctuation, before the system and the test itself have actually stabilized at the intended load level.

❌ Fragile vs. ✅ Recommended

// ❌ A single, undifferentiated threshold covering only one dimension
thresholds: { http_req_duration: ['p(95)<500'] }

// ✅ Multiple thresholds covering response time, error rate, and correctness together
thresholds: {
  http_req_duration: ['p(95)<500', 'p(99)<1500'],
  http_req_failed: ['rate<0.01'],
  checks: ['rate>0.99'],
}

Common Mistakes

  • Defining only a response-time threshold, with no corresponding error-rate or correctness threshold — leaving exactly the kind of gap Chapter 6's misleading-analysis examples warned about.
  • Using abortOnFail on a metric prone to early, transient fluctuation — risks aborting a test before it ever reaches its actual intended load level.
  • Forgetting that http_req_failed uses rate, not a percentile syntax — mixing up which condition type applies to which metric.

Edge Cases

  • A threshold on a custom metric that was never actually populated during the test (a Counter that never got incremented, for instance) — worth confirming the custom metric is genuinely being fed data, since a threshold on an empty metric may behave in ways that aren't immediately obvious.
  • Thresholds evaluated per-scenario — in a multi-scenario test (Chapter 4), it's possible to scope certain thresholds specifically to one scenario's metrics rather than the whole test's aggregate, worth considering when different scenarios have genuinely different acceptable performance targets.

Debugging

If a test aborts unexpectedly early, check whether any threshold has abortOnFail: true set, and whether that specific threshold's condition might be prone to a brief, early transient spike before the system and test have both stabilized — this is the most common cause of a test stopping well before its intended duration.

Best Practices

  • Define thresholds across multiple dimensions together — response time, error rate, and functional correctness — not just one in isolation.
  • Reserve abortOnFail for genuinely catastrophic, unambiguous failure conditions, not metrics prone to early transient fluctuation.
  • Use the correct condition syntax for each metric type — percentiles for Trend-based metrics like http_req_duration, rate for Rate-based metrics like http_req_failed and checks, count for Counter-based metrics.

Practice Exercise

Write a complete threshold configuration for a checkout API requiring: p95 response time under 800ms, p99 under 2,500ms, error rate under 2% (with an abort condition if it exceeds 10%), and at least 97% of all checks passing.

Summary

k6 thresholds support response-time percentiles, error rates, custom metric conditions, and pass-rate checks on the built-in checks metric — all combinable into one configuration covering several genuinely distinct dimensions of health at once. Abort conditions can stop a test immediately on a clear, catastrophic failure, but need careful placement to avoid prematurely killing a test over a transient early-stage fluctuation rather than a genuine problem.

Interview Questions

Why might a threshold configuration define conditions on both p95 and p99 for the same metric?▾
A healthy p95 doesn't guarantee a healthy p99 — the two capture different points in the tail of the distribution, and a system can pass one while badly failing the other. Setting thresholds on both catches a tail-latency problem that checking only one percentile might miss entirely, directly applying the percentile literacy established earlier in this course.
Why does the threshold syntax for http_req_failed use rate rather than a percentile-based condition?▾
http_req_failed is implemented internally as a Rate metric — it tracks the percentage of true/false outcomes (failed vs. not failed), not a distribution of numeric values the way http_req_duration does. Percentile syntax (p(95), for instance) only makes sense for Trend-style metrics with a genuine distribution of values; a Rate metric's threshold condition is naturally expressed as a percentage instead.
Why should abortOnFail be used carefully on a response-time threshold during a ramping test?▾
Early in a ramp-up, before the system and the test have both stabilized at the intended load level, response times can briefly fluctuate in ways that don't represent genuine, sustained performance problems. An abort condition triggered by this kind of transient early spike would stop the test before it ever reached its actual intended peak, potentially missing the very data the test was designed to collect.
Why would a real threshold configuration typically include a threshold on the built-in checks metric, not just http_req_duration and http_req_failed?▾
http_req_duration and http_req_failed only capture HTTP-level mechanics — response time and status-code-based failure — neither says anything about whether the response content was actually functionally correct. A threshold on the checks metric enforces that functional check() calls are passing at an acceptable rate, directly addressing the "fast but functionally wrong" gap covered in the previous chapter, which the other two metrics alone cannot catch.
Can a threshold be defined on a custom metric, and if so, what condition syntax would apply to a Counter versus a Trend?▾
Yes — thresholds work on any metric, built-in or custom. A Counter-based threshold uses a count condition (like count>1000, ensuring a minimum number of occurrences), while a Trend-based threshold uses percentile syntax (like p(95)<300, since a Trend tracks a full statistical distribution similar to http_req_duration). The correct syntax depends entirely on which of the four custom metric types (Counter, Gauge, Rate, Trend) is being thresholded.
