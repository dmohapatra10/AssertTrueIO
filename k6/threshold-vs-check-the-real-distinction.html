Threshold vs. Check: The Real Distinction

Beginner 7 min read

Prerequisites: Threshold Syntax & Types

What is this?

Both check() and thresholds involve pass/fail language, and it's genuinely common to conflate them. They serve completely different purposes, working at different levels — this page draws the line precisely.

check() — Per-Request, Never Stops the Test

check(response, {
  'status is 200': (r) => r.status === 200,
});

As covered in Chapter 3: a check() evaluates one specific response, records whether it passed or failed, and the script keeps running regardless — a failed check never stops the test, it's just tallied. A check answers: "did this individual request behave correctly?"

Thresholds — Whole-Test, the Actual Pass/Fail Gate

export const options = {
  thresholds: {
    checks: ['rate>0.99'],
  },
};

A threshold evaluates an aggregate metric across the entire test run, and its result (passed or failed) is what determines the test's overall exit status — the actual signal a CI/CD pipeline acts on. A threshold answers: "across the whole test, was performance and correctness acceptable overall?"

The Relationship — Checks Feed Into Thresholds

Individual checks:  check(r1, {...})  check(r2, {...})  check(r3, {...}) ...
                            ↓                 ↓                 ↓
Aggregated into:              the built-in "checks" metric (a pass rate)
                                        ↓
Thresholded by:              thresholds: { checks: ['rate>0.99'] }

This is the actual connection between the two: every individual check() call contributes to k6's built-in checks metric, and a threshold on that metric is what turns "most individual checks passed" into an enforced, whole-test requirement. Checks are the raw data; a threshold on checks is the aggregate judgment.

Detailed Example — What Each One Actually Controls

export default function () {
  const response = http.post(orderUrl, orderPayload);

  // check(): per-request. Records pass/fail. Script continues either way.
  check(response, {
    'order created': (r) => r.status === 201,
    'correct total': (r) => r.json('total') === expectedTotal,
  });
}

export const options = {
  // threshold: whole-test. Determines final pass/fail exit status.
  thresholds: {
    checks: ['rate>0.98'],           // at least 98% of ALL checks, across the whole run, must pass
    http_req_duration: ['p(95)<500'], // p95 across the whole run must be under 500ms
  },
};

The individual check() calls run thousands of times, once per request, never halting anything. The threshold is evaluated exactly once, at a whole-test level, and its outcome is the one that determines whether the test run as a whole "passed."

Real-World Example — Why You Need Both, Not Just One

❌ Only checks, no threshold:
   Individual pass/fail is recorded, but nothing ever determines whether
   the AGGREGATE result was acceptable — no automated CI/CD signal at all.

❌ Only a threshold on http_req_duration, no checks:
   Speed is enforced, but nothing verifies individual responses are
   actually functionally correct — exactly the "fast but wrong" gap
   from the previous chapter.

✅ Both together:
   checks verify individual correctness; a threshold on the checks metric
   (plus response-time thresholds) turns the aggregate result into an
   automated, enforceable pass/fail gate.

Neither one alone does the complete job — checks without a threshold produce data nobody automatically acts on; a threshold without checks enforces speed while remaining blind to correctness. They're complementary, not substitutes for each other.

❌ Fragile vs. ✅ Recommended

// ❌ Treating checks as if they were the test's pass/fail mechanism
check(response, { 'ok': (r) => r.status === 200 }); // no threshold anywhere
// The test "passes" regardless of how many checks actually failed —
// nothing is actually gating on this data.

// ✅ Checks feeding an explicit threshold that actually gates the test
check(response, { 'ok': (r) => r.status === 200 });
export const options = { thresholds: { checks: ['rate>0.99'] } };

Common Mistakes

  • Assuming a script full of check() calls automatically fails the test if checks fail — without a corresponding threshold, check failures are recorded but never gate anything.
  • Defining thresholds but never using check() at all — leaves speed enforced but functional correctness completely unverified.
  • Confusing "check failed" with "test failed" in conversation or documentation — these are genuinely different events, and conflating them leads to real confusion about what a test result actually means.

Edge Cases

  • A script with checks but a threshold on a completely unrelated metric — technically valid, but the checks' data is being recorded without ever influencing the test's actual pass/fail outcome, which may not be the intended design.
  • A very low check pass-rate threshold (like rate>0.5) — technically valid syntax, but worth questioning whether that's a genuinely intentional, meaningful bar, or an accidentally lenient one that would let a lot of real failures still "pass."

Debugging

If a test "passes" despite an obviously high number of failed checks appearing in the summary, check whether a threshold was actually defined on the checks metric — without one, no amount of individual check failures affects the test's overall pass/fail status, which is often not what someone assumed when writing the checks in the first place.

Best Practices

  • Always pair meaningful check() calls with a corresponding threshold on the checks metric — checks without a threshold produce data nobody automatically acts on.
  • Be precise in language and documentation: "a check failed" and "the test failed" are different events with different implications.
  • Review any custom pass-rate threshold on checks for whether it represents a genuinely intentional bar, not an accidentally lenient default.

Practice Exercise

Given a script with three different check() calls per iteration but no threshold defined anywhere in options, explain precisely what happens to the test's exit status if every single check fails on every single iteration, and what needs to be added to make that scenario actually fail the test.

Summary

check() operates per-request, recording pass/fail without ever stopping the test — it's data collection. A threshold operates on an aggregate metric across the whole test run, and its result is the actual pass/fail signal a CI/CD pipeline acts on — it's the gate. They're connected (individual checks feed the built-in checks metric, which a threshold can then gate on) but not interchangeable, and a real test needs both: checks to verify correctness, and thresholds to turn that verification into an enforced requirement.

Interview Questions

If every check() in a script fails, does the test automatically fail?▾
No — not unless a threshold is explicitly defined on the checks metric (or another metric affected by the failures). check() failures are recorded as data, but a script's execution continues regardless, and the test's overall exit status is determined entirely by whatever thresholds were configured, not by check() results directly.
How does an individual check() call actually connect to a threshold?▾
Every check() call across the whole test contributes to k6's built-in checks metric, which tracks the overall pass rate. A threshold defined on that checks metric (like checks: ['rate>0.99']) is what turns the aggregate of many individual check results into an enforced, whole-test pass/fail requirement — checks generate the raw data, and a threshold judges it in aggregate.
Why would a test with thresholds but zero check() calls still be missing something important?▾
Thresholds without any checks can enforce things like response time and error rate, but have no mechanism to verify that individual responses actually contain correct data — this is exactly the "fast but functionally wrong" gap covered previously. Checks are what verify per-request correctness; without them, a threshold-only test remains blind to that entire category of problem.
What's the practical difference between "a check failed" and "the test failed" as two separate statements?▾
"A check failed" describes a single per-request event recorded during execution — it doesn't by itself determine anything about the test's outcome. "The test failed" describes the aggregate result of threshold evaluation at the end of the run — the actual exit status a CI/CD pipeline would see. A check failing doesn't automatically mean the test failed, and a test can fail due to a threshold violation even when many individual checks passed, depending on exactly which threshold was violated and why.
Why might a team write extensive check() logic but still find their CI pipeline never actually fails a build over performance regressions?▾
This is a common, genuine gap — if no threshold was ever defined on the checks metric (or on any other relevant metric), check failures are recorded and visible in the summary output, but nothing about them actually influences the test's exit code, which is what a CI pipeline checks to decide whether to fail a build. The fix is adding an explicit threshold on the checks metric (and any other metric that matters), turning the already-collected check data into something the pipeline can actually act on.
