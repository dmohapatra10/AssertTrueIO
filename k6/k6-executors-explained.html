k6 Executors Explained

Beginner 9 min read

Prerequisites: Ramping & Stages

What is this?

An executor is the specific algorithm k6 uses to control how virtual users and iterations are scheduled over the course of a test. Everything covered so far (vus+duration, stages) is actually shorthand for one of two default executors — this page covers all four explicitly, including the two that control load by a genuinely different mechanism: arrival rate instead of VU count.

constant-vus — A Fixed Number of Virtual Users

export const options = {
  scenarios: {
    my_test: {
      executor: 'constant-vus',
      vus: 50,
      duration: '5m',
    },
  },
};

This is the explicit form of what vus: 50, duration: '5m' already does behind the scenes — a fixed number of virtual users, each looping through the default function for the full duration. Use this when you genuinely want to control concurrency directly and don't need arrival-rate precision.

ramping-vus — A Changing Number of Virtual Users Over Time

export const options = {
  scenarios: {
    my_test: {
      executor: 'ramping-vus',
      startVUs: 0,
      stages: [
        { duration: '2m', target: 100 },
        { duration: '5m', target: 100 },
        { duration: '2m', target: 0 },
      ],
    },
  },
};

This is the explicit form of the stages configuration from the previous page — ramping the VU count up and down over time. Use this whenever the traffic pattern being modeled genuinely changes over the test's duration, rather than staying flat.

The Key Limitation of VU-Based Executors — VUs ≠ Throughput

50 VUs against a FAST endpoint (100ms response time):
  → each VU can complete ~10 iterations per second → high actual throughput

50 VUs against a SLOW endpoint (2000ms response time):
  → each VU can complete only 0.5 iterations per second → much lower actual throughput

This is the real limitation both constant-vus and ramping-vus share: the number of VUs controls concurrency, but the actual resulting throughput (requests per second) depends entirely on how fast each iteration completes — which itself depends on the very system performance you're trying to measure. If response times degrade during the test, throughput silently drops too, even though the VU count stayed exactly the same.

constant-arrival-rate — A Fixed Throughput, Independent of Response Time

export const options = {
  scenarios: {
    my_test: {
      executor: 'constant-arrival-rate',
      rate: 50,
      timeUnit: '1s',
      duration: '5m',
      preAllocatedVUs: 100,
      maxVUs: 200,
    },
  },
};

This targets exactly 50 new iterations started per second, regardless of how long each iteration actually takes to complete — k6 automatically adds more virtual users behind the scenes (up to maxVUs) as needed to sustain that rate, even if individual iterations are slow. This is the correct executor when the real requirement is a specific throughput target — "handle 50 requests per second" — rather than a specific concurrency level.

ramping-arrival-rate — A Changing Throughput Target Over Time

export const options = {
  scenarios: {
    my_test: {
      executor: 'ramping-arrival-rate',
      startRate: 10,
      timeUnit: '1s',
      preAllocatedVUs: 50,
      maxVUs: 300,
      stages: [
        { duration: '2m', target: 100 },
        { duration: '5m', target: 100 },
        { duration: '2m', target: 0 },
      ],
    },
  },
};

This combines arrival-rate control with the ramping behavior from the previous page — the target throughput itself ramps up and down over time, rather than staying fixed. Use this when the real requirement is a changing throughput target — "ramp up to handling 100 checkouts per second during a flash sale" — rather than a changing VU count.

Detailed Example — Choosing Between VU-Based and Arrival-Rate-Based

Requirement A: "Simulate 500 concurrent users browsing the site."
→ This is fundamentally about CONCURRENCY → use constant-vus or ramping-vus.

Requirement B: "The system must handle 200 checkout requests per second at peak."
→ This is fundamentally about THROUGHPUT → use constant-arrival-rate or ramping-arrival-rate.

Reading a requirement correctly — is it really about how many users are active at once, or about a specific rate of work being completed — is what determines which pair of executors is actually appropriate, independent of whether the load itself is flat or ramping.

Real-World Example — Why Arrival Rate Matters for an SLA-Driven Test

SLA: "The API must sustain 100 requests per second with p95 under 500ms."

Testing this with constant-vus would only approximate 100 RPS if response times happen to stay exactly at whatever level makes the math work out — a real risk, since the whole point of the test is finding out whether response times hold up. constant-arrival-rate tests this requirement far more directly and honestly: k6 actively works to sustain exactly 100 new iterations per second regardless of how the system responds, which is a much more faithful test of the actual SLA being verified.

❌ Fragile vs. ✅ Recommended

// ❌ Using constant-vus to test a specific throughput SLA — an indirect, unreliable proxy
export const options = { vus: 50, duration: '5m' }; // hoping this produces ~100 RPS

// ✅ Using constant-arrival-rate to test throughput directly
export const options = {
  scenarios: {
    sla_test: {
      executor: 'constant-arrival-rate',
      rate: 100, timeUnit: '1s', duration: '5m',
      preAllocatedVUs: 150, maxVUs: 300,
    },
  },
};

Common Mistakes

  • Using a VU-based executor to test a specific throughput requirement — VU count doesn't directly control RPS, since actual throughput depends on response time, which is exactly what you're trying to measure.
  • Setting maxVUs too low for an arrival-rate executor — if response times degrade during the test, k6 needs more VUs to sustain the target rate; too low a ceiling silently prevents the configured rate from actually being achieved.
  • Not distinguishing a concurrency requirement from a throughput requirement before choosing an executor — these call for genuinely different tools.

Edge Cases

  • An arrival-rate test that can't actually sustain its target rate because maxVUs was reached — k6 will report this, and it's a genuine, important finding (the system, or the test's own VU ceiling, can't keep up), not a configuration bug to just silently increase past without understanding why.
  • A VU-based test where response times vary significantly across the run — the resulting throughput will vary correspondingly, which is worth reporting explicitly rather than assuming a fixed VU count implies fixed throughput.

Debugging

If an arrival-rate test isn't achieving its configured rate, check whether maxVUs was hit — k6 reports this explicitly, and it usually means either the system genuinely can't sustain that throughput, or the VU ceiling needs to be raised to give k6 enough headroom to try.

Best Practices

  • Choose VU-based executors (constant-vus, ramping-vus) when the real requirement is about concurrency.
  • Choose arrival-rate executors (constant-arrival-rate, ramping-arrival-rate) when the real requirement is about a specific throughput target, especially for SLA verification.
  • Set maxVUs generously enough on arrival-rate executors that a degrading response time doesn't artificially cap the achievable rate before the system's real limit is reached.

Practice Exercise

For the requirement "the checkout API must sustain 75 orders per second for 10 minutes, even under degraded response times," write the correct k6 executor configuration, and explain why a VU-based executor would be the wrong choice for this specific requirement.

Summary

k6 has two VU-based executors (constant-vus, ramping-vus) that control concurrency directly, and two arrival-rate executors (constant-arrival-rate, ramping-arrival-rate) that control throughput directly, automatically adjusting VU count behind the scenes to sustain a target rate. The deciding factor for which pair to use is whether the real requirement is fundamentally about concurrency or about throughput — VU count and requests-per-second are related but genuinely different things, and testing an SLA-style throughput requirement with a VU-based executor is an indirect, less reliable proxy for what you're actually trying to verify.

Interview Questions

Why doesn't a fixed VU count guarantee a fixed requests-per-second throughput?▾
Throughput depends on how quickly each iteration completes, which depends on response time — the very thing being measured. If response times degrade during a test, each VU completes fewer iterations per second, silently reducing actual throughput even though the VU count never changed. This is exactly why VU count and RPS are related but not interchangeable.
Why would constant-arrival-rate be a better choice than constant-vus for testing a specific throughput SLA?▾
constant-arrival-rate directly targets a specific number of new iterations per second, automatically adding more virtual users behind the scenes as needed to sustain that rate even if individual iterations slow down. constant-vus only indirectly approximates a throughput level, and that approximation breaks down exactly when response times change — which is precisely the scenario an SLA test is meant to probe.
What does it mean if a constant-arrival-rate test reports that it couldn't sustain its configured rate?▾
It typically means the maxVUs ceiling was reached — k6 needed more virtual users to keep up with the target rate as response times slowed, but was capped by the configured maximum. This is a genuine, important finding: either the system truly can't sustain that throughput at that response time, or the test's own VU ceiling needs to be raised to give k6 enough room to actually attempt it.
How does ramping-arrival-rate differ from ramping-vus?▾
ramping-vus changes the number of concurrent virtual users over time according to defined stages; ramping-arrival-rate changes the target throughput (iterations started per second) over time instead, automatically managing however many VUs are needed to hit each stage's rate target. Both use a similar staged structure, but one directly controls concurrency while the other directly controls throughput.
Why might setting maxVUs too low on an arrival-rate executor produce misleading test results?▾
If response times degrade during the test, k6 needs additional virtual users to sustain the configured arrival rate. A maxVUs ceiling that's too low can prevent k6 from actually achieving the target rate — not because the system itself couldn't handle it, but because the test's own configuration artificially capped the resources available to attempt it, which could be misread as a system limitation when it's actually a test configuration limitation.
