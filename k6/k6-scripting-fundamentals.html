k6 Scripting Fundamentals

Beginner 3 min read

Prerequisites: Getting Started with k6

Building Real Scripting Vocabulary

A minimal test is already running. Here's the real scripting vocabulary every k6 test actually uses — every HTTP method you'll need, the functions that give a script structure and meaning, and how to organize code so it doesn't collapse into an unmaintainable pile as it grows. Three focused pages:

  1. Making HTTP Requests: GET, POST, PUT, PATCH, DELETE — every HTTP method, headers, query params, and request bodies
  2. check(), sleep(), and group() — the three functions that give a script real structure and meaning
  3. Organizing k6 Scripts — variables, reusable functions, and how a k6 script differs from an ordinary JavaScript program

How a k6 Script Differs From a Normal JavaScript Program

A k6 script looks like JavaScript, and mostly is — but it runs inside k6's own execution engine, gets re-executed repeatedly by design (once per iteration, per virtual user, not once like a typical script), and its top-level exports (setup, default, teardown) have specific, reserved meanings k6 looks for automatically. Writing k6 scripts well means keeping this repeated-execution model in mind constantly — code that would be perfectly reasonable in a normal one-shot script can be a real problem once it's about to run thousands of times per test.

The Progression Ahead

Simple Script            →  Realistic API Test         →  Reusable API Functions
(one hardcoded request)     (headers, checks, sleep)      (functions shared across
                                                            many tests)

This is the natural growth path nearly every k6 test suite follows, and each of the three pages ahead moves one step further along it — starting with a single request, adding real structure and verification, then extracting that structure into functions reusable across an entire test suite.

Common Mistakes to Watch For

  • Treating a k6 script as a one-shot program — forgetting that the default function runs repeatedly changes what "reasonable" code looks like.
  • Writing a "test" with no check() calls — a script that only sends requests without verifying anything can run against a broken endpoint indefinitely without ever reporting a problem.
  • Copy-pasting the same request logic across many test files instead of extracting it into a reusable function once a pattern repeats.

What You'll Be Able to Do

By the end of the three pages that follow, you should be able to construct any HTTP request k6 supports with the right headers, parameters, and body; verify a response's correctness with check(), pace a script realistically with sleep(), and organize related requests with group(); and structure a growing test file so common logic lives in one reusable place instead of being copy-pasted everywhere it's needed. Start with Making HTTP Requests below.
