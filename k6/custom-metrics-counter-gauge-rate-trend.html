Custom Metrics: Counter, Gauge, Rate, Trend

Beginner 8 min read

Prerequisites: Built-in HTTP Metrics Explained

What is this?

The built-in metrics from the previous page cover HTTP requests thoroughly, but they can't capture something specific to your own test's business logic — like how many times a particular business rule was triggered, or the size of a shopping cart at checkout. Custom metrics fill that gap, and k6 provides four distinct types, each suited to a different kind of measurement.

Counter — A Running Total

import { Counter } from 'k6/metrics';

const ordersCreated = new Counter('orders_created');

export default function () {
  const response = http.post(ordersUrl, orderPayload);
  if (response.status === 201) {
    ordersCreated.add(1);
  }
}

A Counter tracks a running total that only increases — useful for counting occurrences of something across the whole test, like how many orders were successfully created, or how many times a specific business rule was actually triggered.

Gauge — The Current Value

import { Gauge } from 'k6/metrics';

const cartSize = new Gauge('current_cart_size');

export default function () {
  const response = http.get(cartUrl);
  cartSize.add(response.json('items').length);
}

A Gauge tracks the most recently reported value — unlike a Counter, it can go up or down, and it represents a current state rather than an accumulating total. Useful for something like the current size of a cart, the current queue depth, or any value that genuinely fluctuates rather than only accumulating.

Rate — Percentage of True/False Occurrences

import { Rate } from 'k6/metrics';

const businessRuleViolations = new Rate('business_rule_violations');

export default function () {
  const response = http.post(orderUrl, orderPayload);
  businessRuleViolations.add(response.json('discountApplied') && response.json('total') < 0);
}

A Rate tracks the percentage of true values out of everything added to it — http_req_failed is actually implemented internally using this same concept. Useful for tracking the frequency of any specific condition, like how often a particular (potentially problematic) business outcome occurs.

Trend — Statistical Distribution of a Custom Value

import { Trend } from 'k6/metrics';

const cartCalculationTime = new Trend('cart_calculation_time', true);

export default function () {
  const start = Date.now();
  const response = http.get(cartUrl);
  cartCalculationTime.add(Date.now() - start);
}

A Trend tracks a full statistical distribution of a custom value — reporting min, max, average, median, and percentiles, exactly like http_req_duration does automatically for HTTP requests. Useful when you need percentile-level insight into something that isn't itself an HTTP request duration — like the time spent client-side processing a response, or any other custom-measured duration.

Detailed Example — Choosing the Right Type for a Real Scenario

Need: "How many times did a checkout attempt fail due to insufficient stock,
       specifically (not any other kind of failure)?"
→ Counter — this is a running total of a specific occurrence

Need: "What's the current number of items in the average active cart?"
→ Gauge — this is a current, fluctuating value, not an accumulating total

Need: "What percentage of checkout attempts triggered a specific discount
       calculation edge case?"
→ Rate — this is a percentage of true/false occurrences

Need: "What's the p95 time for a specific client-side calculation step
       that isn't itself an HTTP request?"
→ Trend — this needs full percentile-level statistical detail

Each of these four questions genuinely needs a different metric type to answer correctly — using a Counter where a Trend's percentile detail was actually needed, for instance, would give you a total count but nothing about the distribution, missing exactly the kind of tail-latency insight Chapter 1 established as critical.

Real-World Example — A Custom Metric Revealing a Business-Logic Problem

const failedDiscountCalculations = new Rate('failed_discount_calculations');

export default function () {
  const response = http.post(checkoutUrl, cartPayload);
  const discountCorrect = response.json('discount') === expectedDiscount(cartPayload);
  failedDiscountCalculations.add(!discountCorrect);
}
Result: failed_discount_calculations: 3.2%

This is a genuinely business-specific correctness metric that no built-in k6 metric could ever capture — it's tracking whether a particular business calculation is correct, not anything about HTTP request timing or status codes. A 3.2% failure rate here is a real, concrete finding worth investigating, made visible specifically because a custom Rate metric was defined for it.

❌ Fragile vs. ✅ Recommended

// ❌ No custom metrics — only built-in HTTP metrics, missing business-specific insight
export default function () {
  http.post(checkoutUrl, cartPayload); // no visibility into discount correctness at all
}

// ✅ A custom metric capturing exactly what matters for this specific test's goal
const failedDiscountCalculations = new Rate('failed_discount_calculations');
export default function () {
  const response = http.post(checkoutUrl, cartPayload);
  failedDiscountCalculations.add(response.json('discount') !== expectedDiscount(cartPayload));
}

Common Mistakes

  • Using a Counter when a Trend's percentile detail is actually needed — a total count alone hides the same tail-latency problems an average would.
  • Using a Gauge for something that should accumulate — a Gauge only reflects the most recent value, losing history a Counter or Trend would have preserved.
  • Never defining any custom metrics at all, relying purely on built-in HTTP metrics for a test whose actual goal is measuring something business-specific those metrics were never designed to capture.

Edge Cases

  • A Trend metric with a very low sample count — like percentiles generally, a Trend's percentile values need a meaningfully large number of data points to be statistically trustworthy; a Trend fed only a handful of values produces unreliable percentile figures.
  • Multiple custom metrics needed to fully capture one business scenario — a genuinely complex scenario might need a Counter (how many times something happened) alongside a Trend (how long it took when it did) to tell the complete story; don't force everything into a single metric type if the real question has multiple genuinely distinct dimensions.

Debugging

If a test's built-in metrics all look healthy but a known business-logic issue isn't showing up anywhere in the results, check whether a custom metric was actually defined to capture it — built-in HTTP metrics were never designed to know anything about your application's specific business rules, only about the HTTP mechanics of each request.

Best Practices

  • Choose the metric type that matches the actual shape of what you're measuring — accumulating total (Counter), current fluctuating value (Gauge), percentage of occurrences (Rate), or full statistical distribution (Trend).
  • Define custom metrics for anything business-specific the built-in HTTP metrics structurally can't capture.
  • Give custom metrics clear, descriptive names — they'll appear in the summary output exactly as named, and a vague name undermines the whole point of adding custom visibility.

Practice Exercise

For a hotel booking system, design custom metrics to track: (1) how many booking attempts failed due to a room already being taken, (2) the current number of rooms being actively viewed at any moment, and (3) the percentile distribution of how long the price-calculation step takes. Identify which of the four custom metric types fits each.

Summary

k6's four custom metric types each fit a genuinely different shape of measurement: Counter for an accumulating total, Gauge for a current, fluctuating value, Rate for a percentage of true/false occurrences, and Trend for full percentile-level statistical detail on a custom value. Defining the right custom metric is what makes business-specific correctness and behavior visible in a test's results — something the built-in HTTP metrics, by design, were never able to capture on their own.

Interview Questions

What's the key difference between a Counter and a Gauge?▾
A Counter only ever accumulates — it tracks a running total that increases over the test, suitable for counting occurrences of something. A Gauge instead tracks only the most recently reported value, which can go up or down, suitable for representing a current, fluctuating state like queue depth or cart size rather than an accumulating count.
Why would you use a Trend instead of a Counter to measure how long a custom operation takes?▾
A Counter can only tell you how many times something happened, not how long each occurrence took or how that duration was distributed. A Trend captures the full statistical distribution — min, max, average, median, and percentiles — of a custom value, which is essential for spotting the same kind of tail-latency issues (a healthy average hiding a bad p99) that matter for any duration-based measurement, not just HTTP request timing.
Which built-in k6 metric is conceptually implemented using the same idea as a custom Rate metric?▾
http_req_failed — it reports the percentage of requests that failed out of the total, which is exactly the same concept a Rate metric captures for any custom true/false condition. Understanding this connection makes it clearer when a Rate is the right custom metric type: whenever you're tracking what percentage of something meets a specific condition.
Why can't built-in k6 HTTP metrics capture whether a business calculation (like a discount) was correct?▾
Built-in HTTP metrics only know about the mechanics of a request and response — status codes, timing, size — they have no knowledge of your application's specific business logic or what a "correct" response should actually contain. Verifying business-specific correctness requires comparing the actual response against an expected value, which is exactly what a custom metric (often paired with a check()) is designed to capture, since no built-in metric could ever know what counts as correct for your specific business rules.
Why might a Trend metric's reported percentiles be unreliable if it's only fed a handful of data points?▾
This is the same statistical principle covered for percentiles generally — a percentile calculated from a very small sample size is unstable and not genuinely representative, since a single unusual value can swing the reported percentile dramatically. A Trend metric needs a meaningfully large number of recorded values before its percentile output can be trusted the same way http_req_duration's percentiles need a meaningful request volume to be trustworthy.
